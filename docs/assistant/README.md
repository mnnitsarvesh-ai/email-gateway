# AI assistant (chat-based management)

The AI assistant lets an authorized user manage the Email Security Gateway in natural language from the admin portal: a chat panel in the header ("Ask AI", `Ctrl/Cmd+J`) and the full-screen `/assistant` page. Every action the assistant takes is one existing `/api/v1` operation, executed with the user's own credential through the api's own HTTP pipeline, so permissions, tenant scope, MFA, rate limits, validation, masking and audit are exactly those of the portal.

**Status:** step AI-1 (foundation and every eligible **read**, 174 tools) is committed (`cf4b9ca`); step AI-2 (**action confirmations** and 35 mail-operations tools: 31 writes on policies, quarantine, held messages, recipient suppressions and saved views, and 4 side-effect-free policy `POST`s) is committed (`74c7ef4`). Step AI-3 (2026-11-22) is **built and verified locally, not complete** (not committed; CI, the orchestrator gate's full Playwright suite and a real-provider test pending): it adds 47 identity and tenant administration writes (users, roles, departments, API key revocation, domains, notifications, organizations, scan settings, SMTP connectors, webhooks) and the read `api_keys_get`, 257 enabled tools in all (179 reads, 78 writes), with **proposal guards** (nobody changes their own account, roles, MFA or sessions through chat; the assistant cannot change its own enablement or who configures it), **conditional risk escalation** and re-authentication on every role and permission change. The model can only **propose** a write: the user sees a server-authored confirmation card and the write runs only when they confirm it there (high risk also asks for the password and authenticator code). Credentials are never created, shown or rotated through chat. Writes of the security-operations and compliance modules come in AI-4 and AI-5; see [CHAT_IMPLEMENTATION_STATUS.md](CHAT_IMPLEMENTATION_STATUS.md). Not verified: calls to a real LLM provider, Kubernetes, CI ([CHAT_TESTING_REPORT.md](CHAT_TESTING_REPORT.md)).

## Enabling it locally

The local stack runs the deterministic **fake** provider: no LLM API key, no network call. Three switches must be on, plus the permission:

1. Platform: `ASSISTANT_ENABLED=true` and `ASSISTANT_PROVIDER=fake` in the repository `.env` for an api started on the host (`pnpm --filter @email-gateway/api dev`). The api **container** of Docker Compose receives no `ASSISTANT_*` key and runs `NODE_ENV=production`, where the fake is refused; for a container test stack add [tests/portal-e2e/assistant.override.yml](../../tests/portal-e2e/assistant.override.yml) when recreating the api.
2. Organization: a platform operator enables the feature `ai_assistant` (`PUT /api/v1/organizations/{id}/features/ai_assistant` `{ "enabled": true }`, or the organization page in the portal).
3. Tenant: an organization admin (`assistant:configure`) opens **Settings → AI assistant**, ticks the external-processing acknowledgement and turns it on.

Then ask, for example, "show active policies", "what was quarantined today", "journaling status", "Create an inbound policy that quarantines executables" (a confirmation card follows; after confirming it, "publish it"), "invite <address> as security_analyst", "disable user <address>", "add domain <name>" (then "verify it"), or use the fake's directives `/tool <tool name> <json arguments>`, `/describe <tool name>` and `/text <text>`. A real provider (`anthropic`, `openai`, `azure_openai`) needs its API key in the environment or a secret file; see [AI_CHAT_ARCHITECTURE.md](AI_CHAT_ARCHITECTURE.md#configuration) and [AI_SECURITY_STANDARDS.md](AI_SECURITY_STANDARDS.md#data-handling).
