# AI assistant (chat-based management)

The AI assistant lets an authorized user manage the Email Security Gateway in natural language from the admin portal: a chat panel in the header ("Ask AI", `Ctrl/Cmd+J`) and the full-screen `/assistant` page. Every action the assistant takes is one existing `/api/v1` operation, executed with the user's own credential through the api's own HTTP pipeline, so permissions, tenant scope, MFA, rate limits, validation, masking and audit are exactly those of the portal.

**Status:** step AI-1 (foundation and every eligible **read**, 174 tools) is committed (`cf4b9ca`); step AI-2 (**action confirmations** and 35 mail-operations tools: 31 writes on policies, quarantine, held messages, recipient suppressions and saved views, and 4 side-effect-free policy `POST`s) is committed (`74c7ef4`). Step AI-3 is committed (`4113df5`): it adds 47 identity and tenant administration writes (users, roles, departments, API key revocation, domains, notifications, organizations, scan settings, SMTP connectors, webhooks) and the read `api_keys_get`, 257 enabled tools in all (179 reads, 78 writes), with **proposal guards** (nobody changes their own account, roles, MFA or sessions through chat; the assistant cannot change its own enablement or who configures it), **conditional risk escalation** and re-authentication on every role and permission change. The model can only **propose** a write: the user sees a server-authored confirmation card and the write runs only when they confirm it there (high risk also asks for the password and authenticator code). Credentials are never created, shown or rotated through chat. Step AI-R is committed (`7599f2a`): **HTML dashboard reports in chat** (the native tool `report_generate` builds a report from the existing report, quarantine and ATO APIs, rendered by the server as inert HTML with static SVG charts, stored in object storage and shown in a sandboxed iframe) and **report emails** (the native write `report_send_email`, a `medium` confirmation, only to the user's own address, active users of the organization or addresses of its verified domains, sent by the notification-worker); 259 enabled tools in all (180 reads, 79 writes). Step AI-4 is committed (`3f19349`): **security-operations tools** (64 writes and 2 side-effect-free reads for DLP, BEC, risk-scoring profiles, incidents, ATO triage, ATO responses, ATO settings and IdP integrations, and platform-only threat intelligence, rescans, scan training and dead-letter replay) and four new single-item reads; **four eyes in chat** (the requester of an ATO response, or the creator of the requesting API key, can never approve or reject it); every change that weakens detection needs re-authentication; 329 enabled tools in all (186 reads, 143 writes). Step AI-5 (2026-11-25) is **built and verified locally, not complete** (not committed; CI, the orchestrator gate's full Playwright suite and a real-provider test pending): **compliance and integrations tools** (25 writes for archive settings and retention policies, capture retry, journaling settings, journal intake sources, eDiscovery cases, searches, review tags, exports and case holds, and provider connections guided by their wizard; the mail-flow preview and the new capture-issue read); every change that shortens retention, deletes without review, narrows capture or loosens an intake source needs re-authentication; legal-hold release, disposal and key rotation stay in the portal; impact tokens are filled by the server, never by the model; the journal intake address is never revealed through chat; **every planned tool is enabled**: 356 enabled tools in all (188 reads, 168 writes), `MISSING` 0; see [CHAT_IMPLEMENTATION_STATUS.md](CHAT_IMPLEMENTATION_STATUS.md). Not verified: calls to a real LLM provider, real identity-provider and Microsoft/Google tenants, Kubernetes, CI ([CHAT_TESTING_REPORT.md](CHAT_TESTING_REPORT.md)). Step AI-6 (2026-11-26, the last step of the program) is **built, not committed**: tenant **AI administration** (usage and estimated cost per user and day, limits, a per-user budget, data sharing, an optional tenant-supplied provider key, feedback), a **metadata-only conversation audit view** (`audit:read`), **ratings** and **content search** of one's own conversations, the **`pseudonymized`** data-sharing level, **background reports** for windows longer than seven days, a **secondary provider** with health and breakers, the **`api-assistant`** Deployment, alerts, runbook and a load test; no new tool (356 enabled, `MISSING` 0, 85 not applicable of 439 operations); the brief's §16 final report is [CHAT_CAPABILITY_REPORT.md](CHAT_CAPABILITY_REPORT.md). Final status and what is not verified (real providers, Kubernetes apply, real egress ranges, CI, real-model evaluation): [CHAT_IMPLEMENTATION_STATUS.md](CHAT_IMPLEMENTATION_STATUS.md#final-program-status-brief-15-and-16).

## Enabling it locally

The local stack runs the deterministic **fake** provider: no LLM API key, no network call. Three switches must be on, plus the permission:

1. Platform: `ASSISTANT_ENABLED=true` and `ASSISTANT_PROVIDER=fake` in the repository `.env` for an api started on the host (`pnpm --filter @email-gateway/api dev`). The api **container** of Docker Compose receives no `ASSISTANT_*` key and runs `NODE_ENV=production`, where the fake is refused; for a container test stack add [tests/portal-e2e/assistant.override.yml](../../tests/portal-e2e/assistant.override.yml) when recreating the api.
2. Organization: a platform operator enables the feature `ai_assistant` (`PUT /api/v1/organizations/{id}/features/ai_assistant` `{ "enabled": true }`, or the organization page in the portal).
3. Tenant: an organization admin (`assistant:configure`) opens **Settings → AI assistant**, ticks the external-processing acknowledgement and turns it on.

Then ask, for example, "show active policies", "what was quarantined today", "journaling status", "Create an inbound policy that quarantines executables" (a confirmation card follows; after confirming it, "publish it"), "invite <address> as security_analyst", "disable user <address>", "add domain <name>" (then "verify it"), "generate a security report" (then "send this report to my email"), `add dlp dictionary "Project names" with terms alpha, beta`, "approve the pending response" (as a responder other than the requester), `create ediscovery case "Matter 7"`, `set retention policy "<name>" to 30 days` (a shortening asks for re-authentication), "release the legal hold" (refused: portal only), or use the fake's directives `/tool <tool name> <json arguments>`, `/describe <tool name>` and `/text <text>`. A real provider (`anthropic`, `openai`, `azure_openai`) needs its API key in the environment or a secret file; see [AI_CHAT_ARCHITECTURE.md](AI_CHAT_ARCHITECTURE.md#configuration) and [AI_SECURITY_STANDARDS.md](AI_SECURITY_STANDARDS.md#data-handling).

Since AI-6 (the portal part is WP7 of step AI-6, built after this page was written; see [CHAT_TESTING_REPORT.md](CHAT_TESTING_REPORT.md) for its verification): the **AI administration** page (`/assistant/admin`, Administration section of the navigation) for `assistant:configure` (usage per user, limits and the per-user budget, data sharing, the tenant key section, feedback) and `audit:read` (conversation audit view, metadata only); thumbs up/down under each answer; search in the conversation list; "generate a report for the last 30 days" queues a **background report** that the host-run api consumes (local `.env`: `ASSISTANT_REPORT_JOBS_CONSUMER=true` with `RABBITMQ_ASSISTANT_URL`; the containerized api does not consume); switch the tenant to `pseudonymized` in the administration page to see placeholders in the stored transcript while the answers keep real values. Tenant keys stay off locally (`ASSISTANT_TENANT_KEYS_ENABLED=false`); the tests use local fakes only.
