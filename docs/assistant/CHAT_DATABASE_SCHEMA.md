# Chat database schema

The assistant's own storage: fourteen MySQL 8.4 tables (step AI-R added `ai_chat_reports` and `ai_chat_report_deliveries`, [below](#reports-step-ai-r); step AI-6 five more, [below](#hardening-and-operations-step-ai-6)); originally seven (`ai_chat_*`): six created by the forward migration `packages/database/prisma/migrations/20261120141509_ai_assistant` (AI-1) and `ai_chat_action_confirmations` with the execution status `pending_confirmation` added by `20261120195837_ai_assistant_confirmations` (AI-2); the executor decision `denied_guard` added by `20261121142943_ai_assistant_guard_decision` (AI-3); plus Redis keys under `as:`. The assistant reads and writes no other table directly (I1); everything else goes through the api's operations. Normative sources: [design §3](../plan/steps/28-ai-chat-management.md#3-data-model-migration-ai_assistant-ai-1-wp1), [ADR-0094](../architecture/adr/0094-assistant-conversation-storage-retention-audit.md), [AI-2 design §3](../plan/steps/29-ai-chat-confirmations-mail-writes.md#3-data-model-migration-ai_assistant_confirmations-wp1), [AI-3 design §3](../plan/steps/30-ai-chat-identity-tenant-admin.md#3-data-model-migration-ai_assistant_guard_decision-wp1), [schema reference § AI assistant](../database/schema-reference.md#ai-assistant-7), [database README § Step AI-1 migration](../database/README.md#step-ai-1-migration-20261120141509_ai_assistant) and [§ Step AI-2 migration](../database/README.md#step-ai-2-migration-20261120195837_ai_assistant_confirmations), [retention](../database/retention.md).

Foreign keys: `organizations` `RESTRICT` on all six (the organization purge deletes them first); `ai_chat_conversations.user_id` → `users` `CASCADE` (a user's private data, as `saved_views`); turns, messages and executions → their conversation `CASCADE`; messages and executions → their turn `CASCADE`. No foreign key on the denormalized `user_id` of turns and executions, on `parent_execution_id`, or on the settings' acknowledging or updating user, so the trail survives a user's deletion. `organization_id` is the first column of every tenant index. EXPLAIN of the list and purge queries on 20 000 synthetic conversations is recorded in the [database README](../database/README.md#step-ai-1-migration-20261120141509_ai_assistant) (index range scans, no filesort).

`ai_chat_action_confirmations` (AI-2): `organization_id` → `organizations` `RESTRICT` (the organization purge deletes confirmations before executions); `conversation_id`, `turn_id` and `execution_id` → `CASCADE` (a confirmation is hard-deleted with its proposal execution); no foreign key on `user_id` or `result_execution_id`. `ai_chat_tool_executions.status` gained `pending_confirmation` (appended to the ENUM, `ALGORITHM=INSTANT`). EXPLAIN of the sweeper and pending-cap queries: [database README § Step AI-2 migration](../database/README.md#step-ai-2-migration-20261120195837_ai_assistant_confirmations).

## Retention and purge

| What                                                                                            | When                                                                                                                                                                                | How                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| ----------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Content: `title`, `content`, `provider_transcript`, `result_card`, `result_refs`, `next_cursor` | At `purge_after` = `last_turn_at` + the tenant's `retention_days` (1–365, default `ASSISTANT_RETENTION_DEFAULT_DAYS` = 30)                                                          | Background job every 10 minutes, one api replica at a time (`as:jobs:lock`), in batches via `(purge_after)`; sets the columns to NULL and `content_purged_at`. Each turn sets `purge_after` = its start + `retention_days` (then `last_turn_at` + `retention_days` at its end) and clears `content_purged_at`, so a conversation used again after a purge is purged again; lowering `retentionDays` moves the `purge_after` of the organization's unpurged conversations to `COALESCE(last_turn_at, created_at)` + the new value in the settings transaction (never later: a raised value applies from each conversation's next turn); the job re-checks every candidate under a row lock (`FOR UPDATE`) before purging, so a turn that started meanwhile keeps its content. |
| Content of one conversation                                                                     | Immediately when its owner clears it (`DELETE /assistant/conversations/{id}`)                                                                                                       | Same transaction marks it `deleted`; audited `assistant.conversation_deleted`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| Rows (conversations with their turns, messages, executions) and `ai_chat_usage_daily`           | After `ASSISTANT_EXECUTION_RETENTION_DAYS` (default 400)                                                                                                                            | Same background job, batched hard delete                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| Stale running turns                                                                             | Past their deadline + 60 s (a crashed api)                                                                                                                                          | Same job marks them `failed` (`assistant_turn_abandoned`) and releases the lock                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| Pending confirmations (AI-2)                                                                    | Past `expires_at` (`ASSISTANT_CONFIRMATION_TTL_SECONDS`, default 300 s)                                                                                                             | Same job, batches of 1 000: `pending` → `expired`, audited `assistant.confirmation_expired` per row (a confirm after the expiry does the same at once)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| Confirmations stuck in `executing` (AI-2)                                                       | write started (`execution_started_at`) > `ASSISTANT_TOOL_TIMEOUT_MS` + 60 s ago, or no write started and `decided_at` > 26 × `ASSISTANT_TOOL_TIMEOUT_MS` + 60 s ago (a crashed api) | Same job: `failed` with `assistant_confirmation_outcome_unknown`, audited; never re-executed                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| Confirmation content: `request`, `preconditions`, `summary` (AI-2)                              | With the conversation's content (retention purge or clear)                                                                                                                          | Set to NULL together with the conversation's other content; clearing a conversation also cancels its `pending` confirmations (audited)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| Confirmation rows (AI-2)                                                                        | With their proposal execution                                                                                                                                                       | FK cascade when the execution metadata is hard-deleted                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| Everything of an organization                                                                   | Organization deletion                                                                                                                                                               | `AssistantTenantDataRepository` (tenant-data module), all seven tables (confirmations first)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| `audit_logs` rows                                                                               | Audit retention (never by the assistant)                                                                                                                                            | See [CHAT_AUDIT_DESIGN.md](CHAT_AUDIT_DESIGN.md#retention)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |

## Rollback

The migration is additive (six new tables, two permissions and their grants); nothing existing is altered. Rollback is never automatic: after rolling the api and the portal back, drop `ai_chat_tool_executions`, `ai_chat_messages`, `ai_chat_turns`, `ai_chat_usage_daily`, `ai_chat_settings`, then `ai_chat_conversations`; delete the `role_permissions` rows of `assistant:use` and `assistant:configure`, then the two `permissions` rows (custom roles lose them too); delete the `organization_features` rows with `feature_key = 'ai_assistant'`; delete the migration's `_prisma_migrations` row. The exact statements are in the migration header and in the [database README](../database/README.md#step-ai-1-migration-20261120141509_ai_assistant).

**AI-2 review** (`20261120223558_ai_assistant_confirmation_execution_started`) adds one nullable column (INSTANT): rollback `ALTER TABLE ai_chat_action_confirmations DROP COLUMN execution_started_at;` after rolling the api back. **AI-2** (`20261120195837_ai_assistant_confirmations`) is additive as well: after rolling the api and the portal back, `DROP TABLE ai_chat_action_confirmations;`. The `pending_confirmation` value of `ai_chat_tool_executions.status` may stay (an older api never writes it); to remove it, first delete or re-status the rows that carry it, then `ALTER TABLE ai_chat_tool_executions MODIFY status ENUM('succeeded', 'failed', 'refused', 'timeout') NOT NULL`; delete the migration's `_prisma_migrations` row ([database README](../database/README.md#step-ai-2-migration-20261120195837_ai_assistant_confirmations)). Table count 175 → 176.

**AI-3** (`20261121142943_ai_assistant_guard_decision`) appends `denied_guard` to the `ai_chat_tool_executions.decision` ENUM (`ALGORITHM=INSTANT`, still `NOT NULL` without a default; Prisma enum `AiChatToolDecision`): a proposal guard refused the tool call (execution `refused`, no loopback request, no confirmation row). No table, column, index or Redis key is added; the table count stays 176. Rollback (never automatic; an older api never writes the value): delete or re-decide the rows with `decision = 'denied_guard'`, then `ALTER TABLE ai_chat_tool_executions MODIFY decision ENUM('allowed', 'denied_permission', 'denied_unknown_tool', 'denied_disabled', 'denied_not_applicable', 'denied_schema', 'denied_ref', 'denied_budget') NOT NULL`; delete the migration's `_prisma_migrations` row ([database README](../database/README.md#step-ai-3-migration-20261121142943_ai_assistant_guard_decision)). AI-6 adds `ai_chat_feedback`.

**AI-4 and AI-5** add no table, column, enum value or migration (178 tables). Since AI-5 the stored `request` of a mail-flow apply or disconnect confirmation holds the server-filled provider impact token (a credential-pattern key, valid at most 15 minutes and bound to the user and the change set); it is never copied to `params_redacted`, the summary, the confirmation view or audit params, and is purged with the confirmation content ([note 33 D5, D12](../plan/steps/33-ai-chat-compliance-integrations.md#d12-audit-and-data-handling)).

## Reports (step AI-R)

InnoDB, `utf8mb4_unicode_ci`, not partitioned, public ids `CHAR(36)` UUIDv7. **Metadata only** (I5): the report HTML is an object in the mail bucket, never a MySQL column.

| --------------------------- | --------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ai_chat_reports`           | generated report                              | `public_id`, `organization_id`, `user_id`, `platform_override_id`, `conversation_id`, `execution_id` (the `report_generate` execution, set when available), `status` (`pending`, `available`, `failed`, `purged`), `title`, `period_from`, `period_to`, `granularity` (`hour`, `day`), `sections` JSON (included, omitted with reasons, `atoRange`, `range`, `label`), `figures` JSON (≤ 8), `template_version`, `object_key`, `size_bytes`, `sha256`, `error_code`, `purged_at`, `object_deleted_at` | unique `public_id`; unique `execution_id`; `(organization_id, user_id, created_at)` (daily limit); `(conversation_id, status, created_at)` (latest report, purge); `(status, object_deleted_at, id)` (object purge); `(status, created_at)` (pending sweep) |
| `ai_chat_report_deliveries` | confirmed report email (one per confirmation) | `public_id` (the outbox event id), `organization_id`, `user_id`, `conversation_id`, `report_id`, `confirmation_id` (unique, no FK), `recipient_address` (content: NULL after the purge), `recipient_sha256`, `recipient_kind` (`self`, `member`, `domain`), `status` (`queued`, `sent`, `failed`), `error_code`, `message_id`, `size_bytes`, `correlation_id`, `requested_at`, `sent_at`                                                                                                              | unique `public_id`; unique `confirmation_id`; `(organization_id, requested_at)` (tenant limit); `(organization_id, user_id, requested_at)` (user limit); `(report_id, requested_at)`; `(status, requested_at)` (timeout sweep)                              |

Foreign keys: `organization_id` → `organizations` `RESTRICT` (both); `ai_chat_reports.conversation_id` → `ai_chat_conversations` `CASCADE` (backstop; the purge order is explicit); `ai_chat_report_deliveries.report_id` → `ai_chat_reports` `CASCADE`; `user_id`, `execution_id`, `confirmation_id` without FK. Outbox aggregate type `assistant_report_delivery` (event `assistant.report.email_requested.v1`, payload ids only).

**S3 objects:** `S3_BUCKET_MAIL`, key `org/<organizationId>/assistant/report/<yyyy>/<mm>/<dd>/<reportPublicId>.html` (UTC date of generation, internal organization id), content type `text/html; charset=utf-8`, stored with `ChecksumSHA256`; checked against the organization's prefix before every get and delete; never returned to a client or logged. The mail bucket is versioned and no lifecycle rule covers these keys, so the store's delete removes every version and delete marker of the key (`ListObjectVersions` + delete by `VersionId`): after a purge no copy of the HTML remains in the bucket.

**Purge:**

| What                                                                                                          | When                                                                                                                                                                        |
| ------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Report rows → `purged`, delivery addresses → NULL, `queued` deliveries → `failed` (`assistant_report_purged`) | In the conversation's content purge transaction (retention at `purge_after`, or `DELETE /assistant/conversations/{id}`)                                                     |
| Report objects of purged reports                                                                              | Right after the commit (the retention job in batches of 100: `object_deleted_at`, `object_key` NULL; the delete route inline, best effort)                                  |
| `pending` reports older than 1 hour                                                                           | Retention job: object deleted if present, row `failed` (`assistant_report_abandoned`)                                                                                       |
| `queued` deliveries older than 25 hours                                                                       | Retention job: `failed` (`assistant_report_email_timeout`)                                                                                                                  |
| Report and delivery rows                                                                                      | With their conversation after `ASSISTANT_EXECUTION_RETENTION_DAYS` (a conversation whose report still has an object is skipped until the object is deleted)                 |
| Everything of an organization                                                                                 | Organization deletion: `ai_chat_report_deliveries`, then `ai_chat_reports` (each batch deletes its objects, then its rows; count `reportObjects`), then the AI-1/AI-2 order |

**Rollback** (documented, never automatic): after rolling the api, the notification-worker and the portal back, drop `ai_chat_report_deliveries`, then `ai_chat_reports`; delete the objects under `org/*/assistant/report/` of the mail bucket.

**Rollback** (documented, never automatic; after rolling the api and the portal back): set `data_sharing = 'metadata'` everywhere, drop the five tables (jobs before reports' changes), the three new `ai_chat_turns` columns and the three new settings columns, restore the two ENUMs (`ai_chat_settings.data_sharing`, `ai_chat_reports.status`) only when no row uses the new value, drop the four new indexes. ## Redis keys

Prefix `as:`, in the api's Redis (`KeyValueStore`).

| Key                                         | Purpose                                                                                                                                                                                | Lifetime                                                         |
| ------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| `as:turn:<conversationPublicId>`            | One running turn per conversation (lock; value = turn id)                                                                                                                              | Turn deadline + 10 s                                             |
| `as:turn:cancel:<turnPublicId>`             | Cancellation flag seen by the pod running the turn                                                                                                                                     | Turn deadline + 10 s                                             |
| `as:rl:u:<userPublicId>:<minute>`           | Turns per user per minute                                                                                                                                                              | 60 s window                                                      |
| `as:tok:o:<organizationId>:<yyyymmdd>`      | Tenant tokens of the UTC day (seeded from `ai_chat_usage_daily` on a miss)                                                                                                             | 48 h                                                             |
| `as:tok:p:<yyyymmdd>`                       | Platform tokens of the UTC day (since AI-6: platform-key turns only)                                                                                                                   | 48 h                                                             |
| `as:brk:<provider>`                         | Provider breaker state shared by all api pods                                                                                                                                          | `ASSISTANT_BREAKER_RESET_MS` while open                          |
| `as:brk:<provider>:fb` (AI-6)               | Breaker of the platform secondary provider (D6)                                                                                                                                        | `ASSISTANT_BREAKER_RESET_MS`                                     |
| `as:brk:t:<organizationPublicId>` (AI-6)    | Breaker of one organization's tenant key; never opens a platform breaker (D7)                                                                                                          | `ASSISTANT_BREAKER_RESET_MS`                                     |
| `as:tok:u:<userPublicId>:<yyyymmdd>` (AI-6) | Per-user tokens of the UTC day (the per-user budget; seeded from `ai_chat_usage_user_daily` on a miss)                                                                                 | 48 h                                                             |
| `as:jobs:lock`                              | Retention purge, stale-turn sweeper and confirmation sweeps (one replica)                                                                                                              | 9 minutes per run                                                |
| `as:reauth:<sessionFamilyId>`               | Assistant re-authentication window of a sign-in session (AI-2; value `1`), set only after a successful re-authentication at an assistant confirm, read only by assistant confirmations | `ASSISTANT_REAUTH_WINDOW_SECONDS` (default 300 s; 0 = never set) |

Losing Redis loses only locks, windows and counters (a lost re-authentication window only means the next `high` confirm asks again): budgets are re-seeded from `ai_chat_usage_daily`, and a turn whose lock vanished is still bounded by its deadline and the sweeper.
