# Chat database schema

The assistant's own storage: six MySQL 8.4 tables (`ai_chat_*`) created by the forward migration `packages/database/prisma/migrations/20261120141509_ai_assistant`, plus Redis keys under `as:`. The assistant reads and writes no other table directly (I1); everything else goes through the api's operations. Normative sources: [design §3](../plan/steps/28-ai-chat-management.md#3-data-model-migration-ai_assistant-ai-1-wp1), [ADR-0094](../architecture/adr/0094-assistant-conversation-storage-retention-audit.md), [schema reference § AI assistant](../database/schema-reference.md#ai-assistant-6), [database README § Step AI-1 migration](../database/README.md#step-ai-1-migration-20261120141509_ai_assistant), [retention](../database/retention.md).

## Tables

All InnoDB, `utf8mb4_unicode_ci`, not partitioned (low volume; revisited in AI-6), public ids `CHAR(36)` UUIDv7. **No email body or attachment is ever stored** (I5): content columns hold user text, assistant text and masked metadata cards as the API returned them.

| Table                     | One row per                                 | Main columns                                                                                                                                                                                                                                                                                                                              | Content columns (purged)                               |
| ------------------------- | ------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------ |
| `ai_chat_settings`        | organization                                | `enabled`, `external_processing_ack_at`, `external_processing_ack_by_user_id`, `daily_token_budget` (NULL = platform default), `retention_days` (default 30), `data_sharing` (`metadata`), `updated_by_user_id`, `row_version` (CAS)                                                                                                      | —                                                      |
| `ai_chat_conversations`   | conversation of one user                    | `public_id`, `organization_id`, `user_id`, `platform_override_id`, `status` (`active`, `archived`, `deleted`), `turn_count`, `segment`, `last_turn_at`, `purge_after`, `content_purged_at`, `row_version`                                                                                                                                 | `title`                                                |

## Keys and indexes

| Table                     | Keys and indexes                                                                                                                                                                          |
| ------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ai_chat_settings`        | PK `(organization_id)`                                                                                                                                                                    |
| `ai_chat_conversations`   | unique `(public_id)`; `(organization_id, user_id, status, last_turn_at, id)` (the list route); `(purge_after)` (the content purge); `(user_id)` (foreign key)                             |
| `ai_chat_turns`           | unique `(public_id)`; unique `(conversation_id, seq)`; unique `(conversation_id, client_turn_id)` (idempotent retries); `(organization_id, started_at)`; `(status, started_at)` (sweeper) |
| `ai_chat_messages`        | unique `(public_id)`; unique `(conversation_id, seq)`; `(organization_id, created_at)`; `(turn_id)`                                                                                       |
| `ai_chat_tool_executions` | unique `(public_id)`; unique `(conversation_id, seq)` (refs); `(organization_id, created_at)`; `(correlation_id)` (audit correlation); `(turn_id)`                                        |
| `ai_chat_usage_daily`     | PK `(organization_id, day, provider, model)`                                                                                                                                              |

Foreign keys: `organizations` `RESTRICT` on all six (the organization purge deletes them first); `ai_chat_conversations.user_id` → `users` `CASCADE` (a user's private data, as `saved_views`); turns, messages and executions → their conversation `CASCADE`; messages and executions → their turn `CASCADE`. No foreign key on the denormalized `user_id` of turns and executions, on `parent_execution_id`, or on the settings' acknowledging or updating user, so the trail survives a user's deletion. `organization_id` is the first column of every tenant index. EXPLAIN of the list and purge queries on 20 000 synthetic conversations is recorded in the [database README](../database/README.md#step-ai-1-migration-20261120141509_ai_assistant) (index range scans, no filesort).

## Retention and purge

| What                                                                                            | When                                                                                                                       | How                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| ----------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Content: `title`, `content`, `provider_transcript`, `result_card`, `result_refs`, `next_cursor` | At `purge_after` = `last_turn_at` + the tenant's `retention_days` (1–365, default `ASSISTANT_RETENTION_DEFAULT_DAYS` = 30) | Background job every 10 minutes, one api replica at a time (`as:jobs:lock`), in batches via `(purge_after)`; sets the columns to NULL and `content_purged_at`. Each turn sets `purge_after` = its start + `retention_days` (then `last_turn_at` + `retention_days` at its end) and clears `content_purged_at`, so a conversation used again after a purge is purged again; lowering `retentionDays` moves the `purge_after` of the organization's unpurged conversations to `COALESCE(last_turn_at, created_at)` + the new value in the settings transaction (never later: a raised value applies from each conversation's next turn); the job re-checks every candidate under a row lock (`FOR UPDATE`) before purging, so a turn that started meanwhile keeps its content. |
| Content of one conversation                                                                     | Immediately when its owner clears it (`DELETE /assistant/conversations/{id}`)                                              | Same transaction marks it `deleted`; audited `assistant.conversation_deleted`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| Rows (conversations with their turns, messages, executions) and `ai_chat_usage_daily`           | After `ASSISTANT_EXECUTION_RETENTION_DAYS` (default 400)                                                                   | Same background job, batched hard delete                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| Stale running turns                                                                             | Past their deadline + 60 s (a crashed api)                                                                                 | Same job marks them `failed` (`assistant_turn_abandoned`) and releases the lock                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| Everything of an organization                                                                   | Organization deletion                                                                                                      | `AssistantTenantDataRepository` (tenant-data module), all six tables                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| `audit_logs` rows                                                                               | Audit retention (never by the assistant)                                                                                   | See [CHAT_AUDIT_DESIGN.md](CHAT_AUDIT_DESIGN.md#retention)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |

## Rollback

The migration is additive (six new tables, two permissions and their grants); nothing existing is altered. Rollback is never automatic: after rolling the api and the portal back, drop `ai_chat_tool_executions`, `ai_chat_messages`, `ai_chat_turns`, `ai_chat_usage_daily`, `ai_chat_settings`, then `ai_chat_conversations`; delete the `role_permissions` rows of `assistant:use` and `assistant:configure`, then the two `permissions` rows (custom roles lose them too); delete the `organization_features` rows with `feature_key = 'ai_assistant'`; delete the migration's `_prisma_migrations` row. The exact statements are in the migration header and in the [database README](../database/README.md#step-ai-1-migration-20261120141509_ai_assistant).

AI-2 adds `ai_chat_action_confirmations` ([ADR-0093](../architecture/adr/0093-assistant-action-confirmation.md)); AI-6 adds `ai_chat_feedback`.

## Redis keys

Prefix `as:`, in the api's Redis (`KeyValueStore`).

| Key                                    | Purpose                                                                    | Lifetime                                |
| -------------------------------------- | -------------------------------------------------------------------------- | --------------------------------------- |
| `as:turn:<conversationPublicId>`       | One running turn per conversation (lock; value = turn id)                  | Turn deadline + 10 s                    |
| `as:turn:cancel:<turnPublicId>`        | Cancellation flag seen by the pod running the turn                         | Turn deadline + 10 s                    |
| `as:rl:u:<userPublicId>:<minute>`      | Turns per user per minute                                                  | 60 s window                             |
| `as:tok:o:<organizationId>:<yyyymmdd>` | Tenant tokens of the UTC day (seeded from `ai_chat_usage_daily` on a miss) | 48 h                                    |
| `as:tok:p:<yyyymmdd>`                  | Platform tokens of the UTC day                                             | 48 h                                    |
| `as:brk:<provider>`                    | Provider breaker state shared by all api pods                              | `ASSISTANT_BREAKER_RESET_MS` while open |
| `as:jobs:lock`                         | Retention purge and stale-turn sweeper (one replica)                       | 9 minutes per run                       |

Losing Redis loses only locks, windows and counters: budgets are re-seeded from `ai_chat_usage_daily`, and a turn whose lock vanished is still bounded by its deadline and the sweeper.
