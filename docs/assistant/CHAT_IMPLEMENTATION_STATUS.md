## Known limitations

- **Writes of AI-4 and AI-5 modules** (DLP, BEC, ATO, risk scoring, incidents, platform threat intelligence, rescans, dead letters, archive, journaling, eDiscovery, provider connections, …) are not enabled: asking for them gets `denied_disabled` and a pointer to the portal page (89 writes and 3 side-effect-free `POST` reads `MISSING`).
- **Credential operations stay portal only** (I14): API key creation, webhook creation and signing-secret rotation, SMTP connector creation and secret rotation, journal intake addresses, provider secrets, invitations acceptance and password or MFA self-service. No AI-3 tool's input schema has a credential field (registry check); role `key` fields are a named exception (identifiers, `CREDENTIAL_KEY_EXCEPTIONS`).
- **Nothing about yourself through chat** (I12, A3-1): changes to the signed-in user's own account, roles, status, MFA or sessions, the assistant's own feature `ai_assistant` and roles that grant or lose `assistant:configure` are refused (`denied_guard`); use the portal (or another administrator).
- **No four-eyes approval for role changes** (A3-5): one administrator with re-authentication can change roles within the api's no-escalation rule; there is no second-approver workflow.
- **The denied card of a self guard links nowhere.** The design suggested a link to the account page (D12); the card shows the server message as plain text only (deviation, [note 30 §11](../plan/steps/30-ai-chat-identity-tenant-admin.md#11-deviations-log)).
- **One change per confirmation.** "Create and publish" is two cards (A2-1); bulk quarantine actions are one card for the whole list (the first 25 items are previewed, the api revalidates every item).
- **The confirmation token lives in the proposing browser tab only.** After a reload or in another tab a pending card can be cancelled but not confirmed (A2-3): ask again.
- **Changed state refuses.** Any change of the target's state fields between the proposal and the confirm refuses the confirm (`409 assistant_confirmation_state_changed`), even when the route itself would accept the request (A2-4); a recomputed effective risk that differs from the stored one refuses as `409 assistant_confirmation_tool_changed` (AI-3 D4).
- **Limits.** At most 5 pending confirmations per conversation (`ASSISTANT_MAX_PENDING_CONFIRMATIONS`), 5 minutes to confirm (`ASSISTANT_CONFIRMATION_TTL_SECONDS`), 5 wrong tokens cancel a confirmation, a confirm is refused while a turn of the conversation runs (A2-5, A2-7).
- **Three side-effect-free `POST` reads** (risk dry run, DLP pattern test, mail-flow preview) are deferred to their module's write phase; the webhook test became a write in AI-3.
- **Card columns named like credentials are withheld.** The credential-key pattern also matches harmless fields: the tool sweep reports `roles_list.key` and `incidents_list.titleCode` columns shown as empty; the audit metadata stores the error code under `error` for the same reason.
- **Coverage depth of the tool sweep.** Every enabled read is called once and every enabled write is proposed once (no confirm); the write suites confirm each write against the real api. The sweep proves reachability, validation, permission checks and "no write without confirmation"; it does not compare every tool's data with the portal.
- **Reports (AI-R).** Figures come only from existing APIs (top senders, top targeted recipients and policy hits are not in the report, R-1); one recipient per email and only the own address, active users of the organization or addresses of its verified/active domains (I17); the HTML is static (no interaction, no links); reports are private to the user who generated them; no scheduled reports (AI-6 option); real mail clients' rendering (inline SVG) was not verified; the running Compose notification-worker needs a rebuilt image and the main vhost topology v15 (`pnpm rabbitmq:init`) before it sends report emails.
- **Fake provider only.** Local stacks and all tests run the deterministic fake; the Anthropic, OpenAI and Azure OpenAI adapters are unit-tested against recorded fixtures but no real provider call was made. Whether a real model proposes sensible identity changes, respects the guards' explanations and explains confirmations well is not evaluated (AI-6, with the product owner's approval of spend).
- **Docker Compose api** receives no `ASSISTANT_*` key and runs `NODE_ENV=production`, so the containerized api has the assistant off; the Playwright run adds `tests/portal-e2e/assistant.override.yml`.
- **Not in AI-3** (design note 30 §8): credential creation, display and rotation, invitation acceptance, the caller's own sessions (`/auth/sessions`), SSO, organization status and deletion request/confirm, platform overrides, a four-eyes workflow, AI-4 … AI-6 items (feedback, content search beyond titles, pseudonymized sharing, provider fallback, the `api-assistant` Deployment).
- **Portal page column.** The generator attributes an operation to every portal feature folder whose source files (tests included) name it, so `/assistant` appears beside some non-assistant operations named in the assistant feature's tests. The chat tools and their links are unaffected.
