# Failure handling

What happens when each dependency fails, how the failure is detected and how the platform recovers. The overall flow is [diagram 12](diagrams/12-failure-handling.md). Status labels follow the [diagram convention](diagrams/README.md#status-convention): **IMPLEMENTED** means the behaviour exists and is tested (or, where stated, configured and validated); **PLANNED x.y** names the delivering step.

Principles (ADR-0006, ADR-0014, ADR-0023, ADR-0024, ADR-0026, ADR-0027; ADR-0024 supersedes ADR-0005, ADR-0026 supersedes ADR-0007):

1. **Accept nothing unchecked.** The in-session policy checks (smtp-adapter) fail closed to `4xx`, so the sender keeps the message and retries. The Rspamd milter is the exception: it fails open to accept (ADR-0027), because every accepted message is scanned post-queue and a scan that cannot finish ends `scan_failed`.
2. **Acknowledge only what is durable.** Ingestion answers `250` only after S3 and the MySQL commit; consumers ack only after their transaction commits.
3. **Retry is the default, dead-lettering is the exception.** At-least-once delivery plus `processOnce` gives exactly-once effects.
4. **A failed check is an outcome, not a pass.** Engine `error` and `timeout` are recorded as attempts and, when the budget or the round deadline is spent, end the round `scan_failed` (step 4.1); they are never `clean`, and a `scan_failed` message is never approved (policy's fail-safe action is 5.2).
5. **Degrade the optional, never the essential.** The read replica, OpenSearch and ClickHouse may fail without affecting mail.

### smtp-adapter

The adapter is a dependency of **both** Postfix instances for every decision: relay domains, connector lookups and transport/TLS maps (socketmap), the in-session policy, SASL and LMTP ingestion. Everything fails closed (step 2.2 §2.0).

|                  |                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Failure**      | Process down or restarting, slow (> 10 s), erroring, malformed input; or one of its dependencies (MySQL writer, Redis, S3, redis-dkim) failing                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| **What happens** | **Inbound MX:** an unknown socketmap answer becomes `451 4.3.0 Temporary lookup failure`; the policy default action is `DEFER_IF_PERMIT 4.3.5` (`450`); queued mail stays deferred in the spool while LMTP is unreachable. **Outbound:** submission AUTH answers `454 4.7.0`; connector lookups and the policy tempfail; outbound ingestion and bounce notices wait in the `postfix-outbound` spool. Nothing is accepted unchecked and nothing queued is lost (`smtp-fail-closed.test.ts`, `mail-plane.test.ts`). Note: each `smtpd` caches address resolutions, so a relay domain resolved before the outage can still pass `reject_unauth_destination`; the policy then defers it |
| **Detection**    | `/health/ready` with `mysql`, `redis`, `s3` and the six listeners (IMPLEMENTED). Runbook: [smtp-policy-service-down](../runbooks/smtp-policy-service-down.md)                                                                                                                                                                                                                                                                    |
| **Recovery**     | Restart; senders, tenant servers and Postfix retry by themselves (`postqueue -f` to hurry). Submission listeners run one session per `smtpd` process (`max_use=1`) because Postfix's Dovecot SASL client never reconnects after the auth server closed its connection (found in step 2.2 WP6)                                                                                                                                                                                                                                                                                                                                                                                       |

### Rspamd

Step 4.1 ([ADR-0027](adr/0027-rspamd-milter-policy.md), [S10](../plan/steps/09-rspamd.md#s10-resilience), [runbook](../runbooks/scan-pipeline.md)).

|                  |                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Failure**      | Daemon down, slow, refusing, or answering garbage; DNS resolver or Redis of Rspamd unavailable                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| **What happens** | **In-session (milter):** `milter_default_action = accept` (ADR-0027, replaces ADR-0006's tempfail): Postfix accepts without the SMTP-time pass; only the early GTUBE/score ≥ 15 reject is lost. Timeouts: Postfix connect/command 10 s, content 30 s above the proxy's 25 s. **Post-queue (scan role):** each call is bounded (`SCAN_RSPAMD_TIMEOUT_MS`, Rspamd `task_timeout` 15 s); a failed call (timeout, refused/reset/DNS, HTTP ≥ 400, invalid JSON or schema, `soft reject`) is a **non-final attempt row** (`timeout`/`error`, never clean) and is retried with the `hold` strategy (2 s doubling to 60 s) until `SCAN_RSPAMD_MAX_ATTEMPTS` (6) or the round deadline; the circuit breaker (5 consecutive failures or ≥ 50 % of the last 20, open 15 s, one half-open probe) turns calls into immediate `circuit_open` attempts. The last allowed failure is the **final** `error`/`timeout`: the round ends `scan_failed` (E7, `scan_error`/`scan_timeout`), `scanned.v1` says `scan_failed`, and nothing approves it (the dev pass-through skips it; policy's fail-safe is 5.2). A round whose engine never reports is finalized `timeout` by the deadline sweeper (`SCAN_ROUND_DEADLINE_SECONDS`, 30 min). With Rspamd's resolver down SPF/DKIM/DMARC end `temperror` (`auth.temperror`), never pass |
| **Detection**    | Container health check `rspamc stat`. `scan_engine_failures_total{reason}`, `scan_engine_circuit_state`, `scan_rounds_completed_total{outcome="scan_failed"}`, `scan_deadline_finalized_total`; alerts `ScanEngineCircuitOpen`, `ScanEngineFailureRateHigh`, `ScanRoundsFailing`, `ScanDeadlineFinalizations`, `ScanQueueBacklog`, `ScanLatencyHigh`. Postfix logs a milter connect warning for mail accepted without the SMTP-time pass                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| **Recovery**     | Restart. Messages still within their attempt budget (about 1 minute with the defaults) are scanned automatically once Rspamd is back; `scan_failed` messages are rescanned by an operator (`POST /api/v1/messages/{id}/rescan`, E19: new round, old round kept). Verified by `tests/integration/scan-resilience.test.ts` (stopped and restarted within the budget → scanned and delivered; past the budget → `scan_failed`, never approved; rescan → round 1 scanned and delivered) and the email-worker `scan-resilience` package suite (closed port, hanging server, breaker)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |

### RabbitMQ

Step 3.2 ([design](../plan/steps/07-rabbitmq.md), [ADR-0023](adr/0023-outbox-relay-and-reconciliation.md), [ADR-0024](adr/0024-rabbitmq-topology-retry-dead-letter.md), [runbook](../runbooks/rabbitmq-messaging.md)).

| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Failure**      | Broker restart or down, node loss in a cluster, memory or disk alarm, full work queue, consumer crash, duplicate or poison message                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| **What happens** | **No process exits** (the crash-only module is gone): clients mark themselves disconnected (`amqp_connection_up 0`, readiness red), reconnect with equal-jitter backoff rotating through their node URLs and re-subscribe. **Relay:** unconfirmed publishes are not marked and are republished after the broker returns (duplicates absorbed by the ledgers); while the broker signals `connection.blocked` it waits. ### email-worker MIME ingestion (step 3.1)

It runs after the SMTP `250`, so none of these failures affects mail acceptance. The rule is: **content problems are outcomes, infrastructure problems are retries.**

| Malformed MIME (bad boundaries, base64, QP, charsets, …) | Parsed best effort; every anomaly is a defect code; the final status is `parsed_with_defects` with the codes on the parse row, the `email_events` row and `mail.message.parsed.v1`. Never a crash                                                                                                                                                                                                                                   | IMPLEMENTED (mime-parser corpus, `tests/integration/mime-ingestion.test.ts`)                        |
| A limit is hit (size, depth, parts, headers, ratio, …)   | The parse stops (or, for one over-large body or attachment, that part is not stored and the parse continues); everything before is kept; `parse_limit_exceeded` with the limit names                                                                                                                                                                                                                                                | IMPLEMENTED                                                                                         |
| Parser library throws unexpectedly                       | `parse_failed / parser_error`, keeping what was extracted. Errors are classified by class or code, never by message text, and never logged with their message                                                                                                                                                                                                                                                                       | IMPLEMENTED                                                                                         |

### Message lifecycle (step 3.3)

Every state write is one transition of `@email-gateway/message-lifecycle` inside the writer transaction of its cause (the stage rows, the consumer's ledger row, the history row, `email_events` and the `mail.message.state_changed.v1` outbox row), under the message row lock with a version compare-and-set and an idempotency key per transition ([design](../plan/steps/08-message-lifecycle.md) L5, L13, L14; [ADR-0025](adr/0025-message-lifecycle-state-machine.md); [runbook](../runbooks/message-lifecycle.md)). The rule is: **a state never exists without its history row, and a request never moves a message backwards.**
