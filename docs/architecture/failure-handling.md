# Failure handling

What happens when each dependency fails, how the failure is detected and how the platform recovers. The overall flow is [diagram 12](diagrams/12-failure-handling.md). Status labels follow the [diagram convention](diagrams/README.md#status-convention): **IMPLEMENTED** means the behaviour exists and is tested (or, where stated, configured and validated); **PLANNED x.y** names the delivering step.

Principles (ADR-0005, ADR-0006, ADR-0007, ADR-0014):

1. **Accept nothing unchecked.** In-session checks fail closed to `4xx`, so the sender keeps the message and retries.
2. **Acknowledge only what is durable.** Ingestion answers `250` only after S3 and the MySQL commit; consumers ack only after their transaction commits.
3. **Retry is the default, dead-lettering is the exception.** At-least-once delivery plus `processOnce` gives exactly-once effects.
4. **A failed check is an outcome, not a pass.** Engine `error` and `timeout` go to policy; they are never `clean`.
5. **Degrade the optional, never the essential.** The read replica, OpenSearch and ClickHouse may fail without affecting mail.

## Per dependency

### Postfix (inbound MX)

|                  |                                                                                                                                                                                                                                                     |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Failure**      | Process or host down; disk spool full; instance lost                                                                                                                                                                                                |
| **What happens** | Senders cannot connect and keep the message in their own queues, retrying for days (standard MTA behaviour). Mail already queued but not yet handed off stays in the spool. A lost host loses its unhanded spool unless the EBS volume is recovered |
| **Detection**    | Container health check `postfix status` (IMPLEMENTED). NLB target health checks, queue-size and deferred-count metrics (PLANNED 10.1, 10.3)                                                                                                         |
| **Recovery**     | Restart policy (IMPLEMENTED in Compose). Production: ASG across 3 AZs with EBS spools that outlive the instance, re-attached on replacement (PLANNED 10.1)                                                                                          |

### postfix-outbound

|                  |                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Failure**      | Process or host down; spool full; destination servers unreachable; `rspamd-outbound` down                                                                                                                                                                                                                                                                                                                                                     |
| **What happens** | Tenant servers keep outbound mail queued and retry (4xx / no connection). Accepted submissions wait in the `postfix-outbound-spool` until LMTP ingestion succeeds. Reinjected mail is retried by Postfix with backoff until `maximal_queue_lifetime` (5 d), then a DSN goes to the authenticated sender and a postmaster copy to the bounce handler. `rspamd-outbound` down: `milter_default_action = tempfail` on 10027, never sent unsigned |
| **Detection**    | Container health check `postfix status` (IMPLEMENTED); queue size (`postqueue -j`), deferred counts and bounce metrics (`smtp_bounce_notices_total`, reputation `bounced_hard`) — alerts PLANNED 10.3. Runbook: [smtp-queue-backlog](../runbooks/smtp-queue-backlog.md)                                                                                                                                                                       |
| **Recovery**     | Restart (the spool volume persists, `smtp-durability.test.ts` shows the same for the inbound instance). Production: own ASG with EBS spools and static egress IPs; drain before termination ([deployment](../deployment/smtp-gateway.md))                                                                                                                                                                                                     |

### redis-dkim

|                  |                                                                                                                                                                                                                                                                                                         |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Failure**      | Down or restarted (no persistence: all keys are gone)                                                                                                                                                                                                                                                   |
| **What happens** | The `reinject-outbound` policy cannot see the selector and answers `DEFER_IF_PERMIT 4.7.0 Signing key not available`; rspamd-outbound cannot sign and tempfails. Outbound delivery waits in the delivery-worker / spool; nothing is sent unsigned. Inbound mail and submission ingestion are unaffected |
| **Detection**    | Container health check (`dkim-probe` PING), the api's publisher logs and counts (IMPLEMENTED). Runbook: [smtp-dkim-signing](../runbooks/smtp-dkim-signing.md)                                                                                                                                           |
| **Recovery**     | The api republishes every key within `DKIM_SIGNING_SYNC_INTERVAL_SECONDS` (30 s), or at once with `pnpm --filter @email-gateway/api dkim:sync`                                                                                                                                                          |

### smtp-adapter

The adapter is a dependency of **both** Postfix instances for every decision: relay domains, connector lookups and transport/TLS maps (socketmap), the in-session policy, SASL and LMTP ingestion. Everything fails closed (step 2.2 §2.0).

|                  |                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Failure**      | Process down or restarting, slow (> 10 s), erroring, malformed input; or one of its dependencies (MySQL writer, Redis, S3, redis-dkim) failing                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| **What happens** | **Inbound MX:** an unknown socketmap answer becomes `451 4.3.0 Temporary lookup failure`; the policy default action is `DEFER_IF_PERMIT 4.3.5` (`450`); queued mail stays deferred in the spool while LMTP is unreachable. **Outbound:** submission AUTH answers `454 4.7.0`; connector lookups and the policy tempfail; outbound ingestion and bounce notices wait in the `postfix-outbound` spool. Nothing is accepted unchecked and nothing queued is lost (`smtp-fail-closed.test.ts`, `mail-plane.test.ts`). Note: each `smtpd` caches address resolutions, so a relay domain resolved before the outage can still pass `reject_unauth_destination`; the policy then defers it |
| **Detection**    | `/health/ready` with `mysql`, `redis`, `s3` and the six listeners (IMPLEMENTED). Metrics `smtp_policy_decisions_total{action="tempfail"}`, `smtp_socketmap_lookups_total{result="temp"}`, `smtp_sasl_auth_total{result="temp"}`, `smtp_ingest_messages_total{outcome="tempfail"}` on `/metrics` (IMPLEMENTED); alerts PLANNED 10.3. Runbook: [smtp-policy-service-down](../runbooks/smtp-policy-service-down.md)                                                                                                                                                                                                                                                                    |
| **Recovery**     | Restart; senders, tenant servers and Postfix retry by themselves (`postqueue -f` to hurry). Submission listeners run one session per `smtpd` process (`max_use=1`) because Postfix's Dovecot SASL client never reconnects after the auth server closed its connection (found in step 2.2 WP6)                                                                                                                                                                                                                                                                                                                                                                                       |

### Rspamd

|                  |                                                                                                                                                                                                                                                                                                                                                                                        |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Failure**      | Daemon down or slow                                                                                                                                                                                                                                                                                                                                                                    |
| **What happens** | **In-session:** `milter_default_action = tempfail` makes Postfix answer `4xx` (IMPLEMENTED in configuration; no automated test stops Rspamd mid-session). Postfix also waits for Rspamd to be healthy before it starts (Compose `depends_on`). **Post-queue:** the Rspamd adapter returns `error` or `timeout`, a circuit breaker stops hammering it, and policy decides (PLANNED 4.1) |
| **Detection**    | Container health check `rspamc stat` (IMPLEMENTED). Adapter error and timeout metrics (PLANNED 4.1)                                                                                                                                                                                                                                                                                    |
| **Recovery**     | Restart policy. Mail tempfailed in-session is retried by senders                                                                                                                                                                                                                                                                                                                       |

### ClamAV

|                  |                                                                                                                                                                                                                                                                |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Failure**      | clamd down, signature database missing or stale, scan timeout                                                                                                                                                                                                  |
| **What happens** | Post-queue only, so mail acceptance is unaffected. The antivirus stage returns `error` or `timeout`; policy then applies a fail-safe action, for example quarantine with reason `engine_unavailable` (the enum value exists). Never `clean` (PLANNED 4.2, 5.2) |
| **Detection**    | Image health check `clamdcheck.sh` (IMPLEMENTED, 10 min start period for the first signature download). Signature age metric (PLANNED 10.3)                                                                                                                    |
| **Recovery**     | Restart; freshclam updates signatures in the container. Quarantined messages can be re-scanned (`email_scans.scan_kind = rescan`, PLANNED 5.3)                                                                                                                 |

### MySQL writer

|                  |                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Failure**      | Primary down, failover in progress, connection exhaustion, disk full                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| **What happens** | Every service's readiness fails on `mysql` (IMPLEMENTED), so Kubernetes stops routing to them and Compose marks them unhealthy. The `api` returns `503` on readiness. **Ingestion** answers `451 4.3.0` and mail waits in the Postfix spool (IMPLEMENTED 2.2); the in-session policy and socketmap tempfail (fail closed); the bounce handler answers `451` and Postfix retries the notice. **Consumers:** the transaction fails, `processOnce` rolls back its ledger row, the message is nacked and redelivered (IMPLEMENTED semantics). **Risk:** a long outage would consume the `x-delivery-limit` (5 or 10) and move healthy messages to the DLQ, so consumers must stop consuming while a dependency is down (PLANNED 3.2). The read path in `api` cannot help, because the reader falls back to the writer only for replica problems |
| **Detection**    | `mysql` readiness check (`SELECT 1`, 2 s timeout). RDS events and CloudWatch alarms (PLANNED 10.1, 10.3)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| **Recovery**     | Locally: restart (the `mysql-data` volume persists). Production: RDS Multi-AZ or Aurora failover to the same writer endpoint (PLANNED 10.1). After recovery, the outbox relay publishes rows still at `published_at IS NULL`, DLQ replay re-drives dead-lettered messages, and reconciliation re-drives messages stuck in a non-terminal status (query Q7) (PLANNED 3.2)                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |

### MySQL replica

|                  |                                                                                                                                                                                                                                                                                                                                                                           |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Failure**      | Replica down, replication stopped, lag above `DATABASE_READ_MAX_LAG_SECONDS` (default 10), lag unknown, not a replica                                                                                                                                                                                                                                                     |
| **What happens** | `PrismaReadService` switches to `writer-fallback` within one probe interval (default 5 s) and serves control-plane reads from the writer. It logs one `warn` on entering fallback and one `info` on return. Readiness does **not** fail. The data plane never uses the replica, so mail is unaffected (IMPLEMENTED, `prisma-read.service.test.ts`, `replication.test.ts`) |
| **Detection**    | `/health/ready` on `api`: the `mysql-reader` check reports `details.mode`, `lagSeconds` and `reason` (IMPLEMENTED). Alert on `details.mode != "reader"` (PLANNED 10.3). Replica container health check requires both replication threads (IMPLEMENTED)                                                                                                                    |
| **Recovery**     | Automatic return to `reader` when the probe succeeds. Re-run or re-seed with `mysql-replica-setup` ([replication.md](../database/replication.md#operations)). Binlogs are kept 7 days, so a replica stopped for less than a week catches up by itself                                                                                                                     |

### RabbitMQ

|                  |                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Failure**      | Broker down, node loss, memory or disk alarm, queue overflow                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| **What happens** | **Consumers:** an unexpected connection close makes the process exit; Compose or Kubernetes restarts it and it re-asserts its topology (IMPLEMENTED, crash-only). **Producers:** events stay in `message_outbox` with `published_at IS NULL`; the relay retries with `available_at` backoff, so ingestion and state changes are unaffected (PLANNED 3.2). A full queue rejects publishes (`x-overflow: reject-publish`), the publisher sees a nack and the outbox retries. **Node loss:** quorum queues keep working while a majority of nodes is up (3-node cluster PLANNED 10.1) |
| **Detection**    | `rabbitmq` readiness check (passive `checkExchange`) on every worker (IMPLEMENTED). Broker metrics scraped by Prometheus on `:15692` (IMPLEMENTED config, observability profile). Alerts on DLQ depth, queue age and outbox age (PLANNED 10.3)                                                                                                                                                                                                                                                                                                                                     |
| **Recovery**     | Restart and reconnect. Outbox drains. Dead-lettered messages are replayed with the replay tool (PLANNED 3.2)                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |

### Redis

|                  |                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Failure**      | Down, auth failure, memory full (`noeviction` makes writes fail rather than silently evicting)                                                                                                                                                                                                                                                                                                                                                                                                                        |
| **What happens** | Readiness fails on `redis` for `api`, `smtp-adapter`, `email-worker` and `policy-engine` (IMPLEMENTED). Rspamd loses its Redis-backed module state but keeps scanning. **smtp-adapter:** the rate limiters cannot count, so every policy decision answers `DEFER_IF_PERMIT 4.3.5` and SASL answers `454 4.7.0` (fail closed; IMPLEMENTED, `smtp-fail-closed.test.ts`); cache reads fall back to MySQL. | **Detection**    | `redis` readiness check (`PING`), container health check (IMPLEMENTED)                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| **Recovery**     | Restart. Nothing in Redis is the source of truth, so a flush or loss only costs warm-up time. ### S3 (MinIO locally)

|                  |                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Failure**      | Unreachable, throttled, access denied, object missing                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| **What happens** | Readiness fails on `s3` for `api`, `smtp-adapter`, `email-worker`, `archive-worker` (IMPLEMENTED). **Ingestion** cannot store the EML, answers `451 4.3.0`, and the message waits deferred in the Postfix spool; after recovery a queue run (or `postqueue -f`) stores it exactly once (IMPLEMENTED 2.2, `smtp-durability.test.ts` stops MinIO). | **Recovery**     | Retry after recovery. Versioning on both buckets (IMPLEMENTED locally and in the Terraform module) protects against overwrites and deletes. ## Cross-cutting failure modes

| Failure                                | Handling                                                                                                                                                                                                                                                                               | Status                                                  |
| -------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------- |
| Redelivered event                      | `processOnce` inserts `(consumer, event_id)` first; a duplicate hits the primary key and the handler does not run                                                                                                                                                                      | IMPLEMENTED (`mysql.test.ts`)                           |
| Handler throws                         | The transaction, including the ledger row, rolls back, so the retry can succeed                                                                                                                                                                                                        | IMPLEMENTED (`idempotency.test.ts`)                     |
| Poison message                         | After `x-delivery-limit` redeliveries it moves to `<queue>.dlq` through `mail.dlx`, with at-least-once dead-lettering                                                                                                                                                                  | IMPLEMENTED (topology)                                  |
| Duplicate SMTP delivery of one message | Unique `(organization_id, ingest_key)` in `message_identities`; the key covers the queue file, content and that organization's recipient set, so a redelivery to the same recipients answers `250` without writing again and a retry of deferred recipients only is stored, never lost | IMPLEMENTED 2.2 (LMTP ingestion, stack suite 7)         |
| Message stuck in a non-terminal state  | Reconciliation finds `status IN (...) AND status_changed_at < now - 15 min` (index `(status, status_changed_at)`) and re-drives it                                                                                                                                                     | PLANNED 3.2, 3.3                                        |
| Concurrent updates to one message      | Compare-and-set on `email_messages.version`                                                                                                                                                                                                                                            | PLANNED 3.3                                             |
| Partition maintenance not run          | New rows land in `pmax`; the job warns about non-empty `pmax`, still splits it, and exits non-zero on failure. Outbox partitions with unpublished rows are never dropped                                                                                                               | IMPLEMENTED (`partitions.test.ts`, executor unit tests) |
| Dependency hangs                       | Each readiness check times out after 2 s; the reader probe after 2 s; the policy server closes idle connections after 60 s                                                                                                                                                             | IMPLEMENTED                                             |
| Region loss                            | Warm standby in ap-south-2 ([diagram 15](diagrams/15-dr-hyderabad.md))                                                                                                                                                                                                                 | PLANNED 10.2                                            |

## Alerts to build (step 10.3)

Reader not in `reader` mode; non-empty `pmax` partitions; partition maintenance failure; outbox rows unpublished for more than a few minutes; DLQ depth above zero; queue age; policy and milter tempfail rate; Postfix deferred queue size; ClamAV signature age; readiness failures per service.
