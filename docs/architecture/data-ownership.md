# Data ownership

Which deployable owns (writes) each table, bucket, queue and cache, and who may read from the MySQL replica. The table-level writers come from the step 1.1 design, [§3.11](../plan/steps/01-database.md#311-data-ownership-writers); this page expands them per table and adds the stores outside MySQL. Rules:

1. **One owner per write path.** A table may be read by many services but is written only by its owner (plus the cross-cutting outbox and idempotency tables). A service that needs another owner's data to change asks for it with an event or an API call; it does not write the other owner's table.
2. **The data plane uses the writer only.** `smtp-adapter`, `email-worker`, `policy-engine`, `delivery-worker` and `archive-worker` never register `PrismaReadService` (ESLint rule plus a DI assertion in each `app.module.test.ts`), so replica lag can never affect a mail decision.
3. **Schema changes are owned by migrations.** Only `db-migrate` and partition maintenance use the DDL account (`MIGRATION_DATABASE_URL`). Runtime services have DML only.
4. **Content is never in MySQL.** Bodies and attachments live in S3; MySQL holds keys, sizes and hashes.

Status: all 71 tables are IMPLEMENTED (step 1.1 schema, the steps 1.2 + 1.3 migration `identity_tenancy`, the step 2.1 `domain_onboarding` migration, the step 2.2 `smtp_gateway` migration: `smtp_connectors`, `smtp_connector_networks`, `domain_recipient_addresses`; the step 2.3 `mail_routing` migration: `mail_destination_presets`, `delivery_reinjections`, `delivery_status_events`, `stream_cursors`; and the step 3.1 `mime_ingestion` migration: `email_message_parses`; `tests/integration/schema.test.ts`). The api writes the control-plane tables (steps 1.2–2.2); since step 2.2 **smtp-adapter writes the ingestion and bounce tables below**; since step 3.1 **email-worker writes the parse stage and the parsed metadata** (below); the other data-plane writers arrive with their steps.

### redis-dkim (step 2.2, ADR-0020)

A separate Redis 7.4 without persistence that holds plaintext DKIM signing keys of active, outbound-enabled domains. It is **not** a source of truth: the api's `DkimSigningPublisher` rebuilds it from `domain_dkim_keys` (SecretBox ciphertext) every sync interval.

| Key              | Writer (ACL user)     | Readers (ACL user)                                                                |
| ---------------- | --------------------- | --------------------------------------------------------------------------------- |
| `dkim_selectors` | `api` (`dkim-writer`) | `rspamd-outbound` (`dkim-reader`), smtp-adapter (`dkim-probe`, HEXISTS/HGET only) |
| `dkim_keys`      | `api` (`dkim-writer`) | `rspamd-outbound` (`dkim-reader`) only                                            |
