# Data ownership

Which deployable owns (writes) each table, bucket, queue and cache, and who may read from the MySQL replica. The table-level writers come from the step 1.1 design, [§3.11](../plan/steps/01-database.md#311-data-ownership-writers); this page expands them per table and adds the stores outside MySQL. Rules:

1. **One owner per write path.** A table may be read by many services but is written only by its owner (plus the cross-cutting outbox and idempotency tables). A service that needs another owner's data to change asks for it with an event or an API call; it does not write the other owner's table.
2. **The data plane uses the writer only.** `smtp-adapter`, `email-worker`, `policy-engine`, `delivery-worker` and `archive-worker` never register `PrismaReadService` (ESLint rule plus a DI assertion in each `app.module.test.ts`), so replica lag can never affect a mail decision.
3. **Schema changes are owned by migrations.** Only `db-migrate` and partition maintenance use the DDL account (`MIGRATION_DATABASE_URL`). Runtime services have DML only.
4. **Content is never in MySQL.** Bodies and attachments live in S3; MySQL holds keys, sizes and hashes.

## MySQL tables by owner

### Message lifecycle: one door, many callers (step 3.3)

The lifecycle columns of `email_messages` (`status`, `status_changed_at`, `version`, `lifecycle_round`, `status_reason`) and every row of `email_message_status_history` are written **only** through the transition service of `@email-gateway/message-lifecycle` ([design L5](../plan/steps/08-message-lifecycle.md#l5-the-transition-service), [ADR-0025](adr/0025-message-lifecycle-state-machine.md)), inside the caller's writer transaction, together with its `email_events` row (`lifecycle.<state>`, `lifecycle.ignored`) and its outbox row `mail.message.state_changed.v1`. No raw `UPDATE email_messages SET status` exists anywhere else (a repository test enforces it, L5.9). Like the shared delivery recorder, the library is one door with many callers; each caller owns only the transitions of its role ([L3](../plan/steps/08-message-lifecycle.md#l3-the-transition-table-data)):

| ------------------------------------------------------------------- | ----------------- | --------------------------------------------- | ---- |

| `delivery-worker` dev pass-through (`APP_ENV` local/ci only)        | `dev_passthrough` | E27 `scanned → approved` (E4 retired in 4.1)  | 4.1  |

**Sandbox events on the firehose (step 4.6).** `mail.sandbox.task_requested.v1` and `mail.sandbox.task_completed.v1` also reach `email.analytics` (every `email.security` event does). They are metadata only and carry no secret in clear: the result key is out of band, the task's one-time result token is sealed under it (useless without `SANDBOX_RESULT_KEY`), and artifact data keys are wrapped to a public key whose private half no service holds. They do carry, for the analytics consumer to treat as security telemetry: sample SHA-256 and sandbox-bucket object keys, observed indicator host names and canonical IPs, process image basenames and finding codes. A task is not tenant data by itself (an analysis is shared across tenants by content hash; the envelope's organization is the dispatching one): the analytics consumer (not built) must attribute sandbox results to tenants only through `mail.attachment.sandbox_completed.v1` (one per submission and organization), never through the task or result envelopes.

**Organization purge requirement (step 4.6, threat model R7).** The organization purge job is deferred platform-wide (see [retention](../database/retention.md#organization-deletion-deferred-purge)). Until it exists, a deleted tenant's sandbox data ages out by retention (artifacts ≤ 180 days, default 30; analyses ≤ 180 days; samples ≤ 48 hours). When it is built it **must**, for the analyses linked from the tenant's `sandbox_submissions`, crypto-shred `sandbox_artifacts` (null `wrapped_key`, then delete the objects) unless another live organization's submission still links the analysis, and delete the tenant's submission rows with its other partitioned rows.

**URLs on the bus (step 4.3).** `mail.url.inspection_requested.v1` is the only event that carries a URL (the normalized identity form; the isolated browser worker has no database). Like every `email.security` event it is also forwarded to `email.events` and so reaches the dormant `email.analytics` firehose. **The analytics consumer (not built yet, ADR-0009) must drop or hash the `url` field** before storing anything; `inspection_completed.v1` carries only hosts and hashes, `clicked.v1` no URL and no IP.

Dormant queues are bounded lossy buffers and never the source of truth: a stage's step switches its queue to the work policy and onboards older messages from MySQL. The ADR-0005 queues on vhost `/` (`email-worker.message-received`, …, `<queue>.dlq`) are superseded and removed by `init.mjs --cleanup-legacy` once empty.

### redis-dkim (step 2.2, ADR-0020)
