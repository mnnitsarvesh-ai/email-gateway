# Data ownership

Which deployable owns (writes) each table, bucket, queue and cache, and who may read from the MySQL replica. The table-level writers come from the step 1.1 design, [§3.11](../plan/steps/01-database.md#311-data-ownership-writers); this page expands them per table and adds the stores outside MySQL. Rules:

1. **One owner per write path.** A table may be read by many services but is written only by its owner (plus the cross-cutting outbox and idempotency tables). A service that needs another owner's data to change asks for it with an event or an API call; it does not write the other owner's table.
2. **The data plane uses the writer only.** `smtp-adapter`, `email-worker`, `policy-engine`, `delivery-worker` and `archive-worker` never register `PrismaReadService` (ESLint rule plus a DI assertion in each `app.module.test.ts`), so replica lag can never affect a mail decision.
3. **Schema changes are owned by migrations.** Only `db-migrate` and partition maintenance use the DDL account (`MIGRATION_DATABASE_URL`). Runtime services have DML only.
4. **Content is never in MySQL.** Bodies and attachments live in S3; MySQL holds keys, sizes and hashes.

Status: all 79 tables are IMPLEMENTED (step 1.1 schema, the steps 1.2 + 1.3 migration `identity_tenancy`, the step 2.1 `domain_onboarding` migration, the step 2.2 `smtp_gateway` migration: `smtp_connectors`, `smtp_connector_networks`, `domain_recipient_addresses`; the step 2.3 `mail_routing` migration: `mail_destination_presets`, `delivery_reinjections`, `delivery_status_events`, `stream_cursors`; the step 3.1 `mime_ingestion` migration: `email_message_parses`; the step 3.2 `consumer_progress` migration: `message_consumer_progress`; the step 3.3 `message_lifecycle` migration: `api_idempotency_keys`; the step 4.1 `scan_pipeline` migration: `email_auth_results` (partitioned), `scan_engine_settings`; and the step 4.2 `attachment_scanning` migration: `attachment_scan_results`, `sandbox_submissions` (both partitioned), `attachment_rescan_jobs`, `scan_signature_versions`, new `malware_signatures` columns; `tests/integration/schema.test.ts`, 22 partitioned). The api writes the control-plane tables (steps 1.2–2.2); since step 2.2 **smtp-adapter writes the ingestion and bounce tables below**; since step 3.1 **email-worker writes the parse stage and the parsed metadata** (below); since step 4.1 **the email-worker scan role writes the scan rounds, engine results and authentication results** (below), and since step 4.2 also the per-attachment results, sandbox submissions, signature versions and rescan-job progress; the api writes the known-threat hash catalog and the rescan job requests; the other data-plane writers arrive with their steps.

## MySQL tables by owner

### Message lifecycle: one door, many callers (step 3.3)

The lifecycle columns of `email_messages` (`status`, `status_changed_at`, `version`, `lifecycle_round`, `status_reason`) and every row of `email_message_status_history` are written **only** through the transition service of `@email-gateway/message-lifecycle` ([design L5](../plan/steps/08-message-lifecycle.md#l5-the-transition-service), [ADR-0025](adr/0025-message-lifecycle-state-machine.md)), inside the caller's writer transaction, together with its `email_events` row (`lifecycle.<state>`, `lifecycle.ignored`) and its outbox row `mail.message.state_changed.v1`. No raw `UPDATE email_messages SET status` exists anywhere else (a repository test enforces it, L5.9). Like the shared delivery recorder, the library is one door with many callers; each caller owns only the transitions of its role ([L3](../plan/steps/08-message-lifecycle.md#l3-the-transition-table-data)):

Every smtp-adapter key starts with `sa:` (layout: `apps/smtp-adapter/src/tenancy/cache-keys.ts`); losing Redis loses only caches and counters, and the mail path fails closed (4xx) while Redis is down.

### redis-dkim (step 2.2, ADR-0020)

A separate Redis 7.4 without persistence that holds plaintext DKIM signing keys of active, outbound-enabled domains. It is **not** a source of truth: the api's `DkimSigningPublisher` rebuilds it from `domain_dkim_keys` (SecretBox ciphertext) every sync interval.

| Key              | Writer (ACL user)     | Readers (ACL user)                                                                |
| ---------------- | --------------------- | --------------------------------------------------------------------------------- |
| `dkim_selectors` | `api` (`dkim-writer`) | `rspamd-outbound` (`dkim-reader`), smtp-adapter (`dkim-probe`, HEXISTS/HGET only) |
| `dkim_keys`      | `api` (`dkim-writer`) | `rspamd-outbound` (`dkim-reader`) only                                            |
