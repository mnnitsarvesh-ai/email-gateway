# Architecture diagrams

Twenty-two Mermaid diagrams describe the gateway from system context down to message states, failure handling, isolation, the AWS regions and the routing and delivery sequences. GitHub renders them inline. They are written against the repository as it is on branch `build/platform` (mail-path diagrams updated for steps 2.2 and 2.3). Where a diagram shows something that does not exist yet, it says so and names the step in [`docs/plan/execution-plan.md`](../../plan/execution-plan.md) that delivers it.

## Status convention

Every component and every arrow is labelled as one of two states:

| Status          | Meaning                                                                                                                                                                                               | Flowchart / state diagram                         | Sequence diagram                                                       |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------- | ---------------------------------------------------------------------- |
| **IMPLEMENTED** | Exists in this repository and is exercised by a unit, e2e or integration test, or by a CI validation step (`docker compose config`, `kubectl kustomize`, `terraform validate`). The evidence is named | Green box, **solid** border, solid arrow `-->`    | Plain participant and message                                          |
| **PLANNED x.y** | Designed (ADRs, step design notes) but not built. `x.y` is the execution-plan step that delivers it                                                                                                   | Amber box, **dashed** border, dotted arrow `-.->` | Participant named `... (PLANNED x.y)`, messages inside a shaded `rect` |
| external        | Not built by this project (senders, tenants' mail systems, DNS, AWS services we only consume)                                                                                                         | Grey box                                          | Plain participant                                                      |

The colour is never the only signal. Every planned element also carries the text `PLANNED x.y` (or `P x.y` on short arrow labels), so the diagrams read correctly in monochrome and for colour-blind readers. Each diagram is followed by a legend and a status table that lists the evidence (file or test) for every IMPLEMENTED element.

The class definitions shared by every flowchart:

```text
classDef impl fill:#e8f5e9,stroke:#2e7d32,stroke-width:2px,color:#1b1b1b
classDef planned fill:#fff8e1,stroke:#b26a00,stroke-width:2px,stroke-dasharray:6 4,color:#1b1b1b
classDef ext fill:#eceff1,stroke:#546e7a,stroke-width:1px,color:#1b1b1b
```

**Every diagram except 6, 19, 21 and 22 contains PLANNED elements.** Diagram 21 (step 3.2) and diagram 22 (steps 2.3 and 3.3) are implemented; diagram 20 (step 3.1) is implemented apart from the consumers of its events (4.x, 3.3). Diagrams 10 and 15 are entirely planned (apart from the tables and contracts they rely on). Since step 2.3 the mail path from the inbound MX or the connector to the destination server, with per-recipient delivery status, is implemented end to end; what is planned between ingestion and delivery is scanning and policy (3.x–5.x), whose place the development-only pass-through approval holds in local and CI stacks.

## What is implemented today (summary)

| Area             | Implemented and tested                                                                                                                                                                                                                                                                                                                                              |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Mail edge        | Both Postfix instances, smtp-adapter policy/socketmap/SASL/LMTP ingestion and bounce handling (step 2.2, stack suites `tests/integration/smtp-*.test.ts`)                                                                                                                                                                                                           |
| Routing          | delivery-worker (approval feed, planning, reinjection with token, rate limits, delivery-log status, reconciler), routing module `@email-gateway/mail-routing`, destination presets, per-recipient delivery API (step 2.3, stack suites `tests/integration/routing-*.test.ts`)                                                                                       |
| MIME ingestion   | email-worker post-queue parse: `email.received` consumer (step 3.2), `@email-gateway/mime-parser` (limits, defects, filenames, sniffing, zip flags), part objects in S3, parse/header/attachment rows and `mail.message.parsed.v1` in one transaction (step 3.1, `tests/integration/mime-ingestion.test.ts`, `apps/email-worker/integration`)                       |
| Engines          | Rspamd (`/checkv2` returns a verdict) and ClamAV (EICAR detected) run as daemons and are tested directly (`tests/integration/mail-plane.test.ts`). No Node adapter calls them yet                                                                                                                                                                                   |
| Services         | 9 deployables boot, validate config, connect to their dependencies and expose `/health/live` and `/health/ready` (`services.test.ts`)                                                                                                                                                                                                                               |
| Data             | 73-table MySQL schema with 19 partitioned tables (`tests/integration/schema.test.ts`), GTID primary + replica, reader account and `PrismaReadService` writer fallback (`tests/integration/replication.test.ts`, `prisma-read.service.test.ts`), `processOnce` on `message_idempotency` (`tests/integration/mysql.test.ts`), MinIO buckets with tenant-prefixed keys |
| Messaging        | event-relay (confirmed outbox publish, reconciler), topology v2 in vhost `email-gateway` with role users, the client library (recovery, retries, delay queue, dead letters, content guard), consumers in email-worker and delivery-worker, audited dead-letter replay (step 3.2, `messaging-*.test.ts`, `cluster/node-failure.test.ts`)                             |
| Contracts        | Event envelope, the event registry and payloads with decimal ids and `org/{organizationId}/` keys, RabbitMQ topology v2 as data, lifecycle states and events (step 3.3), security-engine contract (`packages/event-contracts`, `packages/security-contracts`)                                                                                                       |
| Deploy artefacts | Compose stack, Kustomize base + `saas`/`dedicated` overlays (rendered in CI), Terraform S3 + KMS module (`terraform validate` in CI, never applied)                                                                                                                                                                                                                 |
