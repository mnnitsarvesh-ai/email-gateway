# ADR-0050: REST API conventions for `/api/v1`

**Status:** Accepted (implemented in step 6.1; verification record in [§13 of the step design](../../plan/steps/18-rest-api.md#13-verification-record); not verified: CI, a Kubernetes cluster). Design: [step 6.1](../../plan/steps/18-rest-api.md) D1, D2, D14, §3.2, §3.4. Builds on [ADR-0015](0015-api-base-path.md) (base path) and [ADR-0016](0016-authentication-sessions-rbac.md) (authentication, RBAC); supersedes neither.

**Context.** By step 5.3 the api served 229 business operations written over twelve steps. They shared a base path, tenancy from the principal and zod validation, but not one error shape (`code` only on the routes that installed a scoped filter; 401/403/404/429/validation errors carried none), not one validation rule (many request schemas were stripping `z.object`s that silently dropped unknown fields), no request id, no documented rule for status codes, envelopes or deprecation, and an OpenAPI document without shared error components or examples. The admin portal (steps 7.1–7.3) is the first client that will consume the whole surface; it needs one predictable contract.

**Decision.**

1. **Resources.** Plural kebab-case nouns, at most two levels of nesting (`/messages/{messageId}/recipients`); path ids are public ids (UUIDv7) or decimal strings for log-like rows; non-CRUD commands are `POST /…/{id}/<verb>` (`rescan`, `release`, `publish`). Kept legacy exceptions: `POST /domains/{id}/recipients/remove`, `POST /quarantine/entries/{id}/delete` (bodies with reasons). One name per resource (no `/emails` alias of `/messages`).
2. **Methods and status.** `GET` 200; `POST` create 201 with the resource; `POST` command 200 (synchronous) or 202 (asynchronous, with the id to poll); `PUT` 200; `PATCH` 200; `DELETE` 204 (existing `DELETE` routes that answer 200 keep it).
3. **Envelope.** A single resource is returned bare; a collection is `{ "data": [...], "nextCursor": string | null }`. Documented legacy exception: the three quarantine lists of step 5.3 answer `{ "items": [...], "nextCursor" }` (unchanged; the route inventory recognizes both by `nextCursor`).
4. **Errors.** Every error is `{ statusCode, error, code, message, correlationId, requestId, ...details }`; `code` is a stable snake_case machine code, `message` keeps its type (`string`, or `string[]` of `"<path>: <issue>"` for validation; values never echoed). One global `ApiExceptionFilter` renders every exception; uncoded exceptions get a default code by status (`validation_failed`, `unauthorized`, `forbidden`, `not_found`/`route_not_found`, `conflict`, `payload_too_large`, `unsupported_media_type`, `unprocessable`, `rate_limited`, `internal_error`, `service_unavailable`); the permission guard's 403s are coded (`mfa_required`, `mfa_enrollment_required`, `user_required`, `forbidden`) with unchanged messages. Module codes are unchanged.
5. **Request-Id.** Every response (success, error, unknown route, probes) carries `X-Request-Id`, a server-minted UUID never taken from the client; it is in the error body, in every log line and in `audit_logs.metadata.requestId`. `x-correlation-id` keeps its meaning (caller-chosen, echoed). Every `/api/v1` response also carries `Cache-Control: no-store` unless the route sets its own.
6. **Strict validation.** Every body and query schema is a strict zod object at every object node: unknown fields are `400 validation_failed` (`"<path>: Unrecognized key"`). Path params are validated before any database access.
7. **Representation.** Ids are strings; timestamps ISO 8601 UTC with milliseconds; enums lower-snake; no raw `bigint`; never message content, secrets or S3 keys.
8. **Deprecation rule.** A breaking change to a path, DTO or error code needs `Deprecation`/`Sunset` headers on the old behaviour, a test of both behaviours and a changelog entry in the API guide; otherwise it ships as `/api/v2`.
9. **OpenAPI.** Generated from the zod schemas; shared components `ErrorBody`, `ValidationErrorBody`, `RateLimitedErrorBody` and the standard headers; every operation gets the standard error responses it does not document itself (400 with input, 401/403 when secured, 404 with path params, 429, 500, 503) and the response headers. operationIds are the generated `<Controller>_<method>_v1` and are frozen by the snapshot `docs/api/openapi.json` (renaming a handler is a breaking change the snapshot test shows); tags are module tags with descriptions naming the step and deferrals; vendor extensions `x-eg-permissions`, `x-eg-rate-class`, `x-eg-idempotency`, `x-eg-cursor`, `x-eg-returns-secret` for the portal. Routes new in 6.1 carry explicit examples; legacy routes rely on schema-derived examples.
10. **Enforcement.** `test/route-inventory.e2e.test.ts` discovers every served route and fails on a missing permission, OpenAPI operation, tag, summary, security, standard response, body or 2xx schema, 6.1 example, coverage entry, cursor encoding, strict schema or §3.5 idempotency metadata.

**Alternatives considered.** A `{ data }` wrapper on every success body: breaks all existing operations for no portal benefit. A lenient-validation switch for legacy routes: keeps the gap open; v1 is pre-GA and the portal is the first client. Client-supplied request ids: spoofable in logs and audit; `x-correlation-id` already serves the caller's own tracing. Hand-written operationIds: churn without benefit; the generated ones are stable and frozen.

**Consequences.** Two documented contract changes for existing clients (API guide changelog): unknown request fields are rejected, and an `Idempotency-Key` is required on the §3.5 legacy routes (ADR-0052). Errors gain `code` and `requestId` (additive). Every new route must satisfy the inventory test before it merges. The quarantine `items` envelope stays a recorded exception until a `/api/v2` (or a deprecation cycle) changes it.
