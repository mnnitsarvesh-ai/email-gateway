# ADR-0041: Risk scoring model: signals in de-duplicating groups, explicit failures, hard blocks, authenticated trust, versioned bounded profiles

**Status:** Accepted; implemented in step 5.1 — verified locally on 2026-11-11, [§13](../../plan/steps/15-risk-scoring.md#13-verification-results). Implementation notes ([§12](../../plan/steps/15-risk-scoring.md#12-deviations-log)): failure and unknown signals are named `engine_failed_<engine>` / `engine_unknown_<engine>` (a `:` is not allowed in a reason code); DLP coverage uses the row values `complete`/`partial`; an unmapped code keeps 0 points but prevents `clean`; a `scan_failed` round counts as a failure even without a failed engine entry; the calibration report shows the defaults unchanged on 1 050 synthetic fixtures (4 outside their hand-written band, reported, not tuned) and makes no accuracy claim. Design: [step 5.1](../../plan/steps/15-risk-scoring.md) R1–R12, R18. Works with [ADR-0042](0042-risk-scoring-placement-and-policy-handoff.md). Does not supersede an earlier ADR.

**Context.** Phase 4 delivered six engines, each with its own verdict map and reason codes (`rspamd-map/2`, `attachment-map/1`, `url-map/1`, `bec-map/1`, `dlp-map/1`, `sandbox-map/1`), and a round verdict that is only the most severe engine outcome (ADR-0026). The brief for step 5.1 asks for one centralized, configurable, per-tenant, deterministic and explainable risk score over SPF, DKIM, DMARC, spam, IP and domain reputation, URL, attachment, phishing, BEC and DLP, with hard-block indicators, trusted-sender exceptions, risk levels, evidence aggregation, engine-failure handling and versioned configuration; it forbids double counting of overlapping signals and treating unknown, timeout or error as clean, and forbids accuracy claims without validated data. Several engines report the same fact (SPF/DMARC failure from Rspamd and from BEC; lookalike domains from the URL and BEC engines; ClamAV, YARA and known hashes on attachments), and the BEC engine's own 0–100 score already folds in authentication and link evidence.

**Decision.**

1. **A pure library** `@email-gateway/risk-scoring` (no I/O, integer arithmetic only, no clock or randomness) computes `scoreRisk(input, profile)`. The input (`risk-input/1`) is assembled from the round's stored rows by one shared pure function, so the email-worker and the api's dry-run produce identical inputs; its canonical JSON is hashed (`input_sha256`), as is the effective profile (`profile_sha256`). Every result records the scorer (`risk-score/1`), signal map (`risk-signals/1`), input and profile versions.
2. **Signals and groups.** Each engine reason code maps, through the versioned signal map, to a **signal** (one fact; several engines asserting it raise it once). Signals belong to **groups** combined by `max` or a capped sum; overlapping evidence shares a group (DMARC failure with BEC tenant-domain spoofing, URL with BEC lookalikes, all attachment malware findings). The score (0–1000) is the capped sum of group totals. Every code of every engine's code list is either mapped or explicitly informational (an exhaustiveness test); the Rspamd codes become a contract list (`RSPAMD_REASON_CODES`). The BEC aggregate score is not used (it would double count); BEC enters through its deterministic, non-suppressed rule codes.
3. **Failures are outcomes.** A required engine that timed out, errored, is missing or whose child row is missing (`email_auth_results`, `bec_scan_results`, `dlp_scan_results`; a successful Rspamd check always writes its authentication row, so a missing one is lost SPF/DKIM/DMARC evidence) adds failure weight and forces a minimum level (`medium`) and action (`quarantine`); `unknown` adds weight, a minimum level (`low`) and a minimum action (`failures.unknownAction`, default `tag`, tenant bounds `tag | require_approval | quarantine`), so an unknown result is never recommended for plain delivery (review round 1); the verdict is `clean` only when every required engine gave a definite or skipped result with no unknown, no failure and no coverage gap. A scoring error writes a fail-safe error result (`high`, `quarantine`).
4. **Hard blocks** (malware by hash/ClamAV/YARA, malware URLs, a malicious sandbox result, DLP `block`, known phishing URLs, a DMARC-`reject` spoof of the tenant's own domain, tenant-blocked URLs, a deterministic BEC `malicious`; generic DMARC reject optional) set the level to `critical`, the verdict and a non-delivery action regardless of score, trust and weights. Malware and DLP-block indicators cannot be disabled.
5. **Trust** reuses the BEC engine's trusted-sender match (T1, already bound to From authentication and expiry): it may reduce only content-type groups (spam, reputation, URL structure, BEC identity/intent/history) by a bounded factor, only for inbound mail with DMARC `pass` and no authentication-failure signal, and is always recorded.
6. **Levels and actions.** Five levels (`none`, `low`, `medium`, `high`, `critical`) with thresholds; a recommended action from `deliver < tag < require_approval < quarantine < block`, the strictest of the level's action, failure floors, hard blocks, the DLP action binding of ADR-0037 and (for an AI-only BEC raise, ADR-0034) at most `tag`. Engine-verdict floors keep the level at least as severe as an engine's deterministic `malicious` (and BEC `suspicious`).
7. **Profiles.** A platform default (`rsk-default/1`, data in the library, changed only by a new id) plus one tenant profile lineage per organization with bounded overrides (thresholds, level actions, group multipliers 0.5×–2×, hard-block toggles and actions within the allowed set, failure weights and floors raise-only, trust mode and factor, the AI tag switch). Versions are drafts until published; published versions are immutable; activation is a pointer, rollback re-activates a published version. Overrides are re-validated at use; an invalid profile falls back to the platform default, recorded and counted.
8. **Explanations** are rendered from line codes and integers by fixed templates (top signals, hard blocks, failures, trust, floors, profile) and never contain message content.
9. **Calibration without claims.** A labelled synthetic dataset built only from code and outcome combinations the real verdict maps produce, and a generated calibration report (score distributions per class, confusion matrix of levels against labels, threshold rationale) are committed and checked by a unit test. Defaults are engineering defaults, explicitly not validated detection accuracy.

**Alternatives considered.** Summing every engine's own score (double counting, incomparable scales); a weighted average of engine verdicts (cannot express hard blocks or overlaps); a learned model (no validated data; not explainable enough for the brief); floating-point weights (platform-dependent rounding); per-signal tenant weights (≈ 80 unvalidated knobs); trust applied to all signals or from a separate allow-list (spoofable, duplicated data); treating `unknown` as neutral (violates the brief).

**Consequences.** Adding an engine code requires a signal-map decision (the exhaustiveness test fails otherwise); a new signal map or default profile is a new version id, and old rows keep theirs. Scores are reproducible from stored rows. Tenants get a bounded tuning surface with dry-run; the platform still makes no accuracy claim, and real-world calibration needs a validated dataset (external dependency).
