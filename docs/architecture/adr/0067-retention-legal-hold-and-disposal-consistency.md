# ADR-0067: Retention policies, case-scoped legal holds evaluated at disposal time, and one disposal pipeline consistent across S3 (versions and replica targets), MySQL and OpenSearch

**Status:** Accepted (2026-11-17, after the step 8.1 local verification: expiry and disposal consistent across the archive bucket, the (simulated) replica bucket, OpenSearch, MySQL and the disposal log; a legal hold blocking expiry until released; the 5.3 Q17 binding in the api and policy-engine suites; record [docs/plan/steps/23-journaling-archiving.md](../../plan/steps/23-journaling-archiving.md) §13, §14). Proposed by the step 8.1 architect on 2026-11-16 (design A11–A15, A23, A24). Supersedes no ADR decision. Takes over the step 5.3 binding (contracts §29) and changes the Q17 rules accordingly (`409 quarantine_retention_active` is no longer produced). Implementation notes: an Object Lock still running counts as retention (WP2 D8); api-written disposal decisions leave `replica_status` to the worker (WP4 D7). **Not verified:** S3 cross-region replication (10.2).

**Context.** Retention must be configurable per tenant, per direction or category; legal holds must block deletion and expiry; deletion, retention and hold operations must be consistent across replicated storage (S3 versions and replicated buckets, the MySQL writer and its replica, the search index) with reconciliation and an audit trail. Step 5.3 already refuses quarantine deletes under holds read with a conservative criteria subset, and the organization deletion of step 1.2 is blocked by active holds and waits for the latest archive retention.

**Decision.**

1. **Retention policies** have optional criteria (`archive-retention/1`: directions, categories, sources, policy rule references, domains, departments), a priority, an expiry action (`delete` | `review`) and days bounded by the plan's `archive_retention_days` and a platform cap. At capture the first matching live policy (else the tenant's default) fixes `retain_until`. At expiry the effective date is recomputed lazily and only ever **extended** (a lengthened policy protects existing records; a shortened one affects new captures only).
2. **Legal holds** belong to an eDiscovery case, are immutable once created (change = new hold + audited release), and have criteria `archive-hold/1` (custodians, date range, directions); legacy rows keep the 5.3 subset; **unparsable criteria match everything**. Holds are evaluated **authoritatively at every disposal** on writer facts (sender, header From, every envelope recipient, received time, direction) — no per-record hold application job, no second source of truth. The record's `legal_hold` flag is informational.
3. **Expiry** (leader-elected, per organization, bounded batches, one transaction per record under a row lock): extend for a longer policy; else extend by a hold extension when a hold matches; else move to `expiry_review` when the action is `review` (disposed only by an audited human action); else dispose. Locked records are extended at storage level first (ADR-0066).
4. **One disposal pipeline** (expiry, reviewed disposal, organization purge): (a) the decision transaction re-checks holds and retention, writes an `archive_disposals` row (the per-record, append-only compliance log) and **crypto-shreds** the record (wrapped data key nulled, `deleted_at` set, status `disposing`), enqueuing the index delete; (b) every object version under the record (recorded versions, then orphans) is deleted in the archive bucket and **every version of the same keys in each replica target** (replication never propagates version deletes); (c) the index delete is confirmed; (d) the row is hard-deleted, together with the message registry row when the registry purge contract requires it. Each stage is resumable with attempts and backoff; a failed stage leaves only undecryptable data.
5. **Replica consistency.** Every content access re-reads the record on the writer before decrypting, so MySQL replica lag can never serve disposed content; metadata reads converge within the replica lag bound.
6. **Reconciliation**: per-day index counts with repair, sampled verification of completed disposals in every store, orphan object cleanup, stuck-intent detection.
7. **Step 5.3 under 8.1.** Rule 1 (legal hold) uses the 8.1 matcher; rule 2 (retaining mail-bucket objects for archive retention) is removed because the archive keeps its own encrypted copy and the AWS mail bucket expires processed mail after 30 days anyway (`409 quarantine_retention_active` is no longer produced); rule 3 defers purges while a capture is pending for any source.
8. **Organization purge** refuses while holds are active or a record is retained, then disposes every record through the same pipeline, deletes the configuration rows and destroys the tenant keys last; the disposal log and audit rows stay.

**Alternatives considered.** Storing a hold flag on every matching record at hold creation (an O(records) job, drift between flag and criteria, a spoliation risk when the job lags). Deleting the record row first and the objects later (a crash would leave readable objects without a reference). Relying on bucket lifecycle rules for expiry (per-record retention and holds cannot be expressed). Per-record audit rows for system disposals (millions of audit rows; the disposal log is the per-record trail, with one audit row per lifecycle run).

**Consequences.** A hold placed after a record expired cannot resurrect it; a hold placed before expiry always blocks it. Shortening a retention policy never shortens existing records. Disposal is observable per record and per store. Quarantine deletes are no longer refused for archive retention (API changelog).

**Amendment (closing round of step 8.1, 2026-11-17).** (1) Every disposal decision is serialized with legal hold creation: hold creation locks the organization row `FOR UPDATE` before inserting the hold, and every decision (the worker's expiry, the api's manual dispose, each batch of the organization purge) takes the same row `FOR SHARE` before it locks the record and reads the active holds (READ COMMITTED: the read after the wait sees a hold committed meanwhile; lock order organization → record everywhere). A hold confirmed to the user can therefore no longer lose a race with a disposal of a record it covers. (2) Every writer of a disposal decision stores `archive_disposals.objects` in one shape (`{captureId, prefix, versions}`), built by `disposalObjectsOf` of `@email-gateway/archive`; the lifecycle pipeline validates the stored document and derives the prefix and versions from the record identity when it meets the record's own `archive-record-objects` document (rows written by the api before the fix). api-written decisions record no replica targets (`replica_status` `{targets: [], pending: []}`): the worker deletes from its configured targets.
