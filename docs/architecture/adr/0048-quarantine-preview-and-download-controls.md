# ADR-0048: Quarantine preview is sanitized JSON text with DLP masking; downloads only through single-use, re-authorized grants

**Status:** Accepted (implemented in step 5.3, verified locally on 2026-11-12: sanitized, DLP-masked preview and single-use download grants (refused without permission, when disabled, with a wrong password, reused and for EICAR) verified by the `quarantine-smtp` stack suite; [§12, §13](../../plan/steps/17-quarantine.md#13-verification-results); not verified: Kubernetes apply, CI). Design: [step 5.3](../../plan/steps/17-quarantine.md) Q11, Q12. Works with [ADR-0038](0038-dlp-evidence-masking-and-aadhaar-gating.md) (unmasked values stay behind `dlp:evidence_read`).

**Context.** Quarantined mail is by definition suspicious: rendering it can run scripts, load tracking pixels or lure a reviewer into clicking. The brief requires a server-side sanitized preview (no active content, no remote resources, links not clickable or rewritten, attachments listed not served), DLP-matched values masked, a full-preview permission separate from metadata, audit, size limits, and prevention of unauthorized downloads (no direct S3 URLs; a dedicated permission, fresh re-authorization, a short-lived single-use token bound to user, tenant and object, malware blocking, rate limits, audit). Step 3.1 already stores decoded text and HTML parts and allow-listed headers.

**Decision.**

1. **Preview** reads only the stored decoded parts (bounded Range GETs), `email_headers`, attachment and URL rows; it never parses the raw EML in the api. The HTML part is reduced to plain text (active and embedding elements dropped, images replaced by placeholders, no `src`, no CSS, no data URIs), control, bidi and zero-width characters are removed, links are listed **defanged and not clickable**, and the response is JSON text only. Every built-in DLP detector masks its matches in the subject, body and header values. `quarantine:preview` is separate from `quarantine:read`; end users may preview their own non-malicious entries when the tenant allows. Each preview is audited before content is read.
2. **Downloads** are off by default (tenant setting) and need `quarantine:download` (only super and organization admins). A grant requires an MFA user session **and** password (plus TOTP) re-entry, and passes malware gating; it yields an HMAC-signed token (60 s by default, ≤ 300 s) bound to organization, user, entry, object and part, recorded in `quarantine_download_grants` and consumed atomically on first use. The download is served as `application/octet-stream` attachment with `nosniff`, `no-store` and a sandbox CSP. Hard-blocked, malware or phishing messages, and attachments whose latest verdict is not `clean`, are never served. **No defanged archive** is offered in 5.3.

**Alternatives considered.** Sanitized HTML (allow-listed tags) — rejected: a larger attack surface for the portal and CSS-based tricks for little reviewer value. Re-running a MIME parser in the api — rejected (untrusted input parsed twice). Presigned S3 URLs — rejected (bearer URLs, no single use or user binding). Password-protected ZIP of malicious files — rejected (encrypted archives are a known malware delivery vector and a liability).

**Consequences.** Reviewers see text, not the formatted message. Forensic retrieval of malicious samples is out of band (platform operators with S3 access, audited by the cloud provider), not through the product.
