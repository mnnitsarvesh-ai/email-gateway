# ADR-0044: Policy evaluation in the policy-engine on `email.policy.evaluate`; delivery gated only by policy approvals; the development pass-through removed

**Status:** Accepted; implemented in step 5.2 — verified locally on 2026-11-11, [§13](../../plan/steps/16-policy-engine.md#13-verification-results); implementation notes in [§12](../../plan/steps/16-policy-engine.md#12-deviations-log) (the generation is read with a consistent read in the evaluation transaction — §12.3 point 1; the `DELIVERY_OUTBOX_*` keys went with the pass-through — §12.3 point 3; `email.notifications` is not in `RECONCILE_QUEUES` yet — §13 not complete). Design: [step 5.2](../../plan/steps/16-policy-engine.md) P13–P18, §4. Amends [ADR-0024](0024-rabbitmq-topology-retry-dead-letter.md) (topology v9), [ADR-0025](0025-message-lifecycle-state-machine.md) (edge E27 retired; E5, E8–E13 get their producer), [ADR-0026](0026-security-scan-pipeline.md) (S15: the development pass-through after the scan is removed). **Supersedes** decision 5 of [ADR-0037](0037-dlp-policy-actions-and-lifecycle-binding.md) and decision 6 of [ADR-0042](0042-risk-scoring-placement-and-policy-handoff.md) (the pass-through holds); their bindings for 5.2 (ADR-0037 decision 6, ADR-0042 decision 7) are implemented by [ADR-0043](0043-policy-dsl-and-deterministic-evaluator.md). **Amended in step 5.3 by [ADR-0046](0046-quarantine-store-and-per-recipient-decisions.md):** decision 6 — `email.quarantine` is rebound and becomes the release executor's work queue (topology v10); the policy-engine image gains a `quarantine` role.

**Context.** Since step 4.1 the delivery-worker's development pass-through (local/ci only, `DELIVERY_DEV_PASSTHROUGH_ENABLED`) reads `mail.message.scanned.v1` from the outbox and approves mail (E27 `scanned → approved`) unless one of its holds applies. Production has no approver at all: scanned mail waits until its deadline. The queue `email.policy.evaluate` is dormant (bound to `scanned.v1` and `parse_failed.v1`), `apps/policy-engine` is a skeleton with no broker user, and E5, E8–E13 (role `policy`) have no producer. Every scanned round has its revision-0 risk row committed in the same transaction as `scanned.v1` (ADR-0042). Approvals are `mail.delivery.approved.v1` outbox rows consumed by the planner from `email.delivery.pending`; the planner delivers whatever object the approval names (organization-prefixed).

**Decision.**

1. **The policy-engine consumes `email.policy.evaluate`** (topology v9: the queue becomes a work queue with ledger consumer `policy-engine.evaluate`, retry `hold`, dead-letter to `email.dead-letter`; bindings unchanged) as its own least-privilege broker user `eg-policy-engine` (read the one queue; publish only its own retry hops and dead letters). It accepts `mail.message.scanned.v1` (outcomes `scanned`, `scan_failed`) and `mail.message.parse_failed.v1`.
2. **One writer transaction per event** (`processOnce` ledger, budget ≥ 120 s, step 4.2 §6): apply the first lifecycle edge (E8 `scanned → policy_evaluated`, E9 from `scan_failed`, E5 from `persisted`) with `expectedRound` from the event — this locks the message row; if it is not applied (stale, superseded round, already evaluated) the event is acknowledged with only the ledger row. Otherwise read the round's facts on the writer (echo-checked), read the tenant's policy generation and compiled snapshot, evaluate, write the policy copy object if one is needed (deterministic S3 key, idempotent overwrite), then in the same transaction: the `policy_execution_logs` row (unique per message and lifecycle round), `email_messages.final_verdict` / `final_action` / `risk_score`, the disposition edge (E10 `policy_deliver` / `policy_tag`, E11 `policy_quarantine`, E12 `policy_hold`, E13 `policy_reject` / `policy_discard`), the outbox rows (`mail.policy.decided.v1` always; `mail.delivery.approved.v1` with `source = policy` for ALLOW; `mail.message.archive_requested.v1` for ARCHIVE; `mail.policy.notification_requested.v1` for ALERT and the outbound non-delivery notice) and the `email_events` rows. A duplicate event is absorbed by the ledger, the lifecycle edge and the unique key. A rescan is a new round and gets a new evaluation; old evaluations are never changed.
3. **Delivery is gated only by policy.** The only approval producers are the policy-engine (`source = policy`) and the existing operator release (E14/E15, `source = quarantine_release`). The **development pass-through is removed** from the delivery-worker (code, configuration, Compose, metrics), and edge **E27 is retired** (its id is never reused; historic `dev_passthrough` history rows and approval sources stay readable). The local stack runs the policy-engine in the `apps` profile, so local and CI delivery follow exactly the production path. A policy-engine outage leaves mail in `scanned` (held, not delivered) until it recovers; the `scanned` lifecycle deadline still applies.
4. **The approved object** follows the step 4.3 U20 rule (the round's rewritten copy when `url_rewrites.status = rewritten`, echo-checked, else the original EML) and, when TAG or WARN header edits apply, a **policy copy** `org/<org>/policy/<yyyy>/<mm>/<dd>/<messageId>/r<round>-<sha256 prefix>.eml` derived from that object with header edits only (tag `eg-object=policy-copy`, lifecycle expiry). The planner labels it `object = "policy_copy"`. The original EML is never modified.
5. **Next-evaluation-only policy changes:** the api increments `policy_settings.generation` in the transaction of every publish, activation, rollback, status change, deletion or settings change; the engine reads the generation on the writer for every evaluation and caches compiled snapshots by `(organization, generation)`.
6. **Topology v9** also: rebinds the dormant `email.archive` from `mail.policy.decided.v1` to the new `mail.message.archive_requested.v1` (consumer 8.1); keeps `email.quarantine` (dormant, 5.3) bound to `mail.policy.decided.v1`, which is redefined in place (it never had a producer or consumer); adds the work queue `email.notifications` (ledger consumer `notification-worker.policy`, broker user `eg-notification`) bound to `mail.policy.notification_requested.v1`.

**Alternatives considered.** Keep the pass-through as a local fallback "never more permissive than policy": rejected, it cannot see tenant rules (a tenant REJECT or QUARANTINE rule would be bypassed), two approvers race on the same `scanned` messages, and stack tests would not exercise the production path. Wrap the pass-through around a policy call (RPC): rejected, a second decision point and a network hop with no benefit. Evaluate in the email-worker's completion transaction (like 5.1): rejected, policy needs tenant data, directory reads, S3 copies and its own failure domain, and a policy outage must not stop scanning. Apply TAG/WARN header edits in the delivery-worker at reinjection: rejected, the reinjector is a byte pump (ADR-0030 reasoning), retries would need the edits persisted, and the approval contract already allows a modified copy. Re-evaluate when the sandbox revision arrives: rejected for 5.2 (the round is already decided; 5.3 re-validates on release).

**Consequences.** Delivery locally and in production depends on the policy-engine being up (alerted). Stack suites that relied on pass-through metrics change to policy metrics; expectations change only where the new behaviour is stricter or equal (listed in the step's §12). Held messages (quarantined, held_for_review) are released only through the existing operator release until 5.3 adds the quarantine store and approval workflow.
