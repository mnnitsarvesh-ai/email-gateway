# ADR-0029: URL security engine: one `url` engine on `scan.url`, pluggable reputation providers, lookalike detection, one SSRF-guarded fetcher, topology v5

**Status:** Accepted. Amends [ADR-0026](0026-security-scan-pipeline.md) (engine catalog: `url` is registered and required; typed URL child rows are written in the finalize transaction like the 4.2 attachment rows; the orchestrator, verdicts and rounds are unchanged) and [ADR-0024](0024-rabbitmq-topology-retry-dead-letter.md) (topology v5: `scan.url` becomes a work queue, two new queues `scan.url.inspect` and `scan.url.results`, a `stateless` consumer kind and a bounded lossy work policy, a `url-browser` role user). Design: [step 4.3](../../plan/steps/11-url-protection.md).

**Context.** The brief for 4.3 asks for URL extraction, normalization, domain and IP reputation, redirect-chain inspection, short-URL resolution, phishing and lookalike detection, rewriting and time-of-click protection, with strict SSRF controls, isolated browser workers, URL evidence in MySQL and reputation cached in Redis. Step 3.1 stores the text and HTML bodies per part in S3; step 4.1/4.2 built the scan pipeline with Rspamd and the attachment engine; `scan.url` was dormant.

**Decision.**

1. **One `url` engine**, required for every tenant (`requiredByDefault: true`, `tenantMayDisable: false`), ledger consumer `email-worker.scan.url`, deployable separately with `SCAN_CONSUMERS=url`. It reads the stored parts (never re-parses the EML), extracts URLs from text, HTML (href, src, srcset, form actions, meta refresh) and small HTML/text attachments, records obfuscations and dangerous schemes as reason codes, and normalizes with the WHATWG URL parser (UTS #46 IDNA) and the Public Suffix List. A message with a complete parse and no URL is `skipped` (`url.none`).
2. **Reputation through providers** behind one interface with a breaker each: a platform-wide local feed (`threat_indicators`, managed through an audited platform API, never cached), a generic DNSBL provider (covers Spamhaus DBL/ZEN, SURBL and URIBL by configuration) and an RDAP domain-age provider. Google Safe Browsing, PhishTank and URLhaus are documented configurations of the same interface, not implemented and never called in tests. Answers are cached in Redis keyed by provider version, HMAC-authenticated, with short clean TTLs and longer malicious TTLs. External outages make URLs `unknown`, never `clean`, and never fail mail flow; internal infrastructure failures are retried attempts.
3. **Lookalike detection** with UTS #39 confusable skeletons, mixed-script checks, edit distance with explicit thresholds and combosquatting, against a platform brand list, the tenant's own domains and tenant-listed partner domains.
4. **One hardened fetcher** for every outbound request of the URL features: it resolves DNS itself through a restricted resolver, blocks every non-globally-reachable IANA special-purpose range after canonicalizing mapped/NAT64/6to4 forms, blocks metadata names and addresses, dials the validated IP literal (no DNS rebinding or TOCTOU), re-checks the connected address, validates every redirect hop, caps hops, bytes, headers and time, and never sends cookies or credentials. In production it egresses only through the guarded egress proxy or under a NetworkPolicy that denies private destinations. Scan-time fetching is limited by default to shorteners and URLs with risk signals.
5. **Verdict map `url-map/1`**: known-bad feed, DNSBL phishing/malware, tenant block list or a high-confidence lookalike with a credential form → malicious; lookalikes, new domains, IP hosts, redirects to IPs or internal addresses, excessive redirects, obfuscation and credential forms → suspicious; fetch and provider errors → unknown; clean only when every check answered. The mapper is shared with the click service.
6. **Evidence** in new partitioned tables (`message_urls`, `url_scan_results`, `url_rewrites`, `url_dynamic_inspections`, `url_click_events`), never page bodies; exposed tenant-scoped in the scans read API without cache or timing signals.

**Alternatives considered.** Consuming Rspamd's URL symbols at scan time (order-dependent within a round). Fetching every URL (consumes one-time links). Using the unused reputation tables as a cache (MySQL writes on the hot path). A per-request `lookup` hook as the only SSRF control (bypassable by socket reuse and proxies). Blocking only RFC 1918 and loopback (misses CGNAT, NAT64, mapped and documentation ranges).

**Consequences.** Every round waits for the URL engine; a rescan re-evaluates URLs and produces a new rewritten copy. The topology has sixteen queues. `mail.url.inspection_requested.v1` carries a URL and reaches the analytics firehose; its future consumer must drop or hash it. The default DNSBL/RDAP configuration points at test zones locally; production must configure real zones and a recursive resolver that does not serve internal zones.

**Implementation notes (step 4.3, recorded in [§12](../../plan/steps/11-url-protection.md#12-deviations-log)).** The decisions above hold; three details differ from the design text and are recorded with evidence: (a) superseded by review round 1 — IP reputation now covers literal IP hosts and hops and the public addresses every domain host (URL, final URL, later hops) resolves to through the restricted resolver (`HostAddressResolver`; internal answers are never sent to a provider), at scan time and at click time; (b) the retry binding of `scan.url` is `retry.scan.url.org.#` and the scanner's topic permissions are anchored on `.org.`, because `scan.url` is a dot-prefix of `scan.url.inspect` / `scan.url.results` (WP1); (c) the `local_feed` provider surfaces MySQL errors as retryable attempt failures rather than per-item `error` answers (WP3 deviation 9). None changes a security property.

**Review round 1 (2026-11-06).** The guarded fetcher runs every request with OpenTelemetry tracing suppressed, so the auto-instrumentation of the services that trace (email-worker, click-service) never adds propagation headers to requests to untrusted sites (the exact U8 header set) and never records their paths or queries; the rewritten EML copy is tagged `eg-object=rewrite` in the creating request (no separate tagging call that could leave an untagged copy). Recorded in [§12 "Review round 1"](../../plan/steps/11-url-protection.md#review-round-1-security-correctness-completeness-findings-2026-11-06).
