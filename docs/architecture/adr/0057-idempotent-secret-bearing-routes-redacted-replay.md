# ADR-0057: Idempotency-Key on secret-bearing webhook routes with redacted replay

**Status:** Accepted (implemented in step 6.2 and verified locally: api e2e and integration suites assert the redacted replay and that idempotency rows hold no `whsec_`; the stack suite replays a creation and gets `secret: null` with `Idempotency-Replayed: true`; [§14](../../plan/steps/19-webhooks-notifications.md#14-verification-record); not verified: CI. Design: [docs/plan/steps/19-webhooks-notifications.md](../../plan/steps/19-webhooks-notifications.md) W6, W7, §6.1, §6.2). **Supersedes [ADR-0052](0052-rate-limiting-and-idempotency.md) decision 8 for exactly two routes**: `POST /api/v1/webhooks` and `POST /api/v1/webhooks/{webhookId}/rotate-secret`. Decision 8 stays in force for every other secret-bearing route (`POST /api-keys`, `POST /smtp-connectors`, `POST /smtp-connectors/{id}/rotate-secret`, `POST /platform/overrides`, `POST /auth/mfa/totp/setup`, `POST /auth/mfa/recovery-codes`, the public authentication routes).

**Context.** ADR-0052 decision 8 says secret-bearing responses are never stored, so those routes take no `Idempotency-Key`, and `@ReturnsSecret()` refuses to be combined with idempotency (the route inventory enforces it). The step 6.2 brief requires an `Idempotency-Key` on webhook creation and secret rotation: both are sensitive mutations a client retries after a timeout, and a duplicate creation makes a second endpoint with a second secret, a duplicate rotation silently invalidates the secret the client just received. The webhook signing secret must be shown once and never be stored in clear (the stored idempotency response is plain JSON in MySQL).

**Decision.**

1. The two routes require `Idempotency-Key` and use the **transactional** mechanism (`IdempotencyService.execute`): the subscription change, its audit row and the stored response commit in one writer transaction.
2. The **stored** response is the route's representation with `secret: null` (the redacted representation). The secret exists only in the original HTTP response: the service keeps it in a local variable of the transaction's `work` function and adds it to the response after the commit; it never reaches the idempotency row, the audit row or a log line.
3. A replay (same key, same principal, operation and body fingerprint, within 24 h) returns the stored redacted body with `Idempotency-Replayed: true` and status of the original (201 for create, 200 for rotate). It never generates, re-encrypts or reveals a secret. A client that lost the original response rotates the secret (with a new key); the API guide says so.
4. `@ReturnsSecret({ redactedReplay: true })` marks these routes. The route inventory allows `@ReturnsSecret` together with idempotency **only** for routes in its `SECRET_BEARING_REDACTED_REPLAY` list and only with that option; a test asserts that the idempotency rows written by both routes contain no `whsec_` string and no `secret` value other than `null`.
5. Both routes keep the `sensitive` rate class.

**Alternatives considered.** Keep decision 8 (no key): violates the brief and leaves duplicate creation/rotation on retries. Store the secret encrypted in the idempotency row and replay it: a second store of the secret with a different lifetime and access path, and a replay would hand the secret to anyone holding the principal's credentials and the key for 24 h. Return `409` on replay instead of the redacted body: breaks the replay contract of ADR-0052 (same status and body).

**Consequences.** A replayed creation tells the client the subscription exists but not its secret; rotation is the documented recovery. The inventory rule becomes an explicit allow-list instead of a blanket ban. Other secret-bearing routes are unchanged; extending this pattern to them needs a new ADR.
