# ADR-0051: Pagination (cursor v1 and v0), filtering, sorting, scan budget and message list plans

**Status:** Accepted (implemented in step 6.1; verification record in [§13 of the step design](../../plan/steps/18-rest-api.md#13-verification-record); production-scale timing not verified, only EXPLAIN plans on local volumes). Design: [step 6.1](../../plan/steps/18-rest-api.md) D3–D6, §3.3. Builds on [ADR-0014](0014-mysql-data-model-partitioning-read-write-split.md) (replica reads); supersedes nothing.

**Context.** Every list of steps 1.2–5.3 paged with `?limit&cursor` on a keyset, but the cursors were unsigned base64url strings (tamper-evident through a canonical round trip, quarantine bound to a filter hash), not bound to the tenant, and each module had its own ad-hoc filters and no `sort` parameter. Step 6.1 adds lists over the largest tables (`email_messages` at 1M rows per tenant and day, `audit_logs`, `url_click_events`, `email_attachments`), where an unbounded filter is an unbounded scan of the replica.

**Decision.**

1. **One list contract.** `limit` (1–100, default 25; quarantine search keeps its configured cap) and `cursor`; response `{ data, nextCursor }`; keyset order on an indexed key ending in the primary key; `nextCursor: null` on the last page; **no totals** and **no offsets**. A page may hold fewer than `limit` rows, even none, while `nextCursor` is non-null (scan budget); clients follow `nextCursor` until it is null.
2. **Cursor v1** (mandatory for every list added since 6.1): `base64url(JSON payload) + "." + base64url(HMAC-SHA256(API_CURSOR_KEY, "eg-cursor/v1\0" + resource + "\0" + organizationPublicId + "\0" + payloadB64)[0..16])`, payload `{ v: 1, r, k, f, d, w?, t }` (resource, key values, filter hash, direction, the first page's resolved time window, issue time). Verified with `API_CURSOR_KEY`, then `API_CURSOR_KEY_PREVIOUS` (rotation); resource, filter hash and age (`API_CURSOR_TTL_SECONDS`) must match, length ≤ 512; any failure is `400 cursor_invalid` without detail (`api_cursor_rejected_total`). The organization is bound through the MAC (a cursor of tenant A fails for tenant B) and the tenant scope is re-applied regardless, so a cursor never widens access.
3. **Cursor v0** (legacy): the unsigned cursors of the 33 pre-6.1 lists stay unchanged for compatibility (they carry no authority). `@CursorList('v0' | 'v1')` declares the encoding (`x-eg-cursor`); the route inventory fails a list without it and a 6.1 list on v0.
4. **Filtering.** Query syntax `field=value`, `field=a,b,c` (≤ 10 values unless stated), `field.gte|lte|gt|lt=`, booleans `true|false`; unknown parameters or operators are `400 validation_failed`. Each list declares an allow-list (name → type, operators, max values, column constant); column identifiers come only from code constants, values are always bound parameters (Prisma `where` or `Prisma.sql`), never raw SQL. Foreign ids (`domainId`, `messageId`) are resolved inside the tenant scope (another tenant's id answers like a missing one). Lists over partitioned tables require a bounded `from`/`to` (defaults and maximum per resource) so MySQL prunes partitions.
5. **Sorting.** `sort=-key` (default) or `sort=key`, only keys that lead the keyset index (`receivedAt`, `createdAt`, …). Decisions 4 and 5 apply to the v1 lists (the 9 lists of 6.1). The 33 v0 lists keep their fixed keyset order (no `sort` parameter) and their module-specific filters; converging them is a recorded follow-up, not part of 6.1.
6. **Filter hash.** SHA-256 of canonical `{ filters, sort, resource }`, first 16 hex, bound into the cursor (changing a filter with an old cursor is `cursor_invalid`).
7. **Scan budget.** For lists that cannot read their keyset in index order (messages, audit logs, URL clicks): `API_LIST_SCAN_BUDGET_ROWS` (5 000, bounded 1 000–50 000) caps the index entries a request examines when a filter needs a non-indexed column: step 1 finds the boundary key `budget` entries after the cursor (index-only), step 2 filters between the cursor and that boundary with `LIMIT limit+1`; a short page continues at the boundary. `api_list_scan_budget_exhausted_total{resource}` counts short pages.
8. **Message list plans** (`GET /messages`, replica only): index plan (range and sort only) over `(organization_id, received_at, id)`; verdict plan (exactly one `verdict`) over the new `(organization_id, final_verdict, received_at, id)`; recipient plan (`recipient=` exact) over `email_recipients (organization_id, address(100), received_at)` with duplicates collapsed; scan-bounded plan for everything else. Each plan is EXPLAIN-checked in an integration test.

**Alternatives considered.** Re-signing every legacy cursor now: touches every module for no security gain (scope is re-applied); kept v0 behind the inventory guard, migration listed as a follow-up. Offset pagination for "page N" UIs: unbounded at 1M messages/day. Total counts: unbounded counts on the replica; reports give bounded aggregates. Unbounded filtering with a statement timeout: unpredictable latency and replica load; the budget makes cost per request constant.

**Consequences.** Clients must tolerate short and empty pages with a non-null `nextCursor`. A cursor-key rotation without `API_CURSOR_KEY_PREVIOUS` invalidates every outstanding v1 cursor (clients restart the list; runbook). Two `email_messages` indexes cost about 3 % of the bulk insert rate in the local measurement (step design §12 WP1). Migrating v0 cursors, `sort` and the shared filter vocabulary on the v0 lists, field selection and ETags remain open (14.1 or a 7.x need). The attachment hash search reads the keyset in index order (`(organization_id, sha256, received_at, id)`, migration `rest_api_index_coverage`) and therefore needs no scan budget.
