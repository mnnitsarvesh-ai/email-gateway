# ADR-0061: Message search through driver indexes on generated search keys, a capped subject-prefix plan, an audit resource plan and server-side saved views

**Status:** Accepted (2026-11-14; implemented by step 7.2 WP1 and verified locally, see [docs/plan/steps/21-email-explorer-details.md](../../plan/steps/21-email-explorer-details.md) §13 WP1; used by the portal's Email Explorer (WP3) and verified end to end through it, with the full regression, in §14 (WP5); designed there in E1–E4, §3.1–§3.3; proposed by the step 7.2 architect). **Supersedes decision 8 of the Accepted [ADR-0051](0051-pagination-cursor-filtering-sorting.md)** (the four message list plans); decisions 1–7 of ADR-0051 stand (decision 4's filter vocabulary gains the additive `domain` type; decision 7's audit list gains a resource plan). Production-scale timing, CI and a cluster apply are not verified; the step is not committed.

**Context.** Step 7.2 builds the Email Explorer: search by sender, recipient, subject, message ID and domain, and filters by direction, date, risk, verdict, delivery status and quarantine status, over `email_messages` at a design target of 1M messages per day per tenant (monthly partitions of about 30M rows). ADR-0051 decision 8 serves `GET /messages` with four plans: an index plan without filters, a verdict plan (one verdict alone), a recipient plan (recipient alone) and a scan-bounded plan for everything else, which examines `API_LIST_SCAN_BUDGET_ROWS` (5 000) entries of `(organization_id, received_at, id)` per request. Identifier searches are therefore unusable at volume (a Message-ID lookup over 31 days needs thousands of short pages), and there is no subject, domain, delivery-status or quarantine-status search at all. InnoDB has no FULLTEXT on partitioned tables, and an unindexed `LIKE` over these tables is not acceptable. Saved views are wanted, but only if they can be stored server-side per user with tenant scope.

**Decision.**

1. **Generated search keys.** VIRTUAL generated columns (metadata-only, INSTANT on the partitioned tables) with online secondary indexes: `email_messages.subject_key` (reply/forward markers removed, whitespace collapsed, trimmed, 128 code points; case and accents ignored by the `utf8mb4_unicode_ci` collation), `email_messages.sender_domain`, `email_messages.message_id_key` (angle brackets removed, 255 characters), `email_recipients.address_domain`; plain indexes on `envelope_from`, `header_from`, `email_deliveries (organization_id, status, received_at, message_id)` and `quarantine_messages (organization_id, status, message_received_at, message_id)`. Prisma declares the generated columns as read-only nullable fields (their expressions live in the migration, as `final_engine` and `verified_name` already do). TypeScript normalizers mirror each expression and are parity-tested against MySQL.
2. **One driver per request.** The present filters choose a driver by fixed priority (`internetMessageId` > `sender` > `headerFrom` > `recipient` > `subject` > `senderDomain` > `recipientDomain` > `subjectPrefix` > `quarantineStatus` > `deliveryStatus` > one `verdict` > none). The driver's index is read in keyset order `(received_at, id)`; without residual filters the page is exact; with residual filters the ADR-0051 scan budget (decision 7) applies **over the driver's index** (boundary at the budget-th entry, then the residual-filtered page), so a request never examines more than the budget and a selective driver covers far more time than the organization-wide scan. Foreign drivers (recipient domain, delivery status, quarantine status) stream `GROUP BY received_at, message_id` keys from their own index, so a message appears on one page only. Residuals are fixed SQL fragments or correlated `EXISTS` sub-queries on indexed message keys; identifiers are code constants, values bound.
3. **Subject prefix, capped.** A prefix is a range, so its matches are not time-ordered: a probe reads at most `API_MESSAGES_SEARCH_MAX_MATCHES + 1` matching index entries in the window; more answers `422 message_search_too_broad`; otherwise the page is sorted within the cap. Both statements carry `MAX_EXECUTION_TIME(API_MESSAGES_SEARCH_TIMEOUT_MS)` (`503 message_search_timeout`). Minimum normalized length 3. A `LIKE` runs only over rows an index located: the subject-key range as a driver, or at most the budget rows of another driver as a residual.
4. **Filter-level permissions.** `subject` and `subjectPrefix` require `message:reveal` (a subject search is a content oracle, ADR-0062), and so does the exact `recipient` (added when the step was closed: an exact recipient search confirms a recipient address that every read masks, ADR-0062 decision 6; `recipientDomain` stays open because the masked form keeps the domain), `deliveryStatus` requires `delivery:read`, `quarantineStatus` requires `quarantine:read`; otherwise `403 message_filter_forbidden`. Subject searches are audited like the other identifying searches (`message.searched`, SHA-256 of the value).
5. **Cursor binding covers the driver.** The filter hash includes the driver name, so a cursor is bound to its plan; a deploy that changes plan selection invalidates outstanding message cursors once (`400 cursor_invalid`).
6. **Audit resource plan.** With `resourceType` and `resourceId`, the audit searches read `(organization_id, resource_type, resource_id, created_at, id)` in keyset order (other audit filters are budgeted residuals), so a message's audit history is exact at any audit volume.
7. **Saved views** live in `saved_views` (organization, user, kind `message_explorer`, unique name, strict JSON definition ≤ 8 KiB validated by parsing its filters with the real `GET /messages` query schema and its permissions, `row_version`), behind five routes under `/saved-views` (`message:read`, member user principals only, another user's or tenant's view is `404`), at most `SAVED_VIEWS_MAX_PER_USER` per user and kind, audited without names or filter values.

**Alternatives considered.** FULLTEXT on `subject` (not supported on partitioned InnoDB tables). `LIKE '%term%'` inside the scan budget (an unindexed scan; thousands of short pages at volume). A prefix index on the raw subject (no reply-marker normalization; encoded-words before the parse). A token search table written on the data plane (a new writer, backfill and hashed-content privacy questions for a control-plane view; content search belongs to the analytics/search store of ADR-0009). A k-way keyset merge for several status values (correct, but the budgeted-boundary merge is complex for a single-select UI; recorded follow-up). Saved views in browser storage (not shared across devices, not tenant-scoped).

**Consequences.** `email_messages` carries five more secondary indexes (write amplification measured with `pnpm db:perf` and recorded in the step note; virtual columns cost nothing at rest). No writer may ever set a generated column. Pages remain bounded per request and may be short (the ADR-0051 list contract is unchanged); subject-prefix searches may be refused as too broad. Outstanding message cursors are invalidated once at the deploy of this change. Clients get exact identifier, domain, subject and status searches and the portal can store per-user views. Several values per status filter and content search stay out of scope.

**Implementation notes (step 7.2 WP1, 2026-11-14).**

- Migration `20261113212017_email_explorer_search`: the four VIRTUAL generated columns (`ALGORITHM=INSTANT`), the nine indexes (`INPLACE, LOCK=NONE`) and `saved_views`; 121 tables, 33 partitioned; verified on a throwaway schema and applied to the local writer (the replica followed).
- **One expression differs from the design text:** the reply-marker pattern of `subject_key` uses possessive quantifiers (`[[:space:]]*+`). The designed pattern backtracked quadratically and hit MySQL's `regexp_time_limit` (error 3699) on a subject such as `re` + 990 spaces + `x`; since the column is indexed, its expression runs on every insert and on every update of `subject`, so an attacker-chosen subject would have failed ingestion. The possessive form accepts the same language and is linear. The TypeScript normalizers (`apps/api/src/modules/messages/domain/search-keys.ts`) are parity-tested against the generated columns on a corpus that includes those subjects.
- The drivers are `message-list-drivers.ts` (SQL builders, `FORCE INDEX` on every statement) and a pure plan (`message-list-plan.ts`). Every served statement echoes a per-statement nonce besides the organization and the range, which is the exact form of the key echo for the case- and accent-insensitive keys; exact-valued keys (verdict, delivery and quarantine states) are echoed too.
- The subject-prefix probe reads the `(cap + 1)`-th matching index entry (`LIMIT 1 OFFSET cap`, index-only) instead of counting `cap + 1` rows in a derived table (which materialized them and doubled the reads).
- The foreign drivers' budgeted page reads the budget's index entries, the materialized grouped keys and one primary-key lookup per message (≤ 3 × budget handler reads, measured); the exact pages read about `limit` entries without a temporary table or a sort.
- The audit resource plan compares `resource_type` / `resource_id` with the column collation for the index seek and `utf8mb4_0900_bin` (pushed down to the index) for the exact 6.1 semantics.
- Saved views are served from the writer (read-after-write of the user's own settings), with the owner's user row locked for the per-user limit.
- Write amplification (`pnpm db:perf`, one connection, 200 000 messages): `email_messages` 22 225 → 16 143 rows/s while unchanged tables slowed 5–13 % in the same pair of runs; about 15–20 % of the `email_messages` insert rate is attributable to the five indexes on this laptop (production-scale cost not measured).
