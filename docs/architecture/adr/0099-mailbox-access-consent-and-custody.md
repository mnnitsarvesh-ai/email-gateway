# ADR-0099: Mailbox access consent and custody for API mode

**Status:** Accepted (2026-11-26, local verification: stack suite `api-mode.test.ts` 11/11 — `m365.mailbox_remediation` (customer app through provider-fake) and `google.mailbox_remediation` (customer service account, domain-wide delegation) granted through the unchanged 8.2 routes and verified by the integration-worker with the observed permissions; the mailbox-worker decrypts them for Graph, Gmail and Directory tokens; revocation stops feeds and inventory at the next claim (no content fetched), health `failing` with the `api_mode_unhealthy` e-mail, journal detection continues, the mail-flow grant untouched; regression provider-integrations 10/10, ato-idp 7/7; live Microsoft 365 / Google Workspace tenants (incl. RBAC for Applications scoping), CI and Kubernetes apply pending). Proposed by the step API-1 architect, 2026-11-26. Design: [docs/plan/steps/35-api-mode-protection.md](../../plan/steps/35-api-mode-protection.md) §2.0 (N3, N5, N6), D4, §3.3, §6. Contracts [§36](../contracts.md#36-api-mode-protection-step-api-1); migration `20261126022823_api_mode_protection` (permissions `remediation:read`, `remediation:write`; [docs/database/README.md](../../database/README.md#step-api-1-migration-20261126022823_api_mode_protection)). **Supersedes in part** [ADR-0076](0076-provider-integration-framework.md) (its list of permission purposes and the "no write access to customer tenants" rule for mail flow, already relaxed for ATO response profiles by step 8.5) and [ADR-0077](0077-provider-credential-custody-and-encryption.md) (its list of credential holders). Related: [ADR-0098](0098-protection-modes-and-detect-mode-copies.md), [ADR-0100](0100-api-mode-intake-mailbox-worker.md).

**Context.** API mode must enumerate mailboxes and (from step API-2) read, move and delete messages: Microsoft Graph application permissions `Mail.ReadWrite` (+ `User.Read.All`), Google domain-wide delegation of `gmail.modify` (+ `admin.directory.user.readonly`). ADR-0076 defines grants per permission profile and purpose with separate platform apps (admin consent of a multi-tenant app grants every declared permission); ADR-0077 names who may decrypt a grant's credentials.

**Decision.**

1. A new purpose `mailbox_remediation` with the profiles `m365.mailbox_remediation` (Graph `Mail.ReadWrite`, `User.Read.All`; auth methods `platform_app`, `customer_app_secret`) and `google.mailbox_remediation` (`gmail.modify`, `admin.directory.user.readonly`; `platform_service_account`, `customer_service_account`), their own operator apps (`PROVIDER_M365_MAILBOX_APP_*`, `PROVIDER_GOOGLE_MAILBOX_SA_*`), consented, uploaded, verified and revoked through the unchanged step 8.2 grant routes and the step 8.5 auxiliary verification of the integration-worker. **Supersedes ADR-0076's purpose list in part**; the `mail_flow` deny list is unchanged and does not apply to this purpose. No migration per profile (grants store the profile as text).
2. Creating, uploading credentials for, verifying or revoking a grant whose profile purpose is `mailbox_remediation` additionally needs `remediation:write` (`403 remediation_permission_required`), checked in the grants service on top of `integration:manage`. The connection must be bound (step 8.2 I10).
3. **Supersedes ADR-0077's custody list in part:** the mailbox-worker decrypts these grants (besides the integration-worker for verification); tokens stay in process memory only; Graph client-state values are derived in the mailbox-worker and stored as SHA-256 only.
4. Revocation stops feeds and inventory at the next claim (feeds `revoked`, cursors and subscription ids cleared, inventory `unavailable`, health `failing` when feeds were enabled); journal detection continues (it needs no grant).
5. Permissions (catalog and migration): `remediation:read` (tenant read set, `security_analyst`, `domain_admin`) and `remediation:write` (`organization_admin`, `security_analyst`); `remediation:purge` is reserved for API-3 and not created.

**Consequences.** One more consent per tenant, separate from mail flow and ATO; the platform holds a write-capable grant before API-2 uses it (API-1 code only reads; no write endpoint exists in the clients); customers may revoke at any time; guides and examples never contain secret-shaped values.

**Alternatives considered.** Add the scopes to the ATO response app (customers wanting only ATO would be forced to grant mailbox write); a separate connector framework or consent screen (duplicates the 8.2 binding, custody, verification and revocation). Details: design §6.
