# ADR-0028: Attachment scanning: one `attachment` engine with ClamAV INSTREAM, YARA-X in a resource-limited inspector process, a known-hash catalog and a signature-versioned cache

**Status:** Accepted (amended by [ADR-0036](0036-dlp-engine-and-extraction.md), implemented in step 4.5: the inspector pool is generalized to `ChildPool` and shared with the DLP extractor children, and the archive walker gained an optional entry visitor; the attachment engine's behaviour, `INSPECTOR_VERSION` and results are unchanged). Amends [ADR-0026](0026-security-scan-pipeline.md) (engine names: `clamav` and `yara` become components of one registered engine `attachment` on `scan.attachment`; the orchestrator, verdicts and rounds are unchanged), [ADR-0024](0024-rabbitmq-topology-retry-dead-letter.md) (topology v4: `scan.attachment` becomes a work queue; `mail.attachment.sandbox_requested.v1` becomes a registered event) and [ADR-0025](0025-message-lifecycle-state-machine.md) (edge E19 also allows role `scanner` with reason `signature_rescan`). Refines [ADR-0022](0022-mime-parsing-and-post-queue-ingestion.md) (step 4.2 decompresses archives in bounded memory as that ADR foresaw; still no extraction to disk). Design: [step 4.2](../../plan/steps/10-attachment-scanning.md).

**Context.** Step 3.1 stores every attachment leaf as an S3 part with its SHA-256, a first-pass sniffed type, filename flags and declared archive metadata. Step 4.1 built the scan pipeline (per-engine queues, rounds, registry, standardized verdicts, breaker, deadline sweeper) with Rspamd as the only engine and left `scan.attachment` dormant. The brief for 4.2 requires ClamAV, YARA, SHA-256, a known-threat hash database, true file-type verification, archive limits (size, decompressed size, depth, ratio), CPU and memory limits per file, type allow/deny rules, no execution and safe temporary handling, a cache keyed by SHA-256 and signature version that never keeps a clean verdict indefinitely, rescans after signature updates, sandbox submission of unknown or suspicious files, and worker scaling. The local Docker VM has 8 GB of RAM and clamd has been OOM-killed before.

**Decision.**

1. **One engine, `attachment`, required for every tenant.** Registered in `ENGINE_CATALOG` (`stage: attachment`, queue `scan.attachment`, `requiredByDefault: true`, `tenantMayDisable: false`) with its adapter in the email-worker scan role (ledger consumer `email-worker.scan.attachment`, broker user `eg-scanner`, `SCAN_CONSUMERS` lets a Deployment run only this consumer). It reads the parse results (never re-parses the EML) and the S3 part objects. A message without attachments and with a complete parse gets the explicit definite outcome `skipped` (`attachment.none`), which the aggregation ignores, so a round is never clean because of the attachment engine without a decision rule.
2. **ClamAV over clamd `INSTREAM` on TCP**, from a bounded in-memory buffer, inside one `IDSESSION` with `VERSION` so each result records the engine and database version of the clamd instance that scanned it. A new package `@email-gateway/clamav` holds the client. clamd unpacks archives itself (including formats our inspector does not support). `HeuristicScanPrecedence no` so a heuristic hit never hides a signature hit; memory-conservative local settings (`MaxThreads 4`, `ConcurrentDatabaseReload no`, a container memory limit).
3. **YARA-X (VirusTotal's maintained YARA) through the `@litko/yara-x` napi binding, run only inside an inspector child process.** The same child does true-type detection (our reviewed magic/structure table), the in-memory archive walk (zip, gzip, tar and their nesting) with depth, entry, entry-size, total-decompressed and ratio limits checked while inflating, encryption and malformation detection, and per-entry SHA-256. The child has no credentials and no inherited environment, never spawns, writes no files (cwd is a private `0700` directory removed on exit), and is killed by the worker on a CPU-time limit (sampled; `RLIMIT_CPU` via `prlimit` as a backstop on Linux), an RSS limit or a wall-clock timeout. CPU and memory kills are definite `suspicious` limit results (properties of the file); wall-clock timeouts and crashes are attempt failures (retried, never clean). Rules ship as a versioned bundle in the repository with a computed bundle id.
4. **Verdict rules are explicit and ordered** (`attachment-map/1`): known-bad hash (high/critical), ClamAV signature or high-severity YARA → `malicious`; ClamAV heuristics/PUA, medium YARA, lower-severity hashes, every limit breach, encrypted archives, deny-listed or not-allowed types (also inside archives), type mismatch or a disguised executable, malformed archives → `suspicious` (tenants may raise the type, mismatch and encryption verdicts to `malicious`, never lower them); unsupported archive formats → `unknown`; `clean` only from a complete inspection with a definite ClamAV `OK`. Engine errors and timeouts are attempt failures through the 4.1 path and end `scan_failed` when the budget is spent.
5. **Known-threat hashes live in the existing platform catalog `malware_signatures`**, evolved by a forward migration (`added_by_user_id`, `reason`, `expires_at`), managed by platform administrators through an audited API, looked up on every scan (never cached). Platform-wide, not tenant-scoped: a malware hash is a global fact, and tenant-specific file blocking is a policy and type-rule concern.
6. **Cache the tenant-independent content result in Redis**, keyed by SHA-256 and a content version that includes the ClamAV engine and database versions, the YARA-X version and bundle id, the inspector version and the platform limits. A new signature database or rules bundle makes old entries unreachable at once. Clean results expire after at most 24 h (default 6 h), malicious after up to 30 days (default 7). Redis failures bypass the cache. Values are authenticated with an HMAC under a key only the attachment worker holds (review round 1): the Redis credentials are shared by every service, so an unauthenticated value could be planted to make a malicious file come out clean; a value with a wrong MAC or shape is ignored and rescanned. Because entries are shared across organizations, the tenant API never shows whether a file was a cache hit, nor the attachment engine's timings.
7. **Signature updates:** a leader-elected watcher records ClamAV database/engine and YARA bundle versions in `scan_signature_versions`. A change creates an audited rescan job (`attachment_rescan_jobs`), executed only when configured (`ATTACHMENT_SIGNATURE_RESCAN=rescan`; default `record`). Platform administrators can also start bounded jobs through an API. Jobs rescan recent, not-yet-delivered messages with attachments whose latest attachment verdict was not malicious, through the existing rescan path (E19, new round, every engine), rate-limited and cancellable.
8. **Sandbox submission is a contract, not a wait.** Suspicious or unknown attachments with a stored part get a `sandbox_submissions` row and a `mail.attachment.sandbox_requested.v1` outbox event in the engine's finalize transaction. `scan.sandbox` stays a dormant bounded queue until step 4.6 consumes it. The round never waits for the sandbox.
9. **Per-attachment results** are persisted in a new partitioned table `attachment_scan_results` (hashes, types, signature and rule names, archive counts and index-path findings; no content, no entry names) and exposed by the existing scan results read API.

**Alternatives considered.** Separate `clamav` and `yara` engines (two S3 reads and archive walks per part, a second queue the topology does not have, a per-attachment verdict split in two). A separate deployable or broker user for attachment scanning (same image and grants; `SCAN_CONSUMERS` gives independent scaling). The yara 4.x CLI per file (temp files, a system package on the host and in the image, a spawn per file), the unmaintained `yara` npm binding, YARA in `worker_threads` (no native memory bound; a native fault kills the worker), a YARA sidecar (one more service on an 8 GB VM). Extracting archives to disk and scanning paths with `clamdscan` (hostile content on disk, a shared volume with clamd). Caching the final verdict (tenant rules and the hash catalog must apply immediately). A new hash table next to the unused `malware_signatures` (two sources of truth). Treating CPU and memory kills as errors (a bomb would be retried to `scan_failed` instead of being classified).

**Consequences.** The email-worker image ships the YARA-X native binary and the rules bundle; production sets `ATTACHMENT_INSPECTOR_RLIMITS=required`. clamd becomes a hard dependency of every round (a down clamd makes rounds `scan_failed` after the retry budget, the intended fail-safe); clamd is sized and scaled separately in production (`ConcurrentDatabaseReload yes` needs about twice the database memory). A rescan job rescans with every engine, not only the attachment engine. The dev pass-through holds `malicious` messages in `scanned` instead of delivering them. Step 4.6 owns the sandbox consumer, the sandbox result event and the `sandbox_submissions` status transitions; step 5.x consumes attachment verdicts and reason codes.
