# ADR-0022: Post-queue MIME parsing in email-worker with mailsplit, our own limits and a stage table

**Status:** Accepted. Refines [ADR-0002](0002-modular-services-nestjs.md) (the "MIME in 3.1" part of the Email Ingestion row of the service map moves to `email-worker`, the Email Processing deployable) and [ADR-0008](0008-object-storage.md) (fixes the `org/{organizationId}/part/...` layout). Consistent with [ADR-0005](0005-rabbitmq-outbox-idempotency.md), [ADR-0006](0006-postfix-mail-path.md) and [ADR-0019](0019-smtp-gateway-topology.md) (the SMTP hot path is unchanged). Design: [step 3.1](../../plan/steps/06-mime-ingestion.md).

**Context.** Step 2.2 already does durable ingestion at SMTP time: the raw EML is streamed to S3 with its SHA-256, the message id comes from `message_identities`, the tenant is resolved from trusted context, and `mail.message.received.v1` is committed with the rows before the `250`. That path does no MIME parsing, on purpose, so the SMTP session stays fast. Step 3.1 has to parse every stored message. Mail content is hostile, so the parser has to cope with malformed MIME, deep nesting, header and part floods, decoding bombs, hostile filenames, unknown charsets and archive bombs. While doing so it must not buffer whole messages, crash, truncate silently or log content. The RabbitMQ relay is step 3.2 and the message lifecycle state machine is step 3.3.

**Decision.**

1. **Where it runs.** MIME parsing is a post-queue consumer of `mail.message.received.v1` in **`email-worker`**. That is the deployable the service map already assigns to Email Processing, and it already declares the queue `email-worker.message-received` that step 3.2 will feed. Parsing is CPU- and IO-heavy and scales with mail volume. It scales independently of smtp-adapter, which is latency-bound at the edge, and of delivery-worker. Until step 3.2 the event is read from `message_outbox` by the shared outbox poller, now in `@email-gateway/common`. That poller can run several messages concurrently per replica and can be sharded across replicas. It sits behind the `EventFeed` interface, and step 3.2 replaces it with a RabbitMQ consumer.
2. **Parser.** **`@zone-eu/mailsplit`** (Andris Reinman, the maintained successor of `mailsplit`, the tokenizer under `mailparser`, WildDuck and ZoneMTA) splits the stream into MIME nodes and body chunks. It ships TypeScript types, parses embedded `message/rfc822` messages as child nodes, tolerates LF, CRLF and mixed line endings, and has its own `maxHeadSize` and `maxChildNodes` guards. Transfer decoding uses `libbase64` and `libqp`, header and parameter decoding (RFC 2047, RFC 2231) uses `libmime`, and charset conversion uses `iconv-lite`. These are the same libraries mailsplit uses, at the versions it pins. We wrap them with our own limits (message size, nesting depth, part count, header count, header line and block size, attachment, body and total decoded size, decoded-to-encoded ratio, wall-clock timeout). The limits are validated in config and checked on the stream before anything is buffered. Breaching a limit is a recorded outcome (`parse_limit_exceeded` plus the limit names), never a crash or a silent truncation.
3. **Not `mailparser`.** mailparser's `simpleParser` buffers whole messages and attachments. It renders text to HTML (`textToHtml`, linkify; GHSA-7gmj-h9xc-mcxc / CVE-2026-3455 is an XSS in that function) and HTML to text (`html-to-text`). It parses address headers with nodemailer's address parser, which had a ReDoS (GHSA-prgh-xp8r-p3m5, fixed in nodemailer 10.0.5) and an infinite-recursion DoS (GHSA-46j5-6fg5-4gv3). It has no depth or part limits. We use none of those code paths. `postal-mime` buffers the whole message. Hand-written MIME parsing is forbidden by the brief.
4. **Archives.** zip metadata (the central directory only, never entry data) is read with **`yauzl` ≥ 3.2.1** (CVE-2026-31988, an out-of-bounds read in the NTFS extra-field date parser, is fixed there, and we never call `getLastModDate()`). It reads through a bounded random-access reader over ranged S3 GETs of the attachment object we just stored. gzip uses its header and ISIZE trailer, taken from the stream. Other archive types are identified by magic bytes and flagged for step 4.2. Compression ratio, entry count, total declared size, encrypted entries, nested archives, overlapping entries (the Fifield non-recursive zip bomb) and path traversal become **flags** for the scanning steps (4.x). No archive is extracted.
5. **Content types** are sniffed from a fixed, reviewed magic-byte table in our code (the first 4 KiB plus fixed offsets such as the tar `ustar` header at 257). `file-type` is ESM-only and does not resolve under this repository's CommonJS/`node10` build. Its scope is also broader than a first-pass hint, and step 4.2 owns full file-type detection. Attachments are never executed, rendered or opened beyond this sniffing and the archive metadata read.
6. **State.** Parse state lives in a new partitioned stage table, `email_message_parses`: one row per message, statuses `parsing → parsed | parsed_with_defects | parse_limit_exceeded | parse_failed`, attempts, limits, defects, body references and the MIME structure. Step 3.1 does **not** change `email_messages.status`. Under the step 2.3 development pass-through the delivery planner moves that column concurrently, and the column belongs to the step 3.3 state machine, which adopts the parse outcomes as its first stage.
7. **Idempotency and contracts.** The ledger is `processOnce` per event (consumer `email-worker.mime-parser`). The parse row is keyed per message, and the final commit is conditional on `status = 'parsing'`. S3 keys are deterministic (`org/{organizationId}/part/{yyyy}/{mm}/{dd}/{messageId}/{partIndex}.{text|html|att}`, with the UTC date of `received_at`). Headers, attachments, `email_events`, the `email_messages` metadata update and `mail.message.parsed.v1` or `mail.message.parse_failed.v1` commit in one writer transaction. A duplicate or concurrent delivery creates no second row, object or event.

**Alternatives considered.** Parsing in smtp-adapter before the `250`: this lengthens every SMTP session and couples edge capacity to parse cost (the brief says no). A new `ingestion-worker` deployable: one more service to run with no scaling benefit over email-worker, whose next stage (scanning, 4.x) consumes the parse output. New `MessageStatus` values written now: they race with the delivery planner under the dev pass-through and pre-empt step 3.3. Buffering parsers (mailparser `simpleParser`, postal-mime): memory grows with message size. Full archive listing by extraction: out of scope, and an archive-bomb risk.

**Consequences.** email-worker needs S3 read and write access (part prefix), and MySQL writer DML on the new table. Library upgrades of mailsplit, libmime, libqp, libbase64, iconv-lite and yauzl are security-relevant: they are pinned exactly and reviewed against GitHub advisories when bumped. Declared zip sizes can lie, so the zip flags are hints. Step 4.2 enforces limits while it actually decompresses. A parser version change can produce different part indices; parse rows record `parser_version`, and re-parsing is a future operation, not part of this step.
