# ADR-0038: DLP masking everywhere, envelope-encrypted evidence with crypto-shredding, audited access, Aadhaar compliance gating

**Status:** Accepted; implemented in step 4.5 (implementation notes below). Design: [step 4.5](../../plan/steps/13-dlp.md) D15–D17, §2.0.

**Context.** DLP findings are the sensitive values themselves. The brief forbids sensitive extracted values in ordinary logs, requires evidence "with appropriate encryption and access restrictions" and masking in administrative interfaces, and allows Aadhaar-like detection only "subject to approved compliance rules". The product rules forbid email content in MySQL. `SecretBox` (`DATA_ENCRYPTION_KEY`, api only) protects MFA secrets and DKIM private keys (ADR-0018).

**Decision.**

1. **Masked values only** in result rows, the scans read API, the incidents API and audit metadata; no values at all in logs, metric labels and events. Masks are per detector (last 4 for numbers, country + last 4 for IBAN, first character + domain for addresses, type only for keys and secrets, ids for dictionary terms).
2. **Evidence** (bounded match snippets with offsets) is sealed with a fresh AES-256-GCM data key per evidence, AAD bound to organization, message and scan; the data key is wrapped under a **dedicated** key-encryption key `DLP_EVIDENCE_KEY` (rotation through `DLP_EVIDENCE_KEY_PREVIOUS`), held only by the dlp-consuming email-worker and the api. The ciphertext lives in S3 (`org/<org>/dlp-evidence/…`); the MySQL row holds the reference, hash, wrapped key and lifecycle — no content.
3. **Crypto-shredding:** the wrapped key exists only in the committed row, so orphaned objects are undecryptable from birth and purge = null the wrapped key, then delete the object (noncurrent versions stay unreadable). Retention per tenant (1–180 days, default 30) by a leader-elected sweeper; tenant purge APIs (MFA, audited).
4. **One audited door:** the evidence endpoint requires `dlp:evidence_read`, MFA and a user principal; an audit row is committed before any decryption; responses are `no-store` and never logged.
5. **Aadhaar gating:** the Aadhaar detector runs only when the tenant has recorded a compliance basis (enumerated basis, reference, attestation, review date ≤ 365 days) through an MFA-protected, audited endpoint with `dlp:compliance_manage`; otherwise it does not run at all. Aadhaar numbers are stored only as masked last 4 — also inside encrypted evidence. Private keys and secret credentials are masked inside evidence too. **Context windows are redacted before sealing, independently of which match they belong to** (step design D16): every credential candidate (CR1–CR5, reportable or not) is type-masked, every Verhoeff-valid Aadhaar-shaped 12-digit run is masked whether or not Aadhaar detection is enabled, every Luhn-valid card number is masked, and CVV/CVC/CSC codes are removed.
6. **Payment cards (PCI DSS):** evidence never holds a full card number (PC1 is kept as first 6 + last 4) and never a card verification code (PCI DSS req. 3.3.1 forbids storing it after authorization, even encrypted), so the evidence bucket and the api stay outside cardholder-data scope. Masked DLP data in the scans read API is returned only to callers holding `dlp:read` (`message:read` alone is held by `read_only_user` and `platform_admin`).

**Alternatives considered.** Evidence ciphertext in MySQL (atomic, but content fragments in MySQL); reusing `DATA_ENCRYPTION_KEY` (gives the worker the key of MFA and DKIM secrets); an asymmetric seal-only key for the worker (the worker reads all mail in clear anyway; key-pair tooling); KMS per evidence (not available locally; a drop-in replacement of the key source later); storing raw Aadhaar numbers encrypted (unnecessary for investigation, conflicts with the compliance gating).

**Consequences.** A database dump, a replica reader, a bucket leak or an api user without the permission learns only masked values; every unmasked read is attributable. Key custody of `DLP_EVIDENCE_KEY` matters (file-mounted secret, Kubernetes Secret for `email-worker-dlp` and `api`). Rotation keeps the previous key for at least the maximum retention; no re-wrap job yet.

**Implementation notes (step 4.5, recorded in [§12](../../plan/steps/13-dlp.md#12-deviations-log) and verified in [§13](../../plan/steps/13-dlp.md#13-verification-results)).** The decisions hold, including the closer-review amendment (decision 6 and the context redaction of D16: credential candidates, Verhoeff-valid 12-digit runs whatever the gating, Luhn-valid card runs and CVV codes are redacted in every context window before sealing). Refinements: (a) the DC1 masked sample is `term #<index>` (the dictionary's public id is in `dictionaryId`; a UUIDv7 can contain long digit runs that the masked-value schema refuses; WP2 deviation 6); (b) the `dlp_evidence.read` audit row's `resource_id` is the message public id, the scan id is in its metadata (WP4 deviation 11); (c) failures after the audit row answer `500 evidence_unreadable` / `503 evidence_unavailable` with `dlp_evidence.read_failed` (WP4 deviation 2). The stack suite `dlp-smtp` reads evidence with an MFA security_analyst (values = the synthetic fixture: cards first 6 + last 4, the IBAN raw; one audit row with ids and the match count) and gets `403` for a read_only_user. Not done: a re-wrap job on key rotation and KMS (as decided).
