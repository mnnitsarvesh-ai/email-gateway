# ADR-0046: Quarantine store written in the policy evaluation transaction; per-recipient decisions; message state vs recipient state

**Status:** Accepted (implemented in step 5.3, verified locally on 2026-11-12: entries written in the evaluation transaction, per-recipient splits, E28/E29, topology v10 and the two roles verified by the `quarantine-smtp` stack suite and the 3-node cluster test on v10; [§12, §13](../../plan/steps/17-quarantine.md#13-verification-results); not verified: Kubernetes apply, CI). Design: [step 5.3](../../plan/steps/17-quarantine.md) Q2–Q8, Q19, Q27, Q28, §3. **Amends** [ADR-0025](0025-message-lifecycle-state-machine.md) (E10 reason `policy_partial`; E16–E18 produced; E26 role `quarantine`; new edges E28 and E29; a second deliberate exception to the append-only enum rule for `QuarantineStatus`), [ADR-0043](0043-policy-dsl-and-deterministic-evaluator.md) (per-recipient evaluation, setting `recipientSplit`, evaluator `policy-eval/2`) and [ADR-0044](0044-policy-evaluation-placement-and-delivery-gating.md) (decision 6: `email.quarantine` is rebound and becomes a work queue, topology v10; the policy-engine image gains a `quarantine` role).

**Context.** Step 5.2 holds QUARANTINE and REQUIRE_APPROVAL messages in `quarantined` / `held_for_review` but writes no quarantine rows; `mail.policy.decided.v1` lands in the dormant, lossy `email.quarantine`. The 1.1 tables `quarantine_messages` (one row per recipient), `quarantine_actions` and `quarantine_release_logs` exist without a producer. The brief requires per-recipient entries idempotent by (message, scan round, recipient), per-recipient decisions where rules are recipient-scoped, partial release, and consistency with the lifecycle. One disposition per message round (5.2) cannot express "deliver to B, hold A". `deriveDeliveryState` already treats `quarantined` and `discarded` recipients as settled.

**Decision.**

1. **The policy-engine's evaluation transaction writes the entries** (together with the evaluation row, the lifecycle edge, recipient states and approvals), not a consumer of `mail.policy.decided.v1`. One entry per `(message, lifecycle round, recipient)` (unique key); duplicates are stopped by the lifecycle edge and the key. Entries carry ids, the 5.1 recommendation, level, hard blocks, floor reasons, decisive rule and the content-free explanation; never message content (`subject` is retired, never written). The bytes stay in S3.
2. **Per-recipient evaluation.** When the tenant setting `recipientSplit` (default true) is on and an active rule of the direction is recipient-scoped, the evaluator runs once per recipient on an input restricted to that recipient (≤ 200 recipients, else message-level). The floor and the platform recommendation are message facts, so every recipient is at least the floor. One merged set of TAG/WARN/URL_REWRITE edits is applied to the delivered copy.
3. **Message state is the delivery-phase view; recipient fate is per recipient.** Allowed recipients are approved (`E10`, reason `policy_partial` when the message is split); quarantined and review recipients get `email_recipients.status = quarantined` and an entry; rejected recipients become `discarded`. With no allowed recipient the message goes to `quarantined` (any quarantine) or `held_for_review`. `email_messages.final_action` gains the value `partial`.
4. **Lifecycle edges.** E16/E17/E18 are produced (role `quarantine`) when the last held entry of a message is quarantined from review, rejected or deleted; E26 accepts role `quarantine` with reason `quarantine_expired`; **E28** `delivered | rejected | expired → approved` (new round, `quarantine_partial_release`) releases a held recipient after the rest of the message finished; **E29** `rejected → quarantined` (`manual_quarantine`) lets an operator recover a policy-rejected message into quarantine. A rescan's evaluation supersedes earlier entries and resets `quarantined` recipients to `pending`.
5. **`QuarantineStatus` is rebuilt** (widen, backfill, narrow) to `held, pending_approval, releasing, released, rejected, deleted, expired, superseded`. The table never had a producer; the rebuild keeps any rows (perf data) by mapping `quarantined → held`, `release_requested → pending_approval`.
6. **Topology v10 and roles.** `email.quarantine` drops its `mail.policy.decided.v1` binding and becomes the work queue of the release executor (`mail.quarantine.release_requested.v1`, ledger `policy-engine.quarantine`); `email.notifications` also binds `mail.quarantine.notification_requested.v1`. The policy-engine image runs roles `evaluate` and/or `quarantine` (`POLICY_ENGINE_ROLES`); Kubernetes deploys them separately (`policy-engine`, `quarantine-worker`) so a quarantine defect cannot stop the delivery gate.

**Alternatives considered.** A consumer of `decided.v1` on `email.quarantine` creating entries: a window without entries, a lossy buffer, and approvals for split recipients that must commit with E10 — rejected. Per-recipient message copies (one message row per recipient): breaks the one-message model of every engine — rejected. A new `quarantine_entries` table: rejected, the 1.1 table is the intended one and is migrated forward. A separate quarantine service codebase: rejected, it would duplicate the evaluator, fact reader and copy pipeline; two Deployments of one image give the isolation.

**Consequences.** Delivery of a split message ends `delivered` (`delivery_partial`) while held recipients wait; their later release re-enters through E28. The 5.2 stack expectation "department exception with a non-member → whole message quarantined" becomes a split (member delivered, non-member quarantined). Readers must use `email_recipients.status` and entries, not only the message state, to know a recipient's fate.
