# ADR-0095: AI assistant reports: native composite tools over loopback reads, server-rendered static HTML in object storage, confirmed email delivery through the notification mailer

**Status:** Proposed (2026-11-23, step AI-R); amended in step AI-6 (2026-11-26) (see [Amendment AI-6](#amendment-ai-6-2026-11-26)). Design: [docs/plan/steps/31-ai-chat-reports.md](../../plan/steps/31-ai-chat-reports.md) §2 (I15–I17, D1–D11), §3, §4, §5; brief [ai-chat-reports.md](../../plan/briefs/ai-chat-reports.md) (product-owner request of 2026-11-22, including the recipient rule). Contracts [§35.3](../contracts.md#353-reports-step-ai-r); topology v15 ([messaging-topology.md](../messaging-topology.md)); migration `20261123074003_ai_assistant_reports` ([docs/database/README.md](../../database/README.md#step-ai-r-migration-20261123074003_ai_assistant_reports)). Related: [ADR-0091](0091-assistant-architecture-loopback-tools.md) (tools bound to operations; amended in AI-R), [ADR-0092](0092-llm-provider-abstraction-and-data-handling.md) (the model is an untrusted client), [ADR-0093](0093-assistant-action-confirmation.md) (confirmations; amended in AI-R), [ADR-0094](0094-assistant-conversation-storage-retention-audit.md) (storage and retention; amended in AI-R), [ADR-0062](0062-sensitive-message-metadata-masking-and-reveal.md) (masking), [ADR-0055](0055-webhook-signing-and-delivery.md) (webhooks and the notification mailer). **Context.** The product owner wants the chat to answer "generate a security report" with a dashboard-style HTML report (summary cards, line, donut and bar charts, tables) shown in the conversation, and "send this report to my email" with a real email, built only from the existing report and statistics APIs. Up to AI-3 every chat tool is exactly one OpenAPI operation executed through the loopback (ADR-0091), and the confirmation flow executes stored requests only through the loopback (ADR-0093). A report needs several reads and a server-side composition; nothing stores or serves HTML today; the notification mailer sends plain text only and reads no object storage; and no recipient policy exists for user-initiated outbound mail. Three new risks come with the feature: HTML/SVG injection through data strings (domain names, account display names), exfiltration of tenant metrics by email (a prompt-injected "send the report to attacker@…"), and a model that misstates numbers.

**Decision.**

1. **Native composite tools (D1, D2, I15).** A _native tool_ is a hand-written registry record (`packages/assistant/src/registry/native.ts`, `native: true`, operation id `AssistantNative_<camel>` never present in OpenAPI, path template `native:<name>` that the loopback client refuses, strict input schema, requirement, `testedBy`, phase `AI-R`). There are exactly two: `report_generate` (read, `read_audited`, requires `report:read`) and `report_send_email` (write, `medium`, confirm with impact, requires `report:read`). `report_generate` is a fixed, server-defined composition of up to ten **internal loopback reads of existing operations** (`/reports/traffic|threats|url-clicks|delivery|processing|top-domains`, `GET /quarantine/summary`, `GET /ato/overview`, `GET /ato/accounts?sort=-riskScore`) with the user's own bearer token, correlation `<turn>.<seq>.<n>` and the native execution's id: guards, RBAC, tenant scope, rate limits, caching and coded errors are the portal's. A source whose permission the principal lacks is not called and its sections are listed as omitted (`permission`); a non-2xx or an unexpected body omits its sections (`unavailable`, `unexpected_response`); all omitted → `503 assistant_report_sources_unavailable`. The model chooses only the period and the sections; every figure is a value of a response fetched in this request. Platform switches `ASSISTANT_REPORTS_ENABLED`, `ASSISTANT_REPORT_EMAIL_ENABLED`; a per-user daily cap `ASSISTANT_REPORTS_PER_USER_PER_DAY` (30).
2. **Inert HTML (D4, I16).** A pure, deterministic renderer in `@email-gateway/assistant` (`REPORT_TEMPLATE_VERSION = 'assistant-report/1'`) writes one self-contained document with **server-side static SVG** charts: no script, no event-handler attribute, no link or URL, no external resource, a constant `<style>` block, a `Content-Security-Policy` meta of `default-src 'none'; style-src 'unsafe-inline'; img-src data:` and `referrer no-referrer`. Every data string passes one sanitizer (control, bidi and zero-width characters removed, length capped) and then HTML escaping; attribute values are constants or formatted finite numbers; colors come from a fixed palette by series index, never from data. An element and attribute **allow-list** is test-enforced by walking the `parse5` tree of every fixture report and by a property test with hostile strings. Size cap `ASSISTANT_REPORT_MAX_HTML_BYTES` (512 KiB; one retry with a truncated data appendix, then `413 assistant_report_too_large`). The portal shows the HTML only in a **sandboxed `srcdoc` iframe** (`sandbox=""`: opaque origin, no scripts, no `allow-*` token), never through `dangerouslySetInnerHTML`, and the api serves it **only inside JSON** (`GET /assistant/reports/{reportId}` → `{ report, html }`, owner only, `Cache-Control: no-store`), so navigating to a URL never renders report HTML on the portal or api origin.
3. **Object storage and retention (D6, D7).** The HTML is an object in the mail bucket at `org/<organizationId>/assistant/report/<yyyy>/<mm>/<dd>/<reportPublicId>.html` (PutObject with `ChecksumSHA256`; the key is checked with the `isKeyOf` pattern before every get and delete, never returned to a client, never logged). MySQL holds metadata only in two new tables: `ai_chat_reports` (window, sections, omitted reasons, figures, size, SHA-256, key, statuses) and `ai_chat_report_deliveries` (one row per confirmed email). The row is written `pending` before the put and becomes `available` in the execution's persist transaction; a `pending` row older than 1 h is swept (object deleted, `failed`). Reports follow the conversation's content retention: purged with the conversation content (at `purge_after` and on delete), objects deleted after the commit in batches, rows hard-deleted with the conversation; the organization purge deletes deliveries, then reports (objects first, then rows).
4. **Confirmed email delivery (D5, D8, I17).** `report_send_email` is a proposal confirmed in the AI-2 card (risk `medium`). The **recipient rule is enforced by the server** at proposal and again at confirm: the principal's own verified address (`self`), an active user with a verified email of the scope's organization (`member`), or an address whose domain exactly equals a `verified`/`active`, not deleted domain of the organization (`domain`); anything else is refused (`denied_guard`, guard `report_recipient_not_allowed`), stores no confirmation and is audited with the domain and a SHA-256 only. Daily limits per user (`ASSISTANT_REPORT_EMAILS_PER_USER_PER_DAY`, 10) and per organization (`ASSISTANT_REPORT_EMAILS_PER_TENANT_PER_DAY`, 50), counted exactly in MySQL per UTC day and re-checked at confirm under a lock of the organization's `ai_chat_settings` row. The confirmed send inserts the delivery row (`queued`, unique `confirmation_id`) and an outbox row **`assistant.report.email_requested.v1`** (exchange `email.policy`, aggregate `assistant_report_delivery`, eventId = the delivery's public id, payload ids and a time only) in one transaction. Topology **v15** binds it to `email.notifications`; the **notification-worker** reads the delivery and report on the writer scoped to the envelope's organization, reads the object (key prefix, size ≤ `NOTIFICATION_REPORT_MAX_HTML_BYTES`, SHA-256 equal to the row's), and sends one mail through the existing `NoticeMailer` and `postfix-notify` relay to the one recipient: the stored HTML as the HTML part, the same bytes attached as `security-report-<date>.html`, a fixed plain-text part with the figures and the portal link, `Auto-Submitted: auto-generated`. It then marks the delivery `sent` (or `failed` with a reason); a redelivered event sends nothing (`status ≠ queued`). `queued` deliveries older than 25 h are failed by the api sweep.
5. **Audit and observability (D11).** `assistant.report_generated` (sources with their HTTP status) and `assistant.report_email_requested` (recipient class, domain and SHA-256) besides the existing tool and confirmation audit rows; metrics without organization or user labels; logs carry ids and codes only, never an address or HTML.

**Alternatives considered** (design §5).

- **A new public route `POST /reports/dashboards` composing in-process.** It would call the quarantine and ATO services directly (a parallel path that bypasses their guards) or need a second loopback mechanism, and a public route would be a second report product.
- **Let the model call the six report tools and pass the numbers to a "render" tool.** Numbers would pass through the model, which could alter them (I15 violated).
- **The AI-6 plan: an async RabbitMQ job with a service principal.** A service principal reading tenant data on the user's behalf weakens I2 and adds a queue for a request that finishes in seconds; AI-6 keeps only scheduled reports as an option.
- **A client-side chart library in the iframe; PNG rasterization.** Scripts break I16 and do not run in mail; PNG needs a native renderer dependency and loses text and accessibility.
- **HTML in MySQL (`MEDIUMTEXT`); a `text/html` route.** Content-like blobs stay out of MySQL (I5); a `text/html` route renders on the api/portal origin when navigated to.
- **Render the HTML into the portal DOM; a separate report origin.** Inline rendering shares the portal's DOM and CSP; a separate origin needs new infrastructure; `sandbox=""` already gives an opaque origin without scripts.
- **The api's own SMTP sender inside the confirm request.** The brief asks for the existing notification mailer; the worker path is retried and idempotent (ledger) and keeps SMTP latency out of the confirm request.
- **HTML body only, or attachment only.** Gmail and Outlook desktop do not render inline SVG: the attachment opens fully in a browser, the body shows cards and tables (every chart has a data table).
- **Any address with re-authentication; a tenant allow-list.** Refused by the product owner (2026-11-22) as an exfiltration risk; a tenant-managed allow-list is a later option.
- **Daily limits in Redis windows.** Limits must be exact and auditable per UTC day and survive Redis loss; the volume is tiny.

**Consequences.**

- ADR-0091 gains its one exception to "a tool is exactly one operation": native tools, whose data still comes only from loopback reads of existing operations (Amendment AI-R). Every later control on those operations applies to reports automatically.
- ADR-0093 gains native writes executed in-process inside the persist transaction, without an `Idempotency-Key` (one delivery per confirmation by the unique `confirmation_id`) (Amendment AI-R).
- ADR-0094 gains report objects in the mail bucket and two tables purged with the conversation content and at organization deletion (Amendment AI-R).
- One migration (176 → 178 tables), one event type (thirty-nine registered), topology v15 (+1 binding: 74), seven configuration keys, no secret. The notification-worker reads object storage for the first time (Kubernetes: `s3:GetObject` on `org/*/assistant/report/*` of the mail bucket for its service account).
- A sent copy in a recipient's mailbox is outside the platform's control (stated in the confirmation warnings). Report generation adds up to ten `expensive` reads per report against the user's own rate limits (the reports module's 60 s cache absorbs repeats).
- Top senders, top targeted recipients and policy hits have no API yet and are not in the report (design R-1); they appear once the routes exist.

## Amendment AI-6 (2026-11-26)

Step AI-6 ([design](../../plan/steps/34-ai-chat-hardening-operations.md) D5, §3, §4; [ADR-0096](0096-assistant-async-report-jobs-session-job-token.md); contracts [§35.6](../contracts.md#356-hardening-and-operations-step-ai-6)) revisits the rejected alternative **(c)** ("an async RabbitMQ job with a service principal"). The rejection of a service principal stands; an asynchronous job is adopted for long windows, acting with a GET-only token of the requesting user's own live session instead (ADR-0096, I26). Decisions 1–5 are otherwise unchanged; I15–I17 hold for asynchronous reports.

- **Asynchronous jobs.** When `ASSISTANT_REPORT_JOBS_ENABLED` and the window is longer than `ASSISTANT_REPORT_SYNC_MAX_HOURS` (168 h), `report_generate` queues the report instead of composing it in the turn: report row `queued`, an `ai_chat_report_jobs` row, the outbox event `assistant.report.generate_requested.v1` (topology v16, queue `assistant.reports`), execution HTTP 202 and a `queued` card in one transaction. The api-assistant `ReportJobConsumer` composes the same report through the same fixed source plan, loopback reads, renderer and object store (one `buildAndStore` path), then marks the report `available`. Windows up to 168 h still run synchronously exactly as in AI-R.
- **`queued` status.** `ai_chat_reports.status` gains `queued` (appended): `queued` → `available` | `failed` | `purged`. The AI-R `pending` sweep ignores it; the job's `expires_at` sweep fails it (`assistant_report_job_expired`); the content purge marks it `purged` and cancels the job. The report view gains `job: { status, attempts, errorCode, expiresAt } | null`; `report_send_email` on a report that is not `available` is refused at proposal (`409 assistant_report_not_ready`). No automatic e-mail when a job finishes (A6-5).
- **Job table.** `ai_chat_report_jobs` (one per queued report, UQ `report_id`, CASCADE with the report and the conversation): owner, the requesting session id and auth methods (no credential), home organization, override id, validated arguments, organization label, status (`queued`, `running`, `succeeded`, `failed`, `cancelled`), attempts, lease, error code, correlation id, `expires_at` (`ASSISTANT_REPORT_JOB_TTL_SECONDS`, 1 800 s) and `reported_at` (outcome given to the model in the next turn's action updates).
