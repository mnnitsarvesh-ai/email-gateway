# ADR-0103: API-mode retroactive clawback and search and purge

**Status:** Accepted (2026-11-27, local verification: program acceptance stack suite `api-mode-clawback.test.ts` 10/10 on the rebuilt mailbox-worker (`clawback`, `reports`), email-worker, notification-worker and event-relay (topology v18) against the idp-simulator and provider-fake — late sandbox verdict clawback through the finalizer's outbox row (§13 A3 fallback) moving the api and hybrid copies with copy authority and `verdictRevision 1`; a platform URL indicator clawing back in two organizations and none in the control organization; admin purges by Message-ID and by sender + subject over 60 mailboxes with the second approver (requester refused `403`), per-mailbox results and bulk restore to the Inbox; `429 Retry-After` during a purge; Gmail soft delete and restore; `clawback.stalled` while paused; api, worker and portal suites of WP1–WP6; live provider tenants, CI and Kubernetes apply pending); proposed by the step API-3 architect, 2026-11-27. **Context.** Brief scope 6: later signals (threat intel, late sandbox/URL verdicts, campaigns, admin decisions) must find and remediate every copy across a tenant's mailboxes, matched by Message-ID, attachment hash, URL or sender + subject + window; admins search and purge manually; purges above N mailboxes (P2, 50) need a second approver. API-2 ([ADR-0101](0101-api-mode-remediation-policy-and-mailbox-actions.md)) provides the only mailbox action engine; ADR-0101 (3) forbids manual hard delete and (4) never remediates inline-authority copies automatically.

**Decision.**

1. **Clawbacks** (`api_clawbacks`) with frozen per-copy targets (`api_clawback_targets`) are created from `mail.threat.late_signal.v1` (email-worker: sandbox risk revisions and late URL dynamic verdicts; topology v18), a mailbox-worker sweep of new threat indicators and malware hashes (per API-active organization with matches), campaign expansions of a seed, report verdicts and admin searches; criteria `api-clawback-criteria/1` over indexed keys only; one clawback per organization and signal.
2. **Targets execute only as `api_remediation_actions` rows** (triggers `clawback`, `purge`) through the `remediate` role. Automatic signals re-decide copies through the remediation policy with the signal's facts (detect-only and pause respected); clawbacks only escalate and skip copies restored after the signal.
3. **Admin purges** preview the materialized hit list and act with quarantine folder, Junk or soft delete; a purge whose eligible targets span more than the organization threshold of distinct mailboxes (default 50), any hard-delete purge and any automatic clawback above its cap need a second user with the new permission `remediation:purge` (5.3 Q14 rules stored on the clawback row like 8.4 ATO responses). The threshold cannot be lifted by the person it checks: whoever raises it through the settings is still checked against the value before their raise (review fix, note 37 §16.2; migration 46).
4. **Supersedes ADR-0101 decision 3 in part:** hard delete may be used by an admin purge through a separate portal-only operation when `API_MODE_HARD_DELETE_ENABLED=true`, always with a second approver; still never in a default, preset, single-copy manual action or assistant tool.
5. **Supersedes ADR-0101 decision 4 in part:** clawback decisions treat hybrid copies with copy authority (the late signal supersedes the inline decision).
6. Every clawback is audited, shows progress and per-mailbox results, and can be **restored in bulk** where the provider allows it (mailbox entries through the stored-verdict restore check).

**Consequences.** One action engine; frozen, auditable purges; large automatic actions need a person; topology +1 binding for signals.

**Alternatives considered.** A separate purge engine; approvals in `quarantine_approval_requests`; synchronous api search; provider-wide live search; api-side TI fan-out (design §6).
