# ADR-0092: LLM provider abstraction and data handling of the AI assistant

**Status:** Proposed (2026-11-20, step AI-1; product owner accepted the design defaults Q1–Q12 on 2026-11-20, including Q1 provider and model, Q2 no email bodies, Q7 budgets, Q8 platform-managed keys, Q10 provider region by configuration); amended in step AI-6 (2026-11-26) (see [Amendment AI-6](#amendment-ai-6-2026-11-26)). Design: [docs/plan/steps/28-ai-chat-management.md](../../plan/steps/28-ai-chat-management.md) §2 D4, D6–D11, §8, §9. Related: [ADR-0091](0091-assistant-architecture-loopback-tools.md), [ADR-0094](0094-assistant-conversation-storage-retention-audit.md), [ADR-0034](0034-bec-ai-layer-invariant.md) (unchanged). Changes no Accepted ADR.

**Context.** The assistant sends a conversation, a tool catalogue and tool results to an external LLM and acts on what comes back. The operator must be able to choose Anthropic, OpenAI or Azure OpenAI (for example an Azure region in India), tests must never reach a model or the internet, and the model must be treated as an untrusted client: it reads mail-derived strings (subjects, display names, file names, URLs) that an attacker controls. The only LLM code today is the BEC layer (ADR-0034, `@anthropic-ai/sdk` 1.1.0, `claude-opus-5-5` at effort `low`, server-side refusal fallback, fake provider refused in production), which sits on the scan path and is never a verdict authority.

**Decision.**

1. **One interface (D6).** `LlmProvider { id, model, complete(request, signal, onDelta) }` in `@email-gateway/assistant`, with `LlmRequest { system, transcript (provider-native, append-only), tools (the two meta tools), maxOutputTokens }` and `LlmResponse { stop, text, toolCalls, appendToTranscript, usage, responseModel }`. Implementations:
   - **Anthropic** through `@anthropic-ai/sdk` 1.1.0 (as BEC): streaming messages with a cached system block, strict tool schemas, `tool_choice: auto`, `output_config.effort = ASSISTANT_EFFORT`, the server-side refusal fallback beta unless `ASSISTANT_REFUSAL_FALLBACK=off`; no `thinking`, `temperature`, `top_p` or forced tool choice (rejected by Claude Opus 5.5); `stop_reason` checked before content; thinking blocks replayed verbatim (preserved thinking); `logLevel: 'off'`, `maxRetries: 0`, injected `fetch`; errors classified by the SDK's typed classes, never by message text.
   - **OpenAI** over plain HTTPS (no SDK, ADR-0082 precedent): Chat Completions with `stream: true`, usage chunk, strict function tools, bounded SSE line parser, zod-validated chunks.
   - **Azure OpenAI**: the same client against `{endpoint}/openai/deployments/{deployment}/chat/completions?api-version=…` with the `api-key` header.
   - **Fake**: deterministic, no network (directives `/tool`, `/describe`, `/text`, a fixed table of demo intents, templated answers, and an adversarial mode for tests that obeys instructions found in tool results); usage computed from text lengths. `ASSISTANT_PROVIDER=fake` is refused at start when `NODE_ENV=production` and the assistant is enabled, as `BEC_LLM_PROVIDER=fake` is (the fake's constructor also refuses production); `fake` is the default, so a production deployment with the assistant off needs no provider.
2. **Configuration** (`assistantConfigShape` of the api): provider, model (default `claude-opus-5-5`), effort (default `low`), credentials only for the selected provider and only while `ASSISTANT_ENABLED` (`_FILE` accepted, never logged or echoed; start-up errors name the key, never the value), https endpoints outside local/CI, timeouts that fit in the turn deadline. Keys are platform-managed (no tenant keys before AI-6).
3. **The model is an untrusted client (I3).** Everything it emits is validated like internet input (ADR-0091 executor). Its permissions are never more than the user's; it cannot confirm, approve, re-authenticate or change the assistant's own settings; in AI-1 it only has read tools.
4. **Metadata-only data sharing (I5, Q2).** No tool returns message bodies or attachments (preview, download and reveal routes are `not_applicable`); the tenant setting `data_sharing` has the single value `metadata` in AI-1 (`pseudonymized` is an AI-6 option). A tenant enables the assistant only with an explicit external-processing acknowledgement; platform operators gate it with the feature `ai_assistant`.
5. **Minimizer and untrusted envelope (D8).** The model receives `assistant-tool-result/1`: at most `ASSISTANT_TOOL_RESULT_MAX_ROWS` rows and `ASSISTANT_TOOL_RESULT_MAX_BYTES` bytes, strings capped at 300 characters, credential-pattern keys dropped at any depth, control, bidi and zero-width characters stripped, mail-derived and attacker-influenced values (manifest `untrustedFields`) plus every free-form response value (objects without declared properties, maps, untyped values: evidence, detail, metadata, criteria, params; added by the registry generator, `freeFormResponsePaths`) wrapped as `{ "untrusted_text": … }`, a fixed note that data is never instructions, and refs `r<seq>.<row>` instead of raw ids where possible. Errors carry the server-authored code and message only. The user sees a separate card (`assistant-card/1`) rendered from the real API response: numbers shown are the API's, not the model's.
6. **Output rendering (D9).** The portal renders assistant text as a restricted Markdown subset into React elements (no `dangerouslySetInnerHTML`); links only to allow-listed internal portal routes; external URLs and images are plain text (no exfiltration through image URLs); assistant text is capped at 16 000 characters.
7. **Injection defences (D10)** are layered and assume the model can be fooled: envelope and sanitizer, system-prompt rules (only the user's messages are instructions; never claim an action without a tool result), read-only tools in AI-1 and from AI-2 no write without a user confirmation the model never sees (ADR-0093), executor and api re-validation, safe rendering. The adversarial fake proves the controls hold in integration tests.
8. **Budgets and isolation (D11).** Platform switch, organization feature, tenant setting; turns per user per minute plus the api rate class `expensive`; concurrent turns per process; tokens per tenant per UTC day (default 1 000 000, tenant may set up to 5 000 000) and per platform (optional); per-turn rounds, tool calls, output tokens, deadline and tool timeout; conversations per user. Redis-backed budgets and a per-provider breaker shared across pods. Cost is advisory (micro-USD per model; OpenAI/Azure prices only by configuration).
9. **Metrics and logs.** `assistant_*` Prometheus metrics without organization or user labels; logs carry ids and codes only, never prompts, responses, tool arguments or results.
10. **Tests never call an LLM (I8).** Providers take an injected `fetch` and are unit-tested with recorded synthetic fixtures; integration and Playwright run the fake provider; a real call happens only when an operator configures a key.
11. **Relation to ADR-0034 and ATP-8.** The BEC AI layer stays as it is (its invariant and data minimization are scan-path specific). ATP-8 ("AI-assisted analysis") reuses this provider layer rather than adding a third LLM client.

**Alternatives considered.**

- **Provider SDKs for OpenAI/Azure** (`openai`): a new dependency for one endpoint; streaming and tool calls are small to parse and validated with zod.
- **Plain HTTPS for Anthropic:** the SDK is already pinned and reviewed for BEC, with typed errors, streaming helpers and betas.
- **Sending raw records or bodies for better answers:** violates Q2 and widens the injection surface; cards already show the user the full API data.
- **Tenant-supplied keys or provider choice now:** key custody, billing and data-processing terms per tenant; deferred to AI-6 (Q8).
- **Trusting the model's text for numbers:** replaced by cards rendered from API responses.

**Consequences.**

- Switching provider or region is configuration; the code paths for all three providers exist and are tested against fixtures, but no real provider call is verified locally (listed as not verifiable in the design §9).
- Chat answers are limited to metadata the user can see in the portal; questions about message content are answered with a link to the portal page.
- Token spend is bounded per tenant and platform; a running turn may overshoot the daily budget by at most one turn.
- Prompt injection through mail metadata can at most mislead the text of an answer; it cannot execute a write, reach another tenant or exfiltrate through rendering.

## Amendment AI-6 (2026-11-26)

Step AI-6 ([design](../../plan/steps/34-ai-chat-hardening-operations.md) §2.0 I25, I27, D3, D6, D7; [ADR-0097](0097-assistant-provider-routing-tenant-keys-pseudonymization.md); contracts [§35.6](../contracts.md#356-hardening-and-operations-step-ai-6)). Decisions 3 and 5–11 are unchanged.

- **Fallback (decision 1).** The single configured provider becomes a **router** over ordered candidates: tenant key (when configured, valid and in use) → platform primary (`ASSISTANT_PROVIDER`/`ASSISTANT_MODEL`) → platform secondary (`ASSISTANT_FALLBACK_PROVIDER`/`ASSISTANT_FALLBACK_MODEL`, default `none`). One Redis breaker per candidate (`as:brk:<provider>`, `as:brk:<provider>:fb`, `as:brk:t:<organizationPublicId>`); the first candidate with a closed breaker is selected at turn start; one same-turn switch only when the first model call fails before any output or tool; `503 assistant_provider_unavailable` when none is healthy. Turns record the provider and model used, `key_source` and `fallback_from`.
- **Tenant keys (decision 2; PO Q8 answered by A6-7).** "Keys are platform-managed (no tenant keys before AI-6)" is superseded: an organization may store its own Anthropic or OpenAI key when the platform enables `ASSISTANT_TENANT_KEYS_ENABLED`, with a model from `ASSISTANT_TENANT_KEY_MODELS` and the platform's endpoints only (no Azure tenant keys). The key is probed before it is stored, encrypted with the dedicated `ASSISTANT_TENANT_KEY_ENCRYPTION_KEY` (row-bound AAD, `kid`, ADR-0077 construction) and write-only (I27). Tenant and per-user budgets count tenant-key turns; the platform daily cap does not.
- **`pseudonymized` level (decision 4).** `data_sharing` gains `pseudonymized` (recorded per turn): e-mail addresses, IPs, domains and person names in known name fields are replaced by stable per-conversation tokens (`[EMAIL_n]`, `[IP_n]`, `[DOMAIN_n]`, `[PERSON_n]`) in everything the model reads, after the minimizer of decision 5; forged tokens in inbound text are neutralized; tool arguments are de-mapped before validation (unknown token → `denied_schema`) and streamed text before it reaches the browser. The mapping (`ai_chat_pseudonyms`) follows the conversation's content retention (I25). `metadata` stays the default; free-text names are not detected (A6-3).
- **Segment rebinding.** A context segment is bound to one provider and model (preserved thinking forbids replaying native history to another one): a provider or model change starts a new segment from the deterministic recap, with no model call; a same-turn switch rebuilds the context the same way.
- **Metrics** gain the label `role` (`primary|fallback|tenant`) and the series of ADR-0097; labels still never carry organization or user ids. Tests still never call an LLM (decision 10): probes and tenant-key calls use injected local fakes.
