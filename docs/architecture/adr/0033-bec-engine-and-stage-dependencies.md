# ADR-0033: BEC engine on `scan.bec` and second-stage engines triggered by their dependencies

**Status:** Accepted; implemented in step 4.4 (implementation notes below). Amends [ADR-0026](0026-security-scan-pipeline.md) (decision 1 "choreography over per-engine queues" and decision 3 "the orchestrator is unchanged when an engine is added": engines may now declare dependencies and are triggered after them) and [ADR-0024](0024-rabbitmq-topology-retry-dead-letter.md) (topology version 6: queue `scan.bec`, event `mail.message.scan_stage_ready.v1`). Design: [step 4.4](../../plan/steps/12-phishing-bec.md) B1–B3.

**Context.** Phishing/BEC detection needs the authentication results of the Rspamd engine (`email_auth_results`) and the URL engine's verdicts of the same scan round. ADR-0026 runs all engines of a round in parallel off `mail.message.parsed.v1`; reading another engine's result at an arbitrary moment makes a verdict depend on arrival order (the reason step 4.3 refused to read Rspamd URL symbols). The reserved queue `scan.auth` has no consumer.

**Decision.**

1. A required engine `bec` (stage `bec`), consumed by the email-worker scan role from a **new work queue `scan.bec`** (ledger consumer `email-worker.scan.bec`). `scan.auth` stays reserved for a first-party authentication engine.
2. The engine catalog gains `dependsOn` (depth 1). An engine with dependencies is a **stage-2 engine**: its queue binds only `mail.message.scan_stage_ready.v1`. The completion check (message and scan rows locked, finals read after the locks) writes exactly one `scan_stage_ready.v1` outbox row per stage-2 engine, in the transaction that inserts the **last** dependency final of the round (definite or failure). The deadline sweeper writes no trigger; it finalizes every missing required engine, stage-2 included, as `timeout`.
3. A stage-2 engine never opens a round; it joins the existing `email_scans` row named by the event. Missing or failed dependency results are explicit inputs (`not available` reason codes) and never yield `clean`.
4. The minimum round deadline is the longest stage-1 budget plus the longest stage-2 budget.

**Alternatives considered.** Reusing `scan.auth` (misleading name, loses the reserved slot); consuming `parsed.v1` and reading what exists (order-dependent verdicts); deferring with retries until dependencies finish (attempts, backoff latency, noise rows); polling inside the adapter (holds consumer slots); a central saga (rejected by ADR-0026).

**Consequences.** One more quorum queue (17) and grant; BEC latency is the slower of Rspamd/URL plus one outbox hop; a lost trigger ends the round `scan_failed` at its deadline (alert `BecStageTriggerStall`), never `scanned`. Future engines (DLP, sandbox) may declare dependencies the same way.

**Implementation notes (step 4.4, recorded in [§12](../../plan/steps/12-phishing-bec.md#12-deviations-log) and verified in [§13](../../plan/steps/12-phishing-bec.md#13-verification-results)).** The decisions hold. Details that differ from or refine the design text, each with evidence in §12: (a) the default minimum round deadline is 1 755 s, not 1 395 s, because the attachment engine (6 × 240 s) dominates stage 1 (WP3 deviation 1; default deadline 1 800 s unchanged); (b) a stored rule's `evidence` is an array of ≤ 5 entries (B6), and the read API returns it as an array (WP2 deviation 6, WP4 deviation 1); (c) the bec final row records the effective thresholds in `scan_engine_results.evidence.thresholds`, so the read API shows both (WP4 deviation 2, fixed in WP5); (d) a bec `malicious` makes the round `malicious`, so the dev pass-through holds it under the earlier `malicious_verdict` rule; `bec_verdict` is counted for a `suspicious` bec result in a non-malicious round (stack `bec-smtp`); (e) since the bec final normally completes the round, the `scanning → scanned` history row is caused by the stage trigger's event id, not by `parsed.v1` (stack `scan-pipeline`); (f) the scanner's retry/dead-letter grants keep the v5 `.org.` anchoring (WP1 deviation 1); (g) the Kubernetes event-relay `RECONCILE_QUEUES` now lists the scan queues including `scan.bec` (WP5 fix). Not verified: the Kubernetes manifests were rendered, never applied.
