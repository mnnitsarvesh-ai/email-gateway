# ADR-0058: Admin portal architecture (App Router, BFF and browser session, generated client, data fetching, dev fixtures, CSP)

**Status:** Accepted (2026-11-13, step 7.1 WP6; designed in [docs/plan/steps/20-admin-portal.md](../../plan/steps/20-admin-portal.md) P1–P11, foundation by WP2). Verified end to end on the local stack ([verification record](../../plan/steps/20-admin-portal.md#14-verification-record)): the Playwright suite `tests/portal-e2e` (43 tests in Chromium 1.64.1 against the real api, MySQL writer and replica, Redis and MinIO; the portal production build) covers password, TOTP, recovery-code and forced-enrollment logins, silent refresh after the 60 s access token of the e2e api expired, parallel requests and two tabs at expiry, sign-out everywhere, the CSRF-protected BFF, the contract allow-list, tenant isolation and the audited override, with every request outside the portal's origin aborted and every CSP violation failing the test; the image builds alone with the drift check and the mock-layer assertion, contains no fixture marker, runs as `node` with a read-only root filesystem and a healthy `HEALTHCHECK`, and answers with the CSP and security headers. Four defects found by the suite were fixed (§13 WP6): a proactive-refresh loop with short tokens, a refresh that could re-create the cookie after a logout, a stale session cache after MFA enrollment, and the override banner not clearing on "End now". **Not verified:** a Kubernetes apply, CI, real production TLS/Ingress behaviour. Related: [ADR-0059](0059-admin-portal-design-system.md) (design system), [ADR-0060](0060-portal-ingress-and-trusted-client-ip-forwarding.md) (portal Ingress and trusted client-IP forwarding), [ADR-0016](0016-authentication-sessions-rbac.md) (authentication, sessions, RBAC), [ADR-0050](0050-api-conventions.md)–[ADR-0052](0052-rate-limiting-and-idempotency.md) (API conventions, pagination, idempotency).

**Context.** The api returns access and single-use refresh tokens in JSON bodies and leaves cookie handling to the portal (authentication.md). Two concurrent refreshes of one refresh token look like reuse and revoke the whole session. The brief forbids tokens in `localStorage`, requires the tenant to come only from the authenticated context, requires a client generated from (or checked against) the OpenAPI snapshot, realistic mock data only in development, and a production build without any mock code. Three page packages build 22 pages in parallel on one foundation. The platform sends emailed links with the token in the URL fragment (`/auth/<…>#token=`).

**Decision.**

1. **Next.js 15 App Router, client-rendered console.** Route groups `(auth)` (public pages), `(console)` (authenticated shell, `force-dynamic`), `auth/` (the three emailed-link pages), `mfa/enroll`, `bff/` (route handlers), `api/health` (probe). Console pages are client components fetching through the BFF with TanStack Query; server components render only frames. The console never fetches tenant data on the server, so no server-side token refresh and no tenant data in RSC caches.
2. **BFF with a sealed httpOnly session cookie.** Route handlers under `/bff` are the only holders of tokens. The session (`__Host-eg_session`, or `eg_session` on an http origin in local/ci) is AES-256-GCM sealed JSON (Web Crypto, key `PORTAL_SESSION_KEY`, unseal-only `PORTAL_SESSION_KEY_PREVIOUS`, AAD per purpose, `v1.<iv>.<ciphertext>`), `HttpOnly; Secure; SameSite=Strict; Path=/`, `Max-Age` until the refresh-token expiry, at most 3,800 bytes (an override that does not fit is ended and refused, never truncated). The MFA challenge has its own sealed cookie; the CSRF token is a readable double-submit cookie rotated with every new token pair. Session routes: login, MFA, refresh (`{ force? }`, "fresh enough" short-circuit within 60 s of a previous refresh), session view (no tokens), logout and logout-all (cookies cleared even when the api fails), override start/end (the override token stays in the cookie), and the platform readiness card (`platform:operations` checked with `GET /auth/me`).
3. **One refresh coordinator in the browser.** The proxy never refreshes; it answers `401 access_token_expired` when the sealed access token expired. The client refreshes once (in-memory single flight plus `navigator.locks` across tabs), retries the failed request once, refreshes proactively while visible (60 s before expiry, but never before half of the remaining lifetime and never sooner than 5 s: with the api's minimum 60 s token a fixed 60 s lead meant "refresh now" after every refresh, a loop found by WP6), and sends the user to `/login?next=…&reason=expired` when the refresh fails. Sign-out, sign-out-everywhere and starting or ending an override take the same Web Lock, so a refresh in flight never re-creates the session cookie after a logout. Those four BFF session routes refresh an expired access token server-side before calling the api (under that lock, so the single-use refresh token never races), so a sign-out or an override end really reaches the api. An api `401 unauthorized` makes the client force its refresh past the BFF's "fresh enough" short-circuit, so revocation surfaces at the next request (closing round of step 7.1).
4. **Generic proxy restricted to the contract.** `/bff/api/v1/*` resolves method and path against a route table generated from `docs/api/openapi.json`; anything else is `404 route_not_found`; traversal and smuggling (`..`, encoded slashes and backslashes, `//`, NUL, malformed encoding) are refused; the upstream path is rebuilt from the template. Token-bearing operations are refused (`403 bff_route_required`). Request and response headers are allow-listed; the BFF sends the session or override token (never a tenant header), `X-Correlation-Id`, and the trusted forwarder headers of ADR-0060; bodies are limited to 1 MiB and stream back unchanged with `no-store` and `nosniff`; timeouts map to `504 upstream_timeout`, connection failures to `502 upstream_unavailable`. Portal-coded errors use the api envelope.
5. **CSRF:** every non-GET `/bff` request must come from the portal origin (`Origin`, else `Sec-Fetch-Site: same-origin`; middleware and handlers both check) and, when it carries the session, present the CSRF token (constant-time). `SameSite=Strict` is the third line.
6. **One typed client generated from the snapshot.** `scripts/generate-api.mjs` writes `schema.gen.ts` (openapi-typescript) and `operations.gen.ts` (per operation: method, path, tag, permissions, public, idempotency, cursor, rate class, secret flags, list key, allowed sort values, BFF-only; plus the proxy's matcher table). `--check` regenerates in memory and fails the `build` and `typecheck` scripts and a Vitest test on drift; turbo includes the snapshot in the portal's task inputs. Feature code calls `api.GET('/api/v1/…')` (openapi-fetch, base `<origin>/bff`) or `callOperation(operationId, …)`; middleware adds the CSRF header, an `Idempotency-Key` for `required`/`legacy` operations, error normalization (`ApiError`) and the refresh-once rule. ESLint forbids other `fetch` calls to `/bff/api`.
7. **Data fetching and mutations (P8).** Query keys `[operationId, params]`; retries only for network errors and `503`; URL state for filters, sort, range and tab; forward keyset pagination with a cursor stack (no totals); `useApiMutation` creates one `Idempotency-Key` per intent and reuses it for retries, waits on `409 idempotency_request_in_progress`, treats `Idempotency-Replayed` as success, maps `400` to fields, counts down `429`, and raises an MFA dialog on `403 mfa_required`. Secret-bearing results are never cached (`gcTime: 0`).
8. **Permission-aware navigation (UI only).** A single navigation model with gates expressed as OperationId lists evaluated against `GET /auth/me` permissions (`all`/`any` like the api); `<RouteGate>` renders the 403 view for direct visits; `<Can>` hides actions. Tenant switching is only the audited platform override through the BFF; caches are cleared on start and end; an amber banner shows while it is active.
9. **Dev fixture mode.** `PORTAL_DEV_MOCKS=enabled` replaces the BFF's upstream `fetch` with typed fixture handlers keyed by OperationId (synthetic, seeded, `*.example.test` / `example.com`; `501 mock_not_implemented` otherwise), so session and proxy paths behave exactly as against the api. It loads only through `process.env.NODE_ENV === 'development' && config.PORTAL_DEV_MOCKS === 'enabled'`; production builds alias the module to a throwing stub and exclude its sources from file tracing; the config refuses `enabled` outside development, `next.config.ts` throws with `NODE_ENV=production`, and `scripts/assert-no-mock-layer.mjs` fails the build if the fixture marker or path appears anywhere under `.next` (server, static, standalone). A "DEV FIXTURES" badge shows in the top bar.
10. **Security headers.** Middleware (Node runtime) sets a per-request nonce CSP (`script-src 'self' 'nonce-…' 'strict-dynamic'`, `'unsafe-eval'` and `ws:` only in development, `frame-ancestors 'none'`, `base-uri 'none'`, `object-src 'none'`, `upgrade-insecure-requests` and HSTS on https), passes the nonce to Next and next-themes through request headers, and redirects console routes without a readable session to `/login?next=`. `next.config.ts` adds the static headers (frame, nosniff, referrer, permissions, COOP, CORP). Only `NEXT_PUBLIC_*` variables could reach the browser and none exist; every `src/server` module imports `server-only`; a test greps the client build output for server key names and values and token prefixes. Fonts are self-hosted.
11. **Emailed links** read `#token=` once, clear it from the address bar (`history.replaceState`) and call the public operations through the proxy.

**Alternatives considered.** Tokens in `localStorage` with direct CORS calls (XSS steals long-lived refresh tokens; forbidden). A Redis session store behind an opaque cookie (gives the portal a data-store credential and a second session system). Refreshing transparently in the BFF on `401` (parallel requests and replicas would reuse single-use tokens and end sessions). Server components fetching tenant data (server-side refresh races, tenant data in RSC caches, harder CSP). Trusting `X-Forwarded-For` at the api (ADR-0060). MSW in the browser for development (does not cover BFF and session paths; needs a service worker and `worker-src`). Hand-written API types (drift invisible). Full hook generation with orval (large generated surface; cursor, `items`, idempotency conventions still need wrappers).

**Consequences.** The api stays the only session authority; the portal holds only the sealing key and the forwarder token. A changed OpenAPI snapshot fails the portal build until the client is regenerated and compiles. Every console route is dynamic (nonce CSP). The cookie budget limits token sizes (two ~800-character JWTs and a 255-character organization name fit). Local `PORTAL_TRUST_PROXY_HOPS=0` derives the client IP from the socket peer Next fills in, which a client talking to the portal directly can spoof with its own `X-Forwarded-For`; the configuration therefore refuses `0` outside `APP_ENV=local|ci` (deviation recorded in the design note §13). Verified by WP2: unit and component tests (BFF, client, middleware, generator, mock guard, contrast, components, auth pages), the production build with the drift check and the mock-layer assertion, and a local smoke run (`next start` against the api on the host: login of a throwaway invited platform user, MFA enrollment through the proxy, forced refresh, platform readiness, logout-all). Verified by WP6: the Playwright suite and the container image (see the status). Not verified: a Kubernetes apply, CI.
