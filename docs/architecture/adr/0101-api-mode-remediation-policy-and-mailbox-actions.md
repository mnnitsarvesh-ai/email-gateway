# ADR-0101: API-mode remediation policy and mailbox actions

**Status:** Accepted (2026-11-27, local verification: stack suite `api-mode-remediation.test.ts` 9/9 on the rebuilt mailbox-worker (`copies` + `remediate`) against the idp-simulator — P1 decision in the copy transaction for an EICAR journal copy, located by Internet Message-ID and moved to the hidden quarantine folder within seconds; spam → `tag` (Graph category) and its `remove_tag`; detect-only recorded `simulated` with no simulator write call; a hybrid copy with inline verdict authority `skipped inline_authority`; a scripted `429 Retry-After: 2` on the move paused and retried without counting an attempt (`remediation_throttled`); Gmail STRICT preset → `SPAM` label; a revoked grant failed the pending action `mailbox_access_revoked` with health `failing`, the `remediation.access` warning and the `api_mode_unhealthy` e-mail; overview remediation block consistent; regression `api-mode.test.ts` 11/11, `quarantine-smtp` 15/15, `journal-intake` 12/12; live provider tenants, CI and Kubernetes apply pending). Superseded in part by [ADR-0103](0103-api-mode-clawback-search-and-purge.md) (decisions 3 and 4) (step API-3, 2026-11-27): an admin **purge** may use hard delete through a separate portal-only operation when `API_MODE_HARD_DELETE_ENABLED=true`, always with a second approver (single-copy manual remediation, presets, defaults and the assistant still never hard-delete); clawback decisions treat hybrid copies with copy authority, because the late signal supersedes the inline decision (the first-time copy decision keeps `skip inline_authority`).

Superseded in part by [ADR-0105](0105-api-mode-copy-policy-evaluation-and-policy-lane.md) (decision 1) (step API-4, 2026-11-27): the remediation decision has a verdict lane (these rules, unchanged) and a policy lane fed by the copy's detect policy evaluation through the document-level `policyMapping` (default quarantine / require approval / reject → quarantine folder, tagged allow → tag, never hard delete); the stronger action wins, a tenant allow override suppresses verdict-only remediation, the reserved `when.policyDispositions` stays refused (`use_policy_mapping`), and decisions are recorded as `api-remediation-decision/2`. Remediation policies may also carry a detect-only period ([ADR-0107](0107-api-mode-onboarding-provider-ownership-scope-detect-only.md)).

**Context.** Brief scope 4: after-delivery remediation in Microsoft 365 / Google Workspace mailboxes driven by the verdict, idempotent, throttled per tenant, audited, reversible where possible; default P1. API-1 ([ADR-0100](0100-api-mode-intake-mailbox-worker.md)) stores a verdict per mailbox copy and holds a write-capable mailbox grant ([ADR-0099](0099-mailbox-access-consent-and-custody.md)). Tenant policy evaluation on copies is deferred by the product owner (2026-11-26, design §12.2 PO-D2).

**Decision.**

1. **A remediation policy** per organization with optional per-domain overrides (`api_remediation_policies`, one row per scope through the STORED generated `scope_key = COALESCE(domain_id, 0)`; document `api-remediation-policy/1`: ordered first-match rules over verdict, risk level, score and hard blocks → `move_quarantine | move_junk | tag | soft_delete | hard_delete | none`; mode `detect_only | enforce` as a column). Without a row the platform default **P1** applies (high-confidence malware/phishing — any hard block or level `critical` — → quarantine folder; other malware/phishing and suspicious/BEC → tag; spam, bulk and DLP → nothing; never hard delete). Presets P1, "Detect only" (recommended start for new tenants) and Strict (P1 + spam → Junk); no preset contains `hard_delete`. The decision function `decideRemediation` takes a reserved policy-evaluation input (`policyOutcome`, always `null` in API-2) and the schema reserves `when.policyDispositions` (refused today), so a later step can add policy results as a second input.
2. **Decisions are taken in the mailbox-worker `copies` transaction** of `mail.message.copy_scanned.v1` (atomic with the copy's verdict; ledger-protected). Actions are rows of `api_remediation_actions` with a unique `action_key` (SHA-256 of `api-remediation/1`, copy public id, action and generation; every writer uses `INSERT IGNORE`), executed by the new **`remediate`** role (a lease-based claim loop over the table, modelled on the feeds) through the API-1 clients with the per-connection budgets, the shared `Retry-After` pause, back-off (30 s doubling to 1 h) and bounded attempts (8; locate by Message-ID 6). The executor re-reads the provider state before acting (`already_in_target`), so a crash or lease expiry repeats nothing harmful. Manual remediation, restores and retries requested through the api are rows in the same table. Every executed action writes one system `audit_logs` row (`api_mode.remediation_executed`, ids and codes only).
3. **Provider actions.** Microsoft Graph (`Mail.ReadWrite`): a hidden quarantine folder `API_MODE_QUARANTINE_FOLDER_NAME`, the well-known `junkemail`, categories for tags, `recoverableitemsdeletions` for soft delete, `permanentDelete` for hard delete; the id a move returns is stored and used for a later restore (locate fallback). Gmail (`gmail.modify`): a hidden quarantine label, `SPAM`, a tag label, Trash. **Hard delete** needs `API_MODE_HARD_DELETE_ENABLED=true` **and** an explicit tenant rule, falls back to Trash on Gmail (`gmail.modify` cannot delete permanently; recorded as `hard_delete_unsupported_provider`), and is never manual or from the assistant.
4. **Hybrid:** copies whose verdict authority is `inline` are never remediated automatically (`skip inline_authority`); an admin may still remediate one manually.
5. **State and observability:** the copy carries `remediation_state`, `remediation_action` and `remediation_generation` (a successful reversal increments it, so a later remediation gets a fresh key); a per-connection `remediation_paused` stops policy actions (restores continue); hourly counters on `api_mode_counters`, four health checks `remediation.*` appended to `api-mode-health/1`, metrics and Prometheus rules, and the existing alert kind `api_mode_unhealthy`. **Topology unchanged (v17):** no new queue, event, binding, policy or role user; no new permission (`remediation:read` / `remediation:write` from API-1) and no new feature key.

**Consequences.** Two tables (not partitioned), one worker role, no new queue or permission; detect-only gives a safe start; a bad policy is reversible (every action except hard delete, which is off by default) through the quarantine pages and the remediation history; a tenant's provider call rate stays within one budget shared with feeds and inventory. Action rows hold ids, enums, codes, counts, timings and opaque provider ids only. Re-deciding copies on late verdicts (sandbox revision 1) is not done in API-2 (API-3 clawback).

**Alternatives considered.** A command queue (outbox → `email.remediation` → worker; still needs the table for back-off, leases and history); remediation records only as quarantine entries (tags, hard deletes, simulated and skipped decisions and reversals are not entries); Graph immutable ids; Deleted Items for soft delete (user-visible, one click from the Inbox); requesting the full Gmail scope `https://mail.google.com/` (broader than ADR-0099 consented); detect-only as the universal default (P1 says high-confidence threats move automatically); partitioning `api_remediation_actions`. Details: design §6.
