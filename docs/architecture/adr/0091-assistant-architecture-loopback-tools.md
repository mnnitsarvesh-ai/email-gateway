# ADR-0091: AI assistant architecture: an api module, tools bound to public operations, executed through the api's own pipeline

**Status:** Proposed (2026-11-20, step AI-1; product owner accepted the design defaults Q1–Q12 on 2026-11-20); amended in step AI-R (2026-11-23) (see [Amendment AI-R](#amendment-ai-r-2026-11-23)). Design: [docs/plan/steps/28-ai-chat-management.md](../../plan/steps/28-ai-chat-management.md) §2 (I1–I8, D1–D5), §4.1, §4.4, §5. Related: [ADR-0092](0092-llm-provider-abstraction-and-data-handling.md) (providers and data handling), [ADR-0093](0093-assistant-action-confirmation.md) (confirmations), [ADR-0094](0094-assistant-conversation-storage-retention-audit.md) (storage, retention, audit). Changes no Accepted ADR.

**Context.** The product owner wants every operation of the admin portal to be available through a chat. The portal has no business logic of its own (ADR-0063): every UI action is one public `/api/v1` operation, 381 of the 403 operations in `docs/api/openapi.json`. The behaviour that makes an operation safe is spread over the HTTP pipeline, not the services: `AuthGuard`, `ApiRateLimitGuard` and `PermissionsGuard` (fail-closed, MFA, `@UserOnly`), zod pipes, the idempotency interceptor, the platform-override audit interceptor, signed cursors, masking (ADR-0062) and the coded error mapping (ADR-0050–0053). A chat that called services directly, or re-implemented checks, would be a second, weaker path into every module.

**Decision.**

1. **Placement (D1).** The assistant is a Nest module of the api (`apps/api/src/modules/assistant`) plus a pure package `@email-gateway/assistant` (providers, prompt, context, minimizer, registry, stream contract); no new deployable in AI-1. It neither publishes nor consumes RabbitMQ messages, and no worker, smtp-adapter or policy-engine code changes (I7: its failures degrade chat only). Production may later route `/api/v1/assistant` to a second Deployment of the same image (AI-6).
2. **Loopback execution (D2, I1, I2).** A tool is exactly one existing `/api/v1` operation. `AssistantLoopbackClient` sends the same HTTP request the portal would send to `ASSISTANT_LOOPBACK_URL` (empty = the api's own listening address) with the incoming request's `authorization` header verbatim, `x-correlation-id = <turn correlation id>.<execution seq>`, the trusted-forwarder client IP when configured (ADR-0060), `accept: application/json`, `user-agent: eg-assistant/1` and an informational `x-eg-assistant-execution`. No other header is ever set from model output; path parameters are encoded after schema validation, and a value that would not stay one path segment (`''`, `.`, `..`) is refused so the executed route is always the registered (recorded, audited, from AI-2 confirmed) one; the response body is capped at 1 MiB. Guards, MFA, tenant scope (ADR-0016), rate limits (tool calls count against the user's own API limits), idempotency, masking, cursors, audit and coded errors are therefore exactly the portal's. Nothing in the api trusts a header from the assistant for authorization; the one header it honours, `x-eg-assistant-read-primary` (step AI-2 review: the precondition reads of a confirmation, value derived from `AUTH_TOKEN_PEPPER`), only moves that request's reads from the replica to the writer. Tools run only inside a live request of the user with that request's credential; no credential is stored or minted. The assistant's own routes (tag `assistant`) are never tools.
3. **Registry from OpenAPI plus a manifest (D3).** `packages/assistant/scripts/generate-registry.mjs` reads `docs/api/openapi.json`, a classification manifest (rules plus per-operation overrides) and the portal's operation usage, and writes `operations.generated.ts` (one record per classified operation: deterministic `name`, `operationId`, method, path template, module, summary, description, input JSON Schema with `additionalProperties: false`, `requirement` copied from `x-eg-permissions`, idempotency, rate class, cursor, `access`, `risk`, `confirm`, `phase`, `status`, `enabled`, `portalRoute`, display hints, `untrustedFields`, bindings) plus `REGISTRY_VERSION`, and the capability matrix `docs/assistant/UI_TO_CHAT_CAPABILITY_MATRIX.md`. Tests enforce **completeness** (every operation is a tool or `not_applicable` with a reason; a later step's new endpoint fails the build until it is classified) and **consistency** (`requirement` equals `x-eg-permissions`; `x-eg-returns-secret` operations and the tags `auth`, `mfa`, `sessions`, `meta`, `assistant` are `not_applicable`; no `write` tool is enabled in AI-1; a write can be enabled only with a named `testedBy` suite).
4. **Two meta tools (D4).** The model sees exactly two provider-level tools, identical for every provider: `describe_tool { name }` and `call_tool { name, arguments }`. The system prompt carries a deterministic catalogue index of the user's available tools only (permission pre-filtered, grouped by module, one signature line each), so the prompt is cacheable and about 3–5k tokens for 174 read tools.
5. **Executor order (D5).** For each `call_tool`: per-turn cap (`denied_budget`), registry lookup (`denied_unknown_tool`, `denied_not_applicable` with the portal link, `denied_disabled`), **permission pre-filter** with `satisfiesRequirement(principal, requirement)`, the predicate extracted from `PermissionsGuard` into `apps/api/src/auth-contracts/authorization.ts` and used by both (one implementation; `denied_permission`), `self_organization` bindings, refs `@r<seq>.<row>` resolved only within the conversation (`denied_ref`), strict Ajv validation (`denied_schema`, paths only), then the loopback call (a `401` ends the turn `assistant_session_expired`). Every decision, allowed or denied, is a recorded execution and an audit row (ADR-0094). The guard still runs on every loopback call: the pre-filter only hides tools and avoids pointless requests. API keys cannot chat (`@UserOnly`).
6. **Risk classes (§4.4).** `read`, `read_audited`, `low`, `medium`, `high`, `critical`; `critical` (organization deletion and status, legal-hold release, archive disposal and key rotation, DLP evidence purges, BEC history purge) and every content, preview, download, reveal, credential, consent and override operation are `not_applicable`: the chat links to the portal page. AI-1 enables the 174 eligible reads; writes come from AI-2 behind ADR-0093.

**Alternatives considered.**

- **Call services directly with the principal.** Skips guards, rate classes, idempotency, override audit, cursor signing and serialization: a parallel path into every module (rejected by I1).
- **Invoke controller methods through `ModuleRef` and re-run guards manually.** Re-implements Nest's pipeline and still misses interceptors and pipes.
- **A separate assistant service calling the api over the network.** The same HTTP contract plus a new deployable, Dockerfile, auth relay and operations surface; kept as the AI-6 route-split option (same image).
- **Hand-written tool list / runtime generation from Swagger.** Hand lists drift and invite "example tools only"; the Swagger document is not built in production (ADR-0053) and is slow at boot; the committed snapshot is already guarded by the e2e test.
- **One provider tool per operation or provider-specific tool search.** About 100k tokens per request for 348 schemas, provider limits, not portable to OpenAI/Azure.

**Consequences.**

- The assistant can never do more than the user can do in the portal, and every control the api gains later applies to chat automatically.
- Tool calls consume the user's own API rate limits and take one extra in-process HTTP hop (keep-alive, concurrency-capped by `ASSISTANT_MAX_CONCURRENT_TURNS`); heavy use shares api capacity until the AI-6 route split.
- Every later step that adds or changes an operation must classify it in the manifest and regenerate the registry, or the build fails.
- The shared permission predicate is a small refactor of `PermissionsGuard`; its unit tests prove the guard's decisions are unchanged.

## Amendment AI-R (2026-11-23)

Step AI-R ([design](../../plan/steps/31-ai-chat-reports.md) §2.0 I15, D1, D2; [ADR-0095](0095-assistant-reports-native-tools-static-html-email.md); contracts [§35.3](../contracts.md#353-reports-step-ai-r)) adds the one exception to "a tool is exactly one existing `/api/v1` operation" (decision 2): **native tools**. The rest of the decision is unchanged.

- **What a native tool is.** A hand-written registry record in `packages/assistant/src/registry/native.ts` next to the generated operation records (`native: true`, operation id `AssistantNative_<camel>` that never appears in OpenAPI, nominal method `POST`, path template `native:<name>`, strict input schema with `additionalProperties: false`, `requirement`, `phase`, `testedBy`). `ALL_TOOLS = [...OPERATION_TOOLS, ...NATIVE_TOOLS]` backs `findTool`, the catalogue index, `describe_tool` and `GET /assistant/tools`; the generator includes them in the capability matrix and the registry version. Registry checks: unique names across both sets, the id pattern and its absence from OpenAPI, `native:` paths, a confirmation spec and impact template for every enabled native write, a `testedBy`, no credential-shaped input key.
- **They never reach the loopback.** A `native:` path is not under `/api/v1`, so `AssistantLoopbackClient` refuses it; the executor dispatches native tools to `NativeToolsService` after the unchanged steps 1–6 of decision 5 (budget, lookup, availability and permission, refs, schema).
- **Data only from loopback reads.** A native tool computes nothing from the model and calls no service of another module: `report_generate` composes a fixed set of internal loopback **reads of existing operations** with the turn's own credential (the same guards, RBAC, tenant scope, rate limits and coded errors as the portal; a source the principal lacks permission for is not called). AI-R has exactly two native tools: `report_generate` (read) and `report_send_email` (write, confirmed under [ADR-0093](0093-assistant-action-confirmation.md) Amendment AI-R).
