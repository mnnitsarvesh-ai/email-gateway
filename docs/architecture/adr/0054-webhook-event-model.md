# ADR-0054: Webhook event model — public events projected from internal events

**Status:** Accepted (implemented in step 6.2; verification record in [§14 of the step design](../../plan/steps/19-webhooks-notifications.md#14-verification-record); not verified: CI, a Kubernetes cluster apply, production-scale throughput). Design: [step 6.2](../../plan/steps/19-webhooks-notifications.md) §1.2, W1–W5, §4.1, §5, §11. Builds on [ADR-0005](0005-rabbitmq-outbox-idempotency.md) (outbox, at-least-once, idempotent consumers), [ADR-0024](0024-rabbitmq-topology-retry-dead-letter.md) (topology, retry, dead letters) and [ADR-0025](0025-message-lifecycle-state-machine.md) (lifecycle states and reasons). Delivery, signatures and retries: [ADR-0055](0055-webhook-signing-and-delivery.md). Supersedes nothing.

**Context.** Tenants need to feed a SIEM, a SOAR or a ticketing system with what the gateway does to their mail: received, scanned, delivered, rejected, quarantined, released, threats, policy hits and domain DNS problems. Every one of these facts except one is already written by its owner service as an internal outbox event (`mail.message.received.v1`, `mail.message.scanned.v1`, `mail.policy.decided.v1`, `mail.message.state_changed.v1`, `mail.delivery.approved.v1`, `mail.attachment.sandbox_completed.v1`, `domain.status.changed.v1`) and transported at least once by the relay. Internal events are versioned for consumers inside the platform: they carry internal decimal ids, S3 keys of internal objects, engine details and may change with the services. They are not a public contract. The one missing fact was a verified domain whose MX/SPF/DKIM/DMARC record stops validating: the domains check changed `domain_dns_records.status` without an event. The invariants of the product apply in full: tenant from the authenticated context, no message content outside the mail plane, idempotent asynchronous processing.

**Decision.**

1. **Projection, one owner.** The new `webhook-worker` (role `fanout`, queue `email.webhooks`, topology v11) maps internal events to public events by fixed rules (step design W3): `received.v1` → `email.received`; `scanned.v1` → `email.scanned`; `decided.v1` → `email.threat.detected` (final verdict a threat), `email.policy.triggered` (at least one tenant rule matched) and `email.quarantined` (entries of origin `policy` in that round); `state_changed.v1` → `email.delivered` (`delivered`), `email.rejected` (`rejected` with a policy, quarantine or delivery reason) and `email.quarantined` (`manual_quarantine`); `approved.v1` with `source = quarantine_release` → `email.released`; `sandbox_completed.v1` with `malicious` → `email.threat.detected` (stage `sandbox`); `domain.status.changed.v1` → `domain.verified` / `domain.dns.failed`; the new `domain.dns.records_changed.v1` → `domain.dns.failed` (records). The 2.x–5.x producers are unchanged; the public contract lives in one package, `@email-gateway/webhooks`, and one service.
2. **One new internal event.** `domain.dns.records_changed.v1` is written by the api in the domain check transaction only when at least one record's stored status changes (never per check; an indeterminate check changes nothing). Ids and codes only, no observed or expected record values.
3. **Catalogue v1** (ten subscribable types, version 1 each): `email.received`, `email.scanned`, `email.delivered`, `email.rejected`, `email.quarantined`, `email.released`, `email.threat.detected`, `email.policy.triggered`, `domain.verified`, `domain.dns.failed`; plus `webhook.ping` (test deliveries only, not subscribable). Each type has a strict zod schema, a severity rule (`info` < `low` < `medium` < `high`), the filters that apply and an example; `GET /api/v1/webhooks/event-types` serves it. A breaking change ships as version 2 of a type; additive types (8.1 archive, 8.2 integrations) are new types at version 1.
4. **Envelope.** `{ id, type, version, occurredAt, organizationId, data }`. `organizationId` is the organization **public** id; every id in `data` is a public id (message = `message_identities.public_id`, domains, entries, releases, policies). `occurredAt` is the source event's time. The envelope is serialized once at projection, stored as text (`webhook_events.payload_json`, `payload_sha256`) and sent byte-identically on every attempt and replay.
5. **Deterministic ids.** `id = webhookEventId(sourceEventId, type, subKey)`: SHA-256 of `eg-webhook-event/v1\0<source>\0<type>\0<subKey>`, first 16 bytes as a UUID with version nibble 8 (RFC 9562). A redelivered source event yields the same public id and the same partition key, so insert-ignore on `(event_id, occurred_at)` makes projection idempotent, and receivers dedupe by the id (`EG-Event-Id`, `Idempotency-Key`).
6. **Subscriptions and filters.** A subscription lists 1–10 types (no wildcard) and optional strict filters: `directions`, `domainIds` (tenant domain public ids, resolved at write time inside the tenant scope), `minSeverity`, `verdicts`. A filter applies only when the event carries the attribute (domain events have no direction or verdict); a null message domain never matches `domainIds`. Only `active` subscriptions of the **envelope's** organization, created at or before `occurredAt`, receive an event; the per-organization index is cached for `WEBHOOK_SUBSCRIPTION_CACHE_SECONDS` (5 s) together with the `webhooks` plan feature (off → no deliveries).
7. **Metadata only.** Payloads carry ids, codes, counts, times and domain names; never a subject, body, attachment content or file name, local part of an address, raw header (except the documented `internetMessageId`, ≤ 255 characters, cleared when it looks like a URL or an object key), S3 key, URL found in mail, secret or token. `assertWebhookPayloadSafe` (the platform content guard plus a key deny-list, value checks for addresses, `org/<id>/` keys and `scheme://` URLs, and the 16 KiB cap) runs in `buildEnvelope`; a violation dead-letters the source event (`webhook_payload_unsafe`) instead of sending. The stack suite asserts it on every received payload.
8. **What is not an event (stated).** SMTP-time refusals (milter reject, unknown recipient, size, rate limit: no message row exists), per-recipient delivery outcomes (message level with counts instead; detail stays in `GET /messages/{id}/recipients`), URL clicks, DLP incidents, archive actions, adoption of pre-5.3 quarantined messages, and back-fill of events that occurred before a subscription existed or while it was paused or disabled.

**Alternatives considered** (step design §7). New `webhook.*` producer events in five services: touches the mail path for facts already in the outbox and creates two contracts per fact. Tailing `message_outbox` directly: scans millions of rows per day, bypasses the broker's retry and dead letters, competes with the relay. Per-recipient `email.delivered`: up to 1 000 events per message. Addresses in payloads as an opt-in: PII leaves the platform with every event; can be a later payload version. A wildcard type: subscribers would silently receive future types.

**Consequences.** About ten internal events per message reach `email.webhooks`; the fanout acks events that match no subscription and request no alert without a database transaction or ledger row (pure function of cached state), which is why the queue is excluded from the reconciler (ADR-0055). A new subscription may miss events for up to the cache TTL; events while paused or disabled are never recorded and cannot be replayed. `domain.verified` / `domain.dns.failed` are verified at the api and worker integration level only, because the local stack's domain DNS is static. Severity mapping of risk verdicts: phishing, malware and BEC are `malicious` (high), bulk and spam `spam` (low), suspicious `suspicious` (medium); DLP violations are not threats.
