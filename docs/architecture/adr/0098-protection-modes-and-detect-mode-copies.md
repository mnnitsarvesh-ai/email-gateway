# ADR-0098: Protection modes (inline, api, hybrid) and detect-mode copies

**Status:** Accepted (2026-11-26, local verification: stack suite `api-mode.test.ts` 11/11 — journal copies of an `api` domain detect-scanned without archiving (`scan_requested` from API mode), one copy row per api-mode recipient, no delivery, policy log, sink copy, DSN or `email.received` webhook; EICAR → `malware`, GTUBE → `spam`; MX-conflict `409`, `hybrid` accepted with `inbound_enabled`/`outbound_enabled` unchanged, mode-change audit rows, an inline domain of the same organization delivered normally; regression journal-intake 12/12, mime-ingestion 2/2, scan-pipeline 4/4, archive-smtp 19/19, webhooks-notifications 2/2; live provider tenants, CI and Kubernetes apply pending). Proposed by the step API-1 architect, 2026-11-26. Design: [docs/plan/steps/35-api-mode-protection.md](../../plan/steps/35-api-mode-protection.md) §2.0 (N1, N2), §3.1, D1–D3, D6, D8, §6. Contracts [§36](../contracts.md#36-api-mode-protection-step-api-1); migration `20261126022823_api_mode_protection` ([docs/database/README.md](../../database/README.md#step-api-1-migration-20261126022823_api_mode_protection)). **Supersedes in part** [ADR-0087](0087-journal-intake-path.md) (the journal intake entitlement of step 8.6 D1, checked at RCPT by decision 3: archiving is no longer the only entitlement) and the [ADR-0087](0087-journal-intake-path.md) / [ADR-0025](0025-message-lifecycle-state-machine.md) assertion that only `journal_intake` messages may end in `journaled`. Related: [ADR-0099](0099-mailbox-access-consent-and-custody.md), [ADR-0100](0100-api-mode-intake-mailbox-worker.md).

Superseded in part by [ADR-0102](0102-mailbox-located-quarantine-entries-release-as-restore.md) (step API-2, 2026-11-26): decision 7 / note 35 N1 no longer keep copies away from quarantine release entirely: a mailbox-located quarantine entry of a copy is "released" as a provider restore to the Inbox by the mailbox-worker. Copies are still never delivered, reinjected, policy-evaluated or rescanned, and their lifecycle still ends `journaled`.

**Context.** Customers on Microsoft 365 and Google Workspace want protection without an MX change (brief "API mode"); others keep inline filtering; some want both. Step 8.6 built a never-delivering journal intake ([ADR-0087](0087-journal-intake-path.md)) that requires archiving and scans only on request, and lets only `journal_intake` messages end in `journaled` ([ADR-0025](0025-message-lifecycle-state-machine.md) as amended by ADR-0087). Mail-flow behaviour is governed by `domains.inbound_enabled` / `outbound_enabled` and DNS; a mode that silently changed inline acceptance would bounce mail of a domain whose MX still points at the gateway.

**Decision.**

1. `organizations.protection_mode` (ENUM `inline`, `api`, `hybrid`; default `inline`) and `domains.protection_mode` (NULL = inherit); effective mode = domain ?? organization. `api` / `hybrid` need the feature `api_mode_protection` (`403 api_mode_not_enabled`); `inline` is always allowed. Every existing organization and domain stays `inline`.
2. The mode controls the API side only and never changes inline mail flow (`inbound_enabled`, `outbound_enabled`, destinations, connectors, DKIM, recipient validation). A change that makes a domain effective `api` is refused (`409 protection_mode_mx_points_to_gateway`) while its latest definitive MX observation points to the gateway; `api` domains are created with inbound off (`422 protection_mode_inbound_conflict` otherwise); every change is audited with a reason (`organization.protection_mode_changed`, `domain.protection_mode_changed`). Later MX drift is a health warning, never an automatic change.
3. The add-domain wizard starts with a mode step (inline, API, hybrid explained); the `destinations` and `recipients` steps are skipped for `api`, and a `mailbox` step shows the provider connection, the mailbox-access grant and the journal source (informational).
4. **Supersedes ADR-0087 in part (the step 8.6 D1 entitlement):** journal intake is entitled by the `journal_intake` feature **and** (archiving entitled and enabled **or** API mode active). Archive capture still follows the journaling settings (an API-only organization's copies are not archived).
5. `journal_intake_messages.scan_requested` of a journal copy is also true when API mode is active (**detect mode**: full scan, risk score, no policy evaluation, no disposition, no `mail.message.scanned.v1`, no `threat_detected` alert). The email-worker writes `mail.message.copy_scanned.v1` in the E30–E32 transaction instead.
6. **Supersedes the ADR-0087 / ADR-0025 assertion in part:** `journaled` is the terminal state of every non-gateway copy (`email_messages.ingest_source` ∈ `journal_intake`, `mailbox_api`), with the E30–E32 edges and reasons unchanged; the transition service still refuses it for `gateway` messages.
7. API mode never delivers, forwards or bounces (N1): copies never reach the policy engine, delivery, reinjection, quarantine release, customer webhooks or a rescan.

**Consequences.** One data model for three modes; existing domains unchanged (`inline`); API-only customers need no archiving plan; journal copies of API-mode tenants are always scanned; hybrid copies are scanned twice in API-1 (inline verdict authoritative, optimization later). Every "is this an intake copy" test that guards delivery, webhooks, ATO signals, rescans or the lifecycle becomes `ingest_source <> 'gateway'`; gateway views keep filtering `ingest_source = 'gateway'`.

**Alternatives considered.** The mode flips inline acceptance (bounces mail whose MX still points to the gateway); organization-only or domain-only mode (mixed tenants need both, with inheritance); a new terminal state `detected` (four enum columns and every final-state list change for no behavioural difference). Details: design §6.
