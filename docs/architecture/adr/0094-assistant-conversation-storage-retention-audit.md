# ADR-0094: AI assistant conversation storage, retention and audit

**Status:** Proposed (2026-11-20, step AI-1; product owner accepted the design defaults Q4 retention and Q9 privacy of conversations on 2026-11-20); amended in step AI-R (2026-11-23) (see [Amendment AI-R](#amendment-ai-r-2026-11-23)). Design: [docs/plan/steps/28-ai-chat-management.md](../../plan/steps/28-ai-chat-management.md) §2 D7, D12, D13, §3. Migration `20261120141509_ai_assistant` ([docs/database/README.md](../../database/README.md#step-ai-1-migration-20261120141509_ai_assistant)). Related: [ADR-0014](0014-mysql-data-model-partitioning-read-write-split.md) (data model), [ADR-0091](0091-assistant-architecture-loopback-tools.md), [ADR-0092](0092-llm-provider-abstraction-and-data-handling.md). Changes no Accepted ADR.

**Context.** A chat needs durable conversations (history, retry idempotency, refs to earlier results, provider-native transcripts for preserved thinking), usage accounting for budgets and cost, and an audit trail of every tool the model asked for, allowed or denied. Conversation text is user-written and may be sensitive; the platform rule is that email bodies and attachments are never stored in MySQL; the brief requires every assistant action to be auditable with user, tenant, conversation, tool, operation, redacted parameters, permission decision, status, resource id, time and error.

**Decision.**

1. **Six tables in MySQL** (InnoDB, `utf8mb4`, not partitioned, `organization_id` first in every tenant index, `CHAR(36)` UUIDv7 public ids): `ai_chat_settings` (one row per organization, `assistant-settings/1`, CAS), `ai_chat_conversations` (private to their user; under a platform override stored in the target organization with the override id), `ai_chat_turns` (status, provider, configured and reported model, prompt and registry versions, rounds, tool calls, tokens, advisory cost, latency, coded error, correlation id, provider-native transcript ≤ 512 KiB), `ai_chat_messages` (user and assistant text), `ai_chat_tool_executions` (every execution, allowed or denied: decision, status, HTTP status, coded error, correlation id, scrubbed parameters ≤ 4 KiB, resource ref, result card ≤ 64 KiB, refs, cursor) and `ai_chat_usage_daily` (tokens and cost per organization, day, provider, model). Every table references `organizations` with RESTRICT; a conversation references its user with CASCADE and its turns, messages and executions cascade from it.
2. **What is stored.** User text, assistant text, provider transcripts of the turn and masked metadata cards exactly as the API returned them to this user. **No email body or attachment**, ever (I5): no tool returns them. Logs never carry prompts, responses, arguments or results.
3. **Retention (Q4).** Content columns (`title`, `content`, `provider_transcript`, `result_card`, `result_refs`, `next_cursor`) are set to NULL at `purge_after` = `last_turn_at` + the tenant's `retention_days` (1–365, default `ASSISTANT_RETENTION_DEFAULT_DAYS` = 30) by a batched, Redis-locked api job, and immediately when the user deletes a conversation (soft delete, audited `assistant.conversation_deleted`). Each turn sets `purge_after` = its start + `retention_days` (then `last_turn_at` + `retention_days` at its end) and clears `content_purged_at`, so a conversation used again after a purge is purged again; lowering `retentionDays` moves the `purge_after` of the organization's unpurged conversations to `COALESCE(last_turn_at, created_at)` + the new value in the settings transaction (never later: a raised value applies from each conversation's next turn); the job re-checks every candidate under a row lock (`FOR UPDATE`) before purging, so a turn that started meanwhile keeps its content. Rows and execution metadata are hard-deleted after `ASSISTANT_EXECUTION_RETENTION_DAYS` (default 400). Organization deletion purges all six tables (`AssistantTenantDataRepository`, batched, resumable). Audit rows follow the audit retention.
4. **Privacy (Q9).** Only the owner reads a conversation (`404` otherwise, also for admins); administrators with `audit:read` see the tool-execution audit trail.
5. **Audit.** One `audit_logs` row per tool execution: action `assistant.tool_executed` or `assistant.tool_denied`, resource type `assistant_tool_execution`, resource id = execution public id, metadata `{ conversationId, turnId, tool, operationId, access, risk, decision, status, httpStatus, errorCode, resourceRef, params (scrubbed, ≤ 2 KiB), correlationId }`; plus `assistant.conversation_deleted` and `assistant.settings_updated` (and the AI-2 confirmation events). The loopback request carries `x-correlation-id = <turn correlation id>.<execution seq>`, so the operation's own audit rows (writes, audited reads, override audit) share the execution's correlation id.
6. **Transactions.** A turn is written in one writer transaction at start (turn `running`, user message) and one at the end (assistant message, transcript, metrics, usage upsert, status); a turn left `running` beyond its deadline is marked `failed` (`assistant_turn_abandoned`) by a sweeper.
7. **RBAC data.** The migration also upserts `assistant:use` and `assistant:configure` and grants them as the seed does (grant-preserving, idempotent; the pattern of ADR-0089), and the seed adds the operator-enabled feature `ai_assistant`.

**Alternatives considered.**

- **S3 objects for conversation content:** content is small text and masked cards that need transactional turn writes, paging and targeted purges; MySQL with retention is simpler, and I5 still holds.
- **No server-side history (browser only):** loses retry idempotency, refs, audit correlation and preserved-thinking replay.
- **Partitioning now:** volume is low (one row per message or tool call); revisited in AI-6 with real usage.
- **Logging prompts and responses for debugging:** would copy user text and tenant metadata into log storage outside retention; refused.

**Consequences.**

- Tenants control content retention; deleting a conversation removes its content at once, while the audit trail of what the assistant did remains.
- Six more tenant tables to purge on organization deletion (`AssistantTenantDataRepository`, documented in the organization-deletion runbook).
- Usage and cost per day and model are available to `assistant:configure` holders without reading anyone's conversation.

## Amendment AI-R (2026-11-23)

Step AI-R ([design](../../plan/steps/31-ai-chat-reports.md) §3, D6, D7; [ADR-0095](0095-assistant-reports-native-tools-static-html-email.md); migration `20261123074003_ai_assistant_reports`, [docs/database/README.md](../../database/README.md#step-ai-r-migration-20261123074003_ai_assistant_reports)) stores assistant reports. Decisions 2–4 are unchanged; the report HTML is content and follows them.

- **Report objects in the mail bucket.** The rendered HTML of a report is an object in `S3_BUCKET_MAIL` at `org/<organizationId>/assistant/report/<yyyy>/<mm>/<dd>/<reportPublicId>.html`, never a MySQL column (I5 holds: MySQL keeps metadata only). The key is checked against the organization's prefix before every get and delete, never returned to a client and never logged. The mail bucket is versioned, so a report delete removes every version and delete marker of the key (not just the current version).
- **Two new tables** (unpartitioned, `organization_id` first, RESTRICT to `organizations`): `ai_chat_reports` (window, sections, omitted reasons, figures, size, SHA-256, object key, statuses; conversation CASCADE) and `ai_chat_report_deliveries` (one per confirmed email: recipient class, normalized address as content, its SHA-256, status, message id; report CASCADE). Nine assistant tables in total.
- **Purge with the conversation content.** The transaction that purges a conversation's content (at `purge_after` and on delete) marks its reports `purged`, clears the deliveries' recipient addresses and fails their `queued` deliveries; the retention job then deletes the objects in batches (`object_deleted_at`). `pending` reports older than 1 h and `queued` deliveries older than 25 h are swept to `failed`. The hard delete after `ASSISTANT_EXECUTION_RETENTION_DAYS` takes the rows with their conversation after any remaining object is deleted.
- **Organization purge deletes objects first.** `AssistantTenantDataRepository` deletes `ai_chat_report_deliveries`, then `ai_chat_reports` (each batch: its objects, then its rows) before the existing order, and returns the deleted object count (`reportObjects`). A copy already delivered to a mailbox is outside the platform.
