# ADR-0035: Historical communication context for BEC: tenant opt-in, keyed hashes, aggregates, retention

**Status:** Accepted; implemented in step 4.4 (implementation notes below). Design: [step 4.4](../../plan/steps/12-phishing-bec.md) B12.

**Context.** "Unusual communication patterns" (first contact, first contact from a lookalike, replies without history, a known sender from new infrastructure) need memory of who corresponds with whom. A plaintext correspondent graph of every tenant would be a high-value personal-data store.

**Decision.**

1. **Opt-in per tenant** (`history.enabled`, default off; retention 30–730 days, default 365). Disabled tenants are neither read nor written; history rules do not fire and the result records `history: disabled`.
2. **Keyed hashes only:** one table `bec_contact_history` with aggregate rows per `(organization, scope, key_hash)` (`sender`, `pair`), counts, first/last seen and at most eight hashed infrastructure fingerprints. Keys are HMAC-SHA256 under a worker-only secret over the organization id, scope and canonical key, so rows are not reversible from the database alone and not linkable across tenants. No plaintext address, domain, IP or name.
3. **Written once per message** (round 0, in the BEC final's transaction; outbound mail updates pairs so replies become known), deadlock-free key order, bounded rows per message.
4. **Retention** by a leader-elected sweeper; **purge** through an audited, MFA-protected API; key rotation resets history.

**Alternatives considered.** Plaintext pairs (privacy); unkeyed SHA-256 (dictionary-reversible for e-mail addresses); per-message rows (unbounded growth); always-on context (no tenant authorization).

**Consequences.** History-based signals exist only for tenants that opt in, start empty and need warm-up; equality checks are all the engine can do with the data, which is all the rules need.

**Implementation notes (step 4.4, [§12](../../plan/steps/12-phishing-bec.md#12-deviations-log), [§13](../../plan/steps/12-phishing-bec.md#13-verification-results)).** Implemented as decided: HMAC-SHA256 keys over `eg-bec-ctx/v1\0‖org‖\0‖scope‖\0‖key`, sorted upserts of ≤ 51 rows per message as child rows of the round-0 bec final, the `infra` fingerprints as 16-hex HMACs, the retention sweeper (leader lock `scan:bec-history`) and the batched purge API. Refinements: `.env.example` uses `__GENERATE_64__` (32 random bytes) for `BEC_CONTEXT_HMAC_KEY` (WP2 deviation 2); a history read error other than an echo mismatch is recorded as `history: error` (verdict ≥ unknown) instead of failing the attempt (WP3 deviation 3); "first seen at this message" is `first_seen_at ≥ received_at` so rescans see the history of the first scan (WP2 deviation 11). History is verified by the email-worker package integration suite (opt-in on/off, round-0-only writes, retention sweep); the stack suites run with history disabled (the default).

**Amendment (review round 1, 2026-11-07): only authenticated, unflagged inbound mail warms up the history.** The sender row was keyed on the From header (attacker-controlled) and counted for every inbound message, so a few spoofed messages with `From: cfo@partner.test` from the attacker's own infrastructure made the sender "known" and recorded that infrastructure, switching off H1/H2/H5 (first contact) and H4 (new infrastructure) for the real attack. Decided: **inbound rows (the sender row with its fingerprint and the inbound pair rows) are written only when the message authenticated as its From (`authenticatedAsFrom`: DMARC pass, or an aligned passing DKIM signature or SPF identity) and the final bec verdict is `clean` or `unknown`.** Unauthenticated, `suspicious` or `malicious` inbound mail is read against the history but never counted. Outbound and internal pair updates are unchanged (the sender is the tenant's own user). Consequence: senders that never authenticate stay first contacts (their H1 weight applies on every message); that is the intended effect. Tests: `buildHistoryUpdates` (`inboundEligible`), the engine unit test (authenticated partner counted, spoofed and suspicious not), the email-worker integration case "spoofed warm-up mail never makes a sender known".
