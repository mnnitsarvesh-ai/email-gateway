# ADR-0021: Mail routing, direction resolution and per-recipient delivery status from Postfix's delivery log

**Status:** Accepted. Amends [ADR-0019](0019-smtp-gateway-topology.md): decision 2 ("Node never speaks SMTP") now allows one internal SMTP client, the delivery-worker's reinjection into postfix-outbound, and the reinjection contract's `XFORWARD IDENT` carries a reinjection token instead of the original queue id; listener 10027 delivers through a content filter that bypasses `transport_maps`. Consistent with [ADR-0006](0006-postfix-mail-path.md) (Postfix owns retries and DSNs; the pipeline never bounces). Design: [step 2.3](../../plan/steps/05-routing.md).

**Context.** Step 2.2 ingests inbound and outbound mail durably and provides the reinjection listeners 10026 (to tenant servers) and 10027 (to the Internet), but nothing reinjects, nothing tracks deliveries, nothing ever classifies mail as internal, a tenant domain has a single next hop, and the transport map would route outbound mail for another tenant's domain straight to that tenant's server. The product requires inbound, outbound and internal routing, Microsoft 365 / Google Workspace / customer destinations, per-recipient delivery status, retries and bounces, outbound rate limits, loop prevention and a delivery audit, and forbids claiming delivery before the remote server accepted the message and that acceptance is durably recorded.

**Decision.**

1. **One routing module** (`@email-gateway/mail-routing`) shared by smtp-adapter, delivery-worker and the api. Direction is decided per recipient from the ingestion listener and the organizations' verified domains, never from headers: inbound MX → `inbound`; authenticated outbound with the recipient domain an active verified domain of the **same** organization → `internal` (delivered to that organization's destination servers through 10026, never to Internet MX); everything else → `outbound` through 10027 and the recipient's public MX, **including other tenants of this gateway**, which therefore receive the mail through their own inbound path. Classification is stored per recipient at ingestion and re-checked at delivery; a changed classification is not delivered.
2. **One parent message, per-recipient deliveries.** Recipients are grouped per listener and destination into reinjection batches; Postfix splits further per next hop.
3. **Destinations are data**: `domain_mail_servers` (priority-ordered failover lists, TLS mode, verify names, typed provider) plus seeded provider presets for Microsoft 365 and Google Workspace (host patterns, mandatory verified TLS, expected certificate names). Destination hosts must not be non-public IP literals, metadata addresses, single-label/internal names or the gateway itself.
4. **The delivery-worker reinjects over SMTP** (a small internal client; XFORWARD, `RET`/`ENVID`, `NOTIFY`, `ORCPT`), streaming the EML from S3 unchanged after one prepended organization-neutral `X-Gateway-Trace`. It retries only its own hop (idempotent per message, delivery sequence, listener and recipient set). Inbound reinjections use `NOTIFY=NEVER` (no backscatter); internal and outbound use `FAILURE,DELAY` (the sender is an authenticated tenant user). Postfix owns MX resolution, queues, exponential retry, queue lifetime and DSNs, with the backoff configured explicitly.
5. **Delivery status comes from Postfix's own delivery log** (`status=sent|deferred|bounced|expired`, queue id, relay, DSN code, remote reply), matched on the queue id bound to each reinjection through the XFORWARD token Postfix logs as `orig_queue_id`; postmaster DSN copies corroborate failures and delays. `delivered` is recorded only from a `status=sent` line with a `2.x.x` DSN. Every signal is deduplicated by a deterministic key, applied through one monotonic state machine (`pending → queued → deferred* → delivered | bounced | expired`, plus `failed`, `suppressed`, `unknown`), and written with an append-only audit row, `email_events` and an outbox event. Missing signals end in `unknown`, never in a guess.
6. **Approval is an explicit contract** (`mail.delivery.approved.v1`) that the policy engine and quarantine release will produce; until step 3.2 it is read from the outbox by a poller behind a replaceable interface. A development-only pass-through, off by default and refused outside `APP_ENV` local/ci, approves received mail so the stack can be tested end to end.
7. **Outbound rate limits** per tenant, per tenant and destination domain, and per destination domain are enforced by the worker in Redis before reinjection, failing closed (defer, never drop).

**Alternatives considered.** Success DSNs (`NOTIFY=SUCCESS`) as the success signal: they go to the envelope sender, and intercepting them needs a gateway-owned envelope sender that breaks SPF alignment and swallows asynchronous bounces. Direct delivery to another tenant's destination: skips that tenant's inbound controls and mixes tenants. Splitting mixed messages into one message per direction: duplicates objects and records. Building the RabbitMQ relay now: step 3.2's scope. nodemailer as the reinjection client: no XFORWARD, so no crash-safe binding of queue ids. Details in the step note §7.

**Consequences.** postfix-outbound's log becomes a data source: it lives on a dedicated volume, is read by a status reader per Postfix host (the delivery-worker image as a sidecar in production), and its format is pinned by fixtures and tests. Log loss is detectable (`unknown`, metrics) but not recoverable from the log itself. Routing other tenants through the public MX costs an extra hop and a second scan. Worker-side refusals (loops, direction changes, reinjection refusals) are recorded without a DSN until notifications (6.2). Production must block postfix-outbound's egress to private ranges with security groups, because destination names are not resolved at write time.

**Amendments (step 2.3 review, before commit).** Recorded in [05-routing.md §12.7](../../plan/steps/05-routing.md#127-review-fixes-closing-the-step); the decisions above stay, with these refinements:

- _Shared next hops_: Postfix's `tls_policy` lookup is per `[host]:port` with no tenant context, so a custom server shared by several organizations must have **one** TLS policy. The api refuses a custom `host:port` that another organization uses with a different TLS mode or verify-name list (`destination_tls_conflict`) and refuses custom servers on a preset's hosts (`host_reserved_for_provider`). No tenant can make another tenant's next hop stricter (denial of delivery) or weaker (downgrade).
- _Destination ports_: custom destinations are limited to `ROUTING_ALLOWED_DESTINATION_PORTS` (default 25, 587, 2525) and the gateway's internal listener ports are always refused; the production egress control covers every port to private ranges, not only 25.
- _The `client=` binding is a correlation, never proof of queueing_ (smtpd logs it at the first accepted RCPT; an uncommitted file is discarded). Queueing is proven by the worker's `250`, qmgr `queue active` or a result line; a later session rebinds an uncommitted token; the reconciler queues an expired lease only on that evidence, else releases it (clearing the binding), bounds a log that never advances by the reinjection max age (`unknown`, never re-sent), and re-plans recipients of a queued group that Postfix never logged (refused or deferred at RCPT) after `DELIVERY_RECONCILE_UNCONFIRMED_SECONDS`.
- _Final result fields_ (`final_smtp_code`, `enhanced_status`, `final_smtp_response`) never carry the hop's `250 … queued as`.
- _Not built in this step_: DSNs generated by the gateway itself to the authenticated sender of outbound or internal mail for worker-side terminal failures (`reinjection_refused`, `loop_detected`, `reinjection_expired`, `recipient_domain_inactive`, `direction_changed`, `content_missing`). They are recorded and visible through the API; the notification is an open item (planned with step 6.2), listed in the execution plan.
