# ADR-0069: eDiscovery cases with custodians and case-scoped holds; worker-run searches verified against MySQL with explicit completeness; review tags; bounded encrypted EML exports with a signed chain-of-custody manifest and single-use download grants

**Status:** Accepted (2026-11-17, after the step 8.1 local verification: a case with a custodian, a hold, a worker-run search, review, an export downloaded through a re-authenticated single-use grant, its manifest hashes and Ed25519 signature verified with the published key (stack suite case 15, worker integration suite, Playwright `ediscovery.spec.ts`); record [docs/plan/steps/23-journaling-archiving.md](../../plan/steps/23-journaling-archiving.md) §13, §14). Proposed by the step 8.1 architect on 2026-11-16 (design A12, A18, A19, §4.2). Reuses the download model of [ADR-0048](0048-quarantine-preview-and-download-controls.md) and the key hierarchy of [ADR-0065](0065-archive-storage-and-per-tenant-envelope-encryption.md). Implementation notes: a case search may use the case custodians without `message:reveal` (WP4 D11), and since the closing round only a holder of `message:reveal` may write custodian addresses (a non-empty case list on create or `PATCH`, explicit hold custodians: `403 archive_filter_forbidden`), so a case manager cannot use the case list or a hold to probe recipient addresses; a hold snapshot with no custodian is refused (WP4 D12); any item unavailable at build time fails the whole export (WP3 D16).

**Context.** The brief asks for eDiscovery and export with a full audit trail and customer-specific access. Legal matters need cases that group custodians, holds, searches, review decisions and productions; exports must be bounded, asynchronous, encrypted, downloadable only through expiring grants, and accompanied by a chain-of-custody manifest with hashes. Archive content is legally sensitive and must not be reachable by platform operators or bearer URLs.

**Decision.**

1. **Cases** (`ediscovery_cases`) have a unique name per organization, a matter reference, custodians (addresses, optionally linked to users) and a status; a case closes only without active holds. All case routes need `ediscovery:manage`; every holder sees every case of the organization.
2. **Holds** are created inside a case (`archive:legal_hold` + `ediscovery:manage`, MFA) and evaluated at disposal (ADR-0067).
3. **Searches** are jobs: the api stores structured criteria (`archive-search/1`, reveal-gated where they would confirm masked values) and the archive-worker runs them through the tenant alias to completion (bounded hits and deadline), **verifies every hit against MySQL** and stores the hits. Completeness is reported, not assumed: a search is `index_complete` only when the organization's index queue is fresh and every day of the range passed reconciliation; otherwise the reason is shown.
4. **Review** tags hits (`relevant`, `not_relevant`, `privileged`, `untagged`) in bounded, audited batches.
5. **Exports** are built by the archive-worker from one completed search filtered by tags, bounded by items and bytes: a streaming ZIP of the decrypted originals (plaintext SHA-256 re-verified), `manifest.json` (ids, times, Message-ID, path, SHA-256, size and verdict per item, counts) signed with Ed25519 (`manifest.sig`, verification keys published by the api), and a README. Malicious originals are included only after an explicit acknowledgement and are placed in a separate folder. The package is encrypted at rest under the tenant key, never locked, expires after a configurable time, and its SHA-256 and the manifest's SHA-256 are recorded.
6. **Download** needs `archive:export` + `ediscovery:manage`, an MFA user session, password/TOTP re-entry and no platform override; it yields a single-use, short-lived token bound to user, organization and export; the api decrypts and streams the package. Every step (case changes, searches, review, export request, completion, grant, download) is audited.

**Alternatives considered.** Interactive search results as productions (index lag would silently drop items). Building exports in the api (long CPU and memory work in the control plane). Password-protected ZIP (rejected by ADR-0048: encrypted archives are a malware vector). Presigned S3 URLs (bearer, not single-use, not user-bound). HMAC manifests (third parties cannot verify without the platform's secret). Per-case membership lists (useful, deferred; role-based access first).

**Consequences.** Productions are reproducible (search criteria, hits, tags and hashes are stored) and verifiable offline with the published public key. Large matters are split by the operator (narrower searches) until split exports exist. API keys can request but not download exports (MFA user required).
