# ADR-0039: Sandbox as a separate security boundary: the `sandbox-controller` service and pluggable isolation backends, execution disabled

**Status:** Accepted; implemented in step 4.6 (execution disabled; vm runner not implemented) — verified locally on 2026-11-09, [§13](../../plan/steps/14-sandbox.md#13-verification-results). Implementation notes: the controller runs in the Compose `apps` profile with `SANDBOX_BACKEND=disabled`; `static` runs the analyzers in a permission-model child process (no execution); `hardened-container` is wired in the factory as `withStaticAnalysis(static, runner)` and starts only with `APP_ENV` local/ci, outside Kubernetes, with the explicit opt-in and the LOCAL/CI-only exec override (Docker socket, sinkhole) — a shared-kernel container, NOT a VM boundary; the detonation network is `internal` with `gateway_mode_ipv4: isolated` (escape suite finding F1, §12 WP4); `vm` performs its preflight and always refuses (`not_in_kubernetes` here, `vm_runner_not_implemented` in a cluster). Kubernetes manifests are rendered only, not applied; AppArmor is unavailable on Docker Desktop. Threat model: [docs/security/sandbox-threat-model.md](../../security/sandbox-threat-model.md). Design: [step 4.6](../../plan/steps/14-sandbox.md) X1–X9. Works with [ADR-0040](0040-sandbox-engine-dispatch-results-artifacts.md) (the engine side). Amends [ADR-0024](0024-rabbitmq-topology-retry-dead-letter.md) (topology v8: `scan.sandbox` becomes the controller's bounded work queue, new role user `sandbox-controller`) and [ADR-0028](0028-attachment-scanning-engine.md) decision 8 (the sandbox never reads tenant part objects; it reads only a staged, encrypted copy in a dedicated bucket).

**Context.** The brief for 4.6 asks for an isolated malware sandbox orchestration system with disposable execution environments: no access to production databases or cloud metadata, restricted network, CPU/memory/time limits, file-system isolation, browser analysis, process and network collection, screenshots and artifacts, verdicts, automatic cleanup, RabbitMQ dispatch, restricted S3 artifacts, health checks, cleanup tests, escape-resistance tests and failure recovery — and states that the sandbox must be a separate security boundary, not another Node worker, with a threat model written before unknown files are executed. The execution plan fixes the reality of this workstation: orchestration, isolation contract and threat model only; execution stays disabled until a VM-isolated runner exists. Containers share the host kernel; on macOS Docker Desktop no VM-class runtime (gVisor, Kata, Firecracker) can be proven. ADR-0028 decision 8 assumed the sandbox would read `org/*/part/` objects through a read-only grant, which would give the most exposed component read access to every tenant's attachments.

**Decision.**

1. **A separate deployable `apps/sandbox-controller`** with its own broker user `eg-sandbox` (read `scan.sandbox` only; publish only `org.<id>.mail.sandbox.task_completed.v1` and its own queue's retry/dead-letter hops; configure nothing), its own S3 user on a **dedicated sandbox bucket** (`GetObject samples/*`, `PutObject artifacts/*`, nothing else), **no database, Redis, main-S3, token, DLP, DKIM or other broker credentials** (configuration refuses to start if any is present), and its own internal network (`sandbox-control`: RabbitMQ, MinIO, sinkhole admin). It is stateless: idempotency is downstream (ADR-0040).
2. **Pluggable isolation backends** behind one interface (`SandboxBackend`: `selfTest`, `supports`, `run`, `reap`, `close`, with a declared `isolation` class):
   - **`disabled`** (default in every environment): accepts each task and answers a definite `not_executed` result with reason `backend_disabled`, never `clean`.
   - **`static`**: no execution. Our own bounded static analyzers (PE, ELF, OLE/VBA, OOXML, PDF, HTML/SVG, scripts, LNK, generic IOC strings, EICAR test string) in a resource-limited child process (empty environment, Node permission model, heap/RSS/CPU/wall limits) inside the locked-down controller container.
   - **`hardened-container`** (local/CI harness, **not a VM boundary**): one disposable Docker container per task — non-root, `cap_drop ALL`, `no-new-privileges`, seccomp (verified), AppArmor where available, read-only root, tmpfs scratch, pids/CPU/memory limits, no devices or mounts, network `sandbox-detonation` (internal; only the recording sinkhole), wall timeout and forced removal — with process tracing, dropped-file and screenshot capture and browser rendering for HTML/SVG through the existing headless-Chromium image (ADR-0032). Allowed only with `APP_ENV ∈ {local, ci}`, outside Kubernetes and with the explicit opt-in `SANDBOX_ALLOW_NON_VM_EXECUTION=true`; refused otherwise. Its Docker socket is mounted only by a separate Compose override file.
   - **`vm`** (Firecracker / gVisor / Kata via a Kubernetes RuntimeClass): a contract whose preflight must prove the isolation (in Kubernetes, the RuntimeClass exists with an allowed handler, a self-test pod under it is not on the node kernel and cannot reach metadata/node/cluster DNS). Its runner is **not implemented in 4.6**, so the preflight ends with `vm_runner_not_implemented` even when every proof passes, and the controller refuses to start. On this host it refuses with `not_in_kubernetes`.
3. **Production configuration** accepts only `disabled` or `static`. Execution of unknown files in production requires the preconditions of the threat model §8 and a new ADR.
4. **Static analysis runs before execution** for every backend that analyses (`static`, `hardened-container`): one combined observation per task.
5. **Network:** runners have no route except the recording sinkhole (DNS: every name → sinkhole; HTTP: recorded, fixed response; TLS: SNI recorded, closed); never the Internet, metadata (`169.254.169.254`, `fd00:ec2::254`, `metadata.google.internal`), private ranges or the service network. The controller has no route to tenant data.
6. **Cleanup** in `finally` per task, plus a reaper at startup (every runner labelled with this controller's name) and on a timer (runners past their expiry label, scratch older than the task budget). Cleanup failures are metered and alerted as critical.
7. **Health:** liveness; readiness = broker connection + sandbox bucket reachability (when the backend needs it) + the backend self-test (re-run on a timer); readiness details carry the backend, its isolation class and whether it executes.

**Alternatives considered.**

- _Run the sandbox inside the email-worker (like the attachment inspector child):_ rejected — an escape would land next to the writer database, Redis, tenant S3 and every key (the same reasoning as ADR-0032).
- _Give the controller a read-only grant on `org/*/part/` (ADR-0028 decision 8):_ rejected — the most exposed component would read every tenant's attachments; the email-worker stages an encrypted copy instead (ADR-0040).
- _Docker-in-Docker or a privileged controller:_ rejected — a privileged container is the host.
- _nsjail / bubblewrap inside the controller container:_ needs user namespaces or capabilities the locked-down container does not have, and is still a shared-kernel boundary; not better than a hardened sibling container for local tests.
- _Implementing the Kubernetes VM runner now:_ rejected — it cannot be verified on this workstation; an unverified execution path would be presented as working. The preflight contract is implemented and tested to refuse.
- _A commercial or hosted sandbox (Cuckoo/CAPE, Joe Sandbox, VMRay):_ rejected for 4.6 — sends tenant attachments to a third party or needs a nested-virtualization host; can later be another backend behind the same interface.

**Consequences.** One more deployable (small: about 150 MiB RSS with the `disabled` or `static` backend) and, locally, an optional sinkhole and runner image. No message ever waits for it. Analysts get static evidence in production; dynamic behaviour only in local/CI test runs. A Kubernetes environment with gVisor or Kata plus the threat model's operational gates is a prerequisite for real detonation, recorded as an external dependency in the execution plan.
