# ADR-0097: AI assistant provider routing with fallback and health, optional tenant-supplied keys, and the `pseudonymized` data-sharing level

**Status:** Proposed (2026-11-26, step AI-6). Design: [docs/plan/steps/34-ai-chat-hardening-operations.md](../../plan/steps/34-ai-chat-hardening-operations.md) §2.0 (I25, I27), D3, D6, D7, §3, §4, §5, §6 (A6-3, A6-4, A6-6, A6-7). Contracts [§35.6](../contracts.md#356-hardening-and-operations-step-ai-6); migration `20261125195835_ai_assistant_hardening` ([docs/database/README.md](../../database/README.md#step-ai-6-migration-20261125195835_ai_assistant_hardening)). Amends [ADR-0092](0092-llm-provider-abstraction-and-data-handling.md) ([Amendment AI-6](0092-llm-provider-abstraction-and-data-handling.md#amendment-ai-6-2026-11-26): one provider becomes a router, tenant keys, the `pseudonymized` level, segment rebinding) and records that the product owner's **Q8** ("tenant-supplied keys not before AI-6", accepted 2026-11-20) is now answered by **A6-7**. Related: [ADR-0077](0077-provider-credential-custody-and-encryption.md) (dedicated encryption key, `kid`, row-bound AAD), [ADR-0091](0091-assistant-architecture-loopback-tools.md), [ADR-0094](0094-assistant-conversation-storage-retention-audit.md) (content retention; amended in AI-6), [ADR-0034](0034-bec-ai-layer-invariant.md) (unchanged). Changes no Accepted ADR.

**Context.** Up to AI-5 the api builds exactly one provider from configuration, guarded by one Redis breaker (`as:brk:<provider>`); when it is open every turn fails `503 assistant_provider_unavailable`. Production needs a secondary provider and health-based routing. Some tenants want to bring their own provider key (billing, data-processing terms), which ADR-0092 deferred to AI-6 (Q8). And some tenants accept the external processing of metadata only if personal identifiers never reach the provider: the `data_sharing` setting has had a single value, `metadata`, reserving `pseudonymized` for AI-6. Two constraints shape all three: transcripts are provider-native and append-only within a segment (preserved thinking cannot be edited or translated between providers or models), and the model is an untrusted client whose tool arguments must still reach the real resource.

**Decision.**

1. **Provider router with candidates (D6).** Per turn the api builds an ordered candidate list: the **tenant key** (when stored, `valid` and `useTenantKey`) → else the platform **primary** (`ASSISTANT_PROVIDER`/`ASSISTANT_MODEL`) → the platform **secondary** (`ASSISTANT_FALLBACK_PROVIDER`/`ASSISTANT_FALLBACK_MODEL`, `none` by default). With a tenant key the platform candidates follow only when the tenant enabled `tenantKeyFallbackToPlatform` (A6-6). The secondary must differ from the primary unless its model differs, `fake` is refused in production, and an anthropic/openai secondary names its model (configuration validation; Azure reuses the `ASSISTANT_AZURE_OPENAI_*` keys).
2. **Health and breakers.** One Redis breaker per candidate: `as:brk:<provider>` (primary, as today), `as:brk:<provider>:fb` (secondary, so both may be the same family with different models) and `as:brk:t:<organizationPublicId>` (a tenant key; a tenant's bad key never opens a platform breaker). Selection at turn start = the first candidate whose breaker is closed; none → `503 assistant_provider_unavailable`. A breaker re-closes when its window expires (passive half-open). Gauges `assistant_provider_breaker_open{provider,role}` and `assistant_provider_fallback_active`; metrics `assistant_llm_requests_total{provider,role,outcome}`, `assistant_llm_seconds`, `assistant_provider_switches_total{from,to,reason}`; labels never carry organization or user ids.
3. **Same-turn switch, only before output.** When the first model call of a turn fails with a breaker-qualifying error (`connection`, `timeout`, `rate_limited`, `server_error`) **before any text delta was streamed and before any tool ran**, the router records the failure and retries the round on the next healthy candidate (at most one switch per turn). Later failures fail the turn as today. A tenant key answered with `401/403` is marked `invalid` (`last_error_code`), audited `assistant.provider_key_invalidated`, and the turn continues on the platform only when the tenant allowed it, else fails `503 assistant_tenant_key_invalid`.
4. **Segment rebinding.** A segment is bound to one provider and model. When the selected provider or model differs from the segment's last turn, `planWindow` starts a new segment from the existing deterministic recap (`forceNewSegment: true`, no model call); a same-turn switch rebuilds the context the same way. Turns record the provider and model actually used, `key_source` (`platform`/`tenant`) and `fallback_from`.
5. **Budgets.** The tenant daily budget and the new per-user daily budget (`userDailyTokenBudget`, Redis `as:tok:u:<userPublicId>:<yyyymmdd>`, `429 assistant_budget_exhausted` `scope: user`) count every turn regardless of candidate; the platform daily cap counts only `key_source = platform` turns (A6-7). Usage rows record `key_source`.
6. **Tenant-supplied keys (D7, I27, A6-7).** Off platform-wide by default (`ASSISTANT_TENANT_KEYS_ENABLED`); providers `ASSISTANT_TENANT_KEY_PROVIDERS` ⊆ {anthropic, openai} — Azure is not offered because a per-tenant endpoint cannot be allowed by the egress policy in advance; models from the allow-list `ASSISTANT_TENANT_KEY_MODELS`; endpoints are always the platform's. One row per organization in `ai_chat_provider_keys`: `key_ciphertext` = AES-256-GCM `v1.<kid>.<iv>.<tag>.<ct>` under the dedicated **`ASSISTANT_TENANT_KEY_ENCRYPTION_KEY`** (`_PREVIOUS` decrypts only) with AAD `assistant-provider-key:v1:<organizationId>:<keyVersion>` (the `SecretBox` construction generalized with a key-pair factory, as ADR-0077), `key_kid` = `k` + 7 hex of SHA-256(encryption key), `key_fingerprint` = the first 16 hex of SHA-256(API key) — the only visible trace. Routes `PUT|DELETE /assistant/settings/provider-key` and `POST …/validate` (`assistant:configure`, `@UserOnly`, `@RequireMfa`, rate class `sensitive`, CAS); a key is **probed before it is stored** (Anthropic `models.retrieve`, OpenAI `GET /models/{model}`, `ASSISTANT_TENANT_KEY_VALIDATION_TIMEOUT_MS`; `401/403` → `422`, network/5xx → `502`, nothing stored). Responses carry provider, model, fingerprint, status and times only. The plaintext lives only inside a built provider client (cache per organization and `key_version`, ≤ 100, 10 minutes); it is never logged (pino redaction of `apiKey`), audited, put in an event, a card, the model context or an OpenAPI example; tests use synthetic values matching no secret-scanner pattern and local fakes only.
7. **`pseudonymized` data sharing (D3, I25, A6-3, A6-4).** A new value of `data_sharing` (settings and per turn). Pure detection rules in the package (`pseudonym/detect.ts`): e-mail addresses (anywhere), IPv4/IPv6 literals (anywhere), domains (domain-named keys, `name` of `domains` module rows, URL hosts, bare hostnames with a ccTLD or a fixed gTLD list in free text), person names in known name keys and the user's display name; free-text names are not detected (documented limitation). Tokens `[EMAIL_n]`, `[IP_n]`, `[DOMAIN_n]`, `[PERSON_n]`, numbered per kind and conversation and stable for its content lifetime (normalized values; `[KIND_REDACTED]` beyond `ASSISTANT_PSEUDONYMS_MAX_PER_CONVERSATION`). **Neutralization first:** inbound substrings matching the token grammar become `(KIND_n)`, so neither a user nor a mail-derived string can forge a token. **Outbound:** the context block (organization name → "Your organization"), the user message, action updates, recap text and every string of every tool envelope (after the minimizer) are tokenized; keys never change. **Inbound:** tool-call arguments are de-mapped before refs, bindings and Ajv (an unknown bracketed token → `denied_schema` `assistant_unknown_placeholder`); streamed text is de-mapped with a 16-character hold-back buffer; the stored assistant message is de-mapped, `provider_transcript` keeps the tokens. The mapping is stored in plain in `ai_chat_pseudonyms` under the conversation's content retention (rows deleted at the content purge, on delete and with the organization) — encrypting it would add a key without changing the exposure, since the same values are in cards and messages (A6-4). Cards, confirmation summaries, report HTML, audit rows and executed requests carry real values. Prompt `assistant-system/7` tells the model to use placeholders exactly as written and never invent one.

**Alternatives considered** (design §5).

- **Translate transcripts between providers; switch at any round.** Preserved thinking forbids editing or translating native history; a switch after tools ran would confuse the model's context. The recap is deterministic and already tested.
- **One breaker for all candidates.** A tenant's revoked key would take the platform down for everyone; per-candidate breakers isolate it.
- **Encrypt tenant keys with `DATA_ENCRYPTION_KEY` via `SecretBox`.** Key separation (ADR-0077 precedent) limits the blast radius and allows rotation without touching MFA secrets.
- **Tenant keys for Azure OpenAI with tenant endpoints.** A tenant endpoint is an arbitrary host the egress policy cannot allow in advance (SSRF-like egress); platform Azure stays available.
- **An NER model, pseudonymizing inside the provider adapter, per-tool field lists.** A model is a new non-deterministic dependency; the adapter sees provider-native shapes only; per-tool lists for 356 tools would drift — generic key and pattern rules plus module rules are testable with fixtures and property tests.
- **Encrypt the pseudonym mapping.** Same exposure as cards and messages under the same retention; a new key without benefit.

**Consequences.**

- ADR-0092 decision 1 ("one provider") becomes a router; decision 2 gains the fallback and tenant-key keys; decision 4 gains `pseudonymized`; "Keys are platform-managed (no tenant keys before AI-6)" is superseded by decision 6 here (PO Q8 answered by A6-7). See [ADR-0092 Amendment AI-6](0092-llm-provider-abstraction-and-data-handling.md#amendment-ai-6-2026-11-26).
- Two new tables (`ai_chat_provider_keys`, `ai_chat_pseudonyms`), new turn columns (`data_sharing`, `key_source`, `fallback_from`), settings columns (`use_tenant_key`, `tenant_key_fallback_to_platform`, `user_daily_token_budget`), one new secret (`ASSISTANT_TENANT_KEY_ENCRYPTION_KEY`, mounted only on the `api-assistant` Deployment).
- A provider change costs one recap segment (context is summarized, not replayed); the user's next turn after a failure starts on the healthy candidate.
- Pseudonymization can miss free-text names (A6-3) and may tokenize a value that is not personal (a hostname-shaped word); both are documented. Real-provider behaviour with placeholders is not measured (no real-model evaluation, R10).
- Real Anthropic/OpenAI probes and calls are not verifiable locally (no internet in tests); every test uses injected local fakes.
