# ADR-0014: MySQL data model: BIGINT ids, organization_id, partitioning, identity registry and read/write split

**Status:** Accepted. Supersedes [ADR-0004](0004-mysql-primary-store.md). Amends the table names in [ADR-0005](0005-rabbitmq-outbox-idempotency.md) and the tenant column name in [ADR-0012](0012-multi-tenancy-and-deployment-modes.md).

**Context.** Step 1.1 of the product brief defines the complete transactional schema (about 60 tables in 10 modules) for 1M messages/day. It requires `BIGINT UNSIGNED` primary keys, an `organization_id` column on every tenant-owned table, UTC `DATETIME(3)` timestamps, partitioning for high-volume tables, and a separate identity registry where global uniqueness is needed across partitioned tables. The product owner also requires a MySQL primary (writer) and replica (reader) with GTID replication. ADR-0004 chose UUIDv7 `CHAR(36)` ids, a `tenant_id` column, and left partitioning as "planned". The Phase 0 baseline migration was never deployed anywhere shared, so it can be replaced.

**Decision.**

1. **Identifiers.** Every table's surrogate key is `BIGINT UNSIGNED AUTO_INCREMENT`. Pure join tables use a composite key, and `message_idempotency` uses `(consumer, event_id)`. Aggregate roots that are addressed from outside the database (organizations, users, domains, api_keys, email_policies, webhook_subscriptions, quarantine_messages and message identities) also carry a `public_id CHAR(36)` UUIDv7. The REST API exposes `public_id`, so sequential ids never leak volumes or invite enumeration. Inside the platform (events, S3 keys, logs, joins), the numeric id is used and serialized as a decimal string, because JSON numbers cannot hold 64-bit integers.
2. **Tenancy column.** `tenant_id` becomes `organization_id BIGINT UNSIGNED NOT NULL` on every tenant-owned table, and tenant-scoped indexes lead with it. Platform catalogs (permissions, plans, reputation tables, malware signatures, system settings) have no `organization_id`. The few tables that legitimately hold platform-level and tenant-level rows (`roles`, `threat_indicators`, `yara_rules`, `audit_logs`, `login_audit_logs`) have a nullable `organization_id`, and the schema reference explains why. Platform operators are users of a platform organization (`organizations.kind = 'platform'`), so every user has an organization.
3. **Partitioning.** Sixteen high-volume tables are `PARTITION BY RANGE COLUMNS(<time column>)`. Twelve message-scoped tables use **monthly** partitions on the parent message's `received_at`, which every child row copies, so one message's whole graph lives in one partition and is pruned and dropped together. `bounce_events`, `audit_logs` and `webhook_deliveries` use monthly partitions on their own time column. `message_outbox` uses **daily** partitions. Partitioned tables follow MySQL's rules: **no foreign keys in either direction**, and **every primary or unique key includes the partition column**. Migrations create them with a single `pmax` (`MAXVALUE`) partition. Partition creation is date-independent: a maintenance job (`db:partitions`, a Compose step after `migrate deploy` and a Kubernetes CronJob) splits `pmax` into future partitions and drops expired ones by a reviewed per-table retention registry.
4. **Identity registry.** `message_identities` (not partitioned) allocates the message id (`AUTO_INCREMENT`), owns the global uniqueness of `public_id` and of the ingestion idempotency key `(organization_id, ingest_key)`, and maps `id → received_at`. Lookups therefore always reach the partitioned tables with both the id and the partition key. `email_messages.id` is the registry id, not its own auto-increment.
5. **Integrity without foreign keys.** Rows of partitioned tables are written in the same transaction as their parent (ingestion writes the registry row, message, recipients and outbox row atomically). Uniqueness constraints that include `received_at` provide idempotency. Consistency queries are documented. Non-partitioned tables keep normal foreign keys.
6. **Read/write split.** Locally, Compose runs a MySQL 8.4 primary and a replica with GTID-based asynchronous replication (`SOURCE_AUTO_POSITION=1`). The replica is seeded with the CLONE plugin by an idempotent one-shot setup container. There are three accounts: `DATABASE_URL` is the writer with DML only, `DATABASE_READ_URL` is the reader with `SELECT` on the schema plus `REPLICATION CLIENT` (needed only to read `SHOW REPLICA STATUS`; it cannot change data), and `MIGRATION_DATABASE_URL` holds DDL. `packages/common` provides `PrismaService` (writer) and `PrismaReadService` (reader, a separate `PrismaClient`). The reader checks replication lag periodically and serves reads from the writer, with a logged state change, when the replica lags more than `DATABASE_READ_MAX_LAG_SECONDS`, has stopped replicating, or is unreachable. Data-plane apps (smtp-adapter, email-worker, policy-engine, delivery-worker, archive-worker) do not register the reader at all, and ESLint forbids them from importing it. In production, the writer and reader URLs map to the RDS or Aurora writer and reader endpoints.
7. **Retention by partition drop.** Platform-wide maximum retention is enforced by dropping partitions. Shorter retention per tenant or plan is a batched delete by `(organization_id, received_at)`, owned by the feature steps. Archive partitions are never dropped automatically, because legal holds and per-tenant archive retention apply there. The registry rows of archived or quarantined messages are kept after the core tier expires, because the registry is the public-id lookup path; the registry purge skips rows that a live `email_archives` row or a `quarantine_messages` row references ([retention.md](../../database/retention.md#registry-rows-that-outlive-the-core-tier)).

**Alternatives considered.**

- _Keep UUIDv7 `CHAR(36)` keys:_ unique across deployments, but 36-byte keys are repeated in every secondary index of tables that grow by several million rows a day. `BINARY(16)` halves that, but it is awkward in Prisma (`Bytes`) and in logs. The brief mandates `BIGINT UNSIGNED`.
- _No partitioning, purge with batched `DELETE`:_ simple, and foreign keys keep working, but deleting several million rows a day produces undo, purge lag and binlog volume equal to the inserts. Dropping a partition is a metadata operation.
- _Daily partitions for every high-volume table:_ finer-grained drops, but about 180 partitions per table and more maintenance. Monthly partitions are enough for 90 to 180-day tiers. Only the outbox, which churns about 5M rows a day with 7-day retention, uses daily partitions.
- _`message_idempotency` partitioned by time:_ rejected. The primary key would have to include the time column, and a redelivery at a different time would then pass the uniqueness check. It stays unpartitioned, with a batched purge. Range-partitioning on the time-ordered UUIDv7 `event_id` is possible, and is noted as a future option.
- _A heartbeat table for lag (pt-heartbeat style):_ works on any engine and needs only `SELECT`, but it needs a writer process or the event scheduler, and the event scheduler needs re-enabling after a failover. We use `SHOW REPLICA STATUS` for now (local and RDS read replicas). Aurora needs a different probe, which is planned with step 10.1.
- _`relationMode = "prisma"` everywhere:_ rejected. It would drop real foreign keys on the about 45 tables that can have them.

**Consequences.**

- Prisma models for partitioned tables declare composite `@@id([id, receivedAt])` and no `@relation`. Joins to them are explicit queries. Partition clauses are hand-written in migration SQL, and Prisma's drift check does not see partitions (they are not part of its introspection), so it stays clean. A schema integration test asserts the partitioning.
- Every query on a partitioned table must include the partition column (an exact value for point lookups, a range for lists) to prune. The registry and event payloads (`receivedAt`) make that possible.
- Prisma returns `bigint` for ids. API serializers must convert them to strings.
- Partition maintenance and replica lag become monitored operational concerns, with alerts on a non-empty `pmax`, a failed maintenance run, and the reader in fallback mode.
- Event envelopes carry `organizationId` (decimal string) instead of `tenantId` (UUID), and S3 keys are prefixed `org/{organizationId}/`.
- Uniqueness that spans tenants must never let one tenant block or touch another (review amendment, step 1.1): only a **verified** domain is globally unique (`domains.verified_name`, a generated column; pending claims are unique per organization), and threat indicators are unique per tenant scope (`threat_indicators.org_scope`, generated as `IFNULL(organization_id, 0)`). Prisma has no syntax for generated columns: they are declared as plain read-only columns and their expressions live in migration `20261102000000_tenant_scoped_uniques`; the drift check compares type and nullability only and stays clean.
- Partition maintenance runs are serialized by a per-schema MySQL advisory lock, and partition DDL waits at most `lock_wait_timeout` (5 s) for the metadata lock, so a long transaction cannot turn a maintenance `ALTER` into a table-wide stall ([partitioning.md](../../database/partitioning.md)).
