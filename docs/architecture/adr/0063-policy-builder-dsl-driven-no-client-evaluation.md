# ADR-0063: Policy builder driven by the DSL catalogue, with no policy evaluation in the browser; server validation and sample dry-run; rollback by re-activation

**Status:** Accepted (2026-11-16, after the step 7.3 local end-to-end verification: Playwright 85/85 against the real api and the portal production build, the full regression gate, both images rebuilt; design and record [docs/plan/steps/22-policy-builder.md](../../plan/steps/22-policy-builder.md) B1–B17, §4, §13, §14). Proposed by the step 7.3 architect the same day. Supersedes no ADR decision. Extends [ADR-0043](0043-policy-dsl-and-deterministic-evaluator.md) (decision 7, the policy management lifecycle, is used unchanged) and [ADR-0058](0058-admin-portal-architecture.md) (the portal stays a client of the generated, drift-checked API client) with additive contracts only. Not yet exercised in CI or on a cluster.

**Context.** Step 7.3 builds a visual email security policy builder in the admin portal: name, description, direction, priority, enabled/disabled, AND/OR condition groups, dynamic fields, operators and values, multiple actions, exceptions, draft, save, test, dry run, publish, rollback, version history and a readable summary. The product owner requires that policy execution never happens in frontend JavaScript and that the backend stays authoritative. Step 5.2 already provides the `policy-dsl/1` language with a closed field and operator catalogue, a strict validator that reports every violation by JSON path, the deterministic evaluator, and an API for policies, versions (drafts editable with compare-and-set, published immutable), publish, activate (rollback), enable/disable, a synthetic-facts test and a per-round dry-run. Its catalogue route lists field and operator names and vocabularies but no labels, value shapes or action parameters; there is no validation without persisting and no dry-run over more than one stored round.

**Decision.**

1. **The catalogue is the builder's only vocabulary.** Every field, operator, value type, vocabulary, unit, action, action parameter, limit and placement restriction the builder renders comes from `GET /api/v1/policies/catalog`. The presentation metadata (labels, groups, units, code suggestions, operator phrases and value shapes, action labels and parameter definitions, quantifier phrases, scope nouns, placement contexts derived from the DSL's identity and AI rules, time zones, weekdays) lives in `packages/policy-dsl/src/presentation.ts` next to the catalogue it describes, is tested for completeness and for agreement with the validator, and is added to the catalogue response additively. The portal holds rendering only; a field or parameter the portal does not specially know is still editable through generic widgets chosen by value shape and field type.
2. **No policy logic in the browser.** The portal builds and displays `policy-dsl/1` documents through a lossless model (exact build → parse → build round trip). It never matches conditions, computes dispositions, compiles tenant regexes, globs or CIDRs, or validates DSL semantics; validation, test, dry-run and execution are API calls, and server violations are mapped onto the edited nodes by their JSON paths. Client-side checks are limited to input hygiene and to offering only what the catalogue allows. This is enforced by a lint import ban, a source scan and a scan of the production build output for evaluator-only needles; development fixtures answer with canned responses.
3. **Server validation without persistence.** `POST /api/v1/policies/validate` (`policy:manage`) validates a document exactly as a draft save does and reports directory-reference problems separately; it writes nothing and always answers `200` for a well-formed request.
4. **Bounded dry-run over recent stored evaluations.** `POST /api/v1/policies/dry-run` (`policy:manage` and `message:read`) re-evaluates the newest stored round per message of the organization within a bounded window against a target snapshot compiled once, sequentially, up to `POLICY_DRY_RUN_SAMPLE_MAX` rounds and `POLICY_DRY_RUN_DEADLINE_MS`, under the `expensive` class plus a per-principal route limit, and returns stored versus recomputed dispositions without message content. It writes nothing. The per-round dry-run stays for one message.
5. **Rollback is re-activation of a published version.** Rolling back is the existing `POST /policies/{policyId}/versions/{versionNo}/activate` of an earlier published version: one writer transaction under the organization's policy lock, audited `policy.version_activated` with `previousVersionNo`, generation incremented, applied to the next evaluation only, Idempotency-Key required. No separate rollback route, audit action or `rolled_back` status is introduced; "restore as a new draft" creates a draft from that version for editing before publishing.
6. **The readable summary and the version diff are presentation.** Both are computed in the browser from the DSL document and the catalogue labels (live while editing, on version views and in publish and rollback dialogs); they describe the document and never claim an outcome for a message.
7. **Concurrency and replay safety follow step 5.2 and ADR-0052.** Drafts are saved with `expectedRowVersion` and a conflict is resolved by an explicit user choice (reload, overwrite at the current row version, download); publish and activate send one Idempotency-Key per user intent, reused on retry.

**Alternatives considered.** Shipping `@email-gateway/policy-dsl` to the browser for instant validation (it contains the evaluator, RE2 and tldts; a second copy of the validator drifts from the deployed api). Labels and parameter forms hard-coded in the portal (a catalogue change would need a portal release; forbidden by the step). A server-rendered summary (cannot follow every keystroke; may be added for API clients later). A dedicated rollback route and audit action (duplicates activate; a `rolled_back` status would rewrite immutable history). A dry-run of recent messages as a browser loop over the per-round route (N expensive calls, no shared snapshot, no deadline). Saving invalid drafts (every stored version would no longer be a well-formed document). A `{ policyId, definition }` test target for unsaved edits of an existing policy (recorded as a follow-up; the editor saves the draft first).

**Consequences.** The catalogue response grows (additive keys; the generated portal client and its drift check follow the OpenAPI snapshot, and `docs/api/policy-catalog.json` is a drift-checked snapshot). Two read-only operations are added (279 in total) with three configuration keys. The builder cannot preview an outcome without a server round trip, by design. Work in progress that does not validate cannot be stored as a draft; the editor protects it with an unsaved-changes guard. Very large definitions above the api's JSON body limit (100 KiB, below the DSL's 256 KiB document limit) are refused (measured: `500 internal_error`, see the implementation notes) until the follow-up raises the limit. DLP and BEC configuration editing was decided into step 7.3 by the product owner (2026-11-16; see the implementation notes).

**Implementation notes (step 7.3, 2026-11-16).** Built as decided. Precisions recorded in the design note §13: (1) request size: WP1 measured that a body above Express's 100 KiB default was answered `500 internal_error`; the closer (§14.8) mapped body-parser's client errors to their status in the global filter (`413 payload_too_large`) and raised the JSON limit of the definition routes to the DSL's document limit plus 64 KiB, so the editor's size indicator (against `limits.documentBytes`) is the limit that applies and only a `413` is "too large". (2) DLP and BEC configuration editing is **in** step 7.3 by the product-owner decision of 2026-11-16 (editors over the existing api; the DLP pattern test runs on the server and the portal never compiles a pattern); BEC communication-history purge, BEC feedback recording and export, and DLP evidence purge stay out. (3) The catalogue lists the api runtime's time zones (`Asia/Calcutta`, not `Asia/Kolkata`); stored aliases round-trip and are validated by the server. (4) The guards hold on the production build and the image: no evaluator needle in `.next` or anywhere in the `admin-portal` image.
