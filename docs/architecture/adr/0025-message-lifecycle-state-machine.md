# ADR-0025: Message lifecycle state machine, ordering rule and the shared transition service

**Status:** Accepted (edge E27 `scanned → approved` added and E4 retired by [ADR-0026](0026-security-scan-pipeline.md); E27 retired again and E5, E8–E13 produced by the policy-engine, amended by [ADR-0044](0044-policy-evaluation-placement-and-delivery-gating.md), step 5.2). Amends [ADR-0021](0021-mail-routing-and-delivery-status.md) (the message-level delivery aggregate `delivered` / `partially_delivered` / `failed` becomes a derived lifecycle state: `delivered` with reason `delivery_complete` / `delivery_partial`, or `rejected` with reason `delivery_failed`; the per-recipient state machine is unchanged) and [ADR-0024](0024-rabbitmq-topology-retry-dead-letter.md) (topology version 2: two new event types and five new bindings; the six exchanges and fourteen queues are unchanged). Makes a one-time exception to the "enum values are only ever appended" rule of the step 1.1 design ([docs/database/README.md](../../database/README.md)) for `MessageStatus`. Design: [step 3.3](../../plan/steps/08-message-lifecycle.md). **Amended in step 5.3 by [ADR-0046](0046-quarantine-store-and-per-recipient-decisions.md)** (E10 `policy_partial`, E16–E18 produced, E26 role `quarantine` with `quarantine_expired`, new edges E28 and E29) **and [ADR-0047](0047-quarantine-release-revalidation-and-approvals.md)** (operator release of held mail moves from the api to the quarantine release executor).

**Context.** `email_messages.status` has carried the step 1.1 enum (`received`, `scanning`, `scanned`, `policy_evaluated`, `quarantined`, `delivery_queued`, `delivered`, `partially_delivered`, `discarded`, `failed`) since 1.1. Step 2.3 writes it from the delivery planner (`received → delivery_queued`) and the shared delivery recorder (the aggregate `delivered` / `partially_delivered` / `failed`), with an optimistic `version` and an `email_message_status_history` row. Nothing else writes it: the SMTP commit leaves `received` without a history row, step 3.1 records parse outcomes only in `email_message_parses`, and the transitions are hard-coded in one module. The product brief for step 3.3 fixes fifteen states (RECEIVED, PERSISTED, SCANNING, SCANNED, POLICY_EVALUATED, APPROVED, QUARANTINED, REJECTED, DELIVERY_PENDING, DELIVERY_RETRY, DELIVERED, ARCHIVED, SCAN_FAILED, HELD_FOR_REVIEW, EXPIRED) and requires explicit valid transitions, rejection of invalid ones, a MySQL record of every transition with actor, timestamps and reason, concurrency safety, retry and recovery, administrative rescan, quarantine release, per-recipient delivery state, an idempotent transition service, and that an older processing event never overwrites a newer state. Producers live in five deployables (smtp-adapter, email-worker, delivery-worker, event-relay, api), and events reach them at least once and out of order (ADR-0024).

**Decision.**

1. **One shared library, one table.** `@email-gateway/message-lifecycle` (new workspace package) holds the fifteen states, the transition table as data (`from`, `to`, allowed actor roles, allowed reason codes, whether the edge opens a new round), a pure validator (`decideTransition`), the derived message delivery rule, and the transition service that every writer of `email_messages.status` must use. No service writes `status`, `version`, `lifecycle_round`, `status_reason` or `email_message_status_history` except through it (a data-ownership rule, enforced by a repository test that scans the sources for direct writes).
2. **The fifteen brief states are the canonical `MessageStatus`.** Stored lower-case (`received`, `persisted`, `scanning`, `scanned`, `scan_failed`, `policy_evaluated`, `approved`, `quarantined`, `held_for_review`, `rejected`, `delivery_pending`, `delivery_retry`, `delivered`, `archived`, `expired`), like every other enum of the schema. A forward migration widens the enum, backfills, and narrows it to exactly these values: `delivery_queued → delivery_pending`; `partially_delivered → delivered` (reason `delivery_partial`); `failed → rejected` (reason `delivery_failed`); `discarded → rejected` (reason `discarded`); `received → persisted` (history row `lifecycle_backfill`, since every stored row was committed with its EML in S3). Partial and failed outcomes are **reason codes plus the per-recipient states**, not extra states. The append-only enum rule is broken once, on purpose: keeping four retired values would let any typed writer set a non-canonical state, and no production data exists yet (the narrowing is a table rebuild; a later change on production data would need an online schema change and is not allowed by this ADR).
3. **Ordering rule: rounds, versions and state rank, never wall clocks.** Each message carries a monotonic `version` (every applied transition +1) and a monotonic `lifecycle_round` (+1 only on re-entry edges: administrative rescan and quarantine/review release). A transition request may carry `expectedRound` (event-driven producers copy it from the event that caused them), `expectedVersion` (API callers and the sweeper) and `expectedFrom`. Under the message row lock: a request of an older round, or with a stale version, is **stale**; an edge that is not in the table is **stale** when the target ranks at or below the current state (the message is already past it) and **invalid** otherwise; a request whose target equals the current state in the same round is a **duplicate**. Event occurrence times are recorded but never compared, because they come from different clocks (Postfix log lines, service clocks). Delivery-derived transitions carry no round: they are recomputed from the recipients' current states under the same lock, so they cannot be "older".
4. **Atomic, idempotent transitions on the writer.** `transitionMessage(tx, request)` runs inside the caller's writer transaction (so the stage's own effects, its `processOnce` ledger row, the history row, an `email_events` row and the `mail.message.state_changed.v1` outbox row commit together): `SELECT … FOR UPDATE` on `(id, received_at)`, decide, then `UPDATE … WHERE id = ? AND received_at = ? AND version = ?` (compare-and-set; a zero row count is a conflict that the caller's retry absorbs). Every request has a `transitionKey` (the causing event id plus the target, the API's Idempotency-Key, the sweeper's `expire:<version>`, …); its SHA-256 is stored in the history row under the unique key `(message_id, transition_key, received_at)`, so a retried event is a no-op by key even when the consumer ledger was bypassed. Stale and invalid requests from asynchronous producers are recorded as `email_events` rows `lifecycle.ignored` and counted; duplicates are only counted.
5. **Per-recipient delivery state stays per recipient.** `email_deliveries` / `email_recipients` keep the step 2.3 state machine, now expressed as an explicit table in `@email-gateway/mail-routing`. The message state in the delivery phase is **derived** under the message lock from `email_recipients.status` after every applied signal: any `pending` or `deferred` recipient → `delivery_pending` (or `delivery_retry` when one is deferred); otherwise at least one delivered → `delivered` (`delivery_complete` when all, `delivery_partial` when some), none → `rejected` (`delivery_failed`).
6. **States without a producer yet are valid but unset.** `scanning`, `scanned`, `scan_failed`, `policy_evaluated`, `quarantined`, `held_for_review` and `archived` have edges and tests; only the steps that build their stage (4.x, 5.x, 8.1) may set them. The development pass-through (local/ci only) uses its own edge `persisted → approved` with actor role `dev_passthrough`. Administrative rescan (`→ scanning`, new round) publishes `mail.message.rescan_requested.v1` to `email.security`, bound to the five dormant scan queues (topology v2); release (`quarantined | held_for_review → approved`, new round) writes a `mail.delivery.approved.v1` (`source = quarantine_release`) into the existing approval path.
7. **Expiry and recovery run in event-relay.** The reconciliation deployable (ADR-0023) gains a sharded expiry sweeper (per-state deadlines, compare-and-set on the version it read) and a lifecycle check that re-derives the delivery state of messages whose derived transition was lost. Lost transitions of queue consumers need no new mechanism: the transition commits with the consumer's ledger row, so a crash before commit leaves no ledger row and the step 3.2 reconciler re-drives the event.

**Alternatives considered.**

- _Event occurrence time plus state rank as the ordering rule_: rejected. Producers' clocks differ (Postfix log timestamps, container clocks), equal-rank states (`approved`, `quarantined`, `held_for_review`) cannot be ordered by rank, and re-entry (rescan, release) makes rank non-monotonic.
- _A per-message sequence assigned by the producer_: rejected. Producers are independent services; only the database row can assign a monotonic number, which is `version` (plus `lifecycle_round` for re-entry).
- _Keep the old enum values as states, or as retired members_: rejected (see decision 2).
- _Parse states (`parsing`, `parsed`) in `MessageStatus`_: rejected. The brief fixes fifteen states; step 3.1's `email_message_parses` is the stage record, and the parse outcome drives the next transition (4.1 `persisted → scanning`, 5.2 `persisted → policy_evaluated` on `parse_failed`).
- _Message-level delivery states written by the delivery-worker as events_: rejected. Deriving them from the recipients under the message lock cannot be overtaken and needs no ordering metadata.
- _A separate state-machine service (RPC)_: rejected. It would add a network hop and a second transaction to every stage; a library inside each writer transaction keeps atomicity with the stage's own effects.
- _State in a new table instead of `email_messages.status`_: rejected. The column, its index `(status, status_changed_at)` and the history table exist and are already read by the api.

**Consequences.** Every writer of the message state depends on `@email-gateway/message-lifecycle`. The SMTP commit writes two history rows (`received`, `persisted`) in its existing transaction (one `createMany`). Every other applied transition adds one history row, one `email_events` row and one outbox row (`mail.message.state_changed.v1`, published to `email.events` for analytics and the 6.2 webhooks). The step 1.1 enum is replaced once; the API's message status values change (`delivery_queued`, `partially_delivered`, `discarded`, `failed` disappear). A rescan before Phase 4 leaves the message in `scanning` until the expiry deadline, because the scan queues are dormant. Message expiry in a delivery state is final even if a very late delivery signal arrives (the per-recipient state still records it). Old events can only be classified once their round or version is known; producers built later (4.x, 5.x) must carry `lifecycleRound` from their triggering event.
