# ADR-0088: Cross-source archive dedupe

**Status:** Accepted (2026-11-20, local verification: stack suite `journal-intake.test.ts` cases 5–6 (gateway↔intake merge with a content variant, same body without, intake↔intake, hold on a Bcc custodian, disposal with variants), archive-worker `journal-intake` integration 11/11 (WP4), `archive-smtp.test.ts` 19/19; live provider tenants, CI and Kubernetes apply pending). Proposed by the step 8.6 architect, 2026-11-20. Design: [docs/plan/steps/27-journal-intake-and-archive-split.md](../../plan/steps/27-journal-intake-and-archive-split.md) (§2 D7, §3.2). Amends [ADR-0064](0064-journal-capture-intents-and-archive-consumer.md) (one record per message → per message or merged copy group) and [ADR-0067](0067-retention-legal-hold-and-disposal-consistency.md) (disposal covers variants, merged copies and dedupe rows). Supersedes nothing.

**Context.** Customers using both the gateway and journal intake would archive each message twice; journal rules may also emit several reports per message (PO decision 3). The gateway legitimately changes bodies at delivery (banners, URL rewriting), so copies of one message do not have identical bytes.

**Decision.**

1. **Scope.** Merging happens only when at least one copy comes from journal intake (gateway↔intake, intake↔intake). Gateway↔gateway copies keep one record per message (ADR-0064 unchanged for them).
2. **Key.** Same organization, same Message-ID (`archive-dedupe/1` hash) and same header fingerprint (`archive-fingerprint/1`: Date, From, To/Cc, attachment hashes; body excluded) within `ARCHIVE_DEDUPE_WINDOW_HOURS` (72 h). No Message-ID, Date or From → no dedupe.
3. **Merge.** The copies are one archive record: sources OR-ed (`source_gateway`, `source_journal_intake`), parties merged (BCC included), each merged copy's journal object stored under the record's data key, a differing body stored as a content variant of the same record (≤ `ARCHIVE_MAX_CONTENT_VARIANTS` = 4; ≤ `ARCHIVE_MAX_MERGED_COPIES` = 8 merged copies; beyond either, a separate record), retention and lock the maximum. Merged copies are recorded in `archive_record_sources` (partitioned, compliance), keys in `archive_dedupe_keys` (transient).
4. **Concurrency.** Row and gap locks on the dedupe key in one writer transaction; a changed candidate or deadlock retries the intent.
5. **Outcome.** The gateway copy is authoritative for the security outcome; an intake copy never overwrites it.

**Amendment (step 8.6 review, 2026-11-20).** Header equality is not proof of the same message: every input of the key (Message-ID, Date, From, To/Cc, attachments) is known to any recipient, who could resend the message with another body through the gateway and have it merged as a content variant whose gateway outcome becomes authoritative for the record. `decideMerge` therefore also requires the copy to agree with the record on trusted facts: the same `email_messages.direction` (computed from the gateway's listener path and from the provider-proven journal envelope; `direction_mismatch` otherwise), and, for **inbound** mail between a single-source record and a copy of the other source, the gateway copy must not be received more than `MERGE_ORDER_SKEW_MS` (5 min) after the intake copy (inbound mail passes the gateway before the provider journals it; `order_mismatch` otherwise). A refused merge captures the copy as its own record (fail-safe: stored twice). Residual risk: an inbound message that bypassed the gateway, resent through the gateway with identical headers and the same envelope direction **before** the provider's journal report arrived, still merges; its copy is kept as a variant and both copies' facts stay in `archive_record_sources`.

**Consequences.** One search hit per message with both sources; storage saved when bodies match (outbound and internal mail); compliance content is never lost (differing bodies are variants); disposal and holds cover the whole group, and the registry purge keeps the merged messages' registry rows while their `archive_record_sources` rows exist.

**Alternatives considered.** Raw-hash dedupe (copies always differ in headers, nothing would merge); Message-ID-only dedupe (a reused Message-ID could hide a different message); merging and dropping differing bodies (loses content). See the design §5.
