# ADR-0102: Mailbox-located quarantine entries; release as provider restore

**Status:** Accepted (2026-11-27, local verification: stack suite `api-mode-remediation.test.ts` 9/9 — a mailbox-located entry (`location = mailbox`, container `quarantine_folder`, `origin = api_remediation`) listed by `GET /quarantine/entries?location=mailbox` and not by `location=gateway`; an operator release of the hard-blocked entry → `approval_requested` (`hard_block`), the requester refused, a second admin approved → `restore_inbox` (`trigger = release`), entry `released`, release log `restored` (mode `approved`), the simulator message back in the Inbox, copy generation 1, no `mail.quarantine.release_requested.v1`; a Gmail Junk entry self-released by the end user within the quarantine settings → `restore_inbox` (`trigger = end_user`), log `restored` (mode `self`), `INBOX` back and `SPAM` removed; regression `quarantine-smtp.test.ts` 15/15 (gateway entries unchanged) and the policy-engine guards suite of WP5; live provider tenants, CI and Kubernetes apply pending). Proposed by the step API-2 architect, 2026-11-26. Design: [docs/plan/steps/36-api-mode-remediation.md](../../plan/steps/36-api-mode-remediation.md) §1.2 (gaps 1–4), §2, §3.2, R9–R11, R12, §6. Contracts [§37](../contracts.md#37-api-mode-remediation-step-api-2) (the quarantine entry `location` view, audit actions; quarantine routes unchanged in shape; no new event, topology v17 unchanged); migration `20261126173221_api_mode_remediation` ([docs/database/README.md](../../database/README.md#step-api-2-migration-20261126173221_api_mode_remediation)). Related: [ADR-0101](0101-api-mode-remediation-policy-and-mailbox-actions.md) (the actions that create and restore these entries), [ADR-0100](0100-api-mode-intake-mailbox-worker.md). **Supersedes in part** [ADR-0046](0046-quarantine-store-and-per-recipient-decisions.md) (decision 1: the policy-engine evaluation transaction is the only writer of entries), [ADR-0047](0047-quarantine-release-revalidation-and-approvals.md) (the release executor and policy re-validation, for mailbox entries) and [ADR-0098](0098-protection-modes-and-detect-mode-copies.md) (decision 7 / note 35 N1: copies never reach quarantine release).

**Context.** Brief scope 5: API-mode remediations appear in the existing quarantine pages with their location, and the existing release flow and approvals apply. [ADR-0046](0046-quarantine-store-and-per-recipient-decisions.md) makes the policy-engine evaluation transaction the only writer of quarantine entries; [ADR-0047](0047-quarantine-release-revalidation-and-approvals.md) releases entries through the policy-engine executor after policy re-validation and redelivery; [ADR-0098](0098-protection-modes-and-detect-mode-copies.md) (7) / note 35 N1 keep copies away from quarantine release. Copies have no policy evaluation (deferred by the product owner) and end `journaled`.

**Decision.**

1. `quarantine_messages.location` (`gateway` default — every existing entry —, `mailbox`) with the mailbox container (`quarantine_folder`, `junk`, `deleted_items`) and links to the copy, mailbox and remediation action (no FKs); `origin = api_remediation`. For mailbox entries `lifecycle_round` holds the copy's **remediation generation**, so the unique key `(message_id, lifecycle_round, rcpt_seq)` is one entry per copy, recipient and generation.
2. **Supersedes ADR-0046 decision 1 in part:** the mailbox-worker writes a mailbox entry in the transaction that completes a successful quarantine-folder, Junk or soft-delete action (tags and hard deletes create none), and expires mailbox entries itself: no lifecycle edge, no mailbox change (the message stays in its container) and no object purge (the EML follows the copy's message retention).
3. **Supersedes ADR-0047 in part:** releasing a mailbox entry is a **restore to the Inbox** executed by the mailbox-worker (a `restore_inbox` action queued by the api in the release transaction; no `mail.quarantine.release_requested.v1`, no delivery). The api's pre-check and the worker's re-check in approved mode use `decideMailboxRestore` over stored facts (hard blocks → approval, or refusal when the tenant disallows hard-block release; scan failure → approval) instead of policy re-validation. Approvals, separation of duties, end-user self-service bounds, Idempotency-Keys, request shapes, outcomes and audit are unchanged. The release log ends `restored` or `restore_failed` (entry back to `held`).
4. **Supersedes ADR-0098 (7) / N1 in part:** a copy can be "released" only as such a provider restore; copies are still never delivered, reinjected, policy-evaluated or rescanned, and their lifecycle still ends `journaled`.
5. The policy-engine sweeper (entry expiry, adoption, object purge), disposal and release executor handle `location = gateway` only; manual quarantine and rescan stay gateway-message routes (`404` for copies).

**Consequences.** One quarantine for both locations: admins and users act on mailbox threats where they already work (list, detail, approvals, self-service, digests), with the release button reading "Restore to inbox" for mailbox entries. Policy-engine changes are guards only. Mailbox entries survive their expiry in the mailbox container (no automatic deletion). Release approvals of copies rest on stored verdict facts instead of a current-policy re-validation (K7: the hard-block floor and the second approver stay).

**Alternatives considered.** A separate mailbox quarantine page and API (contradicts the brief and N9); policy re-validation for copies (deferred by the product owner); quarantine entries for tags and hard deletes (nothing to release). Details: design §6.
