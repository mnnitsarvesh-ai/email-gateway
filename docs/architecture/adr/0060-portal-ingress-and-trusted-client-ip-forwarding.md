# ADR-0060: Portal Ingress and trusted client-IP forwarding

**Status:** Accepted (2026-11-13, step 7.1 WP1; designed in [docs/plan/steps/20-admin-portal.md](../../plan/steps/20-admin-portal.md) P5, §3.4, §3.5). Implemented and verified: `TrustedForwarderMiddleware` (`apps/api/src/http/trusted-forwarder.middleware.ts`, the first middleware of `configureApiApp`) with unit tests against the installed Express 5 (`req.ip` instance property shadows the `trust proxy` getter), e2e tests (separate per-IP login budgets for two forwarded addresses with the token, one shared budget for forged headers without or with a wrong token, headers never reach a handler, absent from the OpenAPI document) and an integration test (`login_audit_logs.ip_address` and the session IP are the forwarded address); `API_TRUSTED_FORWARDER_TOKEN` (`_FILE`) in the api config, `.env.example`, Compose (api and admin-portal) and Kubernetes (Secret `email-gateway-api-trusted-forwarder` mounted only in api and admin-portal); the portal Ingress in `infrastructure/kubernetes/base/admin-portal.yaml`, encoded in `apps/api/test/public-boundary.e2e.test.ts`; both overlays render with `kubectl kustomize`. **Not applied to a cluster** (rendered and tested only). The portal side (BFF headers, `PORTAL_TRUST_PROXY_HOPS`) was built by step 7.1 WP2 and verified end to end by WP6: every request of the Playwright suite reaches the api with the forwarded browser address (separate per-IP login budgets per test), and the built portal image forwarded through the token to the host api (2026-11-13). **Supersedes decision 4 of [ADR-0053](0053-public-internal-api-boundary.md)** (the list of Kubernetes Ingress paths); decisions 1–3, 5 and 6 of ADR-0053 stay in force. Refines the client-IP source of [ADR-0016](0016-authentication-sessions-rbac.md) decision 8 (per-IP brute-force counters) for requests that arrive through the admin portal's BFF.

**Context.** Step 7.1 builds the admin portal as a Next.js application whose server-side route handlers (the BFF, [ADR-0058](0058-admin-portal-architecture.md)) hold the user's tokens in a sealed httpOnly cookie and call the api over the internal network. Two consequences:

1. The portal needs a public entry point. ADR-0053 decision 4 allows exactly two Ingresses (api `Prefix /api/v1/`, click-service `/c/` and `/static/click.css`) and its boundary test refuses a root path (`/`). The portal is a separate application on its own host; it serves pages, its BFF under `/bff/*` and its own liveness probe `/api/health` (portal-local, returns only `{ service, status }`).
2. Every browser request now reaches the api from the portal's address. The api derives the client IP from Express `req.ip` with `HTTP_TRUST_PROXY` hops and never reads `X-Forwarded-For` directly (ADR-0016, authentication.md). Behind the BFF, the per-IP limits (login 20/min, MFA verify 20/min, refresh 60/min, the IP failure block after 50 failures in 15 min) would apply to all portal users together (one attacker could block every login), and `login_audit_logs.ip_address`, `audit_logs.source_ip` and session IPs would all record the portal. Raising `HTTP_TRUST_PROXY` does not help: the api is reached through its own Ingress (one hop) and directly by the portal (zero hops) at the same time, so a fixed hop count is wrong for one of the paths and `X-Forwarded-For` from an internal caller would be spoofable.

**Decision.**

1. **Portal Ingress.** `infrastructure/kubernetes/base/admin-portal.yaml` gets an Ingress `admin-portal` (class nginx, TLS, host `portal.replace-per-environment.invalid`, distinct from the api host) routing `Prefix /` to the `admin-portal` Service. The allowed Ingress paths are now: api `Prefix /api/v1/` (host api), click-service `/c/` and `/static/click.css`, admin-portal `Prefix /` (host portal). `apps/api/test/public-boundary.e2e.test.ts` encodes this list: it allows `/` only for the `admin-portal` Service, requires that host to differ from the api host, and still fails for any other root, `/metrics`, `/health`, `/docs`, worker Services or default backends.
2. **The portal never exposes the api's internal endpoints.** Its BFF proxies only operations of the published OpenAPI document (`/api/v1/*`, an allow-list generated from `docs/api/openapi.json`), so probes, metrics and docs of the api stay unreachable through the portal host.
3. **Trusted forwarder.** A shared secret `API_TRUSTED_FORWARDER_TOKEN` (32–256 characters, `_FILE` accepted, empty = off) is known to the api and the portal (Kubernetes Secret `email-gateway-api-trusted-forwarder`, mounted in exactly these two workloads). The BFF sends `X-EG-Client-IP` (the browser's address, derived from `X-Forwarded-For` with the portal's own `PORTAL_TRUST_PROXY_HOPS`) and `X-EG-Forwarder-Token`. The api's first middleware compares SHA-256 digests in constant time; on a match and a syntactically valid IP it makes that address the request's `req.ip`, so every existing consumer of `clientIp(req)` (route `@RateLimit`s, the login throttle, `login_audit_logs`, `audit_logs.source_ip`, sessions) sees the browser. Otherwise the header is ignored and the normal `req.ip` stays. Both headers are always removed from the request. Metric `api_trusted_forwarder_total{outcome}`; no IP labels.
4. The portal refuses to start in production without the token; the api warns at startup when it is empty in production.
5. Per-principal and per-tenant limits (ADR-0052) are unaffected; they never used the IP.

**Alternatives considered.** Serving the portal on the api host (`/` → portal, `/api/v1/` → api): one host, but the api origin would carry portal cookies and the boundary between API clients and the browser session blurs. Trusting `X-Forwarded-For` with an IP allow-list of portal pods: pod IPs are not stable and the local stack has no such list. Moving the per-IP limits into the portal: duplicates the api's brute-force logic and its audit; the api must stay authoritative. Signing each forwarded IP with an HMAC and timestamp: the header never leaves the cluster network and is stripped by the api; a constant-time token comparison gives the same guarantee with less moving parts.

**Consequences.** A leaked forwarder token lets an internal caller choose the IP the api attributes to its requests (per-IP limits and audit IP attribution only); it is a Secret file, rotated by updating the Secret and restarting both workloads (runbooks [admin portal](../../runbooks/admin-portal.md#forwarder-token-rotation) and [api rate limits](../../runbooks/api-rate-limits-and-reports.md#trusted-client-ip-forwarder-admin-portal)). The boundary test changes with this ADR. A cluster apply and the ingress controller's behaviour are not verified locally.
