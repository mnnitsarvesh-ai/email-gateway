# ADR-0056: Security alert e-mails — kinds, recipients, preferences and producer-side throttling

**Status:** Accepted (implemented in step 6.2; verification record in [§14 of the step design](../../plan/steps/19-webhooks-notifications.md#14-verification-record); not verified: CI, a Kubernetes cluster apply, production-scale throughput). Design: [step 6.2](../../plan/steps/19-webhooks-notifications.md) N1–N5, §4.1, §6.3, D. Builds on [ADR-0045](0045-policy-action-semantics.md) (5.2 ALERT action and sender notices), [ADR-0047](0047-quarantine-release-revalidation-and-approvals.md) (5.3 approvals and admin alerts) and [ADR-0054](0054-webhook-event-model.md) / [ADR-0055](0055-webhook-signing-and-delivery.md) (the events and the auto-disable that request alerts). Supersedes nothing.

**Context.** Administrators must learn about threats, failing domain DNS and disabled webhook endpoints without watching the portal. The platform already e-mails policy alerts (5.2 `policy_alert`), sender notices, quarantine digests and quarantine admin alerts / approval requests (5.3) through the notification-worker (`email.notifications`, plain-text fixed templates, Bcc, deterministic Message-ID, `postfix-notify` smarthost). A spam or malware campaign can produce thousands of threat events per hour; alert e-mails must stay bounded, must never carry message content, and users must be able to opt out of what is optional.

**Decision.**

1. **Three new kinds**, requested by the webhook-worker as the internal event `notification.alert_requested.v1` (exchange `email.policy`, bound to `email.notifications` in topology v11; ids and codes only): `threat_detected` (an `email.threat.detected` at or above the tenant's minimum severity), `domain_dns_failed` (`domain.dns.failed`) and `webhook_disabled` (the auto-disable of ADR-0055). "Quarantine" and "policy triggered" alerts are the existing 5.3 `admin_alert` and 5.2 `policy_alert`; quarantine digests are the 5.3 digests, reused unchanged. No second mechanism and no second digest.
2. **Producer-side throttling.** The fanout (and the delivery role for `webhook_disabled`) upserts `notification_alert_windows` on `(organization, kind, scope_key, window_start)` in its own transaction, `window_start` = the UTC floor of the source event time to the tenant's throttle minutes, `scope_key` = `-` (threats), the domain public id (DNS) or the subscription public id (webhook). Only the first event of a window writes the alert request (carrying the window and `suppressedBefore` = the previous window's count − 1); later events only increment the count. At most one alert per organization, kind, scope and window. The alert's outbox id is deterministic (`webhookEventId(source, 'alert:<kind>')`) and redeliveries hit the ledger, so nothing is double-counted.
3. **Tenant settings** (`notification_settings`, strict, every key optional, cached by the fanout like subscriptions): per kind `enabled` and `throttleMinutes` (threats 15–1 440, default 60; DNS 60–10 080, default 360; webhook 60–10 080, default 1 440), threats `minSeverity` (`medium` or `high`, default `high`), `includeOrganizationContact` (default true). `GET`/`PUT /api/v1/notifications/settings` (`organization:read` / `settings:manage`, row-version CAS, audited with changed paths only).
4. **Recipients** (resolved by the notification-worker at send time on the writer): active, verified users of the organization holding `quarantine:approve` (threats), `domain:manage` (DNS) or `webhook:manage` (webhook), minus users who opted out, keyset-paged by user id until `NOTIFICATION_MAX_RECIPIENTS`; plus `organization_settings.notification_email` for the three new kinds when the contact is included and well formed. No recipient → nothing sent (`notification_alert_messages_total{result="no_recipients"}`).
5. **Preferences** (`GET`/`PUT /api/v1/notifications/preferences`, the user themself, never an API key): `optOut` ⊆ the three new kinds, `policy_alert`, `quarantine_admin_alert`, `quarantine_approval_requested`; `quarantineDigestOptOut` reads and writes the existing `quarantine_user_preferences.digest_opt_out` (one source of truth; the 5.3 route keeps working). The 5.2/5.3 handlers apply the opt-outs to `policy_alert`, quarantine `admin_alert` and `approval_requested` (decisions to a requester and sender notices are not optional).
6. **Content.** Fixed plain-text templates: organization name, kind, severity, window, counts ("events in this window", "suppressed before") and per kind the verdict and stage plus the message public id and a portal link, the tenant's own domain and failing record purposes, or the subscription name (sanitized, ≤ 80, replaced when it looks like an address or URL) with failure counts. **Never** a subject, sender or recipient address, URL from mail, file name, endpoint URL or secret. `Message-ID: <security-alert.<eventId>@<from domain>>`; sent through the existing `NoticeMailer` (Bcc) at least once inside the ledger transaction.

**Alternatives considered** (step design §7). Throttling in the notification-worker: it would still receive and ledger every candidate event; throttling at the producer bounds the queue. A second digest for alerts: duplicates the 5.3 digest; throttle windows already summarize ("N more since the last alert"). New SMS, chat or push channels: out of scope. Alert recipients by role names instead of permissions: roles are tenant-editable bundles; permissions are what the access model checks.

**Consequences.** One alert per window may hide the details of later events (their counts are shown, details live in the portal and the webhooks). Stored settings that fail the schema resolve to defaults and are flagged (`invalidStored`). The alert e-mail path inherits postfix-notify's relay: locally the stack suite points it at the TEST-ONLY `notify-relay-sink` (authenticated STARTTLS with a pinned certificate) and the fixture organizations of the other stack suites start with every alert off, because a developer `.env` may point postfix-notify at a real smarthost. A settings page and a personal preference center in the portal are 7.x.
