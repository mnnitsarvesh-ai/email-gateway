# ADR-0072: Account takeover response safeguards and approvals

**Status:** Proposed (step 8.4; architect 2026-11-16, file created by step 8.4 WP1 on 2026-11-18, not yet implemented end to end). Supersedes nothing. Design: [docs/plan/steps/24-account-takeover-core.md](../../plan/steps/24-account-takeover-core.md) §7 (placeholder ADR-ATO-3 before numbering).

**Context.** The brief asks for configurable responses with safeguards: no automatic disabling on a single weak signal, configurable thresholds, approval of high-impact actions unless a tenant policy authorizes automation, rollback and recovery, recorded and idempotent actions, and no success claim without provider confirmation.

**Decision.**

1. A response catalogue with impact levels (low, medium, high), rollback support and execution kind: gateway actions (alerts, SOC notification, escalation, SMTP sending restriction, SMTP authentication block) execute inline in the authorizing transaction; provider actions (session revocation, MFA, password reset, suspension, forwarding-rule removal, OAuth grant revocation) execute asynchronously through the port; manual actions are attestations.
2. Medium and high-impact actions need an approval by another user holding `ato:respond` with an MFA session, within a time limit; API keys never approve or roll back. "Another user" excludes the requesting user and, for a request made with an API key, the user who created that key (`api_keys.created_by_user_id`), so one person cannot request with their own key and approve from their session (step 8.4 closer review).
3. Automation per tenant and action type (`off`, `recommend`, `automatic`); a medium or high-impact action runs automatically only in `enforce` mode, at or above the configured level, with a strong or correlation signal and signals from two categories, for an account that is not protected, not under a benign override and not in the platform organization, within per-organization and platform hourly caps. The caps are counted under an exclusive lock on the organization's `ato_settings` row, taken before the incident policy's notification windows, so concurrent detections of one organization never exceed them.
4. One non-terminal action per incident, type and target; state transitions under row locks; every change logged (attempt log, incident timeline, audit log, completion event). Every ATO transaction runs at READ COMMITTED (pinned by the callers, `ATO_TRANSACTION_ISOLATION`), so reads after a lock wait see what the previous holder committed; the lock order is account → incident (the incident store locks the subject account first) and organization automation row → notification windows. One active SMTP restriction per subject: a second action for a running restriction shares it (its expiry extended to the later of the two) and a rollback lifts it only when no other succeeded action relies on it; a restriction past `expires_at` that the sweep has not reached yet is expired and replaced. A provider action left `approved` (or an unpolled `rollback_requested`) beyond the `ato.responses` retry horizon (25 h without progress) is settled `failed` / `rollback_failed` with `provider_retry_exhausted` by the maintenance role.
5. Status semantics: `applied` for gateway restrictions, `queued` for notifications, `confirmed` only with a provider reference; missing adapters or capabilities yield `unsupported`.

**Alternatives considered.** Executing gateway actions through the queue (an extra hop for a database write; two executors). Reusing quarantine approvals (message-specific). Automatic suspension on high scores (forbidden by the brief's safeguards). Allowing API keys to approve (no human in the loop).

**Consequences.** Safe defaults delay containment until an analyst approves unless a tenant opts into automation; the hourly caps can delay legitimate automation during a large attack (an alert fires); 8.5 adds adapters without changing the state machine.

Amended by ADR-0085 (step 8.5): "provider-dependent" rollback is made precise per action and provider (read-back confirmation, pre-state capture, rollback only of what the gateway changed).
