# ADR-0065: Archive storage layout and per-tenant envelope encryption (root key, tenant key versions, per-record data keys, `archive-object/1` streaming format, rotation, crypto-shredding)

**Status:** Accepted (2026-11-17, after the step 8.1 local verification: objects decrypted from MinIO to the byte-identical original in the stack suite and the worker integration suite, rotation and root re-wrap in the worker integration suite; record [docs/plan/steps/23-journaling-archiving.md](../../plan/steps/23-journaling-archiving.md) §13, §14). Proposed by the step 8.1 architect on 2026-11-16 (design A5, A8, A9, §4.1, §4.2). Refines [ADR-0008](0008-object-storage.md) (fixes the `org/{tenantId}/archive/...` layout). Extends the key pattern of [ADR-0038](0038-dlp-evidence-masking-and-aadhaar-gating.md) and [ADR-0055](0055-webhook-signing-and-delivery.md) to per-tenant keys and streaming objects. Implementation notes: the root-key provider is asynchronous (KMS-ready, WP2 D2); the HKDF subject is the message (or export) public id (WP2 D3); decryption refuses chunk sizes outside 16 KiB–1 MiB (WP2 D14). The AWS KMS provider is not built (10.1).

**Context.** Archived mail must live in S3 under per-tenant prefixes, encrypted with per-tenant keys, with key ids recorded, audited rotation and the ability to destroy a tenant's data cryptographically. Messages reach 50 MB and must be stored, downloaded and exported without buffering. The existing envelope helpers (DLP evidence, sandbox samples, webhook secrets) encrypt whole buffers under one platform key. AWS KMS is not available locally.

**Decision.**

1. **Layout.** One archive bucket (`S3_BUCKET_ARCHIVE`, versioned, Object Lock enabled, ADR-0066). Records: `org/{organizationId}/archive/{yyyy}/{mm}/{dd}/{messagePublicId}/{captureId}/eml.bin | journal.bin | scan-r{round}-v{revision}.bin` (UTC date of `received_at`, `captureId` = UUIDv7 per attempt, write-once). Exports: `org/{organizationId}/exports/{yyyy}/{mm}/{exportPublicId}.bin`. Every object is ciphertext (`application/octet-stream`); the committed MySQL row names exact version ids; anything unreferenced is an orphan.
2. **Key hierarchy.** A root key (`ARCHIVE_ROOT_KEY`, 32 bytes, id `ARCHIVE_ROOT_KEY_ID`, held only by the archive-worker and the api) wraps per-organization **tenant keys** with versions (`archive_encryption_keys`, AES-256-GCM, AAD `eg-archive-tenant-key/v1\0<organizationId>\0<version>`, SecretBox format); the active tenant key version wraps a fresh **data key per record** (AAD binds organization, message, capture and version; stored only in `email_archives.wrapped_dek`) and per export; each object uses an HKDF-SHA256 subkey of the data key with a random per-object salt. The root key sits behind a provider interface (`wrap`, `unwrap`): local key now, AWS KMS later.
3. **`archive-object/1`.** A 51-byte header (magic `EGARC1`, version, kind, chunk size, salt, nonce prefix) authenticated as AAD of every chunk; chunks of 64 KiB plaintext (configurable) sealed with AES-256-GCM, nonce = prefix ‖ counter ‖ final flag. Truncation, reordering, extension and tampering fail; encryption and decryption stream in constant memory. The plaintext SHA-256 of the original is verified at capture and on every download and export.
4. **Rotation.** Tenant rotation is an audited api action (`archive:manage`, MFA): a new version becomes active, older versions stay decrypt-only; records keep their version. Root rotation deploys a new root key with the old one as previous; the archive-worker re-wraps every tenant key row (small, bounded, audited), after which the previous root key is removed.
5. **Crypto-shredding.** Disposal nulls the record's wrapped data key in the transaction that decides it, so every version and replica of its objects is unreadable from that commit; the organization purge destroys the tenant keys last.

**Alternatives considered.** One platform key for all tenants (no per-tenant isolation or destruction). Per-object KMS calls (unavailable locally, cost and latency at 1 M/day; the provider interface keeps it possible). Whole-buffer AES-GCM (50 MB in memory per capture, no streaming downloads). Server-side encryption only (no tenant separation inside the platform, no crypto-shredding). Storing data keys in object metadata (a bucket leak would carry the wrapped keys next to the data).

**Consequences.** A database dump without the root key, a bucket leak, or a replica reader learns nothing of archived content. Losing the root key loses every archive (custody, backup and rotation are runbook items). Old tenant key versions remain until the organization purge (no data-key re-wrap job in 8.1). AWS keeps bucket-level SSE-KMS underneath (defence in depth).
