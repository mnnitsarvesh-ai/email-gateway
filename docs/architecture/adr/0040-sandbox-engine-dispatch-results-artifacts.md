# ADR-0040: Sandbox engine: an asynchronous, optional engine of the round; dispatch with content-hash dedup, token-checked results, `sandbox-map/1`, sealed artifacts (topology v8)

**Status:** Accepted; implemented in step 4.6 (execution disabled; vm runner not implemented) — verified locally on 2026-11-09, [§13](../../plan/steps/14-sandbox.md#13-verification-results); late sandbox final adds risk revision 1 ([ADR-0042](0042-risk-scoring-placement-and-policy-handoff.md), step 5.1; the round verdict, lifecycle and delivery stay unchanged). Implementation notes: topology v8 (6 exchanges, 19 quorum queues, 45 bindings); the email-worker's dispatcher, results consumer, finalizer and sweeper; the round aggregation ignores asynchronous finals (unit- and stack-tested: the round verdict is unchanged by any sandbox final); `sandbox-map/1` cannot produce `clean` without a VM-isolated run, which this release cannot perform; the api exposes `/scan-settings/sandbox` (plan feature `attachment_sandbox`, `409 feature_not_enabled`) and the sandbox detail of the scans read API (no reuse flag, analysis ids or timings; no artifact download); the organization purge of sandbox rows is deferred (data-ownership requirement). Design: [step 4.6](../../plan/steps/14-sandbox.md) X10–X20. Works with [ADR-0039](0039-sandbox-security-boundary-and-backends.md). Amends [ADR-0026](0026-security-scan-pipeline.md) (an engine may be **asynchronous**: registered in `ENGINE_CATALOG`, never required, never triggered by `parsed.v1` / `rescan_requested.v1` / `scan_stage_ready.v1`, excluded from the round aggregation; its final row is written into the round when its own work ends), [ADR-0024](0024-rabbitmq-topology-retry-dead-letter.md) (topology v8: queues `scan.sandbox.submissions` and `scan.sandbox.results`, `scan.sandbox` rebound to the task event; events `mail.sandbox.task_requested.v1`, `mail.sandbox.task_completed.v1`, `mail.attachment.sandbox_completed.v1`) and [ADR-0028](0028-attachment-scanning-engine.md) decision 8 (the `sandbox_submissions` status transitions and the sandbox result event are defined here; the round still never waits).

**Context.** Step 4.2 writes a `sandbox_submissions` row and a `mail.attachment.sandbox_requested.v1` event for every `suspicious`/`unknown` attachment with a stored part, and promised that the round never waits for the sandbox. The sandbox-controller (ADR-0039) has no database and no access to tenant objects. The brief asks for the sandbox as a scan engine in `ENGINE_CATALOG` consuming `scan.sandbox`, a decision on stage and required/optional, timeouts, how not-executed and failed runs map (unknown, timeout and error never clean), idempotent tasks with duplicate suppression by content hash, rescans as new rounds, encrypted artifacts in restricted S3 with retention and purge, and versions on every result. Execution is disabled in production, so a synchronous engine would add latency and a hard availability dependency for no verdict value.

**Decision.**

1. **`sandbox` is an asynchronous, optional engine** (`ENGINE_CATALOG`: stage `sandbox`, queue `scan.sandbox`, `requiredByDefault: false`, `tenantMayDisable: true`, `mode: 'asynchronous'`). It is never in `email_scans.required_engines`, never in `SCAN_ENGINES`, never triggered by round events, and **excluded from `aggregateRound`** (so its arrival time can never change a round's verdict). Its final row (`scan_engine_results`, engine `sandbox`) is written into the round of its submissions when the last submission of that round becomes terminal — before or after the round completes. Holding mail until a sandbox verdict ("block mode") is deferred until a VM backend exists.
2. **Three hops, each with one owner:** `sandbox_requested.v1` → **`scan.sandbox.submissions`** (email-worker dispatcher, ledger `email-worker.scan.sandbox`) → staged sample + `mail.sandbox.task_requested.v1` (outbox) → **`scan.sandbox`** (sandbox-controller, stateless, bounded lossy queue) → `mail.sandbox.task_completed.v1` (direct publish with confirms) → **`scan.sandbox.results`** (email-worker, ledger `email-worker.scan.sandbox.results`).
3. **Dispatcher:** tenant gate (plan feature `attachment_sandbox` **and** tenant setting `enabled`, opt-in, default off), type and size bounds (tenant may only narrow the platform settings), then **duplicate suppression by content hash**: one `sandbox_analyses` row per `(sha256, analysis_key)` holds the unique `dedupe_key` while it is in flight or reusable (reuse windows per verdict; failures never reused); a hit links the submission to the existing analysis and dispatches nothing. A new analysis stages the sample to `samples/<yyyy>/<mm>/<taskId>.bin` in the sandbox bucket, sealed (`sandbox-sample/1`: AES-256-GCM data key wrapped under `SANDBOX_SAMPLE_KEY`, AAD bound to task id and SHA-256), and writes the task outbox row with a fresh one-time result token (only its SHA-256 is stored, `sandbox_analyses.result_token_sha256`; the token travels sealed in the task under a subkey of `SANDBOX_RESULT_KEY`, AAD bound to the task id).
4. **Results are accepted only for an analysis in `dispatched` state** whose id, organization and SHA-256 match and whose result MAC verifies — HMAC-SHA256 under a subkey of `SANDBOX_RESULT_KEY` over the canonical JSON of the **whole** payload, the envelope organization and the SHA-256 of the task's result token (a copied MAC never fits a modified body); everything else is dropped and metered. `not_executed` results are reused only for sample-dependent reasons (`type_not_supported`, `profile_not_supported`, `size_exceeded`); `deadline_passed` and `backend_disabled` are operational and never reused. A terminal analysis completes every linked submission, writes `mail.attachment.sandbox_completed.v1` per submission (outbox; no queue binds it in 4.6), and writes the round's `sandbox` final for every round whose submissions are now all terminal (under the `email_scans` row lock). A sweeper expires undispatched submissions and analyses past their deadline (`timeout`, never `clean`).
5. **Verdicts: `sandbox-map/1`** (pure, in `@email-gateway/sandbox`): `not_executed` → `unknown` (`sandbox.not_executed` + `sandbox.not_executed.<reason>`); controller failure → `error`; no answer by the deadline → `timeout`; completed → `malicious` (any high/critical finding), `suspicious` (medium findings, resource-limit kills), else `unknown` (`sandbox.no_findings`, plus `sandbox.static_only` or `sandbox.not_vm_isolated`). `clean` only for `isolation = vm`, a complete run of at least the minimum runtime, no findings and no evasion indicators (unreachable in 4.6). The round-level final is the most severe over the round's submissions (`malicious > suspicious > error > timeout > unknown > clean`; all skipped → `skipped`). Every analysis records backend, backend version, isolation, controller version, analyzer (rules) version and map version.
6. **Artifacts** (≤ 16, ≤ 2 MiB each, ≤ 8 MiB per analysis) are sealed by the controller with a fresh data key wrapped to an **X25519 public key** (`sandbox-artifact/1`; the controller cannot decrypt), written to `artifacts/<yyyy>/<mm>/<taskId>/<runId>/<seq>-<kind>.bin` (a fresh 16-hex run id per run, so a retried or redelivered task never overwrites objects a committed row describes); the wrapped key exists only in the committed `sandbox_artifacts` row (crypto-shredding). Retention 1–180 days (default 30) by the email-worker sweeper (null the wrapped key, delete the object), with a bucket lifecycle backstop. Samples are deleted when the analysis ends (sweeper retry, lifecycle backstop ≤ 48 h). No service holds the artifact private key in 4.6.
7. **Rescans** create a new round (new submissions through the attachment engine); the dispatcher may reuse a fresh analysis, so the new round gets its own `sandbox` final.
8. **Optional hash publishing:** with `SANDBOX_PUBLISH_HASHES=true` (default `false`) a `malicious` analysis adds its SHA-256 to `malware_signatures` (`source = sandbox`, expiring).

**Alternatives considered.**

- _Required stage-2 engine after `attachment`:_ every round with a suspicious attachment would wait for a controller that, in production, can only answer `not_executed`; a controller outage would turn rounds `scan_failed` (mail held) for no verdict value. Rejected for 4.6; revisit with block mode once a VM backend exists (a per-tenant required set at round open).
- _Optional engine included in the aggregation:_ the round verdict would depend on whether the sandbox answered before the last required engine — order-dependent, rejected (the ADR-0033 lesson).
- _Controller consumes `sandbox_requested.v1` directly:_ it would need tenant part keys (ADR-0039 rejects) and DB lookups for opt-in and dedup; rejected for the dispatcher hop.
- _Staging inside the attachment engine:_ couples the required engine to the sandbox bucket (an outage would fail attachment attempts); rejected.
- _Symmetric artifact key (the DLP evidence pattern, ADR-0038):_ a compromised controller could decrypt earlier artifacts; the asymmetric wrap costs one ECDH per artifact.
- _HMAC-signed results with only a shared key the controller holds (and a MAC over a few identity fields):_ a compromised key would forge results for any dispatched task (task ids and hashes are on the firehose) and a copied MAC would fit a modified body. Rejected (the first 4.6 implementation did this; replaced before release, review 2026-11-09): the MAC covers the whole body and is keyed to the per-task result token, which confines forging to tasks the controller actually received.

**Consequences.** Topology v8 has 19 queues. The round verdict and delivery are unaffected by the sandbox; its verdict reaches policy (5.x) through the stored results and `sandbox_completed.v1`. The `sandbox` engine row may appear after `mail.message.scanned.v1`. One new non-partitioned table pair (`sandbox_analyses`, `sandbox_artifacts`) and new `sandbox_submissions` columns. The artifact private key must be generated and custodied (offline / secret store) even though no service uses it yet.
