# ADR-0047: Quarantine release re-validates in an executor; one approval model with separation of duties; bounded self-service

**Status:** Accepted (implemented in step 5.3, verified locally on 2026-11-12: re-validation by the executor, approvals with separation of duties, self-service and bulk verified by the `quarantine-smtp` stack suite; [§12, §13](../../plan/steps/17-quarantine.md#13-verification-results); not verified: Kubernetes apply, CI). Design: [step 5.3](../../plan/steps/17-quarantine.md) Q13–Q16, Q18, Q20, Q30. **Amends** [ADR-0025](0025-message-lifecycle-state-machine.md) decision 6 (the operator release of `quarantined` / `held_for_review` messages moves from the api's E14/E15 to the quarantine executor) and implements the 5.3 bindings of [ADR-0037](0037-dlp-policy-actions-and-lifecycle-binding.md) decision 6 and [ADR-0042](0042-risk-scoring-placement-and-policy-handoff.md) decision 7.

**Context.** The brief: every release must re-validate the current verdict and apply release authorization; releasing hard-blocked mail needs an approval path; separation of duties; end-user self-release only for low-risk reasons; one model for REQUIRE_APPROVAL and quarantine approvals; no one-click release without authentication. The 3.3 operator release delivers the original EML without re-validation. A release copy needs URL token signing and S3 streaming (ADR-0049), which the internet-facing api should not do.

**Decision.**

1. **Two-phase release.** The api authorizes, runs an advisory **pre-check** on replica facts and either refuses (`rescan_required`), creates an approval request, or queues the release (`releasing`, release log, `mail.quarantine.release_requested.v1`). The **executor** (policy-engine `quarantine` role) re-validates authoritatively on the writer under the message lock and only then builds the release copy, applies the lifecycle edge and writes the delivery approval. A disagreement converts the release into an approval request or a refusal; nothing is released on the pre-check alone.
2. **Re-validation** = the latest completed scan round's facts (risk revisions 0 and 1, DLP, BEC, attachments, URLs) evaluated by the **current** published policy for the entry's recipient, plus staleness (verdict age, ClamAV signature lag). Stale verdicts require a rescan when the message state allows one, otherwise an approval. Floor reasons (hard blocks, engine failures, missing data, DLP holds), a current policy REJECT, review entries and stale verdicts are **approval reasons**.
3. **One approval model** (`quarantine_approval_requests`): `policy_review` (REQUIRE_APPROVAL, created by the policy-engine), `release_approval` (a release with approval reasons), `release_request` (a user or end-user request). Approve/deny need `quarantine:approve`, a user session with MFA, and an approver who is neither the requester nor the entry's recipient; API keys and end users never approve. The requester of a request made with an API key is the key's creator (`api_keys.created_by_user_id`): the user who triggers a release with their own key never approves it (a key whose creator was deleted bars nobody, since a deleted user cannot approve). An approval covers the reasons it saw; new reasons need a new approval, and that new request keeps the **original** requester (not the approver who queued the approved release), so the requester can never approve the reasons that appeared after the first approval. The executor re-checks both rules on the stored decision. A rescan of a quarantined or held message re-decides its recipients on fresh facts (approval reasons are always derived from current facts, Q13.3), so it is not an approval bypass, but it can deliver held mail: it therefore needs `quarantine:release` besides `message:rescan`. Requests expire (configurable TTL; reviews with their entry).
4. **Self-service** (`mailbox_user`, `quarantine:self`): own verified address only; self-release only when the tenant enables it, the reason is in a tenant-chosen subset of `{spam, bulk, policy}`, the level is at most a bounded maximum, and no approval reason or staleness applies; otherwise a release request.
5. **No one-click release.** Notification links open the portal, which requires login; signed release links are not offered in 5.3.
6. **The 3.3 endpoint** `POST /messages/{id}/release` answers `409 quarantine_workflow_required` for held messages; messages held before 5.3 are adopted into the store by the sweeper.

**Alternatives considered.** Synchronous release in the api (key custody, request latency, 25 MiB streaming) — rejected. Automatic rescan before release — deferred (a hidden second workflow). A separate approvals table per source — rejected (two models). Allowing the requester to approve with MFA — rejected (no separation of duties). Signed one-click release links — rejected (mail-borne bearer capabilities).

**Consequences.** Releases are asynchronous (202 + release id); the portal polls `GET /quarantine/releases/{id}`. A stalled executor leaves entries `releasing` (alerted). Hard-blocked mail can still be released, by two people, unless the tenant disables it.
