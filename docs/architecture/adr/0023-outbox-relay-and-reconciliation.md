# ADR-0023: Outbox relay and reconciliation in a dedicated `event-relay` deployable

**Status:** Accepted. Amends [ADR-0002](0002-modular-services-nestjs.md) (a ninth deployable, `event-relay`). Works with [ADR-0024](0024-rabbitmq-topology-retry-dead-letter.md) (topology, retry, dead-letter). Design: [step 3.2](../../plan/steps/07-rabbitmq.md).

**Context.** Since step 2.1 every producer writes its events to `message_outbox` in the writer transaction of the state change (ADR-0005, carried forward by ADR-0024). Nothing publishes them: consumers read the table through the shared outbox poller (step 3.1 M2), and outbox partitions are never dropped because the drop guard refuses partitions with `published_at IS NULL`. Step 3.2 must publish every row to RabbitMQ at least once, with publisher confirms, without double effects, scaling independently of the producers, and must find messages that were persisted but never processed.

**Decision.**

1. **A dedicated deployable `apps/event-relay`** (NestJS, port 3070) hosts the outbox relay, the reconciliation service and its metrics. It owns no business table: it reads `message_outbox`, writes only `published_at`, `attempts`, `available_at`, `last_error` (relay) and `redrive_count`, `last_redriven_at`, `published_at`, `available_at` (reconciler), and reads `message_idempotency`. It connects to RabbitMQ as the publish-only user `eg-relay`.
2. **Claiming across replicas = advisory-lock shards.** Rows are split into `RELAY_SHARDS` shards by `MOD(CRC32(CONCAT(aggregate_type, ':', aggregate_id)), n)`. A replica publishes a shard only while it holds `GET_LOCK('er:relay#<i>/<n>')` on the dedicated lock connection of the shared `AdvisoryLocks` (`maxHeldLocks` spreads shards over replicas). All events of one aggregate (one message, one domain) are therefore published by one channel, in id order.
3. **Publish, confirm, then mark.** Per shard: select up to `RELAY_SCAN_LIMIT` unpublished, non-poison rows in id order (index `(published_at, id)`), skip rows still in their backoff and every later row of the same aggregate, build the envelope, validate it against the event registry and the content guard, publish persistent and mandatory on a confirm channel (bounded batch of `RELAY_BATCH_SIZE`), and mark `published_at` **only for rows the broker confirmed** (`UPDATE … WHERE published_at IS NULL`). A crash or a failed `UPDATE` after the confirm republishes the row later: at-least-once; consumers absorb it through `processOnce`.
4. **Failure classes.** Broker unavailable, channel closed or confirm timeout = infrastructure: no row is touched and the relay backs off (`RELAY_BROKER_BACKOFF_*`, full jitter). A nack or a mandatory return = this row: `attempts + 1`, `available_at = now + backoff`, `last_error = <code>`. A contract or content-guard violation can never succeed: the row is set to `attempts = RELAY_MAX_ATTEMPTS` (poison), excluded from publishing and reported (`outbox_poison_rows`, alert) until an operator acts. Rows are never deleted, faked as published or skipped silently.
5. **Reconciliation in the same deployable** (single active instance, `GET_LOCK('er:reconciler')`): a cursor sweep over `message_outbox` finds rows of event types bound to an _active_ work queue that were published longer than `RECONCILE_UNCONSUMED_AFTER_SECONDS` ago but have no `message_idempotency (consumer, event_id)` row of that queue's consumer, and **re-drives them through the outbox** (`published_at = NULL`, `available_at = now`, `redrive_count + 1`), at most `RECONCILE_MAX_REDRIVES` times. Re-driven events keep their `eventId`, so every consumer's ledger absorbs the duplicate. It also reports unpublished and poison rows. It never writes business tables and never invents events.
6. **Lag is a first-class metric**: `outbox_relay_lag_seconds{shard}` (age of the oldest publishable row, also measured for shards no replica holds) and the reconciler's `outbox_unpublished_oldest_seconds`.

**Alternatives.**

- _Relay as a module of an existing worker (email-worker or delivery-worker):_ fewer deployables, but the relay would scale, deploy and fail with an unrelated stage, and the worker would need publish rights on every exchange. Rejected.
- _Relay inside each producer (publish after commit):_ every producer (api, smtp-adapter, email-worker, delivery-worker, the recorder) would need broker credentials and its own retry loop; a crash between commit and publish still needs a sweeper. Rejected.
- _`SELECT … FOR UPDATE SKIP LOCKED` claims:_ holds a writer transaction open across the broker round trip, or needs lease columns and a lease sweeper; per-aggregate ordering is lost because rows of one message can be claimed by two replicas. Rejected for the shard locks already used by the outbox poller.
- _Debezium/CDC from the binlog:_ an extra JVM service and Kafka Connect for one table at our volume. Rejected.
- _Reconciler re-publishing directly to a queue:_ would need consume-side credentials and per-queue routing knowledge; re-driving through the outbox reuses the relay's confirms, ordering and metrics. Accepted trade-off: a re-driven event also reaches the other queues bound to it, where the ledgers absorb it.

**Consequences.** One more deployable to run and monitor (two replicas in production; shards ≤ replicas × `RELAY_MAX_HELD_SHARDS`). Outbox partitions become droppable once published. Every consumer of an active queue must leave a ledger row for every event it handles (true for `processOnce`), or the reconciler re-drives it. Ordering is per aggregate in the normal path; a row in backoff holds back the later rows of its aggregate on that shard, but a poison row does not (it is excluded and alerted).

**Amendment (step 3.2 review round 1, 2026-11-04).**

- _A broker nack is infrastructure, not a row failure._ A nack (a full work queue with `reject-publish`, or a quorum queue without quorum) defers the row (`available_at`, `last_error = 'nacked'`) with a backoff that grows with the shard's consecutive nacking passes, and leaves `attempts` unchanged. Only mandatory returns (`unroutable`) and contract or guard violations count towards poison, so a queue that stays full for hours never poisons healthy rows.
- _"No ledger row" is not "lost"._ Consumers now record what they did with an event they did not handle: `QueueConsumer` upserts `message_consumer_progress (consumer, event_id)` with `retrying` after every confirmed retry hop and `dead_lettered` after the confirmed dead-letter copy (new forward migration `consumer_progress`, purged with the ledger). The reconciler settles dead-lettered events (replay is their recovery path), defers events whose last retry hop is within the threshold plus the queue's longest hop gap, and defers while the work queue has ready messages or its depth cannot be read (passive declare on the relay's connection). Deferred rows are watched (`last_redriven_at`) and re-checked; `redrive_count` only counts real re-drives. A failed progress write is logged and never blocks the ack; the cost is at most one bounded re-drive. A dead letter whose reason a relay copy cannot produce (contract, schema version, tenant, approval provenance) never settles a row: it comes from a forged or altered copy and must not hide a lost event.
