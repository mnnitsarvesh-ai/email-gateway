# ADR-0087: Journal-only intake path

**Status:** Accepted (2026-11-20, local verification: stack suite `journal-intake.test.ts` 12/12 (M365 report unwrapped with Bcc, Google copy with the token stripped, on-premises networks, spoof dropped without DSN, 550/452/450 refusals, scanning, silence alert), smtp-adapter and mail-routing suites (WP3), email-worker/delivery-worker gates (WP4), smtp-inbound 8/8, smtp-fail-closed 2/2, smtp-limits 6/6, mime-ingestion 2/2, scan-pipeline 4/4; decision 7 holds for score-based actions only, the GTUBE pre-result still rejects (WP3 deviation 1); live provider tenants, CI and Kubernetes apply pending). Proposed by the step 8.6 architect, 2026-11-20. Design: [docs/plan/steps/27-journal-intake-and-archive-split.md](../../plan/steps/27-journal-intake-and-archive-split.md) (§2 D1–D11, §4). Amends [ADR-0019](0019-smtp-gateway-topology.md) (a fourth LMTP listener and the intake transport), [ADR-0025](0025-message-lifecycle-state-machine.md) (state `journaled`, edges E30–E32), [ADR-0027](0027-rspamd-milter-policy.md) (decision 1: SMTP-time actions are off for intake-only transactions) and [ADR-0078](0078-provider-relay-tenant-attribution.md) (its proof evaluation reused for intake). Supersedes nothing.

**Context.** Customers want journaling and archiving without routing mail through the gateway (brief 8.6 A). Step 8.1 archives only messages in the registry; the inbound path delivers, scans and evaluates policy; provider infrastructure is shared between tenants, so a sending IP address alone never identifies a customer.

**Decision.**

1. **Addresses.** A platform intake domain (`JOURNAL_INTAKE_DOMAIN`) with per-source addresses `journal-<token>@<domain>`; the token is an HMAC of the source's public id and address version under `JOURNAL_INTAKE_ADDRESS_SECRET` (api only); the database stores only SHA-256 hashes. Google Workspace sources add a header token (`X-EG-Journal-Token`), stripped from the stored message. Rotation keeps the previous address valid for an overlap period.
2. **Routing.** The inbound Postfix routes the intake domain to a dedicated smtp-adapter LMTP listener (`:10053`).
3. **RCPT-time authentication.** Address hash, source and organization state, entitlement; the provider egress range of the bound step 8.2 connection (provider kinds) or the source's own networks, never overlapping a provider range (on-premises kinds); TLS; optional client certificate; size and rate limits; intake-only transactions (`452 4.5.3` on mixing intake and tenant recipients or two sources).
4. **LMTP-time proof.** Microsoft 365: every tenant header equals the bound tenant (DKIM recorded as evidence only); Google Workspace: the header token. A failed proof is accepted and dropped (no backscatter); infrastructure trouble is `451`; the intake LMTP never answers `5xx`.
5. **Unwrapping.** Journal reports are unwrapped to the original message plus the full envelope (BCC included, `journal-envelope/1`); unrecognized reports are stored as received (`journal_report_unparsed`).
6. **Registry messages.** Intake messages are registry messages with `email_messages.ingest_source = journal_intake`, recipients in status `journaled`, details in `journal_intake_messages`. They are parsed as usual, scanned only when the organization opted in (`archive-settings/1` `intake.scanEnabled`), and end in the final state `journaled` (E30 `persisted → journaled`, E31 `scanned → journaled`, E32 `scan_failed → journaled`; only for `journal_intake` messages). They never reach the policy engine, delivery, quarantine, webhooks or rescans, and every gateway view excludes them.
7. **Rspamd.** A settings rule `journal_intake` (selected by the intake domain) applies no action, so a spam or GTUBE journal copy is archived. This amends ADR-0027 decision 1: the per-recipient setting is safe because transactions are never mixed.
8. **Monitoring.** Daily counters per source, health (`unknown`, `healthy`, `silent`, `failing`, `paused`) and a `journal_intake_silent` alert (`notification.alert_requested.v1` through the outbox; no topology change).

**Consequences.** The 8.1 engine archives intake copies unchanged; one column and one index rebuild on `email_messages` (`email_messages_org_received_dir_verdict_src_idx`); customers configure journal rules from generated guides; Google copies carry routed recipients only; proof failures are invisible to senders (visible in health, counters and alerts).

**Alternatives considered.** A separate archive fact source (duplicates the capture engine); ordinary inbound mail with a no-delivery policy (policy, delivery and webhooks would see it); addresses from the organization's public id (not a secret); tenant binding by first use (TOFU); bouncing on proof failure (backscatter); a separate intake MX instance (kept as a deployment option). See the design §5.
