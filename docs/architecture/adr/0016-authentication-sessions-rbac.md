# ADR-0016: First-party authentication, rotating sessions, permission-based RBAC and an audited platform override

**Status:** Accepted

**Context.** Steps 1.2 and 1.3 need login, sessions, MFA, API keys and tenant-aware authorization for the control-plane API. The step 1.1 schema already has `users`, `roles`, `permissions`, `role_permissions`, `user_roles`, `user_sessions` (hashed refresh token plus `family_id`), `api_keys` (prefix plus HMAC) and `login_audit_logs`. `docs/architecture/contracts.md` listed "OIDC for the portal" as the plan, but no identity provider exists, the brief asks for password login with Argon2id, and customer SSO is a plan feature (`sso`), not a prerequisite. ADR-0012 requires the tenant to come from the authenticated principal, never from a header.

**Decision.**

1. **First-party credentials.** The `api` app authenticates users itself: email plus password (Argon2id, OWASP parameters, rehash on login when parameters change), optional TOTP (RFC 6238) MFA with recovery codes. External IdP SSO (OIDC/SAML) is a later addition behind the `sso` feature flag and will issue the same sessions.
2. **Tokens.** Access tokens are short-lived JWTs (HS256, default 10 minutes, at most 15) signed with a key from configuration (`AUTH_JWT_SECRET`, file-mountable, with an optional previous key for rotation). Claims carry only public ids (`sub` = user `public_id`, `org` = organization `public_id`, `sid` = session id). Refresh tokens are opaque 256-bit random strings, stored only as SHA-256 hashes in `user_sessions`. Every refresh **rotates**: the presented row is marked `rotated` and a new row is inserted in the same `family_id`. Presenting a rotated token is **reuse**: the whole family is revoked and audited. A family has a sliding idle expiry and an absolute maximum age.
3. **Immediate revocation.** Revoking a session writes a short-lived Redis deny entry for its `sid`, checked on every request, so a revoked access token stops working before it expires. Suspending a user or an organization revokes their sessions the same way.
4. **Permissions, not role names.** The `permissions` table (seeded catalog) is the source of truth. Guards check `resource:action` permission keys resolved from the principal's roles; no code compares role names. The eight default roles are seeded system roles (`super_admin`, `platform_admin`, `organization_admin`, `domain_admin`, `security_analyst`, `quarantine_reviewer`, `compliance_auditor`, `read_only_user`). Organizations may add custom roles built from tenant-scoped permissions only, and nobody can grant a permission they do not hold. No escalation applies in both directions: a principal may grant or edit only roles whose permissions it holds, and may act on another user (email, status, deletion, MFA reset, roles, sessions) only if it holds every permission of that user's roles.
5. **Tenant context.** Authentication produces a `Principal`; a `TenantScope` (the organization id plus how it was obtained) is derived from it and is the only way to call tenant-scoped repository methods. Repository methods take the scope as a required argument and always filter by `organization_id`. A resource of another tenant is reported as `404`, not `403`.
6. **Platform override.** Platform operators belong to the platform organization. They reach another tenant's data only through an explicit override: an MFA-authenticated platform user with `platform:tenant_override` starts an override for one organization with a written reason and a bounded duration. That writes an `audit_logs` record and returns a short-lived, non-refreshable access token whose scope is the target organization, with permissions limited to tenant-scoped ones. Every request made with it is audited with the override id and reason. Nothing that would outlive the override can be created with it: API keys, invitations, role changes and email changes are refused under an override. Managing the organization catalog itself (`/api/v1/organizations` with `platform:organizations`) is a platform function, not an override, and every mutation is audited.
7. **API keys** are organization-scoped automation credentials: shown once, stored as prefix plus HMAC-SHA256 (server-side pepper), scoped to a subset of tenant-scoped permissions the creator holds, revocable, with expiry and throttled last-used tracking. They require the organization's `api_access` feature.
8. **Brute-force protection** uses Redis counters per account and per client IP with progressive lockout, mirrored to `users.locked_until`, and every attempt is written to `login_audit_logs`. Auth endpoints are rate limited. Responses never reveal whether an account exists.

**Alternatives.**

- _Adopt an external IdP now (Keycloak, Cognito, Auth0):_ strong features, but another stateful service in the 8 GB local stack and in dedicated deployments, and tenant/role mapping still has to live here. Deferred to SSO.
- _Asymmetric JWT (EdDSA):_ lets other services verify tokens without the secret. Only `api` verifies tokens today, and the existing secret tooling generates hex secrets, so HS256 with a 256-bit key is simpler. Switching later is a key-type change behind the same token service.
- _Stateless refresh JWTs:_ no database lookup, but no reuse detection and no revocation. Rejected.
- _One `user_sessions` row per session with the hash updated in place:_ fewer rows, but only the immediately previous token could be recognised as reused. Rejected in favour of one row per issued refresh token, with a purge of expired rows.
- _Checking role names in guards:_ rejected; permissions are data, roles are bundles.
- _Platform users act cross-tenant whenever they hold a platform permission:_ simplest, but no reason is captured and every query path must remember to allow it. Rejected for the explicit, audited override token.

**Consequences.** Every non-public route declares its permissions, and a test enumerates the routes to prove it. Redis becomes a hard dependency of authenticated requests (the API already fails readiness without it); auth fails closed when Redis is unavailable. Rotated session rows accumulate until the purge removes expired ones. Concurrent refreshes of one token are treated as reuse, so clients must serialise refresh.
