# ADR-0096: AI assistant asynchronous report jobs: outbox → RabbitMQ → an api-assistant consumer acting with a GET-only job token of the user's live session

**Status:** Proposed (2026-11-26, step AI-6). Design: [docs/plan/steps/34-ai-chat-hardening-operations.md](../../plan/steps/34-ai-chat-hardening-operations.md) §2.0 (I26), D5, D10, §3, §4.2, §5, §6 (A6-5). Contracts [§35.6](../contracts.md#356-hardening-and-operations-step-ai-6); topology v16 ([messaging-topology.md](../messaging-topology.md#status)); migration `20261125195835_ai_assistant_hardening` ([docs/database/README.md](../../database/README.md#step-ai-6-migration-20261125195835_ai_assistant_hardening)). Amends [ADR-0091](0091-assistant-architecture-loopback-tools.md) (I2 and decision 1: [Amendment AI-6](0091-assistant-architecture-loopback-tools.md#amendment-ai-6-2026-11-26)) and [ADR-0095](0095-assistant-reports-native-tools-static-html-email.md) (its rejected alternative (c), "an async RabbitMQ job with a service principal": [Amendment AI-6](0095-assistant-reports-native-tools-static-html-email.md#amendment-ai-6-2026-11-26)). Related: [ADR-0023](0023-outbox-relay-and-reconciliation.md) (outbox and relay), [ADR-0024](0024-rabbitmq-topology-retry-dead-letter.md) (topology), [ADR-0094](0094-assistant-conversation-storage-retention-audit.md) (storage; amended in AI-6). Changes no Accepted ADR.

**Context.** AI-R composes a security report synchronously inside the turn: up to ten loopback reads (`REPORTS_QUERY_TIMEOUT_MS` 10 s each, `ASSISTANT_TOOL_TIMEOUT_MS` 15 s per tool call) and a render, all within the turn deadline. For windows longer than a week the report sources aggregate far more rows; the turn's patience is not enough, and the brief (§12) asks for long work to run asynchronously through the outbox and RabbitMQ. Up to AI-5 invariant I2 (ADR-0091) says tools run only inside a live request of the user with that request's credential, and nothing in the api consumes RabbitMQ on a user's behalf. ADR-0095 rejected an asynchronous job with a **service principal**: a standing credential that reads tenant data outside the user's session weakens I2 and needs its own RBAC. A background job needs some credential to call the loopback, and every control of the report operations (guards, RBAC, tenant scope, rate limits, plan gating, ATO enablement) must keep applying, as I1 requires.

**Decision.**

1. **When (D5, A6-5).** `report_generate` resolves the window as today. When `ASSISTANT_REPORT_JOBS_ENABLED` and the window is longer than `ASSISTANT_REPORT_SYNC_MAX_HOURS` (168 h, ≤ `REPORTS_MAX_RANGE_DAYS` × 24), the report becomes a job; otherwise it runs synchronously exactly as in AI-R. The tool's input schema is unchanged (the server decides). It is a read: no confirmation; the daily generation limit counts queued reports; no automatic e-mail when ready.
2. **Queue in one transaction.** After the executor's steps 1–6 and AI-R D2 steps 1–4: insert `ai_chat_reports` with the new status **`queued`** (title, period, sections requested; no object), insert `ai_chat_report_jobs` (report, conversation, execution, owner, the principal's **session id** and **auth methods**, home organization public id, platform override id, the validated arguments, the organization label, `expires_at = now + ASSISTANT_REPORT_JOB_TTL_SECONDS` (1 800 s), status `queued`, correlation id), the outbox row **`assistant.report.generate_requested.v1`** (eventId = the job's public id, aggregate `assistant_report_job`, payload strict ids and a time), the execution row (`allowed`, `succeeded`, HTTP 202) with a `report` card in status `queued` and the audit rows `assistant.tool_executed` and `assistant.report_job_queued`. The envelope tells the model not to state figures. No credential is stored: the job row holds the session id, never a token.
3. **Topology v16.** Queue `assistant.reports` (work, home exchange `email.policy`, the event binding and its retry binding, ledger `api-assistant.reports`, service `api-assistant`, retry `hold` 5 attempts 10 s–60 s within 30 min, policy `work`, not reconciled: the api's sweep fails jobs past `expires_at`). Role user **`eg-assistant`**: configure `^$`, read `^assistant\.reports$`, write `^email\.(policy|events)$`, topics `email.policy` `^retry\.assistant\.reports\.` and `email.events` `^dead-letter\.assistant\.reports(\.|$)`; `eg-ops` may replay the queue (retry prefix only).
4. **Consumer in the api process (D5, D10).** `ReportJobConsumer` in the assistant module starts only when `ASSISTANT_REPORT_JOBS_CONSUMER=true` with `RABBITMQ_ASSISTANT_URL` (the `api-assistant` Deployment of the same api image, and host-run development; prefetch `ASSISTANT_REPORT_JOB_CONCURRENCY`). Per message, idempotent through the consumer ledger and row CAS: load the job (missing → ack; terminal → ack; past `expires_at` → job and report `failed` `assistant_report_job_expired`); CAS `queued` (or `running` with an expired lease) → `running`, `attempts + 1`, `lease_until = now + 60 s`, renewed every 20 s while the attempt runs (lost CAS under another consumer's live lease → a transient retry that claims the job once a dead holder's lease lapsed; otherwise → ack; a claim past 5 attempts fails the job `assistant_report_job_failed`); mint the job token (decision 5) and resolve the principal through the same code path the guard uses (`AccessTokenPrincipalResolver`, extracted from `AuthGuard.fromAccessToken`) — `null` (session revoked or expired, user disabled, override ended) → `failed` `assistant_report_session_ended`; re-check assistant availability, `assistant:use` and `report:read` now → else `failed` `assistant_report_not_allowed`; run AI-R's composition (one `buildAndStore` path shared by the sync and async callers) with the job token, correlation `<job correlation>.<n>` and `x-eg-assistant-execution` = the original execution; then one transaction: report `available`, job `succeeded`, audit `assistant.report_generated` (actor = the user, `{ async: true, jobId }`). "No data" or a storage failure is retried by the queue while `attempts < 5` and before `expires_at`, else `failed`. Any unexpected error after the claim releases it (`queued`) before the queue's retry hop, or fails the job `assistant_report_job_failed` at the last attempt; a pod crash leaves at most a 60 s lease, never a job stuck until its expiry.
5. **The job token (I26).** `TokenService.issueAssistantJobAccess({ userPublicId, organizationPublicId (home organization), sessionId, amr, overrideId?, jobId })` mints an ordinary access JWT of the user's **own session family** plus the claim **`ajb: <jobPublicId>`**, `exp = now + 300 s`. It is never stored or logged and never leaves the api process except as the `authorization` header of the loopback call to `ASSISTANT_LOOPBACK_URL`. **AuthGuard rule:** a verified access token with `ajb` is accepted only when the request method is `GET` and the matched route path is in `ASSISTANT_JOB_ROUTES` — the path templates of the report source tools (`/api/v1/reports/{traffic,threats,url-clicks,delivery,processing,top-domains}`, `/api/v1/quarantine/summary`, `/api/v1/ato/overview`, `/api/v1/ato/accounts`), derived from the package's `REPORT_SOURCES` and the registry (one source of truth); anything else → `401 unauthorized`, metric `api_assistant_job_token_refusals_total`, a warn log with the route template and job id only. Session revocation, rate limits, permissions, tenant scope and override checks run unchanged; the principal carries `assistantJobId` (informational).
6. **Retention and the chat.** The conversation's content purge cancels its `queued`/`running` jobs (`cancelled`, report `purged`); the retention job fails jobs past `expires_at`; the AI-R `pending` sweep ignores `queued`; the organization purge deletes jobs before reports. The report card polls `GET /assistant/reports/{reportId}` (view gains `job` and the `queued` status) every 5 s while `queued`/`running`; the next turn's action updates tell the model the outcome (`reported_at`, as confirmations). `report_send_email` on a report that is not `available` → `409 assistant_report_not_ready`.
7. **I2 amended.** I2 becomes: "a tool runs only inside a live request of the user, **or inside a report job created in such a request that acts with a GET-only token of the same live session for at most `ASSISTANT_REPORT_JOB_TTL_SECONDS`**." Nothing else may act in the background on a user's behalf.

**Alternatives considered** (design §5).

- **(a) Keep reports synchronous with longer timeouts.** The brief asks for asynchronous long work through the outbox and RabbitMQ; long windows would block the turn (and the SSE connection) for minutes and still hit the turn deadline.
- **(b) A service principal per tenant.** A standing credential that outlives sessions breaks I2, needs its own RBAC and would keep reading after the user lost a permission or left; rejected again (ADR-0095).
- **(c) Store the user's bearer or refresh token in the job.** Stores a credential at rest (against I2 and the spirit of I27) and a refresh token would outlive the job; the job token is minted per attempt from the live session instead.
- **(d) Let the consumer call the report services in-process.** A parallel business path that skips the guards, plan gating and rate limits of the routes (against I1).
- **A consumer in the notification-worker or a new worker app.** Only the api may depend on `@email-gateway/assistant` (dependency boundary) and only the api pipeline serves the loopback reads; a new deployable would be the same image anyway (the `api-assistant` Deployment).

**Consequences.**

- One event type (forty registered), topology v16 (+1 queue, +2 bindings: 76, +1 policy: 25), one broker user (`eg-assistant`), four configuration keys for jobs plus `RABBITMQ_ASSISTANT_URL`, one table (`ai_chat_report_jobs`) and one ENUM value (`ai_chat_reports.status` `queued`).
- The api process consumes RabbitMQ for the first time (only with `ASSISTANT_REPORT_JOBS_CONSUMER=true`); the main `api` Deployment keeps it off, the `api-assistant` Deployment runs it; the containerized local api keeps it off unless the Playwright override turns it on.
- `AuthGuard` gains a claim-specific allow-list; every other route refuses a job token, and a misuse raises a critical alert (`AssistantJobTokenMisuse`).
- A job dies with the user's session (logout, revocation, expiry), a lost permission, a disabled assistant or after 30 minutes: an accepted limitation (A6-5), stated in the card.
- Report jobs are not reconciled by the relay's reconciler; a lost message ends as an expired job (`AssistantReportJobsFailing`, `AssistantReportJobsBacklog` alerts and the runbook cover it).
