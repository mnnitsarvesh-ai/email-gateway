# ADR-0043: A constrained, declarative policy DSL and a pure deterministic evaluator with an enforced strictness contract

**Status:** Accepted; implemented in step 5.2 — verified locally on 2026-11-11, [§13](../../plan/steps/16-policy-engine.md#13-verification-results); implementation notes in [§12](../../plan/steps/16-policy-engine.md#12-deviations-log) (`@email-gateway/policy-dsl`: `normalizeAddress` is not exported, so the api deep-imports it — §12.4 point 1; the engine resolves directory memberships for recipients and the authenticated sender, the api also for the raw senders, which does not change the input — §12.3 point 2, §12.4 point 2, and dry-runs of a department policy reproduce in the stack; no CHECK constraint for “exactly one of address/user” because MySQL refuses it next to the CASCADE key, enforced by the api — §12.1 point 1). Design: [step 5.2](../../plan/steps/16-policy-engine.md) P1–P12, §3. Builds on [ADR-0041](0041-risk-scoring-model.md) and [ADR-0042](0042-risk-scoring-placement-and-policy-handoff.md) (decision 7, the binding for 5.2), [ADR-0034](0034-bec-ai-layer-invariant.md) (AI never decides alone) and [ADR-0037](0037-dlp-policy-actions-and-lifecycle-binding.md) (DLP action binding). Reuses the step 1.1 policy tables (`email_policies`, `policy_versions`, `policy_execution_logs`) through a forward migration; retires (keeps, never reads or writes) `policy_conditions`, `policy_actions` and `policy_exceptions`.

**Context.** The brief asks for inbound, outbound and internal policies with rule priority, AND/OR groups, sender, recipient, domain, IP, attachment, URL, risk, DLP and time conditions, trusted-sender and department/user exceptions, nine actions (ALLOW, REJECT, QUARANTINE, TAG, WARN, REQUIRE_APPROVAL, URL_REWRITE, ARCHIVE, ALERT), drafts, versions, publish, rollback, testing, dry-run and history, a constrained evaluation DSL, no customer-supplied code, and deterministic evaluation. Step 5.1 left a binding that policy must be at least as strict as every hard block, the failure floor and the DLP binding, that a missing risk row is a hold, that a level-only recommendation may be relaxed only by an explicit audited tenant rule, that an AI-only raise never justifies a hold, and that revision 1 can only make the decision stricter. The step 1.1 schema has policy tables without writers: per-policy rows with direction, priority, status and an active version pointer; versions with a JSON `definition` and its SHA-256; a relational decomposition of conditions (OR groups of AND-ed conditions), actions and exceptions; and a partitioned, unwritten `policy_execution_logs`.

**Decision.**

1. **The DSL is data, never code.** A policy version's `definition` is a JSON document `policy-dsl/1` validated by a strict zod schema in a new pure package `@email-gateway/policy-dsl`: `{ dslVersion, direction, priority, rules[], exceptions[] }`; a rule is `{ id, priority, enabled, directions?, when, unless[], actions[], stop?, override? }`; `when` and each `unless` entry are trees of `all` / `any` / `not` nodes over **leaves** `{ field, op, value, quantifier? }` from a closed field catalog with typed values and a closed operator list (equals, in, not_in, domain_in (label-suffix match), glob (bounded `*`/`?`), regex (RE2 syntax compiled with `re2js`: linear time, ≤ 256 characters), in_cidr, numeric comparisons and between, contains_any / contains_all on code sets, exists, is, and the time leaves `time.window` / `time.date_range` with an explicit IANA time zone). Depth, node counts, list sizes, string lengths, rules per policy, policies per tenant and document size are bounded. Unknown keys, fields, operators or value types are refused with violations by JSON path. No `eval`, `Function`, template, SQL or script is ever compiled or executed; regular expressions run only through RE2.
2. **Three-valued, monotone-safe semantics.** Leaves evaluate to true, false or **unknown** (missing fact, truncated list, absent risk row); `all`/`any`/`not` follow Kleene logic; a rule matches only when `when` is definitely true, and an exception applies only when it is definitely true. Missing data therefore never makes a rule fire and never makes an exception apply.
3. **Exceptions can only remove a tenant rule's effect** and are constrained by schema: positive only (no `not`, no negated operators), list quantifiers `all` (an exception covers a multi-recipient message only if it covers every recipient), and sender identity only through **authenticated** fields (`sender.authenticated.*`, `sender.trusted`, `sender.department`, `sender.user`), never the raw envelope sender or header From. The same identity restriction applies to the `when` of any rule whose disposition is ALLOW or that is flagged `override`. Trusted-sender facts come from the BEC engine (T1 requires authentication as From) plus DMARC pass and no authentication-failure signal, as in 5.1 R7. Departments and users come from tenant directory data (new `tenant_departments` / `tenant_department_members`, and `users`), matched on envelope recipients (inbound/internal) or the organization-authenticated envelope sender (outbound/internal).
4. **Conflict resolution.** The active policies of the message's direction (`direction` or `any`) form one ordered rule list: (policy priority, policy public id, rule priority, rule id), all ascending. Rules are evaluated in order until the first **matched** rule with `stop = true` (default: true when the rule has a disposition). The tenant disposition is the **strictest** disposition among matched rules (`allow < require_approval < quarantine < reject`); the decisive rule is the first matched rule carrying it. Non-terminal actions (TAG, WARN, URL_REWRITE, ARCHIVE, ALERT) of every matched rule are collected and merged deterministically. Policy-wide `exceptions` exempt every rule of that policy.
5. **The strictness contract is code, applied after the rules, and cannot be configured away.** The evaluator computes from the facts: the **floor** (mandatory: every hard block, the failure floor (any failed, missing or unknown required engine, a missing child row, a scoring error row: the whole recommendation of that revision), the DLP binding of ADR-0037 including a missing DLP row, a missing risk row for a scanned round (hold), a parse failure (hold)); and the **recommendation** (the platform default `pol-default/1`: the 5.1 recommended action mapped `deliver → ALLOW`, `tag → ALLOW + TAG`, `require_approval → REQUIRE_APPROVAL`, `quarantine → QUARANTINE`, `block → REJECT`, plus the 4.4 B17 deterministic-BEC-suspicious hold that the development pass-through enforced). Revision 1 joins both by maximum and can only raise them. Final disposition = max(floor, tenant disposition if at least the recommendation, else the recommendation) — except that a tenant disposition weaker than a **level-only** recommendation is kept when its decisive rule has `override: true` **and** the tenant setting `allowRecommendationOverrides` is on (both audited); never below the floor. ALLOW therefore never releases a hard block or failure. A rule that reads AI-derived fields (`bec.verdict`, `bec.aiRaised`) may not carry a hold disposition (schema), so an AI-only raise never holds mail on its own.
6. **Pure and deterministic.** `evaluatePolicy(input, compiledSnapshot)` has no I/O, clock or randomness. The evaluation time is a fact (the round's `completedAt`, or the parse failure time), not the wall clock. Integer arithmetic only; time zones through `Intl` (the Node ICU/tz data version is recorded). Output: matched rules in order, the final action set with origins, the decisive rule, floor, recommendation, override, clamps, an explanation built from codes and ids only, the versions (DSL, evaluator, input, platform default, snapshot SHA-256, tenant generation, every policy version used) and `inputSha256` = SHA-256 of the canonical input. Same input and snapshot → byte-identical output (tested, including permutations and seeded random inputs).
7. **Storage reuses the step 1.1 tables, forward-migrated.** `email_policies` = a tenant policy (name, description, status, active version pointer; `direction` and `priority` are copied from the active version's definition); `policy_versions` = its versions (draft editable with compare-and-set, published immutable; activation and rollback are pointer moves). A new one-row-per-organization `policy_settings` holds the tenant settings and a **generation** counter incremented in every transaction that changes what evaluation sees, so the evaluator caches compiled snapshots by `(organization, generation)` and a change applies to the next evaluation after commit. `policy_execution_logs` (partitioned monthly, empty) gains the evaluation record columns and becomes the execution history (one row per message and lifecycle round). Legacy-format versions are retired by the migration (status `superseded`, pointer cleared, policy `disabled`); the relational tables are kept but no longer read or written.

**Alternatives considered.** A scripting or expression language (CEL, JSONLogic with custom operators, JavaScript in a VM sandbox): rejected, arbitrary code or unbounded evaluation cost is out by brief, and a typed catalog makes validation errors precise. The relational condition tables of step 1.1: rejected, they express only OR-of-AND with one negate flag and no exceptions, quantifiers or typed values, and a JSON document hashes and versions atomically. One policy document per tenant: rejected, independent policies with their own versions and rollback are the expected enterprise model and the legacy tables already have it; one ordered rule list keeps determinism. Pure first-match: rejected, a low-priority REJECT would be skipped by an earlier ALLOW; strictest-of-matched plus explicit `stop` gives both priority and safety. Strictness enforced only by validation at publish: rejected, the floor depends on per-message facts and must be applied at evaluation. Wall-clock evaluation time: rejected, dry-runs could not reproduce stored decisions.

**Consequences.** The evaluator is reusable by the policy-engine (writer facts) and the api (dry-run and test on replica or synthetic facts) through one shared input builder. Tenants cannot weaken hard blocks, failures, DLP holds or missing-data holds by any configuration. Department membership is live directory data (recorded in the input hash, not frozen by a policy version). Multi-recipient messages get one message-level disposition (strictest across recipients); per-recipient split dispositions are not in 5.2.
