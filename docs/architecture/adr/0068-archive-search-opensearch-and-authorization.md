# ADR-0068: Archive search in a metadata-only OpenSearch index with per-tenant filtered aliases, a mandatory tenant filter, field-level authorization and ADR-0062 masking; MySQL stays the source of truth

**Status:** Accepted (2026-11-17, after the step 8.1 local verification against OpenSearch 2.19.3: tenant aliases with the mandatory filter, cross-tenant probes through the aliases, masked search through the api, per-day reconciliation and the rebuild with an atomic alias swap; record [docs/plan/steps/23-journaling-archiving.md](../../plan/steps/23-journaling-archiving.md) §13, §14). Proposed by the step 8.1 architect on 2026-11-16 (design A15–A17, §4.3). Refines [ADR-0009](0009-search-and-analytics.md) and applies [ADR-0062](0062-sensitive-message-metadata-masking-and-reveal.md) unchanged to archived messages. Implementation notes: one ordered index writer (`eg:archive-index-sync`, WP3 D3); new yearly indices carry every tenant alias at creation (WP3 D4). **Not verified:** Amazon OpenSearch fine-grained access control and SigV4 (10.1; locally the security plugin is off).

**Context.** The archive must be searchable by sender, recipient, subject, date, Message-ID, verdict and attachment over years of mail for a 1 M messages/day platform, which MySQL driver indexes (ADR-0061) cannot serve over multi-year ranges. ADR-0009 chose OpenSearch for message metadata search with a mandatory tenant filter, index-per-time-window and aliases, but nothing used it yet. Subjects, recipient addresses and some header values are masked by default for every caller (ADR-0062), and searches that would confirm a masked value need `message:reveal`.

**Decision.**

1. **Metadata only.** Documents hold ids, times, direction, category, sources, status, sender, recipients and their domains, subject, Message-ID key, size, attachment names and hashes, verdicts, risk, authentication results, retention and lock facts. Never a body, attachment content, URL or other header value. `dynamic: strict` mapping.
2. **Layout and isolation.** Yearly indices of a versioned template, custom routing by organization, and a **filtered alias per tenant** (`<prefix>-t<organizationId>`, term filter + routing) over every index of the current version. The api resolves the alias only from the authenticated scope and its query builder always adds the organization term filter; no request field names an index. In production, Amazon OpenSearch fine-grained access control limits the api to reading tenant aliases and the archive-worker to writing indices; locally the security plugin is off (documented difference).
3. **MySQL is the source of truth.** Every record change enqueues an index operation in the same transaction; the archive-worker builds documents from the current row (coalescing, idempotent) and applies them in bulk; per-day count reconciliation repairs drift; a rebuild CLI re-indexes into a new version and swaps aliases atomically. OpenSearch being down never blocks capture, retention or disposal.
4. **Field-level authorization and masking.** Results are masked for every caller exactly as on live messages (subject withheld with a flag, recipients `f***@example.com`, sender side and attachment names in clear); clear subject, recipients and To/Cc/Subject values only through the audited archive reveal (`archive:read` + `message:reveal`), read from MySQL and the encrypted journal report. Filters on recipient, subject and custodian need `message:reveal`.
5. **Contract.** `GET /api/v1/archive/messages` (`archive:search`, class `expensive`): bounded range, allow-listed filters, signed v1 cursor wrapping `search_after`, no totals, an index-lag header; the first page is audited with filter names and hashes only. Unavailable search answers `503`; record details and content routes keep working from MySQL and S3.

**Alternatives considered.** One index per tenant (shard explosion at many tenants; dedicated deployments get their own domain instead). Monthly indices (alias fan-out per tenant per month). The query-layer filter alone (one bug from cross-tenant results; the alias makes isolation structural). Indexing bodies for content search (defeats per-tenant encryption at rest; needs its own access design; deferred). Keeping archive search in MySQL (multi-year ranges and subject text search do not fit the driver model).

**Consequences.** Search is eventually consistent (seconds, reported as lag); eDiscovery searches report completeness explicitly instead of assuming it. The tenant alias count grows with archiving tenants and is re-applied to each new yearly index. Production needs OpenSearch roles and sizing (10.1).
