# ADR-0055: Webhook secrets, signatures and delivery (retries, dead letters, auto-disable, SSRF, topology v11)

**Status:** Accepted (implemented in step 6.2; verification record in [§14 of the step design](../../plan/steps/19-webhooks-notifications.md#14-verification-record); not verified: CI, a Kubernetes cluster apply, production-scale throughput). Design: [step 6.2](../../plan/steps/19-webhooks-notifications.md) W1, W6–W13, §4.2–§4.4, §8, §9. Builds on [ADR-0010](0010-configuration-and-secrets.md) (configuration and secrets), [ADR-0024](0024-rabbitmq-topology-retry-dead-letter.md) (topology), [ADR-0023](0023-outbox-relay-and-reconciliation.md) (relay and reconciliation), [ADR-0029](0029-url-security-engine.md) (the SSRF guard) and [ADR-0054](0054-webhook-event-model.md) (event model). Idempotency of the two secret routes: [ADR-0057](0057-idempotent-secret-bearing-routes-redacted-replay.md).

**Context.** Webhook endpoints are tenant-controlled URLs on the Internet. The platform must prove to a receiver that a request is genuine and unmodified, deliver at least once without letting one slow or dead endpoint (or one tenant) hold the platform's capacity, never be usable to reach internal addresses, and keep the signing secret narrowly held. Webhook traffic is driven by about ten internal events per message, through a new quorum queue on the relay's confirmed publish path.

**Decision — secrets and custody.**

1. A secret is `whsec_` + base64url of 32 CSPRNG bytes (49 characters; step design §13 WP1 deviation 3), generated on create and rotate, shown once (ADR-0057: never in idempotency rows, audit metadata, logs or later responses).
2. Stored only encrypted (`webhook_subscriptions.secret_ciphertext`): AES-256-GCM with a dedicated key `WEBHOOK_SECRET_ENCRYPTION_KEY` (64 hex, `_FILE` accepted; `_PREVIOUS` decrypt-only for key rotation), AAD `webhook-secret:v1:<orgId>:<subscriptionPublicId>:<secretVersion>`. Only the api (encrypt) and the webhook-worker (decrypt) hold the key; it is not `DATA_ENCRYPTION_KEY`. A decryption failure is attempt outcome `secret_unavailable` (retried, not counted toward auto-disable, metric and alert).
3. Rotation keeps the retiring secret for an overlap (0–168 h, default 24): the current ciphertext moves unchanged to `previous_secret_ciphertext` (decrypted with its old version in the AAD) and every attempt during the overlap carries two signatures, current first.

**Decision — signature format.**

4. Header `EG-Signature: t=<unix seconds>,v1=<hex HMAC-SHA256>[,v1=…]`, the HMAC keyed with the UTF-8 bytes of the whole secret string over `` `${t}.${raw body}` ``. Receivers verify before parsing, reject `|now − t| > 300 s`, compare in constant time and accept any `v1` that matches. The exact header set is fixed: `Content-Type`, `User-Agent: EmailGateway-Webhooks/1`, `EG-Signature`, `EG-Event-Id`, `EG-Event-Type`, `EG-Delivery-Id` (new per replay), `EG-Delivery-Attempt`, `EG-Subscription-Id`, `Idempotency-Key` (= event id). `verifyWebhookSignature` in `@email-gateway/webhooks` and a `node:crypto` snippet in the API guide implement the receiver side.

**Decision — delivery guarantees.**

5. **At least once, idempotent everywhere.** The fanout writes `webhook_events` and `webhook_deliveries` (`pending`) with insert-ignore on their unique keys in one writer transaction (ledger `webhook-worker.fanout`), then acks. The `delivery` role is a database-driven loop: it claims due rows (`FOR UPDATE SKIP LOCKED`, forced index `(status, organization_id, next_attempt_at)`), sets a lease (`attempt_count + 1`, `next_attempt_at = now + total timeout + 60 s`), sends outside any transaction and records the attempt with a compare-and-set on `(id, status = pending, attempt_count)`. A crash leaves the lease to expire and the attempt counts. Receivers dedupe on `EG-Event-Id`.
6. **Retries.** Every non-2xx, redirect, timeout, DNS, connection, TLS, size and `secret_unavailable` outcome is retried; `blocked` (SSRF) fails immediately and counts toward auto-disable. Delay after attempt n = `min(max delay, base × 2^(n−1))` × jitter [0.8, 1.2] (defaults 30 s base, 6 h max, 8 attempts). A `Retry-After` (seconds or HTTP date) on any non-2xx is honoured: `max(computed, Retry-After)`, clamped at `WEBHOOK_RETRY_AFTER_MAX_SECONDS` (1 h), never ignored.
7. **Dead letters.** After `WEBHOOK_MAX_ATTEMPTS` or `WEBHOOK_MAX_RETRY_AGE_HOURS` (24 h) a delivery is `dead`: listed, replayable (single delivery or time range, same stored envelope and event id, new delivery id), purged with its monthly partition (retention two months). Poison source events of the fanout go to `email.dead-letter` through the queue policy (operator replay unchanged).
8. **Backlog bound.** A subscription with more than `WEBHOOK_MAX_PENDING_PER_SUBSCRIPTION` (50 000) pending deliveries gets new deliveries inserted directly as `dead` (`backlog_exceeded`), so one dead endpoint cannot grow the table without bound.
9. **Auto-disable.** Each failed attempt increments `consecutive_failures` and sets `failing_since` once; at ≥ `WEBHOOK_DISABLE_AFTER_FAILURES` (50) failures **and** ≥ `WEBHOOK_DISABLE_AFTER_HOURS` (24 h) of failing, the same transaction sets `disabled` (`sustained_failure`), writes a system audit row `webhook.auto_disabled` and a `notification.alert_requested.v1` (`webhook_disabled`, ADR-0056). Pending deliveries become `cancelled`; re-enabling is an explicit, audited `PATCH status=active`.

**Decision — outbound HTTP and fairness.**

10. **SSRF-guarded client** (`GuardedPoster`, `@email-gateway/url-security`): the URL passes the guard's scheme, port (`WEBHOOK_ALLOWED_PORTS`, 443 in production) and name checks; every resolved A/AAAA answer must pass the address checks (one blocked answer blocks the attempt: rebinding safe); the socket dials the checked IP literal with TLS SNI and certificate verification against the host name (TLS ≥ 1.2); the connected remote address is re-checked; one POST, **no redirects** (3xx is a failed attempt, `Location` never followed or stored), connect and total timeouts (3 s / 10 s), at most 4 KiB of the response read and a 512-character redacted snippet stored, no cookies, no proxy variables. The api checks the URL at registration (no DNS: it can change); the worker's checks at every attempt are authoritative. Test seams (documentation-range allow list, dial map, extra CA, plain http) are refused outside APP_ENV `local`/`ci`.
11. **Fairness.** Per tick the loop shuffles the organizations with due work and claims per organization up to its free slots: Redis counters cap in-flight attempts per organization (16) and per subscription (4, lowered by a subscription's `maxConcurrency`) and attempts per subscription per minute (600), all reserved atomically by one Lua script. A slow endpoint holds at most its own caps; other organizations are claimed in the same tick. Redis unavailable → nothing is sent (fail closed).

**Decision — topology v11.**

12. Queue `email.webhooks` (quorum, role `work`, policy `work`: reject-publish at 1 000 000, dead letters to `email.dead-letter`; retry `hold` 10 attempts, 2 s – 1 min, 24 h) bound to the eight source keys; `email.notifications` additionally bound to `notification.alert_requested.v1`. 21 queues. Broker user `eg-webhook` (configure nothing, read `email.webhooks`, write only its retry and dead-letter hops on `email.events`); `ops` gains the queue's retry key (operator replay). 10 role users.
13. **Reconciliation exclusion.** `email.webhooks` is **not** in `RECONCILE_QUEUES`: the fanout writes ledger rows only for events it acted on, so the reconciler would re-drive every no-op event forever. Transport stays at least once from the confirmed publish (durable quorum queue, ack after commit); broker data loss is the residual risk (three replicas in production).

**Alternatives considered** (step design §7). RabbitMQ delay queues per retry: cannot honour per-endpoint `Retry-After` exactly, needs the delivery row anyway, no per-tenant fairness. One delivery row per attempt: scatters the history and blurs replay. Standard Webhooks headers (`webhook-id`, `webhook-timestamp`, `webhook-signature: v1,<base64>`): viable; the brief asks for "timestamp plus raw body" and one `t=…,v1=…` header carries a rotation overlap; possible later as an additive header. The raw 32 bytes as HMAC key: receivers must base64url-decode correctly. Hashed secrets (like API keys): the worker must sign, so it needs the plaintext. `email.webhooks` as a lossy (drop-head) queue so it can never nack the relay: silently loses webhooks during a worker outage. DNS resolution at registration: advisory only and adds a resolver to the api.

**Consequences.** **Reject-publish risk:** a webhook-worker outage queues ~10 events per message; at the 1 000 000 bound the broker nacks the relay's publish, and a nack stalls every queue of that publish (the relay retries). At 1 M messages per day the bound is about 2.4 h of total platform traffic; alert `WebhookFanoutBacklog` (warning > 100 000, critical > 500 000 ready, 10 min) and the runbook (scale the fanout, or temporarily unbind with the documented `rabbitmqctl` procedure) give hours of headroom. ~10 quorum-queue writes per message are added; production throughput is reasoned, not measured. Production egress: the delivery Deployment is the only workload allowed to reach the Internet on 443 for webhooks (NetworkPolicy in the deployment note, not applied locally); no egress proxy in 6.2. A Redis Cluster would need hash tags for the reservation script (not built). The independent review of the SSRF client and the key custody is a 14.1 item.
