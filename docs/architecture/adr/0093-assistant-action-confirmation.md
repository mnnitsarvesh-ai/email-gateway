# ADR-0093: AI assistant action confirmation: server-issued, single-use tokens bound to the exact request

**Status:** Proposed (2026-11-20, step AI-1 fixed the contract); amended and built in step AI-2 (2026-11-21); amended in step AI-3 (2026-11-21); amended in step AI-R (2026-11-23); amended in step AI-4 (2026-11-24) (product owner accepted the design default Q6 on 2026-11-20; see [Amendment AI-2](#amendment-ai-2-2026-11-21), [Amendment AI-3](#amendment-ai-3-2026-11-21), [Amendment AI-R](#amendment-ai-r-2026-11-23) and [Amendment AI-4](#amendment-ai-4-2026-11-24)). Design: [docs/plan/steps/28-ai-chat-management.md](../../plan/steps/28-ai-chat-management.md) §4.4, §4.5, D10, §6 (AI-2); [docs/plan/steps/29-ai-chat-confirmations-mail-writes.md](../../plan/steps/29-ai-chat-confirmations-mail-writes.md) (AI-2 build, §2.1); [docs/plan/steps/30-ai-chat-identity-tenant-admin.md](../../plan/steps/30-ai-chat-identity-tenant-admin.md) (AI-3, §2.1); [docs/plan/steps/32-ai-chat-security-operations.md](../../plan/steps/32-ai-chat-security-operations.md) (AI-4, §2.1). Related: [ADR-0091](0091-assistant-architecture-loopback-tools.md), [ADR-0092](0092-llm-provider-abstraction-and-data-handling.md), [ADR-0052](0052-rate-limiting-and-idempotency.md) (idempotency), [ADR-0047](0047-quarantine-release-revalidation-and-approvals.md) and [ADR-0072](0072-ato-response-safeguards-and-approvals.md) (existing approval workflows, unchanged). Changes no Accepted ADR.

**Context.** From AI-2 the assistant offers write tools (policies, quarantine, users, domains, …). The model is an untrusted client (ADR-0092) that can be manipulated by text inside tool results, so it must never be able to execute, approve or confirm a change on its own. A confirmation must be bound to exactly what the user saw, must not be replayable or transferable, and high-risk changes need the same fresh re-authentication the portal asks for. Existing approval workflows (quarantine release approvals, ATO responses with separation of duties, setup-wizard impact tokens) stay the authority for their actions.

**Decision.** (Contract fixed now; implemented in AI-2.)

1. **A write `call_tool` never executes inside a turn.** The executor resolves the exact request (method, concrete path with validated ids, query, body), fetches the current state through the matching read operation (precondition snapshot, `rowVersion`/ETag where the route supports compare-and-set) and stores an `ai_chat_action_confirmations` row (AI-2 migration): public id, organization, user, the principal's **session family**, conversation, execution, operation id, `request` JSON, `preconditions` JSON, `action_digest` = SHA-256 of the canonical JSON of all of these, `risk`, `requires_reauth`, `token_hash` = SHA-256 of a 32-byte random token, `status` (`pending`, `executing`, `executed`, `failed`, `expired`, `cancelled`), `expires_at` = now + `ASSISTANT_CONFIRMATION_TTL_SECONDS` (default 300), result HTTP status and error code.
2. **The token is never in the model's context.** It goes only to the browser in the stream event `confirmation.required { confirmationId, token, summary, impact, risk, requiresReauth }`; the model receives `{ status: 'pending_confirmation', confirmationId }` and nothing that would let it confirm.
3. **Confirm** with `POST /assistant/confirmations/{id}/confirm { token, reauth? }`: user principals only; the same user **and** the same session family; not expired; constant-time comparison of the token hash; atomic transition `pending → executing` (a second confirm loses); the digest recomputed from the stored request and preconditions must equal `action_digest`; for `requires_reauth` (risk `high`) a fresh `ReauthenticationService.verify` (password + TOTP, lockout accounting) unless the session re-authenticated within `ASSISTANT_REAUTH_WINDOW_SECONDS` (default 300). The stored request is then executed through the loopback (ADR-0091) with `Idempotency-Key = confirmation public id` and the precondition `rowVersion`, so a retried confirm cannot apply twice and a changed record fails with the route's own conflict. `POST /assistant/confirmations/{id}/cancel` cancels.
4. **Risk rules (§4.4).** `low` → confirm; `medium` → confirm with an impact summary; `high` → confirm, impact and fresh re-authentication; `critical` → never through chat (portal only). Existing approval workflows are invoked through their own routes (a request for approval is the write; the approval is another user's action in the portal or chat under its own rules).
5. **One confirmation = one request.** A confirmation can never be reused, transferred to another user or session, edited, or produced by the model; a new request needs a new confirmation. Every confirm, cancel and expiry is audited and linked to the tool execution (ADR-0094).

**Alternatives considered.**

- **Let the model ask "are you sure?" and accept a "yes" message:** the model and anything injected into it could produce the "yes"; no binding to the exact request.
- **Execute immediately and offer undo:** many operations are not reversible (deletions, releases, notifications).
- **Reuse the portal's own forms for every write:** safe but defeats the purpose of chat; kept as the path for `critical` actions.
- **Bind the token to the conversation only:** a stolen or replayed token in another session would work; binding to the session family and the action digest closes that.

**Consequences.**

- AI-2 needs a migration, two routes, a confirmation card in the portal, per-tool impact templates and tests for replay, duplicate, expired, foreign-session and changed-state confirmations plus a digest-binding property test; AI-1 ships none of these and enables no write tool (the registry check enforces it).
- `ASSISTANT_CONFIRMATION_TTL_SECONDS` and `ASSISTANT_REAUTH_WINDOW_SECONDS` are validated by the api configuration from AI-1 so operators can set them before AI-2.
- A confirmed write behaves exactly like the same write from the portal (guards, idempotency, audit), with the confirmation id as its idempotency key and correlation to the execution.

## Amendment AI-2 (2026-11-21)

Step AI-2 ([design](../../plan/steps/29-ai-chat-confirmations-mail-writes.md) §2.1, D1–D3, D7; contracts [§35.1](../contracts.md#351-confirmations-step-ai-2)) builds the decision above unchanged and makes the following precise or adds to it. Nothing here weakens a rule of the decision; each item adds a control or fixes a detail the decision left open.

- **(a) The confirm body carries the card's digest.** `POST /assistant/confirmations/{id}/confirm { token, actionDigest, reauth? }`: `actionDigest` is the digest the confirmation card showed; the server requires it to equal the stored `action_digest` **and** the digest recomputed from the stored columns (`409 assistant_confirmation_digest_mismatch`; a recomputation mismatch, i.e. tampered storage, also fails the row). The digest input is the canonical JSON (keys sorted at every depth) of `assistant-action/1`: confirmation id, organization, user, session family, override, conversation, execution, tool, operation id, risk, `requiresReauth`, the request `{ method, path, body }`, the preconditions and `expiresAt`.
- **(b) State digest and re-read at confirm.** The preconditions include a **state digest** (SHA-256 of the canonical JSON of selected state fields of the target read). Confirm re-reads the target through the same read operation and refuses `409 assistant_confirmation_state_changed` on any difference. The proposal read and this re-read run on the MySQL writer, never on the read replica: the loopback GET carries `x-eg-assistant-read-primary` (HMAC-SHA256 of `AUTH_TOKEN_PEPPER`, a server value; `AssistantReadPrimaryMiddleware` runs the route inside `runReadsOnWriter`, so `PrismaReadService.client` is the writer), so a change committed inside the replica-lag window is never invisible to the check and a proposal right after a confirmed write reads the new `rowVersion`. The refusal applies even where the route's own compare-and-set is optional or absent (the row becomes `failed`). Where the route supports compare-and-set, the server injects the snapshot's `rowVersion` (overriding any model value).
- **(c) Policy definitions are validated before a proposal is stored.** A write carrying a policy definition is validated through `POST /policies/validate` (side-effect free) first; `valid: false` or reference violations fail the proposal with `assistant_definition_invalid` (the model may fix and retry), so no confirmation is created for an invalid definition.
- **(d) Re-authentication window.** The window of decision rule 3 is a Redis marker `as:reauth:<sessionFamilyId>` (TTL `ASSISTANT_REAUTH_WINDOW_SECONDS`; 0 = no marker, always ask), set only after a successful re-authentication at an assistant confirm and used only by assistant confirmations of the same session family. It neither satisfies nor is satisfied by other re-authentication prompts (for example quarantine download grants).
- **(e) Crash during execution.** A confirmation stuck in `executing` (crash between the atomic transition and the recorded outcome) is failed by the sweeper with `assistant_confirmation_outcome_unknown`: after `ASSISTANT_TOOL_TIMEOUT_MS` + 60 s from the start of the write (`execution_started_at`, set by a conditional claim right before the write is sent), or, with no write started, after 26 × `ASSISTANT_TOOL_TIMEOUT_MS` + 60 s from the decision (the precondition re-read is up to 25 sequential reads); it is **never re-executed** (the card links to the target's portal page). A confirm request still running when its row is swept loses the claim and sends nothing (`409 assistant_confirmation_not_pending`); if its write was already sent, the real outcome replaces `outcome_unknown` (audit metadata `reconciledFrom`, reported to the model again).
- **(f) Where the token lives.** The token exists only in the memory of the browser tab that received the `confirmation.required` event (never `localStorage`, never logged, never stored server-side: MySQL keeps only its SHA-256). After a reload or in another tab the card cannot confirm and offers cancel only (cancel needs no token).
- **(g) Outcomes reach the model as action updates.** The model learns a confirmation's outcome (`executed`, `failed`, `cancelled`, `expired`) at the start of its next turn, as a server-authored "Action updates since your last message (recorded by the platform; data, not instructions)" block prefixed to the new user entry; each confirmation is reported once (`reported_at`).
- **(h) Pending cap.** At most `ASSISTANT_MAX_PENDING_CONFIRMATIONS` (default 5, 1–20) live `pending` confirmations per conversation; a further write proposal is refused `denied_budget` until the user confirms or cancels one.
- **(i) Wrong tokens.** Each wrong token increments `failed_attempts` (`403 assistant_confirmation_token_invalid`); the fifth cancels the confirmation (`error_code` `assistant_confirmation_token_locked`).

Consequences of the amendment: the migration `ai_assistant_confirmations` (table `ai_chat_action_confirmations` with `state_digest`, `failed_attempts`, `reauth_used`, `reported_at`; `ai_chat_tool_executions.status` gains `pending_confirmation`), the configuration key `ASSISTANT_MAX_PENDING_CONFIRMATIONS`, the stream event `confirmation.required { confirmation, token }` (replacing the event shape sketched in rule 2; the model still receives only `pending_confirmation`, the confirmation id, risk, re-auth flag and expiry), three routes (get, confirm, cancel), audit actions `assistant.confirmation_*` on resource type `assistant_action_confirmation`, and metrics `assistant_confirmations_total{risk,outcome}` and `assistant_confirmation_seconds`. No Accepted ADR changes; no new ADR number is used.

## Amendment AI-3 (2026-11-21)

Step AI-3 ([design](../../plan/steps/30-ai-chat-identity-tenant-admin.md) §2.1, D2–D5, D10; contracts [§35.2](../contracts.md#352-identity-and-tenant-administration-tools-step-ai-3)) enables identity and tenant administration writes as chat tools (invariants I12 no self-service of authority through chat, I13 the api's no-escalation rules stay the authority, I14 credentials never pass through chat). The decision and the AI-2 amendment stay unchanged; the following items only add refusals or raise risk, none lowers a control.

- **(j) Proposal guards.** A confirmation spec may name server-side guards, pure functions of the final arguments, the principal and the precondition target: `not_self_user` (the argument, a user id, must not be the caller; case-insensitive UUID compare), `deny_values` (the argument must not take one of the listed values, for example `featureKey = ai_assistant`: the assistant cannot turn itself on or off) and `deny_permission_change` (no listed permission, for example `assistant:configure`, may be added or removed; the old set comes from the precondition read). Guards that need no read are evaluated at proposal **before** any loopback request (not even the precondition read is sent); guards that need the target are evaluated **after** the precondition read; both are evaluated **again at confirm** with the stored arguments, the confirming principal and the fresh re-read. A proposal refusal is the executor decision `denied_guard` (execution row `refused`, audit `assistant.tool_denied` with metadata `guard`, stream `tool.denied`, model envelope `{ status: 'denied', decision: 'denied_guard', message }`); messages are fixed server-authored English and never contain argument values. A confirm-time refusal fails the row and answers `403 assistant_action_not_allowed` (audit `assistant.confirmation_refused`, `reason: 'guard'`).
- **(k) Conditional risk escalation.** A spec may name escalations (`present` or `equals` conditions on argument paths, each with a target risk `medium`/`high` and a fixed warning). The **effective risk** is the maximum of the registry risk and every matching escalation; it is what the confirmation stores (`risk`, `requires_reauth = risk === 'high'`) and what the digest binds; the warnings are appended to the card's warnings. Confirm recomputes the effective risk from the stored arguments and refuses a difference (`409 assistant_confirmation_tool_changed`, row failed). The audit metadata of `assistant.confirmation_requested` adds `baseRisk` (the registry risk). An escalation never lowers the risk.
- **(l) Selected-item preconditions.** A single precondition may select its target from a list response (`select: { array, field, arg, required }`): the item whose `field` equals the write argument `arg`. State fields, the row version and the display fields are read from that item; the state digest and the confirm-time re-read compare the item. A missing item fails the proposal like a `404` read when `required`, or is an empty snapshot (digest of `{}`) that must still be absent at confirm otherwise.
- **(m) Identity changes and credentials.** Every role and permission change (inviting with roles, replacing a user's roles, creating, updating or deleting a role) is `high` and needs fresh password + TOTP re-authentication (or the AI-2 re-authentication window). Every operation that creates, displays, rotates or accepts a credential (password, API key, SMTP secret, webhook signing secret, invitation or reset token) stays `not_applicable` and no enabled write's input schema has a credential field (registry check).

Consequences of the amendment: the migration `ai_assistant_guard_decision` (`ai_chat_tool_executions.decision` gains `denied_guard`), the error code `assistant_action_not_allowed` on the confirm route, the metric labels `refused_guard` (confirmations) and `denied_guard` (tool calls), and one new read `GET /api-keys/{id}` (the revocation card names the key). No Accepted ADR changes; no new ADR number is used (next free stays 0095).

## Amendment AI-R (2026-11-23)

Step AI-R ([design](../../plan/steps/31-ai-chat-reports.md) §2.0 I17, D5; [ADR-0095](0095-assistant-reports-native-tools-static-html-email.md); contracts [§35.3](../contracts.md#353-reports-step-ai-r)) confirms the first **native write** (`report_send_email`, [ADR-0091](0091-assistant-architecture-loopback-tools.md) Amendment AI-R). The token, digest, session-family, expiry, atomic-transition and re-authentication rules stay unchanged; the following items only replace the loopback parts for a native spec.

- **(n) State digest from the native state reader.** Instead of a precondition read through the loopback, the proposal calls `NativeToolsService.prepareProposal`: it resolves the report (owner and conversation, `available`, within the size cap) and classifies the recipient by the server rule (own address, active verified user of the organization, address of a verified/active domain of the organization; anything else is refused `denied_guard` and stores no confirmation). The stored request is `POST native:report_send_email` with the normalized address; the preconditions are `{ stateDigest, rowVersion: null }` with `stateDigest = sha256(canonicalJson({ reportId, sha256, status: 'available', recipientKind }))`; the generic proposer then builds digest, token and summary as in AI-2. At confirm, step 12 recomputes the state with `NativeToolsService.readState` on current data: a different digest (report purged or replaced, recipient of another class) fails the row with `409 assistant_confirmation_state_changed`; a recipient that is now refused fails it with **`403 assistant_action_not_allowed`**.
- **(o) In-process execution inside the persist transaction.** Step 13 for a native write runs `NativeToolsService.execute` instead of the loopback, inside the execution's persist transaction: a row lock on the organization's `ai_chat_settings` row serializes the tenant's sends, the per-user and per-tenant daily limits are recounted (limit reached → outcome `failed`, `429 assistant_report_email_limit`, nothing written), and the delivery row, the outbox event `assistant.report.email_requested.v1` and the audit row are written together (outcome `202`).
- **(p) No `Idempotency-Key`.** There is no loopback request to carry it. A confirmation executes at most once by the existing `pending → executing` state machine, and produces at most one delivery because `ai_chat_report_deliveries.confirmation_id` is unique.

## Amendment AI-4 (2026-11-24)

Step AI-4 ([design](../../plan/steps/32-ai-chat-security-operations.md) §2.0 I18–I21, §2.1, D2–D5, D9; contracts [§35.4](../contracts.md#354-security-operations-tools-step-ai-4)) enables the security-operations writes as chat tools (DLP, BEC, risk scoring, incidents, ATO triage, responses and settings, identity-provider integrations, platform operations). The decision and the AI-2, AI-3 and AI-R amendments stay unchanged; the following items only add refusals, raise risk or keep inputs out of stored rows, none lowers a control.

- **(q) Guard kinds `not_self_field` and `require_read_value`.** Two after-read guards on the precondition target (a spec using them needs a `single` precondition): `not_self_field { field, when? }` refuses when the read's `field` (a user public id) is the caller (case-insensitive UUID compare), optionally only when the read's `when.field` equals `when.equals`; a missing field passes (the second guard and the api decide). `require_read_value { field, equals, when? }` refuses unless the read's `field` equals `equals`, optionally only when `when` holds; a missing or different value refuses (fail closed). They read no argument. Handling is the AI-3 one: `denied_guard` at proposal (no confirmation row), evaluated again at confirm with the confirming principal and the fresh re-read, `403 assistant_action_not_allowed` there; audit metadata `guard` is the kind.
- **(r) The ATO four-eyes guard.** `ato_responses_approve` and `ato_responses_reject` carry both guards on `ato_responses_get {responseId}` (message key `ato_four_eyes`, fixed English without values): `not_self_field { field: 'requestedBy.id', when: { field: 'requestedBy.type', equals: 'user' } }` and `require_read_value { field: 'canDecide', equals: true, when: { field: 'status', equals: 'pending_approval' } }` (I18: the requester, or the creator of the requesting API key, can never decide a response through chat, and deciding needs an MFA session). The api's `403 ato_self_approval` stays the authority; chat creates no second approval path. A response that is not `pending_approval` passes both guards and the api answers `409`. Cancel and rollback get no guard (the api has no separation-of-duties rule for them).
- **(s) CAS field names.** `CasInjection.field` may also be `version`, `rowVersion` and `expectedProfileVersion` (besides `expectedRowVersion` and `expectedVersion`), in the body or the query as the write's schema has it; consistency checks that the field exists in the write's schema.
- **(t) Weakening detection is high (I20).** Every confirmed change that adds trust or an exception, suppresses findings, sets a benign verdict, protects an account from automated response, disables a detector or a policy, switches it to monitor-only, adds an `allow` rule, changes ATO settings, or changes which response actions the gateway may take in a tenant's identity provider is `high` (password + TOTP re-authentication), by its base risk (trusted-context add, trusted-sender create, DLP exception create, ATO settings update, IdP integration update) or by the escalation table of the design's D4 / contracts §35.4 (for example `ato_accounts_update` with `protected = true`, `ato_accounts_set_override` with `verdict = benign`, `ato_providers_create` with `settings`, `incidents_update` with `false_positive` or `categoryFeedback`, `bec_message_feedback_record` with `suppress`, BEC and DLP updates that disable, widen or extend, DLP rules with `action = allow`).
- **(u) Redacted read inputs.** A side-effect-free read whose inputs the api promises never to log or audit may name `redactParams` (argument paths; reads only, every path in the input schema): each value is replaced by `[redacted]` before the credential scrub in `ai_chat_tool_executions.params_redacted`, the `assistant.tool_executed` / `tool_denied` audit params and logs (`exact` false), while the loopback request still carries it. AI-4 sets `DlpPatternsController_test_v1: ['body.sample', 'body.pattern']`. The values remain in the conversation transcript, which is conversation content purged by retention. Writes never have `redactParams` (their stored request must stay exact for the digest).

Consequences of the amendment: no migration, table or enum value (`denied_guard` exists since AI-3); four new single-item reads (`GET /bec/trusted-senders/{id}`, `GET /bec/suppressions/{id}`, `GET /dlp/exceptions/{id}`, `GET /platform/threat-indicators/{id}`) give the confirmation cards their precondition reads. No Accepted ADR changes; no new ADR number is used (next free stays 0096).
