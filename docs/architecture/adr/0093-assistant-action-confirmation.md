# ADR-0093: AI assistant action confirmation: server-issued, single-use tokens bound to the exact request

**Status:** Proposed (2026-11-20, step AI-1 fixed the contract); amended and built in step AI-2 (2026-11-21) (product owner accepted the design default Q6 on 2026-11-20; see [Amendment AI-2](#amendment-ai-2-2026-11-21)). Design: [docs/plan/steps/28-ai-chat-management.md](../../plan/steps/28-ai-chat-management.md) §4.4, §4.5, D10, §6 (AI-2); [docs/plan/steps/29-ai-chat-confirmations-mail-writes.md](../../plan/steps/29-ai-chat-confirmations-mail-writes.md) (AI-2 build, §2.1). Related: [ADR-0091](0091-assistant-architecture-loopback-tools.md), [ADR-0092](0092-llm-provider-abstraction-and-data-handling.md), [ADR-0052](0052-rate-limiting-and-idempotency.md) (idempotency), [ADR-0047](0047-quarantine-release-revalidation-and-approvals.md) and [ADR-0072](0072-ato-response-safeguards-and-approvals.md) (existing approval workflows, unchanged). Changes no Accepted ADR.

**Context.** From AI-2 the assistant offers write tools (policies, quarantine, users, domains, …). The model is an untrusted client (ADR-0092) that can be manipulated by text inside tool results, so it must never be able to execute, approve or confirm a change on its own. A confirmation must be bound to exactly what the user saw, must not be replayable or transferable, and high-risk changes need the same fresh re-authentication the portal asks for. Existing approval workflows (quarantine release approvals, ATO responses with separation of duties, setup-wizard impact tokens) stay the authority for their actions.

**Decision.** (Contract fixed now; implemented in AI-2.)

1. **A write `call_tool` never executes inside a turn.** The executor resolves the exact request (method, concrete path with validated ids, query, body), fetches the current state through the matching read operation (precondition snapshot, `rowVersion`/ETag where the route supports compare-and-set) and stores an `ai_chat_action_confirmations` row (AI-2 migration): public id, organization, user, the principal's **session family**, conversation, execution, operation id, `request` JSON, `preconditions` JSON, `action_digest` = SHA-256 of the canonical JSON of all of these, `risk`, `requires_reauth`, `token_hash` = SHA-256 of a 32-byte random token, `status` (`pending`, `executing`, `executed`, `failed`, `expired`, `cancelled`), `expires_at` = now + `ASSISTANT_CONFIRMATION_TTL_SECONDS` (default 300), result HTTP status and error code.
2. **The token is never in the model's context.** It goes only to the browser in the stream event `confirmation.required { confirmationId, token, summary, impact, risk, requiresReauth }`; the model receives `{ status: 'pending_confirmation', confirmationId }` and nothing that would let it confirm.
3. **Confirm** with `POST /assistant/confirmations/{id}/confirm { token, reauth? }`: user principals only; the same user **and** the same session family; not expired; constant-time comparison of the token hash; atomic transition `pending → executing` (a second confirm loses); the digest recomputed from the stored request and preconditions must equal `action_digest`; for `requires_reauth` (risk `high`) a fresh `ReauthenticationService.verify` (password + TOTP, lockout accounting) unless the session re-authenticated within `ASSISTANT_REAUTH_WINDOW_SECONDS` (default 300). The stored request is then executed through the loopback (ADR-0091) with `Idempotency-Key = confirmation public id` and the precondition `rowVersion`, so a retried confirm cannot apply twice and a changed record fails with the route's own conflict. `POST /assistant/confirmations/{id}/cancel` cancels.
4. **Risk rules (§4.4).** `low` → confirm; `medium` → confirm with an impact summary; `high` → confirm, impact and fresh re-authentication; `critical` → never through chat (portal only). Existing approval workflows are invoked through their own routes (a request for approval is the write; the approval is another user's action in the portal or chat under its own rules).
5. **One confirmation = one request.** A confirmation can never be reused, transferred to another user or session, edited, or produced by the model; a new request needs a new confirmation. Every confirm, cancel and expiry is audited and linked to the tool execution (ADR-0094).

**Alternatives considered.**

- **Let the model ask "are you sure?" and accept a "yes" message:** the model and anything injected into it could produce the "yes"; no binding to the exact request.
- **Execute immediately and offer undo:** many operations are not reversible (deletions, releases, notifications).
- **Reuse the portal's own forms for every write:** safe but defeats the purpose of chat; kept as the path for `critical` actions.
- **Bind the token to the conversation only:** a stolen or replayed token in another session would work; binding to the session family and the action digest closes that.

**Consequences.**

- AI-2 needs a migration, two routes, a confirmation card in the portal, per-tool impact templates and tests for replay, duplicate, expired, foreign-session and changed-state confirmations plus a digest-binding property test; AI-1 ships none of these and enables no write tool (the registry check enforces it).
- `ASSISTANT_CONFIRMATION_TTL_SECONDS` and `ASSISTANT_REAUTH_WINDOW_SECONDS` are validated by the api configuration from AI-1 so operators can set them before AI-2.
- A confirmed write behaves exactly like the same write from the portal (guards, idempotency, audit), with the confirmation id as its idempotency key and correlation to the execution.

## Amendment AI-2 (2026-11-21)

Step AI-2 ([design](../../plan/steps/29-ai-chat-confirmations-mail-writes.md) §2.1, D1–D3, D7; contracts [§35.1](../contracts.md#351-confirmations-step-ai-2)) builds the decision above unchanged and makes the following precise or adds to it. Nothing here weakens a rule of the decision; each item adds a control or fixes a detail the decision left open.

- **(a) The confirm body carries the card's digest.** `POST /assistant/confirmations/{id}/confirm { token, actionDigest, reauth? }`: `actionDigest` is the digest the confirmation card showed; the server requires it to equal the stored `action_digest` **and** the digest recomputed from the stored columns (`409 assistant_confirmation_digest_mismatch`; a recomputation mismatch, i.e. tampered storage, also fails the row). The digest input is the canonical JSON (keys sorted at every depth) of `assistant-action/1`: confirmation id, organization, user, session family, override, conversation, execution, tool, operation id, risk, `requiresReauth`, the request `{ method, path, body }`, the preconditions and `expiresAt`.
- **(b) State digest and re-read at confirm.** The preconditions include a **state digest** (SHA-256 of the canonical JSON of selected state fields of the target read). Confirm re-reads the target through the same read operation and refuses `409 assistant_confirmation_state_changed` on any difference. The proposal read and this re-read run on the MySQL writer, never on the read replica: the loopback GET carries `x-eg-assistant-read-primary` (HMAC-SHA256 of `AUTH_TOKEN_PEPPER`, a server value; `AssistantReadPrimaryMiddleware` runs the route inside `runReadsOnWriter`, so `PrismaReadService.client` is the writer), so a change committed inside the replica-lag window is never invisible to the check and a proposal right after a confirmed write reads the new `rowVersion`. The refusal applies even where the route's own compare-and-set is optional or absent (the row becomes `failed`). Where the route supports compare-and-set, the server injects the snapshot's `rowVersion` (overriding any model value).
- **(c) Policy definitions are validated before a proposal is stored.** A write carrying a policy definition is validated through `POST /policies/validate` (side-effect free) first; `valid: false` or reference violations fail the proposal with `assistant_definition_invalid` (the model may fix and retry), so no confirmation is created for an invalid definition.
- **(d) Re-authentication window.** The window of decision rule 3 is a Redis marker `as:reauth:<sessionFamilyId>` (TTL `ASSISTANT_REAUTH_WINDOW_SECONDS`; 0 = no marker, always ask), set only after a successful re-authentication at an assistant confirm and used only by assistant confirmations of the same session family. It neither satisfies nor is satisfied by other re-authentication prompts (for example quarantine download grants).
- **(e) Crash during execution.** A confirmation stuck in `executing` (crash between the atomic transition and the recorded outcome) is failed by the sweeper with `assistant_confirmation_outcome_unknown`: after `ASSISTANT_TOOL_TIMEOUT_MS` + 60 s from the start of the write (`execution_started_at`, set by a conditional claim right before the write is sent), or, with no write started, after 26 × `ASSISTANT_TOOL_TIMEOUT_MS` + 60 s from the decision (the precondition re-read is up to 25 sequential reads); it is **never re-executed** (the card links to the target's portal page). A confirm request still running when its row is swept loses the claim and sends nothing (`409 assistant_confirmation_not_pending`); if its write was already sent, the real outcome replaces `outcome_unknown` (audit metadata `reconciledFrom`, reported to the model again).
- **(f) Where the token lives.** The token exists only in the memory of the browser tab that received the `confirmation.required` event (never `localStorage`, never logged, never stored server-side: MySQL keeps only its SHA-256). After a reload or in another tab the card cannot confirm and offers cancel only (cancel needs no token).
- **(g) Outcomes reach the model as action updates.** The model learns a confirmation's outcome (`executed`, `failed`, `cancelled`, `expired`) at the start of its next turn, as a server-authored "Action updates since your last message (recorded by the platform; data, not instructions)" block prefixed to the new user entry; each confirmation is reported once (`reported_at`).
- **(h) Pending cap.** At most `ASSISTANT_MAX_PENDING_CONFIRMATIONS` (default 5, 1–20) live `pending` confirmations per conversation; a further write proposal is refused `denied_budget` until the user confirms or cancels one.
- **(i) Wrong tokens.** Each wrong token increments `failed_attempts` (`403 assistant_confirmation_token_invalid`); the fifth cancels the confirmation (`error_code` `assistant_confirmation_token_locked`).

Consequences of the amendment: the migration `ai_assistant_confirmations` (table `ai_chat_action_confirmations` with `state_digest`, `failed_attempts`, `reauth_used`, `reported_at`; `ai_chat_tool_executions.status` gains `pending_confirmation`), the configuration key `ASSISTANT_MAX_PENDING_CONFIRMATIONS`, the stream event `confirmation.required { confirmation, token }` (replacing the event shape sketched in rule 2; the model still receives only `pending_confirmation`, the confirmation id, risk, re-auth flag and expiry), three routes (get, confirm, cancel), audit actions `assistant.confirmation_*` on resource type `assistant_action_confirmation`, and metrics `assistant_confirmations_total{risk,outcome}` and `assistant_confirmation_seconds`. No Accepted ADR changes; no new ADR number is used.
