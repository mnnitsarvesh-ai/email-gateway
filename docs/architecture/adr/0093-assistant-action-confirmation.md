# ADR-0093: AI assistant action confirmation: server-issued, single-use tokens bound to the exact request

**Status:** Proposed (2026-11-20, step AI-1 fixes the contract; **built in step AI-2**; product owner accepted the design default Q6 on 2026-11-20). Design: [docs/plan/steps/28-ai-chat-management.md](../../plan/steps/28-ai-chat-management.md) §4.4, §4.5, D10, §6 (AI-2). Related: [ADR-0091](0091-assistant-architecture-loopback-tools.md), [ADR-0092](0092-llm-provider-abstraction-and-data-handling.md), [ADR-0052](0052-rate-limiting-and-idempotency.md) (idempotency), [ADR-0047](0047-quarantine-release-revalidation-and-approvals.md) and [ADR-0072](0072-ato-response-safeguards-and-approvals.md) (existing approval workflows, unchanged). Changes no Accepted ADR.

**Context.** From AI-2 the assistant offers write tools (policies, quarantine, users, domains, …). The model is an untrusted client (ADR-0092) that can be manipulated by text inside tool results, so it must never be able to execute, approve or confirm a change on its own. A confirmation must be bound to exactly what the user saw, must not be replayable or transferable, and high-risk changes need the same fresh re-authentication the portal asks for. Existing approval workflows (quarantine release approvals, ATO responses with separation of duties, setup-wizard impact tokens) stay the authority for their actions.

**Decision.** (Contract fixed now; implemented in AI-2.)

1. **A write `call_tool` never executes inside a turn.** The executor resolves the exact request (method, concrete path with validated ids, query, body), fetches the current state through the matching read operation (precondition snapshot, `rowVersion`/ETag where the route supports compare-and-set) and stores an `ai_chat_action_confirmations` row (AI-2 migration): public id, organization, user, the principal's **session family**, conversation, execution, operation id, `request` JSON, `preconditions` JSON, `action_digest` = SHA-256 of the canonical JSON of all of these, `risk`, `requires_reauth`, `token_hash` = SHA-256 of a 32-byte random token, `status` (`pending`, `executing`, `executed`, `failed`, `expired`, `cancelled`), `expires_at` = now + `ASSISTANT_CONFIRMATION_TTL_SECONDS` (default 300), result HTTP status and error code.
2. **The token is never in the model's context.** It goes only to the browser in the stream event `confirmation.required { confirmationId, token, summary, impact, risk, requiresReauth }`; the model receives `{ status: 'pending_confirmation', confirmationId }` and nothing that would let it confirm.
3. **Confirm** with `POST /assistant/confirmations/{id}/confirm { token, reauth? }`: user principals only; the same user **and** the same session family; not expired; constant-time comparison of the token hash; atomic transition `pending → executing` (a second confirm loses); the digest recomputed from the stored request and preconditions must equal `action_digest`; for `requires_reauth` (risk `high`) a fresh `ReauthenticationService.verify` (password + TOTP, lockout accounting) unless the session re-authenticated within `ASSISTANT_REAUTH_WINDOW_SECONDS` (default 300). The stored request is then executed through the loopback (ADR-0091) with `Idempotency-Key = confirmation public id` and the precondition `rowVersion`, so a retried confirm cannot apply twice and a changed record fails with the route's own conflict. `POST /assistant/confirmations/{id}/cancel` cancels.
4. **Risk rules (§4.4).** `low` → confirm; `medium` → confirm with an impact summary; `high` → confirm, impact and fresh re-authentication; `critical` → never through chat (portal only). Existing approval workflows are invoked through their own routes (a request for approval is the write; the approval is another user's action in the portal or chat under its own rules).
5. **One confirmation = one request.** A confirmation can never be reused, transferred to another user or session, edited, or produced by the model; a new request needs a new confirmation. Every confirm, cancel and expiry is audited and linked to the tool execution (ADR-0094).

**Alternatives considered.**

- **Let the model ask "are you sure?" and accept a "yes" message:** the model and anything injected into it could produce the "yes"; no binding to the exact request.
- **Execute immediately and offer undo:** many operations are not reversible (deletions, releases, notifications).
- **Reuse the portal's own forms for every write:** safe but defeats the purpose of chat; kept as the path for `critical` actions.
- **Bind the token to the conversation only:** a stolen or replayed token in another session would work; binding to the session family and the action digest closes that.

**Consequences.**

- AI-2 needs a migration, two routes, a confirmation card in the portal, per-tool impact templates and tests for replay, duplicate, expired, foreign-session and changed-state confirmations plus a digest-binding property test; AI-1 ships none of these and enables no write tool (the registry check enforces it).
- `ASSISTANT_CONFIRMATION_TTL_SECONDS` and `ASSISTANT_REAUTH_WINDOW_SECONDS` are validated by the api configuration from AI-1 so operators can set them before AI-2.
- A confirmed write behaves exactly like the same write from the portal (guards, idempotency, audit), with the confirmation id as its idempotency key and correlation to the execution.
