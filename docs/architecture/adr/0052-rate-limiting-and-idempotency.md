# ADR-0052: API rate limiting (principal, tenant, classes) and idempotency of sensitive mutations

**Status:** Accepted (implemented in step 6.1; verification record in [§13 of the step design](../../plan/steps/18-rest-api.md#13-verification-record); not verified: CI, a Kubernetes cluster). Design: [step 6.1](../../plan/steps/18-rest-api.md) D8–D10, §3.5, §3.7. Builds on [ADR-0016](0016-authentication-sessions-rbac.md) (per-IP limits of the authentication routes, fail closed); supersedes nothing.

**Context.** Before 6.1 only selected routes had fixed-window limits (`@RateLimit`, quarantine limits); `organization_limits.api_requests_per_minute` (plan values 60/300/1200/3000) was stored but not enforced, and responses carried no rate-limit headers. `Idempotency-Key` existed only where the service ran its effect inside the key's transaction (`IdempotencyService`: messages rescan/release, 11 quarantine mutations); the other mutations that send mail, change who can sign in, purge data or change decisions accepted no key, so a client retry after a timeout could repeat them.

**Decision — rate limiting.**

1. A global `ApiRateLimitGuard` (between `AuthGuard` and `PermissionsGuard`, so denied requests count) applies to every authenticated route, with fixed 60 s windows in Redis (`incrWithTtl`): **per principal** (user or API key; override sessions count as the user) `API_RATE_PRINCIPAL_PER_MINUTE`; **per tenant** (the scope's organization, the target under an override) `organization_limits.api_requests_per_minute` clamped to `[API_RATE_TENANT_MIN_PER_MINUTE, API_RATE_TENANT_MAX_PER_MINUTE]`, `API_RATE_TENANT_DEFAULT_PER_MINUTE` without a row or when the lookup fails (never unlimited), read from the replica through a bounded in-process cache (`API_RATE_LIMIT_CACHE_SECONDS`); **class buckets** per principal for `@RateClass('sensitive')` (`API_RATE_SENSITIVE_PER_MINUTE`) and `@RateClass('expensive')` (`API_RATE_EXPENSIVE_PER_MINUTE`). Tenants cannot change their own limit: only the platform catalog overrides `api_requests_per_minute` (`PUT /organizations/{id}/limits/api_requests_per_minute`), and the clamp bounds the override.
2. Route `@RateLimit`s and the quarantine limits stay and apply in addition; public routes keep their per-IP limits (`GET /meta` got one, 120/min).
3. Every authenticated response carries `RateLimit-Limit`, `RateLimit-Remaining`, `RateLimit-Reset` of the most restrictive counter; `429 rate_limited` carries `scope` (`principal | tenant | sensitive | expensive | route`) and `Retry-After`.
4. **Fail closed:** a Redis failure is `503 service_unavailable` (`api_rate_limit_store_errors_total`, alert `ApiRateLimitStoreErrors`), like the authentication deny-lists.

**Decision — idempotency.**

5. **Two mechanisms, one key space** (`api_idempotency_keys`, unique per organization, bound to principal + operation + resource + body fingerprint, 24 h): (a) **transactional** (`IdempotencyService.execute`, effect + audit + stored response in one writer transaction; exactly once) — mandatory for new mutations and kept for messages and quarantine; (b) the **reservation interceptor** `@Idempotent({ operation })` for legacy services that own their transactions (at most once per key): a `pending` row (new column `state`, `API_IDEMPOTENCY_PENDING_TTL_SECONDS`) reserves the key, a live completed match replays (`Idempotency-Replayed: true`), a mismatch is `422 idempotency_key_reused`, a live pending match is `409 idempotency_request_in_progress` + `Retry-After`, a 2xx is stored, an error releases the reservation. A crash between the handler and the store leaves the key blocked until the reservation expires; a retry after that may run the effect again (documented at-most-once window). Both mechanisms retry a lost race once: the unique key (P2002) and, when the writer runs REPEATABLE READ instead of the configured READ-COMMITTED (ADR-0004), the InnoDB deadlock of two gap locks on the same absent key (P2034); the retry sees the winner's row, so the loser answers `409`, a replay or `422`, never `500`.
6. **The list** (§3.5, the authority for both the key and the `sensitive` class): 13 transactional routes since 3.3/5.3 (message rescan and release, 11 quarantine mutations), 2 new transactional routes (`POST` / `DELETE /recipients/suppressions`), and 22 legacy routes behind the interceptor (DKIM rotation, organization status/deletion request/confirm, user invite/resend/MFA reset, policy and risk-profile publish/activate/reset, BEC history purge, DLP evidence purges and Aadhaar enable/disable, platform dead-letter replay, attachment rescans, scan training, threat hash and indicator creation). Every one is declared in code (`@Idempotent` or the transactional marker) and in OpenAPI (`x-eg-idempotency: required | legacy`).
7. **Missing key:** `400 idempotency_key_required`. For the 22 legacy routes `API_IDEMPOTENCY_LEGACY_MODE=warn` (deprecation switch; default `enforce`) processes a keyless request as before and answers `Deprecation: true` with a `Link rel="deprecation"` (`api_idempotency_total{outcome="missing_legacy"}`).
8. **Secret-bearing responses are never stored:** `POST /api-keys`, `POST /smtp-connectors`, `POST /smtp-connectors/{id}/rotate-secret`, `POST /platform/overrides`, `POST /auth/mfa/totp/setup`, `POST /auth/mfa/recovery-codes` and the public authentication routes take no key (protected by uniqueness, single-use tokens and their limits). `@ReturnsSecret()` marks them (sensitive class) and refuses to be combined with `@Idempotent()` at decoration time; the interceptor refuses (500, nothing stored) to store a body with a key matching the audit credential pattern. Five legacy routes whose unchanged DTOs contain such names (`key`, `code`) use a wrapper that exempts exactly those verified field names (step design §12 WP4).

**Alternatives considered.** Sliding windows or token buckets: fixed windows are already used everywhere with consistent headers; the burst at a window edge is accepted. Limiting at the ingress only: no principal or tenant awareness, and the local stack has no ingress. Loading the tenant limit into the principal snapshot: couples the auth cache to limits. Idempotency by caching responses in Redis: not atomic with the effect and lost on a flush. Making every legacy mutation transactional now: reworks each service's transaction boundary; the interceptor gives replay safety today.

**Consequences.** A Redis outage blocks the authenticated API (as it already blocked authentication); the alert and runbook cover it. Two to four Redis round trips per request. Clients of the 22 legacy routes must send `Idempotency-Key` (contract change, API guide changelog; `warn` mode bridges until the portal sends keys). The GA default of the legacy switch and the removal of `warn` are follow-ups (14.1).
