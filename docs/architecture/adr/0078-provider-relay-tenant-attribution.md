# ADR-0078: Provider relay: accepting Microsoft 365 and Google Workspace outbound and internal mail from shared provider infrastructure

**Status:** Accepted (2026-11-19, after the step 8.2 local verification against the provider simulators: the stack suite `provider-integrations` 10/10, the worker, library, api and smtp-adapter integration suites, the regression stack suites, Playwright 112/112, the 3-node RabbitMQ cluster suite on topology v14; record [docs/plan/steps/25-m365-google-connectors.md](../../plan/steps/25-m365-google-connectors.md) §13 WP6, §14; live verification against real Microsoft 365 and Google Workspace tenants, CI and a cluster apply not done). Proposed by the step 8.2 architect on 2026-11-17. Design: 25-m365-google-connectors.md D7, D8. **Amends [ADR-0019](0019-smtp-gateway-topology.md)** decision 5 (a third post-queue refusal case, `provider_proof_failed`) and step 2.2 D10 (now enforced: `source_ip` connectors may not cover provider egress ranges).

Amended by [ADR-0087](0087-journal-intake-path.md) (step 8.6): its provider proof evaluation (tenant header against the bound connection, DKIM evidence) and the egress-range rule are reused for journal intake sources.

**Context.** Exchange Online outbound connectors cannot use SMTP AUTH, present Microsoft's shared certificate and connect from address ranges shared by every Microsoft 365 tenant; Gmail outbound routes behave the same way. Step 2.2 therefore documented outbound through the gateway as unsupported for Exchange Online and forbade `source_ip` connectors on shared ranges, because any tenant of the provider could relay as any other. The only tenant-unique evidence is in the message: a DKIM signature by the customer's own domain (keys only that customer's provider tenant signs with) and, for Microsoft 365, the `X-MS-Exchange-CrossTenant-Id` header Exchange Online stamps.

**Decision.**

1. A fourth connector authentication type `provider_relay`, one connector per connection, created only through the wizard's explicit-authorization apply (ADR-0080), resolved on the existing `postfix-outbound` relay listener **after** client-certificate and source-IP connectors: client address in the provider's active egress set, non-empty envelope sender whose domain is an active, outbound-enabled domain of an active organization, linked to an `active` connection of that provider with outbound mode `probe_only` or `active`. TLS is required. Unmatched clients receive today's relay-denied answer. A client in the provider egress ranges is shared infrastructure, so a client-certificate or (legacy) source-IP connector matched there applies only to senders of its own organization; every other sender from those ranges is resolved by the provider relay (closer review, 2026-11-19: otherwise one organization could register the provider's shared certificate fingerprint and capture every other organization's provider traffic).
2. At END-OF-MESSAGE the policy service writes a marker (`sa:prelay:{queueId}`) naming the organization and connection, with a lifetime of at least Postfix's `maximal_queue_lifetime` (so a late or split delivery always finds it); a Redis failure defers, and a provider-egress session that no longer resolves at END-OF-MESSAGE is deferred instead of relayed without a marker.
3. LMTP ingestion verifies the **proof** before anything is stored: Microsoft 365 requires every `X-MS-Exchange-CrossTenant-Id` value to equal the connection's verified tenant id **and** an aligned DKIM pass by a linked domain; Google Workspace requires an aligned DKIM pass with a signature time within one hour and a replay counter. Proof failure refuses every recipient of the transaction with `550 5.7.26` (a post-queue DSN to the envelope sender of the organization's own domain); verification trouble is `451`. Tenant overrides may relax only the Microsoft tenant header (never DKIM), and only together with the DKIM freshness window and replay limit (DKIM is then the only proof, with the same replay residual risk as Google); they are themselves explicit-authorization changes.
4. Null-sender mail from provider ranges is refused on the provider relay.
5. Egress ranges are versioned platform data imported by operators (seeded with a snapshot); the adapter keeps the last loaded set on load errors.
6. The mail path never calls a provider API (I1). Accepted mail continues on the normal outbound or internal path unchanged.

**Consequences.** Exchange Online and Gmail outbound and internal mail can be routed through the gateway without a shared-IP relay hole. Customers must enable DKIM signing for each linked domain before activation (validated by the probe). A message that legitimately loses its DKIM signature inside the provider (rare transport-rule rewrites) is refused instead of relayed; the guide warns about body-modifying transport rules before the connector. Residual risks: a message signed by another tenant's linked domain can be replayed within the freshness window up to the replay limit (Google, and Microsoft 365 with the tenant header off); a marker lost with Redis data (not eviction: Redis runs `noeviction`) lets the queue file be ingested on the ordinary outbound path without the proof, which LMTP ingestion cannot tell apart because the relay and submission listeners share one content filter.

**Alternatives considered.** SMTP AUTH; per-tenant certificates; per-tenant ports or host names; `source_ip` connectors over provider ranges; a milter or pre-queue proxy (see the design note §7).
