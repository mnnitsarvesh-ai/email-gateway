# ADR-0062: Sensitive message metadata is masked by default and revealed only through an audited `message:reveal` action

**Status:** Accepted (2026-11-14; implemented by step 7.2 WP2 and verified locally, see [docs/plan/steps/21-email-explorer-details.md](../../plan/steps/21-email-explorer-details.md) §13 WP2; the portal's masked views and reveal flows (WP3, WP4) verified end to end per role, with the full regression, in §14 (WP5); designed there in §1.5, E5–E9, §3.3–§3.5; proposed by the step 7.2 architect; production-scale timing, CI and a cluster apply not verified, the step is not committed). Supersedes no ADR decision. Amends step designs: 2.3 R13 (delivery views return masked recipients), 5.3 Q26 (quarantine entry `recipient` rule for non-deciders) and 6.1 D11 (detail reads no longer return clear subjects or recipients; reveals are audited). Keeps [ADR-0038](0038-dlp-evidence-masking-and-aadhaar-gating.md) (DLP masking and the evidence door) and [ADR-0048](0048-quarantine-preview-and-download-controls.md) (sanitized preview, download grants) unchanged.

**Context.** Until step 7.2 every holder of `message:read` (including read-only users, domain admins, quarantine reviewers and platform admins) received subjects and recipient addresses in clear from `GET /messages`, the message detail, recipients and deliveries; quarantine entries returned recipients to every `quarantine:read` holder; header values had no API at all. The 7.2 brief asks for appropriate masking and role-based access to sensitive message content, and the step directive requires recipient addresses, subjects, header values and DLP matches to be masked by default for roles without the matching permission, revealed only through an explicit, audited, permission-checked API action, enforced by the API rather than the UI. DLP already follows this shape: masked samples by default, decrypted values only through one audited door.

**Decision.**

1. **A new tenant permission `message:reveal`** (catalog 59 → 60), granted to organization admins (through every tenant permission), security analysts and compliance auditors; super admins hold it through all permissions. Platform admins, domain admins, quarantine reviewers, read-only users and mailbox users do not hold it. It is not part of the read-only permission set. API keys may hold it as a scope (no escalation).
2. **Masked by default on the message surface, for every caller.** Reads never return the subject (`subject: null` with `subjectMasked`), recipient addresses (`f***@example.com` with `addressMasked` / `recipientMasked`), the matched user id of a recipient, or the values of the `To`, `Cc` and `Subject` headers. Masking is applied in the api service layer from pure functions, so every client sees the same result.
3. **Clear values only through two explicit `POST` actions** that require `message:reveal`: `POST /messages/reveal` (subjects of up to 100 messages, for a list page) and `POST /messages/{messageId}/reveal` (subject, the masked header values and the recipient addresses with a cursor). Each writes one `message.revealed` audit row **per message** (fields and counts, never values) and commits it before the response is sent; an audit failure returns no value. Responses are `no-store`, a per-principal limit `API_MESSAGES_REVEAL_PER_MINUTE` applies, missing and foreign ids look the same.
4. **Header safe subset.** `GET /messages/{messageId}/headers` returns the stored allow-list of step 3.1; From, Sender, Reply-To, Return-Path, Date, Message-ID, In-Reply-To, References and Authentication-Results are in clear (sender side, identifiers and authentication facts); To, Cc, Subject and any unknown name are masked. The full header block stays in object storage and is never fetched.
5. **Free text.** Address-shaped substrings in SMTP replies, delivery event details and Rspamd symbol options have their local part masked for every caller and are never revealed (the reveal returns the addresses themselves).
6. **Searches that would confirm a masked value need the permission too.** Subject searches and the exact `recipient` search of `GET /messages` require `message:reveal` (ADR-0061 decision 4; `403 message_filter_forbidden`), so a role that cannot see a subject or a recipient address cannot probe it (for example by listing the organization's user addresses with `user:read` and testing each one). `recipientDomain` stays open: the masked form `f***@example.com` keeps the domain in clear. (The recipient rule was added when the step was closed, after review; step note §13 closer.)
7. **Quarantine operator routes keep a role-based rule.** Entry `recipient` is clear for holders of a quarantine decision permission (release, approve, reject, delete, request release, manage) or `message:reveal`, masked (`recipientMasked`) for other `quarantine:read` holders; every quarantine operator read is already audited (5.3). A caller who reads recipients masked may not search entries by an exact `recipient` either (`403 quarantine_filter_forbidden`, refused before any read; added at the step close, as decision 6). Subjects keep the 5.3 rule (`quarantine:preview`). Self-service routes are unchanged.
8. **DLP matches** are unchanged: masked samples with `dlp:read`, decrypted evidence only through the audited, MFA-protected evidence route with `dlp:evidence_read`.
9. **The portal** keeps revealed values only in component state for the page view (never in the query cache, the URL or browser storage) and offers reveal only to holders of the permission.

**Alternatives considered.** Clear values for privileged roles by default (unaudited clear views, contrary to "reveal only through an explicit, audited action"). Reusing `message:read_content` (its meaning is body and attachment content from object storage; compliance auditors reveal metadata without reading bodies). A reveal token forwarded on later GETs (a new header through the portal BFF, a bearer in the browser and cacheable clear responses). One audit row per bulk reveal (the message's audit history could not find it). Masking quarantine recipients for everyone (the reviewer decides per recipient; reviewer reads are audited). Masking sender addresses (triage needs them; the brief names recipients, subjects, header values and DLP matches).

**Consequences.** API clients that relied on clear subjects or recipients (pre-GA; documented as a contract tightening in the API guide changelog) must call the reveal operations with `message:reveal`. Read-only roles lose recipient addresses on the quarantine operator routes. Every clear subject, recipient and masked header value is attributable to a principal, a time, an address and a message. The explorer shows masked subjects unless the user turns on the audited per-page reveal. Roles without `message:reveal` (read-only users, domain admins, quarantine reviewers, platform admins) can no longer search messages by an exact recipient; they keep the recipient domain, the sender and Message-ID searches. Addresses inside URLs remain as the URL engine normalized them (recorded follow-up).

**Open product-owner questions (recorded at the step close, not decided by this ADR).**

- **Attachment file names** are written by the sender and come from the MIME body, like subjects, and can name people or confidential matters. They are **not masked**: every `message:read` holder reads them in clear from `GET /messages/{messageId}/attachments`, `GET /attachments`, the `attachment`/`sandbox` entries of the scan rounds and the policy facts, as before step 7.2 (including `quarantine_reviewer` and `platform_admin`, whose catalog descriptions say "no content access"). Masking them would change the contract of the step 3.x/6.1 attachments routes and the 7.1 Attachments page and needs a reveal field; the product owner decides whether file names are masked like subjects (with an extension kept for triage) or stay in clear.
- **Body preview of messages that were never quarantined.** The only message text the api can show is the sanitized preview of a quarantined copy (ADR-0048, `quarantine:preview`); `message:read_content` ("view message content from object storage") is still used by no route. Whether an audited, on-demand sanitized preview for delivered, tagged or rejected mail (gated by `message:read_content`, fetched only after an explicit request) is wanted is a product-owner decision; step 7.2 builds none.

**Implementation notes (step 7.2 WP2, 2026-11-14).**

- The masks are pure functions of `apps/api/src/modules/messages/domain/sensitive-masking.ts` applied by the services (`MessageDataService`, `DeliveriesService`, the scans mapper, `QuarantineQueryService`, `MessageHeadersService`), so every route, principal kind and client gets the same result. `maskAddress` keeps the first Unicode code point of the local part and the domain as stored, splitting at the last `@`.
- `maskAddressesInText` masks the address shapes of §3.4 plus quoted local parts and domains with Unicode (U-label) labels, which the designed pattern would have left in clear; a lookbehind starts a match only at the beginning of a run of local-part characters, so hostile long runs scan in linear time.
- The header safe subset and the masked names together are exactly the step 3.1 stored allow-list (a unit test compares them with the parser's list); any other name is masked. `availability` is `available` whenever rows exist (a `parse_limit_exceeded` parse can store headers); `retention_expired` uses `retentionCutoff` of the `email_headers` entry of the partition registry, the rule the partition job drops by.
- The reveal operations read the values from the replica and commit every `message.revealed` row in one writer transaction (`TransactionRunner` + `AuditService.record`) before building the response; a failed write is `503 service_unavailable` and no value. Audit metadata holds fields, counts and `rcptSeq` positions only; override sessions add `metadata.override` through `AuditService.actorFrom`.
- `MessageRevealRateLimitGuard` (bucket `message-reveal`, `API_MESSAGES_REVEAL_PER_MINUTE`, per user or API key, shared by both operations) runs after authentication and RBAC, answers the coded `429 rate_limited` (`scope: route`) with `Retry-After`, reports its `RateLimit-*` headers when it is the most restrictive counter and fails closed (`503`) without the store.
- The recipients of a single reveal page with a signed v1 cursor (`message_recipients_reveal`) bound to the message and the organization; a cursor is checked before any read.
- The quarantine recipient rule is `RECIPIENT_CLEAR_PERMISSIONS` (the six decision permissions and `message:reveal`); the DTO of `@email-gateway/quarantine` carries `recipientMasked`. No other quarantine operator response carries a recipient address; the sanitized preview (ADR-0048) is unchanged.

**Implementation notes (step 7.2 close, 2026-11-15).** After review the closer added `recipient: 'message:reveal'` to the filter permissions of `GET /messages` (`domain/message-list-plan.ts` `FILTER_PERMISSIONS`; saved views apply the same rule at save time) and the `403 quarantine_filter_forbidden` refusal of an exact `recipient` search by a masked caller to `QuarantineQueryService.search` (new code in `QUARANTINE_ERROR_CODES` of `@email-gateway/quarantine`). The portal hides both filters from such users and ignores them in shared links and saved views; the dev fixtures follow. Tests: unit, api e2e (every system role), api integration on MySQL, portal component and the Playwright explorer spec.
