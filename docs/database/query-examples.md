# Query examples

The hot queries of the platform (D8 in [the step design](../plan/steps/01-database.md#d8-performance-test)), as SQL and, where practical, as Prisma. `pnpm db:perf` runs exactly this SQL and records the plans, the partitions read and the timings in [performance-report.md](performance-report.md).

Rules that every query on a partitioned table follows ([partitioning.md](partitioning.md)):

- Constrain the partition column: an exact `received_at` for one message (from the registry or the event payload), or a range for lists. Without it, every partition is probed.
- Tenant-scoped queries filter by `organization_id` taken from the authenticated context, and the index leads with it.
- Ids are `bigint` in Prisma. Convert with `formatId` before they leave the service.
- Control-plane list and report reads in the api use `PrismaReadService.client` (the replica, with writer fallback). Read-after-write paths use the writer ([replication.md](replication.md#routing-rules)).

## Q1: Tenant message list, last 24 h, keyset pagination

```sql
-- first page
SELECT id, received_at, status, direction, envelope_from, subject, final_verdict, risk_score
  FROM email_messages
 WHERE organization_id = ? AND received_at >= ? AND received_at < ?
 ORDER BY received_at DESC, id DESC
 LIMIT 50;
-- next page: cursor = (received_at, id) of the last row
SELECT ... FROM email_messages
 WHERE organization_id = ? AND received_at >= ?
   AND (received_at < ? OR (received_at = ? AND id < ?))
 ORDER BY received_at DESC, id DESC
 LIMIT 50;
```

```ts
const page = await reader.client.emailMessage.findMany({
  where: {
    organizationId,
    receivedAt: { gte: since },
    ...(cursor && {
      OR: [
        { receivedAt: { lt: cursor.receivedAt } },
        { receivedAt: cursor.receivedAt, id: { lt: cursor.id } },
      ],
    }),
  },
  orderBy: [{ receivedAt: 'desc' }, { id: 'desc' }],
  take: 50,
});
```

**Pruning:** the partitions overlapping the window (1, or 2 around a month boundary). Backward range scan on `(organization_id, received_at, id)`, no filesort. Keyset pagination never uses `OFFSET`. The cursor is written as an expanded `OR` rather than a row constructor `(received_at, id) < (?, ?)`, which keeps the plan a plain range scan with the `organization_id` prefix (verified in the performance report).

## Q2: Message detail by `public_id`

```sql
SELECT id, organization_id, received_at FROM message_identities WHERE public_id = ?;
SELECT * FROM email_messages WHERE id = ? AND received_at = ? AND organization_id = ?;
SELECT id, rcpt_seq, address, status, final_action
  FROM email_recipients WHERE message_id = ? AND received_at = ? ORDER BY rcpt_seq;
```

```ts
const identity = await prisma.messageIdentity.findUnique({ where: { publicId } });
if (!identity || identity.organizationId !== organizationId) throw new NotFoundException();
const message = await prisma.emailMessage.findUnique({
  where: { id_receivedAt: { id: identity.id, receivedAt: identity.receivedAt } },
});
const recipients = await prisma.emailRecipient.findMany({
  where: { messageId: identity.id, receivedAt: identity.receivedAt },
  orderBy: { rcptSeq: 'asc' },
});
```

**Pruning:** one partition per table. The registry is a unique-key lookup, and the message is a primary-key `const` lookup. A registry row from another organization is answered as "not found", never "forbidden".

## Q3: Scans and engine results for a message

Step 4.1 ([S3, S5, S16](../plan/steps/09-rspamd.md#s3-scan-round-identity)): one `email_scans` row per scan round (`lifecycle_round`), newest round first; per engine its attempts (non-final rows, `is_final = 0`, outcome `timeout`/`error`) and its one final result; plus the round's authentication results. The scans read API (`GET /api/v1/messages/{id}/scans`) runs this on the replica after resolving the message within the caller's organization.

```sql
SELECT s.id AS scan_id, s.lifecycle_round, s.scan_kind, s.status, s.scan_verdict,
       r.engine, r.attempt, r.is_final, r.outcome, r.score, r.duration_ms
  FROM email_scans s
  JOIN scan_engine_results r ON r.scan_id = s.id AND r.received_at = s.received_at
 WHERE s.message_id = ? AND s.received_at = ?
 ORDER BY s.lifecycle_round DESC, r.engine, r.attempt;
SELECT scan_id, engine, spf, spf_domain, dkim, dkim_signatures, dmarc, dmarc_policy, dmarc_domain, arc
  FROM email_auth_results
 WHERE scan_id IN (?) AND received_at = ?;
```

Prisma has no relation between partitioned tables, so it is three queries: `emailScan.findMany({ where: { messageId, receivedAt, organizationId }, orderBy: { lifecycleRound: 'desc' } })`, then `scanEngineResult.findMany({ where: { scanId: { in: ids }, receivedAt }, orderBy: [{ engine: 'asc' }, { attempt: 'asc' }] })` and `emailAuthResult.findMany({ where: { scanId: { in: ids }, receivedAt } })`. `finalEngine` is generated by MySQL and only ever read. **Pruning:** one partition each. The rounds are a `ref` read on UQ `(message_id, lifecycle_round, received_at)`; the engine rows use UQ `(scan_id, engine, attempt, received_at)` and the authentication rows UQ `(scan_id, engine, received_at)`; every join condition repeats `received_at` so the inner tables prune too (verified with `EXPLAIN` on a `db:perf` schema: `ref` on both keys, one partition each; a few rows are sorted in memory).

## Q7: Stuck-message reconciliation

The step 3.3 expiry sweeper and lifecycle check (event-relay) run this shape per state, with a `received_at` lower bound for pruning and `MOD(id, shards)` for sharding (design [L13, L14](../plan/steps/08-message-lifecycle.md#l13-expiry-sweeper-event-relay)).

```sql
SELECT id, received_at, organization_id, status, status_changed_at
  FROM email_messages
 WHERE status IN ('scanning', 'policy_evaluated', 'delivery_pending')
   AND status_changed_at < NOW(3) - INTERVAL 15 MINUTE
 ORDER BY status_changed_at
 LIMIT 500;
```

A platform job, not tenant-scoped. **Pruning:** none (no `received_at` predicate), so the `(status, status_changed_at)` index is probed in every partition. It reads only the few matching entries, so it stays cheap. To bound it, add `received_at >= NOW() - INTERVAL 2 DAY`: a message stuck for longer is handled by an alert, not by this job.

## Q8: Outbox relay poll

> Step 3.2 note: the event-relay (ADR-0023) does not use `FOR UPDATE SKIP LOCKED`. It claims shards with advisory locks (`GET_LOCK('er:relay#<i>/<n>')`, shard = `MOD(CRC32(CONCAT(aggregate_type, ':', aggregate_id)), n)`), reads `WHERE published_at IS NULL AND attempts < :max AND <shard> ORDER BY id LIMIT :scan` without a transaction, publishes with confirms, then marks the confirmed rows `UPDATE … SET published_at = NOW(3) WHERE published_at IS NULL AND (id, created_at) IN (…)` (design Q11). The query below is the original step 1.1 access-path example; the index and pruning notes apply to both.

```sql
SELECT id, created_at, event_id, event_type, organization_id, payload
  FROM message_outbox
 WHERE published_at IS NULL
 ORDER BY id
 LIMIT 100
 FOR UPDATE SKIP LOCKED;
```

Raw SQL in Prisma (`$queryRaw`), inside a transaction that marks the rows published. `SKIP LOCKED` lets several relay instances poll without blocking each other. **Pruning:** none: the `(published_at, id)` index is read in each daily partition (about 15 in steady state), and only unpublished rows match. Mark rows with `UPDATE … WHERE id = ? AND created_at = ?` so the update prunes.

## Q13: Tenant resolution by recipient domain (mail path)

```sql
SELECT d.id, d.public_id, d.organization_id, d.name, d.status, d.inbound_enabled, d.outbound_enabled, o.status
  FROM domains d JOIN organizations o ON o.id = d.organization_id
 WHERE d.verified_name = ?;   -- then require d.status = 'active' AND o.status = 'active'
```

Use `resolveActiveDomain(writer, rawName)` from `@email-gateway/database` (step 2.1 D13): it normalizes the name like the api stores it (`normalizeDomainName`: case, trailing dot, IDN), runs `domain.findUnique({ where: { verifiedName } })` with the organization's status, and returns the owner only when the domain is `active` and the organization is `active`. `verified_name` is a MySQL generated column (`name` while `status` is `verified`, `active` or `suspended`, otherwise NULL) with a unique index, so the lookup is a `const` single-row read and **only the owner** can match: several organizations may hold a pending claim on the same `name` (unique per `(organization_id, live_name)`), and a pending claim never resolves a tenant. Never resolve a tenant with `WHERE name = ?`. Callers then check `inbound_enabled` / `outbound_enabled` for the direction. It runs for every SMTP transaction, so the ingestion step (3.x) can cache it in Redis.

**Post-queue owner** (step 2.2 D7, D13): `resolveDomainOwner(writer, rawName)` runs the same single-row lookup with the same normalization, but also resolves `suspended` domains and organizations (it returns `status` and `organizationStatus` with the owner). LMTP ingestion and the bounce handler use it for mail Postfix has already accepted in-session, so a suspension between acceptance and ingestion never loses a message; `pending_verification`, `verified` (not activated), `failed`, `disabled`, `deleted` domains and `pending_deletion`/`deleted` organizations still resolve to `null`. In-session decisions keep using `resolveActiveDomain`. Both are writer-only.

## Q19: Deliveries of one message (step 2.3)

`GET /messages/{messageId}/deliveries` ([R13](../plan/steps/05-routing.md#r13-api-tenant-scoped-openapi)): the registry resolves the public id to `(id, received_at)` within the caller's organization (Q2), then:

```sql
SELECT d.id, d.delivery_seq, d.direction, d.status, d.attempt_count, d.last_attempt_at,
       d.delivered_at, d.remote_host, d.final_smtp_code, d.enhanced_status,
       d.final_smtp_response, d.last_error_class, d.failure_reason, d.dsn_queue_id,
       d.status_changed_at, r.rcpt_seq, r.address
  FROM email_deliveries d
  JOIN email_recipients r ON r.id = d.recipient_id AND r.received_at = d.received_at
 WHERE d.message_id = ? AND d.received_at = ? AND d.organization_id = ?
 ORDER BY r.rcpt_seq, d.delivery_seq;
```

Prisma: `emailDelivery.findMany({ where: { messageId, receivedAt, organizationId }, orderBy: [{ deliverySeq: 'asc' }, { id: 'asc' }] })`, then `emailRecipient.findMany({ where: { messageId, receivedAt, organizationId } })` joined in memory (no relations on partitioned tables). Index `(message_id, received_at)` on both sides (recipients through the unique `(message_id, rcpt_seq, received_at)`). **Pruning:** one partition of each table. The `organization_id` predicate is a second tenant check on top of the registry lookup. Read from the replica (`PrismaReadService`); a few seconds of lag are acceptable for a status page.

## Q20: Tenant delivery list, bounded window, keyset pagination (step 2.3)

`GET /deliveries` (R13): window `[from, to)` of at most 31 days (default the last 24 h), optional `status` / `direction` filters.

```sql
SELECT id, received_at, message_id, recipient_id, direction, status, attempt_count,
       last_error_class, status_changed_at
  FROM email_deliveries
 WHERE organization_id = ? AND received_at >= ? AND received_at < ?
   AND (? IS NULL OR status = ?) AND (? IS NULL OR direction = ?)
   AND (received_at < ? OR (received_at = ? AND id < ?))  -- next page only
 ORDER BY received_at DESC, id DESC
 LIMIT 50;
```

Prisma: `emailDelivery.findMany({ where: { organizationId, receivedAt: { gte: from, lt: to }, status, direction, OR: cursor ? [{ receivedAt: { lt: c.receivedAt } }, { receivedAt: c.receivedAt, id: { lt: c.id } }] : undefined }, orderBy: [{ receivedAt: 'desc' }, { id: 'desc' }], take: 50 })`. Index `(organization_id, received_at, id)` (step 2.3): a backward range scan in index order, no filesort; `status` / `direction` are filtered on the rows read, so a rare status in a busy tenant reads more rows per page (bounded by the window). The message public id and the recipient address of the page are fetched with two batched lookups (`message_identities` by id, `email_recipients` by `(id, received_at)`). **Pruning:** the partitions overlapping the window (at most 2 for 31 days).

## Q21: Delivery-log and DSN matching by queue id (step 2.3)

The Postfix log tailer and the bounce handler match a line or a notice to a delivery by the postfix-outbound queue id (R9.1 step 1, `recordDeliverySignal`):

```sql
SELECT id, received_at, message_id, recipient_id, delivery_seq
  FROM email_deliveries
 WHERE outbound_queue_id = ?
 LIMIT 1000;
-- then the recipients of those rows, compared case-insensitively on the whole address in code
SELECT id, received_at, address FROM email_recipients WHERE (id, received_at) IN ((?, ?), ...);
-- no hit: a recipient not yet tied to the file, among the bound reinjection's recipients
-- (a log line naming the address proves postfix-outbound accepted it under this queue id):
SELECT id, received_at FROM delivery_reinjections WHERE queue_id = ?;
SELECT id, received_at, message_id, recipient_id, delivery_seq
  FROM email_deliveries
 WHERE reinjection_id = ? AND received_at = ? AND outbound_queue_id IS NULL;
-- bounce notices also look the reinjection up by queue id or token, then its recipients:
SELECT id, received_at, message_id, organization_id FROM delivery_reinjections WHERE queue_id = ?;
SELECT id, received_at, message_id, organization_id FROM delivery_reinjections WHERE public_id = ?;
SELECT id FROM email_deliveries WHERE reinjection_id = ? AND received_at = ?;
```

Prisma: `emailDelivery.findMany({ where: { outboundQueueId }, take: 1000 })`, `deliveryReinjection.findFirst({ where: { publicId } })`, `emailDelivery.findMany({ where: { reinjectionId, receivedAt } })`. Indexes `email_deliveries (outbound_queue_id)` and `(reinjection_id, received_at)` (one partition: `received_at` is the reinjection's), `delivery_reinjections (queue_id)` and `(public_id)`. **Pruning:** none: a log line carries no `received_at`, so the index is probed in every partition (7 monthly partitions at 6 months of retention), returning at most the ≤ 100 recipients of one reinjection. Writer only (data plane, ADR-0014).

## Q23: Parse outcome and attachments of one message (step 3.1)

What the scanning steps (4.x) and the lifecycle (3.3) read after `mail.message.parsed.v1`, with `(messageId, receivedAt)` from the event payload and `organization_id` from the envelope (checked against the message row):

```sql
SELECT status, attempts, parser_version, failure_reason, limits_exceeded, defects,
       part_count, attachment_count, max_depth, header_count,
       text_body_object_key, text_body_sha256, text_body_size_bytes,
       html_body_object_key, html_body_sha256, html_body_size_bytes, completed_at
  FROM email_message_parses
 WHERE message_id = ? AND received_at = ? AND organization_id = ?;

SELECT part_index, part_path, depth, disposition, filename, declared_content_type,
       detected_content_type, size_bytes, encoded_size_bytes, sha256, object_key,
       flags, archive_info, verdict
  FROM email_attachments
 WHERE message_id = ? AND received_at = ? AND organization_id = ?
 ORDER BY part_index;
```

Prisma: `emailMessageParse.findUnique({ where: { messageId_receivedAt: { messageId, receivedAt } } })` (then compare `organizationId`), and `emailAttachment.findMany({ where: { messageId, receivedAt, organizationId }, orderBy: { partIndex: 'asc' } })`. The parse row is a point lookup on UQ `(message_id, received_at)` (`const` in the plan); the attachments are a `ref` read on UQ `(message_id, part_index, received_at)` in index order, no filesort. **Pruning:** one partition for each (`p<yyyymm>` of `received_at`, verified with `EXPLAIN` on the local stack). `original_filename` is escaped metadata for display and forensics; it is never used as a path or an S3 key. Not part of `pnpm db:perf` (like Q19–Q22).
