# Database

MySQL 8.4 is the primary transactional store, managed with Prisma ([ADR-0003](../architecture/adr/0003-prisma-orm.md), [ADR-0014](../architecture/adr/0014-mysql-data-model-partitioning-read-write-split.md)). The schema is `packages/database/prisma/schema.prisma`, and the migrations are in `packages/database/prisma/migrations/`. The design behind it is [step 1.1](../plan/steps/01-database.md).

The schema has **91 tables** in 10 modules, and **28** of them are range-partitioned by time. Steps 1.2 + 1.3 added `user_tokens` and `user_mfa_recovery_codes` and the identity/tenancy columns ([D10](../plan/steps/02-tenants-auth-rbac.md#d10-data-model-changes-one-forward-migration-wp1)); step 2.2 added `domain_recipient_addresses`, `smtp_connectors` and `smtp_connector_networks` ([§3](../plan/steps/04-smtp-gateway.md#3-data-model-one-forward-migration-wp1)); step 2.3 added `mail_destination_presets`, `stream_cursors` and the partitioned `delivery_reinjections` and `delivery_status_events`, plus per-recipient delivery tracking columns on `email_deliveries`, `email_recipients.direction` and destination-server columns on `domain_mail_servers` ([§3](../plan/steps/05-routing.md#3-data-model-one-forward-migration-mail_routing-wp1), migration `20261103090000_mail_routing`; the review fix `20261103180000_delivery_reinjection_index` adds the online index `email_deliveries (reinjection_id, received_at)`). Step 3.1 added the partitioned parse stage table `email_message_parses` (one row per message, owned by email-worker) and the nullable attachment metadata columns `part_path`, `depth`, `disposition`, `encoded_size_bytes`, `original_filename`, `flags` and `archive_info` on `email_attachments` ([§3](../plan/steps/06-mime-ingestion.md#3-data-model-one-forward-migration-mime_ingestion-wp1), migration `20261103200000_mime_ingestion`; the `email_attachments` columns are an `ALGORITHM=INSTANT` change). Step 3.2 added the reconciliation columns `redrive_count` and `last_redriven_at` and the index `(last_redriven_at)` on `message_outbox` ([§4](../plan/steps/07-rabbitmq.md#4-data-model-one-forward-migration-event_relay-wp1), migration `20261104000000_event_relay`, `ALGORITHM=INSTANT` columns; table and partition counts unchanged); its review round 1 added the unpartitioned `message_consumer_progress` (a consumer's `retrying` / `dead_lettered` record of an event it has not handled, read by the reconciler) and the index `message_outbox (event_id)` for the delivery planner's approval provenance check ([§4](../plan/steps/07-rabbitmq.md#4-data-model-one-forward-migration-event_relay-wp1), migration `20261104120000_consumer_progress`). Step 3.3 ([§3](../plan/steps/08-message-lifecycle.md#3-data-model), [ADR-0025](../architecture/adr/0025-message-lifecycle-state-machine.md)) replaced the `MessageStatus` values by the fifteen lifecycle states (backfilling the old values and a version-0 history row per message), added `lifecycle_round` and `status_reason` to `email_messages`, the actor, correlation, transition-key and occurrence columns plus the unique key `(message_id, transition_key, received_at)` to `email_message_status_history`, and the unpartitioned `api_idempotency_keys` (the api's Idempotency-Key store) (migration `20261104130000_message_lifecycle`), and made the five Postfix queue-id columns case-sensitive (`utf8mb4_bin`, migration `20261104130100_queue_id_case_sensitive`); the ALTER algorithms MySQL used are recorded in [schema-reference.md](schema-reference.md#step-33-changes-message-lifecycle). Step 4.1 ([§3](../plan/steps/09-rspamd.md#3-data-model-one-forward-migration-scan_pipeline-wp1), [ADR-0026](../architecture/adr/0026-security-scan-pipeline.md)) made `email_scans` one row per scan round (unique `(message_id, lifecycle_round, received_at)`, with `scan_verdict`, `required_engines`, `reason_codes`, `trigger_event_id`, `deadline_at` and the sweeper index `(status, deadline_at)`), turned `scan_engine_results` into engine attempts with one final row per engine (`attempt`, `is_final`, the generated `final_engine` in a unique key, a CHECK that non-final rows are failures, `EngineOutcome` + `spam`, `unknown`), added `email_messages.client_name` (Postfix XFORWARD NAME), the partitioned `email_auth_results` (SPF/DKIM/DMARC/ARC per round, 6 months, core) and the per-tenant `scan_engine_settings` (migration `20261105090000_scan_pipeline`; algorithms in [schema-reference.md](schema-reference.md#step-41-changes-scan-pipeline)). Step 4.2 ([§3](../plan/steps/10-attachment-scanning.md#3-data-model-one-forward-migration-attachment_scanning-wp1), [ADR-0028](../architecture/adr/0028-attachment-scanning-engine.md)) evolved the never-written platform catalog `malware_signatures` into the known-threat hash catalog (`added_by_user_id` FK `users` SET NULL, `reason`, `expires_at`, index `(source, created_at)`; written by the api's platform threat-hash routes, read by the attachment engine), and added the partitioned `attachment_scan_results` (one row per attachment per scan round; hashes, type ids, signature/rule names and codes only, never a filename or content) and `sandbox_submissions` (the step 4.6 sandbox contract), both 6 months, core, plus the unpartitioned `attachment_rescan_jobs` (bulk rescans after signature updates or by a platform admin) and `scan_signature_versions` (migration `20261105103406_attachment_scanning`; algorithms in [schema-reference.md](schema-reference.md#step-42-changes-attachment-scanning)). Step 4.3 ([§3](../plan/steps/11-url-protection.md#3-data-model-one-forward-migration-url_protection-wp1), [ADR-0029](../architecture/adr/0029-url-security-engine.md)) evolved the never-written `threat_indicators` into the platform URL/domain/IP feed (`added_by_user_id` FK `users` SET NULL, `reason`, `category`, index `(source, created_at)`; written by the api's platform threat-indicator routes, read by the URL engine and the click-service, never cached) and added five partitioned tables (6 months, core): `message_urls` (one row per unique URL of a message: the normalized URL, its identity hash, host, flags and sources; the click-service redirects only to this stored URL), `url_scan_results` (one row per URL per round), `url_rewrites` (the S3 reference of the round's rewritten EML or its skip reason), `url_dynamic_inspections` (browser inspection requests and results) and `url_click_events` (decided clicks, partitioned by `clicked_at`), plus the click-service's own account `gateway_click` (migration `20261105214341_url_protection`; algorithms in [schema-reference.md](schema-reference.md#step-43-changes-url-protection)). Step 4.4 ([§3](../plan/steps/12-phishing-bec.md#3-data-model-one-forward-migration-bec_detection-wp1), [ADR-0033](../architecture/adr/0033-bec-engine-and-stage-dependencies.md), [ADR-0035](../architecture/adr/0035-bec-communication-context-privacy.md)) added the partitioned `bec_scan_results` (one row per scan round with a definite `bec` final: versions, deterministic and final score and verdict, input states, fired rules with bounded evidence, the AI feature vector and assessments; never body text, span text or excerpts; 6 months, core) and six unpartitioned tenant tables: `bec_executive_profiles` and `bec_vendor_profiles` (impersonation profiles, unique per tenant on the normalized name), `bec_trusted_senders`, `bec_feedback` (analyst false-positive / false-negative feedback, unique per scan, user and kind), `bec_suppression_rules` (bounded, expiring suppressions of suppressible codes) and `bec_contact_history` (opt-in communication context as organization-scoped keyed hashes and counts, no plaintext address); the tenant tables reference `organizations` (RESTRICT, no cascade) and `users` (SET NULL) (migration `20261106171051_bec_detection`; see [schema-reference.md](schema-reference.md#step-44-changes-phishing-and-bec)). Email bodies and attachments are never stored in MySQL: only S3 object keys, sizes and hashes.

## Conventions

- **Identifiers.** Every surrogate key is `BIGINT UNSIGNED AUTO_INCREMENT` (`BigInt @db.UnsignedBigInt`). Pure join tables use a composite key, and `message_idempotency` uses `(consumer, event_id)`.
- **`public_id`.** `CHAR(36)` UUIDv7, only on externally addressed aggregates: `organizations`, `users`, `domains`, `api_keys`, `email_policies`, `webhook_subscriptions`, `quarantine_messages`, `message_identities`, `smtp_connectors` (step 2.2), `domain_mail_servers` (step 2.3; rows created before it were backfilled with MySQL `UUID()`, a v1 UUID) and `delivery_reinjections` (step 2.3; indexed but not a unique key, because a unique key of a partitioned table would have to include `received_at`; the reinjection token `dw1-<hex>` is derived from it), `url_click_events` (step 4.3; indexed) and the step 4.4 BEC tenant tables `bec_executive_profiles`, `bec_vendor_profiles`, `bec_trusted_senders`, `bec_feedback` and `bec_suppression_rules` (unique). REST APIs expose `public_id`, never the numeric id, so volumes and sequences do not leak.
- **Tenancy.** Every tenant-owned table has `organization_id BIGINT UNSIGNED NOT NULL`, and tenant-scoped indexes lead with it. It is nullable only on `roles`, `threat_indicators`, `yara_rules`, `audit_logs`, `login_audit_logs` and (step 4.2) `attachment_rescan_jobs` (NULL = platform-level; for a rescan job, every organization). Catalogs (plans, permissions, reputation tables, malware signatures, system settings, scan signature versions) have no `organization_id`; `malware_signatures` is platform-wide by design (step 4.2 A17: a tenant cannot add a hash that changes other tenants' verdicts), and so are the rows step 4.3 writes to `threat_indicators` (`organization_id` NULL; tenant URL lists are settings, `blockedDomains` / `allowedDomains`). The organization always comes from the authenticated context, never from a client header.
- **`bigint` serialization.** Prisma returns ids as `bigint`, and `JSON.stringify` throws on it. Internal contracts (events, S3 keys, logs) carry ids as canonical decimal strings: use `formatId`, `parseId` and `isIdString` from `@email-gateway/database` (`src/ids.ts`). Never put a raw `bigint` into a response or an event.
- **Names.** `snake_case` tables and columns (`@@map`/`@map`), and singular `PascalCase` models (`email_messages` → `EmailMessage`).
- **Time.** `DATETIME(3)` in UTC. `created_at` everywhere, and `updated_at` only on mutable rows (append-only tables have none).
- **Enums** are MySQL `ENUM`s. Values are only ever appended, except the one-time `MessageStatus` replacement of step 3.3 ([ADR-0025](../architecture/adr/0025-message-lifecycle-state-machine.md): widen, backfill, narrow); `MessageStatus` is append-only again from then on. **JSON** is only for flexible configuration and variable scan evidence.
- **Soft delete** only on `organizations`, `users`, `email_policies` and (step 2.1) `domains`; see [retention.md](retention.md).
- **Foreign keys** are real (`RESTRICT`, or `CASCADE` for owned children) between non-partitioned tables. Partitioned tables have **none**, in either direction: see [partitioning.md](partitioning.md).
- **Partitioned tables** have a composite primary key `(id, <partition column>)`, every unique key ends with the partition column, and child rows of a message copy the message's `received_at`.
- **No mail content.** Only `*_object_key VARCHAR(512)`, sizes and SHA-256 hashes. Every table has a primary key (`sql_require_primary_key=ON`).

## Workflows

```bash
pnpm db:migrate                      # history preflight, then apply pending migrations (prisma migrate deploy)
pnpm db:reset:local                  # local only: drop and recreate the schema's tables, migrate, partitions, seed
pnpm db:status                       # migration status
pnpm db:partitions -- plan           # print the partition DDL and purges, change nothing
pnpm db:partitions -- apply          # create partitions ahead, drop expired ones, run purges
pnpm db:seed                         # catalog + demo data (local, dev, CI); idempotent
pnpm db:seed -- --catalog-only       # catalog only (includes the platform organization)
pnpm db:perf                         # performance test in a throwaway schema; writes performance-report.md
pnpm db:migrate:dev --name <change>  # local only: create and apply a new migration
pnpm db:generate                     # regenerate the Prisma client
```

`db:migrate`, `db:reset:local`, `db:partitions`, `db:seed` and `db:perf` build `@email-gateway/database` (and its workspace dependencies) first. `db:partitions` accepts `--now <ISO>`, `--bootstrap-from <YYYY-MM-DD>` and `--lock-wait-timeout <seconds>` (default 5). `db:reset:local` refuses to run when `APP_ENV` is staging/production or `NODE_ENV` is production. In staging and production, `db:seed` refuses to run unless given `--catalog-only --allow-production`, and then seeds only the catalog.

In Compose, the `db-migrate` job runs the history preflight, `migrate deploy` and then `db:partitions apply` before any service starts. In Kubernetes, the `db-maintenance` CronJob runs partition maintenance daily at 01:30 UTC. CI applies the migrations to a fresh MySQL, runs maintenance twice (the second run must be a no-op), checks drift, and seeds twice to prove idempotency.

### Changing the schema

1. Edit `schema.prisma`.
2. Run `pnpm db:migrate:dev --name <short_description>` (or `--create-only` to review the SQL before applying it). This creates `prisma/migrations/<timestamp>_<name>/migration.sql`. `migrate dev` refuses to run in a non-interactive shell when it has a warning to confirm (for example "a unique constraint will be added"); then generate the SQL with `migrate diff --from-migrations prisma/migrations --to-schema-datamodel prisma/schema.prisma --shadow-database-url "$SHADOW_URL" --script` (the URL read with `node --env-file`, never echoed), save it as `prisma/migrations/<UTC timestamp>_<name>/migration.sql` and apply it with `pnpm db:migrate` (step 2.3 did this).
   `migrate dev` replays the migrations into the shadow schema `<db>_shadow` (`SHADOW_DATABASE_URL`), which `01-users.sh` creates and grants to the migrator; the migrator has no global privileges.
3. **Review the SQL.** Prisma does not model partitions or generated columns: for a partitioned table, `migrate dev` generates a plain `CREATE TABLE` or `ALTER TABLE`. Hand-edit the SQL so it keeps `PARTITION BY RANGE COLUMNS(...)`, the composite primary key and no foreign keys, and check locking on large tables. The generated columns `domains.verified_name`, `domains.live_name`, `threat_indicators.org_scope` and (step 4.1) `scan_engine_results.final_engine` are declared in `schema.prisma` as plain nullable columns marked READ-ONLY; their `GENERATED ALWAYS AS` clause lives only in the migration SQL (`20261102000000_tenant_scoped_uniques`, redefined for `verified_name` and added for `live_name` in `20261102091717_domain_onboarding`; `final_engine` in `20261105090000_scan_pipeline`), and application code never writes them. CHECK constraints (step 4.1 `scan_engine_results_attempt_outcome_check`) are not introspected by Prisma either and live only in the migration SQL. Prefer additive, backwards-compatible changes (expand → migrate → contract) so old and new pods can run side by side.
4. Re-run the drift check, which must print `No difference detected`:

   ```bash
   cd packages/database
   MIGRATION_URL=$(node --env-file=../../.env -e 'process.stdout.write(process.env.MIGRATION_DATABASE_URL)')
   node --env-file=../../.env node_modules/prisma/build/index.js migrate diff \
     --from-url "$MIGRATION_URL" --to-schema-datamodel prisma/schema.prisma --exit-code
   ```

   Read `.env` with `node --env-file`, not by sourcing it in the shell: values such as `NOTIFY_SMTP_FROM="Name <addr>"` are valid for Node and Compose but break `. ../../.env` in zsh and sh. Never echo the URL: it contains the migrator password. Partitions do not appear in Prisma's introspection, so the check stays clean after `db:partitions` has split `pmax`.

5. Verify the full history on a clean schema (below), then commit the schema and the migration together. CI fails if they do not match.

#### Clean-schema verification

Before committing a migration, apply **all** migrations to a throwaway schema `email_gateway_verify`, run partition maintenance and the drift check against it, then drop it. Never use the main schema for this and never run `prisma migrate reset` on it. The migrator holds no global `CREATE` (see Accounts), so locally the schema is created and granted by root inside the MySQL container, with the password taken from the container environment and never printed:

```bash
docker compose exec -T mysql sh -c 'MYSQL_PWD="$MYSQL_ROOT_PASSWORD" mysql -uroot -e \
  "CREATE DATABASE email_gateway_verify CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
   GRANT ALL PRIVILEGES ON email_gateway_verify.* TO \"$MYSQL_MIGRATOR_USER\"@\"%\";"'

cd packages/database
VERIFY_URL=$(node --env-file=../../.env -e 'const u=new URL(process.env.MIGRATION_DATABASE_URL); u.pathname="/email_gateway_verify"; process.stdout.write(u.toString())')
DATABASE_URL="$VERIFY_URL" MIGRATION_DATABASE_URL="$VERIFY_URL" node node_modules/prisma/build/index.js migrate deploy
# --env-file never overrides variables already set, so the verify URL wins.
DATABASE_URL="$VERIFY_URL" MIGRATION_DATABASE_URL="$VERIFY_URL" node --env-file=../../.env dist/partitioning/cli.js apply
node node_modules/prisma/build/index.js migrate diff --from-url "$VERIFY_URL" \
  --to-schema-datamodel prisma/schema.prisma --exit-code      # "No difference detected"

docker compose exec -T mysql sh -c 'MYSQL_PWD="$MYSQL_ROOT_PASSWORD" mysql -uroot -e \
  "DROP DATABASE email_gateway_verify;
   REVOKE ALL PRIVILEGES ON email_gateway_verify.* FROM \"$MYSQL_MIGRATOR_USER\"@\"%\";"'
```

The replica follows the `CREATE`, the migrations and the `DROP` through replication. Never echo `$VERIFY_URL`: it contains the migrator password.

Never edit a migration that has been applied anywhere shared. Write a new one instead.

### Upgrading from the phase-0 init migration

Phase 0 shipped `20261101000000_init` (7 tables). Step 1.1 replaced it with `20261101000000_baseline` (the full data model) instead of altering it, because nothing outside local development had applied it. A local schema created in phase 0 still records `_init`, so `pnpm db:status` reports `20261101000000_init` "not found locally" and `migrate deploy` would fail on `CREATE TABLE users`. `pnpm db:migrate` and the Compose `db-migrate` job detect this first (`dist/migrations/cli.js check`) and stop with these instructions. Reset the schema once:

```bash
pnpm db:reset:local    # prisma migrate reset (as the migrator) + db:partitions apply + db:seed
pnpm db:status         # "Database schema is up to date!"
```

This drops and recreates the tables of the gateway schema only (phase-0 data is lost), not the Docker volume; the replica follows through replication. In shared environments there is nothing to reset: they never applied `_init`.
