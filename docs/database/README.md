# Database

MySQL 8.4 is the primary transactional store, managed with Prisma ([ADR-0003](../architecture/adr/0003-prisma-orm.md), [ADR-0014](../architecture/adr/0014-mysql-data-model-partitioning-read-write-split.md)). The schema is `packages/database/prisma/schema.prisma`, and the migrations are in `packages/database/prisma/migrations/`. The design behind it is [step 1.1](../plan/steps/01-database.md).

The schema has **169 tables** in 13 modules, and **41** of them are range-partitioned by time. Steps 1.2 + 1.3 added `user_tokens` and `user_mfa_recovery_codes` and the identity/tenancy columns ([D10](../plan/steps/02-tenants-auth-rbac.md#d10-data-model-changes-one-forward-migration-wp1)); step 2.2 added `domain_recipient_addresses`, `smtp_connectors` and `smtp_connector_networks` ([§3](../plan/steps/04-smtp-gateway.md#3-data-model-one-forward-migration-wp1)); step 2.3 added `mail_destination_presets`, `stream_cursors` and the partitioned `delivery_reinjections` and `delivery_status_events`, plus per-recipient delivery tracking columns on `email_deliveries`, `email_recipients.direction` and destination-server columns on `domain_mail_servers` ([§3](../plan/steps/05-routing.md#3-data-model-one-forward-migration-mail_routing-wp1), migration `20261103090000_mail_routing`; the review fix `20261103180000_delivery_reinjection_index` adds the online index `email_deliveries (reinjection_id, received_at)`). Step 3.1 added the partitioned parse stage table `email_message_parses` (one row per message, owned by email-worker) and the nullable attachment metadata columns `part_path`, `depth`, `disposition`, `encoded_size_bytes`, `original_filename`, `flags` and `archive_info` on `email_attachments` ([§3](../plan/steps/06-mime-ingestion.md#3-data-model-one-forward-migration-mime_ingestion-wp1), migration `20261103200000_mime_ingestion`; the `email_attachments` columns are an `ALGORITHM=INSTANT` change). Step 3.2 added the reconciliation columns `redrive_count` and `last_redriven_at` and the index `(last_redriven_at)` on `message_outbox` ([§4](../plan/steps/07-rabbitmq.md#4-data-model-one-forward-migration-event_relay-wp1), migration `20261104000000_event_relay`, `ALGORITHM=INSTANT` columns; table and partition counts unchanged); its review round 1 added the unpartitioned `message_consumer_progress` (a consumer's `retrying` / `dead_lettered` record of an event it has not handled, read by the reconciler) and the index `message_outbox (event_id)` for the delivery planner's approval provenance check ([§4](../plan/steps/07-rabbitmq.md#4-data-model-one-forward-migration-event_relay-wp1), migration `20261104120000_consumer_progress`). Step 3.3 ([§3](../plan/steps/08-message-lifecycle.md#3-data-model), [ADR-0025](../architecture/adr/0025-message-lifecycle-state-machine.md)) replaced the `MessageStatus` values by the fifteen lifecycle states (backfilling the old values and a version-0 history row per message), added `lifecycle_round` and `status_reason` to `email_messages`, the actor, correlation, transition-key and occurrence columns plus the unique key `(message_id, transition_key, received_at)` to `email_message_status_history`, and the unpartitioned `api_idempotency_keys` (the api's Idempotency-Key store) (migration `20261104130000_message_lifecycle`), and made the five Postfix queue-id columns case-sensitive (`utf8mb4_bin`, migration `20261104130100_queue_id_case_sensitive`); the ALTER algorithms MySQL used are recorded in [schema-reference.md](schema-reference.md#step-33-changes-message-lifecycle). Step 4.1 ([§3](../plan/steps/09-rspamd.md#3-data-model-one-forward-migration-scan_pipeline-wp1), [ADR-0026](../architecture/adr/0026-security-scan-pipeline.md)) made `email_scans` one row per scan round (unique `(message_id, lifecycle_round, received_at)`, with `scan_verdict`, `required_engines`, `reason_codes`, `trigger_event_id`, `deadline_at` and the sweeper index `(status, deadline_at)`), turned `scan_engine_results` into engine attempts with one final row per engine (`attempt`, `is_final`, the generated `final_engine` in a unique key, a CHECK that non-final rows are failures, `EngineOutcome` + `spam`, `unknown`), added `email_messages.client_name` (Postfix XFORWARD NAME), the partitioned `email_auth_results` (SPF/DKIM/DMARC/ARC per round, 6 months, core) and the per-tenant `scan_engine_settings` (migration `20261105090000_scan_pipeline`; algorithms in [schema-reference.md](schema-reference.md#step-41-changes-scan-pipeline)). Step 4.6 ([§3](../plan/steps/14-sandbox.md#3-data-model-one-forward-migration-sandbox_engine-wp1), [ADR-0040](../architecture/adr/0040-sandbox-engine-dispatch-results-artifacts.md)) added two **unpartitioned** platform tables: `sandbox_analyses` (one content-addressed analysis of one sample: the unique nullable `dedupe_key` `<sha256>:<analysis_key>` converges concurrent dispatchers, `public_id` is the task id, `organization_id` the dispatching organization (routing only), status, verdict, reason codes, the bounded report view (codes, counts, hosts, hashes; never content), backend/isolation/versions, the sealed sample's key in the sandbox bucket and reuse/expiry times) and `sandbox_artifacts` (metadata of one sealed artifact object in the sandbox bucket: key, hashes, size, the X25519-wrapped data key (NULL after the crypto-shredding purge), key id, expiry and purge state; FK to the analysis ON DELETE RESTRICT), and extended the partitioned `sandbox_submissions` with `analysis_id` (+ index), `skip_reason`, `sandbox_reason_codes`, `settings_version` and the status value `skipped` (migration `20261107224934_sandbox_engine`, all `ALGORITHM=INSTANT` except the online `INPLACE, LOCK=NONE` index; see [schema-reference.md](schema-reference.md#step-46-changes-sandbox-engine)). ## Conventions

- **Identifiers.** Every surrogate key is `BIGINT UNSIGNED AUTO_INCREMENT` (`BigInt @db.UnsignedBigInt`). Pure join tables use a composite key, and `message_idempotency` uses `(consumer, event_id)`.
- **`public_id`.** `CHAR(36)` UUIDv7, only on externally addressed aggregates: `organizations`, `users`, `domains`, `api_keys`, `email_policies`, `webhook_subscriptions`, `quarantine_messages`, `message_identities`, `smtp_connectors` (step 2.2), `domain_mail_servers` (step 2.3; rows created before it were backfilled with MySQL `UUID()`, a v1 UUID) and `delivery_reinjections` (step 2.3; indexed but not a unique key, because a unique key of a partitioned table would have to include `received_at`; the reinjection token `dw1-<hex>` is derived from it), `url_click_events` (step 4.3; indexed) and the step 4.4 BEC tenant tables `bec_executive_profiles`, `bec_vendor_profiles`, `bec_trusted_senders`, `bec_feedback` and `bec_suppression_rules` (unique), and the step 5.1 risk profile tables `risk_scoring_profiles` and `risk_scoring_profile_versions` (unique, set by the api). REST APIs expose `public_id`, never the numeric id, so volumes and sequences do not leak.
- **Tenancy.** Every tenant-owned table has `organization_id BIGINT UNSIGNED NOT NULL`, and tenant-scoped indexes lead with it. It is nullable only on `roles`, `threat_indicators`, `yara_rules`, `audit_logs`, `login_audit_logs` and (step 4.2) `attachment_rescan_jobs` (NULL = platform-level; for a rescan job, every organization). Catalogs (plans, permissions, reputation tables, malware signatures, system settings, scan signature versions) have no `organization_id`; `malware_signatures` is platform-wide by design (step 4.2 A17: a tenant cannot add a hash that changes other tenants' verdicts), and so are the rows step 4.3 writes to `threat_indicators` (`organization_id` NULL; tenant URL lists are settings, `blockedDomains` / `allowedDomains`). The organization always comes from the authenticated context, never from a client header.
- **`bigint` serialization.** Prisma returns ids as `bigint`, and `JSON.stringify` throws on it. Internal contracts (events, S3 keys, logs) carry ids as canonical decimal strings: use `formatId`, `parseId` and `isIdString` from `@email-gateway/database` (`src/ids.ts`). Never put a raw `bigint` into a response or an event.
- **Names.** `snake_case` tables and columns (`@@map`/`@map`), and singular `PascalCase` models (`email_messages` → `EmailMessage`).
- **Time.** `DATETIME(3)` in UTC. `created_at` everywhere, and `updated_at` only on mutable rows (append-only tables have none).
- **Enums** are MySQL `ENUM`s. Values are only ever appended, except the one-time `MessageStatus` replacement of step 3.3 ([ADR-0025](../architecture/adr/0025-message-lifecycle-state-machine.md): widen, backfill, narrow); `MessageStatus` is append-only again from then on. **JSON** is only for flexible configuration and variable scan evidence.
- **Soft delete** only on `organizations`, `users`, `email_policies` and (step 2.1) `domains`; see [retention.md](retention.md).
- **Foreign keys** are real (`RESTRICT`, or `CASCADE` for owned children) between non-partitioned tables. Partitioned tables have **none**, in either direction: see [partitioning.md](partitioning.md).
- **Partitioned tables** have a composite primary key `(id, <partition column>)`, every unique key ends with the partition column, and child rows of a message copy the message's `received_at`.
- **No mail content.** Only `*_object_key VARCHAR(512)`, sizes and SHA-256 hashes. Every table has a primary key (`sql_require_primary_key=ON`).

## Workflows

```bash
pnpm db:migrate                      # history preflight, then apply pending migrations (prisma migrate deploy)
pnpm db:reset:local                  # local only: drop and recreate the schema's tables, migrate, partitions, seed
pnpm db:status                       # migration status
pnpm db:partitions -- plan           # print the partition DDL and purges, change nothing
pnpm db:partitions -- apply          # create partitions ahead, drop expired ones, run purges
pnpm db:seed                         # catalog + demo data (local, dev, CI); idempotent
pnpm db:seed -- --catalog-only       # catalog only (includes the platform organization)
pnpm db:perf                         # performance test in a throwaway schema; writes performance-report.md
pnpm db:perf -- --quarantine-entries 1000000   # + 1 M quarantine entries for one organization (Q24)
pnpm db:migrate:dev --name <change>  # local only: create and apply a new migration
pnpm db:generate                     # regenerate the Prisma client
```

`db:migrate`, `db:reset:local`, `db:partitions`, `db:seed` and `db:perf` build `@email-gateway/database` (and its workspace dependencies) first. `db:perf -- --quarantine-entries N` (step 5.3 §9.2) additionally loads N quarantine entries for the sample organization with realistic distributions (state ≈ 55 % held / 15 % released / 13 % expired / 5 % each pending approval, rejected and deleted / 2 % superseded; reason ≈ 45 % spam, 20 % bulk, 10 % phishing, 10 % policy; Zipf over 5 000 recipients and 2 000 senders; a decisive tenant policy for ≈ 30 %, Zipf over 20 policies; 1–3 recipients per message; 60 days with a diurnal curve), and Q24 runs the five quarantine search shapes (default view, recipient, sender, state, decisive policy) on them with EXPLAIN. The loader is exported as `loadQuarantineEntries(client, { organizationId, count, now, … })` and the search shapes as `quarantineSearchSteps(organizationId, sample)` (test and perf data only; the api integration test uses them for its EXPLAIN checks). Measured on 1 000 000 entries (one organization, MySQL 8.4, 2026-11-12): the recipient, sender and policy filters use their `(organization_id, <filter>, quarantined_at…)` index with a backward scan and no sort; the default view and a dominant state (`held`) use `(organization_id, quarantined_at, id)`; a rare state uses `(organization_id, status, quarantined_at, id)`; the sweeper's expiry and retention scans use `(status, expires_at)` and `(status, state_changed_at)`; every LIMIT 50 page under 3 ms. `db:partitions` accepts `--now <ISO>`, `--bootstrap-from <YYYY-MM-DD>` and `--lock-wait-timeout <seconds>` (default 5). `db:reset:local` refuses to run when `APP_ENV` is staging/production or `NODE_ENV` is production. In staging and production, `db:seed` refuses to run unless given `--catalog-only --allow-production`, and then seeds only the catalog.

In Compose, the `db-migrate` job runs the history preflight, `migrate deploy` and then `db:partitions apply` before any service starts. In Kubernetes, the `db-maintenance` CronJob runs partition maintenance daily at 01:30 UTC. CI applies the migrations to a fresh MySQL, runs maintenance twice (the second run must be a no-op), checks drift, and seeds twice to prove idempotency.

### Changing the schema

1. Edit `schema.prisma`.
2. Run `pnpm db:migrate:dev --name <short_description>` (or `--create-only` to review the SQL before applying it). This creates `prisma/migrations/<timestamp>_<name>/migration.sql`. `migrate dev` refuses to run in a non-interactive shell when it has a warning to confirm (for example "a unique constraint will be added"); then generate the SQL with `migrate diff --from-migrations prisma/migrations --to-schema-datamodel prisma/schema.prisma --shadow-database-url "$SHADOW_URL" --script` (the URL read with `node --env-file`, never echoed), save it as `prisma/migrations/<UTC timestamp>_<name>/migration.sql` and apply it with `pnpm db:migrate` (step 2.3 did this).
   `migrate dev` replays the migrations into the shadow schema `<db>_shadow` (`SHADOW_DATABASE_URL`), which `01-users.sh` creates and grants to the migrator; the migrator has no global privileges.
3. **Review the SQL.** Prisma does not model partitions or generated columns: for a partitioned table, `migrate dev` generates a plain `CREATE TABLE` or `ALTER TABLE`. Hand-edit the SQL so it keeps `PARTITION BY RANGE COLUMNS(...)`, the composite primary key and no foreign keys, and check locking on large tables. The generated columns `domains.verified_name`, `domains.live_name`, `threat_indicators.org_scope`, (step 4.1) `scan_engine_results.final_engine` and (step 7.2) `email_messages.subject_key`, `sender_domain`, `message_id_key` and `email_recipients.address_domain` are declared in `schema.prisma` as plain nullable columns marked READ-ONLY; their `GENERATED ALWAYS AS` clause lives only in the migration SQL (`20261102000000_tenant_scoped_uniques`, redefined for `verified_name` and added for `live_name` in `20261102091717_domain_onboarding`; `final_engine` in `20261105090000_scan_pipeline`; the step 7.2 search keys in `20261113212017_email_explorer_search`), and application code never writes them. CHECK constraints (step 4.1 `scan_engine_results_attempt_outcome_check`) are not introspected by Prisma either and live only in the migration SQL. Prefer additive, backwards-compatible changes (expand → migrate → contract) so old and new pods can run side by side.
4. Re-run the drift check, which must print `No difference detected`:

   ```bash
   cd packages/database
   MIGRATION_URL=$(node --env-file=../../.env -e 'process.stdout.write(process.env.MIGRATION_DATABASE_URL)')
   node --env-file=../../.env node_modules/prisma/build/index.js migrate diff \
     --from-url "$MIGRATION_URL" --to-schema-datamodel prisma/schema.prisma --exit-code
   ```

   Read `.env` with `node --env-file`, not by sourcing it in the shell: values such as `NOTIFY_SMTP_FROM="Name <addr>"` are valid for Node and Compose but break `. ../../.env` in zsh and sh. Never echo the URL: it contains the migrator password. Partitions do not appear in Prisma's introspection, so the check stays clean after `db:partitions` has split `pmax`.

5. Verify the full history on a clean schema (below), then commit the schema and the migration together. CI fails if they do not match.

#### Clean-schema verification

Before committing a migration, apply **all** migrations to a throwaway schema `email_gateway_verify`, run partition maintenance and the drift check against it, then drop it. Never use the main schema for this and never run `prisma migrate reset` on it. The migrator holds no global `CREATE` (see Accounts), so locally the schema is created and granted by root inside the MySQL container, with the password taken from the container environment and never printed:

```bash
docker compose exec -T mysql sh -c 'MYSQL_PWD="$MYSQL_ROOT_PASSWORD" mysql -uroot -e \
  "CREATE DATABASE email_gateway_verify CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
   GRANT ALL PRIVILEGES ON email_gateway_verify.* TO \"$MYSQL_MIGRATOR_USER\"@\"%\";"'

cd packages/database
VERIFY_URL=$(node --env-file=../../.env -e 'const u=new URL(process.env.MIGRATION_DATABASE_URL); u.pathname="/email_gateway_verify"; process.stdout.write(u.toString())')
DATABASE_URL="$VERIFY_URL" MIGRATION_DATABASE_URL="$VERIFY_URL" node node_modules/prisma/build/index.js migrate deploy
# --env-file never overrides variables already set, so the verify URL wins.
DATABASE_URL="$VERIFY_URL" MIGRATION_DATABASE_URL="$VERIFY_URL" node --env-file=../../.env dist/partitioning/cli.js apply
node node_modules/prisma/build/index.js migrate diff --from-url "$VERIFY_URL" \
  --to-schema-datamodel prisma/schema.prisma --exit-code      # "No difference detected"

docker compose exec -T mysql sh -c 'MYSQL_PWD="$MYSQL_ROOT_PASSWORD" mysql -uroot -e \
  "DROP DATABASE email_gateway_verify;
   REVOKE ALL PRIVILEGES ON email_gateway_verify.* FROM \"$MYSQL_MIGRATOR_USER\"@\"%\";"'
```

The replica follows the `CREATE`, the migrations and the `DROP` through replication. Never echo `$VERIFY_URL`: it contains the migrator password.

### Step 8.1 migration (`20261116224538_journaling_archiving`)

The journaling and archiving migration ([design §3](../plan/steps/23-journaling-archiving.md#3-data-model-one-forward-migration-journaling_archiving-wp1)) follows the same rules as every migration: forward only, partitioned tables altered in place, every algorithm stated.

- **Guard.** `email_archives` gains NOT NULL columns only a capture can fill, so step 0 asserts the table is empty (a temporary stored procedure that `SIGNAL`s otherwise; it had no producer before 8.1, and the perf harness uses its own schema). ### Step 8.4 migrations (`20261118060000_security_incidents`, `20261118060100_account_takeover`)

The account takeover migrations ([design §3](../plan/steps/24-account-takeover-core.md#3-data-model-two-forward-migrations-wp1), [ADR-0075](../architecture/adr/0075-security-incident-model-shared-ato-atp.md), [ADR-0070](../architecture/adr/0070-ato-account-and-event-model.md)) follow the same rules: forward only, partitioned tables altered in place, every algorithm stated.

- **Verified** on the throwaway schema `email_gateway_verify` (all 32 migrations, `db:partitions apply` 39 actions, `migrate diff --exit-code` = no difference, 151 tables, 39 partitioned; dropped afterwards) and on the main schema (`pnpm db:migrate`, `pnpm db:partitions apply`, `pnpm db:seed` twice, `pnpm db:status` up to date) on 2026-11-18 ([step 8.4 record](../plan/steps/24-account-takeover-core.md) §13 WP1).

### Step 8.6 migration (`20261120053633_journal_intake`)

The journal intake migration ([design §3](../plan/steps/27-journal-intake-and-archive-split.md#3-data-model-one-forward-migration-utc-timestamp_journal_intake-wp1), ADR-0087–0089) alters four partitioned tables in place, adds five tables and carries the grant-preserving RBAC data migration.

- **Created** with `migrate diff --from-migrations … --to-schema-datamodel … --shadow-database-url` and hand-edited: every algorithm stated, the report index added before the old one is dropped, the two `PARTITION BY` clauses and the RBAC data sections 9–12.
- **Locking.** `ADD COLUMN` and the appended `journaled` / `ingest_source` ENUM values are `ALGORITHM=INSTANT` on the partitioned `email_messages`, `email_recipients`, `email_message_status_history`, `email_archives` and `archive_capture_intents`; the new report index is `INPLACE, LOCK=NONE` (measured: 0.34 s for 100 000 rows locally; see [indexing](indexing.md#step-86-the-report-index-gains-ingest_source) for the production estimate). **Roll the api together with the migration:** the api image of step 8.5 names the dropped index with `FORCE INDEX`, so its message report routes fail until the 8.6 api (WP5) runs.
- **Partitions.** `journal_intake_messages` (6 months, core) and `archive_record_sources` (never dropped, compliance) are created with the single `pmax` partition; run `pnpm db:partitions apply` after the migration (the registry has 41 tables).
- **RBAC data, effective-permission check.** The data sections are idempotent (a re-run writes nothing) and audit-first. Before applying the migration to a database with users, export every user's effective permission set, and compare after the migration and the seed (public ids only; the file is written with mode 600; any lost permission exits 1):

  ```bash
  cd packages/database && pnpm build
  node --env-file=../../.env dist/migrations/cli.js effective-permissions export /secure/path/perms-before.json
  cd ../.. && pnpm db:migrate && pnpm db:seed && pnpm db:partitions apply
  cd packages/database
  node --env-file=../../.env dist/migrations/cli.js effective-permissions compare /secure/path/perms-before.json
  ```

  The comparison SQL (`EFFECTIVE_PERMISSIONS_SQL` in `src/migrations/effective-permissions.ts`) joins `user_roles` → `role_permissions` → `permissions` for system and custom roles alike. Expected result: no user loses a permission; organization admins of customer organizations gain `journal:read`, `journal:manage` and keep archive access through `compliance_officer`; `super_admin` holders gain `journal:*` after the seed; read-set holders gain `journal:read`. `read_only_user`, `platform_admin` and custom roles holding `archive:read` without `archive:search` keep every permission but lose archived-record **detail** at the route level (record routes move to `archive:search`, ADR-0089).

- **Plan rows of existing organizations** follow the rule above: the seed materializes `journal_intake` and the two intake limits only for the platform and demo organizations; other organizations get their rows when their plan changes or an operator sets them.
- **Verified** on the throwaway schema `email_gateway_verify` (all 36 migrations from empty, `db:partitions apply` then 0 actions on a second run, `migrate diff --exit-code` = no difference, 170 base tables including `_prisma_migrations`, 41 partitioned, `db:seed` twice: 72 permissions, 10 roles, 272 role grants, 5 plans; the RBAC data sections re-run twice after the seed: 272 grants, one audit row and one `compliance_officer` assignment for the demo admin, no duplicates; dropped and its grant revoked), then applied to the main schema (`pnpm db:migrate`, `pnpm db:seed` twice, `pnpm db:partitions apply` 2 actions then 0, `pnpm db:status` up to date with 36 migrations, drift exit 0; the replica followed) on 2026-11-20. Effective permissions on the main schema: 5 users with a role, 0 lost a permission ([step 8.6 record](../plan/steps/27-journal-intake-and-archive-split.md) §13.1).
- **Rollback** (after rolling the api, smtp-adapter, workers and portal back) is described in the migration header: drop the five tables, the added columns and restore the old report index; the additive RBAC grants stay (re-seeding the previous catalog restores `organization_admin`'s archive permissions).

### Upgrading from the phase-0 init migration

Phase 0 shipped `20261101000000_init` (7 tables). Step 1.1 replaced it with `20261101000000_baseline` (the full data model) instead of altering it, because nothing outside local development had applied it. A local schema created in phase 0 still records `_init`, so `pnpm db:status` reports `20261101000000_init` "not found locally" and `migrate deploy` would fail on `CREATE TABLE users`. `pnpm db:migrate` and the Compose `db-migrate` job detect this first (`dist/migrations/cli.js check`) and stop with these instructions. Reset the schema once:

```bash
pnpm db:reset:local    # prisma migrate reset (as the migrator) + db:partitions apply + db:seed
pnpm db:status         # "Database schema is up to date!"
```

This drops and recreates the tables of the gateway schema only (phase-0 data is lost), not the Docker volume; the replica follows through replication. In shared environments there is nothing to reset: they never applied `_init`.
