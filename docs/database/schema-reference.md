# Schema reference

All 107 tables, by module. The source of truth is `packages/database/prisma/schema.prisma` and the migrations. The design is section 3 of [the step 1.1 design](../plan/steps/01-database.md#3-data-model); steps 1.2 + 1.3 added two identity tables and the identity/tenancy columns ([D10](../plan/steps/02-tenants-auth-rbac.md#d10-data-model-changes-one-forward-migration-wp1), migration `20261102061337_identity_tenancy`); step 2.1 added the domain lifecycle, DNS-check and DKIM key-custody columns ([§3](../plan/steps/03-domain-onboarding.md#3-data-model-one-forward-migration-wp1), migration `20261102091717_domain_onboarding`, plus the data-only `20261102110046_domain_check_backfill` that schedules pre-2.1 domains for their first check); step 2.2 added the recipient allow-list and the outbound SMTP connector tables ([§3](../plan/steps/04-smtp-gateway.md#3-data-model-one-forward-migration-wp1), migration `20261102120936_smtp_gateway`); step 2.3 added the destination provider presets, the reinjection groups, the delivery status audit trail, stream cursors and the per-recipient delivery tracking columns ([§3](../plan/steps/05-routing.md#3-data-model-one-forward-migration-mail_routing-wp1), migration `20261103090000_mail_routing`); step 3.1 added the MIME parse stage table and the attachment metadata columns ([§3](../plan/steps/06-mime-ingestion.md#3-data-model-one-forward-migration-mime_ingestion-wp1), migration `20261103200000_mime_ingestion`); step 3.2 added the outbox reconciliation columns (migration `20261104000000_event_relay`) and, in its review round 1, `message_consumer_progress` and the outbox index `(event_id)` (migration `20261104120000_consumer_progress`); step 3.3 replaced `MessageStatus` by the fifteen lifecycle states, added the lifecycle columns of `email_messages` and `email_message_status_history` and the api's `api_idempotency_keys` (migration `20261104130000_message_lifecycle`), and made the five Postfix queue-id columns case-sensitive (migration `20261104130100_queue_id_case_sensitive`); see [Step 3.3 changes](#step-33-changes-message-lifecycle); step 4.1 added the scan round and engine attempt columns, `email_messages.client_name`, the partitioned `email_auth_results` and `scan_engine_settings` (migration `20261105090000_scan_pipeline`); see [Step 4.1 changes](#step-41-changes-scan-pipeline); step 4.2 evolved `malware_signatures` into the known-threat hash catalog and added `attachment_scan_results`, `sandbox_submissions` (both partitioned), `attachment_rescan_jobs` and `scan_signature_versions` (migration `20261105103406_attachment_scanning`); see [Step 4.2 changes](#step-42-changes-attachment-scanning); step 4.3 evolved `threat_indicators` into the platform URL feed and added the five partitioned URL tables `message_urls`, `url_scan_results`, `url_rewrites`, `url_dynamic_inspections` and `url_click_events` (migration `20261105214341_url_protection`); see [Step 4.3 changes](#step-43-changes-url-protection); step 4.4 added the partitioned `bec_scan_results` and the six BEC tenant tables (migration `20261106171051_bec_detection`); see [Step 4.4 changes](#step-44-changes-phishing-and-bec); step 4.5 added the partitioned `dlp_scan_results` and `dlp_evidence` and the six DLP tenant tables (migration `20261107131553_dlp_engine`); see [Step 4.5 changes](#step-45-changes-data-loss-prevention); step 4.6 added the unpartitioned `sandbox_analyses` and `sandbox_artifacts` and the sandbox engine columns of `sandbox_submissions` (migration `20261107224934_sandbox_engine`); see [Step 4.6 changes](#step-46-changes-sandbox-engine); step 5.1 added the partitioned `message_risk_scores`, the unpartitioned `risk_scoring_profiles` and `risk_scoring_profile_versions` and the profile snapshot column `email_scans.risk_profile_version_id` (migration `20261110203003_risk_scoring`); see [Step 5.2 changes](#step-52-changes-policy-engine). Diagrams are in [er-diagram.md](er-diagram.md), and index rationale in [indexing.md](indexing.md).

Legend:

- Every table has `id BIGINT UNSIGNED AUTO_INCREMENT` unless stated, and `created_at` (plus `updated_at` on mutable rows).
- **org** = `organization_id BIGINT UNSIGNED NOT NULL` with a foreign key to `organizations` (none on partitioned tables). **org?** = nullable (NULL means platform-level).
- **P** = partitioned (column, granularity); see [partitioning.md](partitioning.md). Retention tiers are in [retention.md](retention.md).
- **Owner** = the deployable that writes the table ([data ownership](../architecture/data-ownership.md)). Every service writes `message_idempotency` (through `processOnce`) and `message_outbox`.

## Step 3.3 changes (message lifecycle)

Design: [step 3.3 §3](../plan/steps/08-message-lifecycle.md#3-data-model), [ADR-0025](../architecture/adr/0025-message-lifecycle-state-machine.md).

**`MessageStatus` (the one-time enum replacement).** `email_messages.status` and `email_message_status_history.from_status` / `to_status` hold exactly `received`, `persisted`, `scanning`, `scanned`, `scan_failed`, `policy_evaluated`, `approved`, `quarantined`, `held_for_review`, `rejected`, `delivery_pending`, `delivery_retry`, `delivered`, `archived`, `expired` (default `received`). The migration widened the enum, mapped the old values (`received → persisted` with `version + 1` and a `received → persisted` history row, `delivery_queued → delivery_pending` with `status_reason = delivery_planned`, `delivered` gets `delivery_complete`, `partially_delivered → delivered` with `delivery_partial`, `failed → rejected` with `delivery_failed`, `discarded → rejected` with `discarded`; history rows renamed with the same mapping), added a version-0 `NULL → received` history row (`lifecycle_backfill`, `changed_at = received_at`) to every message without one, and then narrowed it. From now on the enum is append-only again.

**New columns.** `email_messages.lifecycle_round SMALLINT UNSIGNED NOT NULL DEFAULT 0` (+1 on rescan and release) and `status_reason VARCHAR(64) NULL` (reason code of the last applied transition). `email_message_status_history`: `lifecycle_round`, `actor_role VARCHAR(32) NOT NULL DEFAULT 'legacy'`, `actor_service VARCHAR(64) NOT NULL DEFAULT 'legacy'`, `actor_type ENUM('system','user','api_key') NOT NULL DEFAULT 'system'`, `actor_id VARCHAR(64) NULL` (operator public id), `correlation_id VARCHAR(128) NULL`, `transition_key CHAR(64) NULL` (hex SHA-256 of the transition idempotency key, [L5.3](../plan/steps/08-message-lifecycle.md#l53-transition-keys-idempotency)), `state_event_id CHAR(36) NULL` (the `mail.message.state_changed.v1` event id), `occurred_at DATETIME(3) NULL` (producer time: recorded, never compared). The unique key `(message_id, transition_key, received_at)` makes a transition idempotent per message; its name is `email_message_status_history_message_id_transition_key_recei_key` (Prisma's default, truncated to MySQL's 64-character identifier limit). Legacy rows have `NULL` keys, which never collide.

**`api_idempotency_keys`** (not partitioned, no foreign keys, owned by the api): see [Platform operations](#platform-operations-10). Purged by `db:partitions` one day after `expires_at` ([retention.md](retention.md)).

**Collations.** Five columns are `VARCHAR(32) CHARACTER SET utf8mb4 COLLATE utf8mb4_bin` (collation `utf8mb4_bin`, case-sensitive Postfix queue ids, step 3.3, [L15](../plan/steps/08-message-lifecycle.md#l15-case-sensitive-postfix-queue-ids-fix-found-in-step-32)): `email_messages.mta_queue_id`, `email_deliveries.outbound_queue_id`, `email_deliveries.dsn_queue_id`, `delivery_reinjections.queue_id`, `delivery_status_events.queue_id`; and `api_idempotency_keys.idempotency_key` is `VARCHAR(128) … utf8mb4_bin`. Every other text column keeps the table collation `utf8mb4_unicode_ci`. The character set is unchanged, so no data was converted. Prisma does not model column collation: `schema.prisma` documents it in the field comments, and `prisma migrate diff` reports no drift (checked against the main schema, a clean schema and the migration history with the shadow database).

**ALTER algorithms (MySQL 8.4.13).** Every statement names its algorithm, so MySQL refuses instead of silently choosing a slower one; the choices were tried on a throwaway schema (`email_gateway_verify`) before the migration ran:

| Migration                 | Statement                                                                                       | Algorithm              | Why                                                                               |

**Tables.** `message_risk_scores` is partitioned monthly by `received_at` (6 months, core, like `email_scans`), with the composite primary key `(id, received_at)`, no foreign keys and the unique key `(scan_id, revision, received_at)`: one row per round and revision, the backstop for the at-most-once writes of R13 (a duplicate insert through `createMany … skipDuplicates` is a no-op, tested). `risk_scoring_profiles` (one row per organization, `organization_id` unique) and `risk_scoring_profile_versions` (unique `(profile_id, version_no)`) are not partitioned: tenant configuration, deleted with the organization. The column `groups` of `message_risk_scores` is a reserved word in MySQL 8.0+: Prisma quotes it; hand-written SQL must backtick it.

**Foreign keys.** The two tenant tables follow the DLP tables: `organization_id → organizations` `ON DELETE RESTRICT` (no cascade: the organization purge deletes `message_risk_scores` by organization in batches, then the versions, then the profile row) and every user column (`updated_by_user_id`, `created_by_user_id`, `published_by_user_id`) `→ users` `ON DELETE SET NULL`. `risk_scoring_profile_versions.profile_id → risk_scoring_profiles` is `RESTRICT`. `risk_scoring_profiles.active_version_id` has **no** foreign key (it would form a cycle with `profile_id`); the api checks that it names a published version of the same organization, and the email-worker echo-checks the version's organization and status when it resolves the round's snapshot. `message_risk_scores.profile_version_id` and `email_scans.risk_profile_version_id` carry no foreign key (partitioned tables, ADR-0014).

**Immutability.** Published versions are immutable by repository discipline (updates and deletes only `WHERE status = 'draft'`), not by a trigger (§7 of the design: the migration tooling and the drift check do not model triggers). The schema test proves that a draft-only update matches nothing once a version is published.

**No content.** Engine names, outcomes, reason codes, signal ids, integers, versions and SHA-256 hashes only: no addresses, domains, URLs, subjects or file names. No TEXT/BLOB column (tested); `explanation_text` is `VARCHAR(2048)` rendered from fixed templates.

**Comments only.** `email_scans.verdict`, `risk_score` and `scoring_version` (step 1.1) get their first writer: the email-worker sets them at round completion from the revision-0 risk score (R13). No DDL.

**Algorithms** (MySQL 8.4; stated explicitly in the migration, so a rebuild would fail instead of copying silently): `email_scans` `ADD COLUMN risk_profile_version_id BIGINT UNSIGNED NULL` `ALGORITHM=INSTANT` — MySQL accepted INSTANT on the partitioned table both on the clean `email_gateway_verify` schema (where `email_scans` still had only `pmax` when the migration ran) and on the main local schema (split monthly partitions); the three new tables are created empty, `message_risk_scores` with `PARTITION BY RANGE COLUMNS(received_at)` and `pmax`; `db:partitions apply` split it into `p202611`–`p202702` and `pmax`.

Counts after the migration (main local schema and the clean `email_gateway_verify` check, 2026-11-11): 104 tables plus `_prisma_migrations`, 31 partitioned, 21 migrations applied; `prisma migrate diff --exit-code` printed `No difference detected` on both (exit 0); the replica carries 104 tables and 31 partitioned tables. No seed change, no new permission (profiles use `policy:read` / `policy:manage` / `policy:publish`).

## Step 5.2 changes (policy engine)

Design: [step 5.2 §3](../plan/steps/16-policy-engine.md#3-data-model-one-forward-migration-policy_engine-wp1), [ADR-0043](../architecture/adr/0043-policy-dsl-and-deterministic-evaluator.md), [ADR-0044](../architecture/adr/0044-policy-evaluation-placement-and-delivery-gating.md), [ADR-0045](../architecture/adr/0045-policy-action-semantics.md). Migration `20261111021501_policy_engine`.

**Enums.** `MessageAction` **appended** `reject` (an outbound/internal message refused by policy; an inbound refusal stays `discard`) and `require_approval` (held for review), used by `email_messages.final_action`, `email_recipients.final_action` and `policy_execution_logs.action` (append-only rule kept). New: `PolicyDisposition` (`allow`, `require_approval`, `quarantine`, `reject`; strictness order), `PolicyEvaluationTrigger` (`scanned`, `scan_failed`, `parse_failed`), `PolicyDecisionSource` (`tenant_rule`, `platform_default`, `floor`), `PolicyDeliveredObject` (`original`, `rewritten`, `policy_copy`, `none`). They mirror the vocabularies of `@email-gateway/policy-dsl` and the event contracts (`POLICY_*_VALUES`).

**Existing tables.** `email_policies` + `row_version` (CAS of metadata and pointer, default 1) and `updated_by_user_id` (FK `users` SET NULL). `policy_versions` + `row_version`, `dsl_version` (NULL = legacy), `references` JSON (directory public ids the definition names; `references` is a **reserved word** in MySQL: Prisma quotes it, hand-written SQL must backtick it), `has_override_rules`, `rule_count`, `created_by_user_id`, `updated_by_user_id` (FKs `users` SET NULL). The name of a policy stays unique per organization including archived (soft-deleted) policies; creating the same name again is `409 policy_name_taken`.

**Legacy retirement** (data step of the same migration): every `email_policies` row whose `active_version_id` named a version without `dsl_version` got `active_version_id = NULL`, `status = 'disabled'`; then every version without `dsl_version` became `superseded`. **Nothing was deleted.** `policy_conditions`, `policy_actions` and `policy_exceptions` keep their rows but have no reader or writer from 5.2 on (removed only by organization purge). On the main local schema this retired the one step 1.1 demo version (policy 1: `disabled`, pointer cleared; version 1: `superseded`); the seed then published and activated version 2 in `policy-dsl/1`.

**New tables** (not partitioned; tenant configuration, deleted explicitly by the organization purge, no cascade from `organizations`): `policy_settings` (one row per organization, `organization_id` unique; `generation` BIGINT UNSIGNED default 0, the per-organization serialization point every effective api change locks `FOR UPDATE` and increments; `settings` JSON + `settings_sha256`; `row_version`), `tenant_departments` (`public_id` unique, unique `(organization_id, name)`), `tenant_department_members` (`department_id` FK RESTRICT, `user_id` FK **CASCADE**: deleting a user removes its memberships; unique `(department_id, address)` and `(department_id, user_id)`, index `(organization_id, address(100))`). Every organization FK is `RESTRICT`, every actor column `SET NULL`.

**"Exactly one of address / user_id" is api-enforced only.** MySQL refuses the CHECK constraint `(address IS NULL) <> (user_id IS NULL)`: `ERROR 3823 (HY000): Column 'user_id' cannot be used in a check constraint …: needed in a foreign key constraint … referential action` (probed on MySQL 8.4.13 with the FK `ON DELETE CASCADE ON UPDATE CASCADE`; the CASCADE delete is required by the design). Recorded in the WP1 note (step 5.2 §12).

**`policy_execution_logs`** (partitioned, empty outside perf data) was **altered, not re-created**: 31 columns added (`scan_id`, `trigger`, `direction`, `disposition`, `decision_source`, `decisive_policy_public_id`, `decisive_rule_id`, `final_verdict`, `risk_score`, `override_applied`, the JSON columns `actions`, `matched_rules`, `floor`, `recommendation`, `override_detail`, `clamps`, `reason_codes`, `delivery`, `explanation`, `policy_versions`, and `delivered_object`, `object_key`, `explanation_text`, `policy_generation`, `snapshot_sha256`, `platform_default_id`, `dsl_version`, `evaluator_version`, `input_version`, `input_sha256`, `tzdata_version`), `action` widened by the appended values, three indexes `(organization_id, received_at)`, `(organization_id, disposition, received_at)`, `(organization_id, decisive_policy_public_id, received_at)`; the primary key `(id, received_at)`, the unique key `(message_id, evaluation_seq, received_at)` (= one evaluation per round) and the partitioning are unchanged. `evaluation_seq` now means the lifecycle round. `trigger` is a **reserved word** in MySQL (quote it in hand-written SQL). No TEXT/BLOB column, no content (tested). Retention 6 months, core (was 3, detail).
