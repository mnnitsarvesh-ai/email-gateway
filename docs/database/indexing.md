# Indexing

Every index in the schema exists for a documented query ([query-examples.md](query-examples.md)) or a constraint. Section 3 of [the step design](../plan/steps/01-database.md#3-data-model) lists the complete set per table. Do not add an index to a partitioned table without a documented query and a plan from `pnpm db:perf`.

## Rules

1. **Tenant-scoped indexes lead with `organization_id`.** Every tenant query filters by it, and putting it first keeps one tenant's rows together in the index, so the query never touches other tenants' entries.
2. **Write-heavy tables get the minimum.** Each secondary index costs a B-tree insert per row. On the message tables (about 1M messages and 15–20M child rows a day at target volume), every extra index is millions of random writes a day plus buffer-pool pressure. So the detail tables (`email_events`, `scan_engine_results`, `email_message_status_history`, `delivery_attempts`, `email_headers`) have only their primary key and the unique key that makes writes idempotent (`policy_execution_logs` was one of them until step 5.2 made it the core evaluation record with three tenant-scoped indexes, four since step 7.3, one row per message and round). They are always read through their message (`message_id, received_at`).
3. **Unique keys double as lookup indexes.** `(message_id, rcpt_seq, received_at)` makes recipient inserts idempotent and also serves "recipients of a message" by its `message_id` prefix.
4. **Keyset pagination needs the sort columns in the index.** `(organization_id, received_at, id)` on `email_messages` serves `ORDER BY received_at DESC, id DESC` without a filesort.
5. **Purge and job queries get an index on their predicate** (`expires_at`, `processed_at`, `(status, next_attempt_at)`), so batched deletes and pollers never scan.

## Prefix indexes

Email addresses are `VARCHAR(320)` in `utf8mb4` (up to 1,280 bytes), which is long for an index key. Five indexes use a 100-character prefix:

| Index                                                                               | Query                                                            |
| ----------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| `email_recipients (organization_id, address(100), received_at)`                     | Messages for a recipient (tracking)                              |
| `bounce_events (organization_id, recipient_address(100), occurred_at)`              | Bounce history of an address                                     |
| `quarantine_messages (organization_id, recipient_address(100), quarantined_at, id)` | Q6, Q24: end-user quarantine and the recipient filter (step 5.3) |
| `quarantine_messages (organization_id, envelope_from(100), quarantined_at)`         | Q24: the sender filter (step 5.3)                                |
| `policy_exceptions (organization_id, exception_type, match_value(100))`             | Exception matching                                               |

100 characters distinguishes practically every real address. A prefix index cannot be covering, so MySQL re-reads the row to compare the full value (the plan shows `Using where`), and columns after the prefix in the index are still used for range and equality. Unique keys never use a prefix: `delivery_suppressions (organization_id, address)` is a full-length unique key, because uniqueness on a prefix would be wrong.

## Partition pruning and secondary indexes

In a partitioned InnoDB table, **every secondary index is partitioned too** (local indexes). There is no global index. That has three consequences:

- With a predicate on the partition column, MySQL first prunes to the matching partitions and then uses the index inside each of them. Q1 reads 2 partitions out of 9, and Q2 reads 1.
- Without one, the same index is probed **in every partition**: one B-tree descent per partition. For selective predicates that return a few rows (Q7 stuck messages, Q10 hash hunt, Q8 outbox poll), this stays at well under 2 ms with 9 monthly partitions (see the [report](performance-report.md)). It grows linearly with the number of partitions, which retention keeps small.
- **Uniqueness is per partition.** That is why every unique key ends with the partition column: a unique key on `message_id` alone could not be enforced across partitions. Global uniqueness of message ids and ingestion keys is enforced by the non-partitioned registry `message_identities`.

Secondary indexes in InnoDB also carry the primary key. For partitioned tables that is `(id, received_at)`, 15 bytes. `BIGINT` keys instead of `CHAR(36)` UUIDs save about 30 bytes per entry in every secondary index ([ADR-0014](../architecture/adr/0014-mysql-data-model-partitioning-read-write-split.md)).

### Step 8.6: the report index gains `ingest_source`

Journal intake messages are registry messages (`ingest_source = 'journal_intake'`) that every gateway view excludes. The report counts (traffic, directions, outcomes, top domains, billing usage) were index-only over `email_messages_org_received_dir_verdict_idx`; the new predicate `ingest_source = 'gateway'` names a column outside that index, so MySQL would read every row of the window. The migration adds `email_messages_org_received_dir_verdict_src_idx (organization_id, received_at, direction, final_verdict, final_action, domain_id, ingest_source)` with `ALGORITHM=INPLACE, LOCK=NONE` and then drops the old index (a second online statement). The report SQL names the new index with `FORCE INDEX` (step 8.6 WP5).

EXPLAIN of the outcomes report (31 days, the largest organization of a 100 000-message `pnpm db:perf` schema, 37 354 messages, monthly partitions; MySQL 8.4, 2026-11-20):

| -------------------------------- | ------------------------------------------------- | ------ | ------------------------------------------------------------------------------------------- |

Partitions pruned to `p202610,p202611` in every plan. One more byte per index entry (the ENUM).

**Duration.** Building the new index took 0.34 s for 100 000 rows locally (the old one 0.46 s; dropping an index is metadata only, 0.02–0.03 s), about 300 000 rows/s on the development VM. In production the build is a sorted scan of every partition of `email_messages` (6 months of messages, core): at 1 M messages per day (≈ 180 M rows) expect on the order of 10–30 minutes on provisioned-IOPS storage, longer under heavy write load. `LOCK=NONE` keeps inserts and updates running; concurrent DML during the build is buffered in the online alter log (`innodb_online_alter_log_max_size`, default 128 MiB; raise it for a busy primary, otherwise the build aborts and must be re-run). Replicas apply the DDL after the primary finished (replica lag of about the same duration; the api's lag check, `DATABASE_READ_MAX_LAG_SECONDS`, sends reads to the writer meanwhile). Run it in a low-traffic window and roll the 8.6 api with it: the step 8.5 api forces the dropped index, so its message report routes fail until the new api runs.
