# Deployment: API-mode protection — the mailbox-worker (steps API-1, API-2)

API mode protects a tenant **without an MX change**: the gateway sees mail only as a copy (journal copy through the 8.6 intake, optional mailbox change feeds) and **never delivers, forwards or bounces it** (N1). The mailbox-worker records one detection copy per mailbox, deduplicates journal and feed copies, measures the lag, keeps the mailbox inventory and evaluates coverage and health. From step API-2 it also **remediates after delivery**: per copy it decides from the tenant's remediation policy (default P1) and moves the message to the gateway's hidden quarantine folder / label, Junk, Recoverable Items / Trash, tags it, or (only with `API_MODE_HARD_DELETE_ENABLED` and an explicit tenant rule) deletes it, with the consented `Mail.ReadWrite` / `gmail.modify` scopes; quarantined messages become mailbox-located quarantine entries whose release is a restore to the Inbox.

## Roles (`MAILBOX_WORKER_ROLES`, default `copies,feeds,inventory,health,remediate`)

| Role        | What it does                                                                                                                                                                                                                                                                                                                                                                      | Concurrency                                                                                                                                                               |
| ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `copies`    | Consumes `mail.message.copy_scanned.v1` from `email.mailbox` as `eg-mailbox` (ledger `mailbox-worker.copies`, retry `hold`, reconciled): per-mailbox copy rows, dedupe by Message-ID + mailbox, hybrid inline link, lag, counters (D7); step API-2: the remediation decision per recorded copy **in the same transaction** (R4)                                                   | every replica; prefetch 16                                                                                                                                                |
| `feeds`     | Every `API_MODE_FEED_TICK_MS` claims due mailboxes (`FOR UPDATE SKIP LOCKED`, lease 120 s) and runs the Graph Inbox delta (with optional change-notification subscriptions) or the Gmail history; fetches content only when no copy of the Message-ID exists for the mailbox (D10)                                                                                                | every replica; ≤ `API_MODE_FETCH_CONCURRENCY` (16) per replica, ≤ `API_MODE_FETCH_CONCURRENCY_PER_CONNECTION` (4) per connection and claim                                |
| `inventory` | Per API connection every `API_MODE_INVENTORY_INTERVAL_HOURS` or on request: users of the linked domains, aliases, disabled/deleted, the per-connection cap (D11.1)                                                                                                                                                                                                                | every replica; one connection at a time per replica (claim + lease)                                                                                                       |
| `remediate` | Step API-2 (R5): every `API_MODE_REMEDIATION_TICK_MS` claims due `api_remediation_actions` (`FOR UPDATE SKIP LOCKED`, lease `API_MODE_REMEDIATION_LEASE_SECONDS`) and executes them through the Graph / Gmail clients: state read first, locate by Message-ID, already-in-target, move / label / category / trash, mailbox quarantine entries (R9) and release completion (R10.3) | every replica; ≤ `API_MODE_REMEDIATION_CONCURRENCY` (8) per replica, ≤ `API_MODE_REMEDIATION_CONCURRENCY_PER_CONNECTION` (2) in flight per connection **across replicas** |
| `health`    | Leader `GET_LOCK('eg:mailbox:health')`, every `API_MODE_HEALTH_INTERVAL_MS`: coverage per mailbox, connection health (incl. the four `remediation.*` checks), audit + `api_mode_unhealthy` alert outbox rows, pruning (incl. remediation actions), mailbox entry expiry, feed start/stop sweeps; flushes the Redis counters every `API_MODE_COUNTER_FLUSH_SECONDS` (D11)          | one leader; the gauges are 0 on the other replicas (aggregate with `max()`)                                                                                               |

Every outbound event is an outbox row relayed by the event-relay (`mail.message.received.v1` of fetched copies, `notification.alert_requested.v1`); the worker publishes only its own retry and dead-letter hops. A role set without `feeds`, `inventory` and `remediate` holds no credential key and makes no provider call (for example a copies-only Deployment: `MAILBOX_WORKER_ROLES=copies,health`). Without `remediate` anywhere, decisions are still taken (rows stay `pending`; the backlog check and alerts report it).

## Configuration

All keys are in `.env.example` (section "API-mode protection") and `infrastructure/kubernetes/base/config.yaml`; defaults are the design's (D16). The worker also reads the shared `DATABASE_URL`, `REDIS_URL`, `S3_*`, `INGEST_HEADER_MAX_BYTES`, `PROVIDER_CREDENTIAL_ENCRYPTION_KEY` (+ `_PREVIOUS`), `PROVIDER_M365_LOGIN_URL`, `PROVIDER_M365_GRAPH_URL`, `PROVIDER_GOOGLE_TOKEN_URL`, `PROVIDER_GOOGLE_ADMIN_URL`, `PROVIDER_ALLOW_HTTP_ENDPOINTS` and `PROVIDER_M365_ALLOW_PLATFORM_SECRET`. Refused configurations name the key, never the value:

- `API_MODE_GRAPH_URL`, `API_MODE_GMAIL_URL`, `API_MODE_GOOGLE_ADMIN_URL` must be `https://graph.microsoft.com`, `https://gmail.googleapis.com`, `https://admin.googleapis.com` unless `APP_ENV` is `local`/`ci`; `http:` additionally needs `API_MODE_ALLOW_HTTP_ENDPOINTS=true` (local/ci only).
- `API_MODE_GRAPH_NOTIFICATION_URL` must be `https:` outside local/ci, without credentials, query or fragment; with it, `API_MODE_NOTIFICATION_SECRET` (≥ 32 characters) is required for the `feeds` role.
- The `feeds`, `inventory` and `remediate` roles need `PROVIDER_CREDENTIAL_ENCRYPTION_KEY`; the `copies` role needs `RABBITMQ_MAILBOX_URL`.
- Thresholds stay ordered (coverage fail ≤ warn, lag fail ≥ warn, renew-before < subscription lifetime, remediation failure fail ≥ warn, backlog fail ≥ warn, per-connection concurrency ≤ overall).

Secrets (Kubernetes, all mounted as `_FILE`): `email-gateway-secrets` keys `database-url`, `redis-url` and the new **`rabbitmq-mailbox-url`** (the `eg-mailbox` user of topology v17); **`email-gateway-api-mode-notification-secret`** key `secret` (64 hex characters, `API_MODE_NOTIFICATION_SECRET`); `email-gateway-provider-credential-key` (as the integration-worker); the optional **`email-gateway-provider-mailbox-platform`** with `m365-mailbox-cert.pem` and `m365-mailbox-cert-thumbprint` (and a Google service-account key file added by an overlay patch that also sets `PROVIDER_GOOGLE_MAILBOX_SA_KEY_PATH`, because that path is read whenever it is set). The ConfigMap holds only the platform client ids (`PROVIDER_M365_MAILBOX_APP_CLIENT_ID`, `PROVIDER_GOOGLE_MAILBOX_SA_CLIENT_ID`); a set client id whose certificate or key file is unreadable stops the worker at start (fail closed, never a silent fallback). Production uses a certificate: `PROVIDER_M365_ALLOW_PLATFORM_SECRET=false`.

## Remediation (step API-2)

**Decision (copies role, R4).** After a copy row is recorded or finalized — never for a ledger duplicate — the copy's verdict and its scan round's risk row (`message_risk_scores`, latest revision: level, hard blocks) run through the effective policy (the mailbox domain's row, else the organization's, else the platform default P1; cached 30 s per organization and keyed by `row_version`) together with the connection's `remediation_paused`, the `*.mailbox_remediation` grant, the domain's effective mode and the mailbox status. The outcome is an `api_remediation_actions` row (`INSERT IGNORE` on `action_key`): `skipped` with the reason, `simulated` (detect-only: no provider call ever), or `pending` due now; the copy's `remediation_state` follows. Hybrid copies whose verdict comes from the inline gateway message are never remediated automatically (`inline_authority`).

**Execution (remediate role, R5).** Before any provider call: action, copy, mailbox and connection must belong to one organization (else `failed integrity_mismatch`, error log); the 8.2 connection must be active and bound and the grant `active` (else `failed mailbox_access_revoked`); a paused connection sends policy actions back for 5 minutes (admin and release actions proceed); a paused provider family (the shared throttle gate) defers without counting an attempt; a policy action whose copy moved on, a reversal of an already reversed generation and a restore whose entry left `releasing` are `cancelled`; an approved restore is re-checked with `decideMailboxRestore`. The plan then reads the message state first (already in target → `succeeded already_in_target`), locates journal copies (and stale Graph ids) by Internet Message-ID (drafts and Sent Items ignored; ≤ 5 matches), and runs the provider steps. Errors: throttled (`429`, Google rate limits, `503` with `Retry-After`) → wait, `remediation_throttled`, no attempt counted; retryable (`5xx`, timeouts) → `30 s × 2^attempts` (≤ `API_MODE_REMEDIATION_BACKOFF_MAX_SECONDS`) until `API_MODE_REMEDIATION_MAX_ATTEMPTS` → `failed provider_unavailable`; `401/403` → `provider_forbidden`; `400` → `provider_rejected`; no message → locate again after `60 s × 2^(n−1)` until `API_MODE_REMEDIATION_LOCATE_ATTEMPTS` → `message_not_found`. Every outcome is one writer transaction with a CAS on the claimed `row_version` (a claim lost to a lease expiry writes nothing); `succeeded` / `failed` write the system audit row `api_mode.remediation_executed` (public ids and codes only).

**What changes in the customer's mailbox.** Microsoft 365: the folder `API_MODE_QUARANTINE_FOLDER_NAME` under the mailbox root (created hidden when `API_MODE_QUARANTINE_FOLDER_HIDDEN`, looked up with hidden folders first; its id is cached on `api_mailboxes.quarantine_container_id` and re-ensured once when it answers `404`), `junkemail`, Recoverable Items Deletions (soft delete), the category `API_MODE_TAG_NAME`, `permanentDelete` (hard delete only). Graph moves return a new id: it is stored in `provider_refs.after` and on the copy. Gmail: the label `API_MODE_GMAIL_QUARANTINE_LABEL` (hidden in the label list, still searchable by the user), `SPAM`, Trash, the label `API_MODE_TAG_NAME`; ids never change.

**Hard delete.** `API_MODE_HARD_DELETE_ENABLED` (default `false`, also read by the api) must be `true` **and** a tenant rule must say `hard_delete`; it is never in a default or preset and never manual. On Microsoft 365 it is irreversible. On Google `gmail.modify` cannot delete permanently: the action runs the Trash plan and records `hard_delete_unsupported_provider` (`provider_refs.container = deleted_items`). Turning the setting off makes the decisions of later copies `skipped hard_delete_disabled`, and a worker without the setting cancels any `pending` hard-delete row it claims (`cancelled hard_delete_disabled`) instead of executing it.

**Mailbox-located quarantine entries (R9, R10.3, R11.4).** A successful quarantine-folder, Junk or soft-delete action writes, in the same transaction, a `quarantine_messages` row with `location = mailbox` (container, copy, mailbox and action links; `lifecycle_round` = the copy's remediation generation; expiry from the organization's quarantine settings and `QUARANTINE_MAX_HOLD_DAYS` / `QUARANTINE_MAX_REVIEW_DAYS`, the same keys and values as the policy-engine) and a `quarantine_actions` row `mailbox_remediated`. Releases of such entries are `restore_inbox` actions queued by the api; the worker completes them (entry `released`, release log `restored`, copy `restored` and generation + 1) or, on a permanent failure, returns the entry to `held` (`restore_failed`). An approved restore whose reasons are no longer covered gets a new `release_approval` request (TTL `approvals.requestTtlHours`). The health leader expires due `held` / `pending_approval` mailbox entries (`expired`, pending requests `expired`, action `expire`) **without touching the mailbox** — the message stays in its container — and without a lifecycle edge or object purge.

**Data ownership.** `api_remediation_actions`: rows are inserted by the mailbox-worker (`copies`, policy decisions) and by the api (manual remediation, restores and retries; WP4), executed and completed only by the mailbox-worker `remediate` role, pruned by its health leader (terminal rows older than `API_MODE_REMEDIATION_RETENTION_DAYS`, 400, whose quarantine entry is terminal or gone). `api_remediation_policies`: written by the api only, read by the worker. Mailbox-located `quarantine_messages` rows: created, completed (restore) and expired by the mailbox-worker; the api changes their state for releases, approvals, rejects and deletes; the policy-engine never touches them (ADR-0102). Organization purge deletes actions before mailboxes and connections, policies before domains (§3.4).

**Scaling.** Throughput per tenant is bounded by the per-connection provider budget, which remediation **shares** with feeds and inventory (`mbx:rb:`), and by `API_MODE_REMEDIATION_CONCURRENCY_PER_CONNECTION` (2) in flight per connection across all replicas; add replicas for many tenants, not for one large tenant. A batch of `API_MODE_REMEDIATION_BATCH` (50) is claimed per tick; a full batch ticks again at once. The lease (`API_MODE_REMEDIATION_LEASE_SECONDS`, 120 s) is renewed while a long plan runs; an action left `in_progress` by a crash is re-claimed after it and re-reads the provider state first, so nothing is repeated. To stop remediation for one tenant, pause its connection (portal "Pause remediation"); to stop it platform-wide, remove `remediate` from `MAILBOX_WORKER_ROLES` (decisions keep queuing).

## Custody of `PROVIDER_CREDENTIAL_ENCRYPTION_KEY` (ADR-0099)

The mailbox-worker is a **decrypting holder** of 8.2's credential key, besides the integration-worker (verification) and the `ato-respond` Deployment (8.5). It decrypts only the `*.mailbox_remediation` grant of the API connection it works on, through 8.2's `ProviderGrantStore` (AES-GCM, AAD bound to organization, connection, grant and credential version), and obtains tokens through `ProviderTokenService` (in-memory LRU cache only; Microsoft: client credentials for the bound tenant, resource `graph`; Google: JWT bearer with subject = the mailbox for Gmail and = the grant's delegated administrator for the Directory). Tokens never leave process memory; nothing secret is logged, stored, put in an error, an audit row or an outbox row. Key rotation follows the 8.2 procedure (set `_PREVIOUS`, re-encrypt with the integration-worker's maintenance, then remove `_PREVIOUS`) — roll the mailbox-worker together with the integration-worker and the api.

A grant that is not `active` (revoked, error, re-consent pending) is handled at the next claim (D4): feeds stop (`feed_status = revoked`, cursors, subscription ids and client-state hashes cleared; Graph subscriptions expire at the provider and their notifications no longer match), inventory becomes `unavailable`, health reports `mailbox_access.grant`. Journal detect scanning continues (it needs no grant). Restoring the grant restarts the feeds (`pending`) at the next health sweep, without backfill.

## Egress

NetworkPolicy: MySQL (3306), Redis (6379), RabbitMQ (5671/5672), cluster DNS, OTLP (4318), and TCP 443 to **public** addresses only (S3, `graph.microsoft.com`, `gmail.googleapis.com`, `admin.googleapis.com`, `login.microsoftonline.com`, `oauth2.googleapis.com`). The provider client of `@email-gateway/idp-adapters` is the second control: it only calls the configured family origins (provider-returned links are followed only when same-origin and under the base path), never follows redirects, refuses proxy environment variables, caps response bytes and streams MIME bodies (≤ `API_MODE_MAX_MESSAGE_BYTES`, 50 MiB) straight to the mail bucket with SHA-256 and size.

S3 (IRSA role of the ServiceAccount): `s3:PutObject` on `org/*/eml/*` of the mail bucket (fetched copies, `message/rfc822`, deterministic keys so a retry overwrites) and `s3:GetObject` on `org/*/eml/*` (bounded range reads of the header block, `INGEST_HEADER_MAX_BYTES`, for the lag of journal copies). No delete, no archive bucket.

## Graph change notifications and public ingress

Notifications are optional (`feed_mode = notify`, Microsoft 365 only) and are **hints**: the Inbox delta query stays the source of truth, and without them the feed polls every `API_MODE_FEED_POLL_SECONDS` (300 s). To use them:

1. Expose the api route `POST /api/v1/provider-notifications/graph` (and `/graph/lifecycle`) publicly over **https** through the api Ingress (Graph cannot reach a private address). The route is unauthenticated by design but unprivileged (N3): it answers Graph's validation handshake, and for a notification only sets `api_mailboxes.sync_requested_at` after a constant-time client-state hash match on a stored subscription id and a tenant check; it always answers `202` with an empty body, caps the body at 256 KiB and rate-limits per client IP (`API_MODE_NOTIFICATION_RATE_PER_MINUTE`, 1 200).
2. Set `API_MODE_GRAPH_NOTIFICATION_URL` (ConfigMap, per overlay) to that public URL and create `email-gateway-api-mode-notification-secret`. The mailbox-worker derives each mailbox's client state as `HMAC-SHA256(secret, "api-mode-graph-client-state/1\0<mailbox>\0<version>")`, sends it to Graph once and stores only its SHA-256. Rotating the secret invalidates current subscriptions' client states: notifications stop matching (polling continues) until each subscription is re-created; clear `subscription_id` of the affected mailboxes (or toggle the connection's feed mode) to re-create them at once.
3. Subscriptions live `API_MODE_GRAPH_SUBSCRIPTION_MINUTES` (4 230, Graph's maximum for mail) and are renewed `API_MODE_SUBSCRIPTION_RENEW_BEFORE_MINUTES` (720) before expiry; with a live subscription the safety poll is `API_MODE_FEED_SAFETY_POLL_SECONDS` (3 600). Lifecycle events: `reauthorizationRequired` forces a renewal, `subscriptionRemoved` a re-creation, `missed` a sync.

Locally the TEST-ONLY idp-simulator (Compose profile `smtp-test`) posts notifications to `http://api:3000/api/v1/provider-notifications/graph` on the shared Compose network (`http:` is accepted only with `APP_ENV=local|ci`).

## Throttling and `Retry-After`

Every provider call takes one unit of the per-connection, per-family Redis budget first (`mbx:rb:<apiConnectionPublicId>:<family>:s<epochSecond>`, `API_MODE_GRAPH_REQUESTS_PER_SECOND` 8, `API_MODE_GMAIL_REQUESTS_PER_SECOND` 10, `API_MODE_DIRECTORY_REQUESTS_PER_SECOND` 5); a call waits ≤ 1 s for budget, then the mailbox is retried 2 s later (no failure counted). One tenant's connection can never consume another's budget (N7). A `429`, a Google rate-limit `403` or a `503` **with** `Retry-After` pauses the whole connection family for every replica: Redis `mbx:throttle:<apiConnectionPublicId>:<family>` with TTL = `Retry-After` (capped at 600 s; a longer existing pause is kept), `api_mode_connections.throttled_until`, counters `throttled_429` / `throttled_503` and `api_mode_throttled_total`. The mailbox ends `throttled` with `next_sync_at` at the end of the pause; every worker checks the pause before any call of that family. Other retryable failures back off per mailbox (`30 s × 2^(n−1)`, ≤ 1 h; `feed_status = error` from the third consecutive failure).

## Scaling

- **Replicas**: every role is safe on every replica (claims with leases, the ledger, the health leader lock). Two replicas (PDB 1) cover a restart; add replicas for many feed mailboxes. Throughput per tenant is bounded by the provider budgets, not by replicas.
- **Writer pool**: 20 connections per replica (`DATABASE_CONNECTION_LIMIT` in `src/app.module.ts`) plus one advisory-lock connection; at 2 replicas the worker uses ≤ 42 writer connections — include it in the writer budget (`max_connections` 300, 80 % budget) when raising replicas.
- **Memory**: MIME bodies are streamed (multipart upload of 5 MiB parts, queue 2) and Gmail `format=raw` is decoded by the streaming extractor; the 768 MiB limit covers 16 concurrent syncs.
- **Queue**: `email.mailbox` backlog is alerted at 10 000 ready messages (`ApiModeCopyQueueBacklog`); scale replicas or check the copies role's errors.
- **Inventory**: ≤ `API_MODE_MAX_MAILBOXES_PER_CONNECTION` (50 000) in-scope users per connection; beyond, the inventory fails `inventory_limit` without changes.

## Rollout order

1. Migration `api_mode_protection` (migration Job), `pnpm db:seed` (feature `api_mode_protection`), partitions (`api_message_copies`).
2. Topology v17 (`rabbitmq-init` / `init.mjs --users`: queue `email.mailbox`, user `eg-mailbox`), `email.mailbox` in the event-relay's `RECONCILE_QUEUES`.
3. Secrets and ConfigMap keys above; the api Ingress path for notifications if used.
4. `api`, `email-worker`, `smtp-adapter`, `archive-worker`, `integration-worker` (API-1 changes), then the `mailbox-worker`. Nothing on the mail path depends on it: while it is down, copies stay `pending` in the queue (reconciled), feeds and inventory pause, and health shows stale data.
5. Step API-2: migration 44 `api_mode_remediation`, the R17 ConfigMap keys (section "Step API-2 remediation" of `config.yaml`), the policy-engine (guards for mailbox entries) and the api before the mailbox-worker with `remediate`. A worker with the new image and the old ConfigMap uses the defaults (P1 in enforce for organizations without a policy): set a `detect_only` policy first for tenants that should start in detect-only.

Prometheus job `mailbox-worker` (`infrastructure/monitoring/prometheus.yml`); rules `infrastructure/monitoring/rules/api-mode.rules.yml` with promtool tests in `infrastructure/monitoring/tests/api-mode.rules.test.yml`: `ApiModeConnectionsFailing` (critical, 15 min), `ApiModeCoverageGaps` (6 h), `ApiModeLagHigh` (p95 > 900 s, 15 min), `ApiModeThrottlingSustained` (> 0.1/s, 30 min), `ApiModeCursorResets` (any in 1 h), `ApiModeCopyQueueBacklog` (> 10 000 ready, 15 min); step API-2: `ApiModeRemediationFailing` (> 20 % failed, 15 min, warning), `ApiModeRemediationBacklog` (> 500 pending or oldest > 1 h, 15 min, warning), `ApiModeRemediationStalled` (pending and nothing succeeded for 30 min, critical). The tenant-facing `api_mode_unhealthy` alert also fires on the four `remediation.*` checks (`failures_1h`, `backlog`, `access`, `paused`).
