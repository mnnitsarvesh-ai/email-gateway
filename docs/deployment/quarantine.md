# Quarantine deployment (step 5.3)

Design: [step 5.3](../plan/steps/17-quarantine.md) (Q2, Q13, Q19, Q20, Q22, Q23, Q27–Q29, §5); decisions [ADR-0046](../architecture/adr/0046-quarantine-store-and-per-recipient-decisions.md)–[ADR-0049](../architecture/adr/0049-policy-copy-body-edits-banners-and-url-rewrite.md). Operations: [runbook](../runbooks/quarantine.md). Policy engine roles and key custody: [policy-engine.md](policy-engine.md#step-53-roles-two-deployments-and-url-key-custody).

## What changes for operations

- Every QUARANTINE / REQUIRE_APPROVAL decision now creates **quarantine entries** (per recipient) in the policy-engine's evaluation transaction; recipient-scoped tenant rules split a message (some recipients delivered, others held or discarded).
- **Releases are re-validated** by the release executor (policy-engine role `quarantine`) on `email.quarantine` (topology v10: a work queue; `mail.policy.decided.v1` is no longer bound to it). The 3.3 operator release (`POST /api/v1/messages/{id}/release`) answers `409 quarantine_workflow_required` for held messages.
- A leader-elected **sweeper** expires entries (never releases), expires approval requests, purges objects subject to legal hold and retention, adopts messages held before 5.3, schedules digests and admin alerts and deletes old terminal rows.
- WARN rules insert a **body banner** and URL_REWRITE rules can be enforced **after the scan** in the delivered policy copy; the policy-engine signs click tokens with the current key (sign only).
- The notification-worker sends the quarantine notices (digests, approvals, blocked releases, admin alerts, sender notices).

## Rollout order

1. **Migration** `20261111204536_quarantine` (Job, `prisma migrate deploy`). The `QuarantineStatus` enum is rebuilt (widen → backfill → narrow; `quarantine_messages` is rebuilt with `ALGORITHM=COPY` for the narrowing: run it in a quiet window on large tenants); everything else is additive. See [schema-reference](../database/schema-reference.md).
2. **Topology v10 and broker users**: run `rabbitmq-init` (`infrastructure/rabbitmq/init.mjs`; it prunes the `mail.policy.decided.v1` binding of `email.quarantine`). **Drain the v9 buffer first**: `email.quarantine` was a dormant, drop-head buffer of `mail.policy.decided.v1` (firehose data only, nothing consumed it). The executor's consumer accepts only the v10 type (`mail.quarantine.release_requested.v1`, the only type bound to the queue); a left-over decided event is dead-lettered as `unknown_event_type`. Before the first quarantine-role start: `rabbitmqctl purge_queue email.quarantine -p <vhost>` (safe: no release event can exist before step 5.3 runs), or discard those dead letters afterwards.
3. **api** (quarantine routes; the download token key Secret `email-gateway-quarantine-download-key`, key `key`, 64 hex, mounted only in the api).
4. **policy-engine with both roles** (Compose: one container, `POLICY_ENGINE_ROLES=evaluate,quarantine`; Kubernetes: `policy-engine` with `evaluate` and the new `quarantine-worker` Deployment with `quarantine`, same image). The **first sweeper pass adopts every message held by 5.2** (`quarantined` / `held_for_review` without entries for their current round): entries with `origin = adopted`, recipients `quarantined`, `expires_at = max(now + 1 day, received_at + hold/review days)`; watch `quarantine_adopted_total`. Adoption runs in batches of `QUARANTINE_SWEEP_BATCH_SIZE` per pass.
5. **notification-worker** (consumes `mail.quarantine.notification_requested.v1` on the existing `email.notifications` queue and ledger).
6. **event-relay**: `RECONCILE_QUEUES` += `email.quarantine` (base manifests and Compose already carry it).

Rollback: scale the `quarantine-worker` to 0 → releases wait in `email.quarantine` (entries stay `releasing`), nothing expires or is purged, digests pause; evaluation and delivery of allowed mail continue (the evaluate role is independent). Rolling the policy-engine image back to 5.2 is **not** supported after the migration (5.2 ignores entries and would hold messages without them; re-adoption happens when 5.3 returns).

## S3 / IAM (policy-engine roles)

- Evaluate and quarantine roles (policy copies and release copies): as step 5.2 ([policy-engine.md](policy-engine.md#s3--iam)) plus `s3:HeadObject` on `org/*/rewrite/*` (a release reuses the latest round's rewritten copy only while it exists).
- Quarantine role (object purge, Q17): `s3:ListBucketVersions` on the mail bucket (prefixes `org/*/eml/`, `org/*/part/`, `org/*/rewrite/`, `org/*/policy/`), `s3:DeleteObject` and `s3:DeleteObjectVersion` on `org/*/eml/*`, `org/*/part/*`, `org/*/rewrite/*`, `org/*/policy/*`. A purge removes every version of the message's EML and of its part, rewrite and policy-copy prefixes, after checking each key is under `org/<organization>/`. MinIO locally needs nothing new.

## Kubernetes

`infrastructure/kubernetes/base/quarantine-worker.yaml` (Deployment of the policy-engine image with `POLICY_ENGINE_ROLES=quarantine`, 2 replicas + PDB, probes, metrics Service; the sweeper is leader-elected so replicas only add executor capacity), `policy-engine.yaml` (`POLICY_ENGINE_ROLES=evaluate`), the Secret keys of [policy-engine.md](policy-engine.md#step-53-roles-two-deployments-and-url-key-custody). Render with `kubectl kustomize infrastructure/kubernetes/overlays/{saas,dedicated}`.

## Monitoring

Prometheus scrapes the quarantine-worker on its metrics port like the policy-engine. Alerts `infrastructure/monitoring/rules/quarantine.rules.yml` (promtool tests `tests/quarantine.rules.test.yml`): `QuarantineReleaseExecutorStalled` (critical), `QuarantineSweeperStalled`, `QuarantinePurgeFailures`, `QuarantineApprovalBacklog`, `QuarantineNotificationFailures`, `QuarantineDownloadRefusalSpike`, `QuarantineInconsistentReads`. New policy-engine series: `quarantine_entries_created_total{origin,kind,reason,direction}`, `quarantine_entries_superseded_total`, `quarantine_releases_total{result,mode}`, `quarantine_release_duration_seconds`, `quarantine_expired_total{kind}`, `quarantine_approvals_expired_total`, `quarantine_purges_total{result}`, `quarantine_adopted_total`, `quarantine_notifications_requested_total{kind}`, `quarantine_entries_retention_deleted_total`, `quarantine_sweep_duration_seconds`, `quarantine_sweep_last_success_timestamp_seconds`, `quarantine_sweeper_leader`, gauges `quarantine_entries{state}` and `quarantine_pending_approvals` (leader only), `quarantine_settings_invalid_total`, `quarantine_inconsistent_reads_total{read}`, `policy_recipient_split_total{result}`, `policy_url_rewrite_total{result}`, `policy_body_banner_total{result}`; notification-worker `notification_quarantine_messages_total{kind,result}`.

## Local

`docker compose --profile apps up -d --wait` runs one `policy-engine` container with both roles. Existing `.env`: append the "Quarantine (step 5.3 …)" section of `.env.example`. To see notices, point the notification-worker at `mail-sink` ([policy-notifications.md](../runbooks/policy-notifications.md#local-stack)). Manual check: `curl -s localhost:3030/metrics | grep -E '^quarantine_(sweeper_leader|sweep_last_success)'`.
