# Sandbox threat model (step 4.6)

Status: **reviewed design baseline (2026-11-08), written before any sandbox code; implemented controls verified locally on 2026-11-09 — see [step 4.6 §13](../plan/steps/14-sandbox.md#13-verification-results).** Verified there: the controller's forbidden-key refusal and least privilege (broker and MinIO), `disabled`/`static` end to end through the stack, the factory-wired `hardened-container` runner's escape-resistance and cleanup suites and the killed-controller recovery (local Docker Desktop only), result forgery rejection, sealed samples and artifacts. **Not verified / not implemented:** any VM-class isolation (the `vm` runner does not exist; gVisor/Kata/Firecracker cannot run on this workstation), AppArmor (unavailable on Docker Desktop), production network policies (Kubernetes manifests rendered only), the organization purge of sandbox rows (R7). Execution of unknown files remains disabled. Owner: principal architect. Decision records: [ADR-0039](../architecture/adr/0039-sandbox-security-boundary-and-backends.md) (the sandbox-controller boundary and the isolation backends) and [ADR-0040](../architecture/adr/0040-sandbox-engine-dispatch-results-artifacts.md) (the asynchronous sandbox engine, dispatch, results, verdicts, artifacts). Design: [step 4.6](../plan/steps/14-sandbox.md).

**Execution of unknown files is disabled.** Every environment runs the `disabled` backend by default; production may run `disabled` or `static` (no execution) only. The only backend that executes anything (`hardened-container`) is a local/CI test harness that is **not a VM boundary** and is refused by the production configuration. The `vm` backend (Firecracker / gVisor / Kata through a Kubernetes RuntimeClass) is a contract that refuses to start until the preconditions of §8 are proven; its runner is not implemented in step 4.6. Nothing in this document is a claim that unknown files can be executed safely today.

This document must be updated (and re-reviewed) before any change that widens what is executed, where it runs, what it can reach or who can read its output.

## 1. Scope and system summary

The sandbox analyses attachments that the attachment engine (step 4.2) classified `suspicious` or `unknown`. The path:

1. **email-worker attachment engine** (trusted, holds tenant data) writes a `sandbox_submissions` row and a `mail.attachment.sandbox_requested.v1` outbox event (unchanged since 4.2).
2. **email-worker sandbox dispatcher** (trusted) consumes it from `scan.sandbox.submissions`, checks the tenant's opt-in, type and size limits, suppresses duplicates by content hash, **copies the sample, encrypted, into the restricted sandbox bucket** and writes a `mail.sandbox.task_requested.v1` outbox event.
3. **sandbox-controller** (the boundary; semi-trusted) consumes the task from `scan.sandbox`, fetches and decrypts the sample, drives one disposable runner through the configured isolation backend, collects observations, seals artifacts and publishes `mail.sandbox.task_completed.v1` directly (publisher confirms).
4. **email-worker results consumer** (trusted) validates the result against the analysis row and its one-time result token, writes the analysis, the per-submission verdicts and the round's `sandbox` engine result, and emits `mail.attachment.sandbox_completed.v1`.

```
 tenant data zone (trusted)              sandbox zone (semi-trusted)            detonation zone (hostile)
 ┌───────────────────────────┐   task    ┌──────────────────────────┐  spec   ┌──────────────────────────┐
 │ email-worker              │──────────▶│ sandbox-controller       │────────▶│ runner (disposable)      │
 │  attachment engine        │ scan.     │  no DB / Redis / tenant  │         │  sample bytes, scratch   │
 │  sandbox dispatcher       │ sandbox   │  S3; own broker user;    │◀────────│  tmpfs, no route except  │
 │  results consumer, sweeper│◀──────────│  sandbox bucket only     │ report  │  the recording sinkhole  │
 │ MySQL, Redis, tenant S3   │ results   │  (samples/ read,         │         └──────────────────────────┘
 └───────────────────────────┘           │   artifacts/ write)      │                │ DNS / HTTP
                                          └──────────────────────────┘         ┌──────▼───────────┐
                                                                               │ sandbox-sinkhole │ (records)
                                                                               └──────────────────┘
```

In scope: the task and result messages, the sample bytes, the artifacts, the controller, the runner host (Docker daemon locally, Kubernetes node in production), the kernel / hypervisor, the networks, the cloud metadata service, the broker, S3, and the tenants. Out of scope: the security of the attachment engine and the scan pipeline themselves (steps 4.1/4.2 threat notes), the click and URL browser paths (ADR-0032), and the portal.

## 3. Adversaries

| #   | Adversary                                                              | Capabilities and goals                                                                                                                                                                                                                                                                                     |
| --- | ---------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| T1  | **Malware author** (sends the attachment)                              | Full control of the sample bytes, file type tricks, parser exploits against our static analyzers, kernel / container / hypervisor exploits when executed, fork/memory/disk bombs, long sleeps, network beacons, data exfiltration, attempts to reach metadata, internal services and the broker.           |
| T2  | **Sandbox-aware / evasive sample**                                     | Detects the sandbox (no user, short uptime, container cgroups, gVisor/Kata fingerprints, sinkholed DNS, missing internet, timing) and behaves benignly; delays execution beyond the timeout; behaves differently on a second run; tampers with in-runner collection output. Goal: a benign-looking report. |
| T3  | **Tenant (authenticated customer or its admin)**                       | Can send arbitrary attachments through its own domains, change its own sandbox settings within bounds, read its own scan results. Goals: learn about other tenants' files (cross-tenant dedup signal, artifacts), exhaust the shared sandbox capacity, disable or weaken the sandbox for others.           |
| T4  | **Compromised controller** (after a runner escape or a controller bug) | Everything the controller process can do: its broker user, its sandbox S3 user, the sample key, the artifact public key, its network position, and (local only) the Docker socket. Goals: forge verdicts, reach tenant data, persist.                                                                      |
| T5  | **Network attacker / external peer**                                   | Responds to the sample's network traffic if it ever leaves the sinkhole; can serve second-stage payloads.                                                                                                                                                                                                  |
| T6  | **Insider / operator error**                                           | Enables an execution backend in production, mounts the Docker socket, attaches the runner network to a routed network, downloads a sample and opens it, publishes a misconfigured bucket.                                                                                                                  |

## 4. Attack surface and threats

### 4.1 Task messages (`scan.sandbox`)

| Threat                                                                                      | Mitigation                                                                                                                                                                                                                                                                                                                                                             |
| ------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Forged or malformed task (path traversal in the sample key, oversized limits, other bucket) | Strict zod schema (`mail.sandbox.task_requested.v1`, strict object, bounded); sample key must match `samples/<yyyy>/<mm>/<taskId>.bin`; limits clamped to the controller's own maxima; the controller's S3 user can read only `samples/` in one bucket. Only the relay (outbox) publishes `org.*` task keys (topic permissions).                                       |
| Replayed task (redelivery, operator replay)                                                 | Results are deduplicated downstream by analysis id, status and the one-time result token; a duplicate run costs capacity only, and writes its artifacts under a new run id (`artifacts/…/<taskId>/<runId>/…`), so it never overwrites the objects an applied result's rows describe. Runner names are deterministic per task attempt and the reaper removes leftovers. |
| Task flood (T3 sends many suspicious attachments)                                           | Per-message cap (`ATTACHMENT_SANDBOX_MAX_PER_MESSAGE`), tenant opt-in, per-tenant size/type bounds, cross-tenant dedup by SHA-256, `scan.sandbox` is a bounded lossy queue (10 000, drop-head) whose dropped tasks expire to `timeout` (never `clean`), controller concurrency 1–4. The mail round never waits.                                                        |

### 4.2 Sample bytes

| Threat                                                    | Mitigation                                                                                                                                                                                                                                                                                                                                                                                                |
| --------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Parser exploit in the static analyzers (T1)               | Analyzers are our own bounded TypeScript parsers (no native parsers, no shelling out), run in a **child process** with an empty environment, the Node permission model (read only its scratch, write only its output, no child processes, no workers, no addons), heap/RSS/CPU/wall limits, inside the locked-down controller container. A crash or kill is an analysis failure (`error`), never `clean`. |
| Accidental execution outside a runner                     | The controller never writes the sample with an executable bit, never passes it to a shell, and the `static` backend has no code path that executes; a test proves a self-replicating benign probe script is not executed by `static` (no marker file, no sinkhole query). Samples at rest are encrypted (`sandbox-sample/1`), so an operator cannot open one by accident.                                 |
| Integrity: a different object than the one scanned        | The plaintext SHA-256 is compared with the task's `sampleSha256` after decryption; AES-GCM with AAD bound to task id and hash.                                                                                                                                                                                                                                                                            |
| Confidentiality of tenant documents in the sandbox bucket | Envelope encryption under `SANDBOX_SAMPLE_KEY` (held by the email-worker and the controller only); samples deleted after the analysis (immediately, plus a sweeper and a bucket lifecycle backstop ≤ 48 h).                                                                                                                                                                                               |

### 4.3 Artifacts

| Threat                                                                                  | Mitigation                                                                                                                                                                                                                                                                        |
| --------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Artifacts are attacker-controlled bytes (malicious PNG, log injection, dropped malware) | Bounded counts (≤ 16) and sizes (≤ 2 MiB each, ≤ 8 MiB total); stored only as sealed objects, never parsed by trusted services; never rendered by the api in 4.6 (metadata only); kinds and content types from a closed enum; log artifacts are treated as untrusted text.        |
| A compromised controller reads earlier artifacts (T4)                                   | Artifacts are sealed with a fresh data key **wrapped to an X25519 public key** (`sandbox-artifact/1`): the controller can seal but cannot open. Its S3 user can write `artifacts/` and cannot read or list it.                                                                    |
| Artifact leak through the bucket                                                        | Sealed objects are useless without the private key and the wrapped key, which lives only in the committed `sandbox_artifacts` row (crypto-shredding: purge = null the wrapped key, then delete the object). Retention 1–180 days (default 30), sweeper plus a lifecycle backstop. |
| Cross-tenant disclosure via dedup (T3)                                                  | Analyses are content-addressed: a tenant can only be linked to an analysis of a file it submitted itself (identical bytes). The tenant API never shows whether an analysis was reused, nor analysis timings; times are rounded; artifacts are metadata-only in 4.6.               |

### 4.4 The runner host, kernel and hypervisor

| Threat                                                           | Mitigation                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Container escape through a shared-kernel exploit (T1)            | **This is why execution is disabled in production.** A container shares the host kernel; seccomp, capabilities and namespaces reduce but do not remove kernel attack surface. Production execution requires a VM-class backend (§8). The local `hardened-container` runner is labelled _not a VM boundary_, opt-in in `APP_ENV=local                                                                                                                                                       | ci`only, and refused when`APP_ENV` is anything else or when running in Kubernetes. |
| Privilege inside the runner                                      | Non-root user (65532), `cap_drop: ALL`, `no-new-privileges`, Docker's default seccomp profile (verified active: `Seccomp: 2`), AppArmor `docker-default` where the host has AppArmor (Docker Desktop's VM has none: recorded in readiness details), read-only root filesystem, no devices, no host mounts, no Docker socket, `ipc: private`, `pid: private`, no privileged mode — every field asserted before create **and re-verified by inspecting the created container** before start. |
| Resource exhaustion (fork, memory, disk, CPU bombs)              | `pids_limit` 128, memory 512 MiB (browser 1 GiB) with swap = memory, `cpus` 1, tmpfs scratch 64 MiB `noexec`-free but size-capped, wall timeout (default 60 s) after which the runner is killed and **force-removed**; per-controller concurrency cap. Limit hits are recorded as findings (a property of the file).                                                                                                                                                                       |
| The Docker socket as a privilege path (T4, local only)           | Only the local/CI `hardened-container` mode mounts it (a separate Compose override file, never the main file, never Kubernetes). Residual: a compromised controller in that mode controls the Docker VM (accepted for local/CI only, §7 R3).                                                                                                                                                                                                                                               |
| Leftover runners or scratch (crash, timeout, controller restart) | `finally` cleanup per task; a **reaper** at startup (removes every runner labelled with this controller's name) and on a timer (removes runners past their expiry label and scratch older than the task budget); cleanup failures are metered and alerted (critical). Tests prove nothing is left after success, failure, timeout and a killed controller.                                                                                                                                 |

### 4.5 The network

| Threat                                                                                    | Mitigation                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| ----------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Runner reaches internal services (MySQL, Redis, RabbitMQ, MinIO, the api, the controller) | Runners sit on `sandbox-detonation`, an **internal** network whose only other member is the sinkhole; no route to any other network; DNS answers come only from the sinkhole (every name → the sinkhole address). Escape tests try each service by name and address (container names, `host.docker.internal`, the published host ports, RFC 1918 and CGNAT samples) and must fail. Production: VM backend pods in a dedicated namespace with a deny-all NetworkPolicy except the sinkhole. |
| Runner reaches cloud metadata (A4)                                                        | No route on the internal network; the escape suite connects to `169.254.169.254:80`, `[fd00:ec2::254]:80` and `metadata.google.internal` (→ sinkhole, never the real service) and must fail. Production: NetworkPolicy denies `169.254.0.0/16` and `fd00:ec2::/32` for both the controller and the runners; IMDSv2 with hop limit 1 on nodes (deployment doc).                                                                                                                             |
| Exfiltration / second-stage download (T5)                                                 | No Internet route at all: the sinkhole answers DNS and HTTP locally and records indicators (names, hosts, methods, path hashes, TLS SNI); it never forwards. Direct-IP connections fail and are recorded from the runner's `connect()` trace.                                                                                                                                                                                                                                              |
| Controller reaches tenant data                                                            | The controller sits on `sandbox-control` (internal: only RabbitMQ, MinIO and the sinkhole admin endpoint); its configuration refuses to start if any database, Redis, main S3, token, DLP, DKIM or other broker credential is present in its environment.                                                                                                                                                                                                                                  |
| Sinkhole admin endpoint abused from a runner                                              | It binds only to the sinkhole's `sandbox-control` address and requires a bearer token the runners never see.                                                                                                                                                                                                                                                                                                                                                                               |

### 4.6 The broker

| Threat                                                          | Mitigation                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| --------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A leaked controller credential (T4) publishes forged results    | The `eg-sandbox` user may read only `scan.sandbox` and publish only `org.<id>.mail.sandbox.task_completed.v1` plus its own queue's retry/dead-letter hops; it configures nothing. The results consumer accepts a result only for an analysis in `dispatched` state whose id, organization and SHA-256 match and whose MAC verifies: HMAC over the **whole** result body and the organization, keyed to the task's **one-time result token** (random 256 bits per task, sealed in the task under a subkey of `SANDBOX_RESULT_KEY`, stored only as a SHA-256). The `eg-sandbox` credential alone signs nothing; the result key plus the tasks the controller actually received is needed, and a body modified by any other publisher (for example a user with `org.*` publish rights on `email.security`) fails the MAC. Anything else is dropped and metered (`SandboxResultsRejected`). |
| A compromised controller lies about a sample it really analysed | Residual (§7 R2): the verdict of that one task can be forged by whoever controls the controller. The verdict never approves mail by itself (the round does not wait; policy 5.x treats sandbox verdicts as evidence), `clean` is unreachable without the VM backend, and a forged `malicious` can only add a hash to the catalog when `SANDBOX_PUBLISH_HASHES` is on (default off).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| Queue exhaustion                                                | Bounded lossy `scan.sandbox`; work-policy `scan.sandbox.results` (reject-publish, the controller retries with confirms).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |

### 4.7 S3

| Threat                          | Mitigation                                                                                                                                                                                                                                                                                                            |
| ------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Controller reads tenant objects | A dedicated bucket (`S3_BUCKET_SANDBOX`) and a dedicated user (`eg-sandbox-controller`): `GetObject` on `samples/*`, `PutObject` on `artifacts/*`, nothing else (no list, no delete, no other bucket). An integration test proves the user cannot read the mail bucket, list the sandbox bucket or read `artifacts/`. |
| Anonymous or public access      | Anonymous access off; production bucket TLS-only, SSE-KMS, Block Public Access (deployment doc).                                                                                                                                                                                                                      |
| S3 outage                       | Transient: the dispatcher and the controller retry with backoff within their budgets; beyond them the task ends `failed` (`storage_unavailable`) or expires (`timeout`), never `clean`.                                                                                                                               |

### 4.8 Tenants

| Threat                                              | Mitigation                                                                                                                                                                                                                         |
| --------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Tenant weakens the sandbox for others               | Tenant settings change only the tenant's own submissions; bounded overrides (opt-in, file types ⊆ platform list, size ≤ platform maximum, browser analysis only if the platform allows it). The backend is platform configuration. |
| Tenant reads another tenant's results               | Read API scoped by the authenticated organization; a tenant sees analyses only through its own submissions.                                                                                                                        |
| Tenant uses the sandbox as a free execution service | No execution in production; opt-in requires the plan feature `attachment_sandbox`; per-message caps; dedup.                                                                                                                        |

## 5. Escape paths and mitigations (summary)

| Escape path                             | Primary control                                                                         | Verified by                                                                                               |
| --------------------------------------- | --------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| Kernel exploit from a container         | **Not mitigated by containers** → execution disabled in production; VM backend required | Config refusal tests; VM preflight refusal test                                                           |
| Privilege escalation inside the runner  | non-root, cap-drop ALL, no-new-privileges, seccomp, read-only rootfs                    | Escape suite: `CapEff=0`, `NoNewPrivs=1`, `Seccomp=2`, writes outside scratch fail                        |
| Docker socket / host mounts             | Never mounted into runners; spec assertion + post-create inspection                     | Escape suite: no socket, no host paths                                                                    |
| Network to internal services / metadata | Internal detonation network, sinkhole DNS                                               | Escape suite: MySQL, RabbitMQ, Redis, MinIO, metadata, host ports unreachable                             |
| Resource exhaustion of the host         | pids / memory / CPU / tmpfs / wall limits, concurrency cap                              | Escape suite: fork bomb, memory bomb, CPU burner, disk fill, long sleep                                   |
| Persistence after the task              | Forced removal, reaper on startup and timer                                             | Cleanup tests: zero labelled containers and empty scratch after every path, including a killed controller |
| Parser exploit in static analysis       | Isolated, limited child process; no execution                                           | Static non-execution test; analyzer kill tests                                                            |
| Controller compromise → tenant data     | No credentials, no route                                                                | Config refusal tests; S3 policy test; network test                                                        |

## 6. Evasion (T2) and what it means for verdicts

- The local runner and gVisor are fingerprintable; a sample that detects them will look benign. Therefore **no backend in 4.6 can produce `clean`**: `static` without findings and every non-VM execution without findings map to `unknown` (`sandbox.no_findings`, `sandbox.not_vm_isolated`). `clean` (rule C1 of `sandbox-map/1`) requires `isolation = vm`, a complete run of at least the minimum runtime, no findings and no evasion indicators — unreachable until a verified VM backend exists.
- Long sleeps: the wall timeout ends the run; the report records `limit.wall_timeout` and the verdict stays `unknown` unless other findings exist.
- In-runner collection (process trace, dropped files) can be tampered with by the sample itself in the local runner (same uid). Its output is evidence for analysts, never a reason for `clean`. The VM backend must collect from outside the guest (§8).

| R7  | The organization purge job does not exist yet (deferred platform-wide); sandbox artifacts of a deleted tenant age out by retention (≤ 180 days, default 30). | Documented in data-ownership; the purge job must crypto-shred `sandbox_artifacts` of the tenant's analyses.                                  |

## 8. Preconditions for enabling execution of unknown files in production

All of the following must be true, verified and recorded (in the step record and the change ticket) before any execution backend is enabled outside local/CI. The controller enforces the first five mechanically; the rest are operational gates.

1. **VM-class isolation proven at startup and continuously:** the `vm` backend runs inside Kubernetes, the configured RuntimeClass exists, its handler is in the allow-list (`runsc` for gVisor, `kata*` / `kata-fc` for Kata / Firecracker), and a self-test pod under that RuntimeClass proves it is not on the node's kernel (gVisor: `/proc/version` names gVisor; Kata/Firecracker: guest kernel version differs from `node.status.nodeInfo.kernelVersion`) and cannot reach the metadata address, the node IP or the cluster DNS. Readiness fails when the self-test fails; the controller refuses to start when the preflight fails.
2. **A VM runner that collects from outside the guest** (process and network telemetry from the host side or a trusted agent that the sample cannot modify) — not implemented in step 4.6.
3. **Dedicated, tainted node pool** for runner pods (no other workloads), nodes without instance-role credentials useful beyond the pool, IMDSv2 with hop limit 1, metadata blocked by NetworkPolicy and by node firewall.
4. **Network:** runner namespace default-deny; only the recording sinkhole reachable; no egress to the Internet unless a separate, reviewed "controlled Internet" design is approved.
5. **The controller's Kubernetes identity** may only create/get/delete pods in the runner namespace with the fixed security context (admission policy enforcing RuntimeClass, non-root, no host namespaces, no volumes except an `emptyDir` with `sizeLimit`); no secrets in that namespace.
6. **Escape-resistance suite** (this repository's suite, extended for the VM runner) green against the production configuration in a staging cluster, plus an external penetration test of the runner pool.
7. **Monitoring and response:** `SandboxCleanupFailures`, `SandboxBackendNotReady`, `SandboxResultsRejected` alerts routed to on-call; a runbook for "suspected escape" (cordon and drain the pool, rotate the controller's credentials and `SANDBOX_SAMPLE_KEY`, preserve the node for forensics).
8. **Update cadence:** gVisor/Kata/Firecracker and node kernels patched on a documented cadence; the runner image rebuilt weekly.
9. **This threat model re-reviewed** with the VM design, and the ADR that enables execution accepted.

Until then: production configuration `SANDBOX_BACKEND ∈ {disabled, static}`; `hardened-container` is refused; `vm` refuses at preflight.

## 9. Test obligations derived from this model

- Configuration: production refuses `hardened-container`; any forbidden credential in the controller environment refuses start; `vm` refuses on this host (`not_in_kubernetes`) and in unit tests for each failed proof.
- Escape-resistance (against the enabled local runner): metadata, internal network, MySQL, RabbitMQ, Redis, MinIO and host ports unreachable; writes outside scratch fail; capabilities empty, no-new-privileges and seccomp active; pids, memory and CPU limits hold; the wall timeout kills; nothing is left behind.
- Static backend: never executes (benign self-marking probe), analyzer isolation (empty environment, no child processes, no writes outside its output).
- Broker/S3 least privilege: the controller user cannot read other queues or publish other keys; the sandbox S3 user cannot read the mail bucket, list the sandbox bucket or read artifacts.
- Results: forged results (unknown task, wrong token, wrong organization, wrong hash, already terminal) are rejected; duplicates are idempotent.
- Only synthetic benign samples written for the tests and the EICAR test string are used. **No real malware is downloaded or stored.**
