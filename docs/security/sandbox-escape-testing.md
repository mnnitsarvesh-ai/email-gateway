# Sandbox escape-resistance testing (step 4.6 §9.3)

Status: **procedure and local results, 2026-11-08 (WP4).** Design: [step 4.6](../plan/steps/14-sandbox.md) X5, X6, X8, §9.3. Threat model: [sandbox-threat-model.md](sandbox-threat-model.md) (§4.4, §4.5, §5, §7, §9). Decision record: [ADR-0039](../architecture/adr/0039-sandbox-security-boundary-and-backends.md).

## 1. What the runner is — and is not

The `hardened-container` backend of the sandbox-controller runs one **disposable, hardened, shared-kernel Docker container** per task. It is a **local/CI test harness and NOT A VM BOUNDARY**: the sample shares the Docker VM's kernel, so one kernel or runtime bug is enough to escape (threat model §4.4). The suite below proves that the container restrictions are in force on this Docker host; it does **not** prove that unknown files can be executed safely, and nothing in it relaxes the production rule: production runs `disabled` or `static` only, and real detonation needs a verified VM-class backend (threat model §8). Only synthetic benign probes written for these tests and the EICAR test string (assembled at run time) are ever executed. No real malware is downloaded, stored or run.

## 2. How to run the suite

Prerequisites: Docker Desktop (or a Linux Docker host), the infrastructure stack up (`mysql`, `mysql-replica`, `rabbitmq`, `redis`, `minio` are probed), the local `.env` (the suite reads `SANDBOX_SINKHOLE_ADMIN_TOKEN` and friends, never prints them), and the two runner images, built **one at a time**:

```bash
docker build -f infrastructure/docker/sandbox-runner.Dockerfile -t email-gateway/sandbox-runner:local .
docker build -f infrastructure/docker/url-browser-worker.Dockerfile -t email-gateway/url-browser-worker:local .
```

Run (host-run; each file starts the sinkhole with `docker compose -f docker-compose.yml -f infrastructure/sandbox/compose.exec.yml --profile sandbox up -d --no-deps --wait sandbox-sinkhole`, which also creates the detonation network, and stops it afterwards):

```bash
pnpm --filter @email-gateway/sandbox-controller exec vitest run --config vitest.integration.config.ts integration/runner
```

The Docker socket is `SANDBOX_DOCKER_SOCKET` when it exists, else `/var/run/docker.sock`, else `~/.docker/run/docker.sock`. The `sandbox-control` network is internal and not routable from a macOS host, so the suite reaches the sinkhole admin API by relaying each request through the sinkhole container (`docker exec … node` fetch to its own control address; the bearer header travels on stdin, never on a command line). Never run it together with the analytics or observability profiles.

Unit tests (no Docker): `pnpm --filter @email-gateway/sandbox-controller test` (includes `node --test` of `infrastructure/sandbox/**/*.test.mjs`) and `pnpm --filter @email-gateway/url-browser-worker test`.

## 5. Findings and residual risks

- **F1 (fixed in the exec override): the Docker VM was reachable on the detonation bridge.** Docker 29 assigns an internal bridge network an address on the VM side (here `172.31.253.128`). From a runner, TCP **111** on that address **answered** (a listener of the Docker Desktop VM; every other scanned port refused). `infrastructure/sandbox/compose.exec.yml` now sets `com.docker.network.bridge.gateway_mode_ipv4: isolated` on `sandbox-detonation` (verified: no IPAM gateway, nothing answers on `.1`/`.128`/`.254`), and the backend's self-test refuses (`spec_not_enforced`, `network_gateway_reachable`) a detonation network without it. An existing detonation network created without the option must be removed once (`docker network rm email-gateway_sandbox-detonation`; Compose recreates it).
- **Shared kernel (threat model §4.4, R3/R4).** A kernel or runc escape bypasses every control above; Docker Desktop has no AppArmor. This is why the runner is local/CI only and why production execution requires the VM-class backend and the threat model's §8 gates.
- **Docker socket in the controller (R3).** The exec override mounts `/var/run/docker.sock` into the controller (with group 0 for the socket); a controller compromise there controls the Docker VM. Local/CI only; the main Compose file and Kubernetes never mount it.
- **In-runner evidence can be tampered with (§6 of the threat model).** The trace, the dropped-file list and the report are produced in the runner with the sample's uid (the crash/freeze probes kill or stop the bootstrap). They are parsed strictly and are evidence only; they can never make a run `clean`.
- **Indicators are best effort (R5).** DNS/HTTP/TLS are recorded by the sinkhole; direct-IP attempts only by the in-runner `connect()` trace (raw protocols to sinkholed names are seen as a TCP connect only). A `connect()` that completed (only possible to a peer on the detonation network, i.e. the sinkhole) is reported with outcome `sinkhole`.
- **Runner-to-runner traffic.** With concurrency > 1, runners share the detonation bridge and could reach each other (inter-container traffic is needed to reach the sinkhole). Local concurrency is 1 (`SANDBOX_CONCURRENCY`).
- **`/dev/shm`** (64 MiB, private IPC) is writable by the sample; its pages are charged to the runner's memory cgroup and it vanishes with the container.
- **Browser runners** run Chromium with `chromiumSandbox: false` (no unprivileged user namespaces under the default seccomp profile) and rely on the container controls; the url-browser-worker image carries more software (Debian, Chromium) than the script runner.
