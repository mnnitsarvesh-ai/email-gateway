# Security baseline

This document lists the controls in place from Phase 0. A full threat model (STRIDE across the mail path, portal and tenant boundaries) is a dedicated follow-up task. Component threat models: the **[sandbox threat model](sandbox-threat-model.md)** (step 4.6: the sandbox-controller boundary, isolation backends, residual risks and the production preconditions for executing unknown files — execution is disabled) with its [escape-testing procedure and results](sandbox-escape-testing.md).

## Secrets

- No credentials in the repository. `.env` is git-ignored. `.env.example` contains only placeholders (`__GENERATE__`).
- `pnpm env:init` generates random 192-bit secrets locally and writes `.env` with mode 600.
- Clusters use AWS Secrets Manager → External Secrets → file mounts, read through `<KEY>_FILE`.
- Config errors name keys, never values. The logger redacts `password`, `secret`, `token`, `authorization`, `cookie`, `accessToken`, `refreshToken`, `mfaToken`, `recoveryCode`, `recoveryCodes`, `code`, `newPassword`, `currentPassword`, `key`, `apiKey` and `otpauthUri` fields (top level and one level down) and the `X-API-Key` header. Request bodies are never logged.
- Application secrets `AUTH_JWT_SECRET`, `AUTH_TOKEN_PEPPER` and `DATA_ENCRYPTION_KEY` (and the optional `*_PREVIOUS*` rotation keys) are generated by `pnpm env:init` and mounted as files in clusters; since step 6.1 also `API_CURSOR_KEY` (api only, its own Kubernetes Secret).

## Least privilege

- Separate DB accounts for runtime (DML) and migrations (DDL). The integration tests check this.
- Redis requires a password. RabbitMQ's default `guest` user is limited to loopback.
- MinIO and S3 buckets deny anonymous access. Production buckets are TLS-only with SSE-KMS (Terraform module).
- Containers run as non-root (`node` user). Kubernetes pods use the `restricted` Pod Security level, a read-only root filesystem, all capabilities dropped and no service-account token.
- Local ports bind to `127.0.0.1` only.

## Authentication and authorization

Details, parameters and procedures: [authentication.md](authentication.md). Decision record: [ADR-0016](../architecture/adr/0016-authentication-sessions-rbac.md).

- First-party login: email + password (Argon2id, OWASP parameters, NIST-style policy), optional TOTP MFA with single-use recovery codes; organizations (always the platform organization) can require MFA.
- Short-lived HS256 access tokens (10 min) and rotating, single-use refresh tokens stored as SHA-256. Reuse of a rotated refresh token revokes the whole session. Revocation is immediate through a Redis deny-list.
- Generic `401 Invalid credentials` for every login failure, dummy hashing for unknown accounts, per-IP and per-account failure counters with progressive lockout mirrored to MySQL, and rate limits on every public auth endpoint. One `login_audit_logs` row per attempt.
- Every route is `@Public()` or declares its required permissions; a route without a declaration is denied (fail closed) and a test enumerates every route. Guards check permission keys, never role names. The tenant comes from the authenticated principal, never from a header.
- API keys: shown once, stored as prefix + peppered HMAC, scoped to tenant permissions, require the `api_access` feature.
- Platform operators reach customer data only through an MFA-gated, time-boxed, audited override whose token is limited to the target organization and to tenant permissions; every request made with it is audited.
- Redis unavailable → authentication fails closed (`503`).
- Single-use links (invitation, reset, verification) carry their token in the URL fragment only.

## Mail-path controls

- Not an open relay: unknown recipient domains get a permanent `554 Relay access denied`.
- The in-session policy service **fails closed** (4xx tempfail). The Rspamd milter **fails open to accept** (`milter_default_action = accept`, [ADR-0027](../architecture/adr/0027-rspamd-milter-policy.md)): it is not the security control of record, because every accepted message is scanned post-queue, and a scan that cannot finish ends `scan_failed`, never `clean` ([ADR-0026](../architecture/adr/0026-security-scan-pipeline.md)).
- `VRFY` is disabled, HELO is required, connection/rate/recipient limits are set and messages are capped at 50 MB.
- Post-queue processing never bounces, which prevents backscatter. `discard` is always audited.
- Message content is untrusted after the `250` too: the post-queue MIME parser (step 3.1) streams under limits, never renders, executes or extracts anything, stores only allow-listed and sanitized header metadata, sanitizes and flags attachment filenames, and keeps bodies and attachments out of MySQL, events and logs ([security boundaries](../architecture/security-boundaries.md#untrusted-message-content-step-31)).
- Opportunistic inbound TLS (TLS 1.2+). Outbound TLS policy (MTA-STS/DANE) comes in the delivery phase.

## Application controls

- Input validation with zod at every boundary: configuration, events and request bodies. Since step 6.1 every API body and query schema is strict (unknown fields `400 validation_failed`), enforced for every route by `apps/api/test/route-inventory.e2e.test.ts`.
- Event payloads must carry tenant-prefixed S3 keys, which are checked against the envelope tenant (the email-worker checks the message row's organization and EML key prefix since step 3.1; every later consumer must do the same).
- The policy protocol parser bounds request size (16 KiB), rejects malformed lines and refuses response splitting.
- Correlation ids are validated to prevent log injection.
- `helmet` security headers on the API. The portal sets `X-Frame-Options: DENY`, `nosniff`, a referrer policy and a permissions policy, and omits `X-Powered-By`.
- Generic 500 responses that never leak internal details.
- REST API (step 6.1, [ADR-0050](../architecture/adr/0050-api-conventions.md)–[ADR-0053](../architecture/adr/0053-public-internal-api-boundary.md)): coded errors with a server-minted `X-Request-Id` (never taken from the client); per-principal, per-tenant and class rate limits in Redis that **fail closed** (`503`); `Idempotency-Key` on the sensitive mutations, never storing a secret-bearing response; v1 list cursors HMAC-signed with the api-only `API_CURSOR_KEY` and bound to the tenant (the scope is re-applied anyway); sensitive searches audited with hashed values only; only `/api/v1` is public (the api Ingress routes `Prefix /api/v1/` only; `/metrics`, `/health/*` and `/docs` stay internal, `/docs` never in production).

## Supply chain

- `pnpm-lock.yaml` is committed, and CI installs with `--frozen-lockfile`.
- `minimumReleaseAge` (7 days) refuses freshly published packages. `onlyBuiltDependencies` allow-lists install scripts.
- Third-party images are pinned by tag (and by digest for MinIO).
- **Follow-ups:** pin GitHub Actions by commit SHA, add secret scanning (gitleaks), dependency audit and image scanning (Trivy) to CI, and generate SBOMs.

## Testing artefacts

Malware tests use only the EICAR test string, which is assembled at runtime and never stored in the repository.
