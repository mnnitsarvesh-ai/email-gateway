# Policy, quarantine and security alert notifications (steps 5.2, 5.3 and 6.2)

The notification-worker sends the notices the policy-engine requests ([design](../plan/steps/16-policy-engine.md) P15, P25; [README](../../apps/notification-worker/README.md)): **policy alerts** (ALERT action) to the organization's policy administrators and **sender non-delivery notices** when an outbound/internal message is rejected. They are _requested_ by 5.2, never part of the mail decision: a lost or late notice never changes a disposition.

## Flow

1. The policy-engine evaluates a round and, in the same commit, writes `mail.policy.notification_requested.v1` to `message_outbox` (`kind = policy_alert` when an ALERT applies and the tenant setting `alerts.enabled` is on; `kind = sender_non_delivery` for a REJECT of outbound/internal mail with the notice on).
2. The event-relay publishes it to `email.policy` (`org.<id>.mail.policy.notification_requested.v1`), bound to the work queue `email.notifications`.
3. The notification-worker (`eg-notification`) consumes it with the ledger `notification-worker.policy`, resolves the recipients on the writer, renders a fixed plain-text notice and submits it to the relay (`NOTIFY_SMTP_*`).

## Recipients and privacy

- `policy_alert`: active, non-deleted, email-verified users of the organization holding `policy:publish` through a role, sorted by id, at most `NOTIFICATION_MAX_RECIPIENTS` (default 50). One message, recipients as Bcc (they do not see each other).
- `sender_non_delivery`: the message's envelope sender, only when its domain is an **active domain of the organization**; an external or null sender gets nothing (`no_recipients`).
- The text holds the organization name, message public id, received time, direction, disposition, decisive policy name and rule id, a portal link, and for the sender notice the Internet-Message-ID and recipient count. Never the subject, body, file names, URLs or other addresses.

## At-least-once semantics

The SMTP submission happens inside the idempotency transaction before the ledger row commits. A duplicate event (relay replay, redelivery) is absorbed by the ledger. A crash after the relay accepted the notice but before the commit sends it again on redelivery with the **same `Message-ID`** (`<policy-notice.<eventId>@<From domain>>`), so mail clients can de-duplicate.

## Failures

| Symptom                                                                                          | Meaning and action                                                                                                                                                                                                                                                                                                                                                       |
| ------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `notification_policy_messages_total{result="failed"}` rising, alert `PolicyNotificationFailures` | The relay refused or was unreachable. The event is retried (hold, 8 attempts, 5 s–1 min, 24 h), then dead-lettered to `dead-letter.email.notifications`. Check the relay (`postfix-notify` logs, `NOTIFY_SMTP_*`), then replay from the dead-letter view (`POST /api/v1/platform/dead-letters/replay`, platform operators; [rabbitmq-messaging](rabbitmq-messaging.md)). |
| `result="disabled"`                                                                              | `NOTIFY_SMTP_HOST` is not set: nothing is sent. Set the relay and restart; already-handled events are not re-sent.                                                                                                                                                                                                                                                       |
| `result="no_recipients"`                                                                         | No verified policy administrator (alert) or the sender is not in an active domain of the organization (notice). Expected; no action.                                                                                                                                                                                                                                     |
| Dead letter with reason `message_not_found`                                                      | The event names a message that is not the organization's (or was purged). Investigate as a defect; never replay blindly.                                                                                                                                                                                                                                                 |
| Readiness `rabbitmq` failing                                                                     | Broker user or URL wrong (`RABBITMQ_NOTIFICATION_URL`); events wait in `email.notifications`.                                                                                                                                                                                                                                                                            |

## Quarantine notices (step 5.3)

`mail.quarantine.notification_requested.v1` (Q20, [17-quarantine.md](../plan/steps/17-quarantine.md)) arrives on the same `email.notifications` queue and ledger. Aggregate `quarantine` (`aggregate_id` = the organization id). The worker reads everything it renders on the writer **at send time**:

| `kind`               | Requested by                                                                   | Sent to                                                                                                                        | Content                                                                                                                                                                                                    |
| -------------------- | ------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `user_digest`        | sweeper (digest schedule of the organization)                                  | the digest's user (active, verified, not opted out, `endUser.enabled`)                                                         | per entry of the window (≤ `digest.maxEntries`): received time, envelope sender, subject (sanitized, ≤ 78, only with `digest.includeSubject`), reason, expiry, `PORTAL_PUBLIC_URL/quarantine/me/<entryId>` |
| `approval_requested` | evaluation (REQUIRE_APPROVAL), executor (new release approval), api (requests) | users holding `quarantine:approve` (active, verified), never the requester, ≤ `NOTIFICATION_MAX_RECIPIENTS`, Bcc               | request ids, kind, entry reason category, approval reasons, links `/quarantine/approvals/<id>`                                                                                                             |
| `approval_decided`   | api (approve/deny/cancel), sweeper (expired)                                   | the requesting user                                                                                                            | decision and request links                                                                                                                                                                                 |
| `release_blocked`    | executor                                                                       | the requesting user (API keys get none)                                                                                        | release id, outcome counts, link `/quarantine/releases/<id>`                                                                                                                                               |
| `admin_alert`        | sweeper (≤ one per organization per `alerts.minIntervalMinutes`)               | as `approval_requested`                                                                                                        | counts of new hard-block entries and of approvals older than one hour, link `/quarantine`                                                                                                                  |
| `sender_rejected`    | api (reject of an outbound/internal entry)                                     | the envelope sender, only when its domain is an active domain of the organization; **never for inbound mail** (no backscatter) | message public id, Message-ID, received time                                                                                                                                                               |

Never a body, an attachment, a URL of a message or another user's address; database text is Unicode-sanitized (controls, bidi overrides, invisible characters) and bounded. Links require login (no one-click actions, ADR-0047). Message-ID `<quarantine-notice.<eventId>@<From domain>>`, at least once. Metric `notification_quarantine_messages_total{kind,result}` (`sent`, `no_recipients`, `no_entries` (nothing held any more), `not_applicable` (opted out, end users disabled, inbound sender notice, nothing pending), `disabled`, `failed`); alert `QuarantineNotificationFailures` ([quarantine.md](quarantine.md#quarantinenotificationfailures)). A missing digest / entry row dead-letters (`digest_not_found`, `entry_not_found`, `entry_message_mismatch`).

## Security alerts (step 6.2)

`notification.alert_requested.v1` ([design](../plan/steps/19-webhooks-notifications.md) N1–N4, ADR-0056; [README](../../apps/notification-worker/README.md#security-alerts-and-preferences-step-62)) arrives on the same `email.notifications` queue and ledger (`notification-worker.policy`), published by the event-relay to `email.policy` (`org.<id>.notification.alert_requested.v1`, aggregate `organization`). The webhook-worker writes it to its outbox for the **first** event of a throttle window only ([webhooks runbook](webhooks.md)).

| `kind`              | Raised by (webhook-worker)                                                                         | Sent to (holders of, minus opt-outs, ≤ `NOTIFICATION_MAX_RECIPIENTS`) | Content                                                                                                      |
| ------------------- | -------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `threat_detected`   | fanout: `email.threat.detected` with severity ≥ `alerts.threatDetected.minSeverity` (default high) | `quarantine:approve`                                                  | verdict, detection stage, first message public id and received time, `/messages/<id>`                        |
| `domain_dns_failed` | fanout: `domain.dns.failed`                                                                        | `domain:manage`                                                       | the tenant's domain name, failed and still-failing record purposes (codes), `/domains/<id>`                  |
| `webhook_disabled`  | delivery role: automatic disable after sustained failure (W11)                                     | `webhook:manage`                                                      | subscription name (≤ 80, hidden if it looks like an address/URL), status, failure counters, `/webhooks/<id>` |

Every alert also carries the organization name, severity, window, `Events in this window so far` and `Suppressed before this alert`, and goes to `organization_settings.notification_email` when `alerts.includeOrganizationContact` is true (default). One mail per alert, recipients as Bcc, `Message-ID: <security-alert.<eventId>@<From domain>>`, at least once. Never a subject, body, file name, address of a message, URL from mail, endpoint URL or secret.

The existing admin kinds now honor the same per-user opt-outs (`notification_user_preferences`, api `PUT /notifications/preferences`): `policy_alert`, `quarantine_admin_alert` (5.3 `admin_alert`) and `quarantine_approval_requested` (5.3 `approval_requested`). Decisions to a requester, blocked releases and sender notices are not optional; the digest opt-out is still `quarantine_user_preferences.digest_opt_out`.

### Why was an alert not sent?

Work down the list; every step is visible in metrics (`GET :3050/metrics`) and in the worker log (`eventId`, `organizationId`, `kind`; never addresses).

| Cause                           | Where to look                                                                                                                                                                                                                                                                                                                                                          | Action                                                                                                                                                                        |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Throttled window** (expected) | `notification_alert_windows` of the organization, kind and scope (`-` for threats, the domain or subscription public id): `event_count` > 1 means the later events of that window were folded into the first alert; the next window's alert reports them as `Suppressed before this alert`. `alert_event_id` is the alert's event id (look it up in the ledger below). | None. Shorten `alerts.*.throttleMinutes` (bounds §6.3) with `PUT /notifications/settings` if the tenant wants more frequent mails.                                            |
| **Never requested**             | No window row: the producer decided no alert was due (kind disabled or below `minSeverity` at projection time, no matching public event) — see the [webhooks runbook](webhooks.md).                                                                                                                                                                                    | Check `GET /notifications/settings` of the tenant.                                                                                                                            |
| **Disabled since the request**  | `notification_alert_messages_total{result="disabled"}` with `notification_alerts_suppressed_total{reason="disabled"}`; log "disabled by the tenant settings".                                                                                                                                                                                                          | Expected: the tenant switched the kind off (or raised `minSeverity`) after the event.                                                                                         |
| **No relay**                    | `result="disabled"` **without** a `reason="disabled"` suppression; log "no relay configured".                                                                                                                                                                                                                                                                          | Set `NOTIFY_SMTP_HOST` (see Failures above). Already-handled alerts are not re-sent.                                                                                          |
| **No recipients**               | `result="no_recipients"`: no active, verified holder of the kind's permission after opt-outs, and no (valid) organization contact.                                                                                                                                                                                                                                     | Grant the permission to a verified user, or set `notification_email`. `reason="invalid_contact"` means the stored contact is not an address.                                  |
| **Opted out**                   | `notification_alerts_suppressed_total{kind, reason="opt_out"}` counts users left out; the user's row in `notification_user_preferences` (`preferences.optOut`).                                                                                                                                                                                                        | The user changes it with `PUT /notifications/preferences`. Operators never edit preferences.                                                                                  |
| **Dead-lettered**               | `result="failed"` and a dead letter in `dead-letter.email.notifications` with a code: `organization_not_found`, `webhook_event_not_found` (the public event row is gone, e.g. purged after 2 months), `webhook_event_mismatch` / `message_mismatch` (refs disagree with the stored rows), `message_not_found`, `domain_not_found`, `subscription_not_found`.           | Investigate as a producer defect or a cross-tenant reference; **never replay blindly**. A replay after fixing the cause sends at most one mail (ledger).                      |
| **Relay failures**              | `result="failed"` rising without dead letters; alert `SecurityAlertNotificationFailures`.                                                                                                                                                                                                                                                                              | As for policy notices: check `postfix-notify` and `NOTIFY_SMTP_*`; the event is retried (8 attempts, 24 h), then dead-lettered and can be replayed from the dead-letter view. |

Ledger check for one alert: `SELECT * FROM message_idempotency WHERE consumer = 'notification-worker.policy' AND event_id = '<alert event id>'` (a row means it was handled: sent or skipped with a result above); retries and dead letters are in `message_consumer_progress` for the same event id.

### SecurityAlertNotificationFailures

Defined with the step 6.2 rules (`infrastructure/monitoring/rules/webhooks.rules.yml`) on `notification_alert_messages_total{result="failed"}`. It fires when security alerts keep failing (relay down or refusing, or alerts dead-lettered for missing references). First tell the two apart: a dead letter carries a reference code (table above); a relay failure shows in the worker log as "security alert send failed (retried)" with the SMTP reply code only. Relay: fix `postfix-notify` / `NOTIFY_SMTP_*`, the retries deliver on their own within 24 h. Dead letters: investigate, then replay from the dead-letter view (`POST /api/v1/platform/dead-letters/replay`).

## Local stack

- `postfix-notify` **discards** mail unless `NOTIFY_RELAY_HOST` is set (no outbound mail leaves a laptop). To see notices locally, point the worker at a sink: Compose maps `NOTIFY_SMTP_HOST: ${NOTIFICATION_SMTP_HOST:-postfix-notify}`, so `NOTIFICATION_SMTP_HOST=mail-sink docker compose up -d notification-worker` (the stack suite does this for its run and restores it afterwards).
- Plaintext SMTP (`NOTIFY_SMTP_SECURE=none`) is accepted only when `APP_ENV` is `local` or `ci`.
- Metrics: `GET http://localhost:3050/metrics` (`notification_policy_messages_total`, `notification_quarantine_messages_total`, `notification_alert_messages_total`, `notification_alerts_suppressed_total`, `notification_send_duration_seconds`).
