# Runbook: local stack

## Start and stop

```bash
pnpm env:init                                         # once
docker compose up -d --wait                           # infrastructure, including the MySQL replica and rabbitmq-init
pnpm rabbitmq:init                                    # (re)apply the RabbitMQ topology and role users from the host (idempotent)
pnpm db:migrate                                       # history preflight + apply migrations from the host
pnpm db:partitions -- apply && pnpm db:seed           # partitions ahead + catalog/demo data (idempotent)
docker compose --profile apps up -d --build --wait    # everything, including services
docker compose --profile smtp-test up -d --wait      # test-only SMTP sinks, test PKI, DNS, tools, reinject-forwarder
docker compose --profile apps down                    # stop (keep data)
docker compose --profile apps down -v                 # stop and wipe all volumes
```

The default (infrastructure) set includes the mail plane of step 2.2: `postfix` (inbound MX, host port `SMTP_HOST_PORT` 2525), `postfix-outbound` (submission `SUBMISSION_HOST_PORT` 2587, connector relay `OUTBOUND_RELAY_HOST_PORT` 2527; reinjection 10026/10027 are not published), `rspamd-outbound` (DKIM signer, no host port) and `redis-dkim` (`REDIS_DKIM_HOST_PORT` 6391, ACL users only). Both Postfix instances need smtp-adapter at `SMTP_ADAPTER_HOST`: with `smtp-adapter` (the `.env.example` default, and this repository's local `.env` since step 3.2 WP5) the apps profile provides it; with `host.docker.internal` run `pnpm --filter @email-gateway/smtp-adapter dev` on the host. After changing it, recreate `postfix` and `postfix-outbound` (`docker compose up -d postfix postfix-outbound`). Without the adapter every SMTP path answers 4xx (fail closed). Details: [docs/deployment/smtp-gateway.md](../deployment/smtp-gateway.md).

Profile `smtp-test` (never deployed) adds `mail-sink` (accepts every `*.test` domain into `/var/mail/sink/<domain>/<local>/`; `hard-bounce@` → 550 5.1.1, `soft-bounce@` → 450 4.2.1, `policy-block@` → 550 5.7.1), `dns-sink` (CoreDNS, authoritative for `sink.test` and, since step 4.1, the `scan.test` test zones; the only resolver of `postfix-outbound` and of the inbound `rspamd`, so neither can reach the Internet locally) and `smtp-tools` (swaks, `smtp-source`, openssl, dig, nc, socat). Step 2.3 adds `sink-m365`, `sink-google`, `sink-google-alt` (Microsoft 365 / Google Workspace stand-ins with test-CA certificates), `relay-sink`, the one-shot `test-pki` and `reinject-forwarder` (`127.0.0.1:2626`/`2627` → postfix-outbound 10026/10027, so a delivery-worker on the host can reinject), and `postfix` joins `mailtest` as `172.31.250.10`. postfix-outbound's delivery log is `./.local/postfix-outbound-log/maillog` (git-ignored). Stacks created before step 2.3 must recreate the `mailtest` network once ([mail-routing.md](../deployment/mail-routing.md#test-profile-smtp-test-never-deployed)). Build images one at a time: `for s in postfix postfix-outbound; do docker compose build $s; done; for s in mail-sink smtp-tools; do docker compose --profile smtp-test build $s; done`.

The stack SMTP suites (`tests/integration/smtp-*.test.ts`, part of `pnpm test:integration`) need all of the above plus a running adapter and a built api (`pnpm build`; they run its `dkim:sync` CLI, or inside the `api` container when the apps profile runs). They fail with the list of what is missing; `SMTP_STACK_TESTS=skip` skips them explicitly, `SMTP_LOAD_SESSIONS`/`SMTP_LOAD_MESSAGES` shrink the 40 × 1 000 load test. They stop and restart MinIO, Redis and `postfix` themselves and always bring them back.

## Admin portal and api on the host (step 7.1)

On this machine port 3000 is taken, so the api runs on the host with `HTTP_PORT=3200` (`API_HOST_PORT=3200`, the Compose `api` also publishes `127.0.0.1:3200`) and the portal on 3001. Only one process can hold each port: `docker compose stop api admin-portal` before running them on the host, `docker compose --profile apps up -d --no-deps api admin-portal` to go back to the containers.

```bash
pnpm --filter @email-gateway/api build
(cd apps/api && HTTP_PORT=3200 node --env-file=../../.env dist/main.js)          # api on http://localhost:3200
pnpm --filter @email-gateway/admin-portal dev                                      # portal on http://localhost:3001 (API_INTERNAL_URL=http://localhost:3200)
```

Open the portal as `http://localhost:3001` (not `127.0.0.1`: the BFF's CSRF check compares the `Origin` with `PORTAL_PUBLIC_URL`). For the portal end-to-end suite the api runs with `AUTH_ACCESS_TOKEN_TTL_SECONDS=60 DNS_SERVERS=127.0.0.1:1053` (and the shipped `expensive` budget) and the portal as a production build (`next start`); see [running and testing](../frontend/running-and-testing.md#end-to-end-suite-testsportal-e2e). Never run `next build` while `next dev` of the same tree runs (shared `.next`). Operations: [admin portal runbook](admin-portal.md).

## RabbitMQ

Topology v3 (step 3.2; v2 step 3.3: `rescan_requested.v1` bindings; v3 step 4.1: `scan.spam` is a work queue, `scan.auth` lost its event bindings; [messaging-topology.md](../architecture/messaging-topology.md)) lives in the vhost `email-gateway` (`RABBITMQ_VHOST`, description `email-gateway topology v3`): 6 exchanges, 14 quorum queues, 35 bindings, one policy per queue, and the role users `eg-relay`, `eg-email-worker`, `eg-scanner` (step 4.1: the email-worker scan role, `RABBITMQ_SCANNER_USER`/`_PASSWORD`/`_URL`), `eg-delivery-worker`, `eg-ops` (no tags, least privilege). `init.mjs` removes bindings on topology queues and exchanges that the definitions no longer declare (`--prune-dry-run` lists them without changing anything); a broker provisioned with v2 loses the two `scan.auth` bindings on the next run. If `rabbitmq-init` fails with `missing environment: RABBITMQ_SCANNER_USER, RABBITMQ_SCANNER_PASSWORD`, append the security scanning keys from `.env.example` and re-run `docker compose up -d rabbitmq-init`. The one-shot `rabbitmq-init` (default profile) applies it after the broker is healthy, on every `docker compose up`; every app service waits for it.

```bash
pnpm rabbitmq:init                                              # from the host: topology + role users, then verification
docker compose run --rm rabbitmq-init                           # the same inside the network, plus --cleanup-legacy
node --env-file=.env infrastructure/rabbitmq/init.mjs --vhost eg-it-1234   # a throwaway test vhost (no users)
node --env-file=.env infrastructure/rabbitmq/init.mjs --delete-vhost eg-it-1234
pnpm --filter @email-gateway/event-contracts topology:export    # after changing topology.ts: regenerate definitions.json
```

- `init.mjs` is idempotent and exits non-zero when anything is missing, unexpected or different (it never deletes topology objects it finds extra: remove them by hand after a topology change). It prints object names and counts only, never passwords.
- `--cleanup-legacy` (the Compose default) deletes the ADR-0005 objects on vhost `/` (`mail.events`, `mail.dlx`, the five `<service>.<event>` queues and their `.dlq`) only when each queue is empty (no messages, no consumers) and each exchange unbound; otherwise it warns and keeps them. The legacy queues are quorum queues, for which RabbitMQ 4.x refuses `DELETE …?if-empty=true` (HTTP 400), so the script checks emptiness itself and then deletes (fixed in step 3.2 WP5; `tests/integration/messaging-legacy-cleanup.test.ts`). Images built before step 3.2 WP4 re-assert those objects when they start. `pnpm rabbitmq:init` does not clean up.
- The broker publishes its Prometheus endpoint on `127.0.0.1:15692`. Changing its ports needs `docker compose up -d --no-deps rabbitmq` (recreates the broker only; queue contents survive in `rabbitmq-data`).
- Dormant queues (`scan.*`, `email.policy.evaluate`, `email.quarantine`, `email.archive`, `email.analytics`) have no consumer and keep at most 10 000 messages (`drop-head`); that is expected until their stage exists. Since step 3.3 every lifecycle transition also publishes `mail.message.state_changed.v1` to `email.analytics`, and a rescan puts one copy into each `scan.*` queue except `scan.sandbox`. The stack suites that send mail purge the dormant queues in `afterAll` (`purgeDormantQueues` in `tests/integration/support/broker.ts`); by hand: `docker compose exec rabbitmq rabbitmqctl purge_queue -p email-gateway <name>` for those names only, never a work, delay or dead-letter queue.

**Test-only 3-node cluster** (profile `rabbitmq-cluster`, broker node-failure test; never with the apps profile on an 8 GB VM, `mem_limit 448m` per node). Stop the app containers **by name** first: `docker compose --profile apps stop` also stops MySQL and the rest of the default profile, which the test needs.

```bash
docker compose stop api admin-portal smtp-adapter email-worker policy-engine delivery-worker \
  event-relay notification-worker webhook-worker archive-worker
docker compose --profile rabbitmq-cluster up -d --wait rabbitmq-node1 rabbitmq-node2 rabbitmq-node3
docker compose --profile rabbitmq-cluster exec rabbitmq-node1 rabbitmq-diagnostics cluster_status   # 3 running nodes
node --env-file=.env infrastructure/rabbitmq/init.mjs --mgmt-url http://127.0.0.1:15701 --users
# AMQP: 127.0.0.1:5701, 5702, 5703 (RABBITMQ_CLUSTER_NODE{1,2,3}_HOST_PORT), administrator = RABBITMQ_USER
pnpm --filter @email-gateway/integration-tests test:cluster      # tests/integration/cluster/node-failure.test.ts
docker compose --profile rabbitmq-cluster rm -sf rabbitmq-node1 rabbitmq-node2 rabbitmq-node3
docker volume rm email-gateway_rabbitmq-cluster-1-data email-gateway_rabbitmq-cluster-2-data email-gateway_rabbitmq-cluster-3-data
docker compose --profile apps up -d --wait
```

Remove exactly those three volumes (never `down -v`, which would wipe every volume of the stack). The nodes share `RABBITMQ_CLUSTER_ERLANG_COOKIE`, written by `infrastructure/rabbitmq/cluster/entrypoint.sh`.

## Webhooks and notifications (step 6.2)

The `webhook-worker` (apps profile, `127.0.0.1:${WEBHOOK_WORKER_HOST_PORT:-3075}`: `/health/ready`, `/metrics`) runs both roles (`fanout` on `email.webhooks` as `eg-webhook`, `delivery`); [runbook](webhooks.md). In the container it resolves only through `dns-sink`, trusts the test-pki CA and may dial only the documentation range of the TEST-ONLY `webhook-receiver` (smtp-test profile, `https://hooks.receiver.test/<path>` = 203.0.113.20):

```bash
docker compose --profile apps --profile smtp-test up -d --wait webhook-worker webhook-receiver notify-relay-sink
curl -s localhost:${WEBHOOK_WORKER_HOST_PORT:-3075}/health/ready
curl -s localhost:${WEBHOOK_RECEIVER_ADMIN_HOST_PORT:-18091}/health
# the requests the receiver recorded for one path (headers, base64 body, signatureValid)
curl -s localhost:${WEBHOOK_RECEIVER_ADMIN_HOST_PORT:-18091}/requests/<path>
curl -s localhost:${WEBHOOK_WORKER_HOST_PORT:-3075}/metrics | grep -E '^webhook_(fanout_events|delivery_attempts|due_backlog)'
```

- New `.env` keys: the "Webhooks and notifications" section of `.env.example` (`WEBHOOK_SECRET_ENCRYPTION_KEY`, `RABBITMQ_WEBHOOK_*`, `NOTIFY_RELAY_SINK_*`, `WEBHOOK_*`); Compose refuses to start without them (`:?`). Then `docker compose up rabbitmq-init` (user `eg-webhook`, topology v11).
- Security alert e-mails go notification-worker → `postfix-notify`. Without `NOTIFY_RELAY_HOST` postfix-notify discards them; **if your `.env` points it at a real smarthost, alerts of your own organizations are really sent**. The stack suite `webhooks-notifications.test.ts` recreates postfix-notify against the TEST-ONLY `notify-relay-sink` (172.31.250.31:587, STARTTLS with the pinned test-pki certificate, SASL `NOTIFY_RELAY_SINK_USER`) through the Compose environment only and restores it from `.env` afterwards; the fixture organizations of the other stack suites keep every alert off.
- `DELETE /requests` on the receiver's admin API forgets **every** path, program and secret (shared by all suites); prefer per-run paths.
- With mail flowing and no webhook-worker running, `email.webhooks` fills up (bounded at 1 000 000); start the worker or purge that queue by name (see [rabbitmq-messaging.md](rabbitmq-messaging.md)).

## Security scanning (step 4.1)

The inbound `rspamd` (default profile, `mem_limit: 768m`) serves the SMTP-time milter (11332, `postfix` only) and the post-queue scan (`/checkv2` 11333, host `RSPAMD_HOST_PORT`); the controller (11334, `RSPAMD_CONTROLLER_HOST_PORT`) needs the read or enable password from `.env` (never echo them). It joins `mailtest` as `172.31.250.11` and resolves only through `dns-sink` (`RSPAMD_DNS_SERVERS=172.31.250.53`, the `scan.test` zones), uses Redis DB `RSPAMD_REDIS_DB` (1), `RSPAMD_RBL_PROFILE=test` and `RSPAMD_BAYES_MIN_LEARNS=10` locally. The email-worker runs the MIME and scan roles in one container (`SCAN_ENABLED=true`, `RABBITMQ_SCANNER_URL`). Details: [rspamd.md](../deployment/rspamd.md), [scan-pipeline runbook](scan-pipeline.md). Step 4.3: the email-worker also runs the URL engine (`SCAN_ENGINES=rspamd,attachment,url`, networks `mailtest` and `urltest`, DNS only through `dns-sink`); the `click-service` runs in the apps profile, `url-test` in `smtp-test`, the browser pair only in `url-browser` — see [url-scanning](url-scanning.md), [click-service](click-service.md), [url-browser-worker](url-browser-worker.md).

```bash
docker compose up -d --wait rspamd && docker compose --profile smtp-test up -d --wait dns-sink
docker compose exec rspamd rspamadm configtest                                    # syntax OK
curl -s localhost:${EMAIL_WORKER_HOST_PORT:-3020}/metrics | grep -E '^scan_(rounds_completed_total|engine_circuit_state|engine_failures_total)'
# rounds and results of one message (writer)
docker compose exec mysql sh -c 'MYSQL_PWD="$MYSQL_ROOT_PASSWORD" mysql -uroot email_gateway -e "
  SELECT lifecycle_round, scan_kind, status, scan_verdict, reason_codes FROM email_scans WHERE message_id = <id>;
  SELECT scan_id, attempt, is_final, outcome, score, error_code, engine_version FROM scan_engine_results WHERE message_id = <id>;
  SELECT spf, dkim, dmarc, dmarc_policy, arc FROM email_auth_results WHERE message_id = <id>;"'
# or through the api (permission message:read): GET /api/v1/messages/<public id>/scans
```

- Since step 5.2 delivery is approved **only by the policy-engine** ([runbook](policy-engine.md)): there is no development pass-through any more (`DELIVERY_DEV_PASSTHROUGH_ENABLED=true` is refused by the delivery-worker; remove `DELIVERY_DEV_PASSTHROUGH_*` from an existing `.env` and append the "Policy engine (step 5.2 …)" section of `.env.example`). The `policy-engine` container (apps profile, port `POLICY_ENGINE_HOST_PORT`, readiness mysql/rabbitmq/redis/s3) must run, or mail stays `scanned`. A clean message goes `received → persisted → scanning → scanned → (policy_evaluated) → approved → delivery_pending → delivered`; a held one ends `quarantined`, `held_for_review` or `rejected`; a `scan_failed` or parse-failed message is quarantined by the strictness floor (rescan it after fixing Rspamd: `POST /api/v1/messages/<id>/rescan`). Why: `GET /api/v1/messages/<id>/policy-evaluations` or `SELECT disposition, decision_source, reason_codes, explanation_text FROM policy_execution_logs WHERE message_id = <id>;`.
- Policy alerts and sender notices go through the `notification-worker` (apps profile) to `postfix-notify`, which discards them without `NOTIFY_RELAY_HOST`. To read them in a test run, point the worker at another relay with `NOTIFICATION_SMTP_HOST` (and `NOTIFICATION_SMTP_PORT`) and recreate it: `NOTIFICATION_SMTP_HOST=<relay> docker compose --profile apps up -d --no-deps --force-recreate notification-worker` (restore by recreating it without the variable). The relay must be reachable on the default network: the smtp-test `mail-sink` sits only on `mailtest`, so the stack suite adds that network through a Compose override. Policy copies (TAG/WARN) are `org/<org>/policy/…` objects in the mail bucket, expired by the MinIO rule `eg-policy-copy-expiry` (`POLICY_COPY_RETENTION_DAYS`).
- Mail through `postfix` from smtp-tools: address `172.31.250.10` (the mailtest address) so the client is in `clean.scan.test`'s SPF; the service name `postfix` resolves to its default-network address.
- Since step 4.4 every round also needs the stage-2 `bec` engine ([runbook](bec-detection.md)): the email-worker readiness reports `bec-engine`, `scan.bec` has one consumer, and a message whose deterministic bec result is `suspicious`/`malicious` is quarantined by the platform default policy (rule D2; `policy_evaluations_total`) — e.g. a display name of a configured executive from a free-mail address. Locally the LLM layer is off (`BEC_LLM_MODE=off`, empty `BEC_LLM_API_KEY`); integration runs use `BEC_LLM_PROVIDER=fake` and never call a real LLM. Inspect a result: `SELECT verdict, deterministic_verdict, score, inputs, rules FROM bec_scan_results WHERE message_id = <id>;` or the `bec` section of `GET /api/v1/messages/<public id>/scans`.
- Since step 4.5 every round also needs the stage-1 `dlp` engine ([runbook](dlp.md)): the email-worker readiness reports `dlp-engine` and `dlp-extractor`, `scan.dlp` has one consumer (topology v7: no longer a dormant queue, never purge it), and the email-worker and the api need `DLP_EVIDENCE_KEY` in `.env` (generated by `pnpm env:init`; for an existing `.env` append the "Data loss prevention (step 4.5)" section of `.env.example` with a fresh 64-hex key and add `dlp` / `scan.dlp` to `SCAN_ENGINES` / `RECONCILE_QUEUES`). Inbound mail is `skipped` (`dlp.not_inbound`) unless the tenant enables inbound scanning; outbound and internal mail is scanned, and a round whose DLP action is `require_approval`, `quarantine` or `block` is held by the policy floor (DLP binding: `held_for_review`, `quarantined`, `rejected`); without a tenant policy the platform default only alerts. Inspect a result: `SELECT verdict, action, action_source, coverage, findings FROM dlp_scan_results WHERE message_id = <id>;` (masked values only) or the `dlp` section of `GET /api/v1/messages/<public id>/scans` (needs `dlp:read`); evidence only through the audited MFA endpoint. Fixture cleanup removes the DLP rows and the `org/<id>/dlp-evidence/` objects with the organization.
- Since step 5.1 every completed round is also **risk-scored** ([runbook](risk-scoring.md)): the policy-engine follows its recommendation by default (`require_approval` → `held_for_review`, `quarantine` → `quarantined`, `block` → `rejected`; hard blocks, failed engines, error and missing rows through the strictness floor); `deliver` and `tag` are approved. Read why with `GET /api/v1/messages/<id>/scans` (`risk[].explanation.text`).
- Since step 4.6 the email-worker also runs the asynchronous **sandbox engine** (`SANDBOX_ENABLED=true`; readiness `sandbox-bucket`; consumers on `scan.sandbox.submissions` and `scan.sandbox.results`, topology v8) and the **`sandbox-controller`** container runs in the apps profile with `SANDBOX_BACKEND=disabled` — **execution of unknown files is disabled** ([sandbox-controller](sandbox-controller.md), [sandbox-engine](sandbox-engine.md), [threat model](../security/sandbox-threat-model.md)). Its only network is the internal `sandbox-control`, so its port 3092 is not published: `docker compose exec sandbox-controller node -e "fetch('http://127.0.0.1:3092/health/ready').then(async r=>console.log(await r.text()))"` (or `/metrics`). Static analysis (no execution): `SANDBOX_BACKEND=static docker compose --profile apps up -d --no-deps sandbox-controller`. The **exec override** (LOCAL/CI only, a shared-kernel container, NOT a VM boundary; mounts the Docker socket into the controller): build `email-gateway/sandbox-runner:local` (`infrastructure/docker/sandbox-runner.Dockerfile`) and `email-gateway/url-browser-worker:local` one at a time, then `docker compose -f docker-compose.yml -f infrastructure/sandbox/compose.exec.yml --profile sandbox up -d --no-deps --wait sandbox-sinkhole` and `docker compose -f docker-compose.yml -f infrastructure/sandbox/compose.exec.yml --profile apps --profile sandbox up -d --no-deps --wait sandbox-controller`; undo with `docker compose --profile apps up -d --no-deps --force-recreate sandbox-controller` and `docker compose -f docker-compose.yml -f infrastructure/sandbox/compose.exec.yml --profile sandbox rm -s -f sandbox-sinkhole`. **Memory:** the controller is limited to 384 MiB; a browser runner takes ~1 GiB, an execute runner 512 MiB (concurrency 1) — never run the exec override together with the analytics or observability profiles. A tenant needs the plan feature `attachment_sandbox` and the opt-in `PUT /api/v1/scan-settings/sandbox`; results in the `sandbox` entry of `GET /api/v1/messages/<public id>/scans` or `SELECT status, skip_reason, sandbox_verdict FROM sandbox_submissions WHERE message_id = <id>;`. Fixture cleanup removes the analyses, artifacts and sandbox-bucket objects of a run's organizations.
- After an Rspamd restart the first start compiles the Hyperscan cache into the `rspamd-data` volume (later starts take a few seconds).

## Message lifecycle (step 3.3)

Every message's state is in `email_messages.status` (with `status_reason`, `version`, `lifecycle_round`) and its transitions in `email_message_status_history`; see the [message lifecycle runbook](message-lifecycle.md) for stuck, expired and ignored transitions. Locally:

```bash
# state and history of one message (writer; add received_at for partition pruning)
docker compose exec mysql sh -c 'MYSQL_PWD="$MYSQL_ROOT_PASSWORD" mysql -uroot email_gateway -e "
  SELECT id, status, status_reason, version, lifecycle_round, status_changed_at FROM email_messages WHERE id = <id>;
  SELECT version, from_status, to_status, reason_code, lifecycle_round, actor_role, actor_service, changed_at
    FROM email_message_status_history WHERE message_id = <id> ORDER BY version;"'
# or through the api (permission message:read): GET /api/v1/messages/<public id>/lifecycle and …/lifecycle/history
curl -s localhost:${EVENT_RELAY_HOST_PORT:-3070}/metrics | grep -E '^lifecycle_(stuck_messages|expired_total|recovered_total|expiry_shards_held)'
```

- With the policy-engine running, a clean message sent to an active tenant domain with a destination goes `received → persisted → scanning → scanned → policy_evaluated → approved → delivery_pending → delivered` within seconds; a deferred recipient shows `delivery_retry`; a partial delivery is `delivered/delivery_partial`, all failed `rejected/delivery_failed`.
- Messages that the step 3.3 migration backfilled (`persisted` from `received`, `delivery_pending` from `delivery_queued`) are left alone by the planner (approvals of messages not in `approved` are rejected with `lifecycle_state`); the lifecycle check re-derives the backfilled `delivery_pending` ones after `LIFECYCLE_CHECK_AFTER_SECONDS`, and the sweeper expires the rest after their deadlines. Re-send test mail rather than editing rows.
- `tests/integration/lifecycle-event-relay.test.ts` stops the `event-relay` container while it runs a test-only event-relay on the host (port `LIFECYCLE_TEST_RELAY_PORT`, default 3071, log `.local/lifecycle-test-event-relay.log`) and starts the container again with `docker start`. If the suite was interrupted: `docker compose --profile apps up -d --wait event-relay` and stop any `node dist/main.js` left listening on 3071.

## Symptoms and fixes

| Symptom                                                                                                                                                                                       | Cause                                                                                                                                                                                                                                   | Fix                                                                                                                                                                                                                                                                                                            |
| --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ports are not available ... address already in use`                                                                                                                                          | Another local stack uses a default port                                                                                                                                                                                                 | Set the matching `*_HOST_PORT` in `.env`, and update the URL that uses it (e.g. `DATABASE_URL`), then `docker compose up -d`                                                                                                                                                                                   |
| `required variable ... is missing a value`                                                                                                                                                    | No `.env`                                                                                                                                                                                                                               | `pnpm env:init`                                                                                                                                                                                                                                                                                                |
| MySQL "Access denied" after regenerating `.env`                                                                                                                                               | The data volume was initialised with the old passwords                                                                                                                                                                                  | `docker compose down -v` (wipes local data), then start again                                                                                                                                                                                                                                                  |
| `mysql-replica` stays `unhealthy`                                                                                                                                                             | Replication is not running yet (the setup has not finished) or has stopped                                                                                                                                                              | `docker compose logs mysql-replica-setup`, then `docker compose run --rm mysql-replica-setup`, which is safe to repeat. See [replication troubleshooting](../database/replication.md#troubleshooting)                                                                                                          |
| `mysql-replica-setup` exited 1                                                                                                                                                                | The log names the cause: `Last_IO_Error`/`Last_SQL_Error`, a CLONE error, or a replication password longer than 32 characters                                                                                                           | Fix the cause, then `docker compose run --rm mysql-replica-setup`. If the replica diverged or the binlogs it needs were purged, re-seed it (next row)                                                                                                                                                          |
| The replica needs a fresh copy (re-seed)                                                                                                                                                      | Diverged, too far behind, or a broken volume                                                                                                                                                                                            | `docker compose rm -sf mysql-replica mysql-replica-setup && docker volume rm email-gateway_mysql-replica-data && docker compose up -d --wait`. Only the replica's volume is deleted                                                                                                                            |
| "Access denied" for `gateway_reader` or `gateway_repl` after regenerating `.env`                                                                                                              | The accounts already exist on `mysql-data` with the old passwords; `01-users.sh` never changes a password                                                                                                                               | Either restore the old `.env` values, or set the new ones on the primary (`ALTER USER … IDENTIFIED BY …` as root), then re-seed the replica. `docker compose down -v` also works but wipes all local data                                                                                                      |
| `docker compose up -d --wait` exits 1 with `minio-init exited (0)` (or `mysql-replica-setup exited (0)`, `rabbitmq-init exited (0)`)                                                          | Compose v5 treats a one-shot container that has finished as a failure when nothing in the started profiles depends on it                                                                                                                | Harmless with infrastructure only: check `docker compose ps`. ## Sending a test message

```bash
# inbound MX (from the host; needs smtp-adapter running and an active tenant domain)
swaks --server 127.0.0.1:2525 --from sender@example.org --to user@<active tenant domain>
# from inside the stack (profile smtp-test)
docker compose exec smtp-tools swaks --server postfix --from sender@example.org --to user@<active tenant domain>
docker compose exec smtp-tools swaks --server postfix-outbound --port 587 --tls \
  --auth PLAIN --auth-user <connector username> --auth-password <secret> --from me@<tenant domain> --to someone@x.sink.test
docker compose exec smtp-tools swaks --server 172.31.250.25 --to user@x.sink.test   # mail-sink directly
docker compose exec mail-sink find /var/mail/sink -type f                            # what the sink received
```

Accepted inbound mail is handed to smtp-adapter's LMTP ingestion (S3 + MySQL) and stays queued in Postfix (`docker compose exec postfix postqueue -p`) while ingestion is unavailable.
