## 2. Decisions

### 2.0 Invariants (never traded away)

1. **Never clean by accident.** A missing, failed or not-in-round dependency (authentication results, URL results), an incomplete text source, a wrong read or an AI failure is never `clean`. `clean` is reachable only through rule C0 (B6) with every input available.
2. **Deterministic first; AI is additive and bounded (B9).** The AI layer (local model or LLM) can never produce `clean`, never lower a deterministic verdict, can raise to at most `suspicious` on its own, and contributes to `malicious` only when deterministic identity **and** intent evidence already put the score within a bounded band of the malicious threshold. Shadow mode never changes a verdict.
3. **Engines classify, policy decides.** The `bec` engine records a verdict, reason codes, evidence and scores; it never blocks, quarantines or delivers. An LLM never authorizes or rejects delivery.
4. **No email content in MySQL, events, logs, metrics or the LLM beyond redacted excerpts.** Rows hold codes, weights, scores, parsed addresses/domains/display names of headers (tenant's own message metadata, already stored in `email_headers`), profile ids, lexicon category ids and **span offsets** (never span text), hashes and versions. The LLM receives only a redacted, bounded excerpt and derived features (B10), never attachments, full bodies, header addresses, tenant names or secrets.
5. **Historical context is opt-in, per tenant, keyed-hash only (B12).** No plaintext address is stored in the context table; hashes are HMAC-SHA256 under a worker-only secret, scoped by organization (unlinkable across tenants); counts and first/last seen only; retention-bounded; purgeable.
6. **Idempotent per (message, round, engine)** through the 4.1 orchestrator (`processOnce`, unique final row) and unique keys on every child row; the history update happens once per message (round 0 only).
7. **Tenant from trusted context.** The worker takes the organization from the envelope checked against the writer rows; the api takes it from the authenticated scope (never from headers or bodies); profiles, trusted senders and suppressions of one tenant never influence another tenant's verdict.
8. **Trust never suppresses authentication failures or malware/credential-harvesting findings** (B7); a trusted sender counts only when the message authenticates as that sender.
9. **Bounded everything** by validated configuration: header bytes parsed, text bytes read, lexicon matches, rules fired, profiles per tenant, LLM calls per tenant/minute, excerpt length, history rows touched per message, API pages.

### B1. One `bec` engine on a new `scan.bec` queue, required for every tenant

- **Catalog** (`security-contracts`): `{ name: 'bec', stage: 'bec', queue: 'scan.bec', requiredByDefault: true, tenantMayDisable: false, dependsOn: ['rspamd', 'url'], description: 'Phishing and BEC: sender identity, impersonation, lookalikes, payment/urgency cues, credential links, communication history; optional AI layer (step 4.4)' }`. `SCAN_ENGINES` default becomes `rspamd,attachment,url,bec`.
- **Required:** yes. Its computation is local (no third party in the deterministic path), so a failure is an infrastructure failure, and a round without a BEC verdict must not be `scanned`.
- **Queue choice: a new `scan.bec`, not the reserved `scan.auth`.** `scan.auth` is reserved for a future first-party authentication engine (ADR-0026) and its name would mislead dashboards, alerts and runbooks; BEC consumes authentication results, it does not produce them. Cost: one more quorum queue (17) and grants. Alternatives in §7.
- **Consumer:** email-worker scan role, broker user `eg-scanner`, ledger consumer **`email-worker.scan.bec`**, registration `becRegistration` in `ENGINE_REGISTRY`. Production: Deployment `email-worker-bec` (`SCAN_CONSUMERS=bec`), the only Deployment that holds the LLM API key and the context HMAC key.
- **Directions:** `inbound` → full rule set. `outbound` and `internal` → definite **`skipped`** with `bec.not_inbound` (account-takeover detection on outbound mail is out of scope, §10); the history context is still updated for them when enabled (B12), because outbound mail is what makes a later inbound reply "known".

### B2. Dependency on other engines' results: a second stage within the round (generic)

The `bec` engine needs Rspamd's authentication results and the URL engine's verdicts **of the same round**. Engines of a round run in parallel (ADR-0026), so reading them at arbitrary time would make the verdict depend on arrival order (the reason 4.3 U1 refused to read Rspamd symbols). Decision: **engines may declare `dependsOn`; a dependent engine is triggered when every dependency in the round's required set has its final row** (definite or failure). It never waits by polling, never blocks the round forever (the round deadline still applies) and records missing inputs explicitly.

- **Catalog:** `EngineCatalogEntry.dependsOn?: readonly EngineName[]` (default none). Validation (`security-contracts`, unit-tested): every dependency is in the catalog, no self-dependency, **depth 1** (a dependency has no `dependsOn` itself). An engine with `dependsOn` is a **stage-2 engine**; the others are stage-1.
- **Trigger event `mail.message.scan_stage_ready.v1`** (`EVENT_REGISTRY`, exchange `email.security`, aggregate `message`, producer email-worker via the outbox; strict zod, example, tests): `{ messageId: decimalId, receivedAt: iso, direction, emlS3Key: 'org/<id>/…' (refined like the other events), lifecycleRound: 0..65535, scanId: decimalId, scanKind: 'initial'|'rescan', engine: engineName, dependencies: [{ engine, outcome: ENGINE_OUTCOMES }] (1..8), readyAt: iso }`. Ids, codes and keys only (content guard).
- **Where it is written (exactly once):** in `ScanRepository.complete()` (both locks held, finals read after the locks), **before** the "not complete" return: for every engine `E` in `round.requiredEngines` that has `dependsOn`, no final row, and whose `dependsOn ∩ requiredEngines` all have final rows, **and** the final inserted by this transaction (`input.final.engine`, `inserted = true`) is one of those dependencies → insert one `scan_stage_ready.v1` outbox row (`engine = E`). Because finals of one round are serialized by the message row lock and read after it, exactly one transaction (the one that inserts the last dependency final) satisfies the condition. The deadline sweeper writes no trigger (it finalizes every missing required engine, including stage-2 ones, as `timeout`). Counted `scan_stage_triggers_total{engine}`.
- **Consumption:** a stage-2 engine's queue binds only `org.*.mail.message.scan_stage_ready.v1` (not `parsed.v1`/`rescan_requested.v1`); `createEngineConsumer` takes the event types from the catalog (stage-1: parsed + rescan; stage-2: stage ready). The round service handles trigger `stage`: round = `payload.lifecycleRound`; `payload.engine ≠` this engine → ledger no-op, skip reason `other_stage_engine`; `decideOpen(..., 'stage')` never returns `open_e3` (the round was opened by stage-1 engines); `openRound` for `stage` **never creates** an `email_scans` row: it finds the round's row and requires `id = payload.scanId` (absent or different → ledger no-op, skip reason `stage_round_missing`, counted, warn). Everything after (attempts, breaker, final row, completion) is unchanged.
- **Configuration rule (email-worker config):** every enabled stage-2 engine must have at least one of its dependencies enabled in `SCAN_ENGINES`, and at least one stage-1 engine must be enabled (else nobody opens rounds). Refused at start with the key named.
- **Deadline validation:** the minimum `SCAN_ROUND_DEADLINE_SECONDS` becomes `max over stage-1 engines of B(e)` + `max over stage-2 engines of B(e)`, with `B(e) = maxAttempts × (timeoutMs + SCAN_RETRY_MAX_MS) / 1000`. Defaults: url 6 × 180 = 1 080 s + bec 3 × 105 = 315 s = 1 395 s ≤ 1 800 s (default deadline unchanged).
- **Rescans:** a rescan round re-runs stage-1 engines; the last of `rspamd`/`url` to finalize triggers `bec` for that round (new `scan_id`). Old rounds' rows are never touched.
- **Reconciler:** `RECONCILE_QUEUES` adds `scan.bec` (env only; the reconciler derives the event types from the binding).
- **Inputs at scan time:** the adapter reads the dependency finals itself (writer, echo-checked). Each input gets a state in `bec_scan_results.inputs` and, when not `available`, a reason code (B6 E-rules): `auth`: `available` (an `email_auth_results` row of `rspamd`) | `failed` (rspamd final `timeout`/`error`) | `missing` (rspamd definite but no auth row, e.g. R1 too large) | `not_in_round` (rspamd not required in this round); `url`: `available` (definite or `skipped` final) | `failed` | `not_in_round`; `text`: `complete` | `incomplete` (parse limits/`body_size`, part over `BEC_TEXT_MAX_BYTES` truncated) | `absent` (no text or HTML body); `history`: `enabled` | `disabled` | `error`. A dependency final that the trigger said exists but the read does not find → attempt failure `inconsistent_read` (retryable).

### B4. Data flow of one `bec` call (`BecEngine.scan(ctx, signal)`)

1. **Direction:** not inbound → B12 history update rows only (if enabled) + `skipped`/`bec.not_inbound`.
2. **Load (writer, every read echo-checked: organization, message, `received_at`, `scan_id` where applicable; mismatch → `error`/`inconsistent_read`, retryable, `scan_bec_inconsistent_reads_total{read}`):** the round's `email_scans` row (required engines), the dependency finals (`scan_engine_results` `is_final = 1` of `rspamd`, `url`), the `email_auth_results` row (`scan_id`, `engine = 'rspamd'`), `url_scan_results` of the scan (≤ 200, ordered by `url_seq`) joined in code with `message_urls` (`url_seq`, `registrable_domain`, `host`), `email_headers` of the message (≤ 200 rows; read as 201 so a truncated read is detected), `email_message_parses` (status, `limits_exceeded`, `defects`, body keys/hashes/sizes; absent → `error`/`parse_row_missing`, not retryable), `email_messages.subject`. **An incomplete header set** (`defects` contains `stored_headers_truncated`, i.e. the MIME stage stored only `MIME_MAX_STORED_HEADERS` of the allow-listed headers, or more than 200 rows are stored) means a Reply-To, Sender or Return-Path after the cap was never examined: the rules input carries `headersIncomplete` and E1 adds `bec.content_incomplete`, so the verdict is at least `unknown` (§2.0 invariant 1; review round 1, §12 "Review round 1").
3. **Tenant data** (writer, per-organization LRU, TTL `BEC_TENANT_DATA_CACHE_TTL_MS` 30 000, ≤ 1 000 organizations): active tenant domains, enabled executive profiles, enabled vendor profiles, unexpired trusted senders, unexpired suppression rules. A change applies within the TTL (documented in the API).
4. **Text** (B8): read the text body and HTML body from S3 with the 4.2/4.3 `S3PartReader` (key prefix `org/<org>/part/`, equal to the row, SHA-256 verified on full reads; `NoSuchKey` → `error`/`part_unavailable` not retryable; integrity → `part_integrity`; other S3 errors thrown → transient), at most `BEC_TEXT_MAX_BYTES` each (a body larger than the cap is read as a range and marked `incomplete`; no hash check on a partial read, recorded).
5. **Parse identities** (B5): From, Sender, Reply-To, Return-Path header, envelope sender, In-Reply-To/References presence.
6. **Deterministic rules** (B6) with the effective settings (B13), trusted senders (B7), suppressions (B11), lookalikes through `@email-gateway/url-security` (B5), history (B12, if enabled).
7. **AI layer** (B9/B10): local model (in-process) and/or LLM (gated, budgeted, timed out) in their modes; failures are recorded, never fail the attempt.
8. **Aggregate** with the invariant (B9) → engine result + child rows `{ bec: { result row, historyUpdates } }`, written by `ScanRepository.insertFinal` in the finalize transaction only when the final row was inserted (B14).

The engine call timeout `SCAN_BEC_TIMEOUT_MS` (45 000) covers everything. **Failure classes:** MySQL/S3/network → thrown (transient); wrong read, part integrity/unavailable/key mismatch, parse row missing → attempt failures (4.1 S5); LLM/local-model/Redis-budget problems → **never** an attempt failure (AI status recorded). `failureReasonCode`/`failureMetricReason` need no new code.

### B5. Identity parsing, normalization and lookalikes (`@email-gateway/bec` `identity/`)

- **Mailbox parser** (own code, bounded, no nodemailer): RFC 5322 `mailbox-list` / `address-list` subset over the stored decoded value: quoted strings with escapes, comments `(…)` (nested ≤ 4, dropped), angle addresses, bare `addr-spec`, groups `name: …;`, obsolete route `@a,@b:` dropped. Input ≤ 2 048 code points, ≤ 20 mailboxes, linear time (a single-pass tokenizer; tested with adversarial 2 048-character inputs). Output `{ displayName: string | null (trimmed, NFKC, ≤ 128 code points), address: string | null, localPart, domain (IDNA → A-label lower case via url-security `normalizeDomainInput`; invalid → null), flags: ('parse_error'|'multiple'|'display_name_truncated'|'idn')[] }`. For comparison both the local part and the domain are lower-cased (mail systems are case-insensitive in practice); the stored evidence keeps the parsed form.
- **Display-name normalization** for profile matching (`normalizeName`): NFKC → remove zero-width/bidi/format characters (`\p{Cf}`) and record `invisible_chars` → casefold → strip punctuation except letters/digits/spaces → collapse whitespace → token list; the **skeleton** of each token through url-security's UTS #39 `skeleton` (so `Аnita` with Cyrillic А matches `anita`). A profile name or alias matches when the token **set** of the display name contains all tokens of the profile name (order-insensitive, so `Sharma Anita` and `Anita Sharma (CEO)` match) or the full normalized strings are equal; single-token profile names (< 2 tokens) require an exact full match and ≥ 4 characters (false-positive control). Matching uses skeletons; the evidence records `match: 'exact'|'token_set'|'confusable'`.
- **Registrable domains:** url-security `registrableDomainOf`. **Free-mail list:** `packages/bec/data/freemail.txt` (≈ 120 entries: gmail.com, googlemail.com, yahoo.\* variants, outlook.com, hotmail.\*, live.\*, msn.com, aol.com, icloud.com, me.com, proton.me, protonmail.com, gmx.\*, mail.com, yandex.\*, zoho.com/zohomail.com, rediffmail.com, mail.ru, qq.com, 163.com, tutanota.com, …), versioned by its SHA-256 (part of the engine version), extended by tenant `freemailExtraDomains`.
- **Lookalikes:** one `ProtectedSet` per evaluation from url-security with `brands` (the packaged brands list or `URL_PROTECTED_BRANDS_FILE`), `tenantDomains` (active domains) and `extraDomains` = vendor profile domains ∪ url-security platform extra domains ∪ the url tenant settings' `lookalike.extraProtectedDomains` (read from the `url` engine settings row through the settings resolver; absent → none). `detectLookalikes` is applied to the From domain, the Reply-To domain(s) and the envelope sender domain. A finding whose `targetDomain` is a vendor domain is attributed to that vendor (`profileKind: 'vendor'`); `targetKind: 'tenant'` → tenant lookalike; `'brand'` → brand lookalike (L5 brand TLD variant stays informational). Thresholds are the URL engine's `URL_LOOKALIKE_*` platform values. **Nothing in url-security is copied or modified**; if a needed function is not exported, the implementer exports it from url-security and records it.
- **Alignment** (no re-evaluation of authentication, data from `email_auth_results` only): `dkimAligned` = some `dkim_signatures` entry with `result = pass` whose registrable domain equals the From registrable domain (relaxed alignment); `spfAligned` = `spf = pass` and the registrable domain of `spf_domain` (else of the envelope sender) equals the From registrable domain; `dmarcPass` = `dmarc = pass`. **Authenticated as From** = `dmarcPass || dkimAligned || spfAligned`.

### B6. Deterministic rules: verdict map `bec-map/1`

Pure function `evaluateBecRules(input, settings) → { firedRules, score, verdict, codes }` in `@email-gateway/bec` `rules/`. Every rule has a **stable id and reason code**, a **category**, a **severity** (`info`, `low`, `medium`, `high`, `critical`) and a **weight** (points, 0–100). Score = sum of the weights of fired, non-suppressed rules, with per-category caps (below), capped at 100. A rule fires at most once per message (several evidence entries allowed, ≤ 5). Each fired rule carries bounded evidence (B15).

**Categories:** `identity` (P, I, D), `auth` (A), `lookalike` (L), `impersonation` (X, V), `intent` (C, K1/K2), `link` (K), `history` (H), `engine` (E), `ai`. Category caps: `intent` ≤ 50, `history` ≤ 30, `identity` ≤ 40; others uncapped. **Structural evidence classes** used by B9: **identity evidence** = any fired rule of A1, A6, L1–L3, X1–X3, V1, V2, R3, D1, D2; **intent evidence** = any fired rule of C1–C6, C9, K1, V4.

**Engine-level rules** (codes also in the table of codes):

- **E0** `bec.not_inbound` → outcome `skipped` (B1).
- **E1** inputs: `bec.input_unavailable.auth` (auth `failed`/`missing`/`not_in_round`), `bec.input_unavailable.url` (url `failed`/`not_in_round`), `bec.content_incomplete` (text `incomplete`), `bec.history_unavailable` (history `error`; history `disabled` is not a code: it is a tenant choice, evidence `history: 'disabled'`). Any E1 → the verdict is **at least `unknown`** (never `clean`).
- **Verdict** (deterministic, `D`): `malicious` if score ≥ `maliciousScore` **and** identity evidence **and** intent evidence; `suspicious` if score ≥ `suspiciousScore`, or (score ≥ `maliciousScore` without both evidence classes); else `unknown` if any E1; else `clean` (`clean.below_threshold`, rule **C0**).
- **Reason codes** of the result: the fired, non-suppressed rule codes ordered by severity (critical → info) then weight then name, plus engine codes, ≤ 32. `signals`: one per fired rule `bec:<id>` with `score = weight` and options `["<category>"]` (≤ 200). `score` = final score; `requiredScore` = `suspiciousScore`; `action` null; `mappingVersion` `bec-map/1`.

`BEC_MAPPER_CODES` (in `@email-gateway/bec`) and `BEC_REASON_CODES` (in `security-contracts`, for the api and metric labels) hold the identical list: every code in the table above, the E-codes, `clean.below_threshold`, and the AI codes of B9 (`bec.ai.flagged`, `bec.ai.corroborated`, `bec.ai.disagrees`, `bec.ai.unavailable`). A contract test (WP3) asserts equality.

**Worked expectations** (fixture corpus, §9; default thresholds 40/80): CEO fraud (exec display name from Gmail, "need you to buy gift cards, keep this confidential") → X1 40 + X2 15 + C3 30 + C8 15 + C7 10 (intent cap 50) → 100 → `malicious`. Vendor invoice change from a lookalike → L2 40 + C5 20 + C2 25 + V4 35 → `malicious`. Reply-To to free-mail alone → R2 20 + R1 15 → 35 → `clean`/below threshold (+ I3/A4 if unauthenticated → `suspicious`). Legitimate executive email from a known, DKIM-aligned address → nothing fires → `clean`. Newsletter (bulk sender, return path on an ESP domain, DKIM-aligned) → P1 does not fire (DKIM aligned) → `clean`.

### B7. Trusted senders

- Table `bec_trusted_senders` (§3): `kind` `address` | `domain`, normalized value, `reason`, optional `expires_at` (≤ 365 days ahead; validated by the api), audit on create/delete.
- **Match:** exact lower-case address, or From registrable domain equal to a domain entry (subdomains match the registrable domain only when the entry is the registrable domain itself; no suffix wildcards).
- **Effect (T1, only when authenticated as From):** rules of categories `identity` (P1, P2, I2, I3, D1–D3, R1, R2), `history` (H1–H5), `intent` content rules (C1–C10, V4) and V1/V3 get weight 0 (listed as suppressed-by-trust in evidence). **Never neutralized:** A1–A6, L1–L4, R3, X1–X3 (an executive's name from a trusted vendor address is still impersonation), K1–K4, E-rules. Without authentication → T2 fires and nothing is neutralized (a spoofer cannot borrow trust). Trust is a BEC-engine concept only; it never touches other engines' verdicts (malware/URL engines unaffected).

### B8. Text analysis: bounded, multilingual, stored parts only

- **Sources:** `email_messages.subject`, the stored text body, the stored HTML body converted to text (parse5 7.3.0 tokenizer/tree: text nodes only; `script`, `style`, `head`, `template`, `noscript` skipped; block elements insert a newline; ≤ 50 000 nodes, else `incomplete`). Attachments are never read. Each source ≤ `BEC_TEXT_MAX_BYTES` (65 536 bytes UTF-8); the analysis text is at most `BEC_TEXT_MAX_CHARS` (40 000) code points total. `TEXT_DERIVATION_VERSION = 'bec-text/1'`.
- **Normalization for matching:** NFKC → remove `\p{Cf}` (zero-width, bidi) → casefold → map confusables to their skeleton for **Latin** tokens only (defeats `gіft card` with Cyrillic і; Devanagari untouched) → collapse whitespace. An offset map back to the source string is kept so evidence spans are offsets into the **source** (`{ source: 'subject'|'text'|'html_text', start, end }` in UTF-16 code units of the derived source text, reproducible with `bec-text/1`).
- **Lexicons** (data, `packages/bec/data/lexicon/*.json`, versioned by a SHA-256 over the files → `lexiconVersion` part of the engine version): one file per language: `en.json`, `hi.json` (Devanagari), `hi-Latn.json` (Hinglish/romanized Hindi). Entry `{ id: 'en.gift_card.003', category, phrase, weight?: 1 }`; categories `payment_request`, `bank_change`, `gift_card`, `wire_transfer`, `invoice_change`, `payroll_change`, `urgency`, `secrecy`, `credential_request`, `authority` (informational: "CEO", "MD sir", "boss"). Matching is **phrase matching on token sequences** (Unicode word tokens `[\p{L}\p{M}\p{N}]+`), compiled into a token trie at load: linear time, no user-controlled regular expressions. Minimum content: English ≥ 15 phrases per category; Hindi ≥ 5 per category for `payment_request`, `bank_change`, `gift_card`, `wire_transfer`, `urgency`, `secrecy` (e.g. `भुगतान कर दो`, `बैंक खाता बदल`, `गिफ्ट कार्ड`, `तुरंत`, `अभी`, `किसी को मत बताना`, `गोपनीय`); Hinglish ≥ 5 per same categories (e.g. `payment kar do`, `paise transfer karo`, `account number badal gaya`, `gift card bhejo`, `turant`, `jaldi karo`, `kisi ko mat batana`, `abhi ke abhi`). Tenants cannot edit lexicons in this step (§10).
- **Pattern detectors** (C10, hand-written linear scanners, no backtracking regex): IBAN (2 letters + 2 digits + 11–30 alphanumerics, mod-97 valid), SWIFT/BIC (8 or 11, context word "swift"/"bic" within 5 tokens), IFSC (`[A-Z]{4}0[A-Z0-9]{6}`) near an account number (9–18 digits), currency amounts. Only counts and categories are recorded.
- **Bounds:** ≤ 5 evidence spans per category, ≤ 64 matches total; `BEC_TEXT_TIMEOUT_MS` (2 000) for extraction and matching together (exceeded → attempt failure `timeout`/`extract_timeout`, retryable, as in 4.3).

### B9. The AI layer and the aggregation invariant (ADR-0034)

- **Providers** behind one interface (`@email-gateway/bec` `ai/`):

```ts
interface BecAiProvider {
  readonly kind: 'local' | 'llm';
  readonly modelId: string; // 'bec-lr' | 'claude-opus-5-5' | 'fake'
  readonly modelVersion: string; // 'bec-lr/1@<sha256 first 12 of weights>' | provider-reported model id
  assess(input: AiInput, signal: AbortSignal): Promise<AiAssessment>;
}
interface AiInput {
  features: Record<string, number | boolean>;
  excerpt: RedactedExcerpt | null;
}
interface AiAssessment {
  status:
    | 'ok'
    | 'timeout'
    | 'error'
    | 'refused'
    | 'invalid_output'
    | 'budget_exceeded'
    | 'skipped'
    | 'circuit_open';
  labels: Array<{ label: 'bec' | 'phishing' | 'benign' | 'spam'; confidence: number /* 0..1 */ }>; // ≤ 4
  confidence: number | null; // of the top label
  citedFeatures: Array<{ feature: string; contribution: number }>; // ≤ 8, feature ∈ AI_FEATURE_NAMES
  spans: Array<{
    source: 'subject' | 'text' | 'html_text';
    start: number;
    end: number;
    label: string;
  }>; // ≤ 8, mapped to source offsets
  indicators: string[]; // ≤ 8, from the fixed AI_INDICATORS enum (no free text)
  modelId: string;
  modelVersion: string;
  promptTemplateVersion: string | null; // LLM only: 'bec-llm-prompt/1'
  responseSha256: string | null; // SHA-256 of the canonical JSON of the validated output
  durationMs: number;
}
```

- **Modes** (`off` | `shadow` | `active`), per layer: platform `BEC_LOCAL_MODEL_MODE` (default **`shadow`**) and `BEC_LLM_MODE` (default **`off`**) are **caps**; tenant settings `ai.localModel`, `ai.llm` choose within the cap (`off < shadow < active`); default for tenants = the platform value for the local model, `off` for the LLM (explicit opt-in). Shadow: the assessment is computed and stored in `bec_scan_results.ai_shadow`, never applied. A model can additionally be configured as a **shadow model** (`BEC_LOCAL_MODEL_SHADOW`) that runs next to the active one (B16).
- **Aggregation** (pure `combineVerdict(D, scoreD, evidence, applied: AiAssessment[], settings)`), with `A⁺` = the strongest applied assessment with status `ok`, top label ∈ {`bec`, `phishing`}:
  1. `D = malicious` → `malicious`.
  2. `D = suspicious`, `aiMaliciousBand > 0`, `scoreD ≥ maliciousScore − aiMaliciousBand`, identity evidence **and** intent evidence fired, `A⁺.confidence ≥ BEC_AI_CORROBORATE_CONFIDENCE` (0.9) → `malicious`, code `bec.ai.corroborated`.
  3. `D = suspicious` → `suspicious`.
  4. `D ∈ {clean, unknown}`, `A⁺.confidence ≥ aiRaiseConfidence` (platform `BEC_AI_RAISE_CONFIDENCE` 0.8; tenant may lower to ≥ 0.6 or raise ≤ 0.99) → `suspicious`, code `bec.ai.flagged`.
  5. otherwise `D`; an applied `benign` assessment with `D ∈ {suspicious, malicious}` adds `bec.ai.disagrees` (informational, never lowers); an applied provider whose status ≠ `ok` adds `bec.ai.unavailable` (informational).
     The AI never changes the deterministic score (`deterministic_score` and `score` are stored separately; `score` = `deterministic_score` unless rule 2/4 applied, in which case `score` = max(`deterministic_score`, `suspiciousScore`) resp. `maliciousScore`).
- **Invariant (tested exhaustively and by property tests):** (P1) final `clean` ⇒ `D = clean`; (P2) final `malicious` ⇒ `D ∈ {suspicious, malicious}` and identity + intent evidence and `scoreD ≥ maliciousScore − aiMaliciousBand` (`aiMaliciousBand` validated 0..15); (P3) final severity ≥ `D` severity (AI never lowers); (P4) with no deterministic rule fired, final ∈ {`clean`, `unknown`, `suspicious`}; (P5) shadow assessments never change the final verdict, reason codes or score; (P6) any AI status other than `ok` leaves the verdict equal to `D`.
- **Local model `bec-lr/1`:** binary logistic regression (label `bec_or_phishing` vs `benign`) over `AI_FEATURE_NAMES` (fixed, ~60): one boolean per deterministic rule id (P1…K4, H1…H5, T1, T2), per-category lexicon match counts (`log1p`), pattern counts, `fromFreemail`, `replyToPresent`, `displayNameMatchesProfile`, `urlCount` (log1p), `textLength` bucket, `isReply`, `authenticatedAsFrom`. Output labels `[bec|benign]` (top label `bec` if p ≥ 0.5, confidence = max(p, 1 − p)); `citedFeatures` = top 5 |weight × value| contributions; `spans` = the lexicon spans of the cited lexicon features. Weights in `packages/bec/models/bec-lr-1.json` (`{ id, version, features[], weights[], bias, trainedOn: { fixtureSet: 'bec-train/1', sha256 }, metrics: { accuracy, precision, recall } }`) and `packages/bec/models/manifest.json` (`[{ id, version, file, sha256, status: 'available' }]`). **Training** (`pnpm --filter @email-gateway/bec model:train`): deterministic batch gradient descent (fixed learning rate, iterations, L2, zero init, features in fixed order) over `packages/bec/training/bec-train-1.jsonl` (≥ 200 synthetic labelled feature records generated from the fixture corpus templates by a committed, seeded generator; no real mail); `model:check` (run by the package test) retrains, asserts the committed weights are reproduced within 1e-9 and the manifest SHA-256 matches, and asserts minimum metrics on a held-out split (recall ≥ 0.9, precision ≥ 0.9). Retraining from tenant feedback exports (B11) is an offline, documented procedure producing `bec-lr/2` (out of scope to run here).
- **LLM provider** (B10).

### B10. The LLM provider: Anthropic Claude via the official SDK

- **Choice:** no LLM provider exists in the repository; the first is **Anthropic Claude through `@anthropic-ai/sdk`** (TypeScript, pinned exact version published ≥ 14 days before implementation, recorded). Model `BEC_LLM_MODEL` default **`claude-opus-5-5`** (configurable to another current Claude model id by the operator; the result records the model id the API reports in `response.model`).
- **Request:** `client.beta.messages.create({ model, max_tokens: BEC_LLM_MAX_OUTPUT_TOKENS (4 096), system: <template bec-llm-prompt/1>, messages: [{ role: 'user', content: <JSON of { features, excerpt }> }], output_config: { effort: 'low', format: { type: 'json_schema', schema: <BEC_LLM_OUTPUT_JSON_SCHEMA> } }, betas: ['server-side-fallback-2026-07-01'], fallbacks: 'default' }, { timeout: BEC_LLM_TIMEOUT_MS, maxRetries: 0 })`. No `thinking` parameter (adaptive thinking is always on for this model; depth is controlled by `effort`), no `temperature`/`top_p`. **Refusal fallback:** the server-side `fallbacks: 'default'` (beta `server-side-fallback-2026-07-01`) is enabled by default (`BEC_LLM_REFUSAL_FALLBACK=default`; `off` removes `betas`/`fallbacks` and uses `client.messages.create`). The implementer verifies the exact SDK shapes against the installed SDK's types and the official docs (never guessed) and records any deviation.
- **Structured output:** a hand-written strict JSON Schema (`additionalProperties: false`, every property `required`): `{ labels: [{ label: enum, confidence: number }] (1..4), indicators: enum[] (0..8; AI_INDICATORS: 'executive_impersonation','vendor_impersonation','payment_redirection','gift_card_request','wire_request','payroll_change','urgency','secrecy','credential_request','lookalike_sender','reply_to_redirection','unusual_request','benign_business','newsletter','transactional'), citedFeatures: [{ feature: enum AI_FEATURE_NAMES, weight: number }] (0..8), spans: [{ start: integer, end: integer, indicator: enum }] (0..8) }`. No free-text field. The response is parsed with `JSON.parse` and validated with the package's zod schema (confidence 0..1, spans within the excerpt, `start < end`); any failure → `invalid_output`. `stop_reason === 'refusal'` (after fallbacks) → `refused`; `max_tokens` → `invalid_output`. `responseSha256` = SHA-256 of the canonical (sorted-key) JSON of the validated output; the raw response text is never stored or logged.
- **Data minimization (`buildExcerpt`, pure, unit-tested):** the excerpt is built only from the analysis text: up to 3 windows of ±200 characters around the strongest lexicon matches (or the first 600 characters when nothing matched), ≤ `BEC_LLM_MAX_EXCERPT_CHARS` (1 500) in total, plus the subject (≤ 200). Redaction (in this order, every replacement recorded as a count): e-mail addresses → `[EMAIL]`, URLs and domain-like tokens → `[URL]`, IBAN/account/IFSC/SWIFT/card-like digit runs and any digit run ≥ 4 → `[NUMBER]`, phone numbers → `[PHONE]`, executive/vendor profile names and aliases → `[EXECUTIVE]`/`[VENDOR]`, tenant domain labels → `[ORG]`. Features sent: the AI feature vector (booleans, counts) and categorical identity facts (`fromDomainKind: 'freemail'|'tenant'|'vendor'|'lookalike'|'external'`, `replyToKind`, `displayNameMatch: 'executive'|'vendor'|'brand'|'none'`, `authenticatedAsFrom`). **Never sent:** addresses, display names, domains, header values, attachment data, full bodies, organization ids/names, message ids, secrets. Spans returned by the model refer to the excerpt and are mapped back to source offsets through the window map; unmappable spans are dropped.
- **Gating:** the LLM runs only when its mode is `shadow`/`active` for the tenant, the direction is inbound, inputs are not all missing, and the deterministic score is in `[BEC_LLM_MIN_SCORE (15), maliciousScore)` or any intent rule fired (definite malicious and obviously empty messages are not sent).
- **Budgets and resilience:** per-tenant daily call budget (`ai.llmDailyCallLimit`, ≤ platform `BEC_LLM_MAX_CALLS_PER_TENANT_PER_DAY` 1 000) and a platform per-minute budget (`BEC_LLM_MAX_CALLS_PER_MINUTE` 120), Redis fixed windows (`eg:bec:llm:t:<org>:<yyyymmdd>`, `eg:bec:llm:m:<epochMinute>`, Lua `INCR`+`EXPIRE`); exceeded → `budget_exceeded`; Redis error → `skipped` (`budget_unavailable` metric) — **never call without a budget check**. Concurrency `BEC_LLM_CONCURRENCY` (4 per process). Breaker `BEC_LLM_BREAKER_THRESHOLD` (5) / `_RESET_MS` (60 000) → `circuit_open`. Timeout `BEC_LLM_TIMEOUT_MS` (20 000, < `SCAN_BEC_TIMEOUT_MS`). Errors are classified with the SDK's typed error classes (never message text). No call when `BEC_LLM_API_KEY` is empty (config refuses mode ≠ `off` without a key).
- **Recorded per result:** provider `anthropic`, model id (reported), prompt template version `bec-llm-prompt/1` and its SHA-256 (template file in the package), response hash, status, labels, confidence, indicators, cited features, mapped spans, input/output token counts (metrics only), duration.
- **Tests never call a real LLM:** the provider takes an injected `fetch` (SDK client option) or a transport; unit tests use recorded fixture responses (valid, refusal, `max_tokens`, schema violation, extra fields, out-of-range confidence, spans out of bounds, 429/500/timeout) and assert the request body (model, `output_config`, no forbidden content: a fixture with marker strings in addresses, names, URLs and digits must not appear in the serialized request). Integration/stack runs use **`BEC_LLM_PROVIDER=fake`** (a deterministic in-process provider keyed by indicators; refused when `NODE_ENV=production`). `BEC_LLM_PROVIDER` ∈ `anthropic` | `fake` (default `anthropic`).

### B11. Feedback, suppression and retraining export

- **Feedback** (`bec_feedback`, §3): an analyst records `false_positive` or `false_negative` against a **bec result of a scan** (`POST /api/v1/messages/{messageId}/scans/{scanId}/bec-feedback`), with optional disputed `reasonCodes` (⊂ the result's codes for FP), an optional `note` (≤ 500 characters, never exported, documented as "do not paste message content"), audited `bec_feedback.recorded`. Idempotent per `(scan, user, kind)` (unique key; a repeat returns `409 feedback_exists`).
- **Suppression** (only from a false-positive feedback, optional block `suppress: { codes: [...], scope: 'address' | 'domain', days: 1..90 }`): creates rows in `bec_suppression_rules` `(organization, reason code, sender scope, sender value = the From address or registrable domain of the scanned message, expires_at, feedback id, created_by)`. **Bounds:** only **suppressible** codes: P1, P2, I2, I3, D1, D3, R1, R2, V3, C1, C4, C5, C7, C8, C10, H1, H3, H4, H5 (never A*, L*, R3, X*, V1, V2, V4, C2, C3, C6, C9, K*, E*, T2, AI codes); ≤ `BEC_SUPPRESSIONS_MAX_PER_TENANT` (200) active rows; expiry ≤ 90 days (no permanent suppression; renew by new feedback); at use, the total weight suppressed in one message is capped at `BEC_SUPPRESSION_MAX_WEIGHT` (40, ordered by weight desc then code); a `domain` scope is refused for free-mail domains (it would suppress for every Gmail user). Suppressed rules appear in evidence with `suppressed: 'feedback'` and S1 fires. Rows are listed and deletable (`DELETE` audited).
- **False negatives** are recorded only (no automatic raising rule in this step: raising from tenant feedback is a tenant-poisoning channel for verdicts on other senders; §10).
- **Export for retraining** (`GET /api/v1/bec/feedback/export?from=&to=` NDJSON, ≤ 10 000 records, cursor): per feedback `{ feedbackId, kind, createdAt, rulesVersion, engineVersion, localModel: { id, version } | null, llm: { modelId, promptTemplateVersion } | null, firedCodes, deterministicScore, score, verdict, deterministicVerdict, features: <AI feature vector stored with the result>, aiLabels }`. **No** bodies, excerpts, spans text, addresses, display names, domains, notes or message ids. Audited `bec_feedback.exported`.

### B12. Historical communication context (ADR-0035)

- **Opt-in:** tenant setting `history.enabled` (default `false`), `history.retentionDays` (30..`BEC_HISTORY_MAX_RETENTION_DAYS` 730, default 365). Disabled → no reads, no writes, evidence `history: 'disabled'`, H-rules never fire. Turning it off does not delete rows (explicit purge: `DELETE /api/v1/bec/history`, audited, deletes the tenant's rows in batches of 5 000).
- **Table `bec_contact_history`** (not partitioned; aggregate rows): `(organization_id, scope, key_hash)` unique; `scope` `sender` (key = From address) | `pair` (key = (external address, internal address, direction-insensitive canonical order)); `key_hash` = HMAC-SHA256(`BEC_CONTEXT_HMAC_KEY`, `"eg-bec-ctx/v1\0" ‖ organizationId ‖ "\0" ‖ scope ‖ "\0" ‖ canonical key`) hex; `message_count` (saturating at 2³²−1), `first_seen_at`, `last_seen_at` (message `received_at`), `inbound_count`, `outbound_count` (pairs), `infra` JSON (sender scope only: ≤ 8 `{ fp: <first 16 hex of HMAC of the fingerprint>, count, lastSeenAt }`, LRU by `lastSeenAt`). **No plaintext address, domain, IP or name.** Infrastructure fingerprint = the DKIM-aligned signing registrable domain if any, else the SPF-pass domain if any, else the client IP network (/24 IPv4, /48 IPv6) — from the trusted envelope and the auth row only.
- **Reads** (scan time, writer, echo-checked on `organization_id` + `scope` + `key_hash`): the sender row and the pair rows of (From, each envelope recipient) for ≤ `BEC_HISTORY_MAX_RECIPIENTS` (50) recipients. "First seen at this message" = `first_seen_at = received_at` (so a rescan sees the same history as the first scan, because the update of round 0 is the only write).
- **Writes:** child rows of the bec final of **round 0 only** (`scan_kind = initial`): `INSERT … ON DUPLICATE KEY UPDATE message_count = message_count + 1, last_seen_at = GREATEST(…), first_seen_at = LEAST(…), …` via `$executeRaw`, keys sorted (deadlock-free order), ≤ 51 rows per message; inbound: sender row + pairs (inbound_count) **only when the message authenticated as its From (`authenticatedAsFrom`) and the final bec verdict is `clean` or `unknown`** (review round 1, ADR-0035 amendment: spoofed or flagged warm-up mail never makes a sender or its infrastructure "known"); outbound/internal (B1 `skipped`): pairs with the internal sender and each external recipient (outbound_count) — outbound mail is what makes the replies known. The `infra` JSON update is a read-modify-write under the row lock (`SELECT … FOR UPDATE` in the finalize transaction) — bounded, one row.
- **Retention sweeper** (email-worker, leader `AdvisoryLocks` `scan:bec-history`, every `BEC_HISTORY_SWEEP_INTERVAL_MS` 3 600 000): per organization with history rows, delete rows with `last_seen_at < now − retentionDays` (tenant setting, else default) in batches of 1 000 (`SCAN_DB_TIMEOUT_MS` transactions); organizations with history disabled for more than `retentionDays` lose their rows too. Metric `bec_history_rows_deleted_total`.
- **Key rotation:** a new `BEC_CONTEXT_HMAC_KEY` makes old rows unreachable (history restarts; old rows expire by retention). Documented in the runbook. The key is held only by the bec-consuming email-worker.

### B16. Model versioning

- **Recorded per result:** `engine_version` = `bec/1;lex=<8 hex>;fm=<8 hex>;br=<8 hex>` (≤ 64), `rules_version` = `bec-map/1`, `text_version` = `bec-text/1`, and per assessment `modelId`, `modelVersion` (local: `bec-lr/1@<12 hex>`), `promptTemplateVersion` (LLM), mode (`active`/`shadow`).
- **Registry = configuration + packaged manifest** (not a table): `packages/bec/models/manifest.json` lists the available local models (id, version, file, SHA-256); `BEC_LOCAL_MODEL` (default `bec-lr/1`) is the active model, `BEC_LOCAL_MODEL_SHADOW` (default empty) an optional second model run in shadow; the worker refuses to start if either is not in the manifest or its file hash differs. The LLM model is `BEC_LLM_MODEL`; its shadow counterpart `BEC_LLM_SHADOW_MODEL` (default empty; budgets count both calls). Rationale: model artefacts are code (reviewed, version-controlled, reproducible via `model:check`), and switching active/shadow is a deploy-time change with an audit trail in Git; a table would add an API and a second source of truth (§7). `scan_engine_info{engine="bec",version}` gauge plus `bec_model_info{layer,model,version,mode}`.

### B17. Development pass-through and BEC verdicts

`DevPassThroughApprover` (local/ci stand-in for policy): in addition to `verdict = malicious` (4.2 A15), a `scanned` round whose `scanned.v1.engines` entry for `bec` has outcome `suspicious` or `malicious` **and whose `bec_scan_results.deterministic_verdict` is `suspicious` or `malicious`** (writer read in the ledger transaction, echo-checked; a missing row is held, fail-safe) is **not approved**: ledger row, `delivery_approvals_skipped_total{reason="bec_verdict"}`, info log (ids, outcome). ## 6. Prisma wrong-read mitigation in this step (4.2 §6)

New interactive transactions: the bec finalize (existing `SCAN_DB_TIMEOUT_MS`), the history sweeper batches (`SCAN_DB_TIMEOUT_MS`), every api write (120 s budget, 10 s `maxWait`, the threat-indicator pattern). Every read whose result decides a verdict, a trust/suppression, a history rule or an api write is echo-checked (identifying columns selected and compared); a mismatch is retryable (engine: `inconsistent_read` attempt failure; api: `503` with code `inconsistent_read` after one retry, as the threat-indicator service does). No socket timeout. No new code uses Prisma's default 5 s interactive budget.

## 7. Alternatives considered

- **Reuse `scan.auth` for BEC:** no new queue, but the queue name misleads operators and removes the reserved slot for a first-party authentication engine; rejected (B1).
- **BEC consumes `parsed.v1` and reads whatever results exist:** order-dependent verdicts (the same message classified differently depending on which engine finished first) and silent `not available` on most messages; rejected. **Deferral by retry** (return a retryable "not ready" until the dependencies finish): consumes attempts and broker hops, adds backoff latency (2 s, 4 s, 8 s …) and non-final rows of noise; rejected. **In-process polling:** holds consumer slots; rejected. **A central second-stage orchestrator queue:** a saga ADR-0026 rejected. The chosen trigger is written in the transaction that makes the dependencies complete, under the locks that already serialize completion: exactly once, no polling, minimal latency.
- **BEC as Rspamd rules/plugins (Lua):** Rspamd lacks tenant profiles, history and URL engine results; explainability per tenant would live in Lua maps; rejected.
- **LLM as a required classifier / verdict authority:** violates the brief; rejected. **LLM on every message:** cost, latency and data exposure; gated to borderline and intent-bearing messages.
- **Free-text rationale from the LLM:** could echo content into the database; rejected in favour of enumerated indicators and offsets.
- **Other LLM vendors / local open-weight LLM:** no existing provider choice; Anthropic through the official SDK behind the provider interface; another provider can be added behind the same interface later.
- **Model registry table:** needs an API, audit and cache invalidation for something that changes with deployments; configuration + packaged manifest chosen (B16).
- **Storing plaintext correspondents for history:** a cross-message address book of every tenant's correspondents is high-value personal data; keyed hashes give the same equality checks; rejected (ADR-0035).
- **Tenant-editable lexicons/rule weights:** deferred (§10); suppression with bounds is the tenant lever.
- **Feedback that automatically raises verdicts (FN → new block rule):** cross-sender poisoning risk; recorded only.
- **nodemailer `addressparser`:** advisory history noted in step 3.1; own bounded parser.

| Risk                                                                                         | Mitigation                                                                                                                                                |
| -------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |

### Review round 1 (2026-11-07): findings and fixes

Five findings (medium and above) of the close-out review, each confirmed against the code before fixing; every fix has unit and integration tests, and each new integration test was checked to fail without its fix (negative control).

1. **High — a truncated header set could be `clean` (§2.0 invariant 1).** Confirmed: the MIME stage stores at most `MIME_MAX_STORED_HEADERS` (200) allow-listed headers and records the overflow only as the defect `stored_headers_truncated`; `PrismaBecStore.loadParse` did not select `defects` and `loadHeaders` read `take: 200`, so a Reply-To after 200 `Authentication-Results` lines was never seen and the result was `clean.below_threshold`. 3. **Medium — rolling upgrade can leave `bec` required but never triggered.** Confirmed (the required set is fixed by the replica that opens the round; only step 4.4 code writes the trigger).
