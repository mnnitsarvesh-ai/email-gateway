## 2. Decisions

### 2.0 Invariants (never traded away)

1. **Never clean by accident.** An attachment that was not extracted (encrypted, unsupported type, image without OCR, PDF without text layer, oversize, not stored, parse error, archive or resource limit, attachment cap), a truncated text source, a parse that may hide parts, a custom pattern that could not run on all text, or a wrong read is never `clean`: it is a coverage reason code and the verdict is at least `unknown` (D10). `clean` requires complete coverage and no reportable finding.
2. **No full sensitive value outside encrypted evidence.** Matched values never appear in logs, metric labels, events, `scan_engine_results`, `dlp_scan_results`, the scans read API, the incidents API, error messages or audit metadata — only **masked** forms (D15), counts, codes, offsets and ids. The only place a raw value may exist at rest is the envelope-encrypted evidence object (D16), and **never** for Aadhaar numbers, private keys or secret credentials (masked even there).
3. **Evidence is readable only through one audited door:** `GET …/dlp-evidence` with `dlp:evidence_read` + MFA, an audit row committed **before** any byte is decrypted (D16).
4. **Engines classify; the DLP policy decides the DLP action; the delivery stage applies it.** The `dlp` engine records findings and the action its tenant policy yields; it never delivers, quarantines or rejects. The dev pass-through (now) and policy 5.2 / quarantine 5.3 (later) apply the action through the lifecycle state machine, and may only be **stricter** than the DLP action, never weaker (ADR-0037).
5. **Deterministic policy evaluation:** the action is a pure function of (findings, coverage, direction, envelope, tenant policy snapshot, exceptions, now); rule order never depends on database or input order (D11).
6. **Bounded, linear-time detection.** Built-in detectors are hand-written scanners or anchored checks on short tokens; tenant regexes run only on RE2 semantics (`re2js`, no backtracking) after validation (D9); every input, match list, finding list and evidence blob is capped by validated configuration; extraction of untrusted formats runs only in the resource-limited child (D4).
7. **Idempotent per (message, round, engine)** through the 4.1 orchestrator (`processOnce`, unique final row), unique keys on `dlp_scan_results (scan_id, received_at)` and `dlp_evidence (scan_id, received_at)`, and the incident outbox row written in the same transaction as the final row.
8. **Tenant from trusted context.** The worker takes the organization from the envelope checked against the writer rows; the api from the authenticated scope (never headers or bodies). One tenant's policies, patterns, dictionaries, exceptions and compliance setting never influence another tenant's result; evidence AAD binds organization, message and scan.
9. **Aadhaar detection only with a recorded compliance basis** (D17); without it the detector does not run at all (no counts, no masked values).

### D1. One `dlp` engine on `scan.dlp`, stage 1, required for every tenant

- **Catalog** (`security-contracts`): `{ name: 'dlp', stage: 'dlp', queue: 'scan.dlp', requiredByDefault: true, tenantMayDisable: false, description: 'Data loss prevention: card, bank, national id, passport, personal, confidential, source code, credential, financial and tenant patterns; attachment text extraction; outbound policy actions (step 4.5)' }` — **no `dependsOn`** (stage 1). `SCAN_ENGINES` default becomes `rspamd,attachment,url,bec,dlp`.
- **Independent of the other engines.** DLP reads the stored text parts and attachment bytes itself; it needs no verdict of rspamd, url, attachment or bec. It **reuses the attachment engine's code** — the archive walker, file-type detection, limits and the inspector child pool (D4) — with the **same** platform archive limits (`ATTACHMENT_ARCHIVE_MAX_DEPTH`, `_MAX_ENTRIES`, `ATTACHMENT_MAX_ENTRY_BYTES`, `_MAX_DECOMPRESSED_BYTES`, `_MAX_COMPRESSION_RATIO`), so DLP reaches exactly the entries 4.2 reaches. Not a stage-2 dependent of `attachment`: that would add the ClamAV/YARA latency (up to its 6 × 180 s budget) before DLP, couple DLP to the attachment engine's failures (a stage-2 trigger fires even on a dependency failure, so nothing would be gained for completeness) and the attachment engine stores no text (§7).
- **Directions:** `outbound` and `internal` → always scanned. `inbound` → scanned only when the tenant setting `inboundEnabled` is true (default false); otherwise a definite **`skipped`** final with `dlp.not_inbound` (fast, no S3 read). Direction is `ctx.direction` (`email_messages.direction`, trusted).
- **Required:** yes, for every direction (inbound rounds finish fast with `skipped`). Outbound approval therefore always waits for the DLP final, which carries the policy action: **outbound policy evaluation happens before delivery approval** by construction (D13).
- **Consumer:** email-worker scan role, broker user `eg-scanner`, ledger consumer **`email-worker.scan.dlp`**, registration `dlpRegistration` in `ENGINE_REGISTRY` (after `becRegistration`). Production: Deployment `email-worker-dlp` (`SCAN_CONSUMERS=dlp`), the only email-worker Deployment holding `DLP_EVIDENCE_KEY`.
- **Budgets:** `SCAN_DLP_CONCURRENCY` 4, `SCAN_DLP_TIMEOUT_MS` 120 000, `SCAN_DLP_MAX_ATTEMPTS` 3. Deadline rule of 4.4 B2 unchanged: `B(dlp) = 3 × (120 + 60) = 540 s` < `B(url) = 1 080 s`, so the stage-1 maximum and the default 1 800 s deadline are unchanged; config validation already enforces the rule.
- **Rolling upgrade:** two phases like 4.4 (new image everywhere with `SCAN_ENGINES` unchanged, then add `dlp`); a replica that opens a round with `dlp` required while no replica consumes `scan.dlp` ends that round `scan_failed` at its deadline (never clean). Documented in the deployment doc and runbook.

### D3. Data flow of one `dlp` call (`DlpEngine.scan(ctx, signal)`)

1. **Settings** (D18) from `ctx.settings`; **direction** check (D1) → `skipped`/`dlp.not_inbound`.
2. **Load (writer, every read echo-checked on organization, message, `received_at`; mismatch → attempt failure `error`/`inconsistent_read`, retryable, `scan_dlp_inconsistent_reads_total{read}`):** `email_messages` (`subject`, `envelope_from`, `header_from`, `direction` echo), `email_message_parses` (status, `limits_exceeded`, `defects`, body keys/hashes/sizes; absent → `error`/`parse_row_missing`, not retryable), `email_attachments` ordered by `part_index`, read `DLP_MAX_ATTACHMENTS + 1` rows (more → the extra ones are `not_extracted`/`attachment_cap`), active tenant domains (`domains` of the organization with an active status — the same rule the bec engine uses; for external-recipient classification).
3. **Tenant data** (writer, per-organization LRU ≤ 1 000 organizations, TTL `DLP_TENANT_DATA_CACHE_TTL_MS` 30 000): enabled policies and their enabled rules, unexpired enabled exceptions, enabled custom patterns (compiled once per row version, D9), enabled dictionaries (compiled into one phrase trie per organization snapshot, D8), the compliance row (D17). Echo-checked. A change applies within the TTL (documented in the API).
4. **Text sources** (D4): subject; stored text body (`readPrefix` up to `DLP_BODY_MAX_BYTES`, truncated → `dlp.text.truncated`; full reads are SHA-256 checked); stored HTML body → `htmlToText` from `@email-gateway/bec` (node cap reached → `dlp.text.truncated`); attachment filenames (keyword detectors only); attachments through the extractor child (D4). `NoSuchKey` → attempt failure `part_unavailable` (not retryable); integrity → `part_integrity`; other S3 errors thrown (transient).
5. **Detection** (D5–D9, `@email-gateway/dlp` `detect()`): chunked (`DLP_SCAN_CHUNK_CHARS` 65 536 with a 512-code-unit overlap; matches de-duplicated by source offset), the event loop is yielded (`setImmediate`) between chunks, `Deadline` of `DLP_DETECT_TIMEOUT_MS` (15 000) → attempt failure `timeout`/`extract_timeout` (retryable). _Closer review 2026-11-08:_ the deadline runs on a `WorkClock` (`@email-gateway/dlp`) that is paused while `detect()` yields the loop, so it bounds the message's own detection work and the time other concurrent scans run on the shared loop does not count; the whole call stays bounded in wall time by `SCAN_DLP_TIMEOUT_MS`.
6. **Classification** (D7): confidence per candidate, reportable findings, per-category aggregates, coverage.
7. **Policy** (D11, D12): `evaluateDlpPolicy` → action, winning rule, matched rules, exceptions applied, `policyVersion`.
8. **Evidence** (D16) when there is a reportable finding and evidence is enabled: build (bounded), seal (envelope encryption), `PutObject` to `org/<org>/dlp-evidence/<yyyy>/<mm>/<scanId>-<uuidv7>.bin` **before** the finalize transaction (an object without a committed row is undecryptable by construction: its data key exists only in the row).
9. **Result** → `EngineDefinite` with child rows `{ dlp: { result, evidence | null, incident | null } }`; `ScanRepository.insertFinal` writes `dlp_scan_results`, `dlp_evidence` and the `mail.message.dlp_incident.v1` outbox row after the final row in the same transaction, only when the final row was inserted. When the final was **not** inserted (a duplicate finalizer) or the transaction throws, the engine deletes its own evidence object (best effort, `dlp_evidence_writes_total{result="orphan_deleted"|"orphan_left"}`).

The engine call timeout `SCAN_DLP_TIMEOUT_MS` covers everything. **Failure classes:** MySQL/S3/network → thrown (transient); wrong read, part integrity/unavailable/key mismatch, parse row missing → attempt failures (4.1 S5); extractor wall-clock timeout → `inspector_timeout`, extractor crash → `inspector_crash` (retryable, reused codes); extractor CPU/RSS kill → a **definite** `not_extracted`/`resource_limit` for that attachment (a property of the file, as 4.2 rule S3); detection deadline → `extract_timeout`. No new failure code is needed in `engine.ts`.

### D4. Attachment text extraction (reusing the 4.2 walker and pool)

- **Where:** in a **DLP extractor child** of a second `InspectorPool` instance (`DLP_EXTRACTOR_POOL_SIZE` 2), same isolation as the 4.2 inspector: empty environment, IPC only, Node permission model (reads of the application directory only, no child processes, no writes), heap cap `DLP_EXTRACTOR_HEAP_MB` (256), on Linux `prlimit --cpu --core=0`, CPU/RSS sampling (`DLP_EXTRACT_CPU_SECONDS` 10, `DLP_EXTRACT_MAX_RSS_MB` 512), wall clock `DLP_EXTRACT_TIMEOUT_MS` (20 000) per attachment, recycling after `DLP_EXTRACTOR_MAX_JOBS` (200), FIFO wait queue. No content is executed: no JavaScript in PDFs (`isEvalSupported: false`), no macros, no external entities, no network, no files.
- **Generalized pool (no duplication):** `InspectorPool` gains a child descriptor (`childEntry`, `childArgs`, `ready` validator) and a generic job method; the attachment engine's construction and behaviour are unchanged (same handshake check of the YARA bundle id, same outcomes, same metrics). The protocol gains `{ op: 'extract', id, bytes, limits: ExtractLimits, hint: { declaredContentType, filenameExt } }` → `{ op: 'result', id, ok: true, extraction }` and a ready message `{ op: 'ready', kind: 'dlp-extractor', extractorVersion }`. The extractor child module graph never imports `child_process` (unit test as for the inspector) and never imports `@email-gateway/bec` or the AI SDK.
- **Shared walker (no duplication):** the zip/gzip/tar walk of `inspect.ts` (class `Walk`, `walkNested`, `walkZip`, `walkGzip`, `walkTar`, `readCounted`, `countEntry`) gains an **optional entry visitor** `onEntry(data, path, depth, type, ext, name)` called for every inspected entry after type detection; `inspectBytes` passes none and YARA keeps running through its existing engine (the extractor passes a no-op YARA engine). `INSPECTOR_VERSION` and the 4.2 content version are unchanged (byte-identical attachment results, asserted by the existing 4.2 tests and corpus). Entry names stay in the child's memory only (used to select OOXML/ODF parts and the text type by extension); the extraction result addresses entries by index path (`"2/0/5"`), never by name.

### D6. Validation and checksums

Luhn (PC1, custom `luhn`), IIN ranges and brand lengths (PC1), ISO 13616 length table + mod-97 (BA1, custom `mod97`), IFSC structure (BA2), ISO 3166 country table (BA3, MRZ issuing state is not validated), PAN entity character (NI1, also inside GSTIN), Verhoeff (NI2, custom `verhoeff`), MRZ 7-3-1 check digits (PP2), GSTIN mod-36 check character (PI4, custom `gstin`), calendar validity (PI3), base64url-JSON header (CR4), exact token lengths (CR2, CR3, CR5). Every validator has true/false vectors in unit tests, including the boundary cases (13 and 19 digit cards, Amex 15, 2-series Mastercard, IBANs of several countries with wrong length, Aadhaar starting with 0/1, Verhoeff single-digit errors and transpositions).

### D7. Context-aware classification

- **Window:** `DLP_CONTEXT_WINDOW_CHARS` (64 code units) before and after the candidate, inside its segment; keywords matched on the bec normalization (`normalizeForMatching`, `wordTokens`) through the DLP phrase trie (D8), so case, NFKC forms, zero-width characters and Latin confusables do not hide a keyword.
- **Confidence** = base + structural bonus + positive context (once) − negative context (once) + document aggregation − code penalty, clamped to [0, 1]:
  - **negative context** (packaged list, per detector family): test, testing, sample, example, dummy, fake, demo, placeholder, order, order id, order no, invoice no, ref, reference, tracking, awb, txn, transaction id, tel, phone, fax, isbn, serial, uuid, timestamp → −0.30 (cards, Aadhaar, PAN, mobile, passport); disclaimer phrases → −0.60 (CF1);
  - **table column context:** in a `table` segment, a header cell containing a positive context term applies to every value in that column (column index = tab/comma count of the line);
  - **document aggregation:** ≥ `DLP_BULK_MIN_DISTINCT` (5) distinct validated values of one detector in one segment → +0.15 to each (bulk exports);
  - **code penalty:** a candidate in a segment classified as source code (SC1 score ≥ 0.5) or on a code-like line (assignment, quotes around the token, `0x`/identifier adjacency) → −0.30 for PAN, passport, mobile and card detectors (the "PAN-like strings in code" case).
- **Reportable** iff confidence ≥ the **category threshold** (tenant setting, default `DLP_CONFIDENCE_THRESHOLD` 0.6, bounds 0.5–0.95) and not excluded (test numbers). Non-reportable candidates are counted only in `suppressed` statistics (no masked value, no evidence).
- **Findings** are grouped per detector (and per custom pattern / dictionary): `count` = distinct normalized values (digits/uppercase compact form), `maxConfidence`, sources (≤ 5 refs), masked samples (≤ 3), `capped` when `DLP_MAX_MATCHES_PER_DETECTOR` (1 000) was hit (`dlp.detector.match_cap`).
- **Category aggregate:** `{ category, count, maxSeverity, maxConfidence }` per category; message-level `findingCount`.
- **Worked expectations** (fixture corpus, §9; threshold 0.6): `Card: 4532 0151 1283 0366 exp 09/27` → PC1 0.45+0.10+0.30+0.10 = 0.95 reportable; a bare `4532015112830366` in prose → 0.45 not reportable; `Order ID 4532015112830366` → 0.15 not reportable; a CSV with header `card_number` and 20 valid cards → column context + bulk → reportable ×20; `4111 1111 1111 1111` → excluded test number; `Aadhaar: 2345 6789 0123` (Verhoeff-valid synthetic) with the compliance basis → 1.00; the same 12 digits failing Verhoeff → no candidate; `const PAN = "ABCPD1234E";` in a code block → 0.20 not reportable; `PAN: ABCPD1234E` in prose → 0.85.

### D8. Keyword dictionaries

- **Built-in** (data files `packages/dlp/data/dictionaries/*.json`, versioned by SHA-256 → `dictionaryVersion` in the engine version): `labels` (CF1), `business` (CF2), `financial` (FI1), context lexicons per detector, negative and disclaimer lexicons; languages `en`, `hi` (Devanagari), `hi-Latn`. Entry `{ id: 'en.labels.003', phrase, weight? }`.
- **Tenant dictionaries** (table `dlp_keyword_dictionaries`, D21): `name`, `category` (`confidential`, `financial`, `personal_info`, `source_code`, `custom`), `terms` (1..`DLP_DICTIONARY_MAX_TERMS` 1 000, each 1..64 characters, 1..8 tokens after normalization), `severity`, `baseConfidence` (0.5–1.0, default 0.7), `minMatches` (1..100), `enabled`. Terms are tenant configuration (may be confidential project names): shown to `dlp:read` holders only, never in the scans read API (which shows dictionary id and term index).
- **Matching:** one phrase trie per organization snapshot (built-in + tenant), phrase matching on token sequences of the bec normalization (linear, longest phrase ≤ 8 tokens, no regex), bounded matches per category.

### D9. Customer-defined patterns: RE2 semantics with safety limits

- **Engine:** **`re2js`** (pure-JS port of RE2/J; linear-time automata, no backtracking; rejects backreferences and lookaround at compile). Exact version: the latest release published at least two weeks before implementation (WP2 records it). No native module (memory note: no new native builds).
- **Validation at create/update and at the test endpoint (api) and again at load (worker)** — `@email-gateway/dlp` `custom/compileCustomPattern(input) → { ok, compiled } | { ok: false, code }`:
  1. pattern length 1..`DLP_CUSTOM_PATTERN_MAX_LENGTH` (256); flags only `caseInsensitive`;
  2. compiles under re2js (else `pattern_syntax`); backreferences / lookaround / possessive constructs → `pattern_unsupported`;
  3. counted repetition `{n,m}` with m ≤ 100 and the product of nested counted repetitions ≤ 1 000 (own parse of the pattern string; else `pattern_too_complex`);
  4. no empty match (`matches('')` → `pattern_matches_empty`);
  5. **breadth probe:** on the packaged probe corpus (`data/probe-corpus.txt`, ≈ 64 KiB of ordinary multilingual prose, numbers, URLs and code without sensitive values) more than 50 matches → `pattern_too_broad`;
  6. **cost probe:** scanning the probe corpus takes more than `DLP_CUSTOM_PATTERN_PROBE_MAX_MS` (50 ms) → `pattern_too_slow`. _Closer review 2026-11-08:_ this wall-clock step is a write-time gate of the **api only** (create/update/test). The worker re-validates stored patterns with steps 1–5 and 7 (`compileCustomPattern(…, { costProbe: false })`) and compiles each row version once per process (`CompiledPatternCache`, keyed by public id, version and every compile input), so its own load can never turn an accepted pattern into `dlp.custom.pattern_invalid` and silently weaken a rule that selects it;
  7. validator (optional) in the enum; context keywords ≤ 20 × 1..64.
- **Run time:** per message, custom patterns scan at most `DLP_CUSTOM_SCAN_MAX_CHARS` (1 000 000 code units) of text in total (deterministic char budget; beyond → `dlp.custom.scan_truncated`, partial coverage), ≤ 1 000 matches per pattern, the chunk-wise deadline of D3. A stored pattern that no longer validates (e.g. after a library upgrade) is skipped with `dlp.custom.pattern_invalid` (partial coverage, never clean) and `scan_dlp_custom_invalid_total`.
- **Test endpoint** `POST /api/v1/dlp/patterns/test` (D21): `{ pattern, caseInsensitive, validator?, contextKeywords?, requireContext?, sample (≤ 4 096 characters) }` → `{ valid, code?, complexity: { repetitionProduct, length }, matches: [{ start, end, masked, validated, contextMatched }] ≤ 50 }`. It persists nothing, the sample and the pattern are never logged, audited or echoed in errors (`dlp_pattern_tests_total{result}` only), rate limit 30/min per principal.

### D10. Verdict, coverage and the engine outcome

- **Coverage** = `complete` | `partial`; `partial` when any coverage code of D5 applies (each source records `{ source: 'subject'|'body_text'|'body_html'|'attachment'|'attachment_name', partIndex?, path?, format, status, reasons, chars, truncated }`, ≤ 64 entries, `coverageDetail` JSON).
- **DLP verdict** (`dlp_scan_results.verdict`): `suspicious` when there is at least one reportable finding; else `unknown` when coverage is partial; else `clean`; `skipped` for D1 inbound-disabled.
- **Engine outcome** (`scan_engine_results.outcome`) = the verdict (`clean` / `unknown` / `suspicious` / `skipped`). **Never `malicious` or `spam`**: sensitive data is not a threat, so a DLP finding never triggers the malicious holds of 4.2/4.4 by itself; the DLP action (D11) is what holds mail. Reason codes (≤ 32): the action code first, then detector codes by severity, then coverage codes, `dlp.no_findings` for `clean`.
- Image-only attachments (logos, signatures) make coverage `partial` and the verdict `unknown` when nothing else is found: this is honest (an image can contain a scanned card) and harmless for delivery (no action is attached to `unknown` unless a tenant rule selects that coverage reason, D11). Recorded as a risk (§8).

### D11. DLP policies and deterministic evaluation

- **Model** (tables in §3): a **policy** (`name`, `enabled`, `mode` `enforce`|`monitor`, `priority` 0..1000, `directions` ⊆ {outbound, internal, inbound}) has ordered **rules** (`name`, `enabled`, `priority`, `conditions`, `action`). `conditions` (strict zod `dlpRuleConditionsSchema` in security-contracts):
  - `selectors` (at least one): `detectors` (DLP_DETECTOR_IDS), `categories`, `customPatternIds` (≤ 20 public ids of this tenant), `dictionaryIds` (≤ 20), `coverageReasons` (DLP_COVERAGE_CODES subset: the rule matches a partial coverage with one of these reasons — e.g. hold encrypted archives outbound);
  - `minCount` 1..10 000 (default 1; distinct values summed over the selected findings), `minConfidence` 0.5..1 (default: the category threshold), `minSeverity` (default `low`);
  - `directions` ⊆ the policy's directions (default: the policy's);
  - `sender` `{ addresses ≤ 100, domains ≤ 100 }` (match = any; envelope sender, lower-cased; domains by registrable domain or exact domain);
  - `recipients` `{ addresses ≤ 100, domains ≤ 100, externalOnly?: boolean }` (match = any envelope recipient; external = domain not among the tenant's active domains);
  - `attachmentsOnly` (only findings whose sources are attachments count).
- **Action order** (`DLP_ACTIONS`, strongest last): `allow` < `alert` < `require_approval` < `quarantine` < `block`. An `allow` rule records a match but has no overriding power (allowing is done with exceptions, D12).
- **Evaluation** (`@email-gateway/dlp` `policy/evaluateDlpPolicy(input) → DlpPolicyDecision`, pure):
  1. Candidate policies: `enabled` and `directions ∋ direction`. **None** → the **platform default policy** `dlp-default/1` per the tenant setting `defaultPolicy` (`alert` (default) or `allow`): `alert` = one rule "categories payment_card, bank_account, national_id, passport, credential; minSeverity high → ALERT" for outbound and internal; `actionSource = default_policy`, code `dlp.policy.default`.
  2. Rules sorted by (`policy.priority`, `policy.id`, `rule.priority`, `rule.id`) ascending (ids break ties: deterministic).
  3. Per rule: selected findings (reportable, selector match, `attachmentsOnly`, `minConfidence`, `minSeverity`) minus findings removed by **sender exceptions** of this rule/policy/global (D12); recipient set minus **recipient exceptions**; the rule matches when the count ≥ `minCount` (or a selected coverage reason is present), the sender scope matches (if set) and some remaining recipient matches the recipient scope (if set; with no scope, at least one remaining recipient).
  4. **Effective action** = the strongest action among matched rules of `enforce` policies (default `allow`); the **winning rule** = the first in sort order with that action. `monitor` matches are recorded (`dlp.policy.monitor_match`) and never change the action.
  5. Output: `{ action, actionSource: 'none'|'tenant_policy'|'default_policy', winner: { policyId, ruleId } | null, matched: [{ policyId, ruleId, action, mode, exceptionIds }] ≤ 16, exceptionsApplied ≤ 16, policyVersion }`; `policyVersion` = `pol/1;h=<12 hex>` of the canonical JSON of (policy ids + versions, rule ids + versions, exception ids + versions, default policy). Unit tests assert permutation invariance (shuffled inputs → same output).
- **Truncated recipient lists** (`rcptTruncated`): recipient scopes are treated as matched and recipient exceptions are **not** applied (an exception cannot be proven to cover every recipient): never weaker than the full list.
- **Message-level action.** Rules see all recipients, the action applies to the message. A per-recipient split (deliver to internal recipients, hold the external copy) is policy 5.2's (ADR-0037, §10).

### D12. Exceptions

- Table `dlp_exceptions` (§3): `scope` `sender_address` | `sender_domain` | `recipient_address` | `recipient_domain`, normalized `value`, optional target (`policyId` or `ruleId`; none = every rule), optional `detectors`/`categories` filter (the exception removes only those findings), `reason` 1..512 (required), `expiresAt` **required**, ≤ now + `DLP_EXCEPTION_MAX_DAYS` (365), `enabled`, `version`, created/updated by. Audited create/update/delete with before-images. ≤ `DLP_EXCEPTIONS_MAX_PER_TENANT` (500). Expired exceptions are ignored by the worker (`expires_at > now` at load and again at evaluation).
- A sender exception removes findings for the targeted rules; a recipient exception removes recipients from the targeted rules' recipient sets. The applied exception ids are recorded in the result (`exceptionsApplied`, `dlp.exception.applied`), so an investigator sees why a message passed.
- Domains are normalized through url-security `normalizeDomainInput` (IDNA A-labels, public suffixes and IP literals refused).

### D13. Actions, lifecycle binding and the development pass-through

`@email-gateway/dlp` `mask/` (pure, unit-tested); the compact value is the detector's normalized form (digits or uppercase alnum without separators):

| --------------------------------- | ------------------------------------------------------------------------------------------- |
| PC1, PI2, NI2, BA2 (account), PP1 | `*` for every character but the last 4: `************0366`                                  |
| BA1                               | country code + `*` + last 4: `GB**************1234`                                         |
| NI1, PI4, BA3                     | last 4 only: `******234F`                                                                   |
| PP2                               | `MRZ:` + the document number masked to its last 4                                           |
| PI1                               | first character of the local part + `***@` + domain: `j***@example.com`                     |
| PI3                               | `**/**/****` (no part of the date)                                                          |
| CR2                               | first 4 + `*` + last 4: `AKIA************WXYZ`                                              |

### D16. Evidence: envelope encryption, storage, access, retention, purge

- **Content** (`evidence/build`): ≤ `DLP_EVIDENCE_MAX_MATCHES` (50) matches, ≤ 5 per detector, each `{ detector, code, source: { kind, partIndex?, path?, segment }, start, end (UTF-16 offsets in the extracted segment text, reproducible with `dlp-extract/1`+`dlp-text/1`), value, context (≤ 48 code units before and after) }`; JSON ≤ `DLP_EVIDENCE_MAX_BYTES` (32 768) UTF-8 (matches dropped from the lowest severity when over). **Never raw:** Aadhaar values (masked, and masked inside every context window), CR1/CR3/CR5 secrets (masked; CR1 keeps only the BEGIN line), CR4 (header only), **PC1 card numbers (masked to first 6 + last 4, `453201******0366`; the evidence never holds a full PAN, so the gateway's bucket and api stay out of PCI DSS cardholder-data scope)**. Other detectors keep the raw value inside the encrypted evidence only.
- **Context redaction (before sealing, in `evidence/build`, closer review 2026-11-07):** every context window is redacted independently of which match it belongs to: (a) every span that **any** credential detector CR1–CR5 matched as a candidate — reportable or not, whatever its score — is replaced by its D15 type-only mask; (b) every 12-digit run (with or without the NI2 separators) whose first digit is 2–9 and that passes Verhoeff is replaced by `[aadhaar]` **whether or not NI2 is gated on** (D17), so an Aadhaar number next to a PAN, a card or an account number is never stored raw when Aadhaar detection is disabled; (c) every Luhn-valid 13–19 digit run is masked as PC1 (first 6 + last 4); (d) a 3–4 digit run within 16 code units after a `cvv`, `cvc`, `cvv2`, `csc`, `cid` or `security code` term (case-insensitive) is replaced by `***`, so card verification codes are never stored (PCI DSS req. 3.3.1 forbids storing them after authorization even encrypted). Expiry dates in a card's context are kept (they are not sensitive authentication data and are evidence of the card context). Unit tests: CR2 + CR3 neighbours (`aws_access_key_id=AKIA… aws_secret_access_key=<40 chars>`: the CR2 match's context holds `[secret: 40 chars]`, never the secret), PAN + Aadhaar with gating **off** (the NI1 match's context holds `[aadhaar]`), card + `CVV 123` (context holds `CVV ***`), and a non-reportable CR3-shaped candidate next to a reportable PI1.
- **Encryption (`dlp-evidence/1`)** in `@email-gateway/dlp` `evidence/envelope.ts` (used by the worker to seal and the api to open): a fresh 32-byte **data key** per evidence; payload AES-256-GCM with a 12-byte random IV and AAD `eg-dlp-evidence/v1\0<organizationId>\0<messageId>\0<scanId>`; object body = magic `EGDLP1` ‖ IV ‖ tag ‖ ciphertext. The data key is **wrapped** with AES-256-GCM under the key-encryption key `DLP_EVIDENCE_KEY` (64 hex, a dedicated secret, **not** `DATA_ENCRYPTION_KEY`) with AAD = the same string + `\0dek`, serialized in the SecretBox format `v1.<kid>.<iv>.<tag>.<ct>`; `DLP_EVIDENCE_KEY_PREVIOUS` decrypts during rotation (keep it set for at least `DLP_EVIDENCE_MAX_RETENTION_DAYS` after a rotation; no re-wrap job in this step). KMS envelope encryption is a drop-in replacement of the KEK source later (ADR-0038).
- **Storage:** the ciphertext object in the mail bucket under `org/<org>/dlp-evidence/<yyyy>/<mm>/<scanId>-<uuidv7>.bin` (the product rule "no email content in MySQL": the evidence holds fragments of content, so it lives in S3 like every part); the **row** `dlp_evidence` (MySQL) holds the object key, SHA-256, size, wrapped key, key id, algorithm, match count, expiry and purge state — never content.
- **Crypto-shredding:** the wrapped key exists only in the row, so (a) an object orphaned by a crashed attempt is undecryptable from birth, (b) **purge = set `wrapped_key = NULL` + `purged_at` in a transaction, then delete the object** (noncurrent versions in the versioned bucket stay undecryptable), (c) a lost S3 delete is retried by the next sweep (`object_key` cleared only after a successful delete).
- **Retention:** `expires_at = received_at + evidence.retentionDays` (tenant setting 1..`DLP_EVIDENCE_MAX_RETENTION_DAYS` 180, default `DLP_EVIDENCE_DEFAULT_RETENTION_DAYS` 30). **Sweeper** (email-worker, leader `AdvisoryLocks` `scan:dlp-evidence`, every `DLP_EVIDENCE_SWEEP_INTERVAL_MS` 3 600 000, batches of 500 in `SCAN_DB_TIMEOUT_MS` transactions): crypto-shred expired rows, then delete objects; gauge `dlp_evidence_expired_unpurged`, counter `dlp_evidence_purged_total{reason}`. The `dlp_evidence` partitions are dropped at 7 months (after every possible expiry).
- **Access:** `GET /api/v1/messages/{messageId}/scans/{scanId}/dlp-evidence` — permission **`dlp:evidence_read`**, `@RequireMfa`, `@UserOnly`, rate limit 30/min per user. Flow: writer read of the row (tenant-scoped, echo-checked; another tenant's id → 404; purged → `410 evidence_purged`; expired → `410 evidence_expired`) → **audit row `dlp_evidence.read` committed first** (actor, message id, scan id, match count; no content) → S3 GET (key must start with `org/<org>/dlp-evidence/`) → SHA-256 and size check → unwrap → decrypt → validate the JSON shape → `200` with `Cache-Control: no-store`. A failure after the audit row writes `dlp_evidence.read_failed` (code only). Metric `dlp_evidence_reads_total{result}`. Response bodies are never logged.
- **Purge APIs:** `DELETE /api/v1/messages/{messageId}/scans/{scanId}/dlp-evidence` and `DELETE /api/v1/dlp/evidence` (all of the tenant's evidence, batched, `202` with the count after completion) — `dlp:manage` + MFA, audited `dlp_evidence.purged`.
- **Key custody:** `DLP_EVIDENCE_KEY` is given only to the dlp-consuming email-worker (seal) and the api (open). The worker can read mail anyway (it scans it), so an asymmetric seal-only key would not reduce what a compromised worker sees; the protected adversaries are database dumps, replica readers, bucket leaks and api users without the permission (ADR-0038 alternatives).

`engine_version` = `dlp/1;dict=<8 hex>;data=<8 hex>;ext=dlp-extract/1` (≤ 96; `dict` = built-in dictionaries hash, `data` = IIN/IBAN/test-card/probe data hash), `rules_version` = `dlp-map/1`, `settings_version` (D18), `policy_version` (D11), `extractor_version` = `dlp-extract/1` (+ the pdfjs version in the engine info gauge `scan_engine_info{engine="dlp",version}`). `TEXT_DERIVATION_VERSION` of the DLP = `dlp-text/1` (the bec normalization + the extraction rules of D4), recorded inside the evidence.

### D24. Security boundaries (summary for `security-boundaries.md`)

The dlp consumer reads tenant mail parts (as 4.2–4.4 do) and writes evidence objects; new secret `DLP_EVIDENCE_KEY` (+ `_PREVIOUS`) given only to the email-worker (Compose) / `email-worker-dlp` (Kubernetes Secret `email-gateway-dlp-evidence-key`) and the api. Extraction of untrusted formats only in the isolated child. The api decrypts evidence only in the audited endpoint. Tenant regexes never run on a backtracking engine. No new egress, no new container.

## 6. Prisma wrong-read mitigation in this step (4.2 §6)

New interactive transactions: the dlp finalize (existing `SCAN_DB_TIMEOUT_MS`), the evidence sweeper batches (`SCAN_DB_TIMEOUT_MS`), every api write and the evidence-read audit (120 s budget, 10 s `maxWait`), the dev pass-through read (inside the existing ledger transaction). Every read whose result decides a verdict, an action, an exception, a hold, an evidence access or an api write selects and compares its identifying columns; a mismatch is retryable (engine: `inconsistent_read` attempt failure; api: one transaction retry, then `503 inconsistent_read`; delivery-worker: throw → redelivery). No socket timeout. No new code uses Prisma's default 5 s interactive budget.

## 7. Alternatives considered

- **DLP as a stage-2 engine depending on `attachment`:** would serialize DLP behind ClamAV/YARA (minutes in the worst case), and the attachment engine stores no text to consume; the walker code and the limits are shared instead (D1). Rejected.
- **The attachment engine extracts text and stores it in S3 for DLP:** a second copy of mail content, a new object class with its own retention, and tenant-independent cache semantics of 4.2 broken by tenant-dependent extraction limits. Rejected.
- **A new extraction container (Apache Tika):** strongest format coverage, but a JVM container of ≥ 512 MB on an 8 GB VM, a network hop with content and a new service to secure. Rejected for this step (memory note); possible later behind the same extraction result type.
- **Extraction in the worker's main process:** a hostile PDF could exhaust the event loop or heap of the scan role. Rejected; the isolated child pool is reused.
- **Own PDF text extractor:** small, but poor coverage of CID fonts and ToUnicode CMaps (most modern PDFs). pdfjs-dist with evaluation disabled inside the limited child chosen; `unpdf` (a pdfjs wrapper) adds a layer without changing the risk.
- **Native RE2 (`re2` npm):** faster, but a native build (not in `onlyBuiltDependencies`, platform binaries in the image). `re2js` (pure JS, same semantics) chosen with deterministic char budgets; JavaScript `RegExp` with timeouts rejected (Node has no regex timeout; catastrophic backtracking blocks the thread).
- **Evidence ciphertext in MySQL:** atomic with the final row, no orphans, but stores content fragments in MySQL against the product rule. S3 + crypto-shredding chosen; orphans are undecryptable by construction.
- **Asymmetric sealing (worker holds only a public key):** protects old evidence from a compromised worker, but that worker already reads all mail in clear; needs key-pair tooling in `init-env`. Rejected for now; KMS envelope later (ADR-0038).
- **Reusing `DATA_ENCRYPTION_KEY`:** would give the email-worker the key of MFA secrets and DKIM private keys. Rejected; a dedicated key.
- **New dev pass-through edges into `quarantined` / `held_for_review` / `rejected`:** would anticipate 5.2/5.3 (quarantine storage, release, NDRs) and change ADR-0025's role model. Rejected; holds by not approving, like 4.2 and 4.4.
- **Policy evaluated in the policy-engine (5.2) only:** 5.2 does not exist; the brief requires outbound policy evaluation before approval in this step. Evaluated at scan time, recorded with its version, applied later; 5.2 may be stricter.
- **Per-recipient actions now:** needs per-recipient approvals and split deliveries that are 5.2's. Message-level action with the strongest rule.
- **`malicious` outcome for blocked content:** would conflate sensitive data with threats (malicious holds, risk scores). The action carries the hold.
- **Scanning images with OCR (tesseract.js):** heavy (WASM + language data, seconds per page). Out of scope; recorded as not extracted.

## 9. Test plan

**Fixture corpus** (`packages/dlp/src/corpus/`, synthetic values only — generated card numbers from test IIN ranges with valid Luhn that are **not** real issued numbers, synthetic Verhoeff-valid Aadhaar-like numbers, invented PAN/GSTIN/passport/MRZ, `example.test` domains; never real personal data; a unit test asserts every corpus value is synthetic by construction, e.g. generated from a seeded PRNG and listed in the corpus manifest):

- **True positives for every detector** PC1–CU1 in plain text, HTML, CSV (column context, bulk), **PDF** (text layer), **DOCX** (body, header, footnote), **XLSX** (shared strings, numeric cells, column header), PPTX, ODT, **ZIP** (a DOCX and a CSV inside), nested ZIP (depth 2), each with expected detector codes, counts, masked samples and coverage.

### Closer review round 2 (2026-11-08): four review findings

Each finding was checked against the code first. Changes are code plus tests unless noted.

- **Fixed (medium, D9): a custom pattern could become invalid because of the worker's load.** `PrismaDlpStore.loadTenant` ran `loadTenantPatterns` with the wall-clock cost probe (`DLP_CUSTOM_PATTERN_PROBE_MAX_MS`) on every tenant cache miss (every `DLP_TENANT_DATA_CACHE_TTL_MS`, after every restart), on the event loop it shares with the scans. Under load an accepted pattern could fail the probe and be skipped (`dlp.custom.pattern_invalid`). A rule selecting it through `customPatternIds` could then never match, so the message got a weaker action. Fix in `@email-gateway/dlp` `custom/`: `compileCustomPattern` takes `costProbe` (default `true`, the api). The worker passes `false`, so steps 1–5 and 7 still run: syntax, unsupported constructs, repetition bounds, empty match and breadth (a match count, which is deterministic). A new `CompiledPatternCache` (bounded at 10 000 entries, oldest evicted first, key = public id + version + max length + every compile input) is held by `PrismaDlpStore` across reloads, so each row version is compiled once per process. `DLP_CUSTOM_PATTERN_PROBE_MAX_MS` is now read by the api only and is no longer in the worker's config shape. Tests: `custom.test.ts` (`costProbe: false` skips only the timing, the deterministic refusals remain; the cache reuses a version, recompiles a new version or changed text, is bounded and caches refusals) and `dlp-store.test.ts` (a stubbed `performance.now` that jumps 10 s per read does not invalidate an accepted pattern across three reloads; the same compiled object is reused across reloads and replaced for version 2).
- **Fixed in part (medium, D3/D4): results depended on load, not only on content.**
  - (a) The detection `Deadline` was wall-clock, so the time other messages spent on the shared loop counted against each message. It now runs on a `WorkClock` (`@email-gateway/dlp` `detect.ts`), which is paused while `detect()` yields the loop. `DLP_DETECT_TIMEOUT_MS` therefore bounds the message's own detection work.
  - (b) Attachments were extracted one at a time. `DlpEngine.extractAll` now runs up to `DLP_EXTRACTOR_POOL_SIZE` extractions per message (`extractConcurrency`) and applies the text budget in part order, so the result does not depend on which job finishes first. The first attempt failure aborts the jobs still running, and is rethrown only after every job has settled, so no byte-budget reservation leaks. The pool's `maxWaiting` became `SCAN_DLP_CONCURRENCY × DLP_EXTRACTOR_POOL_SIZE`.
  - (c) `validateDlpConfig` now refuses `DLP_EXTRACT_TIMEOUT_MS + DLP_DETECT_TIMEOUT_MS ≥ SCAN_DLP_TIMEOUT_MS`.
  - Tests: `detect.test.ts` (with a fake clock that moves only while a sibling task runs, a wall deadline expires and the `WorkClock` deadline does not; `WorkClock` counts only time when it is not paused), `dlp.engine.test.ts` (four slow attachments run two at a time and give the same stored result as one at a time; a failure among five slow attachments starts no new job and leaves none in flight; three concurrent large messages complete) and `dlp-config.test.ts`.
  - **Rejected part of the suggested fix:** we did not turn a deadline hit into a definite `unknown` partial result. That would make the action weaker under load (an attacker could pad the message until it times out, and the rule that would have blocked it would no longer match). That is the same class of defect as the first finding. A wall-clock timeout of the whole call (`SCAN_DLP_TIMEOUT_MS`) or of one extraction child stays a retryable failure, and repeated failures end the round in `scan_failed`, which is never approved (fail-closed).
  - **Still open:** the whole-call wall time is still load-dependent. A message with many attachments that each use their full CPU limit (worst case ⌈50 / 2⌉ × 10 s) does not fit 120 s on any hardware and ends `scan_failed` (held), not with a weaker action.
- **Fixed (high, documentation; enforcement is out of scope): QUARANTINE, BLOCK and REQUIRE_APPROVAL are recorded, not enforced.** Confirmed: the engine and the dev pass-through only record these three actions and withhold approval. Nothing creates a quarantine record, rejects or bounces a message, or opens an approval request. That is the design (§2.0-4, D13: enforcement by policy 5.2 and quarantine 5.3, with no new lifecycle edge in 4.5). Implementing it here would pull 5.2/5.3 into this step. Instead, D13 now has a "What 4.5 enforces" paragraph, and the brief-requirements map, the status line, the README and the execution-plan row say that the actions are decided and recorded in 4.5, and enforced from 5.2/5.3. Brief items 6 and 8 and the five actions are not claimed as fully implemented.
- **Fixed (medium, D14): coverage-only incidents.** `messageDlpIncidentV1.categories` is now `0..10`, and a superRefine allows an empty list only with `coverage: 'partial'`. `detectorCodes` stays `1..24` and holds the coverage codes. `DlpEngine.incident()` writes the event for a coverage-only match, such as an ALERT rule on `dlp.not_extracted.encrypted`. It still writes nothing if there are no codes, or no category with complete coverage (not reachable). Consumers: event-relay validates with the registry schema (its image was rebuilt). No queue binds the event in topology v7. Tests: `dlp-events.test.ts` (accepted with partial coverage, refused with complete coverage or no codes), `dlp.engine.test.ts` (an ALERT rule on an encrypted ZIP writes an incident with `categories: []`) and the email-worker package suite `dlp-scan.test.ts` (the same through MySQL and the real outbox row).
