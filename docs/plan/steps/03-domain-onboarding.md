## 2. Decisions

### D1. Module layout

```
apps/api/src/
  dns/                          (WP2) resolver port, adapters, cache, factory, DnsModule
  modules/domains/
    engine/                     (WP2) pure DNS-record logic: names, tokens, MX/SPF/DKIM/DMARC
                                build + evaluate, DKIM key generation, DomainDnsChecker
    domain/                     (WP3) pure lifecycle rules: state machine, scheduling, readiness
    repositories/               (WP3) *.repository.ts (only files that touch Prisma)
    services/                   (WP3) DomainsService, DomainVerificationService,
                                DkimRotationService, DomainConfigurationService,
                                DomainCheckScheduler, DomainEventsService
    controllers/                (WP3) DomainsController, DomainDnsController
    dto/                        (WP3) zod schemas
    domain.mapper.ts, api-docs.ts, domains.module.ts
packages/database/src/domains/  (WP1) normalizeDomainName, resolveActiveDomain (mail path)
```

Controllers parse/validate and call one service method. Services hold logic. Only repositories import `PrismaService` / `PrismaReadService` (existing ESLint rule). `engine/` and `domain/` are pure (no Nest, no Prisma, no I/O except through the `DnsResolver` port and `node:crypto`), so they are unit-tested exhaustively.

### D2. Domain names

`normalizeDomainName(input, { allowTestNames }): NormalizedDomainName` in `packages/database/src/domains/domain-name.ts` (WP1; used by the API and by `resolveActiveDomain`). Returns `{ ascii, unicode }` or throws `DomainNameError` with a stable `code`:

- Trim; strip **one** trailing dot; IDN → punycode with `node:url` `domainToASCII` (empty result → `invalid`); lower-case. `unicode` = `domainToUnicode(ascii)`.
- ASCII length ≤ 253; at least two labels; each label 1–63 characters of `[a-z0-9-]`, not starting or ending with `-` (`xn--` labels allowed); the last label is alphabetic or `xn--…`. Rejects `*`, `_`, IPv4/IPv6 literals, empty labels → `invalid`.
- Always rejected (`reserved`): `localhost`, and names equal to or under `localhost`, `local`, `invalid`, `arpa`, `onion`, `internal`, `alt`.
- Rejected unless `allowTestNames` (`reserved`): names equal to or under `test`, `example`, and `example.com`, `example.net`, `example.org` (and their subdomains). The API passes `allowTestNames = APP_ENV ∈ {local, ci}`.
- The API additionally rejects (`reserved`) names equal to or under any entry of `DOMAIN_RESERVED_SUFFIXES` and any `GATEWAY_MX_HOSTS` host or the `GATEWAY_SPF_INCLUDE` host (the platform's own names).
- The API also rejects (`too_long`) names whose longest derived record host (D6) would exceed 253 characters: `name.length ≤ 253 − max(len(DOMAIN_VERIFICATION_LABEL) + 1, 27, 7)`, where 27 = `<15-character selector>._domainkey.` and 7 = `_dmarc.`. With the default label `_emailgateway-verify` the limit is **226** characters (`maxDomainNameLength` in `domains.service.ts`). Without it, a 227–253-character name either failed the insert into `domain_dns_records.host` (`VARCHAR(255)`, strict mode → `500`) or was created and then never checkable.

Subdomains are allowed (`mail.acme.com` is a separate domain with its own ownership proof). No public-suffix-list check: ownership proof makes claiming a public suffix impossible in practice (documented).

### D3. Lifecycle and status model

`DomainStatus` gains (appended, never reordered) **`active`, `suspended`, `deleted`**. `disabled` (step 1.1) is no longer written by any code; it is documented as deprecated and treated like `suspended` by the mail-path resolver (i.e. not resolvable).

| From                           | Trigger                                                         | To                     | Side effects                                                                                                                                                    |
| ------------------------------ | --------------------------------------------------------------- | ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| —                              | `POST /domains`                                                 | `pending_verification` | verification challenge, DKIM key(s), DNS record rows, `next_check_at = now + 60 s`, audit `domain.created`                                                      |
| `pending_verification`         | ownership TXT found (definitive) and no other org owns the name | `verified`             | `verified_at`, verification row `verified`, other orgs' pending claims superseded (D4), audit `domain.verified`, event                                          |
| `pending_verification`         | ownership check while another org already owns the name         | `failed`               | `status_reason = claimed_by_another_organization`, `next_check_at = NULL`, audit `domain.claim_superseded`, event                                               |
| `pending_verification`         | `now ≥ verification.expires_at` without definitive success      | `failed`               | verification row `expired`, `status_reason = verification_expired`, `next_check_at = NULL`, audit `domain.verification_expired`, event                          |
| `failed`                       | `POST /domains/{id}/verify`                                     | `pending_verification` | new verification row (same token, new `expires_at`), `status_reason = NULL`, audit `domain.verification_restarted`, then the check runs immediately             |
| `verified`                     | `PATCH /domains/{id}/status {active}`                           | `active`               | `activated_at` (first time), audit `domain.status_changed`, event                                                                                               |
| `active`                       | `PATCH … {suspended, reason}`                                   | `suspended`            | `status_reason = reason`, audit, event                                                                                                                          |
| `suspended`                    | `PATCH … {active}`                                              | `active`               | `status_reason = NULL`, audit, event                                                                                                                            |
| any except `active`, `deleted` | `DELETE /domains/{id}`                                          | `deleted`              | `deleted_at`, `next_check_at = NULL`, non-retired DKIM keys → `revoked` + ciphertext NULL, pending verification rows → `expired`, audit `domain.deleted`, event |

- Any other transition is `409` (`Domain is <status>`). `DELETE` on `active` is `409 Suspend the domain before deleting it` (two-step safeguard against cutting mail flow by mistake).
- **Activation needs ownership only** (`verified`), not MX. Customers must be able to activate the gateway _before_ switching MX, otherwise mail arriving at the new MX in the propagation window would be rejected. The status endpoint reports `readyForActivation` and `mailFlowReady` (= `active` and MX valid) so the portal can guide the order: verify → activate → switch MX.
- **Definitive DNS changes after verification never change the domain status automatically.** A missing ownership TXT, wrong MX, broken SPF/DKIM/DMARC on a `verified/active/suspended` domain changes the per-record status and produces warnings (and `domain.ownership_record_missing` audit on the valid → missing transition of the ownership record), but the domain stays as it is. Automatic revocation of ownership and contested claims are out of scope (§10, risk table).
- **Generated columns** (migration, D9): `verified_name = IF(status IN ('verified','active','suspended'), name, NULL)` STORED UNIQUE (global ownership for every post-verification state; a deleted domain frees it). `live_name = IF(status = 'deleted', NULL, name)` STORED with UNIQUE `(organization_id, live_name)` replacing UNIQUE `(organization_id, name)`: an organization can re-add a domain it deleted (a new row; the deleted row stays as history).
- **Suspension and deletion of the organization** are not cascaded to domains in this step. The mail-path resolver (D13) checks `organizations.status = 'active'`; background checks skip domains of organizations that are not `active` (D11).

### D4. Ownership verification and "first to verify wins"

- Token: 20 random bytes as 40 lower-case hex characters, stored in `domain_verifications.token`. Record: `TXT` at `<DOMAIN_VERIFICATION_LABEL>.<domain>` (default label `_emailgateway-verify`) with value `emailgateway-verification=<token>`. Several organizations can publish their own tokens at the same host; the check passes when **any** TXT string at that host equals the expected value exactly (chunks of one TXT record are joined first; surrounding quotes and whitespace are not part of the value).
- `expires_at = created_at + DOMAIN_VERIFICATION_TTL_DAYS` (default 7). A restart (D3) keeps the token so a record that is already published keeps working.
- **Outcomes:** `answer` containing the token → valid; `answer` without it → `invalid`; `nxdomain`/`nodata` → `missing`; `indeterminate` → nothing changes except evidence and the retry schedule (ADR-0017 §3).
- **Winning the name** (one writer transaction, WP3 `DomainOwnershipRepository`): lock the domain row (`SELECT … FOR UPDATE`, re-check it is still `pending_verification`); `SELECT id, organization_id FROM domains WHERE verified_name = ? FOR UPDATE`; if a row exists → this claim becomes `failed` (`claimed_by_another_organization`). Otherwise update the domain to `verified` (the unique index on `verified_name` is the final arbiter: a concurrent winner makes the update fail with `P2002`; the service then retries the whole transaction once and lands in the "owned elsewhere" branch). In the same transaction, every **other** organization's `pending_verification` row with the same `name` becomes `failed` with `claimed_by_another_organization` and `next_check_at = NULL`, with one `domain.claim_superseded` audit row and one event per affected organization (actor `system`). This is the only cross-tenant write of the step; it lives in a clearly named system repository method and never returns the other tenants' data to the caller.
- **Creating** a domain whose name is already owned by another organization is `409 Domain is already registered with another organization` (no owner details). Creating one that another organization merely claims is allowed.

### D5. DNS resolution (ADR-0017)

Port and adapters exactly as ADR-0017. Contract (WP2, `apps/api/src/dns/dns-resolver.ts`):

```ts
export type DnsIndeterminateReason =
  'timeout' | 'servfail' | 'refused' | 'network' | 'malformed' | 'other';
export interface MxAnswer {
  priority: number;
  /** Lower-case, no trailing dot. */
  exchange: string;
}
interface DnsResultBase {
  /** Stable id of the upstream that answered, e.g. `system:127.0.0.1:53` or `doh:https://…`. */
  upstream: string;
  queriedName: string;
  durationMs: number;
  fromCache: boolean;
}
export type DnsResult<T> =
  | (DnsResultBase & { outcome: 'answer'; records: T[]; ttlSeconds: number | null })
  | (DnsResultBase & { outcome: 'nxdomain' | 'nodata'; ttlSeconds: number | null })
  | (DnsResultBase & { outcome: 'indeterminate'; reason: DnsIndeterminateReason; detail: string });
export interface DnsQueryOptions {
  /** Skip cache reads (results are still cached). User-triggered verification sets it. */
  bypassCache?: boolean;
}
export abstract class DnsResolver {
  abstract readonly upstream: string;
  /** Each TXT record's character-strings joined in order (one string per record). */
  abstract resolveTxt(name: string, options?: DnsQueryOptions): Promise<DnsResult<string>>;
  abstract resolveMx(name: string, options?: DnsQueryOptions): Promise<DnsResult<MxAnswer>>;
}
/** Injectable: the configured primary resolver plus the MX propagation resolvers. */
export abstract class DnsResolverSet {
  abstract readonly primary: DnsResolver;
  abstract readonly propagation: readonly DnsResolver[];
}
```

- Adapters never throw for DNS-level failures; they return `indeterminate`. They throw only for programming errors (invalid name argument).
- `DnsModule` (`apps/api/src/dns/dns.module.ts`, not global) provides `DnsResolverSet` from `API_CONFIG` + `KeyValueStore`, each resolver wrapped in `CachingDnsResolver` (D5 of ADR-0017; disabled when `DNS_CACHE_MAX_TTL_SECONDS = 0`). The primary is also exported as `DnsResolver`.
- Names are queried as given (already normalized ASCII); the adapters strip a trailing dot from answers and lower-case MX exchanges.
- `DohDnsResolver`: `GET <url>?dns=<base64url>` with `accept: application/dns-message`, `AbortSignal.timeout(DNS_TIMEOUT_MS)` per try, up to `DNS_TRIES` tries for `timeout`/`network`/HTTP 5xx; response must be `200` with `content-type: application/dns-message`, ≤ 64 KiB, decodable, with a question matching the query; TTL = min answer TTL; negative TTL = SOA minimum/TTL from the authority section when present. The `AD` flag is recorded as `dnssecAuthenticated` in evidence only.
- `SystemDnsResolver`: one `node:dns/promises` `Resolver({ timeout: DNS_TIMEOUT_MS, tries: DNS_TRIES })` per upstream, `setServers([...])` when servers are configured (accepts `ip`, `ip:port`, `[ipv6]:port`); `ttlSeconds = null` for answers (node:dns does not expose TXT/MX TTLs).

### D6. Expected records (generation)

Built by pure functions in `engine/` (WP2) from the domain, its verification token, its DKIM keys, the gateway config and (for SPF/DMARC) the last observed values. Each expected record has a stable **`recordKey`** used for idempotent upserts into `domain_dns_records` (`UNIQUE (domain_id, record_key)`, D9):

| recordKey                                                       | purpose        | type | host (FQDN)                      | value                                                                     | requirement |
| --------------------------------------------------------------- | -------------- | ---- | -------------------------------- | ------------------------------------------------------------------------- | ----------- |
| `verification`                                                  | `verification` | TXT  | `<label>.<domain>`               | `emailgateway-verification=<token>`                                       | activation  |
| `mx:<gateway host>` (one per `GATEWAY_MX_HOSTS` entry)          | `mx`           | MX   | `<domain>`                       | `<priority> <gateway host>` (stored like that; API splits priority/value) | inbound     |
| `spf`                                                           | `spf`          | TXT  | `<domain>`                       | recommended SPF (D7)                                                      | outbound    |
| `dkim:<selector>` (one per `pending`, `active`, `rotating` key) | `dkim`         | TXT  | `<selector>._domainkey.<domain>` | `v=DKIM1; k=rsa; p=<base64>` or `k=ed25519`                               | outbound    |
| `dmarc`                                                         | `dmarc`        | TXT  | `_dmarc.<domain>`                | recommended DMARC (D8)                                                    | recommended |

`requirement` is derived from `purpose` (not stored): `activation` (needed to activate), `inbound` (needed for inbound mail flow), `outbound` (needed before outbound relay is enabled in a later step), `recommended`. `GATEWAY_MX_HOSTS` changes are reconciled: rows `mx:*` for hosts no longer configured are deleted on the next configuration pass. `mta_sts` and `tls_rpt` purposes are not generated (§10).

**MX evaluation** (`evaluateMx`): `answer` with every exchange in the gateway host set → `valid`; `answer` containing any non-gateway exchange (including a Null MX `0 .`) → `invalid` (warnings `mx_non_gateway_hosts` and, if gateway hosts are present too, `mx_gateway_bypass_possible`); `nxdomain`/`nodata` → `missing`. **Propagation:** the primary and each `DNS_PROPAGATION_UPSTREAMS` resolver are queried in parallel; the MX record is `valid` only when the primary is valid and no upstream returned a definitive disagreement; upstreams that are `indeterminate` add warning `mx_propagation_unknown:<upstream>`; a definitive disagreement makes it `invalid` with warning `mx_not_propagated`. If the **primary** is indeterminate, the MX result is indeterminate. Observed MX hosts are written to `domain_mx_records` (upsert by host, `points_to_gateway`, `last_seen_at`; rows not seen in a definitive answer are deleted). All `mx:*` rows share the same outcome; `observed_value` lists the observed `priority host` pairs.

### D7. SPF

`engine/spf.ts` (WP2): parse `v=spf1` records (case-insensitive prefix, TXT strings joined, RFC 7208 terms), count DNS-querying terms (`include`, `a`, `mx`, `ptr`, `exists`, `redirect`) **recursively** through `include:` and `redirect=` targets resolved with the same `DnsResolver` (depth ≤ 10, at most 20 resolutions per check, loop detection by visited name). Evaluation of the customer's apex TXT:

- `nxdomain`/`nodata`, or an `answer` without any `v=spf1` record → `missing`; recommended value `v=spf1 include:<GATEWAY_SPF_INCLUDE> ~all`.
- More than one `v=spf1` record → `invalid`, warning `spf_multiple_records` (receivers return permerror); recommendation = merge of the first, plus an instruction to remove the others.
- Exactly one: `valid` if it contains `include:<GATEWAY_SPF_INCLUDE>` (case-insensitive) **and** the total lookup count ≤ 10, else `invalid`. Recommendation: insert `include:<GATEWAY_SPF_INCLUDE>` directly after `v=spf1` if absent, keeping every other term and the existing `all`/`redirect` unchanged.
- Warnings: `spf_lookup_limit_exceeded` (recommended record's count > 10, the count includes the gateway include's own lookups), `spf_lookup_count_unknown` (an include was indeterminate; count is a lower bound), `spf_ptr_mechanism`, `spf_plus_all`, `spf_record_too_long` (> 450 characters), `spf_syntax_error:<term>`.
- An indeterminate apex lookup → indeterminate (status unchanged). Indeterminate includes do **not** make the apex result indeterminate; they only add `spf_lookup_count_unknown`.
- The stored `expected_value` of row `spf` is updated to the current recommendation after each definitive check; `evidence` holds `{ lookupCount, lookupCountExact, records, warnings }`.

### D8. DMARC

`engine/dmarc.ts` (WP2): parse `v=DMARC1` at `_dmarc.<domain>` (tags `p`, `sp`, `pct`, `rua`, `ruf`, `adkim`, `aspf`, `fo`, `ri`).

- `missing` (no record) → recommendation `v=DMARC1; p=none; rua=<rua>; fo=1`, `stage = missing`, next step "publish a monitoring policy".
- `invalid`: more than one DMARC record, missing/invalid `p`, `v` not first, or unparsable → warnings `dmarc_multiple_records` / `dmarc_syntax_error`; recommendation as for `missing`, merged with the parsable tags of the first record.
- `valid` otherwise, with `stage` = `none` | `quarantine` | `reject` (and `pct` < 100 noted as `partial`). Progression recommendation: `none` → `p=quarantine` (keep other tags), `quarantine` with `pct<100` → `pct=100`, `quarantine` → `p=reject`, `reject` → keep (stage `final`). The recommendation always keeps existing `rua`/`ruf` URIs and adds `GATEWAY_DMARC_RUA` / `GATEWAY_DMARC_RUF` when configured and absent; when `GATEWAY_DMARC_RUA` is not configured and no `rua` exists, it suggests `mailto:dmarc-reports@<domain>`.
- Warnings: `dmarc_no_rua`, `dmarc_policy_none` (monitoring only), `dmarc_pct_partial`, `dmarc_external_rua_needs_authorization` (RFC 7489 §7.1 external destination; documented for operators in `docs/domains/onboarding.md`).
- A DMARC record does not gate activation (`requirement = recommended`).

### D9. DKIM keys and rotation (ADR-0018)

- **Generation** (`engine/dkim.ts`, WP2): `generateDkimKeyPair('rsa_2048' | 'ed25519')` (async `crypto.generateKeyPair`) → `{ algorithm, publicKeyDns, privateKeyPem }`. RSA: modulus 2048, exponent 65537, `publicKeyDns` = base64 of the SPKI DER; Ed25519: `publicKeyDns` = base64 of the raw 32-byte public key (RFC 8463). `dkimTxtValue(algorithm, publicKeyDns)` = `v=DKIM1; k=rsa; p=…` / `v=DKIM1; k=ed25519; p=…`.
- **Selectors:** `eg<r|e><yyyymmdd><4 random [a-z0-9]>` (e.g. `egr20261102k3f9`), unique per domain (retry on collision).
- **Storage:** `private_key_ciphertext = secretBox.encrypt(privateKeyPem, 'dkim:<domain public id>:<selector>')`, `private_key_ref = NULL`, `public_key = publicKeyDns`.
- **Defaults:** every new domain gets one `rsa_2048` key (`pending`). `POST /domains { dkim: { ed25519: true } }` adds an `ed25519` key as well. Keys of different algorithms are independent families.
- **Evaluation:** TXT at `<selector>._domainkey.<domain>`: a record whose tags parse and whose `p` equals the expected key (whitespace removed) and whose `k` matches → `valid`; a record with another or empty `p` → `invalid` (`dkim_public_key_mismatch` / `dkim_key_revoked_in_dns`); `t=y` adds warning `dkim_testing_mode`; `nxdomain`/`nodata` → `missing`.
- **Activation of a key:** a `pending` key whose record is `valid` while the domain is `verified`, `active` or `suspended` becomes `active` (`activated_at`, audit `domain.dkim_key_activated`). If another key of the same algorithm was `active`, it becomes `rotating` with `retire_after = now + DKIM_ROTATION_OVERLAP_DAYS` (default 7) — it stays published so mail signed with it in transit still verifies.
- **Rotation** `POST /domains/{id}/dkim/rotate { algorithm? = 'rsa_2048' }` (`domain:dkim_rotate`): domain must be `pending_verification`, `verified`, `active` or `suspended`. Cheap checks run **before** key generation, so an unknown or foreign id, a refused status or an in-progress rotation never costs a key pair: domain lookup in scope (`404`), the rules below on the current keys (`409`), then the per-domain counter `domains:rotate:<id>` (`incrWithTtl`, 24 h) > 10 → `429` with `Retry-After` (KV unavailable → `503`). This bounds RSA key generation and the growth of `domain_dkim_keys` (each replaced pending key stays as a `revoked` row) and `audit_logs`. The route also has `@RateLimit({ bucket: 'domains-dkim-rotate', limit: 30, windowSeconds: 60, by: 'principal' })`. The key pair is then generated outside the transaction, and the rules are evaluated again under the domain row lock: if a `pending` key of that algorithm exists and the family also has an `active` key → `409 A DKIM rotation is already in progress`; if the only key of the family is `pending` (never published) it is replaced: old → `revoked` (ciphertext NULL, record row deleted), new `pending`. Otherwise a new `pending` key is created next to the `active` one. Audit `domain.dkim_rotation_started` (metadata: algorithm, new selector, previous selector). The response contains the DNS record to publish.
- **Retirement:** the scheduler (D11) retires `rotating` keys with `retire_after ≤ now`: status `retired`, `retired_at`, ciphertext NULL, their `dkim:<selector>` record row deleted, audit `domain.dkim_key_retired`. `GET /dns-records` lists keys retired in the last 30 days under `cleanup` (TXT the customer can delete).
- Deleting a domain revokes every non-retired key (ciphertext NULL), audit within `domain.deleted` metadata.
- Automatic periodic rotation is out of scope: every rotation needs a customer DNS change (no CNAME delegation, ADR-0018).

### D10. Checking a domain (`DomainDnsChecker`, WP2) and persisting results (WP3)

`DomainDnsChecker.check(input, options): Promise<DomainCheckReport>` runs all queries of one domain **in parallel** under an overall deadline (`DOMAIN_CHECK_DEADLINE_MS`, default 15 000; queries still running at the deadline count as `indeterminate`/`timeout`; a query that throws, e.g. a name an adapter refuses, counts as `indeterminate`/`other` instead of rejecting the whole check). Input: `{ domain: string (ASCII); verification: { host, expectedValue } | null; dkimKeys: Array<{ selector, algorithm, publicKeyDns }>; gateway: GatewayDnsConfig; }`; options `{ bypassCache: boolean }`. Output: one `RecordCheckResult` per expected record key plus analyses:

```ts
export type DnsCheckOutcome = 'valid' | 'invalid' | 'missing' | 'indeterminate';
export interface RecordCheckResult {
  recordKey: string; // as in D6
  outcome: DnsCheckOutcome;
  /** Present for definitive outcomes; what was observed (joined TXT values / "prio host" lines). */
  observedValue: string | null;
  /** Recommended value after this check (SPF/DMARC may change; others = expected). */
  expectedValue: string;
  warnings: string[];
  /** JSON-safe evidence, ≤ 8 KiB serialized: upstream(s), outcome/reason, answers, durationMs, fromCache. */
  evidence: Record<string, unknown>;
}
export interface DomainCheckReport {
  checkedAt: Date;
  records: RecordCheckResult[];
  mx: {
    observed: MxAnswer[] | null;
    propagation: Array<{ upstream: string; outcome: DnsCheckOutcome }>;
  };
  spf: { lookupCount: number; lookupCountExact: boolean; recommendedValue: string };
  dmarc: {
    stage: 'missing' | 'none' | 'quarantine' | 'reject';
    partial: boolean;
    recommendedValue: string;
    nextStep: string;
  };
  /** True when any record's outcome is indeterminate. */
  indeterminate: boolean;
}
```

Persistence (WP3, `DomainVerificationService.applyReport`, one writer transaction with the domain row locked; skipped if the domain was deleted or its status changed to a state the report no longer applies to):

- Per record row: **definitive** outcome → `status` = `valid|invalid|missing` (`status_changed_at` when it changes), `observed_value`, `expected_value` (SPF/DMARC recommendation), `last_outcome`, `last_checked_at`, `last_error = NULL`, `evidence`, `warnings` in evidence. **Indeterminate** → only `last_outcome = indeterminate`, `last_checked_at`, `last_error = '<reason>: <detail>'` (≤ 512), `evidence`; `status` unchanged.
- `domain_verifications` (current row): `attempts + 1`, `last_checked_at`, `last_outcome`, `last_error`, `evidence`, `next_check_at` mirrors the domain's.
- `domain_mx_records` from `report.mx.observed` when the primary MX result was definitive.
- Lifecycle transitions of D3/D4/D9 that follow from the report (ownership valid → win; expiry; DKIM activation).
- `domains.last_checked_at`, `next_check_at` (D11), `check_failures` (+1 when `report.indeterminate`, else 0).
- Audit and events only for transitions (never per check), so re-running a check is idempotent.

### D11. Background verification and re-verification jobs

**Where:** inside the `api` process (`DomainCheckScheduler`, WP3), following the `SessionPurgeService` pattern. Justification: the API already owns the domain tables, `SecretBox`, the DNS module and Redis; a new deployable would add an image, a Kubernetes manifest and memory in the 8 GB local VM for a job that runs a few queries per minute; `notification-worker` has no database model for domains and would need `DATA_ENCRYPTION_KEY` (DKIM keys). The scheduler is safe with any number of API replicas (below). It can move to a dedicated worker later without schema changes.

**Tick** every `DOMAIN_JOBS_INTERVAL_SECONDS` (default 30, timer `unref()`ed, disabled with `DOMAIN_BACKGROUND_JOBS_ENABLED=false`; the integration harness sets it to `false` and calls `runOnce(now)` directly):

1. `kv.setIfAbsent('jobs:domain-checks', <instance id>, max(DOMAIN_JOBS_INTERVAL_SECONDS − 1, 5))`; not acquired → return (another replica runs this tick). KV errors → log `warn`, skip the tick.
2. **Due checks:** `SELECT … FROM domains WHERE next_check_at <= now ORDER BY next_check_at LIMIT DOMAIN_CHECK_BATCH_SIZE` (writer; index `(next_check_at)`; `next_check_at` is `NULL` for `failed` and `deleted`). Each candidate is **claimed** with a conditional update `UPDATE domains SET next_check_at = now + 5 min WHERE id = ? AND next_check_at = <value read>` (affected rows must be 1, otherwise another replica took it) and a per-domain KV lock `domains:check:<id>` (`setIfAbsent`, 120 s; also taken by manual verification). Claimed domains are checked with at most `DOMAIN_CHECK_CONCURRENCY` (default 4) in flight. Domains of organizations whose status is not `active` are not checked; their `next_check_at` moves to `now + DOMAIN_RECHECK_INTERVAL_SECONDS`.
3. Before checking, `DomainConfigurationService.ensure(domain)` makes the configuration complete and idempotent (D12).
4. **DKIM retirement:** `rotating` keys with `retire_after <= now` (index `(status, retire_after)`), batch 100.
5. Logs one `info` line per tick with counts (checked, verified, failed, indeterminate, retired); per-domain errors are logged with the domain id and do not stop the batch; a crashed check leaves the 5-minute claim, so the domain is retried after it.

**Next check** (`domain/schedule.ts`, pure, WP3), with ±10 % jitter, never later than the verification expiry for pending domains:

| Situation                                                                                  | Next check                                                                                     |
| ------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------- |
| any record indeterminate (`check_failures = k ≥ 1`)                                        | `now + min(DOMAIN_RETRY_BASE_SECONDS × 2^(k−1), DOMAIN_RETRY_MAX_SECONDS)` (status unchanged)  |
| `pending_verification` (attempt `n` = `domain_verifications.attempts`)                     | `now + min(DOMAIN_RETRY_BASE_SECONDS × 2^n, DOMAIN_RETRY_MAX_SECONDS)`, capped at `expires_at` |
| `verified` / `active` / `suspended` with any record not `valid` (configuration incomplete) | `now + DOMAIN_RECHECK_INCOMPLETE_SECONDS` (default 1800)                                       |
| `verified` / `active` / `suspended`, all records `valid`                                   | `now + DOMAIN_RECHECK_INTERVAL_SECONDS` (default 86 400)                                       |
| `failed`, `deleted`                                                                        | `NULL`                                                                                         |

Defaults: base 60 s, max 3600 s. The pending sequence is 1, 2, 4, … minutes up to hourly until the 7-day expiry.

### D12. Configuration materialization (`DomainConfigurationService`, WP3)

Domains that existed before this step (the seeded demo domain, pre-2.1 pending claims) had `next_check_at = NULL` after `20261102091717_domain_onboarding`, so the scheduler never reached them and `ensure` never ran. Forward migration `20261102110046_domain_check_backfill` sets `next_check_at = CURRENT_TIMESTAMP(3)` for every `pending_verification/verified/active/suspended` row with `NULL` (a checked status is never `NULL` once the job has seen it), and the seed creates the demo domain with `next_check_at = now` (and makes a never-scheduled demo row due on re-seed, leaving a scheduled one alone). The first tick then materializes the verification row, the RSA key and the D6 record rows.

`ensure(tx?, domain)` is idempotent and is called on create, on manual verify and by the scheduler. It creates whatever is missing: a pending verification row (only for `pending_verification` domains without one; for `verified/active/suspended` domains without one — e.g. the seeded demo domain — a row with a new token and status `verified` is created so its ownership record can be monitored), an `rsa_2048` key when no `pending`/`active` RSA key exists (generated **outside** the transaction, inserted inside), and the D6 record rows (upsert by `record_key`; delete `mx:*` rows for hosts no longer configured and `dkim:*` rows of keys that are not `pending/active/rotating`). It never changes the domain status.

Behaviour:

- **Create**: validate the name (D2; `400` with the error code in the message); `@RateLimit({ bucket: 'domains-create', limit: 60, windowSeconds: 60, by: 'principal' })`; the refusals below are checked once **before** key generation (a refused request never costs a key pair) and again in the writer transaction after it: `OrganizationLimitsService.lockOrganization` → count non-deleted domains → `assertWithinLimit(max_domains)` (`409 Organization limit reached: max_domains`); same organization already has the live name → `409 Domain already exists`; another organization owns it (`verified_name`) → `409` (D4); insert domain, `domain_settings` (defaults), verification row, keys, record rows (D12), audit `domain.created`. A `P2002` on `live_name` from a concurrent create → `409`. Response uses the writer.
- **Verify:** per-domain KV counter `domains:verify:<id>` (`incrWithTtl`, 60 s) > 6 → `429` with `Retry-After`; `@RateLimit({ bucket: 'domains-verify', limit: 30, windowSeconds: 60, by: 'ip' })`; per-domain lock `domains:check:<id>` held → `409 Verification already in progress`; KV unavailable → `503`. `failed` → restart (D3). `deleted` → `404`. Runs `ensure` + `check({ bypassCache: true })` + `applyReport`, returns the status view. Indeterminate results return `200` with `lastOutcome: 'indeterminate'` and the scheduled `nextCheckAt` — never an error, never a status change.
- **Status change / delete / rotate:** writer transaction with the domain row locked (`SELECT … FOR UPDATE` by scope + public id); rules in D3/D9.
- Under a platform override every request is audited by the existing interceptor; domain audit rows carry `metadata.override`.

## 6. Logging and secrets hygiene

- DKIM private keys (PEM) are never logged, returned, put in audit metadata or evidence. `packages/logger` `REDACT_PATHS` gains `privateKey`, `privateKeyPem`, `privateKeyCiphertext` and their `*.` variants (WP2), with a test.
- Evidence and logs may contain domain names, DNS answers and upstream ids (public data). Upstream ids never contain credentials (DoH URLs with userinfo are rejected by config validation).
- Verification tokens are not secret (they are published in DNS) but are not logged either; audit metadata never contains them.
- No secret is added to `.env`/`.env.example` in this step.

## 7. Alternatives considered (step level)

See ADR-0017 (resolution, cache, test DNS) and ADR-0018 (key custody). In addition:

- **A new scheduler deployable or `notification-worker` for the jobs:** rejected for now (D11); the API has every dependency and the KV + conditional-update claim makes multiple replicas safe.
- **RabbitMQ delayed messages for retries:** no relay or consumers exist yet (step 3.2), and the schedule is naturally a `next_check_at` column with an index. Revisit if domain volume grows past what one batch query per tick handles.
- **Hard delete of domains (step 1.1 comment):** loses the DKIM key history and the audit linkage, and the brief asks for soft deletion that frees the name. Soft delete + `live_name`/`verified_name` generated columns.
- **Automatic activation once ownership (or MX) is verified:** removes a customer decision with mail-flow consequences; explicit activation keeps the customer in control and allows activating before the MX switch.
- **Require MX to point at the gateway before activation:** creates a window where mail at the new MX is rejected; rejected (D3).
- **Automatically de-verifying a domain when its ownership TXT disappears:** would break mail flow for a deleted TXT record; we monitor and warn instead, and leave contested ownership to a later step.
- **Ownership TXT at the apex:** clutters the apex TXT set (where SPF lives) and confuses customers; a dedicated `_emailgateway-verify` label is used, as by most providers.
- **One `domain_dns_records` row per purpose with multi-line values:** simpler table, but per-MX-host and per-selector status would be lost; `record_key` gives one row per thing the customer publishes.
- **Separate permission for delete/suspend:** `domain:manage` already covers lifecycle in the default roles; only DKIM rotation (which can break outbound signing when misused) gets its own permission, as directed.

## 8. Risks and mitigations

| Risk                                                                          | Mitigation                                                                                                                                                                                                                      |
| ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A DNS outage or attacker-induced timeouts flip domain state                   | Indeterminate never changes status (ADR-0017 §3); expiry is time-based; dedicated unit and integration tests with SERVFAIL and dropped packets                                                                                  |
| Two tenants race to verify the same name                                      | Row locks + `verified_name` unique index as final arbiter + one retry; integration test with concurrent verify calls                                                                                                            |
| A tenant squats a name by keeping a pending claim                             | Pending claims are not unique across tenants; the first to prove ownership wins; losers are failed and informed                                                                                                                 |
| Previous owner keeps a domain after selling it (TXT removed)                  | Ownership record monitored daily, `domain.ownership_record_missing` audited and surfaced; automatic release/contest flow is out of scope and documented in the runbook (platform operator deletes the domain under an override) |
| Background jobs run twice with several API replicas                           | KV tick lock + DB conditional claim + per-domain KV lock; all writes are state-based and idempotent; audit/events only on transitions; integration test runs two `runOnce` concurrently                                         |
| RSA key generation blocks the event loop                                      | Async `generateKeyPair` (libuv thread pool), outside DB transactions                                                                                                                                                            |
| `DATA_ENCRYPTION_KEY` now also protects DKIM keys                             | ADR-0018; file-mounted secret in Kubernetes; previous-key rotation supported; ciphertext deleted when keys retire                                                                                                               |
| Public DNS used by tests by accident                                          | Integration harness always overrides `DNS_SERVERS`/`DNS_DOH_URL` for domain suites; the test DNS server answers NXDOMAIN for unknown names; tests use `.test` names only                                                        |
| System resolver cannot report TTLs                                            | Cache lifetimes capped by `DNS_CACHE_NEGATIVE_TTL_SECONDS` in system mode (ADR-0017)                                                                                                                                            |
| Large DKIM TXT answers exceed 512-byte UDP                                    | c-ares uses EDNS and falls back to TCP on truncation; the test server implements TCP and truncation, with a test                                                                                                                |
| Generated-column change rebuilds `domains`                                    | Small table (hundreds to thousands of rows); documented in the migration header                                                                                                                                                 |
| `dns-packet` cannot be installed (registry unavailable or release-age policy) | It is a 2023 release; if installation is impossible, WP2 implements a minimal RFC 1035 codec (header, question, TXT/MX/CNAME/SOA/OPT) under `apps/api/src/dns/wire/` with unit tests and documents the deviation                |
| Replica lag hides a just-created domain from `GET /domains`                   | Lists may lag by design; read-after-write endpoints use the writer; tests poll lists                                                                                                                                            |
