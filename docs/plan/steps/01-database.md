## 2. Decisions

### D1. Identifiers and the tenancy column (ADR-0014 §1–2)

- Every surrogate key is `BIGINT UNSIGNED AUTO_INCREMENT`. In Prisma: `id BigInt @id @default(autoincrement()) @db.UnsignedBigInt`. Every foreign key column referencing it is also `@db.UnsignedBigInt`.
- `public_id CHAR(36)` UUIDv7 (`String @unique @default(uuid(7)) @db.Char(36)`) is used **only** on: `organizations`, `users`, `domains`, `api_keys`, `email_policies`, `webhook_subscriptions`, `quarantine_messages` and `message_identities`. APIs expose `public_id`. Internal contracts (events, S3 keys, logs) use the numeric id as a **decimal string**.
- `organization_id BIGINT UNSIGNED NOT NULL` is on every tenant-owned table, and tenant-scoped indexes lead with it. There are no tenant ids from headers, ever (unchanged rule).
- The nullable `organization_id` is allowed only on: `roles` (NULL = built-in system role), `threat_indicators` and `yara_rules` (NULL = platform-wide intelligence or rule), `audit_logs` (NULL = platform action), and `login_audit_logs` (NULL = login attempt for an unknown account).
- Platform catalogs have no `organization_id`: `organization_plans`, `permissions`, `ip_reputation`, `domain_reputation`, `url_reputation`, `malware_signatures` and `system_settings`.
- Platform operators belong to a **platform organization** (`organizations.kind = 'platform'`, seeded with slug `platform`), so `users.organization_id` is always NOT NULL and `(organization_id, email)` stays unique.
- A small helper module `packages/database/src/ids.ts` provides `formatId(bigint): string`, `parseId(string): bigint` (rejects anything that is not `^[1-9][0-9]{0,19}$` or is above 2^64−1), and `isIdString(string): boolean`. API layers must not `JSON.stringify` raw `bigint`.

### D2. Conventions (unchanged unless stated)

- `snake_case` tables and columns via `@@map`/`@map`, and `PascalCase` models. Model names are the singular PascalCase of the table (`email_messages` → `EmailMessage`, `message_idempotency` → `MessageIdempotency`, `organization_settings` → `OrganizationSetting`).
- Timestamps are `DATETIME(3)` UTC: `created_at` `@default(now())`, and `updated_at` `@updatedAt` on mutable rows only. Append-only tables have no `updated_at`.
- Enums are Prisma enums (MySQL `ENUM`), and values are only ever appended. JSON is used **only** for flexible configuration and variable scan evidence. Each JSON column is listed explicitly in §3.
- Soft delete (`deleted_at DATETIME(3) NULL`) only on `organizations`, `users` and `email_policies`. Domains are hard-deleted after deprovisioning (the history is in `audit_logs`), which frees the name. (Review fix: only verified ownership is globally unique, via the generated `domains.verified_name`; `name` is unique per organization, so pending claims cannot squat a domain.)
- Foreign keys between non-partitioned tables are real, `ON DELETE RESTRICT`, except for owned children that are listed as `CASCADE` (join tables and version children). The default for `ON UPDATE` is fine.
- No email bodies or attachment content in MySQL: only S3 object keys (`*_object_key VARCHAR(512)`), sizes and hashes. The bucket comes from config (`S3_BUCKET_MAIL` / `S3_BUCKET_ARCHIVE`). Subjects and a small allow-list of headers are metadata. The full header block stays in the EML in S3.
- Text sizes: email address `VARCHAR(320)`, domain `VARCHAR(253)`, hostname `VARCHAR(255)`, IP `VARCHAR(45)`, sha256 `CHAR(64)` (lowercase hex), SMTP response `VARCHAR(512)`, subject `VARCHAR(998)`.

### D3. Partitioning (ADR-0014 §3)

MySQL constraints we design for: a partitioned InnoDB table **cannot have foreign keys or be referenced by one**, every PRIMARY/UNIQUE key **must include all partitioning columns**, and pruning works only when queries constrain the partition column.

- Syntax: `PARTITION BY RANGE COLUMNS(<col>) (PARTITION pmax VALUES LESS THAN (MAXVALUE))` in the migration. RANGE COLUMNS supports `DATETIME`. If MySQL rejects `DATETIME(3)` there, fall back to `PARTITION BY RANGE (TO_DAYS(<col>))` and record that in `docs/database/partitioning.md`.
- **Partition naming:** monthly `pYYYYMM` (holds `[YYYY-MM-01, next month)`), daily `pYYYYMMDD`, and catch-all `pmax`. Because the first real partition is created by splitting `pmax`, it holds everything before its upper bound.
- Child rows of a message copy the **message's** `received_at` into their own `received_at` column. A message's whole graph is in one partition, and `WHERE message_id = ? AND received_at = ?` prunes to one partition.
- Partitioned tables have a composite primary key `(id, <partition col>)`. In Prisma that is `@@id([id, receivedAt])` and `id BigInt @default(autoincrement()) @db.UnsignedBigInt`. If Prisma rejects autoincrement on a composite id, add `@@index([id])`, which is harmless because InnoDB needs it anyway, and document it. `email_messages.id` has **no** autoincrement: it is the registry id. They have **no `@relation`** in either direction.

| Table                          | Partition column    | Granularity | Platform retention (drop after) | Notes                                                                                                                               |
| ------------------------------ | ------------------- | ----------- | ------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `email_messages`               | `received_at`       | month       | 6 months                        | Core tier                                                                                                                           |
| `email_recipients`             | `received_at`       | month       | 6 months                        | Core                                                                                                                                |
| `email_attachments`            | `received_at`       | month       | 6 months                        | Core                                                                                                                                |
| `email_scans`                  | `received_at`       | month       | 6 months                        | Core                                                                                                                                |
| `email_deliveries`             | `received_at`       | month       | 6 months                        | Core                                                                                                                                |
| `email_headers`                | `received_at`       | month       | 3 months                        | Detail tier                                                                                                                         |
| `email_events`                 | `received_at`       | month       | 3 months                        | Detail. Long-term history lives in ClickHouse (ADR-0009)                                                                            |
| `email_message_status_history` | `received_at`       | month       | 3 months                        | Detail                                                                                                                              |
| `scan_engine_results`          | `received_at`       | month       | 3 months                        | Detail (largest table: about 5 rows/message)                                                                                        |
| `policy_execution_logs`        | `received_at`       | month       | 3 months                        | Detail                                                                                                                              |
| `delivery_attempts`            | `received_at`       | month       | 3 months                        | Detail                                                                                                                              |
| `email_archives`               | `received_at`       | month       | **never auto-dropped**          | Legal hold and per-tenant archive retention: row-level, step 8.1                                                                    |
| `bounce_events`                | `occurred_at`       | month       | 6 months                        | Own time column                                                                                                                     |
| `audit_logs`                   | `created_at`        | month       | **never auto-dropped**          | Compliance. Export and drop are a later manual or ops decision                                                                      |
| `webhook_deliveries`           | `event_occurred_at` | month       | 2 months                        | Deterministic from the envelope, so the unique key works                                                                            |
| `message_outbox`               | `created_at`        | **day**     | 7 days                          | A drop is **skipped** if the partition still has `published_at IS NULL` rows. That is logged as an error and the job exits non-zero |

"Retention N months" means: drop partition `pYYYYMM` when its **upper bound** ≤ the first day of (current UTC month − N months). So 6 months keeps the current month plus 6 full months. Daily: drop when the upper bound ≤ today − N days.

**Not partitioned** (deliberately): `message_identities` (the uniqueness anchor), `message_idempotency` (its key must not contain time; see ADR-0014 alternatives), `quarantine_messages` (about 5% of volume, needs foreign keys from actions and release logs, and is purged by an indexed `expires_at`), and every control-plane table.

**Maintenance job** (`packages/database/src/partitioning/`, CLI `db:partitions`):

1. Reads `information_schema.PARTITIONS` for the current schema.
2. For each registered table, ensures that partitions exist up to **3 months ahead** (monthly) or **7 days ahead** (daily). It does this with `ALTER TABLE t REORGANIZE PARTITION pmax INTO (PARTITION pA VALUES LESS THAN ('…'), …, PARTITION pmax VALUES LESS THAN (MAXVALUE))`. If the table has only `pmax`, the first created partition starts at `--bootstrap-from` (default: the current month or day). If `pmax` already contains rows, it logs a `warn` with the row estimate and still splits (the copy cost is proportional to the stray rows).
3. Drops expired partitions according to the table above (`ALTER TABLE t DROP PARTITION a, b`). It never drops `pmax`, never drops tables marked `drop: false`, and applies the outbox guard.
4. **Retention purges** (DML, batched, 5,000 per statement, with a short sleep between batches): `message_idempotency` rows with `processed_at` older than **30 days**. `message_identities` rows with `id < (SELECT MIN(id) FROM email_messages)` (registry ids are monotonic with time, and if `email_messages` is empty, purge nothing), **except** rows still referenced by a live `email_archives` row or a `quarantine_messages` row; walked in id ranges from a watermark in `maintenance_watermarks` (review fix §9).
5. Everything is idempotent. It supports `plan` (prints the DDL and makes no changes) and `apply`, plus `--now <ISO>` for tests. It runs as `MIGRATION_DATABASE_URL` (DDL). It logs with pino and exits non-zero on any failure.
6. It runs after `prisma migrate deploy` in Compose (`db-migrate` command), on a daily Kubernetes CronJob, and in CI after migrations.
7. `apply` is serialized by a per-schema advisory lock (`GET_LOCK`, no wait; a run that does not get it skips and exits 0) and bounds partition DDL with `SET SESSION lock_wait_timeout = 5` on a single-connection client (review fix §9).

Planning is a **pure function** (`planPartitionChanges(spec, existingPartitions, now, opts) → PartitionAction[]`), so it is unit-testable. Execution is a thin layer on top.

### D4. Identity registry (ADR-0014 §4)

`message_identities` (not partitioned):

```
id BIGINT UNSIGNED AUTO_INCREMENT PK
public_id CHAR(36) UNIQUE (UUIDv7)
organization_id BIGINT UNSIGNED NOT NULL  FK organizations
ingest_key VARCHAR(128) NOT NULL          -- opaque ingestion idempotency key (defined in step 3.1)
received_at DATETIME(3) NOT NULL          -- the partition key of every row of this message
created_at DATETIME(3)
UNIQUE (organization_id, ingest_key)
```

Ingestion (step 3.1) does all of this in **one** transaction: insert the registry row (a duplicate `ingest_key` means it was already ingested, so it answers 250 without writing again), insert `email_messages` with `id = registry.id, received_at = registry.received_at`, insert recipients and attachments, insert `message_outbox`. Reads by public id go `registry → (id, received_at, organization_id check) → partitioned tables`.

### D5. Read/write split (ADR-0014 §6)

**Topology (local Compose):**

- `mysql` (primary): adds `infrastructure/mysql/primary/role.cnf`, which contains `server_id=1`, `log_bin=binlog`, `gtid_mode=ON`, `enforce_gtid_consistency=ON`, `binlog_expire_logs_seconds=604800` and `plugin-load-add=mysql_clone.so`. It is mounted as `/etc/mysql/conf.d/role.cnf`, next to the shared `gateway.cnf`. Turning GTID on at startup on the existing data directory is allowed, so the `mysql-data` volume is **not** wiped.
- `mysql-replica` (new): `mysql:8.4`, volume `mysql-replica-data`, port `127.0.0.1:${MYSQL_REPLICA_HOST_PORT:-3308}:3306`, `restart: unless-stopped`. Its env is only `MYSQL_ROOT_PASSWORD` (no `MYSQL_DATABASE` and no init scripts: CLONE brings everything). It mounts `gateway.cnf` plus `infrastructure/mysql/replica/role.cnf`, which contains `server_id=2`, `gtid_mode=ON`, `enforce_gtid_consistency=ON`, `read_only=ON`, `super_read_only=ON`, `log_replica_updates=ON`, `relay_log=relay-bin`, `replica_parallel_workers=4`, `replica_preserve_commit_order=ON`, `plugin-load-add=mysql_clone.so` and `innodb_buffer_pool_size=256M`. Its healthcheck (root, `MYSQL_PWD` env) passes only when `SHOW REPLICA STATUS\G` shows **both** `Replica_IO_Running: Yes` and `Replica_SQL_Running: Yes`, with `start_period: 180s`.
- `mysql-replica-setup` (new one-shot, `restart: 'no'`, image `mysql:8.4`, entrypoint `/bin/bash /setup/setup-replica.sh`). It depends on `mysql: service_healthy` and `mysql-replica: service_started`. The script `infrastructure/mysql/replica/setup-replica.sh` is idempotent:
  1. Ensures every account on the primary by running `infrastructure/mysql/init/01-users.sh` over TCP. That script is extended to accept `MYSQL_HOST` and connect over TCP when it is set, or over the socket otherwise. It uses only `CREATE USER IF NOT EXISTS` and `GRANT`, so it is idempotent and works on the existing volume.
  2. Waits until the replica accepts root connections.
  3. If replication is configured **and** both threads are `Yes`, exits 0.
  4. If replication is configured but not running, runs `START REPLICA`, waits 20 s, and exits 0 if both threads are now `Yes`.
  5. Otherwise it (re)seeds: `SET GLOBAL super_read_only=OFF` if CLONE requires it, `SET GLOBAL clone_valid_donor_list='mysql:3306'`, then `CLONE INSTANCE FROM '<repl user>'@'mysql':3306 IDENTIFIED BY '<pw>' REQUIRE SSL`. Error 3707 ("not managed by supervisor") is expected: the replica's mysqld exits and Docker's restart policy restarts it on the cloned data. The script then waits for it, runs `CHANGE REPLICATION SOURCE TO SOURCE_HOST='mysql', SOURCE_PORT=3306, SOURCE_USER=…, SOURCE_PASSWORD=…, SOURCE_AUTO_POSITION=1, SOURCE_SSL=1` and `START REPLICA`, waits until both threads are `Yes` (timeout 120 s), and exits 0. On timeout it prints `Last_IO_Error` and `Last_SQL_Error` (never passwords) and exits 1.
  6. Passwords are passed via the `MYSQL_PWD` env or option files, never on the command line. If CLONE proves unworkable, the documented fallback is `mysqldump --single-transaction --set-gtid-purged=ON --source-data` piped into the replica, followed by `RESET BINARY LOGS AND GTIDS`. The implementer records which approach shipped.
- **Accounts** (`01-users.sh`, all from env):
  - `MYSQL_APP_USER`: `SELECT, INSERT, UPDATE, DELETE` on the schema (unchanged).
  - `MYSQL_MIGRATOR_USER`: unchanged.
  - **new** `MYSQL_READER_USER` (`gateway_reader`): `SELECT` on the schema plus `REPLICATION CLIENT` on `*.*`, and nothing else.
  - **new** `MYSQL_REPLICATION_USER` (`gateway_repl`): `REPLICATION SLAVE, BACKUP_ADMIN` on `*.*`.

  Users are created on the primary and reach the replica through CLONE or replication.

- **Env keys** (added to `.env.example`, and working values appended to the local `.env` without rotating existing secrets):

  | Key                                   | Value                                                                                                          |
  | ------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
  | `MYSQL_REPLICA_HOST_PORT`             | `3308`                                                                                                         |
  | `MYSQL_READER_USER`                   | `gateway_reader`                                                                                               |
  | `MYSQL_READER_PASSWORD`               | `__GENERATE__`                                                                                                 |
  | `MYSQL_REPLICATION_USER`              | `gateway_repl`                                                                                                 |
  | `MYSQL_REPLICATION_PASSWORD`          | `__GENERATE__`                                                                                                 |
  | `DATABASE_READ_URL`                   | `mysql://${MYSQL_READER_USER}:${MYSQL_READER_PASSWORD}@localhost:${MYSQL_REPLICA_HOST_PORT}/${MYSQL_DATABASE}` |
  | `DATABASE_READ_MAX_LAG_SECONDS`       | `10`                                                                                                           |
  | `DATABASE_READ_LAG_CHECK_INTERVAL_MS` | `5000`                                                                                                         |

- **Compose app env:** only `api` gets `DATABASE_READ_URL: mysql://…@mysql-replica:3306/…`, `DATABASE_READ_MAX_LAG_SECONDS` and `DATABASE_READ_LAG_CHECK_INTERVAL_MS`, plus `depends_on: mysql-replica-setup: service_completed_successfully`. The shared `x-node-env` keeps only the writer.

**Code (`packages/config`, `packages/common`):**

- `databaseReadConfigSchema` (new, in `packages/config/src/schemas.ts`):
  - `DATABASE_READ_URL`: optional `mysql://` URL.
  - `DATABASE_READ_MAX_LAG_SECONDS`: int ≥ 0, default 10.
  - `DATABASE_READ_LAG_CHECK_INTERVAL_MS`: int, 1000–60000, default 5000.

  Only `apps/api` composes it.

- `DatabaseModule.forRoot({ url, read?: { url?: string; maxLagSeconds: number; lagCheckIntervalMs: number } })`. Without `read`, only `PrismaService` is registered (data-plane apps), so injecting `PrismaReadService` there is a DI error. With `read`, `PrismaReadService` is registered and exported as well.
- `PrismaReadService` (in `packages/common/src/database/prisma-read.service.ts`) does **not** extend `PrismaClient`:
  - `readonly healthName = 'mysql-reader'`.
  - `get client(): PrismaClient` returns the reader client in mode `reader`, otherwise the injected `PrismaService` (writer).
  - `status(): ReaderStatus` returns `{ mode: 'reader' | 'writer-fallback' | 'writer-only'; lagSeconds: number | null; maxLagSeconds: number; reason?: string; checkedAt?: string }`.
  - **Modes:**
    - `writer-only`: no reader URL configured. It logs `info` once at startup.
    - `reader`: the last probe succeeded, both threads are running, and `Seconds_Behind_Source` ≤ max.
    - `writer-fallback`: any of the following: the probe threw or timed out (2 s), `SHOW REPLICA STATUS` returned no rows (reason `not a replica`), either thread is not `Yes` (`replication stopped`), `Seconds_Behind_Source` is NULL (`lag unknown`), or the lag is over the maximum (`lag Ns > max Ms`).
  - **Probe:** `SHOW REPLICA STATUS` on the reader client via `$queryRawUnsafe`. It runs once in `onModuleInit` (awaited, with a timeout; a failure there must **not** fail boot) and then every `lagCheckIntervalMs` on an `unref()`ed timer that is cleared in `onModuleDestroy`. The reader client connects lazily. Do not call `$connect()` eagerly in a way that throws at boot.
  - **Logging:** only on mode **transitions**: `warn` when entering `writer-fallback` (with the reason and lag), `info` when returning to `reader`. Never per query, and never the URL.
  - `checkHealth()` runs a fresh probe and **resolves** with details `{ mode, lagSeconds, maxLagSeconds, reason? }` in every mode. Readiness must not fail because the replica is unhealthy, since the writer fallback keeps the service functional and the writer's own `mysql` check covers the writer. That design choice is recorded in `docs/database/replication.md`.
- Health plumbing: `HealthIndicator.checkHealth(): Promise<void | HealthDetails>`. `HealthDetails = Record<string, string | number | boolean | null>` is exported from `packages/shared-types`. `DependencyHealth` gains an optional `details?: HealthDetails`. `HealthService` copies the details into the check result. Existing indicators are unchanged.
- **Enforcement:** an ESLint rule in `eslint.config.mjs` forbids importing `PrismaReadService` (and `DatabaseReadModule`, if one is created) from `@email-gateway/common` in `apps/{smtp-adapter,email-worker,policy-engine,delivery-worker,archive-worker}/**`. The new block must repeat the existing `patterns`, because in flat config a later `no-restricted-imports` replaces the earlier options. Each data-plane `app.module.test.ts` asserts that `PrismaReadService` is not resolvable. `notification-worker` also stays writer-only for now: it may adopt the reader in step 6.2.
- **Usage rule (documented):** control-plane list, search, report and dashboard reads in `api` use `PrismaReadService.client`. Read-after-write paths (return-after-create, anything inside a transaction, anything that decides authorization right after a write) use the writer. In this step, `api` registers the reader and its health check. Feature modules adopt it in their own steps.
- **Kubernetes:** `api.yaml` gets `DATABASE_READ_URL_FILE=/var/run/secrets/gateway/database-read-url`. The ConfigMap gets `DATABASE_READ_MAX_LAG_SECONDS: '10'` and `DATABASE_READ_LAG_CHECK_INTERVAL_MS: '5000'`. `docs/deployment/README.md` lists the secret keys `database-url`, `database-read-url`, `migration-database-url`, `rabbitmq-url` and `redis-url`.
- **Production mapping:** `DATABASE_URL` points at the RDS or Aurora **writer (cluster) endpoint**, and `DATABASE_READ_URL` at the **reader endpoint** (or an RDS read replica endpoint). `SHOW REPLICA STATUS` works on RDS for MySQL read replicas. Aurora replicas return no rows, which would put the service in permanent `writer-fallback`. An Aurora probe (`information_schema.replica_host_status`) is **planned for step 10.1** and must be documented as such, not implemented now.

### D8. Performance test

`packages/database/src/perf/` (TypeScript, compiled to `dist`, root script `db:perf`):

1. Creates the throwaway schema `email_gateway_perf` with the migrator account (the local migrator has global `CREATE`/`DROP`). 2. Bulk-loads synthetic data with multi-row `INSERT`s (1,000 rows per statement, `$executeRawUnsafe` with placeholders, no new dependency). The default `--messages 200000` covers 20 organizations with a skewed distribution, spread across the last 4 months:
   - 1–4 recipients per message (avg 1.5)
   - 1.1 scans per message
   - 5 engine results per scan
   - 6 events and 5 status-history rows per message
   - a delivery per recipient and 1.2 attempts per delivery
   - 0–2 attachments

## 3. Data model

Legend:

- **PK** is `id BIGINT UNSIGNED AUTO_INCREMENT` unless stated otherwise.
- **org** is `organization_id BIGINT UNSIGNED NOT NULL` plus an FK to `organizations` (RESTRICT) on non-partitioned tables.
- _(P)_ marks a partitioned table: there is no FK, and every unique key ends with the partition column.
- `created_at` and `updated_at` are implied where sensible.
- The listed indexes are the complete set: do **not** add more to partitioned tables without a documented query.

## 4. Alternatives considered (step level)

See ADR-0014 for the identifier, partitioning, idempotency and lag-probe alternatives. In addition:

- **Composite tenant FKs** (`(domain_id, organization_id) → domains(id, organization_id)`), so that the database rejects cross-tenant references. This is strong defense in depth, but it needs an extra unique key on every parent, and Prisma's nested writes become awkward when a scalar is shared by two relations. **Deferred:** the repository layer and cross-tenant tests enforce it (steps 1.2/1.3). It can be added later with additive migrations.
- **A key/value `organization_settings`:** rejected in favour of typed 1:1 columns plus one `preferences JSON` column, so the frequently read settings are typed.
- **Replica seeding by replaying the primary's binlog from GTID 1:** rejected, because the Docker entrypoint runs part of its bootstrap with `sql_log_bin=0`, and an existing primary volume has pre-GTID history. CLONE copies a consistent snapshot, including users and the GTID state.
- **Failing readiness when the replica is down:** rejected, because it would take every `api` pod out of the load balancer while the writer fallback keeps them correct.

## 5. Risks and mitigations

| Risk                                                                                                        | Mitigation                                                                                                                                                                                                                                                                                                      |
| ----------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Prisma rejects a composite `@@id` with autoincrement, or `migrate diff` reports drift on partitioned tables | Verified in WP1. The fallback is `@@index([id])`. Any irreducible drift is documented precisely in `docs/database/partitioning.md`, and the CI step is adjusted only with justification                                                                                                                         |
| `DATETIME(3)` is not accepted by RANGE COLUMNS                                                              | Fall back to `RANGE (TO_DAYS(col))` with integer bounds, consistently, and update the maintenance planner                                                                                                                                                                                                       |
| CLONE recipient restart behaviour in Docker                                                                 | One-shot setup with a wait loop. The mysqldump fallback is documented in D5                                                                                                                                                                                                                                     |
| Maintenance job not run, so rows accumulate in `pmax`                                                       | The job runs in `db-migrate` and in the CronJob, warns on a non-empty `pmax`, and the docs list an alert. Splitting still works (with a copy)                                                                                                                                                                   |
| `bigint` leaking into JSON responses                                                                        | `ids.ts` helpers. Documented in `docs/database/README.md` for the API steps                                                                                                                                                                                                                                     |
| Replica lag during bulk loads (perf test)                                                                   | Expected locally. The reader falls back to the writer, and the perf report records the observed lag                                                                                                                                                                                                             |
| Docker VM memory (8 GB) with a second mysqld                                                                | Replica buffer pool of 256M. No new image builds in parallel                                                                                                                                                                                                                                                    |
| Resetting the local schema destroys local data                                                              | Phase 0 data only. A schema reset (`migrate reset`), **not** a volume deletion. Scripted as `pnpm db:reset:local` (refuses staging/production), and `db:migrate`/Compose `db-migrate` run a preflight (`dist/migrations/cli.js check`) that detects the retired `_init` migration and prints these instructions |
