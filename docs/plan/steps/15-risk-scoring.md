## 2. Decisions

### 2.0 Invariants (never traded away)

1. **Never clean by accident.** `unknown`, `timeout`, `error`, `skipped`-for-a-wrong-reason, a missing final, a missing child row (`bec_scan_results`, `dlp_scan_results`, `email_auth_results` where expected) and a scoring error are never `clean`: each has an explicit contribution, a reason code, a level floor and an action floor: for failures (including a missing child row) `failures.minLevel` / `failures.action`, for an `unknown` result `failures.unknownMinLevel` / `failures.unknownAction` (default `low` / `tag`, so an unknown result is never recommended for plain `deliver`; review round 1).
2. **Deterministic and reproducible.** The scorer is a pure function of `(ScoringInput, EffectiveProfile)` with integer arithmetic only (no floating point, no clock, no randomness, no I/O). Same input and profile → byte-identical output; the row stores `input_sha256`, `profile_sha256` and every version, so any result can be recomputed (the dry-run proves it).
3. **5.1 recommends, never enforces.** No lifecycle transition, no approval, no quarantine row is written by scoring. The only enforcement is the existing local/ci pass-through, which may use the result **only to hold more**.
4. **Hard blocks cannot be outweighed.** A hard-block indicator sets the level to `critical`, the verdict and a non-delivery action regardless of score, trust or profile weights. Malware hard blocks cannot be disabled by any profile.
5. **No trust on spoofable identity.** Trust adjustments apply only when the message authenticated (DMARC `pass`) and no authentication-failure signal fired; never to hard blocks, malware, URL threats, attachments, impersonation, lookalikes, failures or DLP. Every trust decision is recorded.
6. **No message content.** Inputs, rows, explanations, logs and metrics carry engine names, outcomes, reason codes, signal ids, integers and versions only: no addresses, domains, URLs, subjects, file names, finding samples or body text. Metric labels are bounded enums (never tenant ids).
7. **Idempotent per round.** One row per `(scan_id, revision)`, written in the transaction that completes the round (revision 0) or that writes the late sandbox final (revision 1), both under the `email_scans` row lock; the unique key is the backstop. A rescan is a new round and gets new rows; old rows are never updated or deleted (except by retention and organization purge).
8. **Tenant from trusted context.** The worker takes the organization from the locked `email_scans` row; the api from the authenticated scope. A profile version is used only when its `organization_id` equals the round's (echo-checked).
9. **AI never decides alone (ADR-0034).** BEC contributions use the deterministic rule set; an AI-only raise can at most add the action `tag`.

### R1. A pure scoring library `@email-gateway/risk-scoring` (new package `packages/risk-scoring`)

- Dependencies: `zod`, `@email-gateway/security-contracts`; `node:crypto` for SHA-256 only. **No** Prisma, Redis, S3, network, clock or logger. Vitest with SWC like the other packages; `README.md`.
- Exports (names fixed):
  - Versions: `RISK_SCORER_VERSION = 'risk-score/1'`, `RISK_SIGNAL_MAP_VERSION = 'risk-signals/1'`, `RISK_INPUT_VERSION = 'risk-input/1'`, `RISK_PLATFORM_PROFILES = { 'rsk-default/1': … }` and `RISK_DEFAULT_PLATFORM_PROFILE_ID = 'rsk-default/1'`.
  - Vocabularies: `RISK_LEVELS = ['none','low','medium','high','critical']`, `RISK_ACTIONS = ['deliver','tag','require_approval','quarantine','block']` (strictness order), `RISK_VERDICTS` = the Prisma `MessageVerdict` values, `RISK_SIGNAL_GROUPS`, `RISK_SIGNALS`, `RISK_HARD_BLOCKS`, `RISK_REASON_CODES` (every `risk.*` code the scorer can emit; each matches `REASON_CODE_PATTERN`, ≤ 64 chars).
  - Schemas: `scoringInputSchema`, `riskProfileOverridesSchema` (strict, the tenant document), `effectiveProfileSchema`, `riskResultSchema`, `riskResultViewSchema` (for the api).
  - Functions: `buildScoringInput(rows: RoundRows, revision: 0 | 1): ScoringInput` (pure assembly from plain row objects, R12), `resolveProfile(platformId, version: { publicId, versionNo, baseProfile, overrides } | null): ResolvedProfile` where `ResolvedProfile = { profile: EffectiveProfile; source: 'platform' | 'tenant'; id: string; versionNo: number | null; sha256: string; violations: Violation[] }` (R10; a version whose `baseProfile` is no longer shipped resolves against `platformId` with the violation `base_profile_retired`; any violation → the platform default with `source: 'platform'`), `validateOverrides(doc): Violation[]`, `scoreRisk(input, resolved: ResolvedProfile): RiskResult` (R2–R9), `scoringErrorResult(input | null, resolved: ResolvedProfile, reason): RiskResult` (R13), `renderExplanation(lines): string` (R11), `canonicalJson(value): string`, `sha256Hex(text): string`.
- `scoreRisk` never throws for a schema-valid input and profile (property-tested with seeded random inputs, §9.1).

### R2. Inputs (`risk-input/1`)

`ScoringInput` (strict zod schema; the canonical JSON of this object is hashed into `input_sha256`):

```text
{
  version: 'risk-input/1',
  revision: 0 | 1,
  round: { scanKind: 'initial'|'rescan', lifecycleRound, outcome: 'scanned'|'scan_failed',
           requiredEngines: EngineName[] (sorted) },
  envelope: { direction: 'inbound'|'outbound'|'internal', attachmentCount, recipientCount },
  engines: [ { engine, required, status: 'definite'|'failed'|'skipped'|'missing',
               outcome: EngineOutcome | null, errorCode | null, reasonCodes (sorted, ≤ 32),
               score: string | null (decimal as text, informational), engineVersion | null,
               settingsVersion | null, attempts, completedAt ISO | null } ] (sorted by engine),
  auth: { spf, dkim, dmarc, dmarcPolicy, arc } | null      // outcomes only, no domains
  bec:  { deterministicVerdict, verdict, activeRuleCodes (sorted; rules with suppressed = null),
          trustedSender: 'authenticated'|'unauthenticated'|'none', aiRaised: boolean } | null,
  dlp:  { action, verdict, coverage: 'full'|'partial', maxSeverity: DlpSeverity | null } | null,
  sandbox: { outcome, reasonCodes (sorted) } | null         // revision 1 only; null in revision 0
}
```

- **Status** per engine: `definite` (a final with a definite verdict), `failed` (final `timeout`/`error`), `skipped` (final `skipped`), `missing` (in `requiredEngines` without a final; impossible at completion, kept for defence in depth and for the dry-run on a replica). The asynchronous `sandbox` engine is **never** in `engines`; it appears only as `sandbox` in revision 1.
- `trustedSender` is derived from the bec final's codes: `authenticated` when `bec.trusted_sender` is among `activeRuleCodes` or the final's codes, `unauthenticated` for `bec.trusted_sender_unauthenticated`, else `none`. **Reuse decision:** 5.1 reads no trusted-sender table; the BEC engine already matched `bec_trusted_senders` (expiry included) and checked From authentication at scan time, and its codes are part of the hashed input. A tenant manages trusted senders in one place (the existing `/bec/trusted-senders` API).
- `aiRaised = (verdict ≠ deterministicVerdict)` with the AI codes present (ADR-0034).
- Child rows missing where expected (a definite, non-skipped `bec` final without its `bec_scan_results` row; the same for `dlp`; a definite non-`unknown` `rspamd` final without `email_auth_results`) → the corresponding input is `null` **and** the builder adds the engine-level code `risk.input.<engine>_row_missing` to that engine's `reasonCodes` (mapped to a failure-class signal, R6). This is the pass-through's fail-safe expressed as risk.
- `score` of an engine is carried as text for the record only; the scorer never reads it (the Rspamd numeric score enters only through its tenant-threshold codes `spam.score` / `spam.suspicious_score`, so no score is counted twice).

### R3. Signals, the versioned signal map `risk-signals/1`, and groups (no double counting)

- A **signal** is one fact about the message. Each signal lists the `engine:code` pairs that assert it, its group, its default weight (integer points on the 0–1000 scale), the directions it applies to and whether trust may reduce it. **Several engines asserting the same fact raise one signal once** (e.g. `rspamd:auth.spf_fail` and `bec:bec.auth.spf_fail` → `auth_spf_fail`).
- A **group** collects overlapping signals and combines the weights of its fired signals with one rule: `max` (strongest only) or `capped_sum` (sum, capped). Groups are where double counting is prevented: DMARC failure and BEC tenant-domain spoofing share `auth_dmarc` (max); URL lookalikes and BEC sender/link lookalikes share `lookalike` (max); ClamAV, YARA and known-hash findings share `attachment_malware` (max; the per-message codes already de-duplicate per attachment, and two findings on the same or different attachments never add up).
- Group total = `rule(fired weights) × groupMultiplierPermille / 1000` (integer floor), then the trust factor for trust-reducible groups (R7), then the group cap. **Score** = `min(1000, Σ group totals)`, then floors (R5, R6, R8).
- **Exhaustiveness:** every code of `ATTACHMENT_REASON_CODES`, `URL_REASON_CODES`, `BEC_REASON_CODES`, `DLP_REASON_CODES`, `SANDBOX_REASON_CODES` and the new `RSPAMD_REASON_CODES` (R18) is either mapped to a signal or listed in `RISK_INFORMATIONAL_CODES` (contributes 0, recorded in evidence). A unit test fails on any code that is neither. `engine.*` attempt-failure codes are handled by status (R6), not by the map. An unmapped code at run time (a newer engine) is recorded as `risk.signal.unmapped_code` (contribution 0) and counted.

### R4. Levels and recommended actions

- Score 0–1000. Default thresholds (`rsk-default/1`): `low ≥ 100`, `medium ≥ 300`, `high ≥ 550`, `critical ≥ 800`; below `low` = `none`.
- Default action per level: `none → deliver`, `low → deliver`, `medium → tag`, `high → quarantine`, `critical → quarantine` (`block` is reserved for hard blocks that select it).
- **Recommended action** = the strictest (order `deliver < tag < require_approval < quarantine < block`) of: the level's action; the failure action (R6) when a required engine failed or a child row is missing; the unknown action `failures.unknownAction` (R6) when a required engine is `unknown`; the DLP binding (ADR-0037: `allow → deliver`, `alert → tag`, `require_approval → require_approval`, `quarantine → quarantine`, `block → block`; the recommendation is never weaker than the round's DLP action); every fired hard block's action (R5); `tag` for an AI-only BEC raise when `ai.tagOnAiOnlyRaise` (R9).

### R6. Engine failures, unknown results and missing inputs

- Per required engine: `failed`/`missing` → signal `engine_failed:<engine>` (weight `failures.engineFailureWeight`, default 300, bounds 200–600; group cap `failures.groupCap`, default 600, bounds 300–1000), reason `risk.engine.<engine>.<timeout|error|missing>`; `unknown` → signal `engine_unknown:<engine>` (weight `failures.unknownWeight`, default 60, bounds 30–200), reason `risk.engine.<engine>.unknown`.
- Floors when any required engine failed or is missing (or an `email_auth_results`, `bec_scan_results` or `dlp_scan_results` row is missing; a successful Rspamd check always writes its authentication row, so a missing one is lost SPF/DKIM/DMARC evidence, not absent evidence): level at least `failures.minLevel` (default `medium`, allowed `medium | high | critical`) and action at least `failures.action` (default `quarantine`, allowed `require_approval | quarantine`). A `scan_failed` round therefore never recommends `deliver` or `tag`.
- When any required engine is `unknown` (and none failed): level at least `failures.unknownMinLevel` (default `low`, allowed `low | medium | high`). Whenever any required engine is `unknown`: action at least `failures.unknownAction` (default `tag`, allowed `tag | require_approval | quarantine`, never weaker than the platform default and never stricter than `failures.action`), so an unknown result is never recommended for plain `deliver` (review round 1). The verdict is never `clean` (R8).
- `skipped` contributes nothing (not applicable: no attachments, outbound-only engines, BEC on non-inbound mail).
- The optional, asynchronous sandbox never contributes failure weight (it is outside the round, ADR-0040); its failures are recorded (`risk.engine.sandbox.<timeout|error>`) in revision 1.

### R7. Trusted-sender exceptions

- Profile: `trust.mode ∈ {off, reduce_content}` (default `reduce_content`), `trust.contentFactorPermille` (default 500, tenant bounds 250–1000).
- **Applies only when all hold:** direction `inbound`; `bec.trustedSender = authenticated`; `auth` present with `dmarc = pass`; no signal of `auth_dmarc` or `auth_other` fired; the bec input is present.
- **Effect:** group totals of trust-reducible groups (`T` in R3: `spam`, `reputation_ip`, `reputation_domain`, the `T` signals of `url_structure`, `bec_identity`, `bec_intent`, `bec_history`) are multiplied by the factor (integer floor). Nothing else changes: hard blocks, malware, URL threats, credential forms, lookalikes, impersonation, attachments, DLP, failures, floors.
- Recorded as `trust: { status: 'applied' | 'not_trusted' | 'denied_unauthenticated' | 'denied_auth_failure' | 'off', factorPermille, reducedGroups, pointsRemoved }` and codes `risk.trust.applied` / `risk.trust.denied_unauthenticated` / `risk.trust.denied_auth_failure`, plus an explanation line.

### R8. Engine-verdict floors and the final verdict

- **Floors** (profile `floors`, tenants may only raise): a `malicious` final of `rspamd`, `attachment` or `url` → level ≥ `high`; bec `deterministicVerdict = malicious` (when `hb.bec_malicious` is disabled) → level ≥ `high`; bec `deterministicVerdict = suspicious` → level ≥ `low`. Floors make the risk level monotone with the engines' own classifications: scoring never reports less than an engine concluded deterministically.
- A floor raises the score to that level's threshold (`score = max(score, threshold(level))`) so score and level agree.
- **Verdict** (`MessageVerdict`): hard block → its verdict; else `level ≥ low` → the category of the group with the largest applied total (ties: group catalog order) with categories `auth_dmarc → phishing`, `auth_other → suspicious`, `spam/reputation_* → spam`, `url_threat/lookalike/credential/url_structure/phishing_content → phishing`, `attachment_* → malware` when `attachment_malware`, else `suspicious`, `bec_* → bec`, `dlp → dlp_violation`, `coverage/engine_* → unknown`, `sandbox → suspicious`; else (`none`) → `clean` only when every required engine is `definite` or `skipped`, none is `unknown`, no coverage or failure signal fired and no child row is missing; otherwise `unknown`. `bulk` is not produced by `risk-signals/1` (no bulk signal exists).

### R9. The AI layer (ADR-0034)

BEC contributions come from `activeRuleCodes` (deterministic rules, suppressed rules excluded) and the floors use `deterministicVerdict`. AI codes contribute 0. When `aiRaised` and the deterministic verdict is `clean`/`unknown`, the result carries `risk.ai.raise_only` and, if `ai.tagOnAiOnlyRaise` (default `true`; a tenant may set `false`; never stronger than `tag`), the action floor `tag`. AI can therefore never move a message to a hold.

### R10. Profiles: platform default, tenant overrides, versions

- **Platform default** `rsk-default/1`: data in the library (`profiles/rsk-default-1.ts`), reviewed with the calibration report. A changed default is a new id (`rsk-default/2`), never an edit; `RISK_PLATFORM_PROFILE` selects the shipped id (validated against `RISK_PLATFORM_PROFILES`; default `rsk-default/1`).
- **Tenant overrides** (strict `riskProfileOverridesSchema`, every key optional, unknown keys refused):

| Key                                                                                                         | Bound                                                                                                                                                                                              |
| ----------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `thresholds.{low,medium,high,critical}`                                                                     | low 50–250, medium 200–450, high 400–700, critical 650–950; strictly increasing with ≥ 50 between neighbours (after merge)                                                                         |
| `actions.{none,low,medium,high,critical}`                                                                   | none: `deliver`; low: `deliver`/`tag`; medium: `tag`/`require_approval`/`quarantine`; high: `require_approval`/`quarantine`/`block`; critical: `quarantine`/`block`; non-decreasing with the level |
| `groupMultipliersPermille.<group>`                                                                          | 500–2000, for every group except `attachment_malware`, `engine_failure`, `engine_unknown`, `sandbox` (locked at 1000)                                                                              |
| `hardBlocks.<id>.{enabled, action}`                                                                         | `enabled` only for the "may disable"/"may enable" ids; `action ∈ {block, quarantine}` except `hb.dlp_block` (locked)                                                                               |
| `failures.{engineFailureWeight, groupCap, unknownWeight, minLevel, unknownMinLevel, action, unknownAction}` | as R6 (never below the platform default for `minLevel`/`unknownMinLevel`/`action`/`unknownAction`; `unknownAction` never stricter than `action`)                                                   |

- `resolveProfile` merges `RISK_PLATFORM_PROFILES[platformId]` with the overrides, validates the merged result, and returns either the effective profile (`source: 'tenant'`) or the platform default with the violations (`source: 'platform'`, the caller records `risk.profile.invalid_fallback`). `profile_sha256` = SHA-256 of the canonical effective profile.
- **Storage and lifecycle (api, R15):** one `risk_scoring_profiles` row per organization (created lazily) holding `active_version_id` (NULL = the platform default). Versions in `risk_scoring_profile_versions`: `draft` (editable, deletable) → `published` (immutable: the repository updates only `WHERE status = 'draft'`, and no route changes a published row) → activation is a pointer change; rollback = activating an earlier published version; reset = pointer NULL.
- **Effective for the next round only:** the round snapshots the pointer when it opens (`email_scans.risk_profile_version_id`, R13); a change never alters an open round or a stored score.

### R12. Assembling the input from rows (`buildScoringInput`, shared)

`RoundRows` = plain objects: the `email_scans` row (`requiredEngines`, `scanKind`, `lifecycleRound`, `status` → outcome), the message (`direction`, `attachmentCount`, `recipientCount`), the final `scan_engine_results` rows (engine, outcome, errorCode, reasonCodes, score as string, engineVersion, settingsVersion, attempt, completedAt), the rspamd `email_auth_results` row (outcomes only), the `bec_scan_results` row (`deterministicVerdict`, `verdict`, `rules[]` with `code` and `suppressed`), the `dlp_scan_results` row (`action`, `verdict`, `coverage`, `categories[].maxSeverity`), and for revision 1 the `sandbox` final. The email-worker (writer, in the completion transaction) and the api dry-run (replica) fetch the same rows with their own repositories and call this one function, so a dry-run with the profile the round used reproduces `input_sha256` and the result exactly (tested).

Exact type (exported by the library; every field plain data, JSON columns passed as read):

### R13. Where scoring runs: the email-worker, at round completion (ADR-0042)

- **Snapshot at round open:** `ScanRepository.openRound` reads `risk_scoring_profiles.active_version_id` for the round's organization (writer, inside the open transaction, echo-checked) and stores it in the new column `email_scans.risk_profile_version_id` with the `email_scans` insert (`INSERT IGNORE` semantics: the first opener's value wins).
- **Revision 0 at completion:** in `ScanRepository.complete()`, after `aggregateRound` and the `email_scans` update and **before** the lifecycle transition, in the same transaction and under the same locks: read the inputs (R12; finals already read, extend their `select`), resolve the profile (version row by id from a per-process LRU cache of **published, immutable** versions keyed by id; a cache miss reads the writer row and echo-checks `organization_id` and `status = 'published'`; a missing/foreign/invalid version → platform default with `risk.profile.invalid_fallback` or `risk.profile.missing_fallback`), score, insert `message_risk_scores` (revision 0), and set `email_scans.verdict`, `risk_score`, `scoring_version` (`risk-score/1`). Written whether or not the lifecycle transition applies (the score belongs to the round). The deadline sweeper's completion path is the same function, so swept rounds are scored too.
- **Revision 1 (sandbox):** never in revision 0 (order independence, ADR-0040 lesson). Written exactly once per round, by whichever of these two transactions happens second, both holding the `email_scans` row lock: (a) `writeRoundFinal` (sandbox-finalizer) inserted a non-`skipped` sandbox final and the round is no longer `running`; (b) `complete()` finds a non-`skipped` sandbox final already present. Revision 1 = the same round inputs plus `sandbox`, same profile snapshot. The unique key `(scan_id, revision, received_at)` makes a duplicate a no-op (`createMany … skipDuplicates`, counted).
- **Failure of scoring itself:** `scoreRisk` cannot throw on valid input; input validation errors, an unexpected exception or a profile resolution error produce the **error row** (`scoringErrorResult`: `status = error`, `score = thresholds.high` of the platform default, `level = high`, `verdict = unknown`, `recommendedAction = quarantine`, reason `risk.scoring_error`, explanation "Scoring failed; treated as high risk (fail-safe)") so the round still completes and the message is held by the pass-through; counted and alerted. A database error rolls back the whole completion (the delivery is retried, as today).
- Cost: one extra `email_auth_results`, `bec_scan_results` and `dlp_scan_results` read (indexed, unique by scan) and one insert per round; the profile read is cached.

### R14. Persistence (`message_risk_scores`, §3)

Monthly partitions, retention `core` 6 months like `email_scans`. One row per `(scan_id, revision)`. JSON columns bounded as in R11. Never message content.

## 4. Contracts (summary)

- **No new event and no topology change.** `scanned.v1` is unchanged (strict; ADR-0034 amendment). The revision-0 row commits in the same transaction as `scanned.v1`, so every consumer of `scanned.v1` (dev pass-through now, `email.policy.evaluate` in 5.2) can rely on it existing.
- **Binding for policy 5.2** (written into contracts.md by WP5): read `message_risk_scores` revision 0 of the event's `scanId`; a missing row is a hold; the final action must be **at least as strict** as every fired hard block, the failure floor and the DLP binding (ADR-0037), may be stricter than the recommendation, may be weaker than a level-only recommendation only through an explicit, audited tenant policy rule (never for hard blocks or failures); an AI-only raise (`risk.ai.raise_only`) never justifies a hold; revision 1 (sandbox) may be read if present when policy evaluates and may only make the decision stricter. 5.2 owns `email_messages.final_verdict`, `final_action`, `risk_score` (copied from the decisive score) and the transitions E8–E13. **5.3** records the recommendation and explanation with the quarantine entry and re-validates on release (a release re-reads the latest round's score; release of a hard-blocked message needs the 5.3 approval path).
- `RiskResult`/`RiskScoreView` schemas live in `@email-gateway/risk-scoring` (the api imports them for OpenAPI).

## 6. Prisma wrong-read mitigation in this step (4.2 §6)

Every deciding read is echo-checked and a mismatch is retryable: round open (`risk_scoring_profiles` by organization: echo `organization_id`); completion (`email_auth_results`, `bec_scan_results`, `dlp_scan_results` by scan: echo `scan_id`, `message_id`, `organization_id`, `received_at`; the profile version by id: echo `id`, `organization_id`, `status`); sandbox revision-1 path (the same reads); pass-through (`message_risk_scores`: echo every key column); api writers (profile and version rows by public id + organization). Transaction budgets stay ≥ 120 s (`SCAN_DB_TIMEOUT_MS`, the api's writer pattern of the DLP module). Echo mismatches throw `InconsistentRiskReadError` (email-worker: retryable like the other scan reads; api: retry the transaction once, then `503 inconsistent_read`).

## 7. Alternatives considered

- **Scoring in the policy-engine on `email.policy.evaluate`.** Rejected for 5.1: the dev pass-through reads `scanned.v1` from the outbox concurrently, so the score row would race it (missing row → spurious holds or a wait loop); it would add a deployable with a broker user and a ledger now, before 5.2 defines policy; and the score would depend on a second transaction's view of the round. The completion transaction already holds the locks and the exact set of finals. 5.2's policy-engine reads the stored row (ADR-0042).
- **A `mail.message.risk_scored.v1` event.** Not needed (the row commits with `scanned.v1`); would add a topology version for no consumer. Deferred to 5.2 if policy wants it.
- **Using the BEC engine's 0–100 score directly.** Rejected: it already contains the auth, lookalike and link rules that other engines also report (double counting); individual codes in groups avoid it.
- **Floating-point weights.** Rejected: integer points and permille factors make results bit-identical across platforms and Node versions.
- **Including the sandbox in revision 0 when it happened to finish first.** Rejected: order-dependent (ADR-0040). Revision 1 is deterministic.
- **Snapshotting the profile at completion.** Rejected: a profile change during a long round (deadline 30 min) would apply to it; the brief requires next-round-only semantics.
- **Per-signal tenant weights.** Rejected for 5.1: ~80 knobs without validated data invite over-fitting; group multipliers within 0.5×–2× are bounded and explainable.
- **A DB trigger enforcing immutability.** Rejected: the migration tooling and drift check do not model triggers; the repository updates drafts only (`WHERE status = 'draft'`) and tests prove a published version cannot change.
- **New `risk:*` permissions.** Rejected: profiles are policy configuration; the existing `policy:read/manage/publish` triple matches draft/publish semantics and needs no seed change.

## 9. Test plan

### 9.1 Unit (no infrastructure; `packages/risk-scoring`, email-worker, api, delivery-worker)

- **Signal mapping:** every row of the R3 table (each `engine:code` fires its signal, in its direction only); exhaustiveness over every engine code list (R3); unmapped code handling.
- **Groups:** `max` and `capped_sum` semantics, caps, multipliers, integer flooring; the three named overlaps (DMARC reject + BEC tenant-domain spoof = 400 not 700; URL lookalike + BEC link lookalike = 300; ClamAV + YARA + known hash = 1000 once) and same-fact de-duplication (`auth.spf_fail` from rspamd and bec counted once).
- **Failures:** each status (`failed` timeout/error, `missing`, `unknown`, `skipped`) per engine; floors and action floors; `scan_failed` never `deliver`/`tag`; missing child rows; sandbox failures informational.
- **Hard blocks:** each indicator fires, sets level/verdict/action, survives trust and negative-looking profiles; locked indicators cannot be disabled (`validateOverrides` refuses); `hb.dmarc_reject` off by default and enable-able.
- **Trust:** applied only with all R7 conditions; denied for T2, DMARC fail/none, any auth signal, non-inbound; never reduces locked groups; recorded.
- **Thresholds and actions:** boundaries (99/100, 299/300, …), custom thresholds, action monotonicity, DLP binding, AI-only tag.
- **Profile validation bounds:** every key at, inside and outside its bounds; unknown keys; merged-order checks; resolve fallback with violations.
- **Determinism:** same input → identical output and hashes (deep equality and canonical JSON equality); key-order and array-order permutations of the _raw rows_ give the same `inputSha256`; 10 000 seeded random inputs never throw and always satisfy the invariants (never `clean` with a failure/unknown; hard block ⇒ critical; trust never lowers a non-`T` group; score ∈ [0, 1000]).
- **Explanation:** text bounded, built from templates, no `@`/`://`/host-like tokens; ordering rules.
- email-worker: completion writes revision 0 with the snapshot profile; the deadline-sweeper path scores; revision 1 written by either order (sandbox before / after completion) exactly once; error row on scorer exception; profile cache by id; echo-check failures retryable; the rspamd mapper contract test (R18).
- api: overrides validation errors by path; immutability (PUT/DELETE on published → 409); publish/activate/reset pointer CAS; dry-run makes no write (repository spies) and reproduces a stored result; tenant isolation (another tenant's ids → 404); OpenAPI snapshot updated.
- delivery-worker: `riskHoldDecision` table (every action, hard block, error, missing) and the approver ordering (existing reasons first, unchanged).

### 9.5 Stack (`tests/integration/risk-smtp.test.ts`, through Postfix and the live containers)

1. Clean inbound message → one revision-0 row, `level none`, verdict `clean`, action `deliver`, delivered.
2. Spam: **GTUBE** — at SMTP time the inbound milter rejects GTUBE (ADR-0027), so the GTUBE message goes through the **outbound** path (authenticated connector → `postfix-outbound` → post-queue scan), expected `spam.gtube` → `level high`, verdict `spam`, action `quarantine`, held by the pass-through (`risk_recommendation`). If the outbound path also rejects GTUBE in-session, use the corpus spam sample (score between the tenant spam threshold and the milter reject score) inbound and record the deviation in §12.
3. **EICAR** attachment → `hb.malware_attachment`, `critical`, `malware`, `block`.
4. **DLP card number** (outbound, the platform default DLP policy `alert`) → `dlp` group, `low`, verdict `dlp_violation`, action `tag`/`deliver` per defaults; plus a tenant DLP `block` policy → `hb.dlp_block`, `block`.
5. **Engine outage** (stop the engine the existing `scan-resilience` suite stops, with its deadline settings) → `scan_failed` round with a revision-0 row: `risk.engine.<engine>.<error|timeout>`, level ≥ `medium`, action `quarantine`.
6. **Rescan** (`POST /messages/{id}/rescan`) → a second round with its own row; the first row unchanged.
7. **Profile change applies to the next round only:** message A scored with the platform default; publish a tenant version (e.g. `actions.medium = quarantine` or a threshold change); message B (and a rescan of A) use the tenant version (`profile_source = tenant`, `profile_id_text` with the version), A's first row unchanged.
8. **Dry-run changes nothing:** checksums of `message_risk_scores`, `email_scans`, `risk_scoring_*`, `audit_logs` and outbox counts before/after; `reproducible: true` with `profile: 'active'`.

**Regressions:** every stack suite from 2.2 to 4.6 (`smtp-*`, `routing-*`, `mime-ingestion`, `messaging-*`, `lifecycle-*`, `scan-*`, `attachment-*`, `url-*`, `bec-smtp`, `dlp-smtp`, `sandbox-smtp`, `sandbox-exec`, `schema`, `partitions`, `seed`, `replication`, `services`, `storage`, `mail-plane`, `accounts`, `domain-resolution`) and the package integration suites of every touched package.

#### Deviations and precisions

1. **`ALGORITHM=INSTANT` was accepted. No deviation.** MySQL 8.4 accepted `ALTER TABLE email_scans ADD COLUMN risk_profile_version_id BIGINT UNSIGNED NULL, ALGORITHM=INSTANT` in two cases. On `email_gateway_verify`, `email_scans` still had only `pmax` when the migration ran, because partitions are applied after all migrations. On the main local schema, `email_scans` had its split monthly partitions; before the migration `information_schema.innodb_tables` showed 5 partitions with `total_row_versions` ≤ 1, well below the limit of 64 row versions. Evidence: `migrate deploy` succeeded in both, and the drift check is clean. The algorithm is recorded in `docs/database/schema-reference.md` ("Step 5.1 changes").
2. **The catch-all partition is named `pmax`.** The work package text mentioned a "p_future/maxvalue convention". The convention in the repository, used by `dlp_engine`, `bec_detection` and the others and asserted by `schema.test.ts` ("… with a pmax partition"), is the single partition `pmax VALUES LESS THAN (MAXVALUE)` at creation, which `db:partitions apply` splits. The migration follows that convention. Nothing in the repository uses `p_future`.
3. **`public_id` has no database default.** Like the DLP and BEC tenant tables (`DlpPolicy.publicId` has no `@default`, and the tests set `randomUUID()`), both profile tables declare `publicId String @unique @db.Char(36)` with no `@default(uuid(7))`. The api (WP4) must set a UUIDv7, as its DLP and BEC repositories do. §3 says "UUIDv7" without naming the generator, so this is a precision, not a change.
4. **Prisma truncated one index name.** The secondary index `(organization_id, status, version_no)` of `risk_scoring_profile_versions` is named `risk_scoring_profile_versions_organization_id_status_version_idx`: Prisma shortened the default name to fit MySQL's 64-character identifier limit. No code depends on index names. The tests compare column sets, not names.
5. **`groups` is a reserved word in MySQL 8.0+.** The §3 column name `message_risk_scores.groups` was kept. Prisma quotes every identifier, so generated queries work: the insert and select in `schema.test.ts` pass. Any hand-written SQL (for example raw queries in WP3, WP4 or WP5) must backtick it. This is recorded in the migration header and in `schema-reference.md`.
6. **Implicit foreign key indexes.** MySQL created single-column indexes for the user foreign keys: `risk_scoring_profiles.updated_by_user_id`, and `risk_scoring_profile_versions.created_by_user_id`, `updated_by_user_id` and `published_by_user_id`. The organization foreign key of the versions uses the leading column of `(organization_id, status, version_no)`. The profile foreign key uses `(profile_id, version_no)`. This was verified with `information_schema.statistics` and documented in `indexing.md`.
7. **Purge ordering is documented but not implemented here.** §3 says that the organization purge deletes `message_risk_scores` in batches, then the versions, then the profile. The RESTRICT foreign keys enforce that order (tested: deleting a profile with versions, or an organization with risk rows, fails). The purge code in api `tenant-data` belongs to WP4.
8. **The migration timestamp is the UTC creation time** (`20261110203003`, 2026-11-10 20:30 UTC, which was 2026-11-11 local time). It sorts after `20261109092429_sandbox_result_token`.

No other deviation: the columns, types, nullability, defaults, enums, keys, indexes, foreign keys and delete rules match §3 and the WP1 instructions. The schema tests and the drift check verify them.

Work package WP2 of [step 5.1](15-risk-scoring.md) (R1–R12, R18, §9.1 library part, §9.2). This note records every deviation from the design, with evidence, and every code placement the implementer had to decide (§12 asks for it). WP5 folds it into §12.

Delivered: `packages/risk-scoring` (new), `packages/security-contracts/src/rspamd.ts` (+ test, index export, README row), the `@email-gateway/risk-scoring` dependency of `apps/email-worker` and `apps/api` (lockfile updated by `pnpm install`), `packages/risk-scoring/fixtures/calibration/risk-calibration-1.jsonl` and `docs/performance/risk-scoring-calibration.md`.

#### Deviations

1. **Failure and unknown signal ids use `_` instead of `:`.** R3 writes `engine_failed:<engine>` / `engine_unknown:<engine>`. A signal id is part of the reason code `risk.signal.<id>` (R1: every `risk.*` code matches `REASON_CODE_PATTERN` = `^[a-z][a-z0-9_]*(\.[a-z0-9_]+)+$`), which forbids `:`. Decision: one signal per synchronous engine, `engine_failed_<engine>` and `engine_unknown_<engine>` (rspamd, attachment, url, bec, dlp). Same group, weights from the profile, same semantics.
2. **DLP coverage values are `complete | partial`, not `full | partial`.** R2's input sketch says `coverage: 'full'|'partial'`, but `dlp_scan_results.coverage` is Prisma `DlpCoverage { complete, partial }` and `DLP_COVERAGES` in security-contracts is `['complete', 'partial']` (`packages/database/prisma/schema.prisma` model `DlpScanResult`). Decision: the input and `evidence.dlp.coverage` use the row's values, so `buildScoringInput` passes the column through unchanged.
3. **An engine's `reasonCodes` in the input may hold 33 entries.** R2 says ≤ 32; an engine final can already carry 32 codes, and the builder must add `risk.input.<engine>_row_missing` without dropping an engine code (dropping would lose evidence silently). Decision: `MAX_INPUT_REASON_CODES = 33` (32 + the one synthetic code) for `engines[].reasonCodes` only. The result's `reasonCodes` stay ≤ 32.
4. **`riskScoreViewSchema` and `riskResultViewSchema`.** R1 names `riskResultViewSchema`, R11 and the WP prompt name `riskScoreViewSchema`. Both are exported (the second is an alias of the first).
5. **`validateOverrides(doc, platformId?)`.** R1 shows `validateOverrides(doc)`. An optional second parameter (default `rsk-default/1`) lets `resolveProfile` validate a version against its own shipped base; callers that pass one argument get the documented behaviour.
6. **`resolveProfile` merges into the version's own base when it is shipped.** R10 says "merges `RISK_PLATFORM_PROFILES[platformId]` with the overrides". A published version records its `baseProfile`; when that id is still shipped the overrides are merged into it (that is what was validated and hashed at publish), and the id is `<baseProfile>+t:<publicId>#<n>`. Fallbacks always use `platformId`. With one shipped profile (`rsk-default/1`) both readings give identical results.
7. **`ResolvedProfile.fallback`.** Added as the WP prompt specifies (`null | 'invalid' | 'missing' | 'foreign' | 'base_profile_retired'`); the scorer turns it into `risk.profile.invalid_fallback` (for `invalid` and `base_profile_retired`), `risk.profile.missing_fallback` or `risk.profile.foreign_fallback`, so callers do not add these codes themselves.
8. **An unmapped code prevents `clean`.** R3 says an unmapped code contributes 0 and is recorded; R8's clean conditions do not mention it. A code the map does not know comes from a newer engine whose meaning is unknown, so treating the round as completely clean would contradict §2.0-1. Decision: an unmapped code keeps 0 points but turns a `none`-level verdict into `unknown` (tested).
9. **Verdict fallback when the level is ≥ low but no group has points.** R8 takes "the category of the group with the largest applied total"; a floor can raise the level when every group total is 0 (e.g. trust reduced a BEC-suspicious round to 0 points). Decision: `unknown` when a failure or unknown result exists, else `suspicious`. Not reached by the dataset.
10. **`round.outcome = scan_failed` counts as a failure for floors and actions** even if no engine entry shows `failed`/`missing` (defence in depth: "a `scan_failed` round never recommends `deliver` or `tag`", R6).
11. **Contribution `applied`.** R11 does not define it per signal. It is the signal's own points after trust and the group multiplier (`floor(floor(weight × trust / 1000) × multiplier / 1000)`), the number the explanation and the reason-code ranking use; the group total (`max` or capped sum) is in `groups[].total`.
12. **`failures[]` statuses.** R11 lists `{ engine, status, weight }` without the status vocabulary. Values: `timeout`, `error`, `missing`, `row_missing` (bec/dlp child row), `unknown` (weight = `failures.unknownWeight`). `floors[]` sources: `engine_malicious`, `bec_suspicious`, `engine_failure`, `engine_unknown`, `hard_block`. `trust.factorPermille` is the profile factor when trust applied, else 1000.
13. **Explanation line codes** beyond the R11 list: `input_missing` (a missing result row), `unmapped_codes`, `arc_trusted` (the R3 informational sentence "ARC chain of a trusted sealer vouched for a DMARC failure"), `sandbox`, `scoring_error`. Hard-block lines name the indicator without `hb.` so the text has no dotted tokens. Rendered text drops whole lines past 2048 characters and ends with "(more omitted)".
14. **AI raise detection.** R2: `aiRaised = (verdict ≠ deterministicVerdict) with the AI codes present`. Implemented as: verdicts differ **and** the bec final carries one of `BEC_AI_CODES` (`bec.ai.flagged` / `bec.ai.corroborated` are what `packages/bec/src/ai/combine.ts` emits when it raises).
15. **`hb.tenant_domain_spoof` and `hb.dmarc_reject` require `direction = inbound` strictly** (R5 "inbound"), while their signals also fire for `internal` mail when the engine produced the code (R3 direction rule). Trust also requires `inbound` strictly (R7).
16. **`hb.dlp_block` fires from the DLP row whenever it is present**; the DLP signals (action, severity, coverage) fire only when the dlp engine entry is `definite` (WP prompt rule (a)). A row with `block` is never ignored.

#### Deviations and precisions

1. **A draft version in the pointer falls back as `missing`, not `foreign`.** The WP3
   instructions say "status draft or missing → `platformProfile(platformId,'missing')`", while
   the JSDoc of the library's `platformProfile` describes `foreign` as "of another organization
   or not published". The WP instruction was followed: a draft gives `missing`
   (`risk.profile.missing_fallback`), and only another organization's row gives `foreign`. The
   runbook documents this. Drafts and missing rows are never cached, so a draft that is published
   later resolves normally. Evidence: `profile-provider.test.ts` "a missing row or a draft falls
   back (missing) and is never cached".
2. **A round whose message row is gone gets no risk row.** The row needs `direction`
   (`MessageDirection`, NOT NULL), and the message no longer exists: the organization purge or a
   test cleanup deleted it while its round was open. The transition is `not_found` in that case,
   so nothing is delivered. The scorer returns `skipped`, counted as
   `scan_risk_skipped_total{revision,reason="message_gone"}` (a new series) and logged at warn.
   `RiskScoreMissing` subtracts these rounds. Evidence: `risk-scorer.test.ts` and
   `completion.test.ts` "a round whose message row is gone …".
3. **The child rows are read with `FOR SHARE`, on both paths.** R13 says "writer, echo-checked".
   The sandbox path holds only the `email_scans` row lock, and its REPEATABLE READ snapshot can
   predate the completion that committed the finals and the child rows. A consistent read could
   then miss them and score `row_missing` or `missing` by mistake. This is the same reason
   step 4.6 X15 reads submissions `FOR SHARE`. One implementation serves both paths. The locks
   cover only rows of that scan, because every unique key used leads with `scan_id`
   (`scan_engine_results (scan_id, final_engine, received_at)`, `email_auth_results (scan_id,
engine, received_at)`, `bec_scan_results` / `dlp_scan_results (scan_id, received_at)`). Lock
   order is scan → result rows, as in the round's own transactions. The **message** row is read
   without a lock: its direction and counts are fixed before the round opens, and locking it
   after the scan row would invert the message → scan order. On the completion path, the finals
   come from the existing typed read: its `select` was extended with `score`, `engineVersion`,
   `settingsVersion` and `completedAt` (`RISK_FINAL_SELECT`).
4. **Metrics and logs are recorded after the commit.** The design names the series but not when
   they are counted. `scoreRound` returns a record. `ScanRepository.finalize` and `sweepRound`,
   and `PrismaSandboxStore.transaction`, call `RiskScorer.record` only after their transaction
   resolved. A rolled-back completion, which is then retried, is therefore never counted twice,
   and `scan_risk_scores_total{revision="0"}` stays comparable with
   `scan_rounds_completed_total`, which is also counted after the commit. Evidence:
   `completion.test.ts` "records nothing when the completion transaction fails after scoring".
   Wrong reads are the exception: they are counted when they are detected, like the other
   engines' `*_inconsistent_reads_total`.
5. **Two series beyond the R19 list, and one extra label.** The added series are
   `scan_risk_inconsistent_reads_total{read}` (reads `profile`, `profile_version`, `scan`,
   `message`, `finals`, `auth`, `bec`, `dlp`; the same pattern as bec, dlp and sandbox) and
   `scan_risk_skipped_total{revision,reason}` (point 2). The extra label is `revision` on the
   `scan_risk_score` histogram, so that revision-1 rows do not skew the revision-0 distribution.
   All labels are bounded, and an unknown value becomes `other`.
6. **The `RiskScoreMissing` expression is made precise.** It is
   `(sum(increase(scan_rounds_completed_total[30m])) - (sum(increase(scan_risk_scores_total{revision="0"}[30m])) or vector(0)) - (sum(increase(scan_risk_skipped_total{revision="0"}[30m])) or vector(0))) >= 1`,
   with `for: 30m`. Each part has a reason:
   - `sum()` makes the series with different label sets comparable;
   - `or vector(0)` keeps the alert working when no risk series exists at all, for example
     when an old release completes the rounds (tested);
   - skipped rounds are subtracted (point 2);
   - the threshold is `>= 1` rather than `> 0` because `increase()` extrapolates each series on
     its own and can leave fractional differences.

   `RiskScoringErrors` is two rules with the same name: warning with no `for`, and critical with
   `for: 1h`. Both are grouped by `reason`. The other expressions are R19's, grouped by their
   bounded label.

7. **The integration error row uses `profile_error`.** A malformed engine reason code cannot
   reach the scorer on the completion path: when the transition applies, the `scanned.v1`
   contract refuses the code first (`NonRetryableError('scanned_payload_invalid')`, unchanged
   4.x behaviour), and that rolls back the whole completion, risk row included. This was found
   by the first integration run. The integration test therefore triggers the fail-safe row with
   a published version row whose public id is malformed (`profile_error`). `input_invalid` and
   `scorer_exception` are covered by the unit tests (`risk-scorer.test.ts`).
8. **`ScanRepository` takes the scorer as a required constructor argument** (the third, after the
   transaction budget). `createScanInfrastructure` and `createSandboxJobs` accept an optional
   `risk`, which defaults to a new scorer on the same registry, so the integration supports and
   tests always score. `PrismaSandboxStoreOptions.risk` is required. The integration supports
   (`support/scan.ts`, `support/sandbox.ts`, `sandbox-sweeper.test.ts`) were updated.
9. **Revision 1 for a round completed before 5.1.** A late sandbox final of such a round writes
   revision 1 alone, without a revision-0 row. Rows are independent per revision, and the design
   does not require revision 0 to exist first. No special case was added.
10. **Status used for revision 1 on the sandbox path.** The status comes from the locked
    `email_scans` row (`completed` → `scanned`, `failed` / `timed_out` → `scan_failed`, so the
    failure floors still apply). An unexpected status value is treated as `failed`, which is
    defence in depth and never `clean`.
11. **What `duration_us` measures.** It is the time from the start of `scoreRound` (input reads,
    profile resolution, building, scoring and mapping) to just before the insert. It is clamped
    to INT UNSIGNED.
12. **`scan_risk_unmapped_codes_total{engine}` counts from `evidence.unmappedCodes`.** The
    library caps that list at 8, so a round with more than 8 unknown codes counts 8. The alert
    only needs "> 0".
13. **Unit-test doubles.** The repository-level tests (`risk/completion.test.ts`) run the real
    `ScanRepository`, `RiskScorer`, `RiskRoundReader`, `RiskProfileProvider` and
    `DeadlineSweeper` against an in-memory Prisma stand-in (`risk/fakes.test-support.ts`). They
    replace `lockLifecycle` and `transitionMessage` with recorders through `vi.mock`, so that the
    statement order can be asserted. The real lifecycle service is covered by its own tests and
    by `integration/risk-scoring.test.ts`. No production code path is mocked.
14. **The R18 contract test checks both directions.** It drives `mapRspamdVerdict` through every
    exact, prefix and positive-only symbol of the catalog. Each symbol is combined with the
    threshold scores of the settings, a DMARC/SPF failure, a trusted ARC chain, the reject
    action and a pre-filter, under the platform settings and three tenant settings. The test
    also drives the engine's size refusal. It asserts that no emitted code falls outside
    `RSPAMD_REASON_CODES` and that every listed code is reached (including `engine.too_large`).
    It also asserts that the two `RSPAMD_MAPPING_VERSION` values are equal.
15. **Kubernetes**: the risk keys are set in each Deployment's `env`, not in the shared ConfigMap.
    This follows §5 ("the Kubernetes email-worker / api manifests get …") and the WP scope
    ("env entries only").

#### Deviations and precisions

1. **Dry-run `result` is the `RiskResult` plus `revision`, without `createdAt`.** The WP prompt says "riskScoreView-shaped". `RiskScoreView` = result + `revision` + `createdAt`; a dry-run is not stored, so it has no creation time. Decision: `RiskDryRunResultSchema = riskResultSchema.extend({ revision })` (documented in OpenAPI). Every result field, including `versions` and `inputSha256`, is identical in shape to the view.
2. **Inline overrides in the dry-run are labelled `<platform>+t:inline` with `versionNo: null`.** `resolveProfile` requires a UUID public id and a positive version number, which an unsaved document does not have. `inlineProfile` merges the validated overrides into the platform profile (`mergeOverrides` + `effectiveProfileSchema`), computes `sha256` of the canonical effective profile exactly as `resolveProfile` does (unit test: the inline sha equals the sha of the same overrides saved as a draft), and labels it `rsk-default/1+t:inline`. Consequence: its explanation `profile` line reads "Profile: tenant version (rsk-default/1 base)." (empty number; the library's fixed template). Never stored.
3. **`active` with a snapshot the organization does not own resolves to `missing`, not `foreign`.** The dry-run reads the snapshot version tenant-scoped (`WHERE id AND organization_id = scope`), so another organization's row is never read; a non-published row of the organization resolves to `foreign`, as in WP2's definition. The email-worker (WP3) may distinguish a foreign row by its echo check; the only difference is the `risk.profile.missing_fallback` vs `risk.profile.foreign_fallback` reason code, and a foreign pointer cannot arise through the api (activation checks the organization). Recorded so WP5 can compare with WP3.
4. **Version numbers can be reused after the newest draft is deleted.** Numbers are `MAX(version_no) + 1` under the organization lock (unique `(profile_id, version_no)`); deleting the highest-numbered draft frees its number. Published versions are never deleted, so a number that a stored score or the pointer can reference is never reused. No schema counter exists for a strictly monotonic sequence (WP1 schema); not changed.
5. **Optional `expectedProfileVersion` on activate and reset.** R15 gives these routes no body. To let a client avoid racing another administrator, both accept an optional `{ expectedProfileVersion }` (the profile row's `version`, shown as `profileVersion` by `GET /profile`; `409 risk_profile_version_conflict` with `currentProfileVersion`). An empty body behaves as R15. The internal pointer CAS on `version` happens regardless.
6. **No-op pointer changes are not audited.** Activating the already-active version and resetting while the platform default is active return the profile view without a write, an audit row or a counter increment ("audit every change": nothing changed).
7. **Publish re-validates through `resolveProfile`.** `profile_sha256` is `resolveProfile(RISK_PLATFORM_PROFILE, version).sha256`; any violation (including `base_profile_retired`) is `400 risk_profile_invalid` and the draft stays a draft. Since WP2 deviation 6 merges into the version's own (shipped) base, this hash is the one the email-worker computes for the same version.
8. **`risk_revision_unavailable` and the metric.** R19 lists `risk_dry_runs_total{result}` ∈ `ok, not_complete, not_found, invalid_profile`. The new `409 risk_revision_unavailable` (revision 1 without a non-skipped sandbox final) is counted as `not_complete` (the sandbox may not have finished); no new label value was added.
9. **The `risk` section is shown to `message:read` without `dlp:read`.** R15 puts the scans read API (and its `risk` section) under `message:read`. A score's `evidence.dlp` carries the round's DLP action, coverage and maximum severity and its contributions carry `dlp:action.*`/`dlp:severity.*` assertions; the same facts are already visible to `message:read` holders as the `dlp` engine's outcome and reason codes (`dlp.action.<action>`, detector codes) on the engine entry. No masked sample, finding or policy id is in a risk row. Kept as designed; WP5 may want to state it in docs/security/rbac.md.
10. **Purge: no `ORDER BY` on `message_risk_scores`.** Like `dlp_scan_results` (partitioned, `PRIMARY KEY (id, received_at)`), the batch is `DELETE … WHERE organization_id = ? LIMIT n`; the profile tables use `ORDER BY id LIMIT n`. Order scores → versions → profile respects the RESTRICT keys (`versions.profile_id`, both `organization_id`); `active_version_id` has no foreign key.
11. **delivery-worker 4.x integration cases run with `riskHold: false`.** The existing pass-through cases in `integration/approvals.test.ts` insert scanned messages without score rows (their fixtures predate 5.1). With the default `true` they would all be held as `risk_missing` (correct fail-safe behaviour, but not what those cases test). They now construct the approver with `{ riskHold: false }` (`STEP_4_6`, R17: the flag restores 4.6 behaviour), so they keep proving the 4.x holds unchanged; a new case with the default `true` writes revision-0 rows and proves: `require_approval`/`quarantine`/`block` held, hard-block row held, error row held, missing row held (warn), a malicious verdict keeps its 4.x reason with a `deliver` row, `deliver`/`tag` approved, a revision-1 `block` row ignored, and a shifted read rolled back. The unit suite runs every existing case with the flag **on** (its fake transaction answers a `deliver` row of the round asked for). The stack suites (WP5) exercise the default with real scores.
12. **`riskHoldAction` for a hard block.** A hard block always recommends `quarantine` or `block` (R4/R5), so in practice a hard-blocked row is counted under its recommended action; `hard_block` is used only if a row carried hard blocks with a weaker recommendation (defence in depth). `error` takes precedence for an error row. The integration case asserts a hard-blocked `block` row is counted as `block`.
13. **Dry-run of malformed rows.** As in the completion transaction (R13), a `RiskInputError` from `buildScoringInput` returns `scoringErrorResult(null, resolved, 'input_invalid')` (status `error`, level `high`, action `quarantine`) instead of an HTTP error, so the dry-run reproduces stored error rows; an unexpected scorer exception returns the `scorer_exception` error result.

No other deviation: paths, permissions, stores, error codes, audit actions, metrics and the pass-through order follow R12, R15–R17, R19 and §6.

#### Deviations and precisions

1. **Case 4 is two tests, and 4b uses a second organization.** The DLP engine caches tenant policies for up to `DLP_TENANT_DATA_CACHE_TTL_MS` (30 s, D3), so adding a block policy to the organization that just scanned 4a under the default policy could race the cache, and the platform default applies only when the organization has no policy at all. 2. **The rescan target of case 7 is the EICAR message.** E19 (admin rescan) applies from `scanning`, `scanned`, `scan_failed`, `policy_evaluated` and `quarantined`, not from `delivered`, so the clean message of case 1 cannot be rescanned; the EICAR message stays `scanned` (held) and keeps its platform-default round 0.
