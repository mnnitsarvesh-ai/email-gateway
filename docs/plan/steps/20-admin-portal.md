### 1.2 The API contract the portal may use

`docs/api/openapi.json` (OpenAPI 3.0.0, 266 operations, all under `/api/v1`, two security schemes `access-token` and `api-key`; operationIds `<Controller>_<method>_v1` and tags frozen by the snapshot). Vendor extensions the portal consumes: `x-eg-permissions` (243 operations; `[{ mode: "all"|"any", permissions: [...] }]`), `x-eg-idempotency` (42; `required` | `legacy`), `x-eg-cursor` (44; `v0` | `v1`), `x-eg-rate-class` (57), `x-eg-returns-secret` (8), `x-eg-secret-replay` (2). Conventions (ADR-0050/0051/0052): bare single resources; lists `{ data, nextCursor }` **except the 5.3 quarantine lists, which keep `{ items, nextCursor }`**; no totals, no offsets; errors `{ statusCode, error, code, message, correlationId, requestId, ... }` (`message` is `string[]` for `validation_failed`); headers `X-Request-Id`, `RateLimit-*`, `Retry-After`, `Idempotency-Replayed`; strict request schemas (unknown field = `400`). Cursor v1 lists accept `sort` (allow-listed); the 33 v0 lists accept no `sort`.

Authentication (docs/security/authentication.md, ADR-0016): `POST /auth/login` returns tokens **in the JSON body** (`accessToken` 600 s default, single-use rotating `refreshToken`, `sessionId`, `mfaEnrollmentRequired`) or `{ mfaRequired, mfaToken, expiresIn }`; `POST /auth/mfa/verify`; `POST /auth/refresh` (single use; **two concurrent refreshes of one token look like reuse and revoke the whole session**); `GET /auth/me` returns `user`, `organization`, `roles`, **`permissions`**, `mfaEnabled`, `mfaEnrollmentRequired`, `session.mfaAuthenticated`, `override`; the platform override (`POST /platform/overrides`, MFA session, `platform:tenant_override`) returns a non-refreshable access token scoped to the target organization. Emailed links are `${PORTAL_PUBLIC_URL}/auth/<accept-invitation|reset-password|verify-email>#token=<token>`. Per-IP limits: login 20/min, MFA verify 20/min, refresh 60/min, IP failure block after 50 failures in 15 min (§2 P5 explains why the BFF needs the trusted forwarder).

**Links the platform already sends that the portal must serve** (notification-worker and alert templates, steps 5.3 and 6.2): `/messages/<messageId>`, `/domains/<domainId>`, `/webhooks/<webhookId>`, `/quarantine`, `/quarantine/me`, `/quarantine/me/<entryId>`, `/quarantine/approvals/<approvalId>`, `/quarantine/releases/<releaseId>`, `/auth/reset-password`, `/auth/accept-invitation`, `/auth/verify-email`. These paths are a contract (§3.1).

## 2. Decisions

### P1. Next.js App Router, client-rendered console behind a BFF (ADR-0058)

- Keep Next.js 15 App Router, React 19, Tailwind 4, shadcn/ui. Route groups: `src/app/(auth)/…` (public pages, minimal layout), `src/app/(console)/…` (authenticated shell), `src/app/auth/…` (the three emailed-link pages, public), `src/app/bff/…` (route handlers), `src/app/api/health` (probe, unchanged).
- **The console is client-rendered**: pages are client components that fetch through the BFF with TanStack Query. Server components render only static frames (layouts, metadata). Reason: one place refreshes tokens (P4), no server-side token refresh races, no tenant data in RSC payload caches. Every route is dynamic (`export const dynamic = 'force-dynamic'` at the console layout) because CSP nonces (P10) require it.
- `middleware.ts` (Node runtime) does three things only: CSP nonce + headers (P10), redirect to `/login?next=` when the session cookie is missing or unreadable for a console route, and refusal of cross-site state-changing requests to `/bff/*` (P6 first line). It never calls the API.
- `/` redirects to the first navigation entry the user may use (default `/dashboard`).

### P2. Browser session: sealed httpOnly cookie, tokens never reach JavaScript

- The BFF (route handlers under `/bff`) is the only holder of tokens. Session cookie **`__Host-eg_session`** (or `eg_session` when `PORTAL_PUBLIC_URL` is `http://` — allowed only for `APP_ENV=local|ci`; browsers treat `http://localhost` as a secure context so `Secure` stays set): `HttpOnly; Secure; SameSite=Strict; Path=/; Max-Age` = until `refreshTokenExpiresAt`.
- Content: AES-256-GCM sealed JSON (key `PORTAL_SESSION_KEY`, 32 bytes hex; `PORTAL_SESSION_KEY_PREVIOUS` accepted for unsealing during rotation; random 96-bit IV; AAD `eg-portal-session/v1`; format `v1.<b64url iv>.<b64url ciphertext+tag>`; Web Crypto so the same code runs in middleware and handlers): `{ v: 1, at, atExp, rt, rtExp, sid, csrf, mfaEnroll, ovr?: { id, at, exp, organizationId, organizationName } }`. Size budget ≤ 3,800 bytes (asserted by a unit test with two maximum-size JWTs); larger → the override token is refused with `override_cookie_too_large` (never silently truncated).
- Pre-session MFA challenge: cookie **`__Host-eg_mfa`** (sealed `{ v: 1, mfaToken, exp, next }`, `Max-Age` = `expiresIn` ≤ 300 s, same attributes), deleted on success or expiry.
- CSRF cookie **`__Host-eg_csrf`** (not HttpOnly, same other attributes, 32 random bytes b64url) equal to `session.csrf`; rotated on login, refresh and logout.
- Never in `localStorage`/`sessionStorage`/IndexedDB: tokens, `mfaToken`, CSRF token, user data. `localStorage` holds only per-viewer UI conveniences (column visibility, sidebar collapsed, theme) behind `try/catch`.
- Cookie lifetime and logout: `POST /bff/session/logout` calls `POST /auth/logout` (ends an active override with `DELETE /platform/overrides/{id}` first), then clears all three cookies even if the API call fails (logged), and returns `204`.

### P4. Token refresh: one coordinator in the browser

- The proxy **never refreshes**. When `atExp` has passed it answers `401 { code: "access_token_expired" }` without calling the API; an API `401` is passed through.
- The client (`src/lib/session/refresh.ts`) runs a single-flight refresh: in-memory promise + `navigator.locks.request('eg-session-refresh', …)` across tabs (in-memory only when Web Locks is unavailable). The API client retries a request **once** after a successful refresh on `401` with code `access_token_expired` or `unauthorized`. A proactive timer refreshes 60 s before `accessExpiresAt` while the tab is visible.
- Refresh failure (`401 session_expired`) → query cache cleared → `/login?next=<current path>&reason=expired` with a toast. Revocation (logout elsewhere, admin disable) surfaces the same way at the next request: after an api `401 unauthorized` the client refreshes with `force: true`, which skips the BFF's "fresh enough" short-circuit, so the api refuses the revoked refresh token (closing round, §14.6).
- Session mutations (`logout`, `logout-all`, override start and end) refresh an access token that expired, or expires within 5 s, **server-side** before calling the api, and set the rotated cookies on every later response. The client sends them under the refresh Web Lock, so the single-use refresh token never races a refresh in another tab. Logout clears the cookies in every case and answers `502 logout_incomplete` when the api session could not be ended; ending an override counts only `404` as already ended (closing round, §14.6).
- Override: when `ovr.exp` passed the proxy drops `ovr`, answers `401 { code: "override_expired" }`; the client reloads `me`, shows a toast, stays logged in as the operator. Override tokens are never refreshed (API rule).

### P5. Generic proxy and the trusted client-IP forwarder (ADR-0060)

- **Allow-list from the contract:** the proxy resolves `method + /api/v1/<path>` against the generated route table (`operations.gen.ts`, P7) and refuses anything that is not an OpenAPI operation with `404 { code: "route_not_found" }` (portal-coded, same envelope). Path segments are matched against the templates after rejecting `..`, `%2f`, `%5c`, `//`, and NUL; the upstream URL is rebuilt from the template and the encoded parameter values.
- **Token-bearing operations are not proxied** (`403 { code: "bff_route_required" }`): `AuthController_login/verifyMfa/refresh/logout/logoutAll`, `PlatformOverrideController_start/end`. Secret-bearing responses that the user must see once (`x-eg-returns-secret`: API key create, SMTP connector create/rotate, webhook create/rotate, TOTP setup, recovery codes) pass through with `no-store` and are displayed once (P12).
- Authorization header: `Bearer ovr.at` while an override is active, else `Bearer at`; public operations (no `x-eg-permissions`, no security) are sent without it. **No tenant header exists or is ever sent**; the tenant is the token's.
- Request headers forwarded (allow-list): `content-type`, `accept`, `idempotency-key`, `x-correlation-id` (minted by the BFF when absent), `user-agent` (the browser's). Added: `X-EG-Client-IP` and `X-EG-Forwarder-Token` (below). Everything else, including cookies and any client-sent `X-EG-*`, is dropped. Body limit 1 MiB (`413 payload_too_large`). Upstream timeout `PORTAL_API_TIMEOUT_MS` → `504 { code: "upstream_timeout" }`; connection failure → `502 { code: "upstream_unavailable" }`.
- Response headers passed back: `content-type`, `content-disposition`, `x-request-id`, `x-correlation-id`, `ratelimit-limit/remaining/reset`, `retry-after`, `idempotency-replayed`, `deprecation`, `link`; plus `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`. Bodies stream through unchanged (downloads included, P12).
- **Why a forwarder:** every browser request reaches the api from the portal's address. The api's per-IP limits (login 20/min, IP failure block after 50 failures) would then apply to **all portal users together**: one attacker could lock everyone out, and `login_audit_logs`/`audit_logs.source_ip`/session IPs would all show the portal. Reading `X-Forwarded-For` with `HTTP_TRUST_PROXY` hops is not safe here: the api is also reachable through its own Ingress (one hop) and directly on the internal network (zero hops) at the same time.
- **Decision:** a shared secret `API_TRUSTED_FORWARDER_TOKEN` (32–256 characters; `_FILE` accepted; empty = feature off) known to the api and the portal. The portal sends `X-EG-Client-IP: <ip>` and `X-EG-Forwarder-Token: <token>`. The api's `TrustedForwarderMiddleware` (first middleware) compares SHA-256 digests with `timingSafeEqual`; on a match and a valid IP (`net.isIP`, ≤ 45 chars, IPv4-mapped IPv6 normalized) it makes that IP the request's `req.ip` (instance property), so `clientIp(req)`, every per-IP `@RateLimit`, the login throttle, `login_audit_logs`, `audit_logs.source_ip` and session IPs use the browser's address. Mismatch or invalid IP → ignored (the socket/trust-proxy IP stays), metric `api_trusted_forwarder_total{outcome="rejected"|"invalid_ip"}`, warn log without values. Both headers are always deleted from `req.headers`. The portal derives the browser IP from `X-Forwarded-For` with `PORTAL_TRUST_PROXY_HOPS` (0 locally: the entry Next's own server appended for the socket peer; 1 behind the Ingress) and omits the header when it cannot determine one.
- Production: the portal refuses to start without `API_TRUSTED_FORWARDER_TOKEN` when `NODE_ENV=production`; the api logs a startup warning when it is empty in production (the api without a portal does not need it).

### P6. CSRF and request integrity

- Every `/bff/*` request with a method other than `GET`/`HEAD`: (1) `Origin` must equal the origin of `PORTAL_PUBLIC_URL` (fallback: `Sec-Fetch-Site: same-origin` when `Origin` is absent; neither → `403 { code: "csrf_failed" }`); (2) for session-bearing routes (all except `/bff/session/login`, `/bff/session/mfa` and the public operations of the generic proxy) `X-CSRF-Token` must equal `session.csrf` (constant-time). `SameSite=Strict` is the third line.
- `GET` through the proxy never mutates (the API's `GET`s are reads; the proxy refuses a body on `GET`).

### P8. Data fetching, mutations and error handling

- TanStack Query v5. Query keys `[operationId, params]`. Defaults: lists `staleTime` 30 s, reports 60 s (matches the server cache), `retry` only for network errors and `503`, never for `4xx`; `refetchOnWindowFocus: false` for reports.
- **URL state:** filters, search, sort, range and tab live in the search params (shareable, back-button safe). Pagination is forward keyset: a cursor stack in component state (Previous pops it); any filter change resets the stack. No totals ("Page 3 · 25 rows"). A short page with `nextCursor` (scan budget, 6.1 D6) shows "More results may exist further back — Load next page".
- **Mutations:** `useApiMutation(operationId)` creates one `Idempotency-Key` (`crypto.randomUUID()`) per user intent (form submission or confirm click) and reuses it for automatic and manual retries of the same intent; a new intent gets a new key. Handling: `409 idempotency_request_in_progress` → wait `Retry-After` (≤ 10 s) and retry with the same key (twice at most); `Idempotency-Replayed: true` → treated as success, toast "Already applied"; `422 idempotency_key_reused` → error toast (programming error, logged with `requestId`); other `409`/`422` module codes → shown at form level with the API message; `400 validation_failed` → `"<path>: <issue>"` mapped to form fields, remainder at form level; `429` → toast with the `Retry-After` countdown and the submit button disabled until then; `403 mfa_required` → dialog "This action needs an MFA session — sign in again with MFA"; `401` → P4.
- **Error state component** shows: a title by status, the API `message`, the `code`, the `requestId` with a copy button, and Retry. `403` shows the permission(s) the operation requires (from `operations.gen.ts`); `404` renders the not-found state (cross-tenant ids look exactly like missing ones).
- **Forms:** react-hook-form + zod (v4, the repo's version) schemas per form in the feature folder, **strict** objects mirroring the operation's request schema. A shared test helper `expectRequestMatchesContract(operationId, body)` validates form output against the request JSON schema taken from `docs/api/openapi.json` with Ajv (dev dependency) and fails on unknown keys; every form has such a test.

## 4. Alternatives considered

| Alternative                                                       | Why not                                                                                                                                                                         |
| ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Tokens in `localStorage` + direct CORS calls to the api           | XSS steals long-lived refresh tokens; forbidden by the brief                                                                                                                    |
| Server-side session store (Redis) behind an opaque cookie         | Gives the portal a data-store credential (the manifest says it holds none) and a second session system; the sealed cookie keeps the API the only session authority              |
| BFF refreshes transparently on 401                                | Parallel requests and two portal replicas would refresh the same single-use token concurrently = reuse detection = session revoked (authentication.md). One browser coordinator |
| Server components fetching tenant data                            | Needs server-side refresh (same race), RSC caches tenant data, harder CSP; the console is an authenticated SPA-like app where SSR adds little                                   |
| Trust `X-Forwarded-For` with `HTTP_TRUST_PROXY=1` from the portal | The api is reachable over 0 and 1 hops at once; XFF from a direct internal caller would be spoofable                                                                            |
| MSW in the browser for development mocks                          | Does not cover BFF/session paths; needs a service worker and CSP `worker-src`; BFF fixture mode is one switch for both                                                          |
| Hand-written API types                                            | Drift is invisible; the brief requires a client generated from or checked against the snapshot                                                                                  |
| `orval`/full code generation of hooks                             | Large generated surface, custom conventions (cursors, `items`, idempotency) still need wrappers; `openapi-typescript` + `openapi-fetch` is small and typed                      |
| Rollup tables for the new reports                                 | New writer and table for a pre-GA read; covering indexes + cache + bounded ranges follow 6.1 D12                                                                                |
| Estimating latency percentiles client-side from samples           | Unbounded transfer; histogram in SQL is exact and bounded                                                                                                                       |
| Building the full explorer/details and the policy builder now     | 7.2 and 7.3 are separate steps with their own briefs                                                                                                                            |
| Portal served under the api host (`/` → portal, `/api/v1/` → api) | Mixes cookie scope with API clients and blurs ADR-0053; a separate host keeps the api origin cookie-free                                                                        |

## 5. Risks and mitigations

| Risk                                               | Mitigation                                                                                                                                                     |
| -------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Refresh race ends sessions                         | P4 single-flight + Web Locks + "fresh enough" short-circuit in `/bff/session/refresh`; e2e test with parallel requests and two tabs at expiry                  |
| Cookie exceeds 4 KB with an override               | Size budget test; explicit refusal code                                                                                                                        |
| Forwarder token leaks → IP spoofing of rate limits | Only per-IP limits and audit IP attribution are affected (per-principal/tenant limits remain); token in a Secret file; rotation documented in the runbook      |
| CSP nonce breaks Next/Radix/Recharts               | `strict-dynamic` with nonce on Next scripts; styles `'unsafe-inline'` (attributes used by Radix/Recharts); e2e asserts no CSP violation reports in the console |
| New `email_messages` index width at 1M/day         | Redefinition adds 8 bytes per entry; measured with `db:perf` (recorded); online DDL                                                                            |
| Delivery/processing reports slow at volume         | Index-only covering indexes, `MAX_EXECUTION_TIME`, cache, `expensive` class; EXPLAIN checks; production scale not claimed                                      |
| Wave-2 packages need shared changes                | WP2 ships a complete shared kit; deviation log; WP6 consolidates                                                                                               |
| Snapshot changes break the portal build            | Intended (drift check); regenerate is one command                                                                                                              |
| Accessibility regressions                          | axe in every page test and every e2e page visit; contrast test on tokens                                                                                       |
| e2e flakiness on a laptop stack                    | Deterministic seeded data, `expect.poll` on replica visibility, retries 1 locally, traces on failure                                                           |
| Browser download during tests                      | `PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1`, global setup fails if the pinned browser is missing; explicit one-time install script                                    |

## 8. Security notes

- The portal holds no data-store credentials; its secrets are `PORTAL_SESSION_KEY` and the forwarder token.
- Tokens never reach browser JavaScript; the CSRF cookie is the only readable cookie and carries no authority on its own.
- The BFF cannot reach anything but OpenAPI operations under `/api/v1` (allow-list), never probes, metrics or docs.
- No tenant identifier is accepted from the browser for authorization; tenant switching is only the audited override.
- Message content is never rendered; previews are sanitized text; downloads are single-use grants.
- `server-only` imports, no `NEXT_PUBLIC_*` keys, bundle grep test, CSP with nonces.
