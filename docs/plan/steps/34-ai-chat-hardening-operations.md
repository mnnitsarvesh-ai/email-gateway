## 0. Scope in one paragraph

AI-6 makes the assistant operable in production and closes the program. Tenant administrators get an **AI administration page** (usage and estimated cost per user and day, effective limits, a per-user daily token budget, the data-sharing level, an optional **tenant-supplied provider key**, user feedback) and users with `audit:read` get a **metadata-only conversation audit view** (turns, tool calls, confirmations, reports, ratings; never message text, per Q9). Users can rate assistant answers (**`ai_chat_feedback`**) and **search the text of their own conversations**. A new data-sharing level **`pseudonymized`** replaces e-mail addresses, IP addresses, domains and person names in everything the model reads by stable per-conversation tokens and maps them back in the answer the user sees. Security reports for windows longer than seven days are generated **asynchronously**: the turn queues a job through the outbox and RabbitMQ, and the `api-assistant` consumer composes the same report through the same loopback reads with a short-lived, GET-only **job token of the user's live session**, reusing AI-R's renderer, object storage and email delivery. The provider layer gains a **secondary provider with Redis-backed health and circuit breaking**, still under the tenant budget. Operations get an **`api-assistant` Deployment** (same api image, own HPA, PDB, LLM-only egress NetworkPolicy, ingress and BFF route split of `/api/v1/assistant/*` with SSE settings), Prometheus **metrics and alerts**, **runbooks**, and a **load test** with the fake provider run side by side with the SMTP benchmark. The program closes with the brief's **§16 final capability report** in `docs/assistant/`.

## 2. Decisions

### 2.0 Invariants added to I1–I23

- **I24 Administrators see metadata, never conversation content (Q9 kept).** The audit view and the admin pages read ids, timestamps, statuses, tool names, operation ids, decisions, risks, HTTP statuses, error codes, redacted parameters (as already audited), token counts and costs. Conversation titles, message text, provider transcripts, result cards and report HTML are never returned to anyone but the owner. The only user-written text an administrator sees is a feedback comment the user explicitly submitted with a visible notice.
- **I25 Pseudonymized means the model never receives the value.** At `pseudonymized`, every e-mail address, IP address, domain and person name detected by the rules of D3 is replaced by a token before any text reaches the provider (system context, user message, action updates, recap, tool envelopes); the mapping lives only in MySQL under the conversation's content retention and in memory during a turn. The rendered answer, cards, audit and executed requests carry real values.
- **I26 Background work acts only as the user's live session, read-only, for one report.** An async report job reads through the loopback with an access token minted for the requesting user's own session family, valid 5 minutes, accepted by the api only for `GET` on the fixed report source routes; a revoked or expired session, a lost permission, a disabled assistant or an expired job ends it. No credential is stored or published.
- **I27 A tenant key is write-only.** It is encrypted at rest with a dedicated key and row-bound AAD, decrypted only in api memory to call the provider, and never returned, logged, audited, sent to the model, put in an event, a card or an example. Its validation and all tests use local fakes only.

### D1. Tenant AI administration page (portal `/assistant/admin`, api WP3 + WP4)

- **Usage and cost per user and day:** new table `ai_chat_usage_user_daily` (§3) upserted in the turn's finish transaction next to `ai_chat_usage_daily` (same semantics: one row per organization, UTC day, user, provider, model and key source; turns, input/output/cache tokens, `cost_micros`), backfilled from `ai_chat_turns` by the migration. Route `GET /assistant/admin/usage/users?from&to&userId?` (`assistant:configure`, window ≤ 92 days, cursor v1) returns per user and day: user (public id, display name, email), turns, tokens by kind, total tokens, estimated cost (micro-USD, `null` when no price is known), key source; plus totals per user and for the window. Cost is labelled "estimated" everywhere (prices in `prices.ts` + `ASSISTANT_MODEL_PRICES`).
- **Limits:** `GET /assistant/settings` gains `effectiveLimits` (read-only: turns per user per minute, message length, tool rounds and calls per turn, turn deadline, platform daily token cap set yes/no, tenant budget max, reports per user per day, report emails per user/tenant per day, confirmation TTL, retention bounds) and the editable **`userDailyTokenBudget`** (null = none; 1 … the tenant's effective daily budget). It is enforced at turn start like the tenant budget (`429 assistant_budget_exhausted`, `details.scope: 'user'`) with Redis `as:tok:u:<userPublicId>:<yyyymmdd>` (TTL 48 h, seeded from `ai_chat_usage_user_daily` on miss).
- **Data sharing** select (`metadata` | `pseudonymized`, D3) and the **tenant key** section (D7) are part of the same settings document.
- **Feedback** tab (D2) and **Conversation audit** tab (D4).
- Portal page `app/(console)/assistant/admin/page.tsx` → `features/assistant-admin/*`, navigation item "AI administration" (Administration section) shown when the user can call `AssistantAdminController_usageByUser_v1` **or** `AssistantAdminAuditController_conversations_v1`; tabs are gated individually by operation id. The existing Settings → AI assistant tab keeps enable/acknowledge/retention and links to the admin page.

### D2. Feedback on assistant answers (`ai_chat_feedback`, WP4 routes, WP3 view and purge)

- One row per assistant message (`message_id` unique): `rating` `up|down`, `reason` (optional enum `incorrect`, `incomplete`, `not_helpful`, `wrong_action`, `unsafe`, `too_slow`, `other`), `comment` (optional, ≤ 500 characters, sanitized like user text, **content**: set to NULL at the conversation's content purge).
- `PUT /assistant/messages/{messageId}/feedback` (`assistant:use`, owner only: the message must belong to a conversation of the caller's owner scope, role `assistant`, its turn `completed`; else `404 assistant_message_not_found` / `409 assistant_feedback_not_allowed`; the same `409` when the conversation's content was purged, checked under a `FOR SHARE` lock of the conversation row that the content purge locks `FOR UPDATE`, so a comment never outlives a purge, I24), upsert, `200` with the feedback view; `DELETE` → `204`. Audited `assistant.feedback_recorded` / `assistant.feedback_removed` with `{ messageId, conversationId, rating, reason }` (never the comment). Metric `assistant_feedback_total{rating}`.
- `GET /assistant/conversations/{id}/messages` returns `feedback: { rating, reason, comment } | null` on assistant messages (owner view).
- Admin list `GET /assistant/admin/feedback?from&to&rating?&reason?&userId?` (`assistant:configure`, ≤ 92 days, cursor v1): rating, reason, comment, user, created/updated, conversation and message public ids, the turn's provider, model, prompt version, data-sharing level and the names of the tools the turn called (from executions). The portal form says "Your rating and comment are visible to your organization's AI administrators."

### D3. `pseudonymized` data-sharing level (package `pseudonym/*`, api turn engine)

**Entity rules (pure, `packages/assistant/src/pseudonym/detect.ts`):**

| Kind     | Token        | Detected                                                                                                                                                    |
| -------- | ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `email`  | `[EMAIL_n]`  | Any string matching a strict address pattern (local@domain with a dotted domain), anywhere (structured fields, `untrusted_text`, free text, URLs' userinfo) |
| `ip`     | `[IP_n]`     | IPv4 dotted quads with valid octets and IPv6 literals accepted by `net.isIP`, anywhere                                                                      |
| `domain` | `[DOMAIN_n]` | (a) values of keys matching `/(^                                                                                                                            | _)(domain | domainName | hostname | host      | senderDomain | recipientDomain | fromDomain | rcptDomain | helo     | ptr)$/i`; (b) the `name`field of rows of tools in module`domains`; (c) the host of `http(s)://` URLs; (d) bare hostnames in free text (user messages, untrusted text) whose last label is a 2-letter ccTLD or in a fixed gTLD list (`com net org io gov edu mil int info biz co app dev cloud ai online site tech xyz email`). The domain part of an address is covered by its `[EMAIL_n]`. Public ids (UUIDs) and numbers are never tokens |
| `name`   | `[PERSON_n]` | Values of keys `displayName`, `fullName`, `firstName`, `lastName` and `/(from                                                                               | sender    | recipient  | user     | custodian | owner        | requester       | approver   | actor      | reviewer | assignee)Name$/i`; the user display name of the context block. Free-text names are **not** detected (limitation, A6-3)                                                                                                                                                                                                                                                                                                                      |

- **Tokens** are `[KIND_n]`, `n` per kind and conversation starting at 1, stable for the conversation's content lifetime (same normalized value → same token: e-mail lower-cased domain, IPs canonical, domains lower-case without trailing dot, names whitespace-collapsed). **Neutralization first:** any substring of inbound text that already matches the token grammar `\[(EMAIL|IP|DOMAIN|PERSON)_[0-9]{1,6}\]` is rewritten to `(KIND_n)` before tokenization, so neither a user nor a mail-derived string can forge a token.
- **Outbound to the model** (`Pseudonymizer.apply`): the context block (organization name → "Your organization"; user display name → `[PERSON_n]`), the user message, action updates, recap text, and every string of every tool envelope (`data`, `untrusted_text`, error messages); keys are never changed. Applied at serialization of the envelope in the turn engine, after the minimizer (so caps and credential-key drops apply first).
- **Inbound from the model:** (1) tool-call arguments: every string at any depth has known tokens (bracketed, or bare `KIND_n` matching a known token exactly at word boundaries) replaced by the real value **before** refs, bindings and Ajv validation; a bracketed token that is unknown in this conversation → `denied_schema`, message "Unknown placeholder [EMAIL_99]; use a value from this conversation." (code `assistant_unknown_placeholder`); (2) streamed text: a `TextDemapper` with a hold-back buffer (the longest possible token, 16 characters) replaces tokens in `text.delta` events before they reach the browser; the stored assistant message is the de-mapped text; `provider_transcript` keeps the tokens (what the model saw).
- **Storage** `ai_chat_pseudonyms` (§3): token, kind, value (content), SHA-256 of the normalized value; rows deleted at the conversation's content purge and on conversation delete (the transcripts that use them are purged at the same time), with the organization purge. New mappings of a turn are inserted in the turn's finish transaction (all turn outcomes); the turn lock (one turn per conversation) makes numbering race-free. Cap `ASSISTANT_PSEUDONYMS_MAX_PER_CONVERSATION` (5 000): beyond it new values become the irreversible `[KIND_REDACTED]` (metric `assistant_pseudonyms_total{kind="overflow"}`).
- **Recorded per turn:** `ai_chat_turns.data_sharing`. The level is read from the settings at turn start; changing it applies from the next turn. A switch between levels inside one segment is allowed (the transcript stays append-only; older turns keep what they showed the model).
- **Unchanged by the level:** cards, confirmation summaries, report HTML and figures (server-built), audit rows and executed requests (real values), `describe_tool` output and the catalogue.
- **Fake provider:** directive mode receives the tokens and calls tools with them (end-to-end proof of the inbound mapping).

### D4. Conversation audit view (`audit:read`, WP4) and content search (WP4)

- **Audit view (metadata only, I24):**
  - `GET /assistant/admin/conversations?userId?&from?&to?&status?` (`audit:read`, cursor v1, newest `last_turn_at` first; organization from the scope, override conversations of the organization included and flagged): conversation public id, user (public id, display name, email), status, created, last turn, turn count, segment count, content purged yes/no, under platform override yes/no, totals (tokens, cost, tool calls, denied calls, confirmations by status, reports, feedback up/down). **No title.**
  - `GET /assistant/admin/conversations/{conversationId}` (`audit:read`): the same header plus `turns[]` (seq, status, provider, model, response model, key source, data sharing, fallback-from, prompt version, registry version, rounds, tool calls, tokens, cost, latency, error code, started/finished), `executions[]` (seq, turn seq, tool, operation id, method, access, risk, decision, status, HTTP status, error code, `params_redacted` exactly as stored, resource ref, latency, correlation id, created), `confirmations[]` (public id, operation id, risk, requires re-auth, status, created, expires, decided, result HTTP status, result error code), `reports[]` (public id, status, period, sections included/omitted, size, async yes/no, job status, deliveries: recipient kind, recipient domain only, status, error code, times), `feedback[]` (message public id, rating, reason; no comment). Audited `assistant.audit_viewed` (resource `assistant_conversation`).
  - `GET /assistant/admin/executions?from&to&userId?&tool?&module?&decision?&status?&risk?&access?&correlationId?&conversationId?` (`audit:read`, ≤ 92 days, cursor v1): the execution rows above with user and conversation public ids — the "audit view search". No content search across users (A6-2).
- **Content search for the owner:** `GET /assistant/search?q&cursor&limit` (`assistant:use`, rate class `expensive`, `q` 2–200 characters after trimming): searches `ai_chat_messages.content` (user and assistant text) and conversation titles of the caller's **own** non-deleted conversations (owner scope incl. override id, as `GET /assistant/conversations`), case- and accent-insensitive (`utf8mb4_0900_ai_ci` collation) with an escaped `LIKE '%q%'`, newest first, over at most `ASSISTANT_SEARCH_SCAN_MAX_MESSAGES` (20 000) most recent messages, on the replica with `MAX_EXECUTION_TIME(ASSISTANT_SEARCH_TIMEOUT_MS)` (`503 assistant_search_timeout`). Result rows: conversation public id and title, message public id, role, seq, created, and a server-cut **snippet** (≤ 160 characters around the first match, sanitized). Purged content is not found. No email body or attachment is involved: messages hold only user and assistant text (I5). FULLTEXT was rejected (§5).

### D5. Asynchronous security reports (ADR-0096; outbox → RabbitMQ → `api-assistant` consumer)

- **When:** `report_generate` resolves the window as today; when `ASSISTANT_REPORT_JOBS_ENABLED` and the window is longer than `ASSISTANT_REPORT_SYNC_MAX_HOURS` (168 h), the report becomes a job; otherwise it runs synchronously exactly as in AI-R. The tool's input schema is unchanged (the server decides; A6-5). The daily generation limit counts queued reports (every status counts, as today).
- **Queue (in the turn, one writer transaction, after the D5 executor steps 1–6 and AI-R D2 steps 1–4):** insert `ai_chat_reports` with status **`queued`** (new enum value; title, period, sections requested; no object), insert `ai_chat_report_jobs` (§3: report, conversation, execution, owner, the principal's **session id** (`sid`), auth methods (`pwd` / `pwd,otp`), home organization public id, override id, the validated arguments, the organization label the turn uses, `expires_at = now + ASSISTANT_REPORT_JOB_TTL_SECONDS` (1 800), status `queued`, correlation id), the outbox row `assistant.report.generate_requested.v1` (eventId = job public id, aggregate `assistant_report_job`), the execution row (`allowed`, `succeeded`, HTTP **202**) with the card and audit `assistant.tool_executed` + `assistant.report_job_queued`. Card kind `report` with `report.status: 'queued'` and no figures; envelope `status: 'ok'`, `httpStatus: 202`, `data: { ref, reportId, status: 'queued', title, period, sections }`, note "The report is being generated in the background and appears in the chat when it is ready. Do not state any figures for it."
- **Event** `assistant.report.generate_requested.v1`, payload strict `{ jobId: uuid, reportId: uuid, requestedAt }` (ids only), exchange `email.policy`, routing by the registry convention.
- **Topology v16:** queue **`assistant.reports`** (role `work`, home exchange `email.policy`, bindings: the event + its retry binding; consumer `{ kind: 'ledger', ledgerName: 'api-assistant.reports', service: 'api-assistant' }`; retry `hold`, `maxAttempts 5`, base 10 s, max 60 s, `maxRetryAgeMs 30 min`; policy `work`; not in `RECONCILE_QUEUES`: the api's sweep fails jobs past `expires_at`). Role user **`eg-assistant`** (`RABBITMQ_ASSISTANT_USER/PASSWORD/URL`): configure `^$`, read `^assistant\.reports$`, write `^email\.(policy|events)$`, topics `email.policy` `^retry\.assistant\.reports\.`, `email.events` `^dead-letter\.assistant\.reports(\.|$)`. The `ops` user's `email.policy` topic grant gains `assistant\.reports` in its retry alternation (dead-letter replay).
- **Consumer** (`ReportJobConsumer` in the assistant module; started only when `ASSISTANT_REPORT_JOBS_CONSUMER=true` — `api-assistant` pods and host-run development — with `RABBITMQ_ASSISTANT_URL`; prefetch `ASSISTANT_REPORT_JOB_CONCURRENCY` (2)), per message, idempotent through the ledger and row CAS:
  1. Load the job by public id with its report (writer, organization of the envelope). Missing → ack (purged). Terminal → ack. `expires_at` passed → job `failed`/report `failed` `assistant_report_job_expired`, ack.
  2. CAS `queued` (or `running` with `lease_until` in the past) → `running`, `attempts + 1`, `lease_until = now + 60 s`, renewed every 20 s while the attempt runs (the claim's `started_at` is its ownership token; a renewal that finds the job taken over aborts the attempt, which then changes nothing). Lost CAS while another consumer holds a live lease → `ReportJobBusyError`, classified **transient** by the consumer (no attempt spent, bounded by the 30-minute retry age), so a redelivery after a pod crash or OOM claims the job once the dead holder's lease lapsed; lost CAS otherwise → ack. A claim past `attempts = 5` (crash loop) fails the job `assistant_report_job_failed`. Any unexpected error after the claim (principal resolution, availability, composition, finalize) releases the claim (`queued`, `error_code = assistant_report_job_failed`) and is rethrown for the queue's retry hop; at the last attempt or past `expires_at` it fails the job with that code instead (review fix, §12.1).
  3. **Mint the job token:** `TokenService.issueAssistantJobAccess({ userPublicId, organizationPublicId: home org, sessionId, amr, overrideId?, jobId })` → an ordinary access JWT plus claim **`ajb: <jobPublicId>`**, `exp = now + 300 s` (never stored, never logged, never leaves the api process except as the `authorization` header of the loopback call to `ASSISTANT_LOOPBACK_URL`). Resolve the principal with the same code path the guard uses (`AccessTokenPrincipalResolver`, extracted from `AuthGuard.fromAccessToken`): `null` (session revoked or expired, user disabled, override ended) → `failed` `assistant_report_session_ended`.
  4. **Re-check authority now:** assistant availability for the scope (platform switch, feature, tenant setting), `assistant:use` and the tool requirement `report:read` via `satisfiesRequirement` → else `failed` `assistant_report_not_allowed`.
  5. Run the AI-R composition (`ReportGeneratorService`, refactored to share one `buildAndStore` path between the sync and async callers): the fixed source plan, permission pre-check per source, loopback GETs with `authorization: Bearer <job token>`, correlation `<job correlation>.<n>`, `x-eg-assistant-execution` = the original execution id, no client IP (none is forwarded); zod parse, model, render, `PutObject`, then one transaction: report `queued|running → available` (object key, size, SHA-256, figures, sections), job `succeeded`, audit `assistant.report_generated` (actor = the user, metadata as AI-R + `{ async: true, jobId }`). Source failures are handled as in AI-R (omitted sections); "no data" (`503 assistant_report_sources_unavailable`) or a storage failure → throw a retryable error while `attempts < 5` and before `expires_at` (queue retry), else `failed` with the code.
- **AuthGuard rule for `ajb` tokens (I26):** a verified access token with `ajb` is accepted only when the request method is `GET` and the matched route path is in `ASSISTANT_JOB_ROUTES` = the path templates of the report source tools (`/api/v1/reports/{traffic,threats,url-clicks,delivery,processing,top-domains}`, `/api/v1/quarantine/summary`, `/api/v1/ato/overview`, `/api/v1/ato/accounts`), derived from the package's `REPORT_SOURCES` and registry (single source); anything else → `401 unauthorized` (metric `api_assistant_job_token_refusals_total`, warn log with the route template and job id only). The principal carries `assistantJobId` (informational). Rate limits, permissions, tenant scope and override checks run unchanged.
- **Retention and sweeps:** the conversation content purge cancels its `queued`/`running` jobs (`cancelled`, report `purged`); the retention job fails jobs past `expires_at` (`assistant_report_job_expired`) and their reports; the AI-R `pending` sweep ignores `queued`. Organization purge deletes jobs before reports.
- **The chat sees the result:** the report card polls `GET /assistant/reports/{reportId}` (view gains `job: { status, attempts, errorCode, expiresAt } | null` and status `queued`), every 5 s while `queued`/`running`, stopping at a terminal state or `expiresAt`. The next turn's **action updates** (`updates.ts`) tell the model "report_generate (call r<n>): the background report is ready" / "… failed (<code>)", marked reported through `ai_chat_report_jobs.reported_at` like confirmations. `report_send_email` on a report that is not `available` → proposal `409 assistant_report_not_ready`. ### D6. Provider fallback and health (ADR-0097; package helpers, api `ProviderRouterService`)

- **Candidates per turn** (ordered): tenant key (when configured, valid and `useTenantKey`; D7) → else platform **primary** (`ASSISTANT_PROVIDER`/`ASSISTANT_MODEL`) → platform **secondary** (`ASSISTANT_FALLBACK_PROVIDER`/`ASSISTANT_FALLBACK_MODEL`, `none` by default). With a tenant key, the platform candidates follow only when the tenant enabled `tenantKeyFallbackToPlatform` (A6-6).
- **Health:** one Redis breaker per candidate (`as:brk:<provider>` for platform candidates as today — keyed by provider id plus `:fb` for the secondary, so both can be the same provider family with different models; `as:brk:t:<organizationPublicId>` for a tenant key, so a tenant's bad key never opens the platform breaker). Selection at turn start = first candidate whose breaker is closed; none → `503 assistant_provider_unavailable`. A breaker re-closes when its window expires (passive half-open: the next turn tries the primary again). Gauges `assistant_provider_breaker_open{provider,role}` are refreshed at turn start and by `GET /assistant/status`.
- **Same-turn switch:** when the first model call of a turn fails with a breaker-qualifying error (`connection`, `timeout`, `rate_limited`, `server_error`) **before any text delta was streamed and before any tool ran**, the router records the failure and retries the round on the next healthy candidate (at most one switch per turn). Later failures fail the turn as today (the user's retry starts on the healthy candidate). A tenant key answered with `401/403` marks the key `invalid` (`last_error_code`), audits `assistant.provider_key_invalidated`, and continues with the platform only when the tenant allowed it, else the turn fails `503 assistant_tenant_key_invalid`.
- **Segment binding:** provider-native transcripts cannot cross providers or models (preserved thinking). The turn records the provider and model actually used; when the selected provider/model differs from the current segment's last turn, `planWindow` is called with `forceNewSegment: true` and starts a new segment from the existing deterministic recap (no model call). A same-turn switch rebuilds the context the same way.
- **Budgets:** tenant daily budget and the new per-user budget count every turn regardless of candidate; the platform daily cap counts only `key_source = platform` turns (A6-7). Usage rows and turns record `key_source`.
- **Recorded:** `ai_chat_turns.provider/model` (used), `key_source`, `fallback_from` (provider id of the skipped or failed primary). Status `GET /assistant/status` gains `keySource`, `fallbackActive`, `dataSharing`.
- **Metrics:** `assistant_llm_requests_total{provider,role,outcome}` (`role` = `primary|fallback|tenant`), `assistant_llm_seconds{provider,role}` (one model call), `assistant_provider_switches_total{from,to,reason}`, `assistant_provider_fallback_active` (gauge, 1 when this process's last turn start selected a platform secondary because the primary was unhealthy), `assistant_provider_breaker_open{provider,role}`. Labels never carry organization or user ids.

## 5. Alternatives considered

| Decision                                                    | Alternatives                                                                                                                                                                                      | Why not                                                                                                                                                                                                                                                                                                                                                                     |
| ----------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Per-user daily usage table (D1)                             | Aggregate `ai_chat_turns` on every page view                                                                                                                                                      | 92-day scans over turns per request; turns are hard-deleted at 400 days while usage should stay comparable; one upsert per turn is cheap                                                                                                                                                                                                                                    |
| Metadata-only audit view (D4, I24)                          | Let `audit:read` read message text                                                                                                                                                                | Contradicts accepted Q9 and ADR-0094; administrators keep the full tool-execution trail, which is what the brief's audit requirements list                                                                                                                                                                                                                                  |
| `LIKE` scan bounded to the owner's recent messages (D4)     | InnoDB FULLTEXT (ngram) on `ai_chat_messages.content`; OpenSearch                                                                                                                                 | FULLTEXT cannot be scoped to an owner (the index matches across all tenants before the owner filter), the ngram parser cannot be expressed in the Prisma schema (drift for `migrate dev`); OpenSearch would add a second copy of conversation text with its own retention. The owner's own messages are bounded (≤ 500 conversations) and the scan is capped and time-boxed |
| Key-based + pattern pseudonymization in the api (D3)        | An NER model; pseudonymizing in the provider adapter; per-tool manifest field lists                                                                                                               | A model is a new dependency and non-deterministic; the adapter sees provider-native shapes only; per-tool lists for 356 tools would drift — the generic rules plus module rules are testable with fixtures and property tests                                                                                                                                               |
| Plain mapping values under content retention (D3)           | Encrypt the mapping                                                                                                                                                                               | The same values are already stored in plain in cards and messages under the same retention; encryption would add a key without changing the exposure                                                                                                                                                                                                                        |
| Job token of the live session (D5, ADR-0096)                | (a) Keep reports synchronous with longer timeouts; (b) a service principal per tenant; (c) store the user's bearer/refresh token in the job; (d) let the consumer call report services in-process | (a) the brief asks for async through the outbox and RabbitMQ and long windows block the turn; (b) a standing credential that outlives sessions breaks I2 and needs its own RBAC; (c) stores a credential (I2, I27 spirit); (d) parallel business logic, skips guards (I1)                                                                                                   |
| Consumer in the api process (`api-assistant`) (D5)          | notification-worker or a new worker app                                                                                                                                                           | Only the api may depend on `@email-gateway/assistant` (dependency boundary) and only the api pipeline can serve the loopback reads; a new deployable is the same image anyway                                                                                                                                                                                               |
| Same-turn switch only before output, segment rebinding (D6) | Translate transcripts between providers; switch at any round                                                                                                                                      | Preserved thinking forbids editing or translating native history; a switch after tools ran could repeat side-effect-free reads but would confuse the model's context; the recap is deterministic and already tested                                                                                                                                                         |
| Dedicated tenant-key encryption key (D7)                    | `DATA_ENCRYPTION_KEY` via `SecretBox`                                                                                                                                                             | Same pattern as webhook and provider credentials (ADR-0077): key separation limits blast radius and allows rotation without touching MFA secrets                                                                                                                                                                                                                            |
| Tenant keys for Anthropic/OpenAI only (D7)                  | Also Azure OpenAI with tenant endpoints                                                                                                                                                           | A tenant endpoint is an arbitrary host the egress policy cannot allow in advance (SSRF-like egress); platform Azure stays available                                                                                                                                                                                                                                         |
| Loopback from api-assistant to the api Service (D10)        | Loopback to itself (127.0.0.1)                                                                                                                                                                    | Self-loopback needs every backend route of the api (DNS resolvers, OpenSearch, SMTP relay, provider endpoints) in the LLM pods' egress policy; going to the api Service keeps the LLM pods' egress small and puts tool load where the api's HPA already scales                                                                                                              |
| Opt-in load test in the api integration harness (D11)       | k6/Artillery against a container stack                                                                                                                                                            | The containerized api runs `NODE_ENV=production` (fake refused); the harness gives the real pipeline with the fake provider and direct row/counter assertions; no new tool                                                                                                                                                                                                  |
| Generated capability report (D12)                           | Hand-written report                                                                                                                                                                               | Numbers and lists come from the same registry that enforces completeness, and `--check` keeps them current                                                                                                                                                                                                                                                                  |

## 11. Deviations log

### WP1

1. **Migration folder** `20261125195835_ai_assistant_hardening` (UTC timestamp of `migrate dev --create-only`; it sorts after AI-R's `20261123074003_ai_assistant_reports`; migration 42). 183 tables (184 base tables with `_prisma_migrations`), 41 partitioned.
2. **Backfill day = UTC day of `finished_at`, not `started_at`.** `UsageRepository.add` is called by `TurnEngineService.finish` with `day: f.finishedAt`, so the backfill groups by `DATE(finished_at)` to equal what the upsert would have written. It counts turns closed by `finish` (`completed`, `failed`, `cancelled` with `finished_at`) and excludes turns the sweeper abandoned (`failed` + `assistant_turn_abandoned`: `abandonTurn` never calls the usage upsert). Verified: 42 backfilled turns = 42 counted turns = `SUM(turns)` of `ai_chat_usage_daily` on the main schema; synthetic edge cases on `email_gateway_verify`.

4. **Admin list index hint (for WP4).** With 1 000 conversations per organization the optimizer prefers the owner index `(organization_id, user_id, status, last_turn_at, id)` plus a filesort (11.3 ms) over the new `(organization_id, last_turn_at, id)` (1.8 ms, no filesort): the admin repository must name it with `FORCE INDEX`. Likewise the window-only execution search should name `ai_chat_tool_executions_organization_id_created_at_idx` (the optimizer picks a skip scan + filesort). Details in `docs/database/indexing.md` (step AI-6 section).
5. **Configuration.** `ASSISTANT_TENANT_KEY_PROVIDERS` / `_MODELS` parse to frozen, de-duplicated arrays (1–32 entries); `_PREVIOUS` must differ from the current encryption key; the fallback provider's credentials are required while the assistant is enabled (as the primary's; Azure uses the `ASSISTANT_AZURE_OPENAI_*` keys); `ARCHIVE_EXPORT_TTL_HOURS` and `RABBITMQ_ASSISTANT_URL` live in `assistantConfigShape`. - **Stored value = the value as first seen (all kinds, trimmed)**; the normalization (D3) is used for the comparison and `valueSha256` only. So a later `Example.COM` maps to the token of an earlier `example.com` and de-maps to `example.com`. A value longer than 320 characters (the column) becomes `[KIND_REDACTED]` without counting toward `overflowCount()`; over-cap values count.
- **Detection order** in free text: neutralize, e-mail addresses (found around each `@` within the RFC 64/253 limits, linear on long text), IPv6 then IPv4, `http(s)://` URL hosts, bare hostnames. Envelope strings: the same without bare hostnames; `{ untrusted_text }` values and domain-key values that are not one hostname/IP get the full free-text rules. A domain-key value `*.x.example` keeps the `*.`; a name-key value that is one address becomes an `[EMAIL_n]` token. Module rule (b) applies to the key `name` anywhere in an envelope whose `module` (comma list) contains `domains`. The domain-key regex is D3's table pattern reconstructed: `/(^|_)(domain|domainName|hostname|host|senderDomain|recipientDomain|fromDomain|rcptDomain|helo|ptr)$/i`.
- **Arguments**: `demapArguments` also refuses `[KIND_REDACTED]` (returned as the unknown `token`); bracketed and bare tokens are replaced in one pass (inserted values are never rescanned); object keys are never changed. `demapText`/`TextDemapper` replace bracketed tokens only (bare `KIND_n` in the answer stay as written).
- **`ActionUpdate`** keeps its AI-2 shape (now with optional `kind?: 'confirmation'`, alias `ConfirmationActionUpdate`); the report-job line is the new `ReportJobActionUpdate` `{ kind: 'report_job', ref: 'r<n>', outcome: 'ready' | 'failed', code? }`; `buildActionUpdates`/`actionUpdateLine` accept `AnyActionUpdate = ActionUpdate | ReportJobActionUpdate`. Lines: `- report_generate (call r5): the background report is ready.` / `- report_generate (call r7): the background report failed (<code>).` (existing lines byte-identical).
- **Report card `status` is optional in `ReportCardData`** (`REPORT_CARD_STATUSES`, `ReportCardStatus`): the builders always set it (`reportCard` defaults to `available`), but cards stored before AI-6 have none (= `available`), so the api's stored-card zod schema should accept it as optional. `ReportCardInput` = `ReportCardData`. `reportQueuedCard`/`reportQueuedEnvelope` take `{ executionId, refSeq, report: { reportId, title, period, sections } }`; the queued card has `generatedAt: ''`, `sizeBytes: 0`, no figures and the same "Open full size" link and refs as `reportCard`. The synchronous envelope is unchanged (no `status` key).
- **`reportJobRoutePaths()`** lives in `reports/sources.ts`; registry `pathTemplate`s already include `/api/v1`, so it returns the 9 full templates (`/api/v1/ato/accounts`, `/api/v1/ato/overview`, `/api/v1/quarantine/summary`, `/api/v1/reports/{delivery,processing,threats,top-domains,traffic,url-clicks}`), frozen, sorted by code unit.
- **Probe**: Anthropic uses `client.models.retrieve(model, null, { signal, timeout, maxRetries: 0 })` (present in SDK 1.1.0 `resources/models.d.ts`); the SDK sends the key as `authorization: Bearer` with an injected fetch. - **`reasonOfStatus`** maps 401/403 → `auth` for every provider (a platform key answered 401 now also reads `auth`, not `client_error`; the api's `assistant_llm_errors_total{reason}` gains the label value `auth`).
- **Routing**: `PROVIDER_ROLES`, `TENANT_KEY_PROVIDERS` (`anthropic`, `openai`) and `ProviderCommonOptions` are exported; `createProviderFromSpec` refuses a `tenant` spec for Azure/fake or without `organizationPublicId`; `breakerKeyFor` validates its parts (`[A-Za-z0-9_-]{1,64}`).

### 12.2 Review fixes (2026-11-26)

Both review findings were confirmed against the code and fixed.

1. **High: a report job that failed after its claim stayed `running` until it expired.** Only `ReportJobRetryError` put the job back to `queued`. Any other error after the claim kept the 5-minute lease: the principal resolution, the availability check, a composition that did not end in `failed`, or the finalize transaction. A pod crash or OOM did the same. Every retry hop (10–60 s) or redelivery came back inside that lease and was acked as a duplicate, so the job failed only at the 30-minute expiry sweep. Fix (`report-job.processor.ts`, `report-jobs.repository.ts`, `report-job.consumer.ts`, `assistant.constants.ts`):
   - Steps 3–5 run in a `try`. On an unexpected error the processor releases the claim: `requeue(…, 'assistant_report_job_failed', claimedAt)` moves it to `queued` with the lease cleared, and the error is rethrown for the queue's retry hop. At the fifth attempt, or past `expires_at`, the job and its report fail with the new code `assistant_report_job_failed` instead. A failed finalize also deletes the stored object.
   - The lease is now 60 s and is renewed every 20 s while the attempt runs (`renewLease`). The claim's `started_at` is its ownership token. A renewal that finds the job taken over aborts the composition, and the attempt then changes nothing.
   - A claim lost to a live lease now throws `ReportJobBusyError` (`leaseHeld`), which `classifyReportJobFailure` marks transient: no attempt is spent, and the retry age bounds it. A redelivery after a crash therefore claims the job once the dead holder's lease lapses, usually within a minute. A claim past five attempts (a crash loop) fails the job.
   - The composition budget keeps its 290 s (`REPORT_JOB_COMPOSE_BUDGET_MS`).
   - Tests: 5 new unit cases in `report-jobs.test.ts`, the live-lease case changed from an ack to a transient retry, and a MySQL integration case in `assistant-report-jobs.test.ts`.
2. **Medium: a feedback comment could be written after the conversation's content was purged, and then was never purged.** `ratable()` did not read `content_purged_at`, and the retention job never selects a conversation twice. Fix: `PUT …/feedback` reads `content_purged_at` under `SELECT … FOR SHARE` on the conversation row (`FeedbackRepository.lockContentPurged`). The content purge locks the same row `FOR UPDATE` first, so a rating either sees the purge or the purge waits for it and clears its comment. A purged conversation answers `409 assistant_feedback_not_allowed` ("Answers of a conversation whose content was purged cannot be rated"). `DELETE` is unchanged. OpenAPI 409 description and portal client regenerated. Tests: a unit case, an e2e case, and `assistant-admin.test.ts` (a PUT after the purge gets 409 and the row is unchanged).

Also fixed: `apps/admin-portal/src/test/scripts/generate-api.test.ts` timed out at 120 s in the full `pnpm test` twice (and once with the portal suite alone). The check takes 62 s alone (`api:check` 31 s) against the 9.6 MB snapshot, so the budget is now 300 s.
