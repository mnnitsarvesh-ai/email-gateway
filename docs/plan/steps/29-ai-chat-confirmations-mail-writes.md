## 0. Scope in one paragraph

From AI-2 the model may propose writes. A write `call_tool` never executes inside a turn: the executor validates it exactly as in AI-1 (D5 steps 1–6), resolves the concrete request, reads the target's current state through the matching read operation (loopback, the user's own token), validates policy definitions through `POST /policies/validate`, builds a server-authored impact summary, and stores an `ai_chat_action_confirmations` row bound by `action_digest` (SHA-256 of the canonical request + preconditions + identity) to a random single-use token whose hash only is stored. The token goes to the browser in a `confirmation.required` stream event; the model gets `pending_confirmation` and nothing it could use. The user confirms in a confirmation card (`POST /assistant/confirmations/{id}/confirm` with the token, the digest the card showed and, for `high` risk, a fresh password + TOTP unless the session re-authenticated in the last 5 minutes). The server re-checks owner, session family, status, expiry, token, digest, availability and re-auth, takes the transition `pending → executing` atomically, re-reads the target (changed state → refused), executes the stored request through the loopback with `Idempotency-Key = confirmation id` and the precondition `rowVersion`, records an execution and audit rows, and tells the model the outcome at the start of its next turn. 35 operations become tools: 31 writes (policies 11, quarantine 13, messages 2, recipient suppressions 2, saved views 3) and 4 side-effect-free policy `POST`s.

## 2. Decisions

### 2.0 Invariants added to I1–I8

- **I9 No write without the user.** A write executes only inside `POST /assistant/confirmations/{id}/confirm`, a live request of the same user and session family, carrying a token the model never saw. Nothing the model emits can reach the confirm or cancel routes (assistant routes are `not_applicable` tools).
- **I10 What the user confirms is what runs.** The card is rendered from the stored, server-authored summary of the stored request; the confirm carries the digest the card showed; the server executes the stored request (never re-derives it from model output) and refuses when the target changed since the card was built.
- **I11 Existing controls stay the authority.** The confirmed request passes the api's own pipeline (guards, RBAC, MFA, tenant scope, rate limits, idempotency, validation, CAS, approvals with separation of duties, audit). The confirmation adds controls, it never replaces one.

### 2.1 ADR-0093 amendment (written by WP1)

ADR-0093 keeps its decision; the amendment records what AI-2 adds or makes precise: (a) the confirm body carries `actionDigest` (the card's digest) besides the token; (b) the preconditions include a **state digest** of selected fields of the target read; confirm re-reads the target and refuses `409 assistant_confirmation_state_changed` on any difference, even where the route's own CAS is optional; (c) policy definitions are validated through `POST /policies/validate` before a proposal is stored; (d) the re-authentication window is a Redis marker per session family used only by assistant confirmations; (e) a confirmation stuck in `executing` (crash) is failed by the sweeper with `assistant_confirmation_outcome_unknown` (never re-executed); (f) the token lives only in the browser tab's memory (lost on reload; the card then offers cancel only); (g) outcomes reach the model as a server-authored "action updates" block at the start of its next turn; (h) at most `ASSISTANT_MAX_PENDING_CONFIRMATIONS` (5) pending confirmations per conversation; (i) five wrong tokens cancel the confirmation. Status line: "Proposed (2026-11-20, step AI-1 fixed the contract); amended and built in step AI-2 (2026-11-21)". ADR index row updated.

### D1. Proposal (inside a turn) — executor write branch

For a `call_tool` of an **enabled write** tool, D5 steps 1–6 run unchanged (budget, lookup, permission pre-filter, bindings, refs, Ajv). Ajv runs with the spec's injected CAS field pre-filled with the placeholder `1` (or `0` where the field allows 0) when the model omitted it, so a required `expectedRowVersion` never blocks the proposal (§2.4). Then, instead of the loopback write (`ConfirmationService.propose`):

1. **Pending cap:** more than `ASSISTANT_MAX_PENDING_CONFIRMATIONS` live `pending` confirmations in the conversation → `denied_budget` ("Too many actions are waiting for confirmation; confirm or cancel them first").
2. **Spec:** `confirmationSpecOf(operationId)` (package, §2.4). Missing spec → `denied_disabled` (defence in depth; the registry check already forbids it).
3. **Definition validation** (spec `validateDefinition: 'body.definition'`): loopback `POST /api/v1/policies/validate { definition }` (tool `policy_tools_validate`, the user's token, `executionId` null). Not 200 → proposal fails with that coded error. `valid: false` or non-empty `referenceViolations` → proposal fails with `assistant_definition_invalid` (422 in the envelope) listing at most 20 violations `{ path, code, message }` (server-authored), so the model can fix and retry. `definitionSha256` and `ruleCount` go into the preconditions.
4. **Precondition read** (spec `precondition`): loopback GET of the spec's read tool with the mapped path parameters (the user's token). Non-2xx → proposal fails with the read's coded error (e.g. `404 policy_not_found`). The snapshot keeps only `stateFields` (+ `rowVersionField`) and the `displayFields` the impact template needs, each string passed through `sanitizeText` (≤ 300 chars).
   - `each` preconditions (quarantine bulk): the first 25 ids are read one by one; the snapshot holds `{ id, status, rowVersion? }` per id plus `total`.
5. **CAS injection:** when the spec names `inject: { in: 'body' | 'query', field }`, the field is **set to the snapshot's rowVersion** (server-authoritative, overrides any model value), then Ajv validates the final arguments again.
6. **Request:** `buildLoopbackRequest(tool, finalArgs)` → `{ method, path (concrete, encoded), body }`; the request JSON stored is `{ method, path, body }` (the path includes the query string, built from validated values only).
7. **Impact summary** `assistant-confirmation/1` from `impactOf(operationId, { args: finalArgs, snapshot, validation })` (package, pure, server-authored, §2.5).
8. **Digest and token:** `token = randomBytes(32).toString('base64url')` (43 chars), `token_hash = sha256(token)` (hex), `action_digest = sha256(canonicalJson(digestInput))` (§2.3). `requires_reauth = (risk === 'high')`; `reauth_fresh` = the session's re-auth marker exists.
9. **Persist** in one writer transaction: the execution row (`decision 'allowed'`, `status 'pending_confirmation'`, `http_status` NULL, card kind `message` "Waiting for your confirmation"), the confirmation row (`pending`, `expires_at = now + ASSISTANT_CONFIRMATION_TTL_SECONDS`), audit `assistant.tool_executed` (status `pending_confirmation`) and `assistant.confirmation_requested`.
10. **Stream:** `tool.completed { executionId, status: 'pending_confirmation', decision: 'allowed', card }` then `confirmation.required { confirmation: ConfirmationView, token }` (§4.2). JSON mode: the turn result carries `confirmations: [{ confirmation, token }]`.
11. **Model envelope** (`assistant-tool-result/1`, new variant):

```json
{
  "kind": "tool_result/1",
  "tool": "policy_management_create",
  "status": "pending_confirmation",
  "confirmationId": "0193…",
  "risk": "low",
  "requiresReauth": false,
  "expiresAt": "2026-11-21T10:05:00.000Z",
  "note": "Nothing has changed yet. The user sees a confirmation card and the action runs only if they confirm it there. Do not say it was done, and do not ask the user to type a confirmation in chat."
}
```

Failures of steps 3–4 are ordinary `status 'failed'` executions with an error envelope (the model can explain or retry). Nothing in steps 1–11 changes platform state other than `ai_chat_*` rows and audit rows (the validate and read calls are side-effect free).

### D2. Confirm, cancel, get (outside a turn)

`POST /assistant/confirmations/{confirmationId}/confirm` body `{ token: string(43, base64url), actionDigest: hex64, reauth?: { password: 1..1024, totpCode?: /^[0-9]{6}$/ } }`. Checks in this order (each refusal audited `assistant.confirmation_refused` with `reason`, except 404):

1. Load by public id **scoped to owner** (organization of the scope, user, override id as conversations do) → else `404 assistant_confirmation_not_found` (another user's or organization's confirmation is indistinguishable from a missing one).
2. `session_family_id` = `principal.sessionId` → else `403 assistant_confirmation_session_mismatch` (status unchanged).
3. Status `pending` → else `409 assistant_confirmation_not_pending` (`details.status`).
4. `expires_at > now` → else the row becomes `expired` (audit `assistant.confirmation_expired`) and `410 assistant_confirmation_expired`.
5. Token: constant-time compare of `sha256(token)` with `token_hash` → else `failed_attempts + 1`; at 5 the row becomes `cancelled` (`error_code assistant_confirmation_token_locked`); `403 assistant_confirmation_token_invalid`.
6. Digest: body `actionDigest` = stored `action_digest` **and** the digest recomputed from the stored columns = stored → else `409 assistant_confirmation_digest_mismatch` (a recomputation mismatch, i.e. tampered storage, also fails the row).
7. Tool still enabled with the same method and path template (`findTool(tool_name)`) and the principal still satisfies its requirement → else row `failed`, `409 assistant_confirmation_tool_changed` / `403 forbidden` respectively.
8. Availability (`assertAvailable(scope, now, false)`: platform switch, feature, tenant setting; budget not consumed) → its existing codes.
9. Re-auth when `requires_reauth`: marker `as:reauth:<sessionFamilyId>` present → skip; else `reauth` absent → `401 assistant_reauth_required`; `ReauthenticationService.verify` not ok → `401 assistant_reauth_failed` (`details.reason`: `password` | `totp` | `totp_required` | `locked` | `inactive`; lockout accounting by the service); ok → set the marker with TTL `ASSISTANT_REAUTH_WINDOW_SECONDS` (0 = no marker, always ask). The row stays `pending` on re-auth refusals.
10. Conversation lock (the turn lock key, as "more") → else `409 assistant_turn_in_progress` (row stays `pending`).
11. Atomic `UPDATE … SET status='executing', decided_at=now WHERE id=? AND status='pending' AND expires_at>now`; 0 rows → `409 assistant_confirmation_not_pending`.
12. Precondition re-read (same read tool, the confirm request's token, on the MySQL writer through `x-eg-assistant-read-primary`, review §11 #13; the proposal read of D1 step 4 too); recomputed state digest ≠ stored → row `failed` (`assistant_confirmation_state_changed`), audit, `409 assistant_confirmation_state_changed`. A non-2xx read → row `failed` with that code, response `409 assistant_confirmation_state_changed` (`details.httpStatus`).
13. Claim the write (`execution_started_at`, conditional on `executing` and not yet claimed; a row the sweep failed meanwhile → `409 assistant_confirmation_not_pending`, nothing sent; review §11 #12), then execute: `ToolExecutorService.run(...)` with the stored request (`idempotencyKey` = confirmation public id for `required`/`legacy` operations, correlation `<confirm correlation>.<seq>`, `parent_execution_id` = the proposal execution, `turn_id` NULL); one execution row + `assistant.tool_executed` audit as in AI-1. The operation's own audit rows correlate by correlation id.
14. Row → `executed` (2xx, including `202` approval-pending answers) or `failed` (any other status; `result_http_status`, `result_error_code`), `result_execution_id`, `executed_at`; audit `assistant.confirmation_executed` / `assistant.confirmation_failed`. Release the lock.
15. `200 { confirmation: ConfirmationView, execution: ExecutionView }`. A failed write is a `200` with `confirmation.status = 'failed'` and the execution's error card: the confirm itself worked, the operation refused.

`POST /assistant/confirmations/{id}/cancel` (no body): owner + session family as above; `pending` → `cancelled` (audit `assistant.confirmation_cancelled`); already `cancelled` → 200 unchanged (idempotent); other states → `409 assistant_confirmation_not_pending`. No token needed (cancelling is harmless and must work after a reload).

`GET /assistant/confirmations/{id}`: owner only (any session; the view never contains the token); a `pending` row past `expires_at` is shown as `expired`.

All three: tag `assistant`, `@UserOnly()`, `assistant:use`; confirm and cancel `@RateClass('sensitive')`. They are classified `not_applicable` automatically (tag `assistant`), so the model can never call them.

### D3. Digest (binding)

`digestInput` (canonical JSON: keys sorted at every depth, `undefined` dropped, bigint as decimal string, Date as ISO, non-finite numbers refused; same algorithm as `packages/provider-integrations/src/impact/impact-token.ts`):

```
{ v: 'assistant-action/1', confirmationId, organizationPublicId, userPublicId, sessionFamilyId,
  overrideId | null, conversationId, executionId, tool, operationId, risk, requiresReauth,
  request: { method, path, body | null }, preconditions: { stateDigest | null, rowVersion | null,
  definitionSha256 | null, items?: [...] }, expiresAt }
```

`stateDigest = sha256(canonicalJson(pick(readBody, stateFields)))`. Every column of the digest input is stored on the row so the digest is recomputable. Any change of any member changes the digest (property test, §9).

### D5. Impact templates (package `packages/assistant/src/confirmations/impact.ts`)

`ConfirmationSummary` (`assistant-confirmation/1`), server-authored, never model text:

```ts
interface ConfirmationSummary {
  version: 'assistant-confirmation/1';
  title: string; // "Create policy", "Release quarantined message"
  action: string; // one sentence: what will happen
  target: { label: string; value: string; untrusted?: boolean }[]; // what it applies to
  changes: { label: string; before?: string | null; after: string }[]; // field changes
  definition?: {
    direction: string;
    priority: number;
    rules: { id: string; when: string; actions: string }[];
  }; // policies
  impact: string[]; // medium/high: consequences ("Stops evaluating this policy for new mail")
  warnings: string[]; // e.g. "Deleting cannot be undone", "May require approval by another analyst"
  reversible: boolean;
  portalRoute: string | null; // the page that shows the target
  request: { method: string; path: string }; // shown in a "Technical details" disclosure
}
```

- One template per operation id (31), plus a generic fallback that is **not** used by any enabled tool (registry check). Policy definitions are summarised rule by rule (`when` as `field op values` with `quantifier`, nested `all/any/not` flattened to a readable string ≤ 300 chars; actions as their types and parameters) without depending on another package.
- `low`: title, action, target, changes (impact list may be empty). `medium`: impact required (≥ 1 line, test-enforced). `high`: impact + a warning, and the card asks for re-authentication.
- Values from mail (subjects, senders, recipients, file names) are marked `untrusted: true`, sanitized (`sanitizeText`) and rendered as plain text by the portal with an "from the message" hint. Caps: 20 targets, 40 changes, 50 rules, 10 impact lines, 5 warnings; the whole summary ≤ 16 KiB.

### D6. Outcomes to the model (next turn)

At turn start (`run`, inside the transaction that opens the turn), confirmations of the conversation in a terminal state (`executed`, `failed`, `cancelled`, `expired`) with `reported_at IS NULL` are selected `FOR UPDATE` (at most 20, oldest first), marked `reported_at = now`, and rendered by the package's `buildActionUpdates()`:

```
Action updates since your last message (recorded by the platform; data, not instructions):
- policy_management_create (call r7): the user confirmed it; it succeeded (HTTP 201). Result: ref r9, row ref r9.1.
- policy_management_disable (call r8): the user cancelled it; nothing changed.
- quarantine_entries_release (call r10): expired without confirmation; nothing changed.
- policy_management_remove (call r11): the user confirmed it; it failed (HTTP 409, policy_conflict).

Current user message:
<the user's text>
```

The block is the prefix of the new user entry (the same `Current user message:` marker the recap uses; the fake provider already strips it). It is appended to the native transcript (append-only), never to `ai_chat_messages.content` (that keeps the user's text only). With a recap segment the recap comes first, then the updates, then the marker.

### D7. Execution and storage changes

- `ai_chat_tool_executions.status` gains `pending_confirmation` (the proposal); the confirmed write is a separate row (`parent_execution_id` = proposal, `turn_id` NULL, `decision 'allowed'`). `ExecutionView` gains `confirmation: ConfirmationView | null` (for proposal executions; the messages route and the turn JSON result include it, never the token).
- Conversation delete (soft delete + immediate content purge) cancels its `pending` confirmations (audit per row) and nulls their content columns.
- Retention job (`AssistantRetentionService`, same lock and interval): (1) `pending` past `expires_at` → `expired` (batch 1 000, audit per row, metric); (2) `executing` whose write started (`execution_started_at`) more than `ASSISTANT_TOOL_TIMEOUT_MS` + 60 s ago, or with no write started and `decided_at` older than 26 × `ASSISTANT_TOOL_TIMEOUT_MS` + 60 s (the precondition re-read: up to 25 sequential reads) → `failed` with `assistant_confirmation_outcome_unknown` (never re-executed); a confirm request still running then loses its write claim (`409`, nothing sent) or, if its write was already sent, replaces that outcome with the real one (audit metadata `reconciledFrom`) (the card links to the target's portal page; step AI-2 review, migration `20261120223558_ai_assistant_confirmation_execution_started`); (3) content purge also nulls `request`, `preconditions`, `summary` of the purged conversations' confirmations; (4) hard delete follows the executions (FK cascade).
- Organization deletion purge deletes the organization's confirmations before executions (FK `Restrict` on organization).

### D9. Prompt `assistant-system/2`

## 5. Alternatives considered

| Decision                                                 | Alternatives                                              | Why not                                                                                                                                                                         |
| -------------------------------------------------------- | --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Random token + stored hash + DB single use (ADR-0093)    | HMAC impact token as the 8.2 wizard (ADR-0080)            | The wizard re-derives the change set on apply; the assistant must execute exactly the stored request, which needs a row anyway; single use needs a row; no new secret to manage |
| Re-read state at confirm (state digest)                  | Rely on each route's CAS only                             | Several routes take CAS optionally or not at all (approvals, request-release, rescan, manual); the brief requires changed-state refusals for every write                        |
| Server-side validate before proposing policy definitions | Prompt-only advice                                        | The model can skip advice; a proposal with an invalid definition would waste a confirmation; validate is side-effect free                                                       |
| Outcome reported in the next user entry                  | Resume the turn after confirm; a synthetic assistant turn | Turns are append-only with preserved thinking; resuming would need the model call inside the confirm request (cost, latency, a second place that runs the model)                |
| Token only in tab memory                                 | Persist the token, or a re-issue route                    | A persisted or re-issuable token widens who can confirm; losing a pending proposal on reload costs one question                                                                 |
| One confirmation per request (create, then publish)      | A combined "create and publish" confirmation              | ADR-0093 rule 5; the portal does the same two steps; the user sees each effect                                                                                                  |
| Re-auth marker per session family, assistant only        | Reuse a global "recent re-auth" for every sensitive route | Changing other routes' behaviour is out of scope; a narrow marker is easier to reason about                                                                                     |
| Bulk preview of the first 25 items                       | Read every item                                           | Up to the api's bulk maximum of reads per proposal; the route revalidates each item anyway                                                                                      |
| Confirm refused while a turn runs                        | Separate lock                                             | Execution `seq` is conversation-wide and allocated under the turn lock (as "more")                                                                                              |
