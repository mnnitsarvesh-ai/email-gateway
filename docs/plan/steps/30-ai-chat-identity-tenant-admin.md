## 0. Scope in one paragraph

AI-3 enables the 47 identity and tenant administration operations planned for this phase as chat tools, each a write proposed by the model and executed only after the user confirms the server-authored card of AI-2: users (invite, update, status, roles, MFA reset, delete, resend invitation), sessions of other users (revoke one, revoke all), roles (create, update, delete), departments (create, update, delete, members), API key revocation, domains (create, delete, status, DNS verification, DKIM rotation, destinations, recipient validation), notifications (own preferences, tenant settings), organizations (tenant settings and name; platform: create, cancel a pending deletion, feature and limit overrides), scan settings, SMTP connectors (non-secret fields only) and webhooks (update, delete, test, delivery replays; signing secrets never). It adds one missing read (`GET /api-keys/{id}`, needed to show which key a revocation targets) and hardens the reads of these modules (untrusted fields). Three new controls make identity changes safe in chat: **proposal guards** (separation of duties: no change to one's own account, roles, MFA or sessions through chat; the assistant cannot change its own enablement or who configures it), **conditional risk escalation** (an otherwise low/medium change that redirects mail, events, sign-in mail or relay rights, or weakens MFA, becomes `high` and needs re-authentication), and **selected-item preconditions** (the target's state read from a list response). Every role and permission change is `high` (password + TOTP re-authentication). The api's existing no-escalation rules stay the authority and are proven by tests, including the adversarial fake. Credential creation, display and rotation (API key create, webhook create and secret rotation, SMTP connector create and secret rotation), the caller's own sessions, MFA and password, organization status and deletion stay portal-only.

## 2. Decisions

### 2.0 Invariants added to I1–I11

- **I12 No self-service of authority through chat.** Through chat nobody changes their own account, roles, status, MFA or sessions, nor whether the assistant is enabled or who may configure it. The assistant refuses these proposals before anything is stored; the portal keeps its own (unchanged) paths and rules.
- **I13 The api's no-escalation rules stay the authority.** Proposal guards only add refusals; every confirmed identity change still passes `assertCanManageUser`, `assertNoEscalation`, the role-permission rule, the last-administrator guard and the platform-override restrictions. Tests prove the api refuses an escalation that reaches it.
- **I14 Credentials never pass through chat.** No AI-3 tool creates, displays, rotates or accepts a password, API key, SMTP secret, webhook signing secret, invitation or reset token. Operations that do are N/A (unchanged), and no AI-3 tool's input schema has a credential field (registry check, D6).

### 2.1 ADR-0093 amendment AI-3 (written by WP1)

ADR-0093 keeps its decision and the AI-2 amendment. A new section "Amendment AI-3 (2026-11-21)" records: (j) **proposal guards** (D3): server-side refusals evaluated at proposal and again at confirm, recorded as executor decision `denied_guard` (proposal) or row error `assistant_action_not_allowed` (confirm, `403`); (k) **conditional risk escalation** (D4): the stored risk is the effective risk (the registry risk raised by the spec's escalation rules on the final arguments); the digest binds it; confirm recomputes it and refuses a difference (`409 assistant_confirmation_tool_changed`); (l) **selected-item preconditions** (D5); (m) every role and permission change is `high` (re-authentication), and every write of a credential stays N/A. ### D3. Proposal guards (separation of duties; package `confirmations/guards.ts`)

`ConfirmationSpec.guards?: readonly ProposalGuard[]`, evaluated by a pure function of the package:

```ts
export type ProposalGuard =
  /** The argument (a user public id) must not be the caller (case-insensitive UUID compare). */
  | { kind: 'not_self_user'; arg: string }
  /** The argument must not take one of these values. */
  | { kind: 'deny_values'; arg: string; values: readonly string[]; message: GuardMessageKey }
  /** No permission of `permissions` may be added or removed (new set from the argument, old set
   * from the precondition read's `beforeField`; no precondition = old set empty). */
  | {
      kind: 'deny_permission_change';
      arg: 'body.permissions';
      beforeField?: 'permissions';
      permissions: readonly string[];
    };

export interface GuardInput {
  args: Readonly<Record<string, unknown>>; // final arguments
  principalUserPublicId: string;
  read: unknown | null; // the raw precondition body, or the selected item (D5); null before the read
}
export type GuardRefusal = { guard: ProposalGuard['kind']; message: string };
/** `phase: 'before_read'` evaluates the guards that need no read (not_self_user, deny_values). */
export function guardRefusal(spec, input, phase: 'before_read' | 'after_read'): GuardRefusal | null;
```

Messages are fixed server-authored English (`GUARD_MESSAGES`), never containing argument values:

- `self`: "Changes to your own account, roles, status, MFA or sessions are not available in chat. Ask another administrator, or use your account pages in the portal."
- `assistant_feature`: "The assistant cannot turn itself on or off for an organization. Use the Organizations page in the portal."
- `assistant_configure`: "The assistant cannot change who may configure it. Change roles that grant assistant:configure in the portal."

Guards per tool:

| Guard                                                                    | Tools                                                                                                                                                                           |
| ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `not_self_user` on `id`                                                  | `users_update`, `users_change_status`, `users_replace_roles`, `users_reset_mfa`, `users_remove`, `users_revoke_all_sessions`, `users_revoke_session`, `users_resend_invitation` |
| `deny_values` `featureKey ∈ {ai_assistant}` (`assistant_feature`)        | `organization_configuration_override_feature`, `organization_configuration_reset_feature`                                                                                       |
| `deny_permission_change` `{assistant:configure}` (`assistant_configure`) | `roles_create` (no before set), `roles_update` (`beforeField: 'permissions'` from `roles_get`)                                                                                  |

Separation of duties for identity changes in chat therefore is: (1) I12 self guards; (2) the api's target-side and no-escalation rules (I13); (3) `high` risk with fresh password + TOTP re-authentication on every role, permission, status, MFA, session and invitation change (D2); (4) the assistant cannot change its own enablement or who configures it; (5) full audit (proposal, guard denial, confirmation, the operation's own audit row, correlated). A four-eyes approval for role changes is not built (§6 A3-5).

### D5. Selected-item preconditions (package `confirmations/specs.ts`)

`SinglePrecondition.select?: { array: string; field: string; arg: string; required: boolean }`: the read tool returns a list (`array`, a dotted path to an array in the read body); the item whose `field` equals the write argument `arg` (string compare) is the target. `stateFields`, `rowVersionField` and `displayFields` are then relative to the item. Not found: `required: true` → the proposal fails like a `404` read (`kind: 'response', status 404, code 'not_found', "The target was not found"`); `required: false` → the snapshot's fields are null and the state digest is that of `{}` (a feature or limit without a stored value; the confirm re-read must still find it absent or refuse as changed). Helpers: `selectTarget(body, precondition, args)`; `stateDigest`, `rowVersionOf`, `buildSnapshot` are applied to the selected item. Consistency: `select.arg` exists in the write's input schema; `select.array` is non-empty; `select` is only allowed on `single`.

### D7. Impact templates (47)

One `assistant-confirmation/1` template per operation id, same rules as AI-2 D5 (title, one-sentence action, targets, changes before → after from the snapshot, `medium` ≥ 1 impact line, `high` ≥ 1 warning, caps, ≤ 16 KiB, `untrusted: true` for user display names, session user agents and anything listed in D9). Escalation warnings (D4) are appended to `warnings` (dedup, cap 5). Content rules specific to AI-3:

- Role changes list **added and removed permissions** (users: added/removed role keys from the snapshot's `roles`; roles: permission diff against the snapshot's `permissions`), never the full catalog; impact "Every holder of this role gets/loses these permissions" with the holder count only if the read gives it (it does not today: say "every user who holds this role").

- DKIM rotation: "A new key is created; publish its DNS record before the old key retires (overlap set by the platform)."
- Users invite: the email, display name and role keys; warning "An invitation email is sent; the person gets these roles when they accept."
- MFA reset / revoke sessions: "The user is signed out everywhere" and "must enrol MFA again at the next sign-in" as applicable.
- Webhook test: "Sends a test event to <url>." Replays: count/range from the arguments.
- Organization (platform) templates name the target organization from the snapshot where there is one (create: the slug and name from the arguments).
- Never a value of a credential-pattern key; the snapshot never contains one (the reads in D6 return none; tests assert it).

`reversible`: false for deletes, MFA reset, session revocation, DKIM rotation, invitations and tests/replays (sent); true otherwise.

### D10. api changes (assistant module)

- **Executor** (`tool-executor.service.ts`): after D5 step 6 (Ajv) of a write and before `propose`, `guardRefusal(spec, { args, principalUserPublicId, read: null }, 'before_read')` → `deny(..., 'denied_guard', refusal.message, { guard })`: execution row `refused` / `denied_guard`, `assistant.tool_denied` audit (metadata `guard`), stream `tool.denied`, envelope `{ status: 'denied', decision: 'denied_guard', message }`. Before-read guards re-evaluated with the stored arguments and the confirming principal (same user, so normally a no-op; defence in depth); after the precondition re-read (D2 step 12) the after-read guards re-evaluated on the fresh target → row failed `assistant_action_not_allowed`, `403 assistant_action_not_allowed`, audit `assistant.confirmation_refused` (`reason: 'guard'`), metric outcome `refused_guard`.

Decision `denied_guard` in `assistant.schemas.ts` (ExecutionView, stream event schemas), OpenAPI snapshot regenerated, portal generated client regenerated.
- **Metrics:** `assistant_confirmations_total` outcome adds `refused_guard`; `assistant_tool_calls_total` (or the AI-1 equivalent) decision label adds `denied_guard`.
- **Logs and audit:** never argument values of identity changes in logs; audit metadata keys as AI-2 plus `guard`, `baseRisk` (both safe against the credential scrub).

## 5. Alternatives considered

| Decision                                                         | Alternatives                                                             | Why not                                                                                                                                                                                                                                                              |
| ---------------------------------------------------------------- | ------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Self guards in the assistant (I12)                               | Rely on the api only                                                     | The api allows self role changes that do not add permissions and self profile/session changes; the brief requires that the AI never grants itself permissions or changes the rules about itself; changing the api would change the portal's behaviour (out of scope) |
| Guards as data in the spec, evaluated by a pure package function | Hard-coded checks in the executor                                        | Testable without the api, visible in the registry check and the matrix, one place for proposal and confirm                                                                                                                                                           |
| Conditional escalation by argument                               | Make every such tool `high`                                              | Renaming a webhook or a connector with password + TOTP is friction that trains users to confirm blindly; escalation targets exactly the dangerous fields                                                                                                             |
| Conditional escalation                                           | A separate tool per dangerous field                                      | The tool set is bound 1:1 to API operations (ADR-0091)                                                                                                                                                                                                               |
| `select` over a list read                                        | New single-item read routes for features, limits, sessions, scan engines | Those lists are small and complete in one response; new routes widen the api for no portal use                                                                                                                                                                       |
| New `GET /api-keys/{id}`                                         | `select` over `GET /api-keys`                                            | The key list is cursor-paginated (100 per page): a key on a later page would be "not found"                                                                                                                                                                          |
| New decision value `denied_guard` (migration)                    | Reuse `denied_permission` or a `failed` execution                        | The user has the permission; a failed execution implies the api answered; audit and UI must say "not allowed in chat" exactly                                                                                                                                        |
| `webhooks_test` as a write                                       | Keep it a side-effect-free read                                          | It sends an event to an external URL; a prompt-injected loop could spam a third party; one confirmation per test is cheap                                                                                                                                            |
| Feature `ai_assistant` and `assistant:configure` guarded         | Allow with re-auth                                                       | I3: the model must not change permissions or settings of the assistant itself; a confirmed card does not change who proposed it                                                                                                                                      |
