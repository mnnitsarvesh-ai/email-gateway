## 0. Scope in one paragraph

Every API-mode copy that API-1 records (`api_message_copies`, one row per mailbox with verdict and risk score) is run through a **remediation policy** (per organization, with optional per-domain overrides) that maps verdict and risk to a **mailbox action**: move to the gateway's quarantine folder (Graph) or label (Gmail), move to Junk, tag with a category/label, soft delete (recoverable), or hard delete (only when a platform setting allows it, off by default, never in a default). The default is P1: high-confidence malware and phishing go to the quarantine folder automatically, suspicious mail is tagged, nothing is hard-deleted; a **detect-only** mode records what would have happened without touching mailboxes. The mailbox-worker's new **`remediate`** role executes actions through the API-1 Graph/Gmail clients: idempotent (one action row per copy, action and generation, unique key), budgeted per tenant, retried with back-off on 429/503 honouring `Retry-After`, audited and reversible where the provider allows it. Hybrid copies the inline path already decided are never remediated automatically. Messages moved to the quarantine folder, Junk or a soft-delete location become **mailbox-located quarantine entries**: they appear in the existing quarantine pages and APIs with their location ("in mailbox quarantine folder"), and the existing release flow, approvals and end-user self-service apply — a release is a **restore to the Inbox** through the provider API, never a delivery. Remediation success, failure, backlog and throttling are counted, alerted and shown on the API-1 coverage page.

### 1.2 Gaps and conflicts found

1. **N1 of note 35 says copies never reach quarantine release.** A mailbox-located entry is released by moving the provider message back to the Inbox — no delivery, reinjection, lifecycle edge or rescan. → ADR-0102 supersedes N1/ADR-0098 (7) in part: "release" of a mailbox entry is a provider restore; every other N1 guarantee stays (copies never delivered, never in `parsed.v1` → policy, never `scanned.v1`, lifecycle still ends `journaled`).
2. **The quarantine store is written only by the policy-engine evaluation transaction** (ADR-0046 decision 1) and **released only by the policy-engine executor after policy re-validation** (ADR-0047). Copies have no policy evaluation (out of scope ii) and no lifecycle round to re-enter. → Mailbox entries are written and released by the mailbox-worker; their release pre-check is a stored-verdict decision (`decideMailboxRestore`, R10) instead of policy re-validation (ADR-0102).
3. **Entry uniqueness `(message_id, lifecycle_round, rcpt_seq)`.** A journal copy fans out to many mailboxes (one recipient row each; distinct `rcpt_seq`); a copy can be remediated again after a restore. → For `location = mailbox`, `lifecycle_round` holds the copy's **remediation generation** (0, 1, …) and `rcpt_seq` the copy's recipient (R9.2); documented on the column.
4. **The quarantine sweeper and disposal apply message lifecycle edges** (E17/E18/E26) and S3 purges. Copies are `journaled` (terminal) and their EML follows message retention. → The policy-engine skips `location = mailbox` entries for expiry, adoption, purge and the release executor; the mailbox-worker expires mailbox entries without lifecycle or object changes (R11.4).
5. **The API-1 clients are read-only and journal copies have no provider message id** (note 35 §2.4 hook). → Locate step by Internet Message-ID before the first action (R6.3).
6. **Graph `move` returns a new message id** (ids are folder-scoped unless immutable ids are requested). → Every remediation action stores the id the move returned (`provider_refs`), a restore first tries it and falls back to the locate step (R6.4).
7. **Gmail `gmail.modify` does not allow permanent deletion** (`messages.delete` needs the full `https://mail.google.com/` scope, which ADR-0099 does not request). → Hard delete on Google falls back to Trash and records it (R5.4).
8. **API-1's `api_mode_unhealthy` alert and the health document** have no remediation checks. → Four new checks (R14); same alert kind, no contract change.
9. **Topology:** decisions are taken inside the existing `email.mailbox` consumer (RabbitMQ, ledger) and executed from a DB-claimed action table (the feeds pattern); restores requested by the api are rows in the same table. → No new queue (topology v17 unchanged); §6 records the alternative.

## 2. Program position and invariants

The note 35 invariants N1–N9 hold, with N1 amended by ADR-0102 (release of a mailbox entry = provider restore). API-2 adds:

- **R-I1 Never claim a mailbox state that did not happen.** A copy's `remediation_state` and a mailbox entry exist only after the provider call succeeded (or the target state was found already reached); simulated (detect-only) and skipped decisions are recorded as such.
- **R-I2 Never irreversible by default.** Hard delete needs the platform setting `API_MODE_HARD_DELETE_ENABLED=true` **and** an explicit tenant rule; it is never in a default or preset, never manual, never from the assistant.
- **R-I3 Inline decides first.** A copy whose verdict authority is `inline` (hybrid, linked to a gateway message) is never remediated automatically.
- **R-I4 One action per (copy, action, generation).** `action_key` is unique; every writer uses `INSERT IGNORE` on it; the executor re-reads the provider state before acting, so a lease expiry or crash repeats nothing harmful.
- **R-I5 Tenant from trusted context.** The api takes the organization from the principal (foreign ids → `404`); the worker from the action row and re-checks the copy, mailbox and connection belong to the same organization before every provider call.
- **R-I6 No content in MySQL.** Action rows hold ids, enums, codes, provider message ids (opaque), counts and timings; never subjects, addresses beyond the mailbox reference, bodies or provider response bodies.

## 4. Decisions

### R1. Where decisions and actions live (ADR-0101)

- **Decision** (policy → action row) is taken by the mailbox-worker **`copies`** role inside the existing ledger transaction of `mail.message.copy_scanned.v1`, right after the copy row is written/finalized (atomic with the verdict; a redelivery is a ledger duplicate; `INSERT IGNORE` on `action_key` is the backstop).
- **Execution** is the new **`remediate`** role: a claim loop over `api_remediation_actions` (`status = pending AND next_attempt_at <= now AND (lease_until IS NULL OR lease_until < now)`, `FOR UPDATE SKIP LOCKED`, lease `API_MODE_REMEDIATION_LEASE_SECONDS` 120, status `in_progress`), modelled on `feeds/feed-claims.ts`.
- **Manual remediation, restores and retries** requested through the api insert action rows (status `pending`, `next_attempt_at = now`) in the api's writer transaction; the claim loop picks them up within one tick (`API_MODE_REMEDIATION_TICK_MS` 2 000).
- `remediate` is a provider-calling role (`PROVIDER_CALLING_ROLES` gains it). Default `MAILBOX_WORKER_ROLES` = `copies,feeds,inventory,health,remediate`.

### R2. Remediation policy (pure: `@email-gateway/mailbox-api` `src/remediation/policy.ts`)

**R2.1 Document `api-remediation-policy/1`** (strict zod `remediationPolicySchema`, exported with its TypeScript type):

```text
{
  v: 1,
  rules: [                                   // 1..16, first match wins, evaluated in order
    {
      id: string (1..48, [a-z0-9_-]),        // unique within the document
      when: {
        verdicts: MessageVerdict[] (1..9, unique; 'clean' and 'unknown' refused),
        minLevel?: 'low'|'medium'|'high'|'critical',
        maxLevel?: 'low'|'medium'|'high'|'critical',   // ≥ minLevel
        hardBlock?: boolean,                            // true: any hard block; false: none
        minScore?: int 0..1000
      },
      action: 'move_quarantine'|'move_junk'|'tag'|'soft_delete'|'hard_delete'|'none'
    }
  ],
  remediateScanFailures?: false              // reserved; must be false in API-2 (scan_failed copies are never remediated)
}
```

`mode` (`detect_only`/`enforce`) is a column, not part of the document. Unknown keys are refused (`.strict()` everywhere). `when.policyDispositions` is **reserved** for the later policy-evaluation step and refused today with the zod issue `unsupported_until_policy_evaluation`.

**R2.2 Decision input** `RemediationInput` (`decideRemediation(input, policy, options)`, pure, table-tested):

```text
{
  copy: { status: ApiCopyStatus, verdict: MessageVerdict | null, riskScore: number | null,
          verdictAuthority: 'copy'|'inline' },
  risk: { level: RiskLevel | null, hardBlocks: string[] } | null,   // round's latest revision row
  policyOutcome: null,               // R2.5 hook; API-2 always passes null
  context: { provider: 'microsoft_365'|'google_workspace', grantActive: boolean,
             remediationPaused: boolean, domainEffectiveMode: 'inline'|'api'|'hybrid'|null,
             mailboxStatus: 'active'|'discovered'|'disabled'|'deleted' },
  options: { hardDeleteEnabled: boolean }
}
```

Output `RemediationDecision`:

```text
{ outcome: 'none' } |
{ outcome: 'skip', reason: SkipReason, ruleId: string|null, action: Action|null } |
{ outcome: 'act', action: Action, ruleId: string, simulated: boolean, notes: string[] }
```

Order of evaluation: (1) `copy.status !== 'scanned'` or verdict `clean`/`unknown`/null → `none`; (2) first matching rule → its action; no match or action `none` → `none`; (3) `verdictAuthority = 'inline'` → `skip inline_authority`; (4) domain effective mode not `api`/`hybrid` or mailbox `disabled`/`deleted` → `skip out_of_scope`; (5) `hard_delete` with `!hardDeleteEnabled` → `skip hard_delete_disabled`; (6) policy `mode = detect_only` → `act` with `simulated: true` (no provider call); (7) `remediationPaused` → `skip remediation_paused`; (8) `!grantActive` → `skip no_mailbox_access`; (9) otherwise `act`. A Google `hard_delete` decision carries the note `hard_delete_falls_back_to_trash` (R5.4). A rule matches when the verdict is in `verdicts` and every present bound holds (`level` null fails `minLevel`/`maxLevel`; `hardBlocks` empty fails `hardBlock: true`; score null fails `minScore`).

**R2.3 Platform default policy** `DEFAULT_REMEDIATION_POLICY` (P1, mode `enforce`; product-owner default API2-1, revisable):

| #   | id                                       | when                                                 | action            |

### R4. Decision step in the copies role (mailbox-worker, WP3)

After `recordJournalCopies` / `finalizeFeedCopies` wrote a copy (only for copies actually recorded or finalized, never for a `duplicate`), in the same transaction:

1. Load the round's latest risk row (`message_risk_scores` by `message_id`, `received_at`, `scan_id = payload.scanId`, highest `revision`) — `level`, `hard_blocks[].id`. Missing → `risk: null`.
2. Resolve the effective policy (R2.6), the connection's `remediation_paused`, grant status (the active `*.mailbox_remediation` grant of the provider connection), domain effective mode, mailbox status; run `decideRemediation`.
3. `none` → nothing (copy stays `remediation_state = none`).
4. `skip` → `INSERT IGNORE` an action row (`status = skipped`, `reason_code`, `trigger = policy`, `generation` = the copy's `remediation_generation`), copy `remediation_state = skipped`, `remediation_action` = the rule's action (if any); counter `remediation_skipped`.
5. `act` + `simulated` → action row `status = simulated`; copy `remediation_state = simulated`; counter `remediation_simulated`.
6. `act` → action row `status = pending`, `next_attempt_at = now`, `verdict_at`; copy `remediation_state = pending`, `remediation_action`, `last_action_id`.

A copy that already has a non-terminal or succeeded remediation of the same generation is left alone (the unique key returns 0 rows). Late verdicts (sandbox revision 1 after `copy_scanned.v1`) are not re-decided in API-2 (API2-15 → API-3 clawback).

### R5. Execution (mailbox-worker `remediate` role, WP3)

**R5.1 Claim and pre-checks.** Up to `API_MODE_REMEDIATION_BATCH` (50) due rows per tick, concurrency `API_MODE_REMEDIATION_CONCURRENCY` (8) overall and `API_MODE_REMEDIATION_CONCURRENCY_PER_CONNECTION` (2) per connection. Before any provider call: connection active and bound, grant `active` (else `failed mailbox_access_revoked`), `remediation_paused` (policy-triggered rows go back to `pending` with `next_attempt_at = now + 300 s`; admin, release and end-user rows proceed), the throttle gate of the family (paused → `next_attempt_at = throttled_until`, no attempt counted), organization consistency (R-I5; mismatch → `failed integrity_mismatch`, error log).

**R5.2 Statuses.** `pending → in_progress → succeeded | failed | pending (retry)`; `cancelled` (a pending policy action whose copy was restored/remediated otherwise, or a restore cancelled because its entry left `releasing`); `skipped` and `simulated` are terminal at insert. Each terminal transition updates the copy in the same transaction (`remediated`, `restored`, `failed`; the copy row is locked before the action's CAS, the api's lock order). A `failed` or `cancelled` action that the copy's `last_action_id` points at never leaves the copy `pending` (review fix, §15.2): a failed remediation of the current generation → `failed`; otherwise the state the history implies — a succeeded unreversed remediation of the current generation → `remediated` (a failed `remove_tag` leaves the tag in effect), else after a restore → `restored`, else the latest other `failed`/`simulated`/`skipped` row, else `none`. A remediation of an older generation is `cancelled` before any provider call whatever its trigger (policy rows are also cancelled when another action took over the copy). Each terminal transition writes counters (after commit) and, for `succeeded`/`failed` of non-simulated rows, one **`audit_logs`** system row `api_mode.remediation_executed` `{ actionId, action, trigger, result, reasonCode, copyId, mailboxId, connectionId }` (ids and codes only).

**R5.3 Locate step** (no usable provider id: journal copies, or a stored id that returns `404`): Graph `GET /users/{u}/messages?$filter=internetMessageId eq '<id>'&$select=id,parentFolderId,isDraft&$top=10` (quotes escaped per OData), Gmail `GET …/messages?q=rfc822msgid:<id>&includeSpamTrash=true&maxResults=10`. Keep matches that are not drafts and not in Sent Items (Graph `parentFolderId` ≠ well-known `sentitems` id resolved once per mailbox; Gmail without the `SENT`-only label set), at most 5; act on each (`provider_refs.before`). No match → `locate_attempts + 1`, `pending` with `next_attempt_at = now + 60 s × 2^(locate_attempts−1)` up to `API_MODE_REMEDIATION_LOCATE_ATTEMPTS` (6, ≈ 1 h), then `failed message_not_found`. The found id is written to `api_message_copies.provider_message_id` when it was NULL.

**R5.4 Idempotent execution.** Before acting, read the message's current state (Graph `GET …/messages/{id}?$select=id,parentFolderId,categories`; Gmail `GET …?format=minimal` → `labelIds`): target already reached → `succeeded` with `reason_code = already_in_target`. Graph moves store the returned id in `provider_refs.after` (and `api_message_copies.provider_message_id`). A Google `hard_delete` runs the `soft_delete` plan and records `reason_code = hard_delete_unsupported_provider`; the row's `action` stays `hard_delete` (what was decided) and `provider_refs.container = 'deleted_items'` records what happened.

**R5.5 Generations.** `generation` = the copy's `remediation_generation` at insert. A successful reversal increments the copy's `remediation_generation`, so a later remediation of the same copy (manual or a future clawback) gets a fresh `action_key`; repeated requests within one generation collapse on the key.

**R5.6 Errors and retries.** `ProviderCallError` classes: `throttled` (429/503 with `Retry-After`, capped 600 s): the shared throttle gate is set (API-1 D10.6 behaviour), counter `remediation_throttled`, `next_attempt_at = throttled_until`, attempt not counted; retryable (5xx, timeouts, network): `attempts + 1`, `next_attempt_at = now + min(API_MODE_REMEDIATION_BACKOFF_MAX_SECONDS 3600, 30 s × 2^attempts)` until `API_MODE_REMEDIATION_MAX_ATTEMPTS` (8), then `failed`; an execution that never wrote its outcome (an outcome write that threw, a crashed replica) is re-claimed after its lease with `attempts + 1` (the thrown error's code kept in `last_error_code`), and a claimed row whose `attempts` reached the maximum is `failed internal_error` before any provider call; non-retryable: `401/403` after the client's token retry → `failed provider_forbidden`, `404` on a container (re-ensure once) or message (locate step), `400` → `failed provider_rejected`. Logs: public ids, codes, HTTP status, provider family; never ids of messages beyond the action's own public id, never bodies.

**R5.7 Budgets.** Every call takes the existing per-connection budget of its family (`mbx:rb:<connection>:<family>`) — remediation shares the tenant's provider budget with feeds and inventory, so a tenant's total call rate stays within one limit.

### R9. Mailbox-located quarantine entries (ADR-0102)

**R9.1 Creation.** When a `move_quarantine`, `move_junk` or `soft_delete` action succeeds (including `already_in_target`), the same writer transaction inserts a `quarantine_messages` row: `location = mailbox`, `mailbox_container` per R3, `origin = api_remediation`, `kind = quarantine`, `status = held`, `organization_id`, `message_id` / `message_received_at` = the copy's registry message, `lifecycle_round` = the copy's `remediation_generation`, `scan_id` = the copy's scan, `recipient_id` / `rcpt_seq` / `recipient_address` = the copy message's `email_recipients` row whose address is the mailbox's primary or alias address (lowest `rcpt_seq`; feed copies have one row), `user_id` = the organization's active user with that email (as 5.3), `direction`, `reason` = verdict mapped (`malware`→`malware`, `phishing`→`phishing`, `spam`→`spam`, `bulk`→`bulk`, `bec`→`bec`, `dlp_violation`→`dlp`, `suspicious`→`suspicious`, else `policy`), `envelope_from`, `header_from`, `has_attachments`, `attachment_count`, `size_bytes` from the registry message, `risk_score`, `risk_level`, `recommended_action`, `risk_verdict`, `has_hard_block`, `hard_blocks`, `reason_codes` from the risk row, `primary_engine` from the first hard block (`hb.malware_attachment`→`attachment`, `hb.malware_url`/`hb.url_tenant_blocked`→`url`, `hb.malware_sandbox`→`sandbox`, `hb.known_phishing`→`rspamd`, `hb.bec_malicious`→`bec`, `hb.dlp_block`→`dlp`, else `none`), `decision_source` NULL, `explanation_text` = a fixed template ("Removed from the mailbox by the API-mode remediation policy (rule <ruleId>)", content-free), `eml_object_key` = the copy's EML, `quarantined_at = now`, `expires_at = computeExpiry({ kind: 'quarantine', holdDays, … })` from the organization's resolved quarantine settings, `api_copy_id`, `api_copy_received_at`, `api_mailbox_id`, `api_remediation_action_id`. One `quarantine_actions` row `mailbox_remediated` (actor `system`, `result` = the action, `details` `{ actionId, container }`). The action row's `quarantine_entry_id` is set. An `INSERT` that hits the unique `(message_id, lifecycle_round, rcpt_seq)` means the entry already exists (crash replay) and is adopted.

**R9.2 Uniqueness.** `lifecycle_round` = remediation generation makes `(message_id, lifecycle_round, rcpt_seq)` unique per (copy, generation): a journal copy fans out to distinct recipients; a re-remediation after a restore uses the next generation.

**R9.3 What is not created:** `tag` (the message stays in the Inbox), `hard_delete` (nothing to release; visible in the remediation history), simulated and skipped decisions.

### R10. Release, approvals and self-service for mailbox entries (api, WP4; pure decision in `@email-gateway/quarantine`, WP2)

**R10.1 Pure decision** `decideMailboxRestore(input)` (`packages/quarantine/src/mailbox-restore.ts`): input `{ entry: { kind, reason, state, riskLevel, hasHardBlock }, copyStatus, mode: 'operator'|'self'|'approved', approvedReasons?, settings: Pick<QuarantineSettings,'release'|'endUser'> }` → the existing `ReleaseDecision` shape with `staleness` = not stale and `summary = null`. Approval reasons from stored facts only: `hard_block` when `hasHardBlock`; `scan_failed` when the copy status is not `scanned`; `review` for `kind = review` (never created in API-2). Hard blocks with `settings.release.allowHardBlocks = false` → refused `quarantine_hard_block_release_disabled`; self mode uses the same end-user bounds as `decideRelease` (enabled, self-release, reasons, max level, no approval reasons); no `rescan_required` (copies are never rescanned, N1). This replaces policy re-validation for mailbox entries (PO item ii deferred).

**R10.2 Release paths** (existing routes, unchanged request/response shapes): `POST /quarantine/entries/{id}/release`, `…/request-release`, the self routes and `POST /quarantine/approvals/{id}/approve` branch on `entry.location`:

- `gateway` → unchanged 5.3 behaviour.
- `mailbox` → pre-check = `decideMailboxRestore` (no replica policy facts); `approval_required` → the existing `release_approval` request (unchanged); `release` (or approval granted) → in the same transaction: a `quarantine_release_logs` row (`status = pending`, `mode`, `precheck` = the decision JSON, `released_to` = recipient address), entry → `releasing`, and an `api_remediation_actions` row `restore_inbox` (`trigger = release` or `end_user` for self-release, `reverses_action_id` = the entry's `api_remediation_action_id`, `quarantine_entry_id`, `release_log_id`, `generation` = the copy's current generation, `next_attempt_at = now`). **No** `mail.quarantine.release_requested.v1` outbox row. Response `202 { outcome: 'queued', releaseId, … }` as today.
- Separation of duties (`checkApprover`), request TTLs, approval notifications: unchanged.

**R10.3 Completion (mailbox-worker).** `restore_inbox` succeeded → entry `releasing → released` (`released_at`, `decided_at` kept from the request), release log `restored` (`completed_at`), `quarantine_actions` `mailbox_restored`, copy `remediation_state = restored`, `remediation_generation + 1`, the reversed action's `reversed_by_action_id`. In `approved` mode the worker re-runs `decideMailboxRestore` with the approval's `approved_reasons` first (facts can only have changed by a copy status change; uncovered reasons → entry back to `pending_approval` with a new `release_approval` request, release log `approval_required`). Failed permanently → entry `releasing → held`, release log `restore_failed` (`blocked_reason` = the code), `quarantine_actions` `mailbox_restore_failed`, copy unchanged (`remediated`). Entry no longer `releasing` when claimed (concurrent reject/delete) → action `cancelled`, release log `stale`.

**R10.4 Reject, delete, bulk** (api, WP4): `reject` → entry `rejected` without lifecycle edges or object changes (the message stays in the mailbox container). `delete` → entry `deleted`, and when the container is not `deleted_items` a `soft_delete` action (`trigger = admin`, `generation` = current) is queued; `quarantine_actions` `mailbox_deleted`; no object purge request (the EML follows message retention). Bulk applies the same per entry. Manual quarantine and rescan are gateway-message routes and stay `404` for copies (N1).

**R10.5 Read surfaces.** Entry list/detail gain `location: { kind: 'gateway' } | { kind: 'mailbox', container, mailboxAddress, provider, connectionId, detectionId, remediationId, remediationStatus }`; list filter `location=gateway|mailbox`; preview and download work unchanged from `eml_object_key` (same sensitive-content and malicious-content rules). Digests include mailbox entries (location-agnostic query); the template line reads "in your mailbox's quarantine folder" for `location = mailbox` when the template distinguishes locations (WP5 checks).

### R11. Policy-engine guards (WP5)

1. The release executor ignores (ledger only, counter `quarantine_releases_total{result="stale"}`) any release whose entries are `location = mailbox` (defensive: such events are never emitted).
2. The sweeper's entry expiry, adoption, object-purge selection and disposal select `location = 'gateway'` only.
3. Approval-request expiry applies to both locations (it only moves the entry back to `held`; WP5 confirms no lifecycle edge is applied for mailbox entries and guards it if one is).
4. **Mailbox entry expiry** is done by the mailbox-worker health leader: due `held`/`pending_approval` mailbox entries → `expired` (pending approvals `expired`), `quarantine_actions` `expire` (actor system); **no mailbox change** (the message stays in its container; API2-12).
5. The digest scheduler includes mailbox entries (verify; add the location text if the template is location-aware).

### R12. Manual remediation, restore and retry (api, WP4)

- `POST /api-mode/detections/{detectionId}/remediate` `{ action: 'move_quarantine'|'move_junk'|'tag'|'soft_delete', reason }` (`remediation:write`, Idempotency-Key): copy must be `scanned` or `scan_failed` (any verdict, also `clean` — an admin decision), grant active (`409 api_mode_mailbox_access_required`), no pending/in-progress action for the copy (`409 api_mode_remediation_in_progress`), current state not already that action (`409 api_mode_remediation_already_applied`); inserts a `pending` row (`trigger = admin`), copy `remediation_state = pending`; audit `api_mode.remediation_requested`. `hard_delete` is refused `422 api_mode_hard_delete_not_manual` (R-I2).

## 6. Alternatives considered

- **A new queue for remediation commands** (outbox → `email.remediation` → worker). Rejected for API-2: the decision already runs inside the RabbitMQ-driven, ledger-protected `copies` transaction, and actions need durable per-row back-off, leases, `Retry-After` pauses and retries over hours — a DB-claimed table (the feeds pattern) gives that with no topology change; a queue would still need the table for state and history.
- **Remediation records only in `quarantine_messages`.** Rejected: tags, hard deletes, simulated and skipped decisions and reversals are not quarantine entries; the quarantine state machine stays focused on releasable items.
- **A separate "mailbox quarantine" page and API.** Rejected by the brief ("the same quarantine pages … the existing release flow and approvals apply") and N9.
- **Policy re-validation on release for copies.** Rejected for API-2 by the product owner (policy evaluation on copies deferred); stored-verdict approval reasons keep the hard-block floor (second person) intact.
- **Graph immutable ids** (`Prefer: IdType="ImmutableId"`) so moves keep ids. Not chosen: API-1 feeds store regular ids; mixing id types needs translation calls. Storing the id the move returns plus the locate fallback is simpler; recorded as a later optimization.
- **Soft delete to Graph Deleted Items.** Rejected: the message would be user-visible and one click from the Inbox; Recoverable Items Deletions is recoverable but not browsable.
- **Gmail hard delete by requesting `https://mail.google.com/`.** Rejected: a broader scope than ADR-0099 consented, for an off-by-default action; Trash fallback recorded.
- **Default policy `detect_only` for everyone.** Not chosen: P1 says high-confidence threats are moved automatically by default; detect-only is a one-click preset recommended for new tenants (API2-1, revisable).
- **Partitioning `api_remediation_actions`.** Rejected (§3.1).
- **Re-deciding copies on late verdicts (sandbox revision 1).** Deferred to API-3 clawback (late signals).

## 11. ADR texts (WP1 creates the files; WP7 updates status lines to "Accepted (date, evidence)" after verification)

### ADR-0101: API-mode remediation policy and mailbox actions

**Context.** Brief scope 4: after-delivery remediation in Microsoft 365 / Google Workspace mailboxes driven by the verdict, idempotent, throttled per tenant, audited, reversible where possible; default P1. API-1 (ADR-0100) stores a verdict per mailbox copy and holds a write-capable mailbox grant (ADR-0099). Tenant policy evaluation on copies is deferred by the product owner.

**Decision.** (1) A remediation policy per organization with optional per-domain overrides (`api_remediation_policies`, document `api-remediation-policy/1`: ordered first-match rules over verdict, risk level, score and hard blocks → `move_quarantine | move_junk | tag | soft_delete | hard_delete | none`; mode `detect_only | enforce`); without a row the platform default P1 applies (high-confidence malware/phishing → quarantine folder, other malware/phishing and suspicious/BEC → tag, never hard delete). The decision function takes a reserved policy-evaluation input for a later step. (2) Decisions are taken in the mailbox-worker `copies` transaction; actions are rows of `api_remediation_actions` (unique `action_key` per copy, action and generation) executed by the new `remediate` role through the API-1 clients with the per-connection budgets and the shared `Retry-After` pause, back-off and bounded attempts; every executed action is audited. (3) Graph: hidden quarantine folder, `junkemail`, categories, `recoverableitemsdeletions`, `permanentDelete`; Gmail: hidden label, `SPAM`, labels, Trash; hard delete needs `API_MODE_HARD_DELETE_ENABLED` and an explicit rule, falls back to Trash on Gmail (`gmail.modify`), is never manual. (4) Hybrid copies with inline verdict authority are never remediated automatically. (5) Remediation state on the copy; counters, health checks (`remediation.*`) and the existing `api_mode_unhealthy` alert; topology unchanged.

**Consequences.** Two tables, one worker role, no new queue or permission; detect-only gives a safe start; a bad policy is reversible (except hard delete, off by default).

**Alternatives.** A command queue; remediation records only as quarantine entries; immutable Graph ids; Deleted Items for soft delete; requesting the full Gmail scope; detect-only as the universal default (design §6).

### ADR-0102: Mailbox-located quarantine entries; release as provider restore

**Context.** Brief scope 5: API-mode remediations appear in the existing quarantine pages with their location, and the existing release flow and approvals apply. ADR-0046 makes the policy-engine evaluation transaction the only writer of quarantine entries; ADR-0047 releases entries through the policy-engine executor after policy re-validation and redelivery; ADR-0098 (7)/note 35 N1 keep copies away from quarantine release. Copies have no policy evaluation and end `journaled`.

**Decision.** (1) `quarantine_messages.location` (`gateway` default, `mailbox`) with the mailbox container and links to the copy, mailbox and remediation action; `origin = api_remediation`; for mailbox entries `lifecycle_round` holds the copy's remediation generation. (2) **Supersedes ADR-0046 decision 1 in part:** the mailbox-worker writes mailbox entries when a quarantine-folder, Junk or soft-delete action succeeded, and expires them (no lifecycle edge, no mailbox change, no object purge). (3) **Supersedes ADR-0047 in part:** releasing a mailbox entry is a restore to the Inbox executed by the mailbox-worker; the pre-check and the executor's re-check use `decideMailboxRestore` over stored facts (hard blocks → approval or refusal per tenant setting; scan failure → approval) instead of policy re-validation; approvals, separation of duties, end-user bounds, Idempotency-Keys and audit are unchanged. (4) **Supersedes ADR-0098 (7) / N1 in part:** a copy can be "released" only as such a provider restore; copies are still never delivered, reinjected, policy-evaluated or rescanned. (5) The policy-engine sweeper, disposal and executor handle `location = gateway` only.

**Consequences.** One quarantine for both locations; admins and users act on mailbox threats where they already work; policy-engine changes are guards only; mailbox entries survive their expiry in the mailbox container.

**Alternatives.** A separate mailbox quarantine; policy re-validation for copies (deferred by the product owner); entries for tags/hard deletes (design §6).

### 15.2 Closer round (2026-11-27, lead engineer)

The three medium review findings were checked against the code. All three were real and are fixed, with tests.

1. **Copy left `pending` after a failed or cancelled action** (`apps/mailbox-worker/src/remediation/outcomes.ts`). `fail()` only reset the copy for remediations, and `cancel()` never touched it, so a failed `remove_tag`, or an api-queued action the worker cancelled, left the copy `pending` with nothing queued. Fix: `settleCopy` runs in the outcome transaction for every `failed` and `cancelled` outcome, but only when the copy's `last_action_id` is this action (or, for a failed remediation, is still unset). A failed remediation of the current generation → `failed`. Otherwise the copy gets the state its history implies: a succeeded unreversed remediation of the current generation → `remediated`; else after a restore → `restored` (with the reversed action); else the latest other `failed`/`simulated`/`skipped` row; else `none`. `succeed`, `fail` and `cancel` now lock the copy row before the action's CAS, which is the api's lock order (copy, then action). Tests: worker integration "a failed remove_tag gives the copy back remediated" and "an admin action of an older generation is cancelled".
2. **Stale-generation retry** (`apps/api/src/modules/api-mode/domain/remediation-rules.ts`, `executor.ts`). `decideRetry` now refuses a row whose generation differs from the copy's (`409 api_mode_remediation_not_retryable`, `cause: stale_generation`). `lockRemediation` locks the copy, then the action row, and returns the copy's generation. The worker's precheck cancels a remediation of an older generation for every trigger, before any provider call; the `last_action_id`/`restored` checks stay policy-only. Tests: rules unit, service unit and api integration (`api-mode-remediation.test.ts`, stale retry refused, copy unchanged), plus the worker integration test above. The OpenAPI description, snapshot, portal client and portal error text were updated.
3. **Endless re-claim when the outcome write throws** (`claims.ts`, `executor.ts`). Re-claiming an expired `in_progress` lease now counts one attempt (`attempts + IF(status = 'in_progress', 1, 0)`, placed before the `status` assignment because MySQL applies SET assignments left to right). `tick()` records the thrown error's code in `last_error_code` on the claim it still holds (best effort, CAS). A claimed row whose `attempts` reached `API_MODE_REMEDIATION_MAX_ATTEMPTS` is failed with the new result/failure code `internal_error` (vocabulary, contracts §37, portal text) before any provider call. Test: worker integration "an outcome write that keeps throwing is counted per lease and ends failed internal_error".
