## 0. Scope in one paragraph

**Part A (PO-D2, parity).** Every API-mode copy that has copy verdict authority is evaluated against the tenant's **5.2 policies** (custom rules, allow/block lists expressed as rules, the DLP binding, BEC facts, the platform default and the strictness floor) by the **same evaluator, input builder, snapshot and fact readers** the policy-engine uses, extracted into `@email-gateway/policy-runtime` and run by the mailbox-worker `copies` role inside the existing ledger transaction of `mail.message.copy_scanned.v1`, in **detect mode**: the evaluation is stored (`policy_execution_logs.evaluation_mode = detect`), but nothing is delivered, held, bounced, rewritten, archived or re-routed. The evaluation result becomes the **policy lane** of the API-2 remediation decision (the reserved `policyOutcome`): policy dispositions map to mailbox actions through the tenant's remediation policy (`policyMapping`: quarantine → quarantine folder, require approval → quarantine folder as a review entry, reject → quarantine folder, tag/warn → tag by default), the stronger of the verdict lane and the policy lane wins, a tenant allow-override suppresses verdict-only remediation exactly as inline, and actions that have no post-delivery meaning are recorded as not applicable with a reason. Hybrid copies with inline verdict authority are never evaluated or acted on again. **Outbound** journal copies are evaluated too (DLP detect + alert): a detection is recorded on the sender's mailbox as an `outbound` copy that is never remediated; internal copies are remediated through the API-2/API-3 paths. Detections raise **`threat_detected`** and the new **`dlp_detected`** alerts and the new public webhook types **`mailbox.threat.detected`** and **`mailbox.dlp.detected`** (protection mode in the payload) through the existing webhook-worker fanout and notification-worker, fed by one new internal event `mail.message.copy_detected.v1`. A **Protection by mode** page explains what inline, API and hybrid cover and shows each domain's actual coverage. **Part B (PO-D1, onboarding).** The add-domain wizard, when the mode is `api`, shows only the steps that apply: the TXT ownership record (or **automatic ownership verification through the organization's bound Microsoft 365 / Google Workspace connection**), **Connect mailboxes** (the 8.2 consent flow, mailbox remediation profile), **Intake** (journal copy and/or change feeds), **Which mailboxes** (all, policy-directory departments or selected mailboxes), **Threat action** (remediation preset; detect-only for 7 days by default with a reminder or an automatic switch), **Review and activate** with a live first-copy check and troubleshooting hints. Hybrid shows the inline steps plus the API steps; the inline wizard is unchanged. The domain detail page shows mode-relevant sections only.

### 1.2 Gaps and conflicts found

1. **ADR-0098 decision 5 and 7 / note 35 N1:** copies get "no policy evaluation" and "never reach the policy engine", "no `threat_detected` alert". → ADR-0105 supersedes in part: copies are policy-evaluated in **detect mode** (no lifecycle edge, no delivery, no hold, no gateway quarantine entry, no policy copy, no `mail.policy.decided.v1`); every other N1 guarantee stays. ADR-0106 supersedes the alert part.
2. **ADR-0044 (policy runs in the policy-engine consumer only).** → ADR-0105: detect evaluations of copies run in the mailbox-worker with the shared `@email-gateway/policy-runtime`; inline evaluation, gating and disposition stay with the policy-engine.
3. **ADR-0101 decision 1 / R2.2:** the remediation decision returns `none` for a clean verdict before any rule, and the reserved key is `when.policyDispositions`. A tenant rule can decide on a clean-verdict message (a block-list sender). → Two lanes; the policy lane runs whatever the verdict; the reserved rule key is replaced by a document-level `policyMapping` (so existing stored policies get the default mapping without an edit).
4. **ADR-0104 decision 1:** outbound-only journal messages are never recorded. Outbound DLP needs a record the tenant can see and alert on. → ADR-0105: an **outbound detection** is recorded on the sender's mailbox (`direction = outbound`) only when the evaluation is a detection; it is never remediated, never a clawback target, never a coverage sighting.
5. **ADR-0054 decision 8 ("DLP incidents … not an event")** and strict v1 data schemas: adding a mode field or a stage value to `email.threat.detected` would break strict receivers. → ADR-0106: two **new public types** at version 1; `email.threat.detected` v1 is unchanged (inline; mode implied); a copy's sandbox verdict moves from `email.threat.detected` to `mailbox.threat.detected` (stage `sandbox`) — the former was an N1 leak.
6. **Step 2.1 D4 / 8.2 I6 ("gateway domain ownership stays TXT-only") and ADR-0076 decision 1 (binding proof).** → ADR-0107: a domain may be proven by its listing as verified in the organization's **bound** provider tenant; provider-proven domains never count as binding proof; links accept `verified` domains.
7. **Copies handler transaction budget.** Policy evaluation adds the 5.2 reads (≈ 12 indexed reads + snapshot on a generation change). The handler uses `TX_TIMEOUT_MS` of the mailbox-worker; the 4.2 §6 rule requires ≥ 120 s budgets for deciding reads. → WP3 verifies `TX_TIMEOUT_MS ≥ 120 000` for the copies transaction (raise it if lower) and keeps the evaluation inside the ledger transaction.
8. **No mailbox scope exists:** every mailbox of an api/hybrid domain is in scope. → `api_mailboxes.scope_state` + per-domain scope (B6); out-of-scope copies are recorded for visibility, never remediated or fed.
9. **The wizard's provider ownership needs a worker:** the api never decrypts provider grants (ADR-0077). → The integration-worker records the provider's answer; the api applies the ownership win in its existing scheduler (B3).

## 2. Program position and invariants

Note 35 N1–N9 (N1 as amended by ADR-0102 and now ADR-0105), note 36 R-I1–R-I6 (R-I2, R-I3 as amended by ADR-0103), note 37 C-I1–C-I7 hold. API-4 adds:

- **P-I1 Detect means detect.** A copy evaluation never applies a lifecycle edge, never writes `email_messages.final_verdict`/`final_action`, a delivery approval, a gateway quarantine entry, a policy copy object, `mail.policy.decided.v1`, `mail.message.archive_requested.v1` or a sender non-delivery notice. Its only effects are the `policy_execution_logs` detect row, copy columns, remediation action rows through the API-2 engine, ALERT requests and the detection event.
- **P-I2 Same engine, same facts.** Detect evaluations use `@email-gateway/policy-runtime` + `@email-gateway/policy-dsl` exactly as the policy-engine does (same snapshot generation rule, same floor, same per-recipient evaluation); a fixture evaluated inline and as a copy yields the same `inputSha256` modulo the trigger and the same disposition (parity test, §10.1).
- **P-I3 Inline decides first (unchanged R-I3).** Copies with `verdict_authority = inline` are never policy-evaluated, never remediated automatically and never produce a detection event or alert (the inline path already did).
- **P-I4 Never weaker than API-2 by accident.** The policy lane can only add or strengthen an action; the only weakening is a tenant **allow override** on a level-only verdict (the same rule the inline floor enforces); a policy evaluation failure falls back to the verdict lane (API-2 behaviour) and is counted and alerted through health.
- **P-I5 Outbound is never touched in a mailbox.** Outbound detection copies have no remediation action, no quarantine entry, no clawback target and do not count as coverage.
- **P-I6 Ownership is never weakened.** A provider-proven domain must be listed as verified by a tenant that is already **bound** to the organization through a DNS-TXT-proven domain; "first to verify wins" and `verified_name` uniqueness apply unchanged; provider-proven domains never prove a tenant binding.
- **P-I7 Tenant from trusted context; content-free state.** Every new route takes the organization from the principal (foreign ids `404`); workers echo-check the organization on every read; events, alerts and webhooks carry ids, codes, counts and the protection mode only.

## 4. Decisions — part A (PO-D2: same protection for API-mode mail)

### A1. Where detect evaluation runs (ADR-0105)

In the **mailbox-worker `copies` role**, inside the existing ledger transaction of `mail.message.copy_scanned.v1`, after the copy rows of the message are written and **before** the remediation decision, once per registry copy message. Reasons (alternatives in §7): the decision is atomic with the evaluation (no second event, no ordering race between two queues, no "decide later" state), no topology change for the evaluation itself, no dependency of copy recording on the policy-engine's availability, and the evaluator is the same library and runtime code (P-I2).

Skips (the copy rows get `policy_state` and the decision runs with `policyOutcome: null`, i.e. API-2 behaviour):

| Condition                                                                                                  | `policy_state`                                                                                                                 |
| ---------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| Platform switch `API_MODE_POLICY_EVALUATION_ENABLED=false` or organization `policy_evaluation_enabled = 0` | `disabled`                                                                                                                     |
| Every recorded copy of the message has `verdict_authority = inline` (hybrid)                               | `inline` (the copy's `policy_disposition` = the linked gateway message's latest inline evaluation's disposition, display only) |
| Outcome `parse_failed` or copy status `too_large`; report-mailbox copies (C-I5)                            | `not_applicable`                                                                                                               |
| `PolicyInputError` (malformed rows) or an exception of the evaluator                                       | `failed` (counter `policy_errors`, metric, error log with message public id; never dead-letters the copy event)                |
| Otherwise                                                                                                  | `evaluated`                                                                                                                    |

An `InconsistentPolicyReadError` (4.2 §6 wrong read) is **retryable**: the whole ledger transaction rolls back and the event is redelivered (nothing partial).

### A2. `@email-gateway/policy-runtime` (new package, WP2)

Moved **unchanged in behaviour** from `apps/policy-engine/src/evaluation`: `FactsRepository` (+ `RoundRef`, `RoundFacts`), `SnapshotRepository` + snapshot LRU cache, `DirectoryRepository` (+ `EMPTY_DIRECTORY`, `DirectoryMaps`), `AtoFactsRepository`, `buildInputWithDirectory`, `errors.ts` (`InconsistencySink`, `wrongRead`, the inconsistent-read error, `POLICY_INPUT_INVALID`), with their unit tests. `apps/policy-engine` imports them from the package (no local copies left; its suites pass with unchanged assertions). New in the package:

- `evaluateCopyRound(tx, deps, ref)` → `{ status: 'evaluated', input, perRecipient: PerRecipientEvaluation, meta: { generation, snapshotSha256, platformDefaultId, policyVersions, invalidVersions, cache }, durationUs } | { status: 'failed', code }`: reads the generation and snapshot on the writer (same LRU rule as P12), the round facts (`trigger` = `scanned`/`scan_failed` from the copy outcome, `scanId` from the event, `round` = the message's lifecycle round, `olderRoundAllowed: false`), the directory of the snapshot's references, the sender's ATO facts for outbound/internal (same `AtoFactsSource` rule as 8.4 D23), builds the input and runs `evaluatePolicyPerRecipient`. `PolicyInputError` and evaluator exceptions → `failed` with a code; inconsistent reads throw.
- `policyOutcomeOf(evaluation, rcptSeq | null)` → the `PolicyOutcomeFacts` of mailbox-api (A4): `resultForRecipient` for a recipient (journal copies), the message-level result for `null` (feed copies have one recipient; outbound uses the message level).
- `detectRowData(evaluation, ref, now)` → the `policy_execution_logs` create data from `evaluationResultToRow` + `perRecipientToRowFields` with `evaluationMode: 'detect'`, `deliveredObject: 'none'`, `delivery: null`, `objectKey: null`, `action` = `lifecycleOutcome(result, direction).finalAction` (recorded, never applied), action `status` from `postDeliveryStatusOf` (A5). Typed against the Prisma client WP1 generates (WP2 may type the new field loosely until WP1 lands; WP3 compiles it against the real client).
- Dependencies: `@email-gateway/database`, `@email-gateway/policy-dsl`, `@email-gateway/mailbox-api` (types and A5 vocabulary only), `@email-gateway/logger`. No Nest, no RabbitMQ.

Config (mailbox-worker reads existing keys): `POLICY_PLATFORM_DEFAULT`, `POLICY_SNAPSHOT_CACHE_MAX_ENTRIES` (same defaults and validation as the policy-engine).

### A3. Copy evaluation in the copies handler (WP3)

1. **Journal copies:** after `recordJournalCopies` has written the copy rows (not duplicates), if at least one recorded copy has copy authority and A1 does not skip: `evaluateCopyRound` once; insert the detect row with `INSERT … ` on the unique `(message_id, evaluation_seq, received_at)` — a duplicate (redelivery after a crash cannot happen inside one ledger transaction, but a manual replay can) reads and reuses the stored row's result instead of re-evaluating. For each recorded copy with copy authority: the recipient row (`email_recipients`, the mailbox's primary or alias address, lowest `rcpt_seq`, R9.1 rule) → `policyOutcomeOf(evaluation, rcptSeq)` → copy columns `policy_state = evaluated`, `policy_disposition`, `policy_tagged`, `dlp_action` (the message's `dlp_scan_results.action` when the DLP final is definite) → remediation decision with that outcome (A4).
2. **Feed copies (`finalizeFeedCopies`):** the same with `rcptSeq` = the single recipient row.
3. **Counters and metrics** (after commit): `policy_evaluations` / `policy_errors` per API connection; `api_mode_policy_evaluations_total{result="evaluated|failed|disabled|inline|not_applicable"}`, histogram `api_mode_policy_evaluation_seconds`.
4. **Report-mailbox copies** are not evaluated (C-I5); clawback re-decisions (C3.2) keep `policyOutcome: null` (late signals are verdict facts; a copy's stored policy outcome is not re-applied by a clawback).

### A4. The policy lane of the remediation decision (mailbox-api, WP2; ADR-0105 supersedes ADR-0101 decision 1 in part)

**A4.1 Input.** `RemediationInput.policyOutcome: PolicyOutcomeFacts | null`:

```text
PolicyOutcomeFacts = {
  disposition: 'allow'|'require_approval'|'quarantine'|'reject',
  tagged: boolean,                     // TAG or WARN applies with disposition allow
  overrideApplied: boolean,            // P9 step 6 override of the recommendation
  decisionSource: 'tenant_rule'|'platform_default'|'floor',
  decisiveRuleRef: string | null,      // '<policyPublicId>#<versionNo>/<ruleId>'
  floorReasons: string[] (≤ 8),        // e.g. policy.floor.dlp_block
  dlpAction: 'allow'|'alert'|'require_approval'|'quarantine'|'block' | null,
  actionTypes: PolicyActionType[] (unique, ≤ 9),
  recommendationOnly?: boolean         // §15.8 review fix: only restates the platform default's risk recommendation
}
```

`copy.direction` gains `outbound`; `context.mailboxInScope?: boolean` (absent = true, B6).

**A4.2 Document.** `api-remediation-policy/1` gains an optional, strict `policyMapping` object (additive; documents without it stay valid and get the default):

| Key                | Allowed values                                               | Default (API4-3)  |
| ------------------ | ------------------------------------------------------------ | ----------------- |
| `quarantine`       | `move_quarantine`, `move_junk`, `soft_delete`, `tag`, `none` | `move_quarantine` |
| `require_approval` | same                                                         | `move_quarantine` |
| `reject`           | same                                                         | `move_quarantine` |
| `allow_tagged`     | `tag`, `none`                                                | `tag`             |

`hard_delete` is never allowed in `policyMapping` (R-I2). `when.policyDispositions` stays refused, now with the issue code `use_policy_mapping` (the reserved hook is realized by `policyMapping`). Presets (`P1`, `DETECT_ONLY_START`, `STRICT`) carry no `policyMapping` (default applies).

**A4.3 Algorithm** (`decideRemediation`, pure, table-tested; strength order `none < tag < move_junk < move_quarantine < soft_delete < hard_delete`, the clawback order of C5.3, one shared constant):

1. `copy.status !== 'scanned'` → `none` (unchanged; scan-failed copies are never remediated, `remediateScanFailures` stays reserved).
2. **Verdict lane:** verdict not in (`clean`, `unknown`, null) → first matching rule (R2.2) → its action (or `none`).
3. **Policy lane:** `policyOutcome` present → `quarantine`/`require_approval`/`reject` → the mapped action; `allow` + `tagged` → `allow_tagged` mapping; `allow` → `none`. **Review fix (§15.8):** an outcome that only restates the platform default's 5.1 risk recommendation (`recommendationOnly`: decision source `platform_default`, not a deterministic BEC hold, no floor reason binding at that disposition; for `allow`, only the platform risk TAG applies) feeds no policy lane — the verdict lane already turns that recommendation into a mailbox action through the tenant's verdict rules. Tenant rules (`tenant_rule`), the raised floor (`floor`) and a floor reason binding at the same level (DLP, hard block, missing data) still feed it.
4. **Allow override (P-I4):** `policyOutcome.disposition = allow` and `overrideApplied` and `decisionSource = tenant_rule` → the verdict lane is suppressed: if the verdict lane had an action → `skip policy_allow_override` (recorded, visible), else `none`. (The 5.2 floor only lets an override through on a level-only recommendation, so hard blocks are never suppressed.)
5. Final action = the stronger lane (ties → verdict lane); no action → `none`. The winning lane's id: a verdict rule id, or the synthetic `policy-mapping:<key>`.
6. `copy.direction = outbound` → `skip outbound_not_remediable` (P-I5).
7. Then the existing order: inline authority → `skip inline_authority`; domain not api/hybrid, mailbox disabled/deleted **or `mailboxInScope = false`** → `skip out_of_scope`; internal while internal mail is off → `skip internal_mail_disabled`; hard delete without the setting → `skip hard_delete_disabled`; detect-only → `act` simulated; paused → `skip remediation_paused`; no grant → `skip no_mailbox_access`; else `act`.

New skip reasons: `outbound_not_remediable`, `policy_allow_override` (vocabulary §5).

**A4.4 Decision record `api-remediation-decision/2`** (written from API-4 on; readers accept `/1` and `/2` through one exported zod union): `/1` fields + `policyOutcome: PolicyOutcomeFacts | null` + `lanes: { verdict: { ruleId, action } | null, policy: { key: 'quarantine'|'require_approval'|'reject'|'allow_tagged', action } | null, winner: 'verdict'|'policy'|null, suppressedBy: 'policy_allow_override' | null }` + `postDelivery: [{ type, status, reason }]` (A5, ≤ 9).

### A6. Outbound and internal copies (ADR-0105 supersedes ADR-0104 decision 1 in part; WP3)

1. **Internal copies** (recorded since API-3 when `internal_mail_enabled`) are evaluated like inbound copies; the policy lane (incl. the DLP floor: `block → reject`, `quarantine`, `require_approval`, `alert → tag`) drives API-2 remediation of the recipient mailboxes (A4).
2. **Outbound** journal messages (no API-side recipient, org-side sender; today `outbound_only`, metric only): when `outbound_detection_enabled` and the organization is API-active, the handler evaluates the message (A3) and records an **outbound detection copy** only when it is a detection (A8.1): one `api_message_copies` row for the **sender's mailbox** (resolved by the header-From addr-spec, else the envelope sender, through `api_mailbox_addresses`; unknown → `discovered` mailbox under the intake source's connection, as journal recipients are), `direction = outbound`, `source = journal`, policy columns, verdict, risk, lag `NULL` (no delivery into a mailbox), `seen_journal = 1`, no dedupe claim on the sender mailbox's `(mailbox, hash)` key when an inbound/internal copy of the same message already exists for that mailbox (then nothing is recorded: the sender was also a recipient). Not a coverage sighting (`journal_last_seen_at` unchanged). Remediation decision → `skip outbound_not_remediable` (row recorded for history). Counter `outbound_detections`.
3. **Hybrid outbound:** when a gateway message (`ingest_source = gateway`, `direction = outbound`) with the same `message_id_key` exists in the hybrid link window, the gateway already enforced outbound policy inline → no outbound copy (P-I3).
4. **Clawback and coverage:** clawback criteria directions stay `inbound`/`internal` (C4.1), so outbound copies are never targets (WP3 asserts the search filters `direction IN (…)`); coverage queries ignore outbound copies.
5. **Incidents:** no security incident is created (the incident categories are `account_takeover` only; a DLP incident category is an ATP-4 item, API4-7).

### B6. Which mailboxes: scope (api WP4, mailbox-worker WP3, mailbox-api WP2)

- Document `api-mode-scope/1` (strict zod in mailbox-api): `{ kind: 'all' } | { kind: 'departments', departmentIds: uuid[1..API_MODE_SCOPE_MAX_DEPARTMENTS (20)] } | { kind: 'mailboxes' }`.
- `GET /api-mode/domains/{domainId}/scope` (`remediation:read`): kind, departments (id, name, member count), selected mailbox count, in-scope/excluded counts, `rowVersion`. `PUT /api-mode/domains/{domainId}/scope` (`remediation:write`, Idempotency-Key, CAS `expectedRowVersion` (null = create), rate class `sensitive`) `{ scope, mailboxIds?: uuid[] (only for kind mailboxes, ≤ API_MODE_SCOPE_MAX_MAILBOXES 5 000, mailboxes of this domain), reason }`: upserts `api_mode_domain_settings`, sets `api_mailboxes.scope_selected` for the domain (clear + set in one transaction), `scope_recompute_requested_at = now`; departments must belong to the organization (`422 api_mode_scope_department_invalid`); domain must be effective api/hybrid (`409 api_mode_scope_domain_not_api`); audit `api_mode.scope_updated` `{ domainId, from: kind, to: kind, departments: count, mailboxes: count, reason }`.
- **Evaluation** (mailbox-worker health leader each tick for domains with `scope_recompute_requested_at` set and every `API_MODE_SCOPE_REFRESH_MINUTES` (15) for `departments` domains): `all` → every mailbox `in_scope`; `mailboxes` → `scope_selected`; `departments` → in scope when the primary or an alias address is a member address of a listed department or belongs to an active user who is a member (P5 resolution rules, bounded batches of 1 000 mailboxes); writes `scope_state`, `scope_evaluated_at`; clears the request. New mailboxes (inventory or journal discovery) get `excluded` immediately for `mailboxes` domains, `in_scope` otherwise (departments: protected until the next evaluation — fail-safe toward protection, API4-10).
- **Effects of `excluded`:** copies still recorded (visibility), decision `skip out_of_scope` (`mailboxInScope = false`, read live for `all`/`mailboxes`, stored state for `departments`), feeds stop for the mailbox (`feed_status = off`, cursor cleared; resumed without backfill when back in scope), coverage `out_of_scope`, clawback targets skipped `out_of_scope` (shared decision context), not counted in detection events.
- Directory: deleting a department referenced by a scope → `409 department_in_use` (reference `api_mode_scope`, WP4 directory module).
- Provider groups (Microsoft 365 / Google groups) are not a scope kind in this step (they need group-read consent the mailbox profile does not request; API4-11).

### B7. Threat action and the detect-only start period (api WP4, mailbox-worker WP3)

## 7. Alternatives considered

- **Detect evaluation in the policy-engine** (a new queue bound to `copy_scanned.v1`, an evaluation event back to the mailbox-worker). Rejected: two consumers of one scan would race (the decision needs both the copy rows and the evaluation), the mailbox-worker would need a "decision pending" state with a timeout fallback, copy recording would depend on a second service's availability, and the topology would grow by a queue and two bindings. The policy-engine's role (inline gating and dispositions) stays focused; the evaluation code is shared, not duplicated.
- **A third copy of the fact reader in the mailbox-worker.** Rejected (N9, P-I2): parity would drift; extraction to `policy-runtime` keeps one implementation.
- **Reusing `mail.policy.decided.v1` for copies.** Rejected: the delivery-worker, archive-worker and webhook fanout consume it with gateway semantics (P-I1).
- **Adding `protectionMode` / a `post_delivery` stage to `email.threat.detected` v1.** Rejected: strict v1 receivers would break (ADR-0054 requires v2 for that); new types follow ADR-0054's additive rule. A `version 2` of the existing type was rejected as heavier for receivers than one more subscription.
- **First-match over one rule list for verdicts and policy dispositions** (the reserved `when.policyDispositions`). Rejected: rule order would decide whether a tenant `TAG` weakens a malware quarantine; two lanes with "stronger wins" are order-independent, and a document-level mapping applies to every stored policy without edits.
- **Remediating outbound mail in the sender's Sent Items.** Rejected: the message has left; removing the sender's copy hides evidence (P-I5).
- **Ownership by provider listing without a bound tenant** (any consented tenant). Rejected: consent of the shared platform app proves nothing about the tenant's owner (ADR-0076 rationale).
- **Scope by provider groups.** Deferred: needs `GroupMember.Read.All` / `admin.directory.group.member.readonly`, i.e. a profile change and re-consent for every tenant.
- **Auto-enforce after 7 days by default.** Not chosen: a human should confirm the switch from simulated to real mailbox changes; offered as an option.
- **A stored wizard step pointer.** Rejected as in 8.2 (drifts from reality); server-computed state.

### ADR-0105: Policy evaluation of API-mode copies (detect mode) and the policy lane of remediation

**Context.** PO-D2 (decided 2026-11-27): API-mode mail must get the same tenant policy protection as inline mail (DLP, BEC, custom rules, allow/block lists). ADR-0098 (5, 7) keeps copies away from policy evaluation; ADR-0044 places policy evaluation in the policy-engine consumer; ADR-0101 (1) reserved a policy input; ADR-0104 (1) never records outbound-only journal messages.

**Decision.** (1) **Supersedes ADR-0098 decisions 5 and 7 in part and ADR-0044 in part:** copies with copy verdict authority are evaluated by the 5.2 evaluator with the policy-engine's runtime code (extracted to `@email-gateway/policy-runtime`) in the mailbox-worker `copies` transaction, in detect mode: stored as `policy_execution_logs` rows with `evaluation_mode = detect`; no lifecycle edge, delivery, hold, gateway quarantine entry, policy copy, `mail.policy.decided.v1`, archive request or sender notice. Organization setting and platform kill switch; failures fall back to the verdict-only decision. (2) **Supersedes ADR-0101 decision 1 in part:** the remediation decision has a verdict lane (unchanged rules) and a policy lane (document-level `policyMapping`, defaults quarantine/require-approval/reject → quarantine folder, tagged allow → tag; never hard delete); the stronger action wins; a tenant allow override suppresses verdict-only remediation; decision record `api-remediation-decision/2`; a policy `require_approval` creates a `review` mailbox entry. Post-delivery-meaningless actions are recorded as not applicable with reasons. (3) **Supersedes ADR-0104 decision 1 in part:** outbound journal messages are evaluated; a detection is recorded on the sender's mailbox as an `outbound` copy that is never remediated, never a clawback target and never a coverage sighting. (4) Hybrid inline-authority copies are never evaluated or acted on.

**Consequences.** Inline-equivalent protection for API mode with one evaluator; a library extraction in the policy-engine; one migration; more evaluation rows; tenants can tune the mapping per disposition.

**Alternatives.** Evaluation in the policy-engine with a second event; a third fact reader; reusing `mail.policy.decided.v1`; one first-match rule list (design §7).

### ADR-0106: API-mode detections in alerts and webhooks

**Context.** PO-D2 asks for `threat_detected` (and DLP/BEC) alerts and webhooks for API-mode detections with the protection mode where contracts allow. ADR-0054: strict v1 types, breaking changes need v2, additions are new types; DLP incidents are not events (decision 8). A copy's sandbox verdict currently yields `email.threat.detected` (an N1 leak).

**Decision.** (1) Internal event `mail.message.copy_detected.v1` from the mailbox-worker per copy message with a detection (topology v19: bound to `email.webhooks`). (2) New public types `mailbox.threat.detected` and `mailbox.dlp.detected` (catalogue v1, version 1, metadata only, protection mode in `data`); `email.threat.detected` v1 unchanged and no longer fed by sandbox verdicts of copies. **Supersedes ADR-0054 decision 8 in part** (DLP detections of API-mode copies are events). (3) Alerts: `threat_detected` also for API-mode detections (post-delivery template); new kind `dlp_detected` (recipients `dlp:read`, tenant settings, opt-out); new kind `api_mode_detect_only_ended`. (4) Policy ALERT actions of copies use `mail.policy.notification_requested.v1` with `evaluationMode: detect`. (5) Hybrid inline-authority copies produce no event.

**Consequences.** Receivers subscribe to the new types explicitly; no breaking change; one more binding.

**Alternatives.** Mode field or stage value in v1; a v2 of `email.threat.detected`; reusing `mail.policy.decided.v1` (design §7).

### ADR-0107: API-mode onboarding: ownership through a bound provider tenant, mailbox scope and the detect-only start

**Context.** PO-D1 (decided 2026-11-27, note 35 §17 feedback): the API-mode wizard should hide inapplicable steps, show only the TXT ownership record or verify ownership automatically through the connected provider tenant, and add mailbox-scope and threat-action steps. Step 2.1 D4 and 8.2 I6 keep gateway ownership TXT-only; ADR-0076 (1) binds a tenant on TXT-verified, gateway-`active` linked domains; links need `active`; ADR-0098 (3) defines the API-1 wizard.

**Decision.** (1) **Supersedes step 2.1 D4 / 8.2 I6 in part:** a pending domain may be proven by its verified listing (verified for Email) in a provider tenant **already bound** to the organization, checked by the integration-worker with the read-only mail-flow grant and won by the api's existing first-to-verify-wins transaction (`domains.ownership_method = provider_tenant`). (2) **Supersedes ADR-0076 decision 1 in part:** tenant binding counts only DNS-TXT-proven linked domains, in `verified` or `active` status; links accept `verified` domains. (3) Per-domain mailbox scope (`all`, policy-directory departments, selected mailboxes); out-of-scope mailboxes are recorded but not remediated or fed. (4) Remediation policies may carry a detect-only period with a reminder (default) or an automatic switch to enforce; the wizard defaults to 7 days detect-only with a reminder. (5) **Supersedes ADR-0098 decision 3:** mode-specific wizard step lists (inline unchanged; api hides inapplicable steps; hybrid = inline + API steps) with a server-computed onboarding state and a live first-copy check.

**Consequences.** Second and later domains of a bound tenant onboard without DNS changes; ownership remains globally unique and auditable; tenants can stage protection.

**Alternatives.** Unbound-tenant listings; provider-group scopes; auto-enforce by default; a stored wizard pointer (design §7).

### 15.8 Review fix (closing round, 2026-11-27)

**Finding (medium, confirmed).** The policy lane mapped every disposition of the detect evaluation, including `platform_default` dispositions that only restate the 5.1 risk recommendation (`pol-default/1`: tag → allow + platform tag, quarantine → quarantine, block → reject). The same risk signal was therefore counted twice — once by the tenant's verdict rules, once by the platform default through `policyMapping` — and the stronger lane won, so no verdict rule could be weaker than the inline default (STRICT `spam → move_junk` became `move_quarantine`; a clean copy with a `tag` recommendation was tagged). WP7 had hidden this by running the API-1..API-3 stack suites with `API_MODE_POLICY_EVALUATION_ENABLED=false` (§15.7 fix 1).

**Fix.** (1) `@email-gateway/mailbox-api`: `PolicyOutcomeFacts.recommendationOnly` (optional; absent in `/2` records written before the fix = `false`) and the pure `recommendationOnlyOf({ disposition, decisionSource, decisiveReason, floorDisposition, tagOrigins })`: for `allow`, true when every applying TAG/WARN has origin `platform_default`; otherwise true when the decision source is `platform_default`, the decisive reason is not `policy.default.bec_deterministic` (D2) and the floor does not bind at that disposition. `policyLaneOf` returns no lane for such an outcome. (2) `@email-gateway/policy-runtime` `policyOutcomeOf` and the mailbox-worker's `storedOutcomeOf` (A1 reuse of a stored detect row; split recipients use the recipient decision's first reason code) fill it; `tagOriginsOf` exported. (3) The api's `PolicyOutcomeViewSchema` exposes the optional `recommendationOnly` (OpenAPI snapshot and portal client regenerated). (4) Portal: the remediation-policy mapping fieldset and the wizard's threat-action explanation say that the platform default's risk recommendation alone is not mapped (the verdict rows decide it). (5) `tests/integration/support/api-mode.ts` no longer switches policy evaluation off for the API-1..API-3 stack suites; `api-mode.test.ts` case 1 now expects no `inline` row and exactly one `detect` row for the journal message (N1 as amended by ADR-0105). The mailbox-worker package harness keeps the switch off for its API-1..API-3 suites because they write no scanner round rows (§15.3 deviation a; a fixture limitation, not a behaviour switch). Tests: mailbox-api `recommendationOnlyOf` table (10 cases), `policyLaneOf` and 4 `decideRemediation` rows (STRICT spam → Junk kept, P1 spam none, platform risk tag not re-tagged, tenant rule still raises); policy-runtime `policyOutcomeOf` (platform-default spam quarantine, platform vs tenant TAG, tenant rule, raised DLP floor, DLP floor at the same level); mailbox-worker `storedOutcomeOf`; portal wizard explanation text.

**Consequence for open item 1 (§15.7).** A DLP quarantine decided at the same level as the platform default still feeds the policy lane (the floor binds), so case (3) of the parity suite is unchanged; its entry label (`policy` vs `dlp`) stays an architect decision.
