## 2. Decisions

### D1. API base path (ADR-0015)

- `apps/api/src/http/configure-api-app.ts` exports `configureApiApp(app, config)`: `app.setGlobalPrefix('api', { exclude: [{ path: 'health/live', method: RequestMethod.GET }, { path: 'health/ready', method: RequestMethod.GET }] })` and `app.set('trust proxy', config.HTTP_TRUST_PROXY)` on the Express instance. `main.ts` calls it inside `configure` (after the shared `configureHttpApp`), and every in-process test (e2e and API integration) calls `configureHttpApp` **and** `configureApiApp`.
- Business routes: `/api/v1/...`. `/v1/meta` → `/api/v1/meta`. Health stays `/health/live`, `/health/ready`. Swagger stays at `/docs`.
- Compose health checks, K8s probes and the portal's `fetchPlatformHealth` keep their paths; the portal gets a doc comment that business calls use `${API_INTERNAL_URL}/api/v1/...`. `tests/integration/services.test.ts` moves to `/api/v1/meta` and asserts `/v1/meta` is 404.

- **Controllers** only parse, validate and call a service (ADR-0002). **Services** hold logic. **Repositories** (`*.repository.ts`) are the only files under `apps/api/src/modules/**` that may import `PrismaService` or `PrismaReadService`; an ESLint rule enforces this (tests exempt). Services that need a transaction use `TransactionRunner.run(fn)` (in `apps/api/src/database/`, outside `modules/`) and pass the `Prisma.TransactionClient` to repository methods.
- **Reader vs writer:** list and usage endpoints use `PrismaReadService.client`. Mutations, read-after-write (return-after-create), everything inside a transaction, and **every authentication/authorization lookup** use the writer (`PrismaService`).
- **Serialization:** responses are built by explicit mapper functions; Prisma rows are never returned. External ids are `public_id` (organizations, users, api keys). Roles are addressed by `key`. Sessions by `family_id`. Log rows (login events) expose `id` as a decimal string. `bigint` never reaches `JSON.stringify`.

### D3. Validation, OpenAPI, pagination, errors

- **Validation:** zod schemas are the single source of truth for request bodies and queries. `ZodValidationPipe(schema)` returns `400` with `message: string[]` (`"<path>: <issue>"`), never echoing input values. Path ids are validated as UUID (`400` if malformed).
- **OpenAPI:** `zodToOpenApi(schema)` converts with `z.toJSONSchema(schema, { target: 'openapi-3.0' })` (fall back to the default draft and strip `$schema` if the installed zod lacks that target) and is used in `@ApiBody({ schema })`, `@ApiOkResponse({ schema })`, `@ApiQuery`. `http/openapi.ts` exports `buildOpenApiDocument(app)` and `setupOpenApi(app)` with `addBearerAuth({ type: 'http', scheme: 'bearer', bearerFormat: 'JWT' }, 'access-token')` and `addApiKey({ type: 'apiKey', in: 'header', name: 'X-API-Key' }, 'api-key')`. Every protected route has `@ApiBearerAuth('access-token')` (and `@ApiSecurity('api-key')` where API keys are accepted), `@ApiTags`, and documented `401/403/404/409/429` responses where they apply. A snapshot `docs/api/openapi.json` is generated by a test (§9).
- **Pagination:** `?limit=` (1–100, default 25) and `?cursor=` (opaque base64url of the last row's numeric id; `400` if undecodable). Lists are ordered by id descending (newest first). Response `{ "data": [...], "nextCursor": string | null }`.
- **Errors:** the existing `AllExceptionsFilter` shape. A resource of another tenant, a soft-deleted resource and a non-existent resource are all `404`. Missing permission is `403`. Missing/invalid credentials are `401` with the single message `Invalid credentials` on login, `Unauthorized` elsewhere. Limit exceeded, state conflicts and duplicates are `409`.

### D5. Sessions, refresh rotation and revocation

- A **session** is a refresh-token family (`family_id`, UUIDv4, exposed as `sessionId`). Each issued refresh token is one `user_sessions` row. Exactly one row of a live family has `revoked_at IS NULL`.
- **Login** inserts the first row: `expires_at = now + AUTH_REFRESH_TOKEN_TTL_SECONDS` (sliding idle, default 7 days), `absolute_expires_at = now + AUTH_SESSION_MAX_AGE_SECONDS` (default 30 days), `authenticated_at = now`, `mfa_authenticated`, IP and user agent (truncated to 512).
- **Refresh** (`POST /api/v1/auth/refresh`, writer, one transaction):
  1. Find the row by SHA-256 of the presented token. Not found → `401`.
  2. Row revoked with reason `rotated` → **reuse detected**: revoke every live row of the family (`reuse_detected`), deny-list the `sid`, write `audit_logs` `auth.refresh_token_reused` (org of the session, metadata: session id, IP), `401`.
  3. Row revoked for any other reason, `expires_at` or `absolute_expires_at` passed, user not active, or organization not active → `401` (no family revoke).
  4. Conditional update `revoked_at = now, revoked_reason = 'rotated' WHERE id = ? AND revoked_at IS NULL`. Zero rows → the token was rotated concurrently → treat as step 2 (reuse). Clients must serialize refreshes (documented).
  5. Insert the new row in the same family: `expires_at = min(now + idle TTL, absolute_expires_at)`, same `absolute_expires_at`, `authenticated_at`, `mfa_authenticated`; issue a new access token (re-evaluating `mfa_enroll`).
- **Revocation** (logout, logout-all, admin revoke, password change/reset, MFA enable, user suspension/deletion, org suspension/deletion): set `revoked_at`/`revoked_reason` on live rows and write deny entries `auth:revoked:<sid>` with TTL = access-token TTL + 60 s. The guard rejects deny-listed `sid`s, so revocation is effective immediately.
- **Purge:** `SessionPurgeService` (in the auth module) runs hourly on an `unref()`ed timer guarded by a KV lock (`jobs:auth-purge`, 55 min). In batches of 1,000 it deletes `user_sessions` with `expires_at < now − 1 day`, `user_tokens` with `expires_at < now − 7 days`, and `login_audit_logs` older than `AUTH_LOGIN_AUDIT_RETENTION_DAYS` (default 365). Disabled in tests by `AUTH_BACKGROUND_JOBS_ENABLED=false`.

### D6. Login, brute-force protection and login audit

Login identity is **(organization, email)** because email is unique per organization only. `POST /api/v1/auth/login { email, password, organization? }` where `organization` is an org **slug**. Without it, the account is resolved only if exactly one non-deleted user with that email exists in a non-deleted organization; otherwise the request behaves exactly like a wrong password (same status, body and timing), so nothing is disclosed. The slug only selects which account to authenticate; the tenant context comes from the authenticated result.

Order of checks (every path writes one `login_audit_logs` row; `failure_reason` values in brackets):

1. `@RateLimit` (per IP, 20/min) → `429` with `Retry-After`.
2. Per-IP failure block: KV counter `auth:fail:ip:<ip>` ≥ `AUTH_LOGIN_MAX_IP_FAILURES` (50) in the window (`AUTH_LOGIN_FAILURE_WINDOW_SECONDS`, 900) → `429` [outcome `rate_limited`, `ip_blocked`].
3. Resolve the account. Not found → dummy hash verify, increment IP counter, `401` [`unknown_account`; `organization_id` = the slug's org if it resolved, else NULL].
4. `locked_until > now` → `401` [outcome `locked`, `account_locked`], IP counter++ (no password verification; the lock is not revealed).
5. Verify password (dummy verify if `password_hash` is NULL [`not_activated`]). Wrong → account counter `auth:fail:acct:<userId>` (window 900 s) and `users.failed_login_count` ++, IP counter ++. When the account counter reaches `AUTH_LOGIN_MAX_ACCOUNT_FAILURES` (5): `locked_until = now + min(AUTH_LOCKOUT_BASE_SECONDS × 2^n, AUTH_LOCKOUT_MAX_SECONDS)` where `n` = KV `auth:lockouts:<userId>` (TTL 24 h, incremented per lockout), account counter reset, outcome `locked` [`lockout_started`]; otherwise outcome `failure` [`invalid_password`]. `401`.
6. User `status` not `active`, user soft-deleted, or organization `status` not `active` → `401` [`user_disabled` / `org_inactive`].
7. Rehash if needed. MFA enabled → create MFA challenge (D7), outcome `mfa_required`, `200 { mfaRequired: true, mfaToken, expiresIn }`.
8. Success: reset account counter, `failed_login_count = 0`, `locked_until = NULL`, `last_login_at = now`; create session; outcome `success`; `200` with the token response (§4.1).

All `401` responses use the body `Invalid credentials`. Redis (KV) unavailable → `503` (fail closed); the login is not attempted. Admin unlock (`PATCH /users/{id}/status` → `active`) clears `locked_until`, the DB counter and both KV counters.

`login_audit_logs` stores email attempted (lower-cased, max 320), IP, user agent; **never** passwords, tokens or codes. `LoginOutcome` gains `rate_limited` (appended, D10).

Other rate limits (`@RateLimit`, per IP unless noted): MFA verify 20/min; refresh 60/min; password forgot 5 per 15 min per IP and 3 per hour per email; reset, invitation accept/inspect, email verify 20 per 15 min; email verification resend 3 per hour per user. Client IP is `req.ip` with Express `trust proxy` = `HTTP_TRUST_PROXY` (hop count; `0` locally, `1` behind the ALB/ingress).

### D7. MFA

- **Login challenge:** `mfaToken` = `egt_…` random; KV `auth:mfa:<sha256>` → `{ userId, organizationId, ip }`, TTL 300 s, at most 5 attempts (KV counter), deleted on success or on the 5th failure. `POST /api/v1/auth/mfa/verify { mfaToken, code? , recoveryCode? }` (exactly one of the two). Failures write outcome `mfa_failure` and count toward the account lockout counter. Success creates the session with `mfa_authenticated = true`, `amr = ["pwd","otp"]`.
- **Enrollment** (authenticated user): `POST /auth/mfa/totp/setup` stores a new pending secret (encrypted) while `mfa_enabled = false` and returns `{ secret, otpauthUri }` (`409` if already enabled). `POST /auth/mfa/totp/enable { code }` verifies against the pending secret, sets `mfa_enabled = true`, `mfa_last_used_step`, creates 10 recovery codes (returned once), marks the **current** session row `mfa_authenticated = true`, revokes all **other** sessions, audits `auth.mfa_enabled`. `POST /auth/mfa/totp/disable { password, code }` (`409` while the org requires MFA). `POST /auth/mfa/recovery-codes { code }` regenerates.
- **Organization policy:** `organization_settings.mfa_required` (new, D10). When true and the user has no MFA, login succeeds with `mfaEnrollmentRequired: true` and an access token carrying `mfa_enroll: true`. Such a principal may call only routes marked `@AllowDuringMfaEnrollment()` (`GET /auth/me`, MFA setup/enable, sessions list, logout, logout-all); everything else is `403` with message `MFA enrollment required`. The **platform organization is seeded with `mfa_required = true`**.
- **Step-up:** the platform override (D9), organization deletion request/confirm (D12) and `POST /users/{id}/mfa/reset` require a session with `mfa_authenticated = true` (`403 MFA required` otherwise).
- **Admin reset:** `POST /api/v1/users/{id}/mfa/reset` (`user:manage`) clears the secret, recovery codes and `mfa_last_used_step`, revokes the user's sessions, audits `user.mfa_reset`.

### D8. Authorization model

**Permissions catalog** (seeded; `permissions` is the source of truth). Existing 26 keys plus 4 new ones (WP1):

| New key                    | Meaning                                                          |
| -------------------------- | ---------------------------------------------------------------- |
| `role:read`                | View roles and the permission catalog                            |
| `apikey:read`              | View API keys (never secrets)                                    |
| `session:manage`           | View and revoke other users' sessions                            |

Retired seed keys are migrated by the seed (idempotently): their `user_roles` move to the new role (`platform_support`→`platform_admin`, `tenant_admin`→`organization_admin`, `security_admin`→`organization_admin`, `helpdesk`→`quarantine_reviewer`, `auditor`→`compliance_auditor`, `end_user`→`read_only_user`), then the retired role, its `role_permissions` and its `user_roles` are deleted. (Only local/dev data used them.) End-user self-service quarantine roles return with step 5.3.

**Rules enforced by services:**

- Guards check permission keys, never role names.
- A role containing any `platform:*` permission is a **platform role**; it may be assigned only to users of the platform organization (`kind = platform`). Customer organizations never see platform roles in `GET /roles`.
- **No escalation:** a principal may assign a role, or create/edit a custom role, only if it holds every permission of that role (super admin holds all).
- **Target-side no escalation** (added at the step's review): a principal may act on another user (profile or email change, status change and unlock, deletion, MFA reset, invitation resend, role change, session revocation) only if it holds every permission of every role the target currently has (`403`). Otherwise `user:manage` alone (a custom role or an API key) could change a stronger user's email and take the account over through a password reset. Email changes additionally require a user principal (API keys `403`), and password-reset links go only to verified addresses (D11).
- **Custom roles** belong to one organization, contain only TENANT_PERMISSIONS, use keys `^[a-z][a-z0-9_]{2,63}$` that are not system keys.
- **Last administrator:** an organization must keep at least one active, non-deleted user whose roles grant `user:manage`; suspending, deleting or changing roles that would violate this is `409`. Users cannot suspend or delete themselves.
- Domain Admin is organization-wide; per-domain role scoping is out of scope (§10).

### D9. Principal, tenant scope, guards and the platform override

**Guards** (WP3, registered as `APP_GUARD` in this order: `AuthGuard`, `PermissionsGuard`):

- `AuthGuard`: routes with `IS_PUBLIC_KEY` pass. Otherwise exactly one credential must be present: `Authorization: Bearer <jwt>` **or** `X-API-Key: egk_…` (both → `401`). Bearer: verify JWT (D4); deny-listed `sid` → `401`; load the principal snapshot (below); `sub`/`org` must match; user active, not deleted, org `active` → else `401`. If `ovr` is present, load the override from KV `auth:override:<id>` (missing → `401`), its `userId` and `sessionId` must match, the target org must exist and not be `deleted`; effective permissions = user permissions ∩ TENANT_PERMISSIONS. API key: parse, look up by prefix (KV cache 60 s, writer on miss), constant-time hash compare, not revoked/expired, org `active`, org feature `api_access` enabled, effective permissions = scopes ∩ TENANT_PERMISSIONS (minus `API_KEY_FORBIDDEN_SCOPES`, D11); throttled `last_used_at` update (KV `apikey:used:<id>` set-if-absent 60 s, then a fire-and-forget writer update with error logging). Sets `req.principal`, `req.tenantScope = scopeFromPrincipal(...)`, and the logger context `tenantId` (decimal org id of the scope) via a new `setContextTenant()` in `packages/logger`.
- `PermissionsGuard`: public → pass. No `AUTHZ_KEY` metadata on a non-public route → **`403` and an error log** (fail closed; the route-security test makes this impossible to ship). `mfaEnrollmentRequired` and route not `@AllowDuringMfaEnrollment()` → `403`. `@UserOnly()` with an API key → `403`. `@RequireMfa()` without `mfaAuthenticated` → `403 MFA required`. Then `all`/`any` permission checks → `403`.
- Redis/KV unavailable during authentication → `503` (fail closed).

**Principal snapshot cache:** KV `auth:principal:<userPublicId>` = `{ orgVersion, userVersion, user fields, org fields, permissions[], mfaRequired }`, TTL 60 s; valid only if its `orgVersion` equals KV `auth:orgver:<orgId>` (missing = 0) and its `userVersion` equals KV `auth:userver:<userPublicId>` (missing = ''). `PrincipalCacheService` (exported by the auth module) has `invalidateUser(userId)` (writes a fresh random nonce to `auth:userver:…` with a 1-hour TTL, then DEL), `invalidateOrganization(orgId)` (INCR orgver; used for org status changes and custom-role permission edits), `invalidateApiKey(prefix)` (nonce in `auth:apikeyver:<prefix>`, then DEL). Every write that changes status, roles, role permissions, MFA state or org status calls it **after commit**. **Fill order:** on a miss the filler resolves the (immutable) organization id with a light lookup, reads both versions, and only then reads the snapshot or key row; a change that commits after that read moves a version, so the entry it writes is never served (a plain DEL could be overwritten by a racing fill for up to 60 s). The nonce TTL exceeds the entry TTL so an entry stamped before an invalidation cannot become current again when the nonce expires.

**Platform override** (`/api/v1/platform/overrides`, WP3):

- `POST` `{ organizationId (public UUID), reason (10–500 chars), durationMinutes (5–PLATFORM_OVERRIDE_MAX_MINUTES, default 30) }`. Requires a user principal from the platform org, not already under override, with `platform:tenant_override`, `@RequireMfa()`. Target must be a `customer` org that is not `deleted`. Creates KV `auth:override:<id>` `{ userId, sessionId, targetOrganizationId, reason, expiresAt }` with TTL, writes `audit_logs` `platform.override_started` (`organization_id` = target, `actor_type user`, `actor_id` = user public id, `resource_type organization`, `resource_id` = target public id, metadata `{ overrideId, reason, expiresAt }`). Returns `{ overrideId, accessToken, tokenType, expiresAt, organization: { id, slug, name } }`. The override token is a normal access token with `ovr`, `exp` = override expiry, and **cannot be refreshed**.
- `DELETE /api/v1/platform/overrides/{overrideId}` (same user; normal or override token) deletes the KV entry and audits `platform.override_ended`. Revoking the session also ends the override (the `sid` is shared).
- **No standing access under an override** (added at the step's review): actions whose effect would outlive the time-boxed override are `403` for an override principal: creating API keys, inviting users and resending invitations, changing user roles, and changing a user's email. Operational support (status changes, unlocks, display names, MFA resets, session revocation) stays available and audited.
- `OverrideAuditInterceptor` (global, WP3): for every request whose principal has `override`, after the response completes (success or error) write `audit_logs` `platform.override_request` with metadata `{ overrideId, reason, method, route (the route template, never the raw URL or query), statusCode }`. Mutations made under override also carry `metadata.override = { id, reason }` in their own audit rows (AuditService adds it automatically from the principal).
- The organization catalog (`/api/v1/organizations` with `platform:organizations`) is a platform function, **not** an override: no reason is required, every mutation is audited. Under an override token `platform:*` permissions are stripped, so the override principal sees only the target organization like a member would.

**Tenant-scoped repositories:** every method that reads or writes tenant-owned rows takes `scope: TenantScope` as its first parameter and builds its `where` with `tenantWhere(scope, …)` (or the equivalent raw SQL filter). Lookups by public id are `findFirst({ where: { publicId, organizationId } })`, never `findUnique({ publicId })` followed by a check. The only unscoped identity lookups are the authentication paths (login by email/org, token hash, API-key prefix, principal snapshot) inside `modules/auth/repositories/`.

### D11. Identity administration (WP4)

- **Invitation:** `POST /users/invitations { email, displayName, roleKeys[≥1] }` (`user:manage`). In one writer transaction: lock the organization row (`SELECT … FOR UPDATE` via `OrganizationLimitsService`), enforce `max_users` (count of non-deleted users), check roles (D8 rules), insert the user (`status invited`, email lower-cased; a soft-deleted user with the same email is reinstated: `deleted_at NULL`, password/MFA cleared), insert `user_roles` (`granted_by_user_id`), create the invitation token (`InvitationService.createToken(tx, …)` from the auth module), audit `user.invited`. **After commit** send the email (`InvitationService.sendInvitation(…)`). Existing non-deleted email → `409`. Resend: `POST /users/{id}/invitation` (invited users only).
- **Activation/suspension:** `PATCH /users/{id}/status { status: 'active' | 'disabled', reason }`. `active→disabled`, `disabled→active`, locked (`locked_until > now`) `→active` (unlock), `invited→disabled` (cancels invitation tokens). Disabling revokes sessions. Self and last-admin rules (D8). Audited `user.status_changed`.
- **Profile and email:** `PATCH /users/{id} { displayName?, email? }`. An email change clears `email_verified_at` and sends a verification link to the new address (an invited user gets a new invitation instead). It needs a user principal and is refused under an override (`403`). `POST /auth/password/forgot` only sends links to active accounts with a **verified** email, so an administrator-set address must be confirmed by its owner before it can receive a reset link.
- **API keys:** `scopes` must be non-empty, ⊆ the creator's permissions, ⊆ TENANT_PERMISSIONS, and must not contain `API_KEY_FORBIDDEN_SCOPES` = `apikey:manage`, `role:manage`, `session:manage`. `expiresAt` optional, default now + 365 days, max now + 730 days. Creating requires the org feature `api_access` (`403` otherwise) and a user principal. Revocation is idempotent (`204`), invalidates the auth cache. Audited `apikey.created` / `apikey.revoked` (metadata: name, prefix, scopes; never the key).

### D13. Email delivery (EmailSender port)

The `.env.example` already defines the transactional-email relay (added by the product owner during this step; **reuse these keys, do not rename or duplicate them**): `NOTIFY_SMTP_HOST`, `NOTIFY_SMTP_PORT` (587), `NOTIFY_SMTP_SECURE` (`starttls`), `NOTIFY_SMTP_USER`, `NOTIFY_SMTP_PASSWORD` (secret), `NOTIFY_SMTP_FROM`. The local `.env` holds working values for a real authenticated submission relay: never print them, never overwrite them.

- `EmailSender` (abstract class) `send(email: OutboundEmail): Promise<void>`; `OutboundEmail { to, subject, text, kind: 'invitation' | 'password_reset' | 'email_verification', devLink?: string }`.
- **Selection:** `SmtpEmailSender` when `NOTIFY_SMTP_HOST` is set, otherwise `LogEmailSender`. `api` logs one `info` line at startup naming the transport (never the host credentials), and a `warn` when `LogEmailSender` is active with `NODE_ENV=production`.
- `SmtpEmailSender`: nodemailer submission to `NOTIFY_SMTP_HOST:NOTIFY_SMTP_PORT`, `from = NOTIFY_SMTP_FROM`, auth from `NOTIFY_SMTP_USER/PASSWORD` when set. `NOTIFY_SMTP_SECURE`: `tls` (implicit TLS, nodemailer `secure: true`), `starttls` (`secure: false, requireTLS: true`), `none` (plaintext; accepted only when `APP_ENV` is `local` or `ci`). Certificate verification is always on. Timeouts: connection 10 s, socket 20 s. Errors are logged with the SMTP response code only (no credentials, no message body).
- `LogEmailSender`: logs `info` `{ kind, to: <masked, e.g. a***@gateway.test>, subject }`. It adds `devLink` (the link with the token) **only** when `NODE_ENV !== 'production'` and `APP_ENV` is `local` or `ci`. In production mode it never logs the token, and emails are then **not delivered** — a documented limitation when no relay is configured, not a mock.
- **Tests never send real email:** the API integration harness replaces `EmailSender` with `RecordingEmailSender`; the `SmtpEmailSender` integration test constructs the sender with explicit options pointing at the Compose Postfix (127.0.0.1:`SMTP_HOST_PORT`, `none`, recipient `@gateway.test`), never at `NOTIFY_SMTP_HOST`.
- Links: `${PORTAL_PUBLIC_URL}/auth/<accept-invitation|reset-password|verify-email>#token=<token>` — the token is in the **fragment**, so it never reaches server logs or `Referer`. The portal pages arrive with step 7.x (documented).
- Emails are sent **after** the database transaction commits. A send failure is logged (without the token) and does not roll back; the user can request a resend.
- The notification service (step 6.2) will take over delivery and reuse the same `NOTIFY_SMTP_*` keys; the relay config schema therefore lives in `packages/config` (`notifySmtpConfigSchema`).

## 7. Alternatives considered (step level)

See ADR-0015/0016 for the API prefix, token, session, RBAC and override alternatives. In addition:

- **Prisma client extension that injects `organization_id` automatically:** invisible at call sites, easy to bypass with raw queries, awkward with partitioned tables and nested writes. Rejected for explicit `TenantScope` parameters plus a lint rule that keeps Prisma inside repositories.
- **`@nestjs/throttler` / passport / `@nestjs/jwt` / `otplib`:** each is fine, but the needed behaviour (Redis-backed per-identifier counters, two credential types, RFC 6238 with replay protection) is small and testable in-house; fewer dependencies under `minimumReleaseAge`. The JWT itself uses `jose` (no hand-rolled signature code).
- **Separate token tables per purpose (`password_resets`, `email_verifications`, `invitations`):** three identical tables; one `user_tokens` table with a purpose enum is simpler.
- **Locking accounts by `users.status = locked`:** would require an admin for every lockout; time-based `locked_until` with progressive backoff is the OWASP recommendation. `status = locked` remains available for manual locks.
- **Recovery codes hashed with Argon2:** strongest, but verifying a code would need up to 10 Argon2 runs; HMAC with a server pepper makes offline guessing infeasible without the pepper and allows an indexed lookup.
- **Hard delete of organizations:** violates retention and legal-hold obligations. Soft delete with `purge_after` plus a deferred purge job.
- **403 for cross-tenant resources:** leaks existence. `404`.

## 8. Risks and mitigations

| Risk                                                                        | Mitigation                                                                                                                                                         |
| --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| A new route ships without authorization metadata                            | Fail-closed `PermissionsGuard` plus `apps/api/test/route-security.e2e.test.ts`, which enumerates every route and asserts `@Public()` or an `AUTHZ_KEY` requirement |
| A repository query forgets the tenant filter                                | `TenantScope` required parameter, lint rule (Prisma only in repositories), cross-tenant integration matrix (§9)                                                    |

| Integration tests trip the per-IP limits (all requests come from 127.0.0.1) | The API test harness sets `HTTP_TRUST_PROXY=1` and gives each test its own `X-Forwarded-For` address; lockout tests use dedicated IPs                              |
| Argon2 memory under load (19 MiB per concurrent hash)                       | Parameters at the OWASP floor; login rate limits; pods have 512 Mi; document sizing                                                                                |
| Redis outage locks everybody out                                            | Deliberate fail-closed; Redis is in readiness; documented in `docs/security/authentication.md`                                                                     |
| `argon2` native build in Docker / CI                                        | Prebuilt glibc binaries; `onlyBuiltDependencies`; verifier builds the `api` image once                                                                             |
