## 0. Scope in one paragraph

AI-4 enables the 66 security-operations operations planned for this phase as chat tools — 64 writes executed only through the AI-2 confirmation card and 2 side-effect-free reads (`dlp_patterns_test`, `risk_dry_run_dry_run`) — for DLP (policies, rules, patterns, dictionaries, exceptions, Aadhaar compliance), BEC (executives, vendors, trusted senders, suppressions, per-message feedback), risk-scoring profiles (drafts, publish, activate, reset), incidents (create, update/triage, notes), ATO triage (account protection, verdict overrides, trusted contexts, mailbox refresh), ATO responses (request, approve, reject, cancel, rollback **strictly through the existing ATO approval model**), ATO settings and identity-provider integrations (non-secret fields only), and the platform-only operations (threat hashes and indicators, attachment rescans, scan training, dead-letter replay). It adds the four missing single-item reads the confirmation cards need (`GET /bec/trusted-senders/{id}`, `GET /bec/suppressions/{id}`, `GET /dlp/exceptions/{id}`, `GET /platform/threat-indicators/{id}`). Two new guard kinds make the ATO four-eyes rule visible in chat before anything is stored (the requester, or the creator of the requesting API key, can never approve or reject a response; the api's `ato_self_approval` refusal stays the authority and is proven by tests, including the adversarial fake). Every change that weakens detection (trust, exceptions, suppressions, benign verdicts, protection from automation, disabling or monitor-only, allow rules, ATO settings, IdP response permissions) is `high` (password + TOTP re-authentication) directly or by escalation. Platform-only tools stay invisible to tenant users and to platform users under an override. Provider credentials, OAuth consent, DLP evidence, BEC history purge and file exports stay portal-only. The step also fixes the ATO Playwright timeout recorded at the AI-2/AI-3/AI-R gates: its root cause is in the ato-worker (D14).

## 2. Decisions

### 2.0 Invariants added to I1–I17

- **I18 Four eyes stay four eyes.** No ATO response is approved or rejected through chat by the user who requested it, or by the user who created the API key that requested it. The assistant refuses such a proposal before anything is stored (D3) and again at confirm; the api's `ato_self_approval` refusal stays the authority and is proven to fire when a request reaches it, through chat and directly (§9). Chat never creates a second approval path: approve/reject/cancel/rollback are the existing operations with the user's own token, MFA session and `ato:respond`.
- **I19 Platform tools never reach tenant principals.** `platform:*` tools are absent from the catalogue, `describe_tool` and `GET /assistant/tools` for customer users and for platform users under an override (permissions stripped), and a forced call is `denied_permission` without a loopback request.
- **I20 Weakening detection needs re-authentication.** Every confirmed change that adds trust or an exception, suppresses findings, sets a benign verdict, protects an account from automated response, disables a detector or a policy, switches it to monitor-only, adds an `allow` rule, changes ATO settings, or changes which response actions the gateway may take in a tenant's identity provider is `high` (password + TOTP), directly or by escalation (D2, D4).
- **I21 No content to the model, no secret through chat (I5, I14 restated for AI-4).** No AI-4 tool returns a message body, an attachment, DLP evidence or a provider credential; DLP evidence read and purge, BEC history purge and feedback export, provider credential upload and OAuth consent stay N/A; the DLP pattern-test sample is never stored in execution or audit rows (D9).

### D3. Proposal guards for the ATO approval model (package `confirmations/guards.ts`)

Two new guard kinds, both **after-read** (they need the precondition target; a consistency rule requires a `single` precondition):

```ts
  /** The read's `field` (a user public id) must not be the caller (case-insensitive UUID
   * compare), optionally only when the read's `when.field` equals `when.equals`. A missing
   * field passes (the second guard and the api decide). */
  | { kind: 'not_self_field'; field: string; when?: { field: string; equals: string }; message: GuardMessageKey }
  /** The read's `field` must equal `equals`, optionally only when `when` holds; a missing or
   * non-matching field refuses (fail closed). */
  | { kind: 'require_read_value'; field: string; equals: string | boolean; when?: { field: string; equals: string }; message: GuardMessageKey };
```

`guardPhase` returns `after_read` for both; `guardArgumentPaths` returns `[]` for both (they read no argument); `guardNote`: `guard: not requester`, `guard: <field> = <equals>`.

Message key `ato_four_eyes` (fixed English, no values): "This response needs a different person to decide it. The person who requested a response, or who created the API key that requested it, can never approve or reject it, and deciding needs a session signed in with MFA. Ask another responder to decide it in chat or on the Responses page."

| Tool                                            | Guards (both `message: 'ato_four_eyes'`)                                                                                                                                                                            |
| ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ato_responses_approve`, `ato_responses_reject` | `not_self_field { field: 'requestedBy.id', when: { field: 'requestedBy.type', equals: 'user' } }`; `require_read_value { field: 'canDecide', equals: true, when: { field: 'status', equals: 'pending_approval' } }` |

Semantics: the first guard is the explicit requester check (independent of the api's view logic, defence in depth); the second covers the API-key creator and a session without MFA through the api's own `canDecide` (computed for the caller of the precondition read, who is the proposing user). A response that is not `pending_approval` passes both guards and the api answers `409 ato_response_state` (surfaced as a failed proposal read or failed confirmation as today). Cancel (requester or another responder) and rollback (any responder with MFA) have no separation-of-duties rule in the api and get no guard. At confirm the proposer's re-read runs with the confirming principal (same user) and the after-read guards are evaluated again (AI-3 D10): a response that moved to another state or whose `canDecide` became false is refused `403 assistant_action_not_allowed`.

### D14. ato-worker: the ATO Playwright timeout (root cause and fix)

**Symptom.** `tests/portal-e2e/specs/ato-providers.spec.ts` › "mailbox changes: remove an external forwarding rule through approval" times out (its `until` waits 300 s for the alex mailbox account, its incident and the inbox-rule item) under full-suite load and passes alone; the ato-worker logs `P2024` / `P1001` at those times.

**Root cause (from the code and the logs; WP2 confirms it by fault injection and records the evidence in §11):**

_Correction (closing round, 2026-11-25): the two causes below are the likely causes, derived from the code and the logged `P2024` / `P1001` errors. The fault-injection test proves that the fix handles them, but the original full-suite timeout was never reproduced exactly; the evidence that it is gone is the forwarding-rule spec passing alone, with other heavy specs and in parallel (§11 WP2, §12.1), and the orchestrator gate's full Playwright run._

1. _A transient database error becomes a long stall._ The IdP probe loop claims an integration by moving `next_health_at` to `now + ATO_IDP_HEALTH_INTERVAL_SECONDS` (900 s) **before** probing; when the probe then throws (a `P2024`/`P1001` inside `orgs.get`, `store` or the adapter's writes), the error is only logged ("ato idp probe failed") and the integration keeps the 15-minute lease. A freshly connected integration has `health_checked_at = NULL`, so every stream is "not probed" until the next probe: nothing is ingested for 15 minutes. The stream runner has the same shape with a smaller effect: a transient database error inside a poll is caught as a provider failure (`failure()`), increments `consecutive_failures`, backs off `poll interval × 2^failures` (120 s, 240 s, … up to 1 h), feeds the integration's failure aggregate and, after three, forces a probe; if the failure write itself fails, the claim lease (5 min) holds. Either path pushes the mailbox snapshot sweep beyond the test's 300 s window. Database outages are not provider failures (ADR-0083's backoff is about provider throttling and errors).
2. _An undersized pool with a short pool timeout._ The worker's single writer client uses Prisma's default pool (`2 × CPUs + 1` = 17 on the 8-CPU VM) and the default `pool_timeout` of 10 s, while up to 68 queue handlers (prefetch 32 + 32 + 4, each an interactive transaction with `maxWait` 30 s and a 120 s timeout), 4 parallel stream polls, the probe loop and ~10 maintenance jobs share it. Under full-suite load (slow MySQL), plain queries wait more than 10 s for a connection → `P2024`, while transactions may wait 30 s: the pool timeout is shorter than the transaction start wait. `P1001` is the connect timeout under load (MySQL never reached `max_connections`: 93 of 300 used, no `Connection_errors_max_connections`).

The queue consumers (detect, respond) already classify `P1001`/`P2024` as transient (`defaultClassify`) and redeliver with the queue's hold back-off; the `Periodic` maintenance loop retries with 1–60 s back-off. Neither is a cause.

**Fix (product):**

1. **Transient database errors never count as provider failures** (`isTransientInfrastructureError` from `@email-gateway/common`, the classifier the queue consumers use):
   - Stream runner: `withDeadlockRetry` becomes `withTransientRetry` (lock conflicts **and** transient infrastructure errors; at most 5 attempts, jittered back-off `200 ms × 2^(n−1)` capped at 5 s; the page transaction is atomic and ledgered, so a retry is idempotent); the claim, `success` and `failure` writes get a bounded retry (3 attempts, same back-off). A poll that still ends in a transient infrastructure error (and is not a `ProviderAdapterError` / `ConnectionAccessError`) is **deferred**: `next_poll_at = now + backoffDelay(k, { baseMs: 5 000, maxMs: 60 000 })` with an in-process per-stream counter `k` (reset on success), `consecutive_failures`, `last_error_code`, the integration aggregate and the probe trigger untouched.
   - Probe loop: a probe that throws a transient infrastructure error re-schedules `next_health_at = now + backoffDelay(k, 5 s … 60 s)` instead of keeping the 15-minute lease, without changing `health_status`; any other unexpected throw re-schedules after `min(health interval, 300 s)` (the cap the "failed" transition already uses). A transient error while reading the provider connection is deferred the same way, not recorded as a probe failure.
   - Metric `ato_idp_transient_db_errors_total{loop="stream"|"probe", outcome="retried"|"deferred"}`; warn logs carry class name and code only (existing rule).
2. **A correctly sized pool.** `databaseClientUrl` (packages/database) gains options `connectionLimit` (1–500) and `poolTimeoutSeconds` (1–600) that set `connection_limit` / `pool_timeout` on the URL (the option wins over a value in the URL; errors never contain the URL); `DatabaseModuleOptions` / `PrismaService` (packages/common) pass them through (other services unchanged: they pass nothing). The ato-worker passes **`ATO_DATABASE_CONNECTION_LIMIT`** (int 4–200, default **32**) and **`ATO_DATABASE_POOL_TIMEOUT_SECONDS`** (int 5–300, default **30**, ≥ the transaction `maxWait` of 30 s; the config refuses a smaller value with a clear message). Budget: 32 per ato-worker process (Compose: one container; Kubernetes: `ato-detect` and `ato-respond` Deployments, each replica) stays far below `max_connections` 300 with the other services (documented in `docs/deployment/account-takeover.md` with the formula "replicas × 32 + other services ≤ 80 % of max_connections"). _Closing round (2026-11-25, review finding): at the `ato-detect` HPA maximum (8 replicas) a pool of 32 would open about 297 connections, so the base manifest sets `ATO_DATABASE_CONNECTION_LIMIT=12` for `ato-detect` and keeps 32 for the single `ato-respond` pod (8 × 13 + 1 × 33 = 137 ≤ 144, 60 % of the 80 % writer budget); the rule is now `Σ maxReplicas × (limit + 1) ≤ 0.6 × 0.8 × max_connections` and `apps/ato-worker/src/deployment/connection-budget.test.ts` enforces it (§11 Closing round)._
3. **The test** keeps its 300 s budget (it is not too tight once a transient error defers by seconds instead of minutes) but its `until` timeout message includes diagnostics (the integration's `status`, `health_status`, `health_checked_at`, `next_health_at` and each stream's `status`, `next_poll_at`, `consecutive_failures`, `last_error_code`), so a future timeout names its cause.

## 5. Alternatives considered

| Decision                                                               | Alternatives                                       | Why not                                                                                                                                                                                                                                                            |
| ---------------------------------------------------------------------- | -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Four-eyes guard in the assistant **and** the api's refusal             | Rely on the api only                               | The api refuses correctly, but only at confirm, after the user re-authenticated for a card that can never succeed; a guard at proposal says why at once and keeps the refusal visible in audit (`denied_guard`); defence in depth if the view logic ever regresses |
| Guard on `canDecide` plus an explicit requester check                  | Only `canDecide`                                   | `canDecide` also covers the API-key creator and MFA, but it is view logic; the explicit `requestedBy.id` compare does not depend on it                                                                                                                             |
| A guard on rollback / cancel                                           | Same four-eyes rule                                | The api has no such rule (rollback restores the prior state; cancel is the requester's own right); adding one in chat would make chat stricter than the portal without a product decision                                                                          |
| `high` for trust/exception creates and ATO settings                    | Keep `low`/`medium`                                | These are the changes a prompt-injected model would aim for (I20)                                                                                                                                                                                                  |
| Escalation for weakening updates                                       | Make every DLP/BEC update `high`                   | Renaming a policy with password + TOTP trains users to confirm blindly (AI-3 precedent)                                                                                                                                                                            |
| Four new GET-by-id routes                                              | `select` over the lists                            | The lists are cursor-paginated without an id filter (A3-7 precedent); hashes have an exact `sha256` filter and use `select`                                                                                                                                        |
| `redactParams`                                                         | Mark `dlp_patterns_test` N/A                       | It is the only way to check a pattern before creating it by chat; the api already persists nothing                                                                                                                                                                 |
| Platform tools tested through `DirectExecutor`                         | Enable the assistant for the platform organization | Never change settings of organizations 1/2 (standing rule)                                                                                                                                                                                                         |
| ato-worker: classify database errors as transient and defer by seconds | Raise the test timeout; raise the pool only        | A longer wait hides a product defect (a 15-minute stall after any database hiccup); a bigger pool alone still leaves the lease/backoff stall on the next `P1001`                                                                                                   |
| Explicit pool size in config                                           | Prisma default                                     | The default depends on the CPU count of the host and is far below the worker's own concurrency                                                                                                                                                                     |
