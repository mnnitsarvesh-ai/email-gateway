Status: **implemented and verified locally (2026-11-11), not complete** ([§13](#13-verification-results); quarantine store 5.3, archive consumer 8.1, WARN banners, per-recipient dispositions and the items of §13.7 are not done; committed after the [§13.10](#1310-final-gate-2026-11-12) final gate, CI not run). Decision records: [ADR-0043](../../architecture/adr/0043-policy-dsl-and-deterministic-evaluator.md) (the DSL, the evaluator, conflict resolution, the strictness floor, storage), [ADR-0044](../../architecture/adr/0044-policy-evaluation-placement-and-delivery-gating.md) (where policy runs, how delivery is gated, removal of the development pass-through, topology v9), [ADR-0045](../../architecture/adr/0045-policy-action-semantics.md) (what each of the nine actions does in 5.2). This note is the single source of truth for the implementers of this step. Decisions of steps 1.1–5.1 stay in force unless a decision below names them. If a decision proves impossible (a library, Prisma, MySQL, RabbitMQ or Node behaviour differs from what is assumed here), the implementer verifies the real behaviour, records it in §12 with evidence and picks the closest alternative that keeps the invariants of §2.0. **Nobody silently changes a decision.** Section numbers (§) and decision ids (P*n*) are stable references.

**What 5.2 enforces, plainly** (details in ADR-0045 and P19):

- **Enforced:** the final disposition of every scanned, scan-failed and parse-failed message (ALLOW → approved and delivered; QUARANTINE → held in `quarantined`; REQUIRE_APPROVAL → held in `held_for_review`; REJECT → `rejected`, nothing delivered); the strictness floor (hard blocks, failures, DLP binding, missing data can never be weakened); TAG/WARN headers and subject prefixes in a delivered policy copy; delivery of the round's URL-rewritten copy; tenant policies, versions, publish, rollback, testing, dry-run, history and audit.
- **Requested (performed by another stage):** ARCHIVE (`email.archive`, consumer is **step 8.1**), ALERT and the outbound non-delivery notice (notification-worker, at least once).
- **Recorded only:** WARN body banners (not supported in 5.2); TAG/WARN when headers are disabled or the message is too large for a copy; URL_REWRITE when the round was not rewritten and the rule says `deliver`.
- **Not in 5.2:** the quarantine store, end-user quarantine, release re-validation, digests and request-release workflow (**5.3**); archiving and journaling (**8.1**); per-recipient split dispositions; enabling URL rewriting after the scan.

## 2. Decisions

### 2.0 Invariants (never traded away)

1. **No customer code.** Policies are JSON data validated by a strict schema from a closed catalog. No `eval`, `new Function`, `vm`, template engine, SQL fragment or user regex outside RE2 is ever compiled or run. Anything outside the schema is refused with violations by path.
2. **Never weaker than the floor.** The final disposition is at least as strict as every hard block, the failure floor, the DLP binding (ADR-0037) and the missing-data holds, for every configuration, rule, exception, override and setting. ALLOW never releases them. Enforced in the evaluator (code), proven by unit, property and stack tests.
3. **Deterministic and reproducible.** `evaluatePolicy` is a pure function of `(PolicyInput, CompiledSnapshot)`; the evaluation time is a fact of the input; same input and snapshot → byte-identical result and `inputSha256`. A dry-run of a stored round with the same snapshot reproduces the stored decision.
4. **Missing data never relaxes.** Unknown facts evaluate to _unknown_ (three-valued logic): they never make a rule match and never make an exception apply; the floor turns missing risk/DLP/scan data into holds.
5. **No trust in spoofable identity.** Exceptions and relaxing rules see sender identity only through authenticated facts (P6). Recipient identity is the envelope recipient. Tenant from the trusted context: the engine takes the organization from the writer message row matched by the event's organization; the api from `CurrentScope`, never from headers or bodies.
6. **AI never decides alone (ADR-0034).** Rules that read AI-derived fields cannot hold mail; platform holds use deterministic verdicts only.
7. **Idempotent per round.** One evaluation per `(message, lifecycle round)` (unique key); duplicate events are absorbed by the ledger, the lifecycle edge and the key. A rescan or release is a new round. Stored evaluations are never updated or deleted (except retention and organization purge).
8. **No message content stored or logged.** Evaluation rows, explanations, events, logs and metrics hold ids, codes, enums, integers, hashes and tenant policy identifiers only: no subject, body, file name, URL, header value or address (addresses appear only where the existing read APIs already show them: the messages API, not the policy records). Metric labels are bounded enums; never tenant ids.
9. **Never claim enforcement that did not happen.** Every stored action has a status `enforced | requested | recorded | not_applicable` (ADR-0045).

### P2. The document `policy-dsl/1`

```text
PolicyDefinition = {
  dslVersion: 'policy-dsl/1',
  direction: 'inbound' | 'outbound' | 'internal' | 'any',
  priority: int 0..10000,                     // policy order (ascending)
  rules: Rule[] (1..POLICY_LIMITS.rulesPerPolicy),
  exceptions?: ExceptionNode[] (≤ 8)          // exempt every rule of this policy
}
Rule = {
  id: /^[a-z0-9][a-z0-9_-]{0,47}$/ (unique in the policy),
  priority: int 0..10000 (unique in the policy),
  description?: string ≤ 256 (printable, no control characters; never rendered into mail),
  enabled?: boolean = true,
  directions?: non-empty unique subset of ['inbound','outbound','internal'], each allowed by the policy direction,
  when: Node,
  unless?: ExceptionNode[] (≤ 8),
  actions: Action[] (1..8; at most one disposition; each non-terminal type at most once),
  stop?: boolean (default: true iff the rule has a disposition),
  override?: boolean (default false; only with a disposition; P9)
}
Node = { all: Node[] (1..16) } | { any: Node[] (1..16) } | { not: Node } | Leaf
Leaf = { field, op, value?, quantifier?: 'any' | 'all' }   // quantifier only for list-scoped fields
     | { field: 'time.window', op: 'within', value: { timeZone, days: Weekday[] (1..7, unique), from: 'HH:MM', to: 'HH:MM' } }
     | { field: 'time.date_range', op: 'within', value: { timeZone, from: 'YYYY-MM-DD', to: 'YYYY-MM-DD' } }
ExceptionNode = Node restricted by P6 (positive only, `all` quantifiers, authenticated identity)
Action = { type: 'ALLOW' } | { type: 'REQUIRE_APPROVAL' } | { type: 'QUARANTINE' }
       | { type: 'REJECT', notifySender?: boolean }
       | { type: 'TAG', label: /^[a-z0-9][a-z0-9._-]{0,31}$/, subjectPrefix?: SubjectPrefix, addHeader?: boolean = true }
       | { type: 'WARN', level: 'caution' | 'warning' | 'danger', text?: HeaderText, subjectPrefix?: SubjectPrefix }
       | { type: 'URL_REWRITE', ifNotRewritten?: 'deliver' | 'quarantine' = 'deliver' }
       | { type: 'ARCHIVE' }
       | { type: 'ALERT', severity: 'info' | 'warning' | 'critical' }
SubjectPrefix = printable ASCII 1..32, no CR/LF, no ':'      HeaderText = printable ASCII 1..128, no CR/LF
```

Strict objects everywhere (unknown keys refused). `policyDefinitionSchema` plus a `superRefine` pass implement every cross-field rule of P3–P6 and P9; `validatePolicyDefinition` returns all violations (not only the first), sorted by path.

| `scan.verdict`                                            | enum (`SCAN_VERDICTS`)                                                  | message                     | equals, in                                                  |                                                                                                                                                                                                                       |
| `scan.reason_codes`                                       | codes                                                                   | message                     | contains_any, contains_all                                  |                                                                                                                                                                                                                       |
| `scan.failed_engines` / `scan.unknown_engines`            | codes (engine names)                                                    | message                     | contains_any, exists                                        |                                                                                                                                                                                                                       |
| `time.window` / `time.date_range`                         | time                                                                    | message                     | within                                                      | P2; IANA zone validated against `Intl.supportedValuesOf('timeZone')`; `from > to` wraps midnight (window)                                                                                                             |

Operators: `equals`, `in`, `not_in` (list ≤ `maxListValues`), `domain_in` (exact or label-suffix: `a.example.com` matches `example.com`, `badexample.com` does not), `glob` (patterns of `*`/`?`/literals, ≤ 128 chars, ≤ 10 patterns, matched by a linear two-pointer matcher, never compiled to a JS regex), `regex` (≤ 5 patterns, each ≤ 256 chars, compiled with `re2js` at validation and at compile, flags only `i`; the subject is cut to 1 024 characters), `in_cidr` (≤ 100 IPv4/IPv6 CIDRs, canonical, prefix within range; IPv4-mapped IPv6 normalized), `eq`/`gt`/`gte`/`lt`/`lte`/`between` (numeric or ordered enum), `contains_any`/`contains_all` (≤ 64 codes, each a valid code), `exists`, `is`, `within` (time).

Quantifiers (list-scoped fields only; required in `unless`, default `any` in `when`): `any` = at least one element satisfies the leaf; `all` = every element satisfies it. On an empty list: `any` → false, `all` → **false**; on a truncated list (`attachments.truncated`, `urls.truncated`): `any` → true if a seen element satisfies, else **unknown**; `all` → **unknown** unless a seen element fails (false). A leaf on a missing fact → unknown.

### P4. Limits (`POLICY_LIMITS`; the api may lower some through settings bounds, never raise)

Document ≤ 262 144 bytes (canonical JSON); rules per policy ≤ 100; nodes per rule (`when` + all `unless`) ≤ 64; depth ≤ 6 (root = 1); children per `all`/`any` ≤ 16; list values per leaf ≤ 500; string value ≤ 320 chars; globs ≤ 10 × 128; regexes ≤ 5 × 256; CIDRs ≤ 100; codes ≤ 64; exceptions ≤ 8 per rule and ≤ 8 per policy; actions ≤ 8 per rule; active policies per organization ≤ 100 and active rules per organization ≤ 5 000 (the api bounds them lower by env, §5); recipients considered ≤ 1 000, attachments ≤ 200, URLs ≤ 500 (more → truncated flags).

### P5. Directory: departments and users

- **New tenant directory tables** (§3): `tenant_departments` (name unique per organization) and `tenant_department_members` (exactly one of a normalized address or a `users` id). Managed by the api under `user:read` / `user:manage` (§P22). Membership is live data: a change applies to the next evaluation without a policy publish; the resolved memberships are part of the evaluation input (hashed), so dry-runs report `reproducible: false` when membership changed.
- **Users:** `recipient.user` / `sender.user` reference `users.public_id` of the organization; a user matches an address equal to its `email` while `status = active` and `deleted_at IS NULL`.
- **Resolution (engine and api):** from the compiled snapshot's referenced department and user ids only (`referencedDirectoryIds`): `departmentsByAddress[address] = sorted department public ids` for every address among the message's envelope recipients and its authenticated sender; members with a `user_id` resolve through that user's email (active only). `usersByAddress[address] = sorted user public ids`. Reads are bounded by the message's addresses, never by department size: first the organization's active, not deleted users whose `email` is one of the addresses, then the members of the referenced departments whose `address` is one of them or whose `user_id` is one of those users (closing round, §13.9).
- A department referenced by an active version cannot be deleted (`409 department_in_use`, the api checks `policy_versions.references` of active versions).

### P6. Exceptions and identity restrictions (validated by schema, re-checked by the evaluator)

- `unless` (rule) and `exceptions` (policy) nodes: **positive only** (no `not`, no `not_in`); list-scoped leaves must use quantifier `all`; sender identity only through `sender.authenticated.*`, `sender.trusted`, `sender.department`, `sender.user` (raw `sender.envelope.*` / `sender.header_from.*` refused with code `identity_unauthenticated`); no AI-derived field.
- The `when` of a rule whose disposition is `ALLOW` or which has `override: true` follows the same identity restriction (an attacker must not be able to match a relaxing rule by forging an address).
- **Trust semantics:** `sender.trusted` and `sender.authenticated.*` are unknown/false whenever authentication failed (P3), so a trusted-sender exception never applies to an unauthenticated or failing message (as in 5.1 R7). Outbound/internal sender identity is **organization-authenticated** (the connector authenticates the organization, not the user; ADR-0037 decision 2): department/user facts of the sender are as trustworthy as the tenant's own submission control, which the DSL reference states.
- An exception can only remove a tenant rule's effect; it never touches the platform default or the floor.

### P9. Conflict resolution, the platform default and the strictness floor (ADR-0043 decisions 4–5)

Evaluation of one input against a compiled snapshot:

1. **Candidate rules:** every enabled rule of every active, valid policy whose `direction` is the message direction or `any` and whose `directions` (if present) include it, ordered by `(policy.priority, policy.publicId, rule.priority, rule.id)` ascending.
2. For each candidate in order: if a policy-wide exception of its policy is **true**, the rule is `excepted`; else evaluate `when`: not true → `not_matched` (false) or `unknown`; true → evaluate each `unless`: any **true** → `excepted`; else `matched`. Stop after the first matched rule with `stop = true`; later rules are `not_evaluated`.
3. **Tenant disposition** = the strictest disposition among matched rules (none if no matched rule has one). Its **decisive rule** = the first matched rule carrying it.
4. **Recommendation** (`pol-default/1`, overridable part): from the max of the present risk revisions' `recommendedAction` mapped `deliver → allow`, `tag → allow + platform TAG(label "risk-<level>")`, `require_approval → require_approval`, `quarantine → quarantine`, `block → reject`; plus the platform rule **D2**: `bec.deterministic_verdict ∈ {suspicious, malicious}` → `quarantine` (the 4.4 B17 hold of the pass-through; required because the 5.1 floor maps a deterministic BEC `suspicious` only to level `low`). The recommendation is **level-only** when every present revision has `levelOnly = true` (D2 counts as level-only for `suspicious`; `malicious` is a hard block in 5.1 anyway).
5. **Floor** (mandatory, never overridable): the max of
   - each present revision that is **not** level-only: its whole `recommendedAction` mapped as in 4 (hard blocks, failures, unknown engines, missing child rows, scoring error rows) — reason codes `policy.floor.hard_block`, `policy.floor.engine_failure`, `policy.floor.unknown_engine`, `policy.floor.risk_error`;
   - the **DLP binding** when the dlp final is definite and not skipped: `allow → none`, `alert → allow + mandatory TAG(label "dlp-alert")`, `require_approval`, `quarantine`, `block → reject` (`policy.floor.dlp_<action>`); a definite non-skipped dlp final **without** its row → `quarantine` (`policy.floor.dlp_missing`);
   - trigger `scanned`/`scan_failed` with **no revision-0 risk row** → `quarantine` (`policy.floor.risk_missing`);
   - trigger `scan_failed` → at least `quarantine` (`policy.floor.scan_failed`; the risk row normally already says so);
   - trigger `parse_failed` → `quarantine` (`policy.floor.not_scanned`).
     Mandatory tags: an unknown-engine floor of `tag` (5.1 `failures.unknownAction`) and DLP `alert` add a mandatory TAG.
6. **Base disposition:** if a tenant disposition exists and is at least the recommendation → the tenant disposition (source `tenant_rule`); if it is weaker: kept only when (a) some matched rule with that disposition has `override: true`, (b) `settings.allowRecommendationOverrides = true`, (c) the recommendation is level-only — then source `tenant_rule`, `override = { applied: true, … }`, code `policy.override.applied`; otherwise the recommendation (source `platform_default`, a **clamp** `{ rule, from, to, reason: 'override_not_allowed' | 'override_disabled' | 'not_level_only' }` is recorded). No tenant disposition → the recommendation (`platform_default`).
7. **Final disposition** = max(base, floor); if the floor raised it, source `floor`, decisive reason = the strictest floor reason.
8. **AI:** rules referencing `bec.verdict` or `bec.ai_raised` may not carry `REQUIRE_APPROVAL`, `QUARANTINE` or `REJECT` (schema code `ai_field_in_hold_rule`); the evaluator ignores such a disposition defensively (`policy.clamp.ai_only`). The recommendation's AI tag (5.1 R9) is a platform TAG like any `tag` recommendation. An AI-only raise therefore can at most tag or warn.
9. **Non-terminal actions** = merge, in rule order, of matched rules' TAG/WARN/URL_REWRITE/ARCHIVE/ALERT, plus mandatory tags, plus the platform TAG of a `tag` recommendation **unless** an override decided: TAG labels union (sorted, ≤ 8), first subject prefix wins (TAG before WARN), WARN strongest level and first text, URL_REWRITE strictest `ifNotRewritten`, ARCHIVE once, ALERT highest severity. `URL_REWRITE ifNotRewritten = quarantine` with `urls.rewrite_status ≠ rewritten` raises the final disposition to at least `quarantine` (`policy.url_rewrite.required`) before step 10.
10. **Applicability:** final ≠ `allow` → TAG, WARN, URL_REWRITE are `not_applicable`; ARCHIVE and ALERT apply to every disposition. `REJECT` of an `outbound`/`internal` message requests a sender non-delivery notice when `notifySender ?? settings.notices.senderNonDelivery` (default true); inbound never.
11. Platform TAG headers on outbound mail are suppressed (status `recorded`) unless `settings.tagging.platformTagOutbound = true`; inbound/internal platform TAG headers follow `settings.tagging.platformTagHeader` (default true).

Strictness order of dispositions: `allow < require_approval < quarantine < reject`. Mapping from risk actions as in 4. **Revision 1** joins the recommendation and the floor by max only (it can only raise them); facts `risk.*` are maxima/unions over present revisions (P3).

### P12. Snapshot, generation and caching

- `policy_settings` (one row per organization, created lazily by the api) holds `generation BIGINT UNSIGNED` (0 when no row). **Every api transaction that changes what evaluation sees** (publish with activation, activate/rollback, policy enable/disable/delete, settings change) locks the organization's `policy_settings` row `FOR UPDATE` (creating it if absent), applies the change and increments `generation` — one serialization point per organization.
- `PolicySnapshotSource = { generation: string; settings: unknown | null; platformDefaultId: string; policies: [{ publicId, versionNo, definition: unknown, definitionSha256 }] }` = the organization's `email_policies` rows with `status = active`, `deleted_at IS NULL`, `active_version_id` set and the version `status = published` (echo-checked).
- `compileSnapshot` validates each definition again (a definition that no longer validates — e.g. a retired DSL version — is excluded, listed in `invalid`, code `policy.snapshot.invalid_version`, counted and alerted; this can only drop tenant rules, never the platform default or the floor), resolves settings, pre-compiles globs/regexes/CIDRs, sorts rules, computes `snapshotSha256 = sha256(canonicalJson({ generation, platformDefaultId, settings: effective, policies: [{ publicId, versionNo, definitionSha256 }] sorted }))`.
- The engine reads `generation` on the writer **in the evaluation transaction** (echo-checked) for every message and uses a per-process LRU of compiled snapshots keyed `(organizationId, generation)` (`POLICY_SNAPSHOT_CACHE_MAX_ENTRIES`); a miss loads the source in the same transaction. Therefore a change committed before the evaluation transaction reads the generation applies to that message, and a message already evaluated is never re-evaluated by a change (**next-evaluation-only**).

### P13. Where policy runs (ADR-0044): the policy-engine consumer

- `apps/policy-engine` gains `AmqpModule` (broker user `eg-policy-engine`, `RABBITMQ_POLICY_ENGINE_URL`), a `QueueConsumer` of `email.policy.evaluate` (event types `mail.message.scanned.v1`, `mail.message.parse_failed.v1`; prefetch `POLICY_EVALUATE_PREFETCH`; retry policy from the topology; `PrismaConsumerProgress`), `processOnceHandler` with ledger consumer **`policy-engine.evaluate`** and budget `POLICY_DB_TX_TIMEOUT_MS` (≥ 120 000), `S3Service` (mail bucket), metrics (`/metrics`), and readiness checks mysql, redis (existing), rabbitmq, s3.
- **Handler (one writer transaction):**
  1. Validate the envelope payload; organization = envelope `organizationId`; the message row is read by `(id, received_at, organization_id)` inside `transitionMessage`.
  2. First edge: `scanned.v1` `outcome = scanned` → E8 (`policy_decided`); `outcome = scan_failed` → E9 (`scan_failed_fail_safe`); `parse_failed.v1` → E5 (`parse_failed_fail_safe`); actor `{ role: 'policy', service: 'policy-engine', type: 'system' }`, `transitionKey = evt:<eventId>:policy_evaluated`, `expectedRound` = the event's `lifecycleRound` (parse_failed: the message's current round 0), `expectedFrom` = the edge's source. **Not applied** (stale/invalid/duplicate/not_found) → return (ledger row only), `policy_lifecycle_skipped_total{result}`.
  3. Read the facts (P8 rows) on the writer, echo-checked (§6), resolve the directory for the snapshot's references, build the input, evaluate.
  4. Deliver object (P20) and the policy copy if needed (P21).
  5. Insert the `policy_execution_logs` row (P10/§3) — the unique key `(message_id, evaluation_seq, received_at)` with `evaluation_seq = lifecycle round` is the backstop (a duplicate → retryable conflict → redelivered → step 2 is then stale).
  6. Update `email_messages.final_verdict`, `final_action`, `risk_score` (`WHERE id, received_at, organization_id`; one row expected).
  7. Disposition edge via `transitionMessage` (`expectedFrom: ['policy_evaluated']`, same round, key `evt:<eventId>:<to>`): `lifecycleOutcome(result, direction)` (P18).
  8. Outbox rows (P15) and `email_events` rows (`policy.evaluated` with `{ disposition, source, generation, evaluationSeq }`, plus `delivery.approved` per approval as the pass-through wrote).
- Errors: `PolicyInputError` from malformed rows → **not** a silent pass: the evaluation is written as `status = error`? No — rows are engine-written and validated; a malformed row is a defect: the handler throws `NonRetryableError` after recording `policy_input_errors_total` and the event dead-letters (the message stays `scanned` = held; alert `PolicyInputErrors`). Echo-check mismatches and S3 errors are retryable. An exception in `evaluatePolicy` (should be impossible) is treated like an input error.
- **Rescan:** a new round produces a new `scanned.v1` and a new evaluation row; earlier rows are unchanged. **Sandbox revision 1** arriving after evaluation does not re-evaluate (5.3 re-validates on release).
- Outage: messages stay `scanned`/`scan_failed`/`persisted` (no approval exists); the queue buffers (work queue, reject-publish at 1 000 000); on restart the backlog is evaluated with the generation current at evaluation time. The `scanned` lifecycle deadline still expires mail that waits too long (documented in the runbook).

### P17. Policy management lifecycle (api, ADR-0043 decision 7)

- **Policy** (`email_policies`): created with a first draft (`status = draft`, `active_version_id = NULL`). `status`: `draft` (never activated), `active` (has an active published version and is evaluated), `disabled` (has versions, not evaluated), `archived` (soft-deleted: `deleted_at` set; invisible in lists; versions kept for history). `direction`/`priority` columns are copied from the active version's definition at activation (from the newest draft while never activated) for listing and ordering.
- **Versions** (`policy_versions`): `version` = 1, 2, … per policy (MAX + 1 under the `policy_settings` lock); `draft` → editable (`PUT` with `expectedRowVersion`, CAS on `row_version`) and deletable; `published` → **immutable** (repository updates/deletes only `WHERE status = 'draft'`; no route changes a published row). Publishing re-validates and stores `definition_sha256` (= `sha256Hex(canonicalJson(definition))`), `references` (directory ids), `has_override_rules`, `rule_count`, `dsl_version`, `published_at/by`.
- **Activate** = pointer move (`active_version_id`) + `status = active` + `generation++`; **publish** optionally activates (`activate = true` default); **rollback** = activate an earlier published version. **Disable/enable** toggle evaluation (`generation++`). **Delete** soft-deletes (`archived`, pointer kept for history, `generation++` if it was active).
- Every write: writer transaction (`POLICY_TX`, 120 s budget, one retry on `InconsistentPolicyReadError`, then `503 inconsistent_read`), organization from `CurrentScope`, audited (§P22), metrics.

### P19. Action semantics and statuses (ADR-0045)

As in the ADR table. The engine sets each stored action's `status`: ALLOW/QUARANTINE/REQUIRE_APPROVAL/REJECT `enforced`; TAG/WARN `enforced` when written into a delivered policy copy, `recorded` when headers are suppressed (P9.11, `addHeader: false`) or the copy is refused (too large, header block too large, read failure → retried, never silently skipped: only the deterministic size refusals record), `not_applicable` when not delivered; WARN additionally records `bodyBanner: not_supported`; URL_REWRITE `enforced` (rewritten copy delivered, or the quarantine raise), `recorded` (not rewritten, `deliver`); ARCHIVE `requested`; ALERT `requested` (`recorded` when `alerts.enabled = false`); sender notice `requested`.

### P20. Which object an ALLOW delivers

Base object = the round's `url_rewrites` row with `status = rewritten` (writer, echo-checked: message, organization, `received_at`, round, scan, status; key prefix `org/<org>/rewrite/`, no `.`/`..`/empty segment) else `email_messages.eml_object_key`. With header edits → the policy copy of that base (P21). Parse-failure and scan-failure rounds are never ALLOW (floor), so they never deliver.

### P21. The policy copy (header edits only)

- Key: `org/<org>/policy/<yyyy>/<mm>/<dd>/<messageId>/r<round>-<first 32 hex of sha256(baseKey | canonical edits)>.eml` (UTC date of `received_at`); deterministic, so a retry overwrites the same object with the same bytes. Object: `ContentType: message/rfc822`, `ContentDisposition: attachment`, tag `eg-object=policy-copy`; the MinIO/S3 lifecycle rule `eg-policy-copy-expiry` expires tagged objects after `POLICY_COPY_RETENTION_DAYS` (30). Written inside the evaluation transaction before the outbox rows (an object without a committed evaluation is an orphan the lifecycle rule removes).
- Edits (in `apps/policy-engine/src/delivery/policy-copy.ts`, streaming): read the header block up to the first empty line (≤ `POLICY_COPY_MAX_HEADER_BYTES`, else refuse → `recorded`); remove existing `X-EG-Policy-Tag` / `X-EG-Policy-Warning` headers (with continuation lines) from the copy; prepend `X-EG-Policy-Tag: <labels comma-separated>` and/or `X-EG-Policy-Warning: <level>; <text>`; with a subject prefix: insert `<prefix> ` after `Subject:` and its whitespace unless the unfolded value already starts with the prefix; no Subject → add `Subject: <prefix>`; keep line endings of the original (CRLF or LF) and every other byte (body streamed unchanged); lines over 998 octets are folded at the inserted point. Messages larger than `POLICY_COPY_MAX_MESSAGE_BYTES` → no copy, TAG/WARN `recorded` (`policy_copy_total{result="too_large"}`).
- Inbound DKIM signatures covering Subject break downstream (documented, as for URL rewriting); outbound copies are signed afterwards at 10027.

### P25. Notification-worker (minimal, for ALERT and sender notices)

- Consumes `email.notifications` (`QueueConsumer`, ledger `notification-worker.policy`, `processOnceHandler`, budget 120 s) as `eg-notification`. ## 6. Prisma wrong-read mitigation in this step (4.2 §6)

Every deciding read is echo-checked and a mismatch throws `InconsistentPolicyReadError` (retryable, `policy_inconsistent_reads_total{read}`): the message row (inside `transitionMessage`), `email_scans` by id (`id`, `message_id`, `organization_id`, `received_at`, `lifecycle_round`), every child row by scan (`scan_id`, `message_id`, `organization_id`, `received_at`), `message_risk_scores` (also `revision`), `url_rewrites` (also `lifecycle_round`, `status`), lists by message (every row's `message_id`, `organization_id`, `received_at`), `policy_settings` (`organization_id`), policy and version rows (`organization_id`, `policy_id`, `status`), directory rows (`organization_id`). Transaction budgets ≥ 120 s; no socket timeout. The api writers use the 5.1 `RiskWriter` pattern (one retry, then `503 inconsistent_read`); the api readers use the replica and return `409 scan_round_not_complete` while the round is not replicated.

## 7. Alternatives considered

See ADR-0043/0044/0045. Additionally:

- **One evaluation per (message, round, policy version)** as the idempotency key: rejected in favour of `(message, round)`; the lifecycle allows only one decision per round, and a second evaluation of the same round under a newer generation could never apply. The generation is recorded.
- **Wall-clock caching with a TTL** for snapshots: rejected; a published change must apply to the next evaluation, which the per-evaluation generation read guarantees for one indexed read.
- **New `policy_evaluations` table** instead of altering `policy_execution_logs`: rejected; the existing table is partitioned, empty and meant for this, and the brief prefers reuse.
- **Department data from an external directory (LDAP/Graph):** out of scope; the tables are the integration point for a future sync.
- **Per-recipient dispositions:** rejected for 5.2; message-level lifecycle states cannot represent a split, and the strictest-across-recipients rule plus `all` quantifiers for exceptions keeps it safe.
- **Exposing message subject/body conditions:** rejected (content conditions belong to DLP; the policy engine never reads content).

## 8. Risks and mitigations

| Risk                                                         | Mitigation                                                                                                                                  |
| ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------- |
| Policy-engine down → no mail delivered                       | Alert `PolicyEvaluationsStalled`; queue buffers; runbook; Kubernetes replicas ≥ 2 (prefetch-bounded, per-message lock)                      |
| Regression suites relied on the pass-through                 | WP5 rewrites helpers to policy metrics/states; an expectation changes only when the new behaviour is stricter or equal and is listed in §12 |
| Tenant rule weakens protection                               | Floor in code; overrides need a per-rule flag **and** the audited setting **and** a level-only recommendation                               |
| ReDoS / CPU abuse                                            | RE2 only, bounded patterns and subjects, linear globs, bounded documents and rule counts, evaluation duration histogram                     |
| Header injection through tags                                | Labels/prefixes/texts restricted to printable ASCII without CR/LF/`:` (schema), headers built only from policy data                         |
| Spoofed identity used for exceptions                         | Authenticated-identity restriction (P6), Kleene unknown on missing auth                                                                     |
| Department membership changes make dry-runs non-reproducible | Membership is part of the hashed input; `reproducible` reports it                                                                           |
| Backlog of held `scanned` messages evaluated at rollout      | Deployment doc: expected, decided under the current generation; stale ones skipped by the lifecycle                                         |
| ICU/tz data differences between nodes                        | `tzdata_version` recorded; images pin Node; DST tests                                                                                       |
| Policy copy breaks DKIM (inbound Subject)                    | Documented (like URL rewriting); header-only edits; tag headers default without subject prefix                                              |
| Archive requests lost in the dormant buffer                  | Durable evaluation rows; 8.1 reconciles                                                                                                     |
| Legacy demo policy data                                      | Retired by the migration without deleting; seed writes a DSL version                                                                        |

#### Deviations and precisions (with evidence)

1. **No CHECK for "exactly one of address / user_id" (§3 item 6 allowed it only if possible).** MySQL refuses it: probe `ALTER TABLE m ADD CONSTRAINT m_chk CHECK ((address IS NULL) <> (user_id IS NULL))` with `user_id … REFERENCES u(id) ON DELETE CASCADE ON UPDATE CASCADE` → `ERROR 3823 (HY000): Column 'user_id' cannot be used in a check constraint 'm_chk': needed in a foreign key constraint 'm_fk' referential action.` (MySQL 8.4.13). The CASCADE on user delete is required by the design, so the rule is **api-only** (WP4 must enforce it in the department member writer; documented in the model comment, the migration header and schema-reference).
2. **ALTER algorithms** (recorded in schema-reference): `MODIFY final_action` on `email_messages`/`email_recipients` and the 31 `ADD COLUMN` + `MODIFY action` on `policy_execution_logs`: `ALGORITHM=INSTANT` (accepted on the pmax-only clean schema and on the split main schema); `ADD COLUMN` on `email_policies`/`policy_versions`: `INSTANT`; the three `ADD FOREIGN KEY` on those two tables: default = `COPY` (MySQL adds an FK with `foreign_key_checks = 1` only by copying; tiny tables; same choice as steps 4.2/4.3); the three indexes: `INPLACE, LOCK=NONE`; new tables created empty.
3. **NOT NULL columns without defaults on `policy_execution_logs`.** Prisma warns they are impossible on a non-empty table; MySQL actually accepts them with INSTANT and gives existing rows JSON `null` / the first enum member / `''` (probe above). Only perf data could ever hold rows; nothing to backfill.
4. **Reserved words:** `trigger` (`policy_execution_logs`) and `references` (`policy_versions`) are reserved in MySQL 8.4; Prisma quotes them; hand-written SQL (WP3 purge batches, WP4 raw queries) must backtick them. The Prisma field names are the column names (`trigger`, `references`).
5. **Column precisions** where §3 left nullability open: `policy_settings.settings_sha256` NOT NULL (the api computes it on lazy creation; the seed uses `sha256('{}')`); `policy_settings.row_version`, `tenant_departments.row_version` NOT NULL DEFAULT 1; `tenant_departments.public_id` / `tenant_department_members.public_id` have the Prisma-side `@default(uuid(7))` (like `email_policies`); `policy_execution_logs.trace` stays nullable (kept as it was); `decisive_rule_id` VARCHAR(48) (the rule id bound).
6. **`policyDecidedV1` cross-field rules** (P15 lists fields only; added because the contract must never carry an impossible decision): `finalAction` follows `disposition` per P18 (allow → deliver|tag; require_approval → require_approval; quarantine → quarantine; reject → discard inbound, reject outbound/internal); `scanId` null **exactly** for `parse_failed`; `trigger ∈ {scan_failed, parse_failed}` ⇒ `disposition ∈ {quarantine, reject}` (the floor, P9.5); `decisive.source = tenant_rule` ⇔ `policyId`, `versionNo`, `ruleId` all set (platform default and floor name none); `nonTerminalActions` unique, ≤ 5. `policyGeneration` is a decimal **counter** `^(0|[1-9][0-9]{0,19})$` (the envelope's `decimalIdSchema` refuses `0`, but generation 0 = no settings row, P12). `versionNo` 1…4 294 967 295 (`policy_versions.version` is INT UNSIGNED). WP3 must produce payloads accordingly.
7. **`policyNotificationRequestedV1`**: `kind = sender_non_delivery` requires `direction ≠ inbound` and `disposition = reject` (P9.10); `ruleRefs` unique. Rule references match `POLICY_RULE_REF_PATTERN` = lower-case UUID `#` versionNo `/` ruleId (UUIDv7 public ids are lower-case); ≤ 96 chars.
8. **`messageArchiveRequestedV1.ruleRef` nullable** (as P15 writes `string | null`); `source` is the literal enum `['policy']`.
9. **Seed version number on the main schema is 2** (legacy v1 retired), 1 on a fresh database: both asserted (`seed.test.ts` derives the expectation from the legacy rows present). The seed does not validate the definition with `policyDefinitionSchema` (the database package must not depend on policy-dsl); see open items.

Until WP3's consumer runs, its `scanned.v1` / `parse_failed.v1` events accumulate (bounded at 1 000 000, reject-publish) and are evaluated or skipped as stale once it runs; the pass-through keeps approving meanwhile.

#### Deviations and precisions (with evidence)

1. **Result gains `round: { trigger, direction, lifecycleRound, scanId }`.** P10 does not list it, but the row stores `trigger`, `direction`, `evaluation_seq`, `scan_id` and `action` (which needs the direction), and P10 asks for _one_ mapping `evaluationResultToRow(result)`. Without these the mapping could not be a function of the result.
2. **`RiskFacts` gains `failureStatuses` (sorted statuses of the row's `failures[]`) and `sandboxOutcome` (revision 1 `evidence.sandbox.outcome`).** P7 lists neither; the floor reasons `engine_failure` / `unknown_engine` (P9.5) and the field `risk.sandbox_outcome` (P3) need them. `levelOnly` is derived exactly as P7 (`status = scored`, no hard blocks, no failures, every engine `definite`/`skipped` and not `unknown`, no `risk.input.*`/`risk.scoring_error`).
3. **`reasonCodes[0]` is always `decisive.reason`.** §3 has no column for the decisive reason; the view reconstructs it from `reason_codes[0]`. `decisive.versionNo` is reconstructed from `policy_versions` (one version per policy in a snapshot). `notices.senderNonDelivery` is stored as the REJECT action's `params.notifySender` (the effective value) and reconstructed from it. The `trace` column stores `{ entries, truncated }`. Round trip tested for every decision source.
4. **Statuses.** `evaluatePolicy` stays pure and records applicability; `intendedActionStatuses(result)` gives the P19 statuses when every effect succeeds, and `evaluationResultToRow` takes the statuses the engine actually achieved (`AppliedEffects`), plus the delivered object, the copy key and the internal `policy_versions.id` map (the library never sees internal ids).
5. **Action entries.** One disposition entry first (origin = decision source, `params.notifySender` for REJECT), then one TAG entry **per origin** (`tenant_rule`, `platform_default`, `floor`), WARN, URL_REWRITE, ARCHIVE, ALERT — at most 8 (P10 bound 9). Params: TAG `{ labels, headerLabels, subjectPrefix }` (`headerLabels` empty when the header is disabled by `addHeader: false` or platform suppression), WARN `{ level, text, subjectPrefix }`, URL_REWRITE `{ ifNotRewritten, raised }`, ALERT `{ severity, notify }` (`notify = alerts.enabled`).
6. **URL_REWRITE raise.** A URL_REWRITE whose `quarantine` fallback raised the decision keeps applicability `applies` (P19: `enforced` through the hold) although the final is not ALLOW; the decision is `source = tenant_rule`, decisive = the first rule carrying the quarantine fallback, reason `policy.url_rewrite.required`. The floor is applied again after the raise.
7. **Time zones.** P3 says "validated against `Intl.supportedValuesOf('timeZone')`". Evidence (Node 22.23.4, ICU 78.3, tz 2026e): the list has 418 zones, contains `Asia/Calcutta` but **not** `Asia/Kolkata`, and contains neither `UTC` nor any `Etc/*` zone, while `Intl.DateTimeFormat` accepts them (`Asia/Calcutta` resolves to itself, `utc` to `UTC`). Decision: a zone is valid when it matches an IANA name pattern and is listed, or `Intl.DateTimeFormat` resolves it to a listed zone, `UTC` or `Etc/*`. `Asia/Kolkata` is used throughout the tests. DST behaviour was verified against the same ICU data before writing the expectations.
8. **DLP binding is applied whenever the DLP row exists** (not only when the DLP final is `definite`); a definite DLP final without its row → `quarantine` (`policy.floor.dlp_missing`). Stricter than or equal to P9.5 (a row exists only for a definite final in practice).
9. **D2 `malicious` counts as not level-only** (never overridable); `suspicious` counts as level-only (P9.4). With `hb.bec_malicious` enabled (default) the hard block floor decides anyway; if a tenant profile disabled it, D2 still cannot be overridden.
10. **Floor reason dispositions and the decisive floor reason.** `hard_block` carries the strictest mapped hard-block action; `risk_error`, `engine_failure`, `unknown_engine` carry the revision's whole mapped recommendation; one entry per code (strictest). The decisive reason is the strictest, ties in `POLICY_FLOOR_CODES` order (hard_block, risk_error, engine_failure, unknown_engine, dlp_*, risk_missing, scan_failed, not_scanned). The mandatory TAG of a `tag` floor is labelled `risk-<level of that revision>`; the DLP alert tag `dlp-alert`.
11. **Recommendation tag.** `recommendation.tag = (max risk action = tag)` even when D2 raised the disposition; the platform TAG `risk-<max level>` is emitted unless an override applied (the only way P9.9's "unless an override decided" can occur). An override recorded at step 6 stays recorded when the floor later raises the decision (source `floor`).
12. **Three-valued details.** `exists` is two-valued (a missing fact → false, never unknown). A null fact (null sender `<>`, missing domain) makes every other comparison unknown, including `not_in`. `sender.trusted` is `false` (not unknown) for outbound/internal mail. Directory facts of the sender are unknown inbound and when the sender is not authenticated. For `id` fields `in` = some of the address's ids is listed, `not_in` = none is.
13. **Validator.** The strict shape is a hand-written walk (wrapped as `policyDefinitionSchema = z.unknown().superRefine(walk).transform(clone)`) because P2 requires _all_ violations with stable codes and paths through a recursive node union; zod's union errors cannot give per-branch codes. Issue `path` is the single formatted path string; `params.code` is the code. Codes added to the listed ones: `value_required`, `unknown_operator`, `unknown_action`, `quantifier_not_allowed`, `duplicate_action`, `dsl_version_unsupported`, `ai_field_in_exception`, `definition_hash_mismatch` (snapshot only). Over-long regex/glob and over-full lists are `limit_exceeded`; an over-long scalar string is `value_invalid`. Paths sort segment-wise (numeric indices numerically).
14. **Regex.** Items are `"pattern"` or `{ "pattern", "flags": "" | "i" }`. Besides RE2's own refusals, the constructs refused by DLP D9 (backreferences, lookaround, atomic/possessive, conditionals) and nested counted repetition (bound > 100 or product > 1 000, reusing the DLP numbers) are `regex_invalid` before compilation. RE2 inline flag groups such as `(?i)` are accepted (RE2-safe). Globs are case-insensitive.
15. **Time window.** `to` may be `24:00` (end of day); `from = to` is refused (ambiguous). Date ranges are inclusive; dates 1970–9999.
16. **Snapshot.** `compileSnapshot` also excludes (and lists) a policy whose `definitionSha256` does not match `sha256Hex(canonicalJson(definition))`, a malformed public id/version reference and a duplicated policy. `snapshotSha256` hashes every **source** reference (sorted by public id, version), so it identifies the source independent of validation; `versions.policies` lists the valid ones. A malformed generation → `'0'`; an unknown `platformDefaultId` → `pol-default/1` with `policy.snapshot.platform_default_fallback`.
17. **Input builder.** `attachments.count` = number of attachment rows (`message.attachmentCount` stays in `message`); `declaredType` = `normalizeContentType` of the declared type; `detectedType` = the round result's FILE_TYPES id (null without a result); `scan.engines` excludes the asynchronous sandbox (as 5.1); URL hosts of IP kind are canonicalized (RFC 5952); `clientName = unknown` → null; `encrypted` also honours the round result's `archive.encrypted`. Directory maps must be keyed by the normalized address.
18. **Explanation.** Line `params` allow `[`/`]` (for `unless[0]`); the snapshot line is always last; ≤ 24 lines.
19. **Vitest without SWC.** `packages/risk-scoring` (the package to copy) runs vitest without SWC; the library has no decorators, so the same config is used.

For WP4: `rowToEvaluationView` expects the column names of the WP1 Prisma model (`PolicyExecutionLog`); a renamed column must be mirrored in `PolicyEvaluationRowJson`.

#### Deviations and precisions (with evidence)

1. **Read consistency of the snapshot.** P12 says the generation is read "on the writer in the evaluation transaction". It is read with a **consistent (non-locking) read**, like the policies and versions of a cache miss, so the generation and the policy set always come from the same InnoDB read view (taken after the message lock, at the first consistent read inside `transitionMessage`). A locking read of the generation with consistent reads of the policies could have cached an old policy set under a new generation. The api increments the generation in the transaction of every change, so a committed change is either fully visible or not at all; next-evaluation-only holds (integration test "publish between two messages").
2. **Directory addresses.** `normalizeAddress` is not exported by `@email-gateway/policy-dsl`; the engine builds the input once without directory, takes the normalized recipient and authenticated-sender addresses from it, resolves the directory (only when the snapshot references departments or users) and builds again. Same input as one build with the maps; no change to policy-dsl.
3. **`DELIVERY_OUTBOX_*` removed with the pass-through.** The outbox poller served only the pass-through (config comment since 3.2); keeping the keys would leave dead configuration. Removed from the config shape (ignored if set: the worker reads only its own keys), Compose, `.env.example` and the local `.env`. `OutboxPoller` stays in `@email-gateway/common` (not mine) but has **no user** now; the delivery-worker's integration suite no longer exercises it (its unit tests in common remain).
4. **`nonTerminalActions` of `policy.decided.v1`** lists actions whose stored status is `enforced` or `requested` (P15 "applied or requested"); TAG/WARN refused for size or with headers suppressed (`recorded`) are not listed. `finalAction` still follows `lifecycleOutcome` (`tag` when a TAG/WARN applies), as P18 requires.
5. **Sender non-delivery notice** uses `severity: 'info'` (P15 has no rule for this kind) and the REJECT action's rule references. **ARCHIVE `ruleRef`** = the first rule reference of the merged ARCHIVE action.
6. **event-relay image rebuilt.** Adding `email.policy.evaluate` to `RECONCILE_QUEUES` (requested by WP1) made the **running** relay (image built before topology v9) refuse to start (`RECONCILE_QUEUES: entry 9 must be a work queue with a ledger consumer`). It was restored within a minute with the previous value (shell override), then the event-relay image was rebuilt from the current tree (no event-relay code change; v9 support verified by WP1) and recreated with the new list: healthy. `email.notifications` is **not** added (its consumer is WP4's, in progress).
7. **Policy copy upload budget.** No dedicated S3 timeout key exists in §5; the copy runs with `AbortSignal.timeout(POLICY_DB_TX_TIMEOUT_MS / 2)` inside the transaction. Refusals: `ContentLength > POLICY_COPY_MAX_MESSAGE_BYTES` (or counted while streaming) → `too_large`; no empty line within `POLICY_COPY_MAX_HEADER_BYTES` → `header_too_large`. The tag is set on the creating request (`Tagging`), never by a later PutObjectTagging (same reason as the 4.3 rewrite store). A message without a header/body separator is treated as all headers. Header edits are byte-preserving (latin1), a subject value starting on a continuation line gets the prefix alone on the first line.
8. **`policy_floor_raises_total{reason}`** counts each floor reason of a committed evaluation (`result.floor.reasons`), labelled without the `policy.floor.` prefix (bounded list of 12).
9. **`policy_evaluation_duration_seconds`** measures fact reads + snapshot + directory + evaluation; the S3 copy is excluded (it is counted by `policy_copy_total`); `duration_us` in the row is the same measurement.
10. **Parse failures read** the `email_message_parses` row (completion time, `PolicyInputError` when missing or unfinished) and the message's attachments/URLs (none in practice); no scan rows.
11. **A scan row with `scan_kind = release_revalidation`** (enum reserved for 5.3) or not final → `PolicyInputError` (dead letter): `scanned.v1` cannot carry it.
12. **Terraform**: the mail-storage module defines only `expire-processed-mail`, **not** the step 4.3 rewrite rule, so per the WP3 scope no Terraform change was made; `docs/deployment/policy-engine.md` documents both rules to add (open item).

Documented in the route description.
4. **Drafts must validate.** Create/PUT of a draft validate the DSL (`400` with violations) and store hash, references, rule count and override flag already (recomputed at publish); directory references are enforced at **publish, activation and enable** (`400 policy_definition_invalid`, codes `department_unknown` / `user_unknown` with the leaf value path), not for drafts (a draft may be written before its department exists).
5. **Lazy `policy_settings` row.** Created by the first policy or department write (`{}`, `settings_sha256 = sha256(canonicalJson({}))`, generation 0, row version 1): the same effective snapshot as no row. `PUT /policy-settings` accepts `expectedRowVersion` 0 or 1 for a row that was never changed (`GET` shows 0 before the row exists); an identical document writes nothing.
6. **No-op semantics.** Disabling a policy that is not `active` and enabling an `active` policy write nothing; activating the active version of an active policy writes nothing (P17 "exactly once per effective change"); deleting a draft or disabled policy archives it without `generation++`. Activating a version of a `disabled` policy activates the policy.
7. **Additional error codes** (listed above): needed for not-found cases, settings/synthetic-facts validation and directory rules P22 does not name. `policy_input_invalid` is `409` (the stored rows are a defect the engine dead-letters; counted `invalid`). `policy_dry_runs_total{result}` mapping: 404s → `not_found`, `scan_round_not_complete` → `not_complete`, definition/facts/input errors → `invalid`.
8. **Archived policies** answer `404 policy_not_found` on every route (they are invisible) and keep their name (`409 policy_name_taken` for a new policy of the same name, §3 item 1).
9. **Department rules.** Department writes take the `policy_settings` lock (one serialization point with activation, so a department cannot vanish while a version referencing it is activated). `department_in_use` = referenced by the active version of an **active** policy; a disabled policy's version is re-checked when it is enabled. `DELETE /departments/{id}` deletes its members in the same transaction (members reference the department `RESTRICT`). Member addresses are trimmed, normalized like the input builder and need an active, non-deleted `domains.name` of the organization (exact domain); member user ids must be non-deleted users of the organization; "exactly one of" is enforced by the api and the repository (WP1 deviation 1).
10. **Test targets.** `platform` = the platform default with the tenant's settings and generation and no tenant policies; `{ definition }` is added as policy `00000000-0000-7000-8000-000000000000` version 1 (`compileSnapshot` needs a UUID and a version ≥ 1); `{ policyId, versionNo }` replaces (or adds) that policy with a draft or published version. `evaluationTime` defaults to the request time (P23 comment). `resolveDirectory: true` resolves memberships of the facts' recipients and senders as in precision 2.
11. **History.** `from` inclusive, `to` exclusive, `to - from ≤ POLICY_HISTORY_MAX_RANGE_DAYS` (`400`); `overrideApplied` takes `true`/`false`; row `messageId` = the message public id from `message_identities` (null if gone); `decisive.versionNo` from the row's `policy_versions` JSON; `actions` = `{ type, status }`.
12. **Scans `policy` per round** is matched by `scan_id`; parse-failure evaluations (no scan) appear only in `GET /messages/{id}/policy-evaluations`.
13. **Metrics.** `policy_changes_total{operation}` operations: `created, updated, enabled, disabled, deleted, draft_created, draft_updated, draft_deleted, published, activated, settings_updated, department_created, department_updated, department_deleted, member_added, member_removed`.
14. **Notification recipients and Message-ID.** One message per event (P25's single deterministic `Message-ID`), all recipients as Bcc (no To header: administrators do not see each other). Alert recipients need a role of the organization or a system role holding `policy:publish` assigned in that organization. The portal link uses the message **public id** (`PORTAL_PUBLIC_URL/messages/<publicId>`), not the decimal event id.
15. **Notification results.** No `NOTIFY_SMTP_HOST` → `disabled` (ledger committed, nothing sent). An event whose message is not the envelope organization's (or was purged) → `NonRetryableError('message_not_found')` → dead-letter, counted `failed`. SMTP failures (`NoticeSendError`) are retryable (default classification) and counted `failed` per attempt; the integration test proves 451 → retry → `sent`.
