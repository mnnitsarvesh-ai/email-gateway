**What 5.3 enforces, plainly** (details in the ADRs and the decisions below):

- **Enforced:** every QUARANTINE and REQUIRE_APPROVAL disposition creates per-recipient quarantine entries in the policy-engine's evaluation transaction; per-recipient dispositions when tenant rules are recipient-scoped (some recipients delivered, others held or rejected); manual quarantine (from review and from a policy rejection); tenant-scoped search; a sanitized, DLP-masked preview behind its own permission; downloads only through single-use, short-lived grants after password re-authentication, never of malicious content; release with authoritative re-validation (latest round's risk revisions 0 and 1, the current published policy, signature/verdict staleness) and approval for hard blocks, engine failures, DLP holds and policy rejections, by a second authorized user; reject; delete refused under legal hold or retention; bulk limits; expiry that never releases; per-user digests and admin alerts through the notification-worker; an audit trail of every view, preview, download, release, reject, delete, approval and expiry; WARN body banners and URL rewriting after the scan in the delivered policy copy.
- **Recorded only:** a WARN banner on a signed or encrypted message (`skipped_signed` / `skipped_encrypted`), on a part that cannot be edited safely or on a message over the size bound; URL_REWRITE when the message cannot be rewritten (signed, encrypted, too large, structure mismatch).
- **Not in 5.3:** admin-portal screens (7.x); webhooks and a general notification service (6.2); archiving, journaling, legal-hold management APIs and archive retention evaluation beyond the conservative rules of Q17 (8.1); post-delivery clawback from mailboxes (8.2); defanged-archive downloads; one-click release links in mail.

## 2. Decisions

### 2.0 Invariants (never traded away)

1. **No message content in MySQL from this step.** Entries, actions, release logs, approvals, grants, digests, events, logs and metrics hold ids, enums, codes, integers, hashes, addresses already stored by earlier steps (envelope sender, header From, recipient) and operator-typed reasons. Never body text, attachment bytes or URLs. `quarantine_messages.subject` (1.1) is retired: never written. A subject is read from `email_messages.subject` at response time only where Q10/Q20 allow it.
2. **Message bytes stay in S3.** The api never returns an S3 URL (presigned or not). Content leaves only through the preview (sanitized JSON) and the download door (Q12).
3. **Tenant from the authenticated context.** Every api route takes the organization from `CurrentScope`; end-user routes additionally restrict to the caller's own verified address. Another tenant's or another user's entry is `404`, never `403`.
4. **A release never weakens the floor without a second person.** Hard blocks, engine failures, DLP holds, missing data and a current policy REJECT can be released only through an approval by a different, authorized user (never the requester, never the entry's recipient, never an end user, never an API key). Malicious content is never served by the download door.
5. **Never release on expiry.** Expiry ends an entry as `expired`; the object is kept or purged per retention and legal hold.
6. **Idempotent and ordered.** Entries are unique per `(message, lifecycle round, recipient)`; every api mutation takes an `Idempotency-Key`; the executor and sweeper are idempotent under redelivery; every entry write is a compare-and-set on `row_version` under the message lock.
7. **The lifecycle has one door.** Message state changes only through `@email-gateway/message-lifecycle`; recipient state (`email_recipients.status`) and entry state are written in the same writer transaction as the message transition.
8. **Never claim enforcement that did not happen** (ADR-0045 statuses carry over: banners and policy URL rewrites record `skipped_*` reasons).

### Q2. Who writes the store (ADR-0046 decision 1)

**The policy-engine's evaluation transaction writes the entries** (the same writer transaction that inserts the `policy_execution_logs` row and applies E11/E12/E10), not a consumer of `email.quarantine`. Reasons: the entry, the lifecycle edge, the recipient states and the approval rows commit atomically (no window where a message is `quarantined` without entries or approved without its held recipients being held); no lossy dormant buffer; idempotency is the existing evaluation idempotency plus the entry unique key. `mail.policy.decided.v1` stays an analytics/firehose event; its binding to `email.quarantine` is removed. **`email.quarantine` becomes the work queue of the release executor** (topology v10, Q27).

### Q3. Entry model and state machine

One `quarantine_messages` row ("entry") per `(message, lifecycle round, recipient)`.

- `kind`: `quarantine` (QUARANTINE disposition, manual quarantine) or `review` (REQUIRE_APPROVAL disposition).
- `origin`: `policy`, `manual`, `adopted` (Q8).
- `state` (`QuarantineStatus`, migrated forward, §3): `held`, `pending_approval`, `releasing` (transient: a release is queued for the executor), `released`, `rejected`, `deleted`, `expired`, `superseded` (a later round re-decided the recipient). Terminal: `released`, `rejected`, `deleted`, `expired`, `superseded`. `releasing` and `superseded` are additions to the brief's list, documented in ADR-0046.

Transitions (`ENTRY_TRANSITIONS`, data; anything else is refused with `409 quarantine_state_conflict`):

| From                       | To                 | Cause                                                                                                       |
| -------------------------- | ------------------ | ----------------------------------------------------------------------------------------------------------- |
| (create)                   | `held`             | policy QUARANTINE, manual quarantine, adoption of a `quarantined` message                                   |
| (create)                   | `pending_approval` | policy REQUIRE_APPROVAL (with a `policy_review` approval request), adoption of a `held_for_review` message  |
| `held`                     | `pending_approval` | release needs approval; release request (user or end user)                                                  |
| `held`                     | `releasing`        | release queued (operator with no approval reasons, or self-release allowed)                                 |
| `pending_approval`         | `releasing`        | approval granted                                                                                            |
| `pending_approval`         | `held`             | request denied (`release_request`, `release_approval`), cancelled or expired; manual quarantine of a review |
| `releasing`                | `released`         | executor dispatched the approval                                                                            |
| `releasing`                | `held`             | executor blocked (state, rescan required, self-release no longer allowed)                                   |
| `releasing`                | `pending_approval` | executor found approval reasons not covered (a new `release_approval` request is created)                   |
| `held`, `pending_approval` | `rejected`         | reject; deny of a `policy_review` request                                                                   |
| `held`, `pending_approval` | `deleted`          | delete (Q17)                                                                                                |
| `rejected`, `expired`      | `deleted`          | delete (object purge request, Q17)                                                                          |
| `held`, `pending_approval` | `expired`          | sweeper (Q19)                                                                                               |
| any non-terminal           | `superseded`       | a later round's evaluation of the message (rescan)                                                          |

Every transition: entry row `SELECT … FOR UPDATE` after the message lifecycle lock (`lockLifecycle`: lock order message → entries → approval requests), `UPDATE … WHERE id AND row_version` (CAS), one `quarantine_actions` row, `state_changed_at`, and the recipient status of Q5.

### Q4. Per-recipient evaluation (ADR-0046 decision 2; `policy-dsl`)

- New tenant policy setting `recipientSplit: boolean` (default **true**, `policyTenantSettingsSchema`, part of the snapshot hash).
- `snapshotHasRecipientScopedRules(compiled, direction)`: true when any enabled candidate rule of the direction (or a policy-wide exception of its policy) references `recipient.address`, `recipient.domain`, `recipient.local_part`, `recipient.department` or `recipient.user` in `when` or `unless`.
- `evaluatePolicyPerRecipient(input, compiled): PerRecipientEvaluation`:
  1. `message = evaluatePolicy(input, compiled)` (unchanged semantics; stored as today).
  2. No split when `settings.recipientSplit = false`, no recipient-scoped rule, `input.recipients.length ≤ 1`, `input.recipientsTruncated`, or `input.recipients.length > POLICY_LIMITS.splitRecipients` (new limit **200**; reason code `policy.split.too_many_recipients`). Result `{ split: false, uniform: true, message, recipients: null, lifecycleDisposition: message.disposition }`.
  3. Otherwise for each recipient `r` (ascending `rcptSeq`): `evaluatePolicy(restrictToRecipient(input, r.rcptSeq), compiled)` where `restrictToRecipient` keeps every field and sets `recipients = [r]` (`message.recipientCount` unchanged). The floor and the recommendation are message-level facts, so every per-recipient result is at least the floor.
  4. `effective(r) = perRecipient[r].disposition`; `split = distinct(effective).size > 1`; the **lifecycle disposition** = `strictest(effective)` when not split (it can differ from `message.disposition` for quantifier-`all` rules; the stored row keeps `message` as the decision record and adds `recipientDecisions`), and the Q5 split mapping otherwise. Result `{ split, uniform: !split, message, recipients, lifecycleDisposition }`.
  5. Non-terminal actions of the delivered copy = the merge (P9.9 merge rules) of the non-terminal actions of every **allowed** recipient's result (one copy per round; a recipient may see a TAG triggered by another recipient's rule; documented). ARCHIVE/ALERT from the merge over all recipients.
  6. Output `recipientDecisions: [{ rcptSeq, disposition, source, decisiveRuleRef | null, reasonCodes (≤ 8) }]` (≤ 200).
- `POLICY_EVALUATOR_VERSION = 'policy-eval/2'` (per-recipient, Q23 rewrite eligibility, banner fields). `policy-input/1` is unchanged. Dry-run (api) uses `evaluatePolicyPerRecipient` too and reports `recipientDecisions`.
- Explanation: a new line code `split` (`{ allowed, held, review, rejected }` counts); never addresses.

### Q5. Lifecycle mapping, recipient state vs message state (ADR-0046 decision 3)

Let A, Q, H, X be the recipients whose effective disposition is allow, quarantine, require_approval, reject (all recipients when not split).

| Case                       | Message edge            | Reason (new: `policy_partial`)   | `final_action` (new value `partial`) | Recipients                                                                   |
| -------------------------- | ----------------------- | -------------------------------- | ------------------------------------ | ---------------------------------------------------------------------------- |
| all A                      | E10 → `approved`        | `policy_deliver`/`policy_tag`    | `deliver`/`tag`                      | stay `pending`; approvals                                                    |
| all Q                      | E11 → `quarantined`     | `policy_quarantine`              | `quarantine`                         | `quarantined`; entries `held`                                                |
| all H                      | E12 → `held_for_review` | `policy_hold`                    | `require_approval`                   | `quarantined`; entries `pending_approval` + one `policy_review` request each |
| all X                      | E13 → `rejected`        | `policy_discard`/`policy_reject` | `discard`/`reject`                   | `discarded` (new in 5.3; no entry)                                           |
| split, A ≠ ∅               | E10 → `approved`        | `policy_partial`                 | `partial`                            | A `pending` + approvals; Q/H `quarantined` + entries; X `discarded`          |
| split, A = ∅, Q ≠ ∅        | E11 → `quarantined`     | `policy_quarantine`              | `partial`                            | Q/H `quarantined` + entries; X `discarded`                                   |
| split, A = ∅, Q = ∅, H ≠ ∅ | E12 → `held_for_review` | `policy_hold`                    | `partial`                            | H `quarantined` + entries; X `discarded`                                     |

`email_recipients.final_action` is set per recipient (`deliver`/`tag`/`quarantine`/`require_approval`/`discard`/`reject`). The message state is the **delivery-phase view** (what happens to the message as a whole next); each recipient's fate is its `email_recipients.status` plus its entry. `deriveDeliveryState` already treats `quarantined`/`discarded` as settled, so a split message ends `delivered` (`delivery_partial`) after A is delivered, while Q/H entries stay `held`.

Lifecycle table changes (`packages/message-lifecycle`, ADR-0046 decision 4):

- E10 reasons += `policy_partial`.
- E16 (`held_for_review → quarantined`, `review_quarantined`), E17 (`quarantined → rejected`, `quarantine_deleted`), E18 (`held_for_review → rejected`, `review_rejected`): produced by 5.3 (role `quarantine`). E17/E18 are applied when the last non-terminal entry of the message ends in `rejected`/`deleted` and no recipient is `pending`, `deferred` or `delivered` (reason `quarantine_deleted` for deletes **and** rejects from `quarantined`; `review_rejected` from `held_for_review`).
- E26 roles += `quarantine` with new reason `quarantine_expired` (`reasonRoles`: `deadline_exceeded` → `sweeper`, `quarantine_expired` → `quarantine`): the quarantine sweeper expires a `quarantined`/`held_for_review` message whose last entries expired.
- **E28 (new)** `delivered | rejected | expired → approved`, role `quarantine`, reason `quarantine_partial_release`, **new round**: releasing a held recipient after the rest of the message finished (partial delivery, all other recipients failed, or the delivery deadline expired). ADR-0025's "final states" stay final for automatic processing; E28 is an explicit operator-caused re-entry like E14.
- **E29 (new)** `rejected → quarantined`, role `quarantine`, reason `manual_quarantine` (same round): manual quarantine of a policy-rejected message (Q7). Allowed only when `status_reason ∈ {policy_reject, policy_discard}`.
- E14/E15 stay (role `quarantine` used by the executor; the api operator role no longer uses them, Q30).
- `LIFECYCLE_REASON_CODES` += `policy_partial`, `quarantine_partial_release`, `manual_quarantine`, `quarantine_expired` (append). `transitions.test.ts`, `one-door.test.ts` and the docs diagram (`docs/architecture/diagrams/11-message-state-machine.md`) are updated.

Release by message state (executor, Q13.5): `quarantined` → E14 (new round); `held_for_review` → E15 (new round); `approved`, `delivery_pending`, `delivery_retry` → **no transition**, the approval carries the message's current round (the planner plans approvals of `approved`/`delivery_*` messages of that round); `delivered`, `rejected` (`delivery_failed` or E17 with other held entries), `expired` → E28 (new round); `scanning`, `scanned`, `scan_failed`, `policy_evaluated`, `persisted` → blocked `message_busy` (a re-decision is in progress; entries will be superseded); `archived` → blocked `message_archived`.

Rescan interplay: E19 is unchanged (from `quarantined`, `held_for_review`, …); since the closing round (§13.9) the operator route `POST /messages/{id}/rescan` from `quarantined`/`held_for_review` also requires `quarantine:release` (`403 quarantine_rescan_forbidden`; the audit row records `quarantineEntriesSuperseded`), because a clean new round delivers the held recipients. The evaluation of round _m_ (policy-engine, same transaction): (1) every non-terminal entry of the message with `lifecycle_round < m` → `superseded` (and its pending approval requests → `cancelled`); (2) every recipient of the message with status `quarantined` → `pending` (they are re-decided); then Q5 applies to the recipients that are `pending`.

### Q6. Entry creation (policy-engine evaluation transaction, WP3)

For each Q/H recipient (Q5), `INSERT … ` with `createMany({ skipDuplicates: true })` on the unique `(message_id, lifecycle_round, rcpt_seq)` (a duplicate evaluation is already stopped by the lifecycle edge; the key is the backstop). Columns from the writer rows and the evaluation result (§3): ids, round, scan id, `evaluation_seq` (= round), recipient id/seq/address (lower-cased), `user_id` (the organization's active, not deleted user whose `email` equals the address, resolved with the existing directory lookup; informational only, Q15 scopes by address), direction, kind, origin `policy`, `reason = quarantineReasonFor(result, recipientDecision)`, envelope sender, header From, `has_attachments`, `attachment_count`, `size_bytes`, risk (max over revisions: score, level, recommended action, verdict), `hard_blocks` (ids, ≤ 9), `reason_codes` (≤ 32), `floor_reasons` (≤ 16), `primary_engine`, decisive source/policy public id/version/rule id, `explanation` (the evaluation's line codes, ≤ 24) and `explanation_text` (≤ 2048, the policy explanation; content-free by construction, P10), `eml_object_key` (the **original** EML), `quarantined_at` = evaluation time, `expires_at = computeExpiry`, `state`, `row_version = 1`.

- `quarantineReasonFor`: the strictest present cause in this order: floor `hard_block` with a malware hard block (`hb.malware*`, attachment malicious) → `malware`; phishing verdict/hard block → `phishing`; BEC deterministic suspicious/malicious → `bec`; DLP floor or DLP-decisive rule → `dlp`; floor `engine_failure`/`unknown_engine`/`risk_error`/`risk_missing`/`scan_failed`/`not_scanned` → `engine_unavailable`; tenant rule decisive → `policy`; risk verdict `spam` → `spam`, `bulk` → `bulk`; else `suspicious`. Table-tested.
- `primaryEngineFor`: enum `rspamd | attachment | url | bec | dlp | sandbox | policy | none` from the decisive cause (hard block engine, failing engine, DLP, tenant rule → `policy`).
- REQUIRE_APPROVAL entries get one `quarantine_approval_requests` row each (`kind = policy_review`, `requested_by_type = system`, `approval_reasons = ['review', …approvalReasonsFor(result)]`, `expires_at = entry.expires_at`), entry `approval_request_id` set.
- Outbox: when review entries were created and `alerts.approvalRequests` is on, one `mail.quarantine.notification_requested.v1` (`kind = approval_requested`, ≤ 50 request ids) per evaluation; when an entry has a hard block and `alerts.hardBlocks` is on, nothing per message (the sweeper's rate-bounded `admin_alert`, Q20, covers it).
- `quarantine_actions`: one `quarantine` row per entry (actor system, `details = { origin, evaluationSeq }`). `email_events`: `quarantine.created` (`{ entries, kind }`).
- Metrics `quarantine_entries_created_total{origin,kind,reason,direction}`, `policy_recipient_split_total{result}` (`split`, `uniform`, `not_scoped`, `disabled`, `too_many`).

### Q7. Manual quarantine (api, WP4)

`POST /api/v1/quarantine/entries` (`quarantine:manage`, Idempotency-Key) `{ messageId, rcptSeqs?: int[] (≤ 1000; default all eligible), reason: string 1..512 }`:

- message `held_for_review`: the selected `pending_approval` review entries become `kind = quarantine`, `state = held`, `origin` unchanged, their `policy_review` requests → `cancelled`; when no review entry remains non-terminal → E16 (`review_quarantined`).
- message `rejected` with `status_reason ∈ {policy_reject, policy_discard}`, within `QUARANTINE_MANUAL_FROM_REJECT_MAX_DAYS` (default 30, 1–60) of `received_at`, and the EML object present (HEAD): E29 → `quarantined` (same round); one entry per selected recipient (`origin = manual`, `kind = quarantine`, `reason = manual`, facts and decisive data copied from the round's evaluation row, `expires_at` from now); recipients `discarded → quarantined`. A later release of such an entry re-validates; the current policy still says reject → approval reason `policy_reject` (Q13).
- any other state → `409 quarantine_state_conflict` (no clawback of delivered mail; 8.2).
- Audited `quarantine.manual_quarantined`; `quarantine_actions` `quarantine` per entry.

### Q8. Adoption of messages held before 5.3 (policy-engine sweeper, WP3)

Messages in `quarantined`/`held_for_review` whose current round has no entry (held by 5.2, or fixtures) are adopted by the sweeper: entries for every `pending`/`quarantined` recipient, `origin = adopted`, kind from the state, facts from the round's `policy_execution_logs` row when present (else `reason = policy`, empty explanation, `primary_engine = none`), recipients → `quarantined`, `expires_at = max(now + 1 day, computeExpiry(received_at))`, review entries with `policy_review` requests. Bounded batches (`QUARANTINE_SWEEP_BATCH_SIZE`), `quarantine_adopted_total`. Idempotent (unique key; message lock). Candidates must have a `pending`/`quarantined` recipient, or nothing live and no open entry: such a message (for example a quarantine-expired message rescanned by an operator, whose recipients are all `discarded`, so the new round creates no entry) ends `expired` again (E26 `quarantine_expired`, purge re-decided) instead of being selected on every pass (§13.9).

### Q9. Search (api, replica, WP4)

`GET /api/v1/quarantine/entries` (`quarantine:read`) and `GET /api/v1/quarantine/me/entries` (`quarantine:self`, Q15):

- Filters (all optional except the range): `from`, `to` (ISO, on `quarantined_at`, required, `to - from ≤ QUARANTINE_SEARCH_MAX_RANGE_DAYS` (62)), `state[]`, `kind`, `direction`, `reason[]`, `riskLevel[]` (or `minRiskLevel`), `primaryEngine[]`, `policyId` (decisive public id), `ruleId`, `sender` (exact envelope or header From address, normalized), `senderDomain`, `recipient` (exact address), `hasAttachments`, `hasHardBlock`, `messageId`. No free-text or subject search (OpenSearch is 6.x/ADR-0009).

Response `{ items, nextCursor | null }`; no total count (bounded `count` only via `GET /quarantine/summary`, Q26).

- Item DTO `QuarantineEntrySummary` (Q26). `subject` is included only when the caller holds `quarantine:preview` or is the entry's own recipient (self routes), read from `email_messages.subject` (replica join by `(message_id, message_received_at)`), sanitized (control and bidi characters removed, ≤ 256 characters).

### Q11. Preview with sensitive-content controls (ADR-0048, WP2 renderer, WP4 route)

`GET /api/v1/quarantine/entries/{entryId}/preview` (`quarantine:preview`; self route Q15 when `endUser.preview`), `Cache-Control: no-store`, rate `QUARANTINE_PREVIEW_RATE_PER_MINUTE` per principal.

- Sources (never the raw EML, so malformed MIME is never parsed in the api): headers from `email_headers` (the 3.1 allow-list), the decoded text part (`.text`) and/or HTML part (`.html`) from `email_message_parses`, attachments from `email_attachments` + the latest scan round's `attachment_scan_results`, URLs from `message_urls` + `url_scan_results`. S3 reads use a **Range GET** of at most `QUARANTINE_PREVIEW_MAX_BODY_BYTES` (256 KiB) per part, prefix-checked (`org/<org>/part/`). Parse outcome not `parsed` or a missing body key → `body.unavailableReason` (`not_parsed`, `too_large`, `no_text_part`, `purged`).
- `renderPreview` (pure): prefers the text part; the HTML part is converted to text with parse5: `script`, `style`, `noscript`, `template`, `head`, `object`, `embed`, `iframe`, `frame`, `svg`, `math`, `form` subtrees dropped; comments dropped; `img`/`picture`/`video`/`audio` replaced by `[image]`/`[media]` (no `src`, no data URI, no CSS); block elements become line breaks; anchors become `text [link N]` and the link is listed separately; entities decoded; output normalized (NFC), C0/C1 controls except `\n`/`\t` removed, bidi overrides (U+202A–U+202E, U+2066–U+2069) and zero-width characters removed, ≤ `QUARANTINE_PREVIEW_MAX_TEXT_CHARS` (100 000) characters, `truncated` flag. **The response is JSON text only; never HTML** (the portal renders it as text).
- Links: `{ n, displayUrl (defanged: `hxxp(s)://`, `[.]` in the host, ≤ 256 chars), host (defanged), verdict | null }` (≤ 200); **not clickable**, never rewritten, never fetched.
- Attachments: `{ partIndex, filename (sanitized, ≤ 128), declaredType, detectedType, typeFamily, sizeBytes, sha256, verdict, reasonCodes, downloadable: boolean }` — listed, never served here.
- DLP masking: `maskDlp` runs the `@email-gateway/dlp` built-in detectors (every detector, independent of tenant DLP configuration; masking needs no Aadhaar basis because it reveals nothing) over the subject, the body text and the header values, and replaces each match with the `@email-gateway/dlp` mask of its detector (cards first 6 + last 4, everything else fully masked with `•`); `dlp: { masked: count, categories }`. Unmasked values exist only behind `dlp:evidence_read` (4.5).
- Audit: `quarantine_actions` `preview` + audit row `quarantine.previewed` (`{ entryId, bodySource, truncated, masked }`) **committed before** the parts are read (like 4.5 D16); a failure afterwards adds `quarantine.preview_failed` (reason code only).
- Entries with `state = deleted` and a purged object → `410 quarantine_content_purged`.

### Q12. Download door (ADR-0048)

Default **not offered**: tenant setting `download.enabled` (default `false`) **and** permission `quarantine:download` (not held by any system role except super admin and organization admin) are both required.

1. `POST /api/v1/quarantine/entries/{entryId}/download-grants` (`quarantine:download`, `@UserOnly()`, `@RequireMfa()`, rate `QUARANTINE_DOWNLOAD_GRANTS_PER_HOUR` (20) per user) `{ object: 'eml' | 'attachment', partIndex?: int, password: string, totpCode?: string }`: **fresh re-authorization** — the password is verified with the auth module's password service (and a TOTP code when the user has MFA enrolled), failures count toward the login lockout and answer `401 quarantine_reauth_failed`; then malware gating (below); then a `quarantine_download_grants` row (`jti` UUIDv7, organization, user, entry, object, part index, `expires_at = now + QUARANTINE_DOWNLOAD_TOKEN_TTL_SECONDS` (60, 10–300)), audit `quarantine.download_granted`. Response `{ token, expiresAt, filename, sizeBytes, sha256 }`.
2. Token `qdl1.<b64url(payload)>.<b64url(mac)>`, payload `{ v:1, jti, org, usr, ent, obj, part, exp }`, `mac = HMAC-SHA256(QUARANTINE_DOWNLOAD_TOKEN_KEY, "eg-quarantine-download/v1\0" ‖ payload bytes)`, constant-time verification (`signDownloadToken`/`verifyDownloadToken`).
3. `GET /api/v1/quarantine/downloads/{token}` (`quarantine:download`, authenticated **user** session; rate per user): verify MAC and expiry; `org`/`usr` must equal the caller; atomically consume the grant (`UPDATE … SET consumed_at = now WHERE jti = ? AND organization_id = ? AND user_id = ? AND consumed_at IS NULL AND expires_at > now`, one row expected, else `410 quarantine_download_token_used` / `404 quarantine_download_token_invalid`); re-run the malware gating; stream the object (S3 GET, organization prefix check, size ≤ `QUARANTINE_DOWNLOAD_MAX_BYTES`) with `Content-Type: application/octet-stream`, `Content-Disposition: attachment; filename="<sanitized>.eml.bin|.bin"`, `X-Content-Type-Options: nosniff`, `Cache-Control: no-store`, `Content-Security-Policy: sandbox; default-src 'none'`. Audit `quarantine.downloaded` (or `quarantine.download_refused` with the reason).
4. **Malware gating** (`checkDownloadable`): refused (`409 quarantine_download_blocked`, reason) when the entry or the message has any hard block, the latest round's verdict is `malware` or `phishing`, or — for an attachment — its latest-round verdict is not `clean` (suspicious, malicious, error, skipped or missing all refuse) or its object key is NULL; for the EML — any attachment not `clean`, or any URL `malicious`. **No defanged archive in 5.3** (ADR-0048).
5. End users never download (no `quarantine:download` on `mailbox_user`). API keys never download.

### Q13. Release with re-validation (ADR-0047)

**13.1 API (WP4).** `POST /api/v1/quarantine/entries/{entryId}/release` (`quarantine:release`, Idempotency-Key) `{ reason: 1..512, expectedRowVersion?: int }`; self route Q15. In one writer transaction (`QUARANTINE_TX_TIMEOUT_MS` 120 s, one retry on an inconsistent read, then `503 inconsistent_read`): Idempotency-Key lookup → message lock → entry lock (CAS) → state must be `held` → **pre-check** = the re-validation of 13.3 on **replica** facts (`PolicyFactsRepository` + the api's snapshot loader + `evaluatePolicyPerRecipient` restricted to the entry's recipient) → outcome:

- `rescan_required` → `409 quarantine_rescan_required` `{ staleness }` (nothing written but the audit row `quarantine.release_refused`);
- `approval_required` → a `release_approval` request (requester = caller, `approval_reasons`), entry → `pending_approval`, notification `approval_requested`, `202 { outcome: 'approval_requested', approvalRequestId, approvalReasons }`;
- `release` → a `quarantine_release_logs` row (`status = pending`, `release_public_id`, `mode = operator`, `precheck` JSON), entry → `releasing`, outbox `mail.quarantine.release_requested.v1`, `202 { outcome: 'queued', releaseId }`.
  The pre-check is advisory (fast feedback); the executor decides. Audit `quarantine.release_requested` with the outcome.

**13.2 Executor (WP3, policy-engine `quarantine` role).** Consumes `email.quarantine` (`mail.quarantine.release_requested.v1`; tolerates and ignores stale `mail.policy.decided.v1` with a counter), ledger `policy-engine.quarantine`, one writer transaction per event (`QUARANTINE_DB_TX_TIMEOUT_MS` ≥ 120 s): lock message → lock the release's entries (must be `releasing`, same release id; else ledger only, `quarantine_releases_total{result="stale"}`) → message-state check (Q5) → **authoritative re-validation** on writer facts (13.3) with `mode` from the release (`operator`, `self`, `approved` + `approvedReasons`) → outcome:

- `release`: build the delivered object (13.6, S3 write before commit), apply the lifecycle edge for the state (Q5), recipients `quarantined → pending`, `mail.delivery.approved.v1` (`source = quarantine_release`, `deliverySeq` = highest + 1, the round after the edge, chunks ≤ 1000, `emlS3Key` = the release copy or base), entries → `released` (`released_at`, `released_by_*` from the release), release log → `dispatched` (`revalidation` JSON, `delivered_object`, `object_key`, `delivery_seq`, `approval_event_ids`, `lifecycle_round_after`), `quarantine_actions` `release`, `email_events` `quarantine.released` + `delivery.approved`, notification `approval_decided`/none.
- `approval_required` (new reasons): release log → `approval_required`, entries → `pending_approval` with a new `release_approval` request (requester = the release's requester, in `approved` mode the approved request's requester; for `self` mode: entries → `held`, log `refused`, no request), notification `release_blocked` to the requester.
- `rescan_required` / `message_busy` / `message_archived`: release log → that status, entries → `held`, notification `release_blocked`.
  Metrics `quarantine_releases_total{result,mode}`, `quarantine_release_duration_seconds`.

**13.3 Re-validation (`decideRelease`, pure, `@email-gateway/quarantine`).** Inputs: the entry (kind, reason, state, recipient), the **latest completed scan round** of the message (`email_scans` with `completed_at`, the greatest `lifecycle_round`), the policy input built from that round's rows (both risk revisions 0 and 1, P8) restricted to the entry's recipient, the **current** compiled snapshot (current generation) → `evaluatePolicyPerRecipient` → that recipient's result; staleness facts; the message state; `mode`; `approvedReasons`; tenant settings; platform bounds. Output `{ outcome: 'release' | 'approval_required' | 'rescan_required' | 'refused', approvalReasons[], refusal?, staleness, summary }` where `summary = { disposition, source, decisiveRuleRef, floorReasons, hardBlocks, level, score, recommendedAction, generation, snapshotSha256, inputSha256, evaluatorVersion, scanId, scanCompletedAt }` (stored in the release log; content-free).

- **Approval reasons** (`APPROVAL_REASONS`): `hard_block`, `engine_failure`, `risk_error`, `risk_missing`, `dlp_require_approval`, `dlp_quarantine`, `dlp_block`, `dlp_missing`, `scan_failed`, `not_scanned` (from the result's floor reasons; an unknown-engine floor of `tag` is not a reason), `policy_reject` (the current policy disposition for the recipient is `reject`), `review` (entry kind `review`: REQUIRE_APPROVAL always needs an approver), `stale_verdict` (13.4 when a rescan is impossible), `no_scan_round` (adopted entries without a completed round).
- `mode = operator`: no reasons → `release`; reasons → `approval_required`.
- `mode = approved`: `approvalReasons ⊆ approvedReasons` → `release`, else `approval_required` (the new reasons only).
- `mode = self` (Q15): any reason, a reason not allowed, a level above the bound, or staleness → `refused` (`self_release_not_allowed`, with the cause).
- `release.allowHardBlocks = false` (tenant) and `hard_block` present → `refused` (`hard_block_release_disabled`) in every mode.
- A current disposition of `quarantine`/`require_approval` without floor reasons is **not** an approval reason: releasing quarantined mail against the policy's opinion is the operator's job (recorded).

**13.4 Staleness.** `stale = (hasAttachments ∨ hasUrls) ∧ now − scanCompletedAt > QUARANTINE_RELEASE_MAX_VERDICT_AGE_HOURS (72)` **or** `hasScannedAttachments ∧ newestClamavDb.firstSeenAt − scanCompletedAt > QUARANTINE_RELEASE_SIGNATURE_MAX_LAG_HOURS (24)` (newest `scan_signature_versions` row of `attachment/clamav_db`). Stale and the message state is an E19 source (`quarantined`, `held_for_review`) → `rescan_required` (the operator calls the existing `POST /messages/{id}/rescan`; the new round re-decides and supersedes the entries); stale otherwise (delivery-phase or final states, where a rescan is impossible) → approval reason `stale_verdict`.

**13.5 Lifecycle per state:** Q5 table.

**13.6 Delivered object of a release.** Base = the latest scan round's `url_rewrites` row with `status = rewritten` (echo-checked) **if its object still exists** (HEAD), else the original EML (amends 4.3 U20: the copy of the re-validated scan round is reused, never another round's; documented in ADR-0049). Edits = `releaseDeliveryEdits(result, settings)` (new `policy-dsl` helper: the TAG/WARN/URL_REWRITE edits the result would apply **if** the recipient were allowed, i.e. P9.9–P9.11 ignoring applicability) plus a release header `X-EG-Quarantine-Release: <release public id>`. Then Q22/Q23 build a policy copy `org/<org>/policy/<yyyy>/<mm>/<dd>/<messageId>/r<roundAfter>-<32 hex of sha256(baseKey | canonical edits | releaseId)>.eml` (tag `eg-object=policy-copy`). A release always produces a policy copy (the header is always added). Copy refusals (size, header block) → the base object is delivered and TAG/WARN/banner are `recorded` in the release log, as P21.

### Q14. Approval workflow (ADR-0047)

One table `quarantine_approval_requests`, one model for policy REQUIRE_APPROVAL (`policy_review`), releases that need approval (`release_approval`) and user requests (`release_request`).

- Request: created by the policy-engine (policy_review), by a release (release_approval) or by `POST …/{entryId}/request-release` (`quarantine:request_release`, or the self route) `{ reason }` → `release_request` (approval reasons computed by the pre-check, stored). One `pending` request per entry (enforced under the entry lock: entry `approval_request_id` and `state = pending_approval`).
- `GET /api/v1/quarantine/approvals` (`quarantine:read`; filters `status`, `kind`, `from/to`, cursor) and `GET …/approvals/{approvalRequestId}`.
- **Approve** `POST …/approvals/{id}/approve` (`quarantine:approve`, `@UserOnly()`, `@RequireMfa()`, Idempotency-Key) `{ reason }`: `checkApprover` refuses (`403 quarantine_approval_forbidden`, reason code) when the approver is the requester (the requesting user id, or for a request made with an API key the key's `created_by_user_id`: `isAccountableRequester`, §13.9), the entry's recipient (`user_id` or own verified address equals the recipient), lacks `quarantine:approve`, or the request is not `pending`/expired (`409 quarantine_approval_not_pending`). Then the api re-runs the pre-check in `approved` mode; request → `approved` (`decided_by`, `decision_reason`, `approved_reasons` = the request's reasons ∪ the pre-check's), entry → `releasing`, release log (`mode = approved`, `approval_request_id`), outbox release event; the executor re-validates (13.2) — reasons that appeared after the approval need a new approval, whose requester is the approved request's requester (never the approver who queued the release, §13.9).
- **Deny** `POST …/{id}/deny` (`quarantine:approve`, same SoD) `{ reason }`: `policy_review` → entry `rejected` (as Q16, including recipient `discarded` and the E18 rule); `release_approval`/`release_request` → entry `held`. Notification `approval_decided` to the requester (user requesters only).
- **Cancel** `POST …/{id}/cancel` by the requester (or `quarantine:approve`) → `cancelled`, entry `held` (a `policy_review` cannot be cancelled: `409`).
- **Expire**: the sweeper expires `pending` requests at `expires_at` (`release_*`: `now + approvals.requestTtlHours`; `policy_review`: the entry's expiry) → `expired`, entry `held` (release requests) or entry `expired` (policy_review, Q19); notification `approval_decided` (`expired`).
- Separation of duties is checked in the api **and** re-checked by the executor against the stored request (requester ≠ decider, decider held `quarantine:approve` at decision time is recorded as `decider_permissions_hash`; the executor trusts the stored decision but refuses a release log whose `approval_request_id` is not `approved`).
- Audit: `quarantine.approval_requested`, `.approval_approved`, `.approval_denied`, `.approval_cancelled`, `.approval_expired` (system).

### Q15. End-user self-service (ADR-0047)

- New system role **`mailbox_user`** ("Mailbox User") with the single permission `quarantine:self`. Routes under `/api/v1/quarantine/me/…` require `quarantine:self` and a **user** principal with a verified email; the scope is `organization_id = scope ∧ recipient_address = lower(user.email)` (plus `endUser.enabled`). API keys and platform overrides are refused (`403`). An entry of another address → `404`.

### Q16. Reject

`POST /api/v1/quarantine/entries/{entryId}/reject` (`quarantine:reject`, Idempotency-Key) `{ reason, notifySender?: boolean }`: entry (`held`/`pending_approval`) → `rejected` (pending request → `cancelled`), recipient → `discarded`, E17/E18 when it was the last non-terminal entry and no recipient is pending/deferred/delivered. Sender notice (ADR-0045): only for `outbound`/`internal` entries, when `notifySender ?? settings.notices.senderOnReject` (default true), as `mail.quarantine.notification_requested.v1` `kind = sender_rejected`; the notification-worker sends it only when the envelope sender's domain is an active domain of the organization. **Inbound: never** (no backscatter). Audit `quarantine.rejected`. Object disposal is scheduled by Q17's rules (no explicit delete needed).

### Q17. Delete subject to retention and legal hold

`POST /api/v1/quarantine/entries/{entryId}/delete` (`quarantine:delete`, Idempotency-Key) `{ reason }` (`held`, `pending_approval`, `rejected`, `expired` → `deleted`). `decideObjectDisposal` (pure) is evaluated in the transaction on writer facts:

1. **Legal hold** (refuse, `409 quarantine_legal_hold`): any `archive_legal_holds` row of the organization with `status = active` whose `criteria` match the message. 5.3 understands only the strict subset `{ custodians?: string[] (addresses), from?: date, to?: date }` (match = no custodians or the recipient/sender is one of them, and `received_at` within the range); **criteria it cannot parse match everything** (fail-safe). 8.1 owns the full criteria language.
2. **Retention** (refuse, `409 quarantine_retention_active` `{ retainUntil }`): `archive_settings.enabled` and its `scope` covers the direction, and `received_at + max(retention_days of the organization's archive_retention_policies)` > now (5.3 does not evaluate `criteria`; the maximum is conservative); or an `email_archives` row of the message with `retain_until > now` or `legal_hold = true`.
3. **Archive pending**: an evaluation of the message has ARCHIVE `requested` and no `email_archives` row exists → the logical delete is allowed, the object purge is **deferred** (`retained`, reason `archive_pending`) until 8.1 archives it.
4. **Shared object**: the EML is the message's; it is purged only when **every** entry of the message is terminal and not `released`, and no recipient is `pending`, `deferred` or `delivered`; otherwise the entry is deleted and the purge stays `retained` (`shared`).

Allowed → entry `deleted`, recipient `discarded`, E17/E18 as Q16, and a `quarantine_object_purges` row (`pending`, `purge_after = now`). The sweeper (Q19) re-checks 1–4 at purge time and deletes the EML, the message's part objects (prefix `org/<org>/part/<yyyy>/<mm>/<dd>/<messageId>/`), rewrite copies (`…/rewrite/…/<messageId>/`) and policy copies (`…/policy/…/<messageId>/`), then sets `purged`, `quarantine_messages.object_purged_at` on the message's entries; failures are retried (`attempts`, `last_error_code`). The message metadata rows stay (retention of the core tier). Audit `quarantine.deleted` / `quarantine.delete_refused` (reason); system `quarantine.object_purged` / `.object_retained`.

**Tenant purge** (`tenant-data` organization purge, WP4): refused while any active legal hold exists for the organization; otherwise deletes the quarantine tables in RESTRICT-safe order (grants, approval requests, release logs, actions, purges, digests, preferences, entries, settings) in batches; S3 objects follow the organization deletion runbook (deferred job, 1.2).

### Q18. Bulk actions

`POST /api/v1/quarantine/bulk` (Idempotency-Key) `{ action: 'release' | 'reject' | 'delete' | 'approve' | 'deny', ids: string[] (entry ids; approval request ids for approve/deny), reason, notifySender? }`:

- Limits: `1 ≤ ids ≤ QUARANTINE_BULK_MAX_ITEMS` (100, bound 1–500) per request (`400 quarantine_bulk_limit`), unique ids; per organization per minute `QUARANTINE_BULK_MAX_ITEMS_PER_MINUTE` (1 000, 10–10 000) items, a Redis fixed-window counter incremented by the item count before work (`429 quarantine_bulk_rate_limited`, `Retry-After`); plus the route rate limit `QUARANTINE_BULK_REQUESTS_PER_MINUTE` per principal (20).
- The route requires the action's permission (`quarantine:release` / `:reject` / `:delete` / `:approve`); approve/deny additionally `@UserOnly()` + MFA.
- Each item runs the **same service method** as the single-item route in **its own writer transaction** (same re-validation, SoD, CAS, audit), sequentially, with a per-request deadline (`QUARANTINE_BULK_DEADLINE_MS` 25 s; unprocessed items → `skipped/deadline`).
- Response `200 { action, results: [{ id, status: 'queued' | 'approval_requested' | 'done' | 'refused' | 'not_found' | 'skipped', code?, releaseId?, approvalRequestId? }], counts }` (partial failure is reported per item, never as an HTTP error); the whole response is stored under the Idempotency-Key. One audit row `quarantine.bulk` (`{ action, itemCount, counts }`) plus the per-item rows.

### Q19. Expiry and maintenance sweeper (policy-engine `quarantine` role, WP3)

Leader-elected (`GET_LOCK('eg:quarantine-sweeper')` on a dedicated connection, like the 4.5 evidence sweeper), every `QUARANTINE_SWEEP_INTERVAL_MS` (60 s), bounded batches (`QUARANTINE_SWEEP_BATCH_SIZE` 200), each message in its own writer transaction under the message lock:

1. **Entry expiry**: `state IN (held, pending_approval) AND expires_at <= now` (index `(state, expires_at)`) → `expired` (pending requests → `expired`), recipient → `discarded`; when no non-terminal entry remains and no recipient is pending/deferred/delivered and the message is `quarantined`/`held_for_review` → E26 (`quarantine_expired`). **Never** releases. Object: a `quarantine_object_purges` row (`pending` when Q17 rules 1–4 allow, else `retained` with the reason and `purge_after = retainUntil` when known).
2. **Approval-request expiry** (Q14).
3. **Object purge** (Q17) of `pending` rows with `purge_after <= now` (re-checked), and re-evaluation of `retained` rows whose `purge_after` passed.
4. **Adoption** (Q8).
5. **Digest and admin-alert scheduling** (Q20).
6. **Entry row retention**: terminal entries whose `state_changed_at` is older than `QUARANTINE_ENTRY_RETENTION_DAYS` (186, ≥ the 6-month core tier) are hard-deleted with their actions, release logs, grants and approval requests (batched); when the message's registry row is below `MIN(email_messages.id)`, the `message_identities` row is deleted in the same transaction (D3.4 contract).

Hold period: `holdDays = clamp(organization_settings.quarantine_retention_days, 1, QUARANTINE_MAX_HOLD_DAYS)` (default 30; `QUARANTINE_MAX_HOLD_DAYS` 60, bound 7–80 and **validated `< LIFECYCLE_DEADLINE_QUARANTINED_HOURS / 24`** so the lifecycle backstop never fires first); review period `review.days` (default 7, 1–`QUARANTINE_MAX_REVIEW_DAYS` 13, validated `< LIFECYCLE_DEADLINE_HELD_FOR_REVIEW_HOURS / 24`). `expires_at` is fixed at creation (a settings change applies to new entries). Metrics `quarantine_expired_total{kind}`, `quarantine_approvals_expired_total`, `quarantine_purges_total{result}`, `quarantine_sweep_duration_seconds`, `quarantine_sweep_last_success_timestamp_seconds`, gauge `quarantine_entries{state}` (non-terminal states only, refreshed each sweep with one grouped count on `(state, expires_at)`), `quarantine_pending_approvals`.

### Q20. User notifications (WP3: scheduler and notification-worker)

Event `mail.quarantine.notification_requested.v1` (Q27) on `email.policy` → `email.notifications` → notification-worker (ledger `notification-worker.policy`, unchanged consumer name, new handler by event type).

- **User digest** (`kind = user_digest`): scheduler (sweeper step 5) computes due schedule instants with `nextDigestWindows(organization_settings.digest_schedule, organization_settings.timezone, last scheduledFor, now, maxPerDay = 24)` for organizations with `digest_enabled` and `endUser.enabled`; per due instant one `quarantine_digest_runs` row (unique `(organization_id, kind, scheduled_for)`; at most one per hour: coalesced) and, for each user with `held`/`pending_approval` entries addressed to their verified email and created in `(previous scheduledFor, scheduledFor]`, not opted out, a `quarantine_digests` row (unique `(run_id, user_id)`) and one outbox event (`{ digestId, userId, window }`) — ≤ `QUARANTINE_DIGEST_MAX_USERS_PER_RUN` (5 000) per sweep, continued next sweep. Organizations are paged with a keyset cursor (`organization_id > cursor`, wrapping to the lowest id; `QUARANTINE_SWEEP_BATCH_SIZE` per sweep), so every organization with open entries is reached within ⌈organizations / batch⌉ sweeps; when the user budget runs out inside an organization the next sweep starts there; admin alerts run for every examined organization regardless of the budget; the cursor is in the leader's memory (a new leader starts at the lowest id) (§13.9). The worker reads the entries on the writer at send time (≤ `digest.maxEntries`, default 50, bound 1–200) and sends one plain-text mail to the user: per entry received time, envelope sender, subject (sanitized, ≤ 78 characters; only when `digest.includeSubject`, default true), reason, expiry, and the portal link `PORTAL_PUBLIC_URL/quarantine/me/<entryId>`; never body, attachments or URLs. Links **require login**; no one-click release (Q30, ADR-0047).
- **Approval requested** → active, verified users holding `quarantine:approve` (excluding the requester), ≤ `NOTIFICATION_MAX_RECIPIENTS`, Bcc; ids, reason categories and approval reasons, link to `/quarantine/approvals/<id>`.
- **Approval decided / release blocked** → the requesting user (not API keys).
- **Admin alert** (`admin_alert`): scheduler step 5 emits at most one per organization per `alerts.minIntervalMinutes` (default 60, 15–1 440) when new hard-block entries (`alerts.hardBlocks`) or pending approvals older than 1 hour exist; recipients as approval requested; counts and a link only.
- **Sender rejected** → Q16.
- Message-ID `<quarantine-notice.<eventId>@<from domain>>`, at least once, `notification_quarantine_messages_total{kind,result}`. Tests use the `mail-sink` sink only.

### Q22. WARN body banners (ADR-0049; `mail-safety` + policy-engine)

- `insertWarningBanner({ source, sink, level, text | null, limits, structure })` streams the object (mailsplit Splitter → editor → Joiner): the **first** inline, filename-less `text/plain` and the first `text/html` leaf of the primary body (outside `message/rfc822`, not under `multipart/related` attachments other than the HTML root) are buffered (≤ `POLICY_BANNER_MAX_PART_BYTES` 1 MiB encoded), decoded (CTE, charset; ASCII-compatible charsets only, lossless round trip), edited, and re-encoded with the **original CTE** (7bit/8bit with a line > 998 octets → quoted-printable, header updated), like the 4.3 rewriter. Text: `"[<LEVEL>] <text or fixed template>\r\n" + "-" × 40 + "\r\n\r\n"` prepended (line ending of the part). HTML: a `<div role="alert" style="…inline, no url()…">` with the escaped text inserted right after the `<body …>` start tag (parse5 source offsets), or at the start when there is no body tag. Fixed templates per level (`caution`, `warning`, `danger`); the rule `text` (P2 HeaderText) is HTML-escaped; never message data.
- Message-level skips (the object is passed through unchanged, result recorded): `skipped_signed` (`multipart/signed`, `application/pkcs7-signature`, inline PGP signature), `skipped_encrypted` (`multipart/encrypted`, `application/pkcs7-mime`, PGP), `skipped_too_large` (message > `POLICY_COPY_MAX_MESSAGE_BYTES`), `skipped_no_text_part`, `skipped_part` (charset/decode/size of every candidate part). Signed/encrypted detection reuses `signedOrEncrypted`/`inlinePgp` from `@email-gateway/url-security` on `email_message_parses.structure` and the first 64 KiB of the candidate parts.
- Result `{ status: 'applied' | 'skipped_*', partsEdited }`; stored in the evaluation row's `delivery.bodyBanner` (values extended: `requested` by the evaluator, the engine replaces it with the outcome; `not_supported` remains for 5.2 rows) and the action status (`enforced` when applied, `recorded` otherwise). DKIM: an inbound DKIM signature covering the body no longer verifies downstream (as with URL rewriting; documented).

### Q23. URL_REWRITE after the scan (ADR-0049)

- Rewriting happens in the **policy-engine**, in the policy copy pipeline, with `rewriteEml` from `@email-gateway/url-security`: the tenant's URL rewrite settings (resolved like the email-worker's url engine settings, inspected in `apps/email-worker/src/scanning/url-config.ts` and `settings-resolver.ts`, except that `enabled` and `direction` are forced on), the round's `message_urls` (`url_seq`, truncated flag, identity hash) as the URL map, the click base URL and tokens signed with `URL_TOKEN_KEY_CURRENT` (expiry per 4.3 settings from the evaluation time). **Key custody widens to the policy-engine (sign only; ADR-0049 amends ADR-0030).** The click-service needs no change.
- When: URL_REWRITE applies, the delivered base is not a rewritten copy, and the round's skip reason is `disabled` or `direction` (the evaluator now treats these as _policy-rewritable_: no `ifNotRewritten = quarantine` raise for them). Any other skip (`signed_*`, `encrypted`, `too_large`, `dkim_policy`, `structure_mismatch`, `parse_incomplete`) cannot be fixed by the policy. If the policy rewrite itself skips deterministically and the rule says `ifNotRewritten = quarantine`, the engine **re-evaluates** with the input's `urls.rewriteSkipReason` set to the policy rewrite's skip reason (deterministic; the stored row records `delivery.urlRewrite.policyAttempt`, and the dry-run of such a round reports `reproducible: false` with that cause). `no_urls` counts as satisfied. A transient error is retryable.
- Order in the copy pipeline: base → URL rewrite (Q23) → banner (Q22) → header edits (P21). Metrics `policy_url_rewrite_total{result}`, `policy_body_banner_total{result}`.
- **The 4.3 tenant setting remains**: scan-time rewriting is still the default path; policy rewriting only fills the gap when a tenant rule demands it.

## 6. Prisma wrong-read mitigation (4.2 §6)

Every deciding read is echo-checked and a mismatch throws a retryable `InconsistentQuarantineReadError` (`quarantine_inconsistent_reads_total{read}`): entry rows (`id`, `organization_id`, `message_id`, `row_version` after lock), approval requests (`organization_id`, `quarantine_message_id`), release logs (`release_public_id`, `organization_id`), grants (`jti`, `organization_id`, `user_id`), the latest scan round (`message_id`, `organization_id`, `received_at`, `lifecycle_round`, `status`), every fact row of 5.2 §6 (the policy-engine reuses its `facts.repository.ts`), `quarantine_settings` and `organization_settings` (`organization_id`), legal holds/retention policies (`organization_id`). Transaction budgets ≥ 120 s; api writers retry once, then `503 inconsistent_read`; replica reads used only for search, views, the release pre-check and previews.

## 7. Alternatives considered

- **Store driven by a consumer of `mail.policy.decided.v1` on `email.quarantine`:** rejected (ADR-0046): a window where the message is `quarantined` with no entry, a lossy buffer, a second transaction to reconcile, and per-recipient approvals that must commit with E10.
- **Release executed synchronously in the api:** rejected: the release copy needs URL token signing and S3 streaming of up to 25 MiB; key custody would reach the internet-facing api. The api pre-checks synchronously for feedback; the executor decides.
- **Rescan automatically on a stale release:** rejected for 5.3 (a hidden second workflow; the portal can chain "rescan, then release").
- **Separate `quarantine-worker` codebase:** rejected; the executor reuses the policy-engine's facts reader, snapshot cache, evaluator and copy pipeline. Failure isolation comes from two Deployments of one image (Q28).
- **Per-recipient TAG/WARN edits (one copy per recipient group):** rejected (copies multiply; one merged copy per release/round).
- **Presigned S3 URLs for downloads:** rejected (bearer URLs leak through logs and browsers; no single use; no user binding).
- **Defanged archive (password-protected ZIP) of malicious attachments:** rejected for 5.3 (ADR-0048).
- **Preview by parsing the raw EML in the api:** rejected; the decoded parts already exist (3.1), so untrusted MIME is never parsed again in the api.
- **New approval table separate from REQUIRE_APPROVAL:** rejected; one model (Q14).
- **Keeping `quarantine_messages.subject`:** rejected (content in MySQL); the column stays retired, never written.
- **Dropping and recreating the quarantine tables:** rejected (forward migration; data preserved).
- **Message-level only decisions (5.2):** replaced; per-recipient decisions are required by the brief.

### 9.3 Stack (`tests/integration/quarantine-smtp.test.ts`, WP5, through Postfix and the live containers)

1. GTUBE (outbound) and a tenant QUARANTINE rule (inbound) → entries per recipient (`held`, reason, rule, level), message `quarantined`, nothing delivered.
2. Per-recipient rule (`recipient.address in [a]`): `a` quarantined (entry), `b` delivered; message `delivered` (`delivery_partial`); later release of `a` → E28, delivered once to `a` only.
3. Release re-validates: an operator release of the tenant-rule entry → `dispatched`, the delivered copy carries `X-EG-Quarantine-Release` and the policy edits; the release log holds the re-validation summary.
4. EICAR (inbound, allowed through a REQUIRE_APPROVAL/quarantine path or manual quarantine from the policy rejection) → release → `approval_requested` (`hard_block`); approve by the requester → `403 quarantine_approval_forbidden`; approve by a second admin → delivered.
5. Reject (outbound entry) → `rejected`, sender notice in mail-sink; inbound reject → no notice.
6. Delete → `deleted` and the EML purged by the sweeper; with an active legal hold row → `409 quarantine_legal_hold`, object kept.
7. Expiry: an entry with a past `expires_at` (settings fixture) → `expired`, never delivered, message `expired` (E26 `quarantine_expired`).
8. Digest: a `mailbox_user` with held entries receives a digest in mail-sink (sender, subject, portal link; no body).

#### Deviations and precisions (with evidence)

1. **114 tables, not 115.** §3 lists seven new tables (items 4–9: approval requests, download grants, settings, user preferences, object purges, digest runs, digests); 107 + 7 = 114. Main and the clean schema both count 114 (`information_schema.TABLES`, base tables without `_prisma_migrations`), 31 partitioned. The suites and docs say 114.
2. **Migration authoring.** `migrate dev --create-only` refuses a non-interactive shell (output above); `migrate diff` (from the migrations with the shadow database, and from the main URL) produced identical SQL with two defects: it dropped `quarantine_messages_organization_id_fkey` (its index was being replaced) **without re-adding it**, and it added `yara_rules_organization_id_fkey`, which exists on main (the committed schema diffs empty against main). #### Deviations and precisions (with evidence)

- **D1 Cron library:** Q1 names `cron-parser`; the package implements its own 5-field evaluator (allowed by the WP2 brief) so the accepted grammar is **exactly** the api validator's (`5/10` refused, names case-insensitive, `0`/`7` Sunday, ≤ 64 chars) — a unit test imports `apps/api/.../settings-validation.ts` and compares 20 000 random expressions. DST resolution follows `Temporal` `compatible` (gap → shifted after the gap, overlap → first occurrence); day-of-month/day-of-week use the Vixie OR rule when both are restricted. `isValidTimeZoneName` applies the api's IANA shape rule (no `+05:30`, no abbreviations).
- **D2 Digest windows (Q20 precision):** coalescing keeps an instant only when it is ≥ 1 hour after the previous kept instant (or the last run), so a `*/15` schedule yields hourly runs whose windows chain without gaps; the first run (no previous `scheduledFor`) covers `now − 24 h`; instants older than 48 hours are not run separately (their entries fall into the first window); more than `maxPerDay` due runs keep the latest ones and the first returned window starts at the last run, so no entry is lost.
- **D3 Extra workspace dependencies:** `quarantine` → `risk-scoring` (`RISK_HARD_BLOCKS` verdicts drive the reason table; levels/actions order); `mail-safety` → `bec` (the `Deadline` the DLP structure scanners take), `security-contracts` (`DLP_DETECTORS` categories, `FILE_TYPE_FAMILIES`), `quarantine` (one display-text sanitizer); `policy-engine` → `url-security` (Q23 rewriting/signing, so wave 2 needs no dependency). No new third-party package or version.
- **D4 `effectivePolicySettingsSchema.recipientSplit` is optional** in that schema (the TypeScript type `PolicyTenantSettings` and `resolvePolicySettings` always have it): the api builds its catalog `settingsDefaults` literal without it (`apps/api/src/modules/policies/domain/policy-definition.ts:360`) and would otherwise stop type-checking. WP4 should add `recipientSplit` there.
- **D5 `POLICY_FINAL_ACTIONS += 'partial'`** (mirrors the 5.3 `MessageAction`; `lifecycleOutcome` never returns it). Evidence: with WP1's schema the api failed `policy-history.service.ts(64)` (`MessageAction` not assignable); fixed by this vocabulary change.
- **D6 Defect fix (5.2, ADR-0043 "AI never holds"):** the new per-recipient property test (seed `20261112`) found a rule reading `bec.verdict` with `URL_REWRITE ifNotRewritten = quarantine` that raised a skipped round to QUARANTINE with that rule decisive. The schema refuses only disposition actions in AI rules, so the evaluator now ignores the quarantine fallback of AI-derived rules (clamp `{ ref, from: 'quarantine', to: <final>, reason: 'ai_only' }`, `policy.clamp.ai_only`). The schema is unchanged so no stored definition becomes invalid. Covered by a unit test and both property tests.
- **D7 Decision record annotation:** `PerRecipientEvaluation.message` is `evaluatePolicy(input)` plus the `policy.split.*` code (appended, decisive code stays first) and, when evaluated per recipient, the `split` explanation line before `snapshot` (24-line bound kept). `not_scoped` and `single_recipient` leave it byte-identical to `evaluatePolicy`; `disabled`, `truncated`, `too_many` add their code only when recipient-scoped rules exist.
- **D8 Not evaluated per recipient:** `recipientDecisions = []` (the row column is NULL via `perRecipientToRowFields`); `recipientDecisionFor` / `resultForRecipient` fall back to the message result, so callers handle both cases with one call. `outcome` has two values beyond the five metric labels (`single_recipient`, `truncated`); mapping in the API section.
- **D9 Stored-view compatibility:** result/view schemas accept `policy-eval/1` and `policy-eval/2`, `bodyBanner: 'not_supported'`, and `rowToEvaluationView` adds `policyRewritable: false` to 5.2 deliveries; the evaluator always emits `policyRewritable` and `policyAttempt: null`.
- **D10 `quarantineReasonFor` / `primaryEngineFor` signature precision:** hard-block ids, BEC, attachment, URL and engine facts are input facts (not in `PolicyEvaluationResult`), so the first argument is `{ result, input?, hardBlocks? }`; adopted entries without the input pass the stored `hard_blocks`. Precisions: malware also for `finalVerdict = 'malware'`; phishing = any hard block whose 5.1 verdict is phishing (`known_phishing`, `tenant_domain_spoof`, `url_tenant_blocked`, `dmarc_reject`) or the phishing verdict; engine-failure causes count only when the floor holds (an unknown-engine `tag` floor never makes an entry `engine_unavailable`); a DLP-decisive tenant rule is one whose matched trace leaf is a `dlp.*` field. Engines: auth-based hard blocks → `rspamd`; failing engine → the first `timeout`/`error`/`missing` engine of the round.
- **D11 `approvalReasonsFor(result, input?)`:** with the input, each floor reason's own disposition is recomputed (`computeFloor`) and allow-level reasons (unknown-engine `tag`, DLP `alert`) are dropped exactly; without it, floor reasons count when the floor as a whole holds. `policy_reject` = any current `reject` disposition (also from the floor, next to `hard_block`).
- **D12 `decideRelease` precisions:** refuses `quarantine_state_conflict` when the entry is not `held`/`releasing` (operator/self) or `pending_approval`/`releasing` (approved); order: hard blocks disabled → self-mode bounds (the higher of the stored and the re-validated level; `level_unknown` refuses) → stale with an E19 source state → `rescan_required` → operator/approved. Self mode never returns `rescan_required` (staleness refuses). `releaseLifecycleFor` treats `received` as busy.
- **D13 Self-service codes:** API keys, missing `quarantine:self` or no verified email → `code: 'forbidden'` (the api's generic 403; Q26 has no dedicated code); `endUser.enabled = false` → `quarantine_entry_not_found` (nothing is visible).
- **D14 Disposal precisions:** `email_archives.legal_hold = true` refuses with `quarantine_retention_active` and `retainUntil: null` (rule 2 as written); retention needs at least one retention policy; `entries` must describe the state **after** the action; date-only legal-hold bounds are whole UTC days.
- **D15 Download token precisions:** `org`/`usr`/`ent` accept public UUIDs or decimal ids; `exp` in epoch seconds, valid while `exp > now`; payload bytes are JSON with the fixed key order of Q12; canonical base64url only; the key is ≥ 32 bytes (hex string or Buffer).
- **D16 Banner contract:** a skip destroys the sink (mirroring `rewriteEml`) instead of copying the bytes through; the delivered object is still unchanged because the caller keeps its input (`insertWarningBannerBuffer` returns it). There is no `error` status: unexpected failures are thrown (retryable). `application/pkcs7-mime; smime-type=signed-data` is `skipped_signed` (url-security maps every pkcs7-mime to encrypted). When the HTML has no `<body>` start tag in the source (parse5 implies one without a location) the banner goes at offset 0. Inside `multipart/related` only the first child is a candidate. Fixed templates: caution "Be careful with this message. Check the sender before you open links or attachments.", warning "This message may be unsafe. Do not open links or attachments unless you trust the sender.", danger "This message is likely dangerous. Do not click links, open attachments or reply with information."
- **D17 Preview precisions:** text and HTML-derived URLs are shown inline defanged with `[link N]` (deduplicated by normalized identity); header values and the subject are defanged without numbers; order sanitize → defang → mask → cut so hidden characters cannot split a URL or a value; when a part was cut (by the caller's range read, `maxHtmlChars`, the node budget), the trailing partial token and trailing digit groups are dropped so a cut value is never shown partially; extra limits `maxHtmlChars` 1 MiB, `maxHtmlNodes` 200 000, `maxHeaders` 64, header values/subject 998; `title`, `select`, `textarea`, `button`, `applet`, `base`, `link`, `meta` are dropped too.
- **D18 DLP masking scope:** value detectors only (PC1, BA1–BA3, NI1, NI2, PP1, PP2, PI1–PI4, CR1–CR5); keyword/classification detectors (CF1, CF2, FI1, DC1, SC1) mark documents, and CU1 is tenant configuration. Every candidate is masked whatever its confidence or context requirement; a mask is at most 64 `•`; cards show the digits only (separators dropped). Known test card numbers are not detected by `@email-gateway/dlp` (its own exclusion list) and therefore not masked.
- **D19 DTO precisions:** `messageId` is the decimal message id (as in the other message routes); `decisive.source` is nullable (adopted entries without an evaluation row).

2. **Approval expiry**: `release_*` → `expired`, entry back to `held`, `approval_expired` action, `approval_decided (expired)` to a user requester; `policy_review` → the entry expiry of step 1.
3. **Purge**: due `pending`/`retained`/`failed` rows re-decided under the message lock; `now` → every EML key of the entries and the message checked `org/<org>/…`, then every version of the EML and of `org/<org>/{part,rewrite,policy}/<yyyy>/<mm>/<dd>/<messageId>/` deleted, row `purged`, entries `object_purged_at`, `object_purged` actions, `quarantine.object_purged`; failures → `failed`, `attempts`, `last_error_code`, `purge_after` backoff (1 min … 6 h).
4. **Adoption** (Q8): `quarantined`/`held_for_review` messages without entries of their current round; entries for `pending`/`quarantined` recipients, `origin = adopted`, kind from the state, facts from the round's evaluation row (`rowToEvaluationView`) or `policy`/`none`, `expires_at = max(now + 1 day, computeExpiry(received_at))`, recipients `quarantined`, `adopt` actions, `policy_review` requests.
5. **Digests and admin alerts** (Q20): organizations with open entries; `nextDigestWindows(schedule, timezone, last run, now, 24)` → `quarantine_digest_runs` (`createMany skipDuplicates`); unfinished runs continued; per eligible user (active, verified, not deleted, e-mail = an entry's recipient address in the window, not opted out when `allowOptOut`) one `quarantine_digests` row + one `user_digest` event (pre-allocated event id stored on the row), ≤ `QUARANTINE_DIGEST_MAX_USERS_PER_RUN` per pass; admin alert rate-bounded by an `admin_alert` run row per `alerts.minIntervalMinutes`.
6. **Retention**: terminal entries older than `QUARANTINE_ENTRY_RETENTION_DAYS` with their release logs, actions, approval requests, grants; when the message has no entry left, its `purged` purge row and (id below `MIN(email_messages.id)`, no live `email_archives`) its `message_identities` row (D3.4 contract); grants expired > 1 day; digest runs > 90 days.

Gauges `quarantine_entries{state}` (grouped count of non-terminal states) and `quarantine_pending_approvals`; `quarantine_sweep_duration_seconds`, `quarantine_sweep_last_success_timestamp_seconds` (only when every step succeeded), `quarantine_expired_total{kind}`, `quarantine_approvals_expired_total`, `quarantine_purges_total{result}`, `quarantine_adopted_total`, `quarantine_entries_retention_deleted_total`, `quarantine_settings_invalid_total`, `quarantine_inconsistent_reads_total{read}`.

#### Deviations and precisions (with evidence)

1. **Stale `mail.policy.decided.v1` on `email.quarantine` are not acked by the executor.** `QueueConsumer` (packages/common) refuses at construction any event type not bound to the queue (`event type … is not bound to queue …`), and topology v10 binds only `release_requested.v1`; its codec dead-letters an unaccepted type as `unknown_event_type` before any handler runs. So the "ignore with a counter" of Q13.2 cannot be implemented in the engine without changing packages/common or the topology (not this package). Instead `docs/deployment/quarantine.md` drains the v9 buffer before the first quarantine-role start (`purge_queue email.quarantine`, safe because no release event can predate 5.3) and the runbook says to discard such dead letters. WP1 recorded 0 messages in the local queue. No counter is registered (a counter that can never move would be a false claim).
2. **Copies with body edits are built in memory.** `rewriteEml` and `insertWarningBanner` each destroy their sink on a message-level skip, so chaining the two streams with a pass-through on skip is not possible without buffering; the pipeline reads the base (refused above `POLICY_COPY_MAX_MESSAGE_BYTES`, checked on `ContentLength` and while reading), applies the steps on buffers and uploads once. Header-only copies keep the 5.2 streaming writer (same keys, same bytes). Memory bound: copy size × in-flight evaluations.
3. **`POLICY_URL_REWRITE_ENABLED=false`** keeps 5.2 behaviour by re-evaluating a `disabled`/`direction` round under `ifNotRewritten = quarantine` with `urls.rewriteStatus = 'none'` (the evaluator raises for `none`; re-using `disabled` as the skip reason would not raise because it is policy-rewritable). `policyAttempt = { skipped, disabled }` is recorded. `deliver` rules are recorded.
4. **Copy refusals and URL rewriting.** A size or header-block refusal reports the banner as `skipped_too_large` and the policy rewrite as `skipped`/`too_large` (no other skip reason fits); under `ifNotRewritten = quarantine` that re-evaluates and holds, i.e. a message too large to rewrite is held as the rule demands.
5. **Split decision record.** The row stores the message-level result (Q4.4) with the delivered copy's `delivery` record; its `action` column is the Q5 final action (`partial` for a split) rather than the record's own. For a split, TAG/WARN/URL_REWRITE actions of the record that are `not_applicable` (the record is not allow) but whose rules were merged into the delivered copy are reported with the delivered status (`storedStatuses`); when nobody is delivered TAG/WARN are `not_applicable`. `mail.policy.decided.v1.disposition` is the lifecycle disposition unless split (then the record's), so a quantifier-`all` uniform result never reports `allow` for a held message.
6. **ARCHIVE / ALERT and the sender notice** are requested from the message-level decision record (it evaluates rules over all recipients), not from `mergedDeliveryActions.archive/alert`: for recipient rules with quantifier `any` the two agree; for `all` the message-level result needs every recipient. Recorded for WP5 (§12); no test case of the design depends on it.
7. **`approval_requested` per evaluation** is chunked: one event per 50 review requests (the payload maximum), so an evaluation with more than 50 review entries emits several. The notice also names the message (`refs.messageId/receivedAt`).
8. **Release precisions.** (a) A stale release marks its still-`pending` logs `stale` (`blocked_reason = stale`) so the release view does not show pending forever; nothing else changes. (b) `message_archived` has no `QuarantineReleaseStatus` value: the log is `refused` with `blocked_reason = message_archived`; the metric result is `message_archived`. (c) One release copy per release: the edits are `releaseDeliveryEdits` over the actions of every released entry's result (one merged copy, the per-release equivalent of Q4.5). (d) A release copy's URL rewrite is attempted only when the latest round was skipped as `disabled`/`direction`; a skip is recorded in `revalidation.copy` and never blocks the release (the operator released against the policy's opinion, Q13.3 last bullet). (e) The new `release_approval` of an `approval_required` outcome also emits `approval_requested` (when `alerts.approvalRequests`). (f) A released recipient gets `final_action = deliver`. (g) Executor reads that come from the shared facts/snapshot readers count in `policy_inconsistent_reads_total`; quarantine rows in `quarantine_inconsistent_reads_total`. (h) An input that cannot be built for the latest round (malformed rows) is treated as "no scan round" (`no_scan_round` approval reason), never as a release.
9. **Sweeper precisions.** Expired recipients keep their `final_action`. A `retained` purge without a known date is re-evaluated one day later. Purges delete **every version** (the mail bucket is versioned) — the policy-engine needs `s3:ListBucketVersions` and `s3:DeleteObjectVersion` (deployment doc). Adoption also covers `quarantined` recipients (a fixture or a partial 5.2 state). `quarantine_sweep_last_success_timestamp_seconds` is stamped only when every step succeeded.
10. **Digests.** A digest goes to any active, verified, non-deleted user whose e-mail equals an entry's recipient address — holding `quarantine:self` is not required to _receive_ it (Q20 names none; the portal link requires login and the self routes check the permission). The worker lists the entries of the event's window (the scheduler's eligibility window), not every open entry of the user. Entries held after the last due instant wait for the next instant (`nextDigestWindows` windows end at `scheduledFor`); the integration test therefore moves `quarantined_at` back two hours.
11. **Alert expressions** follow Q29 with aggregation: `sum()` on both sides of `QuarantineReleaseExecutorStalled` (the api and the policy-engine series carry different `job`/`instance` labels, so a bare `and` never matches) with `or vector(0)` for a never-started executor, and `max()` over replicas for the leader-only gauges (`QuarantineSweeperStalled`, `QuarantineApprovalBacklog`), so a standby's 0 never pages.
12. **Explanation column.** `quarantine_messages.explanation` stores the evaluation's explanation lines (code + content-free params, ≤ 24), not codes only, so the api can render them (Q10 "explanation lines").
13. **Hardening outside the strict scope (notification-worker):** the 5.2 `safeText` did not remove bidi overrides/isolates and zero-width characters; it now does (a test added). No 5.2 expectation changed.

#### Deviations and precisions (with evidence)

1. **`messageId` in the DTOs is the message's registry public id (UUID), not the decimal id** (bug fix in `packages/quarantine/src/dto.ts` + `dto.test.ts`, package rebuilt). WP2 D19 says "the decimal message id (as in the other message routes)", but every `/messages/{messageId}` route takes the registry public id (`MessageIdSchema = z.uuid()` in `apps/api/src/modules/messages/dto/messages.schemas.ts`), and the api never exposes internal ids. Q7's `messageId` body field and the search filter are the same public id. `packages/quarantine` tests: 261 passed after the change.
2. **Search `sender` is the exact envelope sender; `headerFrom` is a separate exact filter.** Q9 says "sender (exact envelope or header From address)". An `OR` across two columns cannot use the `(organization_id, envelope_from, quarantined_at)` index (the first EXPLAIN attempt planned the default index with a row filter), and there is no header-From index; adding one is a schema change this package may make only when unavoidable. So `sender` uses the index (asserted by the EXPLAIN check) and `headerFrom` is filtered within the bounded range. `senderDomain` filters the envelope sender's domain within the range.
3. **State-filter plan.** For a rare state the optimizer chooses either `(organization_id, status, quarantined_at, id)` or the ordered default `(organization_id, quarantined_at, id)` with a row filter (backward index scan stopping at the page size), by statistics; on 50 000 rows it chose the default index (no filesort), on 5 000 rows it even chose `(status, expires_at)` + filesort (tiny org). The assertion accepts both organization-leading `quarantined_at` indexes and forbids filesort; the other four shapes assert their exact index. Results below.
4. **Self routes are `@UserOnly()`** (Q15: API keys refused) and refuse platform overrides in the service (`scope.via !== 'member'` → `403`).
5. **Cancel** is `RequireAnyPermission(quarantine:approve, :release, :request_release, :self)` at the route (the possible requesters' permissions and approvers'); the service allows the requester (user id or API key id) or a holder of `quarantine:approve`, else `403`. A `policy_review` cancel is `409 quarantine_state_conflict` (`cause: policy_review`).
6. **Bulk** is `RequireAnyPermission` of the four action permissions at the route; the action's own permission (and user + MFA for approve/deny) is checked in the service (`403`). Unknown body shapes are `400 quarantine_bulk_limit` (`cause: invalid`) as `checkBulkRequest` decides.
7. **Env-configured rate limits.** `@RateLimit()` takes constants; the quarantine routes use `QuarantineRateLimitGuard` (same fixed-window counters `rl:<bucket>:<principal>` in Redis, `429` + `Retry-After`, `503` fail-closed) reading `QUARANTINE_PREVIEW_RATE_PER_MINUTE`, `QUARANTINE_DOWNLOAD_GRANTS_PER_HOUR` (grants **and** downloads: §5 has no separate download key) and `QUARANTINE_BULK_REQUESTS_PER_MINUTE`.
8. **No Idempotency-Key on `PUT /settings`, `PUT /me/preferences` and download grants.** Q26 lists none for them: the PUTs are idempotent (whole document + `rowVersion` CAS; a value), a grant is single-use by design and a retry simply creates another short-lived grant (each audited). Every other mutation requires the header.
9. **Bulk idempotency.** A bulk request spans one transaction per item, so `IdempotencyService.execute` cannot wrap it: the service checks the stored record first (replay / `422`), runs the items, then stores the whole response and the `quarantine.bulk` audit row in one transaction (a concurrent winner's record is replayed). Each item runs through the single-item method with a derived key `qb.<first 32 hex of sha256(key)>.<id>`, so a repeated or concurrent bulk request never applies an item twice (each item's response is stored under its own key).
10. **`quarantine_actions.idempotency_key`** (unique per organization; one request may write several rows): `sha256(<sha256 of the Idempotency-Key>:<entry public id>:<action>)`; `NULL` for views, previews, downloads.
11. **Preview audit metadata.** Q11 lists `{ entryId, bodySource, truncated, masked }` and requires the row **committed before** the parts are read; `truncated` and `masked` exist only after reading. The row holds `{ entryId, bodySource (planned: text, html or null), self }`; truncation and masking go to the response and `quarantine_previews_total`. A failure afterwards adds `quarantine.preview_failed` (`{ reason }`). Decoded parts are read as UTF-8 (the 3.1 parser stores decoded text). A text part is shown as text (a literal `<script>` in a text part is text, not markup); HTML is converted by mail-safety.
12. **Reject schedules the object disposal** (Q16 "Object disposal is scheduled by Q17's rules"): after the reject, `decideObjectDisposal` on writer facts decides a `quarantine_object_purges` row `pending` or `retained` (legal hold, retention, archive pending, shared) — never a refusal (refusals belong to delete).
13. **Retained purges without a known date** (`purgeAfter` null from the library): `purge_after = now + 1 day`, so the sweeper re-evaluates daily.
14. **Approve = one operator-mode evaluation.** `approved_reasons` = the request's reasons ∪ the current pre-check's; with that set `decideRelease` in `approved` mode always releases unless the round is stale on a rescannable message (`409 quarantine_rescan_required`) or the tenant refuses hard-block releases (`409`). The service therefore evaluates once (entry state seen as `held` for the reason computation) and refuses or queues; the executor re-validates with `mode = approved`. `decided_by_user_id`, `decision_reason`, `decider_permissions_hash` are set.
15. **Request-release** stores the pre-check's approval reasons (operator mode); a stale round does not block the request (the approver gets `rescan_required`); a tenant hard-block refusal is `409`.
16. **Manual quarantine precisions** (Q7): eligible recipients of a rejected message are those `discarded` (5.3) **or `pending`** (a 5.2-rejected message left them `pending`) without an entry of the round; facts copied from the round's latest `policy_execution_logs` row and its `message_risk_scores` (max level, last recommended action, union of hard blocks ≤ 9), `primary_engine` from the first hard block's engine, else `policy` for a tenant-rule decision, else `none`; `decisive_policy_version_no` from the stored `policy_versions` JSON when present; `user_id` by the directory lookup; `email_events` `quarantine.created`. An unknown or foreign message is `404 quarantine_entry_not_found` (Q26 has no message code); a non-policy rejection, an old message or a missing EML is `409 quarantine_manual_not_allowed` with `cause` (`not_policy_rejected`, `too_old`, `content_missing`, `no_eligible_recipient`, `no_review_entry`).
17. **Q30 without entries.** The 409 also applies when the message has no entry yet (a 5.2-held message the sweeper has not adopted): "for every quarantined/held_for_review message" (`entries: 0`).
18. **Pre-check input failures.** A stored round the input builder refuses (`PolicyInputError`) is decided like no round (`no_scan_round` approval reason), as WP3's executor does (WP3 precision 8h).
19. **Downloads.** The EML filename is `message-<entryId>.eml.bin`; attachment names are NFKD-folded to `[A-Za-z0-9._-]`, ≤ 100 characters + `.bin`. The token's `org` is the decimal organization id of the scope (WP2 D15 allows decimal ids), `usr`/`ent` the public ids. The gate also refuses a deleted/purged entry (`410`), a missing object key and an object above `QUARANTINE_DOWNLOAD_MAX_BYTES`. A refused download keeps the grant consumed (the consume is repeated after the rollback). The grant route checks the entry exists in the scope before re-authorization (no password oracle on ids); a missing TOTP for an enrolled user counts as a failed attempt.
20. **Settings.** `GET` without a stored row: `raw: null`, `rowVersion: 0`; `PUT` with `expectedRowVersion: 0` creates the row. The `PUT` response is computed from the written document and the writer's `organization_settings` (the replica may lag). Changed paths are leaf paths (`endUser.selfRelease`).
21. **Detail/history bounds.** History returns at most 500 actions (oldest first) and 100 release attempts, no cursor. Self detail shows no release attempts. Summary = counts by state over a bounded `quarantined_at` range + pending approvals.
22. **Organization usage** (`organization-usage.repository.ts`): "active quarantine" now counts `held`, `pending_approval`, `releasing` (was the retired `quarantined`, `release_requested`; WP1's enum rebuild broke the type-check).
23. **Read-your-write.** Search, detail and lists read the replica: a just-released entry may still show `held` for the replication lag (documented in the OpenAPI descriptions).
24. **EXPLAIN check method.** The test captures the **repository's own SQL** (a `PrismaClient` with query events behind `QuarantineReadRepository`) and runs `EXPLAIN` on it with the same parameters; Prisma returns `EXPLAIN` rows positionally (`f0…f11`: `f6` key, `f9` rows, `f11` Extra). Rows are seeded with WP1's `loadQuarantineEntries` (`days: 60` so the 62-day search range covers them; WP1's selective `sample` values).
25. **Retired column.** The step 1.1 read-only `tenant-data/quarantine.repository.ts` still selects `subject` (always NULL; unchanged, no writer).
26. **Self-service and SoD by address.** The approver's own address is checked only when verified (`emailVerifiedAt`); unverified approvers are compared by user id only.
