## 0. Scope in one paragraph

AI-5 enables the last 26 planned operations as chat tools — 25 writes that run only through the AI-2 confirmation card and the side-effect-free read `provider_mail_flow_preview` — for archive settings and retention policies, capture-issue retry, journaling settings, journal intake sources (non-secret fields only), eDiscovery cases, searches, review tags, exports (the export is a confirmed write; its download stays in the portal), case holds, and provider connections (create, rename, domains, attestations, grant verify and revoke, health check, mail-flow preview, apply and disconnect, guided by the existing wizard; credentials, OAuth consent, the Google delegation confirmation, validation probe addresses and intake addresses stay in the portal). It adds the one missing single read the confirmation cards need (`GET /archive/capture-issues/{messageId}`), and closes an AI-1 gap: the enabled read `intake_sources_get` exposes `reveal=true`, which would return a journal intake address in clear to the model; AI-5 removes that input from chat. Legal-hold release, archive disposal and archive key rotation stay critical (portal only); previews, downloads, download grants and reveal stay not applicable. Every change that shortens retention, deletes expired records without review, changes which mail a retention policy matches, turns capture off or narrows it, or pauses, disables or loosens an intake source is `high` (password + TOTP), directly or by escalation; no chat tool can remove or shorten a legal hold. Archived message bodies and attachments never reach the model. The step also finds and fixes the cause of the ATO Playwright timeout carried from the AI-4 gate (D13).

## 2. Decisions

### 2.0 Invariants added to I1–I21

- **I22 Compliance stays compliant through chat.** No chat tool releases, removes, shortens or narrows a legal hold, disposes of an archived record or rotates archive keys (critical, portal only). Every confirmed change that shortens retention, makes expired records delete without review, changes which mail a retention policy applies to, changes the default retention or the immutability mode, turns archiving or journaling off, replaces capture settings (directions, included outcomes, scope, policy archiving, intake scanning, access), or pauses, disables, loosens or narrows an intake source (networks, TLS, client certificates, a lower size limit, the silence alert off) is `high` (password + TOTP re-authentication), by its base risk or by escalation (D2, D3). Placing a legal hold and creating an eDiscovery export are `high` (the hold blocks every disposal and is released only in the portal; the export packages decrypted originals).
- **I23 No archived content and no integration secret through chat.** No AI-5 tool returns a message body, an attachment, an export package or a download link: download grants, previews, downloads and reveal stay N/A, an export's file is downloaded only in the portal. Journal intake addresses are never revealed through chat (`omitInputs`, D7); intake source creation and address rotation, provider grant creation, credentials, OAuth consent, the Google delegation confirmation (`subjectEmail`), and validation runs (single-use probe address) stay N/A or portal-only. Provider impact tokens never reach the model: the server obtains them from a fresh preview and injects them (D5); they are dropped from envelopes, cards, execution params and audit params by the credential-key scrub and are kept only in the stored confirmation request until it expires.

### D3. Conditional risk escalation, including read-relative conditions (package `confirmations/escalation.ts`)

Existing kinds `present` and `equals` (final arguments only) stay. Three **read-relative** kinds compare an argument with the precondition read (ADR-0093 amendment (v)):

```ts
  /** The (numeric) argument is lower than the read's number (shortening). */
  | { below: { path: string; field: string; absentAs?: number } }
  /** The argument equals `value` and the read's value does not (a switch to `value`). */
  | { becomes: { path: string; field: string; value: string | number | boolean | null; absentAs?: string | number | boolean | null } }
  /** The argument differs from the read's value (canonical JSON; arrays keep their order). */
  | { differs: { path: string; field: string; absentAs?: unknown } };
```

Semantics: the argument is `valueAtPath(args, path)`, or `absentAs` when the path is absent and `absentAs` is given (the `PUT` defaults of the route); an absent argument without `absentAs` never matches. The read value is `snapshot[field]` (the precondition snapshot, keyed by the field path). **Fail closed:** a missing or `null` read value, a non-number for `below`, or a snapshot string that does not parse (`differs` parses snapshot strings starting with `{` or `[` as JSON; a list or object cut by the snapshot caps no longer parses) counts as a match. `differs` compares `canonicalJson(argument)` with `canonicalJson(readValue)` (sorted object keys; arrays in order; a reordered list escalates, which is safe). `effectiveRisk(tool, spec, finalArgs, snapshot)` gains the snapshot (`null` → every read-relative condition matches). The proposer passes `state.snapshot`; the confirm route's step 7a passes the stored `preconditions.snapshot`; because every read-relative `field` must be one of the spec's `stateFields` (consistency rule), the step-12 state-digest check guarantees the value the risk was computed from is the value at execution. `escalationNote`: `↑ high when body.retentionDays < retentionDays`, `↑ high when body.onExpiry → delete`, `↑ high when body.criteria ≠ criteria`.

### D5. Server-filled impact tokens for mail-flow apply and disconnect (ADR-0093 amendment (w))

The 8.2 wizard requires `impactToken` from `POST …/mail-flow/preview` for `POST …/mail-flow/apply` and `DELETE /provider-connections/{id}`. The model never sees an impact token (it is a credential-pattern key, dropped from envelopes and cards), and must not be the one to bind the user's approval to a change set. So:

```ts
export interface ImpactTokenInjection {
  /** The allow-listed side-effect-free POST read (`IMPACT_PREVIEW_TOOLS` = ['provider_mail_flow_preview']). */
  previewTool: 'provider_mail_flow_preview';
  /** Path parameters of the preview from the write's arguments (`{ id: 'id' }`). */
  params: Readonly<Record<string, string>>;
  /** The preview body's `change`: the write's `body.change`, or a constant change. */
  change: { from: 'body.change' } | { constant: Readonly<Record<string, unknown>> };
}
// ConfirmationSpec gains `impactToken?: ImpactTokenInjection` (requires a `single` precondition).
```

Flow:

1. **Executor, before the schema check** (with the CAS placeholder): when the spec has `impactToken`, `body.impactToken` is set to a placeholder (`'pending-preview'`, valid against the schema) and `body.confirm` to `true` when absent, so the required fields never block a proposal.
2. **Proposer, after the single GET precondition read**: sends the preview through the loopback (`POST`, the caller's bearer and correlation id, writer read as for every precondition, body `{ change }` per `change`), and merges the response under the key `preview` into the precondition target, so state and display fields address it as `preview.<path>` and the existing `stateDigest` / `buildSnapshot` / `rowVersionOf` work unchanged. A non-2xx preview fails the proposal like a failed read (its coded error surfaces, e.g. `409 outbound_active`, `422`). Then `body.impactToken` ← `preview.impactToken` and `body.confirm` ← `true` (always overriding the model's values), before CAS injection and the final schema check.
3. **Confirm, step 12 re-read**: the same GET + preview; the state digest over the spec's state fields (including `preview.*` change-set fields) must equal the stored one (else `409 assistant_confirmation_state_changed`); the stored request keeps the proposal's token (bound into the action digest; the TTL 900 s outlives the 300 s confirmation). An expired or invalidated token (`409 impact_changed`) fails the confirmation with the route's code.
4. The api audits each preview (`integration.mail_flow_previewed`, kind and counts only): one at proposal, one at confirm — documented in `CHAT_AUDIT_DESIGN.md`.

Rules (consistency, package): `impactToken` only with a `single` precondition; the write's input schema has `body.impactToken` and `body.confirm`; `body.impactToken` is accepted by the credential-key input rule **because** it is server-filled (no `CREDENTIAL_KEY_EXCEPTIONS` entry; a credential-pattern input that is not server-filled still fails); no state or display field may contain a credential-pattern key (`preview.impactToken` is never a state or display field); `IMPACT_PREVIEW_TOOLS` lists exactly `provider_mail_flow_preview`, an enabled `read` tool. The api's `readPreconditions.get` keeps refusing non-GET tools; a separate `preview()` path accepts only `IMPACT_PREVIEW_TOOLS`. The tool descriptions (manifest `description` override) say: "`impactToken` and `confirm` are filled by the server from a fresh preview; pass only `change`" (apply) and "pass only `id`; the server previews the disconnect" (disconnect).

Specs: `provider_mail_flow_apply`: precondition `provider_connections_get {id}`, `impactToken { params: { id: 'id' }, change: { from: 'body.change' } }`; `provider_connections_disconnect`: same read, `change: { constant: { kind: 'disable' } }`. State fields: `rowVersion`, `status`, and the preview's change-set fields (implementer picks the scalar/JSON paths of the preview response that describe the change set and its warnings, never `impactToken`).

### D13. The ATO Playwright timeout in the full suite (find the cause, fix, prove)

**Symptom (AI-4 gate, 2026-11-25).** `tests/portal-e2e/specs/ato-providers.spec.ts` › "mailbox changes: remove an external forwarding rule through approval" waits 300 s for the `alex@<run domain>` mailbox account with an active incident and an `inbox_rule` mailbox item, and times out only in the full suite (workers 1); it passes alone and with other heavy specs in parallel. No `P2024`/`P1001` in the ato-worker during the failing run, so the AI-4 pool fix is not the cause. In the full suite the files before it are, in Playwright's alphabetical order: `archive-only`, `archive-split`, `archive`, `assistant` (then `ato-providers`); its own earlier tests are "connect …" (binding with `backfillDays: 0`, waits for Healthy and a sign-in poll) and "backfill request, pause and resume" (backfill of sign-ins, pause, resume).

**Candidate causes from the code (to be confirmed or refuted with evidence; none is assumed):**

1. _Historical-mode race of the first mailbox sweep._ The Microsoft snapshot primary is `mailbox_audit` (companions `forwarding_changes`, `delegation_changes`); `processPage(..., initialSnapshot)` runs every page of that group in historical mode (PX3: no incident) until the first full sweep completes (`backfill_completed_at`). The forwarding-rule audit event (`New-InboxRule`, 40 min old in `microsoftDirectory(now)`) can land in a page before or after the sweep completes depending on timing (page sizes, `ATO_IDP_SNAPSHOT_MAX_USERS_PER_POLL`, `ATO_PROVIDER_MAX_PAGES_PER_POLL`, the 60 s poll interval). Once processed historically it is remembered (Redis seen-set, `isReplayed`) and never produces the live signal, so no incident is opened.
2. _Pause/resume against an in-flight poll._ "backfill request, pause and resume" may pause while a `mailbox_audit` poll holds its claim lease (`IDP_STREAM_LEASE_MS` 5 min); resume sets `next_poll_at = now`, but the in-flight poll's `success()`/`failure()` overwrites it (now + interval or a backoff), or the backfill request moves the cursor (CAS miss: "the cursor was changed by the api in between") and the poll stops; the 5-minute lease equals the test's 300 s budget.
3. _Cached organization context._ `OrgContext` is cached for `ATO_SETTINGS_CACHE_SECONDS`; specs that run first (archive, assistant) make the ato-worker load alpha's context earlier; a stale context (ATO settings, learning state, feature flags) could keep provider events from opening incidents.
4. _Shared simulator or clock state._ The `idp-simulator` runs since the stack start (call log, scripted failures, dataset); a state left by the api integration suites, an earlier run or time windows relative to the dataset's `now`.
5. _Spec cleanup or seed interplay._ An `afterAll` or the global seed/teardown of another spec touching alpha's ATO rows, integrations or incidents.

**Procedure (WP2).** (a) Run, with the stack as the gate runs it (api recreated with the e2e override and `tests/portal-e2e/assistant.override.yml`, fake provider; images built one at a time; capture the api container's current compose files first and restore them afterwards with the product owner's local override, never printing a secret), the specs in full-suite order with one worker: `pnpm --filter @email-gateway/portal-e2e test -- --project=desktop --workers=1 specs/archive-only.spec.ts specs/archive-split.spec.ts specs/archive.spec.ts specs/assistant.spec.ts specs/ato-providers.spec.ts` (and, if that passes, the full `pnpm test:portal`), with `E2E_KEEP_DATA=1` on the failing attempt so the rows stay for inspection. (b) Extend `integrationDiagnostics` (no secrets, no payloads): per stream `backfill_completed_at`, `last_success_at`, cursor sweep state (decoded `sw`), `backfill_requested_at`; whether the alex account, its identity, signals (codes, `historical` if stored), the `inbox_rule` item and an incident exist; the idp-simulator admin call log for the run's tenant (paths and counts only). (c) Use the ato-worker logs (debug level for the provider role during the run if needed) and the simulator call log to decide between the candidates. (d) Fix the cause in the product (preferred when the behaviour is a product defect, e.g. an audit event that should alert being swallowed as historical, or a resume overwritten by an in-flight poll) or in the test (when the test's assumptions are wrong), with a deterministic regression test where the cause is in the product (ato-worker unit/integration with a fake adapter or the simulator). (e) **Prove it** with a full-suite-order run (step (a) order, workers 1) that passes, recorded in §12 with timings, plus the spec alone. (f) Record the confirmed cause, the evidence and the refuted candidates in §12 (WP2) and in a short "Cause" paragraph appended to this D13 (one edit). If the cause turns out to be outside the files WP2 owns (§10), WP2 records it and the orchestrator assigns the fix; WP2 never changes an OpenAPI contract.

**Cause (WP2, 2026-11-25).** The cause is a stale provider context in the ato-worker, close to candidate 3 but in a different cache. The provider rules (`ato.provider.risk_event`, `ato.oauth.*`, `ato.mailbox.*`) need the `provider:<stream>` capabilities from `ProviderContextCache`, which is cached per organization for `ATO_SETTINGS_CACHE_SECONDS` (30 s). Nothing refreshed it when the probe stored the integration's capabilities. When an alpha event (the administrator's portal sign-in at the start of "connect") loaded the entry less than 30 s before the first stream poll, every event of that poll was evaluated with no provider streams. No rule fired. The events were still marked as processed (Redis seen-set and page ledger), so no later poll raised the signals, and alex never got an incident. The window depends on timing: sign-in to first poll takes 5–40 s, because the probe loop runs every 15 s and the stream runner every 5 s. It does not depend on the spec order. The integration harness hid the gap, because `IdpWorld.probe()` clears the cache after every probe.

Evidence: the ato-worker container that served the AI-4 gate was still running. For the gate's integration (org 33941, integration 646), Redis held 14 seen-set keys, the same number as a passing run. Yet the worker's counters, which covered both that run and a later passing one, held only one run's provider signals: `provider_risk` strong 1, `oauth_activity` strong 1, `mailbox_configuration` 6 moderate / 1 strong, and one critical incident. So the gate's events were ingested and processed and produced no signal at all. The adapter counters (`ato_idp_events_total` emitted, `ato_idp_snapshot_items_total`) were doubled, so the gate also read every record and wrote the mailbox items. The new integration case reproduces this exactly without the fix: the context is cached before the first probe, and the first poll gives "expected 0 to be greater than 0" `ato.provider.risk_event` signals.

Refuted candidates:

1. The historical sweep race. The forwarding incident does not need the `New-InboxRule` event. The `Set-Mailbox` forwarding, the SendAs grant, the risk detection and the consents are `o365:`/Graph events and are never historical. The sweep's `snap:` items are informational by design (PX3). The passing diagnostics show this order.
2. Pause/resume. Only `sign_ins` is backfilled. The mailbox_audit poll had finished before the pause (last success about 30 s before the backfill), and an overwrite would only delay a poll by the interval.
3. The `OrgContext` cache. Its TTL is 30 s, and ATO was on throughout. The incident was not missing because of ATO settings.
4. The simulator state. The spec resets the simulator and loads it in `beforeAll`. The gate read every record (adapter counters).
5. The cleanup and seed. The run domain's rows are the spec's own, and the gate showed an ingested, unsignalled run, not missing rows.
