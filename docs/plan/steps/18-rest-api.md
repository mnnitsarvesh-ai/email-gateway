## 2. Decisions

### D1. One convention for every `/api/v1` route (ADR-0050)

- **Resources:** plural kebab-case nouns (`/smtp-connectors`, `/url-protection/clicks`); at most two levels of nesting (`/messages/{messageId}/recipients`); path ids are public ids (UUIDv7) or, for log-like rows, decimal strings (existing rule, contracts §10). Commands that are not CRUD are `POST /…/{id}/<verb>` (existing: `rescan`, `release`, `publish`). Documented legacy exceptions kept for compatibility: `POST /domains/{id}/recipients/remove`, `POST /quarantine/entries/{id}/delete` (bodies with reasons).
- **Methods and status:** `GET` 200; `POST` create 201 with the resource; `POST` command 200 (synchronous) or 202 (asynchronous, with the id to poll); `PUT` replace 200; `PATCH` partial 200; `DELETE` 204 (existing `DELETE` routes that return 200 keep it). No `HEAD`/`OPTIONS` routes besides CORS.
- **Success envelope:** a single resource is returned **bare** (its representation is the body); a collection is `{ "data": [...], "nextCursor": string | null }` and nothing else. Rejected alternative: wrapping every body in `{ data }` (breaks all 229 existing operations, no benefit to the portal).
- **Error envelope** (additive, non-breaking): every error from the api is
  `{ statusCode, error, code, message, correlationId, requestId, ...details }` — `message` keeps its current type (`string` or `string[]` for validation), `code` is a stable snake_case machine code. Existing coded errors keep their codes; uncoded errors get a default code from §3.2. One global `ApiExceptionFilter` (apps/api) renders every exception, `CodedExceptionFilter` stays (same output) for backward compatibility.
- **Request-Id:** every response (success, error, unknown route, probes) carries `X-Request-Id`, a server-minted UUID (never taken from the client; clients use `x-correlation-id` for their own ids, which keeps working). It is in the error body (`requestId`), in every log line (`requestId` in the pino mixin) and in `audit_logs.metadata.requestId`.
- **Headers on every `/api/v1` response:** `X-Request-Id`, `x-correlation-id`, `Cache-Control: no-store` (unless the route sets its own), and on authenticated routes `RateLimit-Limit`, `RateLimit-Remaining`, `RateLimit-Reset` (D8).
- **Validation:** every body and query schema is a **strict** zod object at every object node (unknown fields → `400 validation_failed`, message `"<path>: Unrecognized key"`); path params validated before any database access. This tightens legacy routes that silently dropped unknown fields; it is recorded as a documented, tested contract change (the documented schemas never accepted those fields; nothing that was accepted changes meaning). Alternative rejected: a `lenient` switch (keeps the gap open; v1 is pre-GA and the portal 7.x is the first client).
- **Representation:** ids are strings; timestamps ISO 8601 UTC with milliseconds; enums lower-snake; no `bigint`, no numeric internal ids for aggregates; no message content, secrets or S3 keys (`eml_object_key` and friends are never returned).
- **Deprecation rule:** a breaking change to a path, DTO or error code needs `Deprecation`/`Sunset` response headers on the old behaviour, a test of both behaviours and an entry in the API guide's changelog; otherwise it ships as `/api/v2`.

### D2. Machine-readable error codes

Default codes for uncoded exceptions (by status and, for 403, by the existing message): see §3.2. The permission guard throws coded exceptions with the **same messages** it throws today (`MFA required` → `mfa_required`, `MFA enrollment required` → `mfa_enrollment_required`, `This operation requires a user` → `user_required`, otherwise `forbidden`). Module codes (`message_not_found`, `version_conflict`, `quarantine_cursor_invalid`, …) are unchanged.

### D3. Pagination: one list contract, two cursor encodings (ADR-0051)

- **Contract for every list:** query `limit` (1–100, default 25; quarantine search keeps its configured cap) and `cursor`; response `{ data, nextCursor }`; keyset order on an indexed key ending in the primary key; `nextCursor: null` on the last page; **no totals** (`X-Total-Count` is not offered: counting is unbounded at 1M messages/day). A page may contain fewer than `limit` rows (even zero) while `nextCursor` is non-null when a scan budget ended the page (D6); clients follow `nextCursor` until it is null.
- **Cursor v1 (every list added by 6.1, mandatory for new lists):** opaque, signed and tenant-bound:
  `cursor = base64url(JSON payload) + "." + base64url(HMAC-SHA256(API_CURSOR_KEY, "eg-cursor/v1\0" + resource + "\0" + organizationPublicId + "\0" + payloadB64)[0..16])`
  payload `{ v: 1, r: resource, k: [<key values as strings>], f: <filterHash 16 hex>, d: "desc"|"asc", w?: [fromMs, toMs], t: issuedAtEpochSeconds }`. Verification: MAC with `API_CURSOR_KEY` then `API_CURSOR_KEY_PREVIOUS` (rotation), `v`, `r` equal to the route's resource, `f` equal to the hash of the current filters and sort, age ≤ `API_CURSOR_TTL_SECONDS`, total length ≤ 512. Any failure → `400 cursor_invalid` (no detail on which check failed). The organization is bound through the MAC, so a cursor of tenant A presented by tenant B fails; the server re-applies the tenant scope regardless, so a cursor never widens access. `w` pins the resolved time window of the first page so later pages stay stable when `to` defaulted to "now"; a later request may omit `from`/`to` or repeat the same values, anything else is `cursor_invalid`.
- **Cursor v0 (legacy):** the unsigned cursors of the 2.x–5.x lists (`http/pagination.ts`, deliveries, quarantine, message scans, policy history, login events, BEC/DLP lists, …) are kept unchanged for backward compatibility. They are tamper-evident (canonical round-trip; quarantine binds the filter hash) and carry no authority (scope re-applied). The route inventory test (WP5) records the encoding of every list (`v0`/`v1`) so a new list cannot use v0. Migrating v0 lists is not in 6.1 (§11).
- **Offset pagination:** none exists; none is added.

### D4. Filtering and sorting

- **Syntax (query string, Express' simple parser):** `field=value` (equals), `field=a,b,c` (in, ≤ 10 values unless stated), `field.gte=` / `field.lte=` / `field.gt=` / `field.lt=` (typed ranges), booleans `true|false`. Unknown parameters and operators are `400 validation_failed` (strict schemas).
- **Allow-list per resource:** each list declares its filters (name → type, operators, max values, the SQL column it maps to through a code-side constant) and sorts (`sort=-receivedAt` default, `sort=receivedAt`; only keys that are the leading key of the keyset index). Column identifiers come only from those constants; values are always bound parameters (Prisma `where` objects or `Prisma.sql` tagged templates). Never a raw SQL fragment, `$queryRawUnsafe` or string concatenation of input.
- **Time ranges:** every list over a partitioned table requires a bounded range `from`/`to` (ISO; defaults per resource; maximum per resource from config) so MySQL prunes partitions.
- **Foreign ids in filters** (`domainId`, `messageId`) are resolved inside the tenant scope; an id of another tenant answers exactly like a missing one (`404 <resource>_not_found`).
- **Filter hash:** SHA-256 of the canonical JSON `{ filters, sort, resource }` (first 16 hex) bound into the v1 cursor.

### D5. Cursor-based message listing on the replica (WP2)

`GET /messages` reads the replica only. Three query plans, chosen by the filters:

1. **Index plan** (no filter besides the range and `sort`): keyset `(received_at, id)` over the existing `(organization_id, received_at, id)` index, `received_at` range pruning, `ORDER BY received_at DESC, id DESC LIMIT limit+1`. Same shape as `MessagesRepository.listRecent` (reuse it).
2. **Verdict plan** (exactly one `verdict` value and no non-indexed filter): new index `(organization_id, final_verdict, received_at, id)`.
3. **Recipient plan** (`recipient=` exact address): the existing `email_recipients (organization_id, address(100), received_at)` index, keyset `(received_at, recipient row id)`, then the messages by `(id, received_at)` in one query; duplicates of one message on a page are collapsed.
4. **Scan-bounded plan** (any other filter, alone or combined with the verdict or recipient plan: `direction`, `status`, several verdicts, `action`, `sender`, `headerFrom`, `riskScore.*`, `hasAttachments`, `domainId`, `internetMessageId`): step 1 finds the boundary key of the next `API_LIST_SCAN_BUDGET_ROWS` index entries after the cursor (`SELECT id, received_at … ORDER BY received_at DESC, id DESC LIMIT 1 OFFSET budget-1`, index-only); step 2 runs the filtered query between the cursor and that boundary with `LIMIT limit+1`. If step 2 fills the page → `nextCursor` = last row; else if the boundary exists → `nextCursor` = the boundary (short page); else `null`. MySQL never examines more than the budget per request.

Every plan is EXPLAIN-checked in an integration test (§9). A 1M messages/day tenant scans at most `budget` index entries per page; the pruned range keeps one or two monthly partitions in play. Production-scale timing is not verifiable locally (§11).

### D6. Scan budget

`API_LIST_SCAN_BUDGET_ROWS` (default 5 000, bounded 1 000–50 000) applies to every v1 list that filters on a non-indexed column (messages, audit logs, URL clicks). The attachments search needs none since the closing migration `rest_api_index_coverage` (§13.2): its keyset `received_at DESC, id DESC` is read in the order of `(organization_id, sha256, received_at, id)`, so a page reads about `limit` entries however common the hash. It is a documented part of the list contract (short pages). The `api_list_scan_budget_exhausted_total{resource}` counter shows how often pages end short.

### D7. Tenant-aware authorization on every route

- Every route has exactly one authorization requirement (`@RequirePermissions` / `@RequireAnyPermission`) **or** is in an explicit allow-list of `@AuthenticatedOnly()` routes (self-service: `auth/me`, logout, sessions, MFA enrollment, `quarantine/me`) **or** of `@Public()` routes (unchanged list). The route inventory test fails otherwise.
- Organization scope always from the principal; new repositories take `TenantScope` first and use `tenantWhere`; raw SQL includes `organization_id = ${scope.organizationId}` as the first predicate.
- Platform cross-tenant reads only where designed: `GET /platform/audit/logs` (user only, MFA, `platform:operations` + `audit:read`, explicit target, audited). Everything else cross-tenant stays behind the audited override.
- New permissions (seed catalog, §3.6): `threat_intel:read`, `billing:read`, `delivery:suppression_manage`.

### D8. Rate limiting (ADR-0052)

- **Global API limiter** `ApiRateLimitGuard` (global guard registered between `AuthGuard` and `PermissionsGuard`, so denied requests count too), fixed 60 s windows in Redis via `KeyValueStore.incrWithTtl`, for every authenticated route (public routes keep their per-IP `@RateLimit`s; `GET /meta` gets a per-IP one):
  - **per principal** (user or API key, override sessions count as the user): `API_RATE_PRINCIPAL_PER_MINUTE`;
  - **per tenant** (the scope's organization; under an override the target): `organization_limits.api_requests_per_minute` (plan value, overridable only by the platform catalog), **clamped** to `[API_RATE_TENANT_MIN_PER_MINUTE, API_RATE_TENANT_MAX_PER_MINUTE]`; no row → `API_RATE_TENANT_DEFAULT_PER_MINUTE`. Read from the replica through a cache (`API_RATE_LIMIT_CACHE_SECONDS`); a lookup failure uses the default (logged), never "unlimited";
  - **class buckets** per principal, declared with `@RateClass('sensitive' | 'expensive')`: `sensitive` = every route of the sensitive-mutation list (D10) `API_RATE_SENSITIVE_PER_MINUTE`; `expensive` = reports, billing usage, threat lookup, attachment hash search, policy test/dry-runs `API_RATE_EXPENSIVE_PER_MINUTE`.
  - Existing route `@RateLimit`s and quarantine limits stay and apply in addition.
- **Headers:** `RateLimit-Limit`, `RateLimit-Remaining`, `RateLimit-Reset` (seconds to window end) of the most restrictive applied counter on every authenticated response; on `429`: `Retry-After` and the coded body `rate_limited` with `scope: principal | tenant | sensitive | expensive | route`.
- **Store down:** `503 service_unavailable` (fail closed, as the auth and route limits already do).
- **Metrics:** `api_rate_limited_total{scope}`, `api_rate_limit_store_errors_total` (no tenant or principal labels).
- **Auth routes** keep their stricter per-IP/per-body limits (unchanged).

### D9. Idempotency for sensitive operations (ADR-0052)

- **Two mechanisms, one key space** (`api_idempotency_keys`, unique per organization, bound to principal + operation + resource + body fingerprint, 24 h):
  1. **Transactional** (exactly once): the existing `IdempotencyService.execute` with the effect inside the transaction. Mandatory for new mutations (recipient suppressions) and kept for messages and quarantine.
  2. **Reservation interceptor** (at most once per key, for legacy services that own their transactions): `@Idempotent({ operation })` + `IdempotencyInterceptor`. Transaction 1 locks the key: live `completed` match → replay; mismatch → `422 idempotency_key_reused`; live `pending` match → `409 idempotency_request_in_progress` + `Retry-After`; expired → replaced; else insert a `pending` row (expires after `API_IDEMPOTENCY_PENDING_TTL_SECONDS`). The handler runs. 2xx → transaction 2 stores status + body, `state = completed`, expiry 24 h. Error → the pending row is deleted (the client may retry with the same key). A crash between handler and transaction 2 leaves the pending row until it expires; a retry after that may run the effect again (documented at-most-once window).
- **Lost races** (both mechanisms) are retried once: a P2002 on the unique key, and an InnoDB deadlock (P2034, or 1213 from a raw query), which two `SELECT … FOR UPDATE` of the same absent key cause under REPEATABLE READ (compatible gap locks, then crossed insert-intention waits). The configured writer runs READ-COMMITTED (ADR-0004, `gateway.cnf`), where no gap lock is taken, but a writer left at the MySQL default must not turn the D9 `409` path into a `500` (closing round §13.2). A second deadlock is rethrown as it is (`500`, retryable), never reported as a key reuse.
- New column `api_idempotency_keys.state ENUM('completed','pending') DEFAULT 'completed'` (migration `rest_api`, §3.1). `IdempotencyService.runOnce` treats a live `pending` row with the same request as `409 idempotency_request_in_progress` and a different one as `422`.
- **Fingerprint** = SHA-256 of canonical JSON `{ operation, resourceId: canonical path params, body }`; `resource_id` stores the first path id (or `-`).
- **Missing header** on a sensitive route: `400 idempotency_key_required`. For the **legacy** routes newly placed on the list, `API_IDEMPOTENCY_LEGACY_MODE=warn` (deprecation switch, default `enforce`) accepts a missing key, processes the request as before and answers with `Deprecation: true` and `Link: <…/docs/api/README.md#idempotency>; rel="deprecation"`; metric `api_idempotency_total{outcome="missing_legacy"}`. Both modes are tested.
- **Secret-bearing responses are never stored** (the stored body is plain JSON in MySQL): `POST /api-keys`, `POST /smtp-connectors`, `POST /smtp-connectors/{id}/rotate-secret`, `POST /platform/overrides`, `POST /auth/mfa/totp/setup`, `POST /auth/mfa/recovery-codes` and the public auth flows take no Idempotency-Key; they are protected by uniqueness, single-use tokens and their rate limits. `@Idempotent` refuses (at decoration time) to be combined with the `@ReturnsSecret()` marker on those routes, and the interceptor refuses to store a body with a key matching `AuditService`'s `SENSITIVE_METADATA_KEY` pattern (programming error → 500, never stored).
- **The list** is §3.5. OpenAPI documents the header (`ApiIdempotencyKey()`) and `x-eg-idempotency: required|legacy`.

### D10. Sensitive mutations

The list of §3.5 is the authority for both D8 (`sensitive` class) and D9 (Idempotency-Key). It covers mutations that send mail, change who can sign in, change mail decisions for a tenant or the platform, purge data, re-run pipelines or are irreversible.

### D11. Audit

- Every mutation already writes an `audit_logs` row in its transaction (existing modules); new mutations do the same (`recipient_suppression.created|deleted`).
- **Sensitive reads** audited (one row per search, written on the first page only, i.e. without `cursor`): `message.searched` when a person- or message-identifying filter is present (`sender`, `headerFrom`, `recipient`, `internetMessageId`), `attachment.searched` (hash search), `audit.searched` (tenant), `platform.audit_searched` (platform, with the target), `threat_intel.looked_up`. Metadata: filter **names**, the filter hash, SHA-256 of identifying values, result count; never addresses, subjects, hashes of content in the clear, or message content. Existing audited reads (quarantine search/preview/download, DLP evidence, BEC export) are unchanged. Detail reads (`GET /messages/{id}` etc.) are not audited (they are plain metadata reads behind `message:read`), stated in the API guide.
- `AuditService.record` adds `metadata.requestId`.

### D12. Reports, usage and billing from real data (WP3)

- Computed on the replica only, over ranges ≤ `REPORTS_MAX_RANGE_DAYS` (UTC; `hour` granularity ≤ 7 days, `day` ≤ the max), aligned to bucket boundaries; `SELECT /*+ MAX_EXECUTION_TIME(REPORTS_QUERY_TIMEOUT_MS) */` through `Prisma.sql`; a timeout is `503 report_timeout`.
- Message counts use the new covering index `(organization_id, received_at, direction, final_verdict)` (index-only), extended with `final_action` by the closing migration `rest_api_index_coverage` (§13.2) so the threats outcomes (verdict × action) are index-only too; quarantine counts use `quarantine_messages (organization_id, quarantined_at, id)`; clicks use `url_click_events (organization_id, clicked_at)`.
- Results cached in Redis per organization and normalized query for `REPORTS_CACHE_TTL_SECONDS` (key `rpt:v1:<orgId>:<report>:<sha256(params)>`), so a dashboard refresh does not rescan. Cache never shared across organizations.
- **Billing** = the plan (code, name, description) and its effective entitlements (limits with `source plan|override`, features), and monthly metered quantities from recorded rows (messages by direction for the calendar month, current users, domains, active API keys). No prices, currencies, invoices, payment methods or subscriptions exist, and none are invented; the response says `pricing: null` with a fixed note. Months older than the `email_messages` retention (6 months, partitioning registry) answer `400 usage_period_unavailable`.
- **Usage** `GET /usage` = `OrganizationUsageService.get` for the caller's own organization (no duplicated logic).

### D13. Public / internal boundary (ADR-0053)

- **Public:** only `/api/v1/*` on the api. **Internal:** `/health/live`, `/health/ready`, `/metrics` (api), every worker's HTTP port (probes, metrics), `/docs` and `/docs-json` (never in production), RabbitMQ management, MinIO, Redis, MySQL.
- The api router serves nothing else: a route that is not under `/api/v1` and not in the internal allow-list fails the route inventory test; `/api/metrics`, `/api/health/*`, `/api/docs` are `404`.
- The public OpenAPI document contains only `/api/v1/*` (the two probes are removed from it; they keep working and stay documented in contracts §9).
- A Kubernetes `Ingress` for the api (base `api.yaml`) routes only the `Prefix /api/v1/` path to the api service; a test (WP5) parses the rendered base manifests and fails if any Ingress routes `/metrics`, `/health`, `/docs` or a worker service.
- No worker exposes a business HTTP API; internal callbacks are RabbitMQ messages, not HTTP. The sandbox controller and click-service keep their own documented boundaries (ADR-0031, ADR-0039).

### D14. OpenAPI (frontend-ready)

- Post-processing in `buildOpenApiDocument` adds shared components: schemas `ErrorBody`, `ValidationErrorBody`, `RateLimitedErrorBody`, `CursorPage` description; headers `X-Request-Id`, `X-Correlation-Id`, `RateLimit-Limit`, `RateLimit-Remaining`, `RateLimit-Reset`, `Retry-After`, `Idempotency-Replayed`; on every operation the standard responses it does not document yet (`400` when it has params/body, `401`/`403` when not public, `404` when it has path params, `429`, `500`, `503`) referencing `ErrorBody`, and the response headers on every response.
- **operationIds** stay the generated `<Controller>_<method>_v1` and are frozen by the snapshot (renaming a handler is a breaking change the snapshot test shows). **Tags** are the module tags; new tags: `recipients`, `attachments`, `url-protection`, `threat-intelligence`, `reports`, `usage`, `billing` (`audit`, `messages`, `platform` exist). Tag descriptions name the step and deferrals.
- New routes have explicit request/response examples; legacy routes rely on schema-derived examples (stated plainly; the inventory test requires examples only for 6.1 routes).
- Vendor extensions for the portal: `x-eg-permissions`, `x-eg-rate-class`, `x-eg-idempotency`, `x-eg-cursor` (`v0`/`v1`).
- The document description lists the deferred modules (archive → 8.1, webhooks → 6.2, M365/Google → 8.2, deployments → 8.3) and the integration surfaces available today.

### D15. Data access rules for new code (Prisma wrong-read mitigation)

- Reads on `PrismaReadService.client`; writes and read-after-write on the writer via `TransactionRunner.run` with the module's documented budget (≥ the 15 s default; suppressions use 30 s).
- **Echo checks:** every new repository selects `organizationId` (and the key it queried by) and verifies them on every returned row; a mismatch throws `InconsistentReadError` → `503 inconsistent_read` (existing code, used by BEC/quarantine) and is logged; it is never served.
- Partitioned tables are always queried with their partition column (`received_at` / `clicked_at` / `created_at`).

### D16. Metrics, alerts, runbook

## 4. Alternatives considered

| Alternative                                               | Why not                                                                                                                                      |
| --------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `{ data }` wrapper on every success body                  | Breaks all existing operations; no portal benefit                                                                                            |
| Re-sign all legacy cursors now                            | Touches every module's pagination for no security gain (scope is re-applied); kept v0 + inventory guard; migration listed in §11             |
| Offset pagination for "page N" UIs                        | Unbounded at 1M/day; portal uses cursors                                                                                                     |
| Total counts on lists                                     | Unbounded counts on the replica; reports give bounded aggregates                                                                             |
| Sliding-window or token-bucket limiter                    | Fixed windows already used everywhere (auth, quarantine); consistent headers; burst at window edge accepted                                  |
| Rate limiting at the ingress only                         | No principal/tenant awareness; local stack has no ingress                                                                                    |
| Tenant limit loaded into the principal snapshot           | Couples the auth cache to limits; a separate cached resolver is simpler                                                                      |
| Generic idempotency by response caching in Redis          | Not atomic with the effect; loses on Redis flush; DB store already exists                                                                    |
| Making every legacy mutation transactional-idempotent now | Requires reworking each service's transaction boundary; the reservation interceptor gives replay safety now                                  |
| Rollup tables for reports                                 | A new writer (data plane) and a new table for a pre-GA read; covering index + cache + bounded ranges suffice; analytics store is future work |
| `/emails` alias of `/messages`                            | Two names for one resource                                                                                                                   |
| Expose tenant `threat_indicators` / reputation tables     | No engine reads them: a management API would be a mock                                                                                       |
| Archive retention/legal-hold routes now                   | 8.1 owns them (brief); building them twice risks conflicting semantics                                                                       |
| Removing nothing from OpenAPI (keep probes)               | The public document would list internal endpoints (D13)                                                                                      |

## 5. Risks and mitigations

| Risk                                                               | Mitigation                                                                                                                                                     |
| ------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Global limiter adds 2–4 Redis round trips per request              | One fixed-window `INCR`+`EXPIRE` per counter; measured in e2e timing; store errors fail closed and alert                                                       |
| Redis outage now blocks the whole API (fail closed)                | Same as authentication today (deny-lists need Redis); alert `ApiRateLimitStoreErrors`; runbook                                                                 |
| Strict schemas reject clients that sent extra fields               | Pre-GA; documented in the API guide changelog; every module's e2e tests updated                                                                                |
| New `email_messages` indexes cost write amplification at 1M/day    | Two narrow indexes; measured with `pnpm db:perf` insert rate before/after (WP1 records numbers); online DDL                                                    |
| Scan-bounded pages confuse clients (short/empty pages)             | Documented in the contract, OpenAPI description and examples; portal follows `nextCursor`                                                                      |
| Interceptor at-most-once window after a crash                      | Pending TTL bounded (300 s default); documented; transactional mechanism for new code                                                                          |
| Stored responses could hold secrets                                | Secret-bearing routes excluded by marker; interceptor refuses bodies with secret-like keys                                                                     |
| Reports cold cache at 1M/day over 31 days scans ~31M index entries | Index-only covering index, `MAX_EXECUTION_TIME`, `expensive` class, cache; `503 report_timeout` instead of an overloaded replica; production scale not claimed |
| Cross-tenant leaks through caches or cursors                       | Report cache keyed by organization; cursor MAC bound to the organization; cross-tenant tests per route                                                         |
| Prisma wrong-read defect                                           | D15 echo checks and budgets                                                                                                                                    |
| Wave-2 packages break the OpenAPI snapshot concurrently            | Only WP1 (wave 1) and WP5 (wave 3) regenerate `docs/api/openapi.json`; wave-2 packages assert their own operations in their tests                              |

## 8. Security notes

- No new public route; no new secret except `API_CURSOR_KEY` (api only, never logged; start-up errors name the key only).
- Content never leaves through the new routes: subjects and addresses are metadata the existing `message:read` already covers in quarantine and delivery views; bodies and attachments stay in S3 and are reachable only through the 5.3 preview and download grants.
- Attacker-controlled strings (subjects, filenames, header-from) are returned as JSON strings; filenames use the existing sanitizer of the scans view.
- Threat lookups could be an oracle ("is my sample known?"): authenticated tenants only, `threat_intel:read`, `expensive` class, audited.
