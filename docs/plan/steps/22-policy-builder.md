**Brief (product owner, authoritative):** a visual email security policy builder supporting policy name, description, direction, priority, enabled/disabled, AND/OR condition groups, dynamic condition fields, operators, values, multiple actions, exceptions, draft, save, test, dry run, publish, rollback and version history; a readable policy summary (example: "IF: Email direction = Outbound AND attachment contains confidential data THEN: Quarantine AND Notify administrator"); responsive layouts; integration with the backend policy APIs; **never** policy execution in frontend JavaScript (the backend stays authoritative). The product owner signed off on 2026-11-14 that 7.1 ships pages 13 (Policy management) and 14 (Policy builder) as read-only lists and a DSL catalogue reference with "arrives in 7.3" states; 7.3 replaces those states with the builder and the management flows.

### 1.2 Gaps found

1. The catalogue has no human labels, no grouping, no units, no operator value shapes and no action parameter definitions, so a portal would have to hard-code them (forbidden by the step directive: the field list, operators and value types must come from the API).
2. No server-side validation without persisting: create and PUT validate but store; an unfinished or experimental document cannot be checked without saving.
3. The only dry-run reads **one** stored round; "dry run against recent stored messages" would need one request per message from the browser (rate-limit hostile, `expensive` class per call).
4. The api's JSON body parser keeps Express's default limit (100 KiB; no `useBodyParser` anywhere), below the DSL's 256 KiB document limit: a valid but very large definition is refused with `413 payload_too_large` (pre-existing; §2 B16).
5. Portal pages 13/14 are read-only; the dev catalogue fixture is not realistic.

### B1. The builder is driven by the API's DSL catalogue (ADR-0063 decision 1)

- Every field, operator, value type, vocabulary, unit, action, action parameter, limit and context restriction the builder renders comes from `GET /api/v1/policies/catalog`. The portal contains **no** field names, operator lists, enum vocabularies, action parameter lists or DSL rules; it contains only rendering (widgets per value shape and field type, wording of the summary grammar, layout). A field the portal does not specially know is still fully editable through the generic widgets (§4.7).
- The presentation metadata (labels, groups, units, suggestions, operator phrases and value shapes, action labels and parameter definitions, quantifier phrases, scope nouns) lives **in the DSL package**, next to the data it describes: new module `packages/policy-dsl/src/presentation.ts`, exported from the package index, tested for completeness and for agreement with the validator (§9.1). The api's `catalogView` merges it into the catalogue (additive response keys, §4.1). The policy-engine ignores it.
- `docs/api/policy-catalog.json` (new) is a drift-checked snapshot of the catalogue with the shipped default bounds (`timeZones` replaced by the marker `["<runtime: Intl.supportedValuesOf('timeZone')>"]` because it depends on the Node ICU build). It documents the catalogue and feeds the portal dev fixture (§2 B15).

### B2. No policy logic in the browser (invariant; ADR-0063 decision 2)

- The portal **builds and displays** `policy-dsl/1` documents. It never decides whether a condition matches, never computes a disposition, never compiles a regex/glob/CIDR for matching, never validates DSL semantics. Validation, test, dry-run and execution are API calls. Client-side checks are limited to **input hygiene** needed to produce a well-typed JSON value (an integer input parses to an integer, a required input is not empty, a list item is trimmed) and to **catalogue-driven offering** (only the field's `ops`, only fields whose `contexts` allow the place). The server's violations are always shown and always win.
- The readable summary and the version diff are presentation of the document (B5, B10); they never state an outcome for a message.
- Guards (WP2): (1) ESLint `no-restricted-imports` in `apps/admin-portal` forbids `@email-gateway/policy-dsl`, `@email-gateway/risk-scoring`, `@email-gateway/dlp`, `@email-gateway/bec`, `re2js`; (2) a Vitest source scan (`src/test/scripts/assert-no-policy-evaluator.test.ts`) asserts that no file under `apps/admin-portal/src` (excluding `*.gen.ts`, tests, `test-data.ts`, `src/server/dev-mocks/**`) imports those packages and that `apps/admin-portal/package.json` does not depend on them; (3) `apps/admin-portal/scripts/assert-no-policy-evaluator.mjs`, run by the package `build` script after `assert-no-mock-layer.mjs`, scans `.next` (server, static, standalone; `cache` skipped) for needles that exist only in the evaluator library (package names, `policy-input/1`, `evaluatePolicyPerRecipient`, `compileSnapshot`, `buildPolicyInput`, `policy.floor.hard_block`, `policy.clamp.ai_only`, `policy.override.applied`); its unit test proves each needle **is present** in `packages/policy-dsl/src` (so the needles are meaningful) and that the scanner finds a planted needle in a temporary directory and passes a clean one. Dev fixtures (B15) return canned responses and never evaluate.

### B3. The editor model and an exact round trip

- The portal holds a **builder model** (§4.7) that is a lossless mirror of the DSL document plus stable UI keys: `BuilderDefinition { dslVersion, direction, priority, rules[], exceptions? }`, `BuilderRule { key, id, priority, description?, enabled?, directions?, when, unless?, actions[], stop?, override? }`, nodes `group { joiner: 'all' | 'any', children }`, `not { child }` and `leaf { field, op, value?, quantifier? }`, `BuilderAction { key, type, params }`.
- **Exactness:** `parseDefinition(doc)` accepts exactly the documents whose keys are the `policy-dsl/1` keys (values are carried through unvalidated) and refuses others with a reason (legacy `dslVersion: null` rows and unknown keys → the version view falls back to the JSON view). For every accepted document `buildDefinition(parseDefinition(doc).model).definition` deep-equals `doc`; optional keys keep their presence (`enabled` absent ≠ `enabled: true`, `unless` absent ≠ `[]`, action parameters absent ≠ their defaults). The editor writes an optional key only when the user sets it. `not` is a node of its own (a NOT wrapper toggle), so `{ not: { not: X } }` survives.
- **Rule ids and priorities:** a new rule gets `id = rule-<n>` (smallest free n, matching `^[a-z0-9][a-z0-9_-]{0,47}$`) and `priority = max + 10` (0 for the first); ids are editable; rules are listed by `priority`, and "move up/down" swaps the two rules' priorities (the evaluation order is the priority, not the array order). Conditions inside a group move up/down by array position (order does not change the result; it changes trace paths only).
- **Paths:** `buildDefinition` also returns a path index (`rules[2].when.all[0]` → node key, `rules[2].actions[1]` → action key, `rules[2]` → rule key, `exceptions[0]` → node key). Server violations and test/dry-run trace paths are mapped to the deepest indexed prefix and shown on that node; unmapped violations appear in the policy-level list.
- Limits (`depth`, `childrenPerGroup`, `nodesPerRule`, `rulesPerPolicy`, `actionsPerRule`, `exceptionsPerRule`, `exceptionsPerPolicy`, `listValues`, `globs`, `regexes`, `cidrs`, `codes`) come from `catalog.limits`; the editor disables "add" controls at a limit and shows the canonical JSON size of the document against `limits.documentBytes` (and B16).

### B4. Server validation (`POST /api/v1/policies/validate`, new; §4.2)

- Validates a document exactly as a draft save would (`checkDefinition`), plus the directory references against the replica (reported separately as `referenceViolations`, because drafts may reference a department created later but publish/activate/enable require them). Writes nothing (no row, no audit, no outbox, no idempotency record), `policy:manage`, standard rate class, always `200` for a well-formed request (an invalid document is a result, not an error).
- The editor calls it (a) on the explicit **Validate** button, (b) automatically 2 s after the last edit when the document changed since the last validation, at most once per 10 s, only while the tab is visible, paused for `Retry-After` after a `429`, and (c) before the publish dialog confirms. Regex, glob, CIDR and time-zone values are therefore validated by the server (RE2 in `packages/policy-dsl`), never in the browser. Save (create/PUT) still validates on its own and its `400 policy_definition_invalid` violations are mapped the same way.

### B5. Readable summary (presentation only)

- `summarizeDefinition(definition, catalog, names)` (portal, pure) renders the DSL into structured lines with the fixed grammar of §4.7: per rule a title line, `IF:` lines (the policy direction when it is not `any` and the rule `directions` come first as "Email direction is Outbound"), `AND`/`OR` joiners per group with indentation, `NOT:` for negations, `UNLESS:` for rule exceptions, `THEN:` action lines joined with `AND`, notes for `stop`, `override` and disabled rules; then "Policy-wide exceptions". Leaf text = `[quantifier phrase + scope noun:] <field label> <operator phrase> <values>`; enum and code values are humanized, numbers formatted with units, regexes shown as `/pattern/flags`, directory ids replaced by department/user names when known, long lists cut after five items ("and 12 more"). The brief's example renders as:

  ```text
  Rule quarantine-confidential (priority 10): Hold confidential data leaving the organization
  IF:
    Email direction is Outbound
    AND DLP data categories contain any of Confidential
  THEN:
    Quarantine
    AND Alert administrators (severity: warning)
  ```

- Shown live beside the editor (desktop) or above it in a collapsible section (mobile), and on every version view, publish and rollback dialog. It states "The platform floor still applies" from `catalog.enforcement`; it never states that a message would match.

### B6. Draft, save and optimistic concurrency

- **New policy** (`/policies/new`): name, description, change note and the definition; **Save draft** = `POST /policies` → navigate to `/policies/{id}/versions/1`. `409 policy_name_taken` → field error on name; `409 policy_limit_reached` → form error with the limit.
- **Edit** (`/policies/{id}/versions/{n}` with `status = draft` and `PolicyManagementController_updateDraft_v1` allowed): **Save** = `PUT` with `{ definition, changeNote, expectedRowVersion: <loaded rowVersion> }`. On `409 policy_conflict` (`currentRowVersion`) a dialog offers **Reload theirs** (discard local edits), **Overwrite with mine** (re-PUT at `currentRowVersion`, an explicit choice) and **Download my definition** (JSON file). On `409 policy_version_immutable` (published meanwhile) it offers **Save as a new draft** (`POST …/versions` with the local definition). A draft must be a valid document (5.2 §12.4 precision 4): until it validates, the work exists only in the editor; an unsaved-changes guard (`beforeunload` and confirmation on the page's own navigation controls) prevents silent loss. No browser storage of definitions.
- **New draft from a version** = `POST …/versions { basedOnVersionNo }` (the "Edit" action of a published version, and "Restore as new draft"). Several drafts may coexist; the editor lists the other drafts of the policy.
- Name and description of an existing policy change through `PATCH /policies/{id}` with the policy `rowVersion` (rename dialog). Direction and priority belong to the version (publish to change them; the dialog says so).

### B7. Test (server-side, synthetic facts)

- Panel `PolicyTestPanel` (sheet on mobile, side panel on desktop): **target** — "This draft" (`{ policyId, versionNo }` of the saved draft; when the editor has unsaved changes the button reads **Save and test**), "This new policy (unsaved)" (`{ definition }` before the policy exists; the API adds it to the active set), "Active policies" (`active`), "Platform default only" (`platform`); **facts** — `SyntheticFactsForm` (direction, sender envelope/header From/authenticated, recipients, client IP/host, authentication results, attachments, URLs and rewrite status, risk revision 0, DLP, BEC, scan outcome, evaluation time, `resolveDirectory`) whose vocabularies come from the catalogue fields with the same names (`auth.spf` values for SPF, `dlp.categories` values for DLP categories, …), presets (clean inbound, outbound confidential data, phishing URL, malware attachment, executable attachment) and an **Advanced (JSON)** editor; the server answers `400 policy_test_facts_invalid` for invalid facts. Not offered for `{ policyId, definition }` (no such API target; alternative §5).
- The result view renders the server's `PolicyTestResponse`: disposition and lifecycle disposition, recipient split and decisions, decisive source/policy/version/rule, explanation text, matched rules, actions with applicability, delivery header edits, floor reasons, recommendation, override and clamps, invalid versions, trace (each trace path has **Show in editor**, which highlights the node through the path index).

### B8. Dry run (server-side, bounded)

- **Recent messages** (new `POST /api/v1/policies/dry-run`, §4.3): re-evaluates the newest stored evaluations of the organization (one per message, rounds with a scan) in a window (default the last 7 days, at most `POLICY_HISTORY_MAX_RANGE_DAYS`) against a target, compiling the target snapshot once, reading each round's facts from the replica exactly as the per-message dry-run does, sequentially, at most `limit ≤ POLICY_DRY_RUN_SAMPLE_MAX` rounds and `POLICY_DRY_RUN_DEADLINE_MS`; class `expensive` plus a per-principal limit `POLICY_SAMPLE_DRY_RUNS_PER_MINUTE`; writes nothing; returns per-round stored vs dry-run disposition and decisive rule, change flags and a summary with transition counts. Never subjects, addresses or content (message public ids only, as the history route).
- **One message** (existing per-round route): message id → `GET /messages/{id}/scans` → pick a completed round → dry-run; shows stored vs recomputed and `reproducible`.
- The portal shows the remaining budget (`RateLimit-*` headers via `ApiError`/429 countdown) and disables **Run** during `Retry-After`. Targets as in B7 (saved draft version, inline for a new policy, active, platform).

### B9. Publish, activate, enable/disable and rollback (ADR-0063 decision 5)

- **Publish** (`policy:publish`): dialog showing the summary, the server validation result (re-run), the reference check, and "Activate now" (default on; off = published but inactive). `POST …/publish { activate, expectedRowVersion: <draft rowVersion> }` with an Idempotency-Key (handled by `useApiMutation`, reused on retry). Success shows the new organization `generation` and "applies to the next evaluation only".
- **Activate / roll back** (`policy:publish`): a published, non-active version shows **Activate vN** (newer than the active one) or **Roll back to vN** (older). The confirm dialog shows the active and target version numbers, the diff summary (rules added/removed/changed, B10) and the next-evaluation note; `POST …/activate { expectedRowVersion: <policy rowVersion> }` with an Idempotency-Key; `409 policy_conflict` → "the policy changed; reload and confirm again"; `409 policy_rule_limit_reached`, `400 policy_definition_invalid` (a version the DSL no longer accepts or with a vanished department) shown with their details.
- **Rollback is the existing server operation**: re-activating an earlier published version is audited `policy.version_activated` with `previousVersionNo` and `versionNo`, increments the generation in the same transaction, and applies to the next evaluation only (P12). No new route, no `rolled_back` status written (the column value stays unused, as 5.2 documented); a separate audit action was considered and rejected (§5). "Restore as new draft" (B6) is the alternative when the user wants to edit before re-publishing.
- **Enable / disable** (policy status): switch with confirm; `POST …/enable|disable { expectedRowVersion }`; enable is offered only with an active version. **Delete policy** (archive) with a confirm that requires typing the policy name; **Delete draft** with a confirm.
- Mutations follow `useApiMutation` (one key per intent where the operation declares idempotency; `Idempotency-Replayed` counts as success; `429` countdown); every success invalidates the policy, versions, list and audit queries.

### B10. Version history and diff

- The versions table (newest first, `GET …/versions`) shows status, active marker, rules, override flag, change note, author and publisher (user names when `user:read`, else ids), published time, and actions (open, edit/new draft, publish, activate/roll back, delete draft, compare). ### B11. Audit visible

- The policy detail page has an **Audit** tab (gated by `AuditLogsController_search_v1`): two keyset reads `resourceType=email_policy&resourceId=<policyId>` and `resourceType=policy_version&resourceId=<policyId>` over the last 90 days (`API_AUDIT_MAX_RANGE_DAYS`), merged by `createdAt`, rendering action, actor, time and the metadata numbers (version, previous version, generation, rule count, hashes). ### B12. RBAC and tenant isolation

### B16. Request size (known limitation)

- The api's JSON body limit is Express's default 100 KiB (no `useBodyParser` in `apps/api`), lower than the DSL's 262 144-byte document limit. 7.3 does **not** change the global parser (a cross-cutting API decision). The editor shows the document size; a `413 payload_too_large` from save/validate/test is shown as "This policy is too large to send to the API (limit about 100 KiB); split it into several policies." WP1 measures the boundary (a ~150 KiB definition) and records the observed status in §13; the follow-up is §12.
- **Resolved by the closer (§14.8):** the global parser is unchanged (100 KiB); the routes that carry a definition get their own JSON parser with the DSL's document limit plus 64 KiB (327 680 bytes), and the global filter maps body-parser's client errors to their status (`413 payload_too_large`). The editor's message is now "This policy is larger than the policy document limit; split it into several policies." with the size against `limits.documentBytes`.

## 5. Alternatives considered

- **Ship `@email-gateway/policy-dsl` to the browser** for instant validation and previews: rejected. It contains the evaluator (forbidden in the browser by the brief), RE2 and tldts (bundle size), and a second copy of the validator would drift from the api's deployed version; the server validate route is cheap and authoritative.
- **Hard-code labels and parameter forms in the portal:** rejected (directive: the catalogue is the source; a new field or parameter must appear without a portal release). Keeping labels in the api module instead of the DSL package: rejected; the DSL package owns the catalogue data and its docs test.
- **A server-rendered summary** (`GET …/versions/{n}/summary`): rejected for 7.3: the summary must update live on every keystroke; it is pure presentation of the document. A server summary may be added later for API clients (§12).
- **A dedicated rollback route / audit action** (`POST …/rollback`, `policy.version_rolled_back`): rejected. `activate` of an earlier published version is already the audited, generation-incrementing, idempotent rollback of ADR-0043 decision 7 with `previousVersionNo` in the metadata; a second route would duplicate it and the `rolled_back` status would rewrite immutable history. The UI names it "Roll back" when the target is older than the active version.
- **Dry-run of recent messages by looping over the per-round route in the browser:** rejected (N `expensive` calls per run, N × facts reads with no shared snapshot, no deadline, and the 7.2 tenant-budget finding). One bounded server request with one compiled snapshot is cheaper and rate-limit friendly.
- **Test target `{ policyId, definition }`** (an unsaved edit of an existing policy replacing its active version): useful but an API target change on three routes; rejected for 7.3: the editor saves the draft first ("Save and test"), which is exact because `{ policyId, versionNo }` replaces the policy's active version. Recorded in §12.
- **Saving invalid work-in-progress drafts** (relaxing 5.2's "drafts must validate"): rejected; stored drafts stay valid documents so every version view, test and publish works on a well-formed definition. Unsaved work is protected by the unsaved-changes guard, not by browser storage (definitions are tenant configuration; no storage on shared machines).
- **Raising the api's JSON body limit** in this step: deferred (§2 B16); a global parser change is a cross-cutting API decision.
- **DLP/BEC editing forms in 7.3:** first deferred by the directive's default; the product owner then decided on 2026-11-16 to include them (§2 B13, WP5).
- **Drag-and-drop reordering:** not required; move buttons are keyboard accessible and testable. Drag-and-drop may be added later on top of the same reducer commands.

## 7. Security notes

- No new data path: validate and dry-run read through the existing tenant-scoped repositories (replica) and write nothing; sample items carry message public ids, times, enums and rule ids (as `GET /policies/executions`), never subjects, addresses, file names, URLs or content.
- No organization id from the client; foreign ids → `404`; the sample selection is scoped by `CurrentScope`.
- Regexes are compiled only on the server (RE2); the portal never constructs a `RegExp` from tenant input (the source scan checks for `new RegExp(` in `features/policies/**`).
- Policy definitions are never written to browser storage, logs or analytics; the "Download my definition" action creates a local file only on explicit request.
- Secret-shaped strings: none added; examples use placeholders containing `EXAMPLE`; test literals that look like secrets are built at runtime.

#### Deviations and precisions (with evidence)

1. **76 fields, not 75.** `POLICY_FIELD_NAMES.length` is 76 (`node -e "require('./dist').POLICY_FIELD_NAMES.length"` in `packages/policy-dsl`); the presentation covers all 76 and the test asserts the exact key list.
2. **`bec.rule_codes` suggestions = the codes of the `BEC_RULES` table (50).** That is the instruction's list (the deterministic codes of `BEC_REASON_CODES` without `BEC_AI_CODES` and `BEC_INPUT_UNAVAILABLE_CODES`) minus `bec.not_inbound` and `clean.below_threshold`, two engine-level codes a `bec_rules` row never carries: the fact is built from the rows' codes (`packages/policy-dsl/src/input.ts`, `ruleCodes` of `rows.bec.rules`) and `becRuleEntrySchema` binds every row's code to its rule id (`BEC_RULES[id].code`). Suggesting them would offer conditions that can never match.
3. **`scan.reason_codes` and `risk.reason_codes` get suggestions** (choice left to WP1): `scan.reason_codes` = the sorted unique union of `RSPAMD_REASON_CODES`, `ATTACHMENT_REASON_CODES`, `URL_REASON_CODES`, `BEC_REASON_CODES`, `DLP_REASON_CODES` (244): the round's codes are the union of the synchronous engines' finals (`apps/email-worker/src/scanning/aggregate.ts`; the asynchronous sandbox never contributes). `risk.reason_codes` = `RISK_REASON_CODES` of `@email-gateway/risk-scoring` (158, “every `risk.*` reason code the scorer can emit”; a dependency the DSL package already has). Engine failure codes of a round (`engine.timeout`, …) are not an exported list and stay typeable (suggestions are never closed). All six suggestion lists are sorted (code-point order) and unique; every suggestion validates in a `contains_any` leaf.
4. **Time zones are the runtime's list.** Node 22.23.4 (ICU 78.3, tz 2026e) lists 418 zones; `policyTimeZones()` returns 419 with `UTC`. It lists `Asia/Calcutta`, not `Asia/Kolkata`; the validator accepts both (`isValidTimeZone` resolves aliases), so WP2/WP3 should allow a typed zone the list does not show, or show the server's violation.
5. **Operator item lengths** follow the instruction: `maxItemLength` is `stringValue` (320) for `in`/`not_in`/`domain_in` (a domain item longer than 253 is refused by the validator anyway), `globLength`/`regexLength`, and null for `in_cidr` and the code operators (the reason-code maximum of 64 is not a `POLICY_LIMITS` value).
6. **Action parameter patterns** are documentation (the server validates): the tag-label pattern escapes the class hyphen (`^[a-z0-9][a-z0-9._\-]{0,31}$`) so it compiles with the `u`/`v` flags (an HTML `pattern` attribute uses `v`); the subject prefix is `^[\x20-\x39\x3B-\x7E]{1,32}$` (printable ASCII without `:`), the warning text `^[\x20-\x7E]{1,128}$`. The test compiles each with `v` and checks it against the validator.
7. **Sample defaults clamped to the configured bounds.** `sample.limit` is optional in the schema and defaults to min(25, `POLICY_DRY_RUN_SAMPLE_MAX`); `from` defaults to `to` − min(7, `POLICY_HISTORY_MAX_RANGE_DAYS`) days. With the design's literal defaults a request without `sample` would be refused with `400` whenever an operator configures a maximum below 25 rounds or 7 days. An explicit value above a bound is still `400 validation_failed` (message names the key).
8. **B16 measured: a body above the JSON limit is answered `500 internal_error`, not `413 payload_too_large`.** Evidence: `test/policy-builder.e2e.test.ts` and `integration/policy-builder.test.ts` POST a valid ~150 KiB definition (`validatePolicyDefinition` accepts it; 145–155 KiB on the wire) to `POST /policies/validate` and observe `[500, 'internal_error']` on the stubbed app and on the real stack; a probe showed the same on the pre-existing `POST /policies/test`; the boundary is Express's 100 KiB (a 101 399-byte body → `200`, 102 423 bytes → `500`); malformed JSON → `400 validation_failed`. #### Deviations and precisions (with evidence)

1. **`SyntheticFacts` is `NonNullable<RequestBody<'PolicyToolsController_test_v1'>['facts']>`.** `facts` is optional in the request body, so the §4.7 type includes `undefined`, which a controlled form value never is. Same keys; WP3 passes `{}` for empty facts.
2. **A leaf's `field` and `op` are optional in the model.** `emptyDefinition` must hold "one empty condition" and "Add condition" adds an empty row whose field the user picks; the model represents it as `{}` (the server reports `value_required` until it is filled). `parseDefinition` therefore accepts leaves without `field`/`op` (they round-trip exactly); every other required key (`dslVersion`, `direction`, `priority`, `rules`, rule `id`/`priority`/`when`/`actions`, action `type`) must be present.
3. **"Values carried through unvalidated" vs. `malformed`.** Leaf values and action parameter values are carried as any JSON; structural values the model types (policy/rule `direction`, `priority`, `id`, `enabled`, `stop`, `override`, `directions[]`, `quantifier`, `field`, `op`, node arrays, action `type`) must have their JSON type, else `malformed` with the path. Stored drafts always validate on the server, so only legacy or foreign documents are refused (the page shows JSON, B3).
4. **Action parameters are not checked by `parseDefinition`.** It has no catalogue (its §4.7 signature takes only the document), so every non-`type` key of an action is a parameter and round-trips; the actions editor shows keys the catalogue does not define as "not in the catalogue" with a Remove control, and the server reports `unknown_key`.
5. **Two value kinds the catalogue does not state are derived from the field name's last segment** (catalogue gap; evidence: §4.1 gives `id` fields no directory kind and both time fields `valueShape: 'time'`, "the field decides"): the directory of an `id` field (`department` → departments, `user` → users, any other `id` field offers both lists) and the time value (`window` → weekly window, `date_range` → date range, any other `time` field uses its value's keys or a "Weekly window / Date range" choice). Summaries look ids up in both name maps. No field list is hard-coded; a new field of either type stays editable. Follow-up below.
6. **The direction line's label** is the label of the catalogue field named `direction` (the document keys `direction`/`directions` describe that fact; fallback "Direction"), and its verbs `is`/`is one of` are summary grammar words. WP1's snapshot labels the field "Email direction", matching B5.
7. **`summaryToText` excludes `floorNote`;** `header` holds only "This policy has no rules." (or why a document cannot be summarized). Evidence: B5's exact text block has neither a header line nor the floor statement; `PolicySummaryView` shows the floor statement under the summary.
8. **Diff precisions:** per-rule `IF` lines leave out the policy-direction line (a policy direction change is reported once under `policy`, instead of as a change of every rule; a rule's own `directions` stay in its lines), and diff summaries list every list item (no "and N more", which could hide the changed item). `change` is decided by the canonical JSON of the rule, so a change the summary does not show still counts.
9. **Additive optional props:** `DefinitionDiffView` `view`/`onViewChange` (the compare page's `?view=summary|json`, §4.6); `EvaluationResultView` `isEditorRef(ref)` (trace rows of other policies of the active set get no "Show in editor"; without it every row with a path does). `useBuilderContext` is exported (the provider's context hook).
10. **Build scanner precisions.** (a) Package-name needles are the evaluator packages present in `packages/policy-dsl/src` (`@email-gateway/policy-dsl`, `@email-gateway/risk-scoring`, `re2js`); `@email-gateway/dlp` and `@email-gateway/bec` are banned by lint and the source scan but are not needles: they do not occur in `packages/policy-dsl/src` (so the needle test could not prove them) and they do occur in the copied root manifest. (b) `standalone/package.json` is skipped: Next copies the monorepo's root manifest there, whose scripts name every workspace package; evidence: `grep -l @email-gateway/dlp .next/standalone/package.json` hit the existing 7.2 build output. The portal's own manifest (`standalone/apps/admin-portal/package.json`) is scanned.
11. **Defaults the design leaves open:** `emptyDefinition()` uses direction `any` and policy priority `100`; the Enabled switch writes `enabled: false` when turned off and removes the key when turned on; the stop control is a tri-state select (Default / Stop evaluating later rules / Continue with later rules); a new nested group takes the opposite joiner of its parent; removing a condition that is the only child of a NOT removes the NOT; the `when` root cannot be removed (an empty rule shows "No conditions in this group yet"). In a relaxing or holding rule the field picker offers only fields allowed in every place of the rule (`fieldsForAll`), and existing disallowed conditions get warnings.
12. **No catalogue field list in the test form, except the facts form's mapping.** The facts form names the catalogue fields "with the same meaning" as the instructions list (`auth.spf`, `dlp.categories`, …), and maps `scan.outcome`'s `not_scanned` to the facts `trigger` `parse_failed` (the DSL documents `not_scanned` as the parse failure).

#### Deviations and precisions (with evidence)

1. **`src/server/dev-mocks/dev-mocks.test.ts` (outside WP5's file list) gained one line.** Its first test pins the exact key set of `FEATURE_FIXTURES`; the registration the package instructions require (`'dlp-bec'` as the last entry) makes it fail without `'dlp-bec'` in that list. The change is the single list entry; nothing else in the file changed. WP3 does not own the registry (design §4.8), so no concurrent edit is expected.
2. **`POST /dlp/patterns/test` answers `200 { valid: false, code }` for a refused pattern and `400` only for a malformed request** (evidence: `DlpPatternsService.test` returns the safety result; the `400` comes from the body schema, e.g. a sample over 4 096 characters). The panel shows both: the server's refusal (`valid: false`, the code explained) and a `400` (messages by input, code, request ID). A `400` whose code is a safety code (as create/update answer) is also explained. Tested.
3. **Editors work on a snapshot.** Edit forms keep the entry as it was when the editor opened (`useEntryEditor`, a dictionary's first loaded detail, the compliance settings when "Record basis" was clicked); a background refetch (window focus, invalidation) never replaces what the user is editing or the `version` the save is based on. Only "Load the current version" after a `409 version_conflict` replaces it. Delete confirmations do the same (`useEntryTarget`): the version sent is the one the user saw; after a conflict (shown in the dialog) the target is refreshed and a second, explicit confirm applies to the current version. Evidence: tests "a background refetch never replaces the policy being edited" and the exception delete conflict test.
4. **Form values are strings; body builders convert.** Numbers, confidences and "one per line" lists stay strings in the zod schemas (refinements, no transforms) because the portal's field components need equal react-hook-form input and output types (as in the existing forms); the builders produce the typed request bodies, checked against the OpenAPI request schemas.
5. **Native `<select>` for every enum input** (as the 7.2 Email Details pages do): labelled, keyboard and phone friendly, and reliable inside sheets. Multi-value enums are checkbox groups in a `fieldset` with a `legend`; errors are linked with `aria-describedby`.
6. **Addresses and domains of DLP rule scopes are lower-cased in the browser.** The OpenAPI pattern of `conditions.sender|recipients.addresses|domains` requires lower case, while the API normalizes before validating; lower-casing keeps the request valid against the published schema (input hygiene). International domain names are not converted (the API normalizes them). BEC and exception values are sent as typed (their schemas have no case pattern; the API normalizes).
7. **Expiry and review dates are day inputs**, sent as the end of that day in UTC (`T23:59:59.000Z`), like the threat-intelligence forms. An unchanged expiry is neither re-validated nor sent (so an expired exception can still get a new reason).
8. **The DLP policy delete requires typing the policy name** (it deletes every rule of the policy; the same rule as B9's email policy delete). Other deletes use a plain confirmation.
9. **The rules of a DLP policy are viewable with `dlp:read`** ("Rules" row action, no editing control): a read of `GET /dlp/policies/{id}` that the read-only roles hold. Editing controls inside it need `dlp:manage`.
10. **Detector, category and coverage-reason labels are portal presentation** (the API has no labels for them); `model.test.ts` asserts every vocabulary equals the OpenAPI enum, so a change of the API fails the portal tests.
11. **Incidents and feedback reads are re-implemented in `fixtures/dlp-bec.ts`** (derived from the message dataset as `policies.ts` does, but linked to this fixture's policy and rule ids), so the whole DLP/BEC surface lives in one fixture; registered last, these replace the read-only lists of `policies.ts` (which WP5 did not edit).
12. **The MFA state is decided from `GET /auth/me` `session.mfaAuthenticated`** before any request; a `403 mfa_required` from the API (a stale session flag) shows the same state with the request ID inside the form or dialog and raises the shell's MFA dialog (`useApiMutation`).
