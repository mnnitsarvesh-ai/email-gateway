## 2. Decisions

### 2.0 Invariants (never traded away)

1. **Never clean by accident.** A ClamAV error/timeout/open breaker, an inspector crash or wall-clock timeout, a missing or corrupt part object, a Redis error or an incomplete attachment list is never `clean`. `clean` is reachable only through rule C1 (§A6) on a complete inspection with a definite ClamAV answer.
2. **No file content outside S3 and process memory.** Attachment bytes are read from S3 into bounded memory, streamed to clamd over TCP and handed to the inspector child over IPC. Nothing is written to disk (no temp files at all, A4), MySQL, Redis, events, logs or metrics. Rows hold hashes, sizes, type ids, rule names, signature names, counts and codes. Archive entry names are never stored or logged (entries are addressed by index path).
3. **No execution.** No attachment or archive entry is ever executed, rendered, opened by a viewer, or passed to a shell. The inspector child parses bytes in memory, has no credentials, no inherited environment and never spawns a process.
4. **Idempotent per (message, round, engine)** through the 4.1 orchestrator: ledger `processOnce(consumer, eventId)`, the unique final row per `(scan, engine)`, and child rows (`attachment_scan_results`, `sandbox_submissions`) with unique keys per `(scan_id, attachment_id)` written **in the finalize transaction** of the final row. A duplicate delivery creates no second row, submission or event.
5. **Tenant from trusted context.** The organization comes from the envelope, is checked against the writer row; every part key must start with `org/<envelope org>/` and equal the `email_attachments.object_key` of that organization's message. Admin APIs take the organization from the authenticated scope or require platform permissions.
6. **Engines classify, policy decides** (4.1 §2.0-8). The attachment engine records verdicts, reason codes and sandbox submissions; it never blocks, strips or quarantines. The dev pass-through decision for `malicious` (A15) is a local stand-in.
7. **Bounded everything.** Every byte count, entry count, depth, ratio, CPU second, RSS megabyte, connection, queue slot, cache entry and API page is bounded by validated configuration.

### A1. One `attachment` engine on `scan.attachment`, required for every tenant

- **Catalog:** `ENGINE_NAMES` becomes `['rspamd', 'attachment', 'url', 'bec', 'dlp', 'sandbox']` and `SECURITY_STAGES` `['antispam', 'attachment', 'url', 'bec', 'dlp', 'sandbox']` (`clamav` and `yara` were never registered or stored; ClamAV and YARA are components of one engine, see alternatives §7). New entry `{ name: 'attachment', stage: 'attachment', queue: 'scan.attachment', requiredByDefault: true, tenantMayDisable: false, description: 'Attachments: file type, known-threat hashes, ClamAV, YARA, archive limits (step 4.2)' }`.
- **Why one engine, not `clamav` + `yara`:** both need the same bytes, the same archive walk and the same per-attachment verdict; two engines would read every part twice from S3, need two queues (the brief fixes `scan.attachment` only) and split one per-attachment verdict across two final rows. Component versions are kept separately (A9), so explainability is not lost.
- **Required:** yes, for every tenant and every direction (`requiredByDefault: true`, `tenantMayDisable: false`). `SCAN_ENGINES` default becomes `rspamd,attachment`. A round whose attachment engine cannot decide ends `scan_failed` (4.1 invariant).
- **No attachments (rule A0):** a message whose parse row is complete (status `parsed` or `parsed_with_defects`, or `parse_limit_exceeded` without an attachment-affecting limit, A6 E1) and that has **zero** `email_attachments` rows gets the definite outcome **`skipped`** with reason code `attachment.none`. `skipped` is ADR-0026's "not applicable" outcome; `aggregateRound` ignores it for the verdict (so a clean Rspamd result plus `skipped` is `clean` **because Rspamd decided**, never because of the attachment engine) and it satisfies "every required engine has a final row". The rule is explicit in the mapper and tested.
- **Consumer:** the 4.1 scan role (`SCAN_ENABLED`), same `eg-scanner` broker user, ledger consumer **`email-worker.scan.attachment`**. A new env `SCAN_CONSUMERS` (comma list, default = every enabled engine; must be a non-empty subset of `SCAN_ENGINES`) selects which engine consumers a replica runs, so production can deploy `email-worker-attachment` (`SCAN_CONSUMERS=attachment`) separately from the Rspamd consumers. `requiredEngines` of a round still comes from `SCAN_ENGINES` (identical on every scan replica; documented and checked at start by logging the hash). **Not a separate broker user:** both deployments run the same image, code and queues of one bounded context; a second user would duplicate the same grants. Justified in ADR-0028.

### A3. Data flow of one engine call (`AttachmentEngine.scan(ctx, signal)`)

The orchestrator (`ScanRoundService`) is unchanged except for the generic extensions in A12. Inside the adapter:

1. **Load (writer, one query each):** `email_message_parses` row of `(message, received_at)` (status, `limits_exceeded`, `attachment_count`); `email_attachments` rows of the message (`organization_id = ctx.organizationId`, ordered by `part_index`, at most `ATTACHMENT_MAX_PER_MESSAGE`; more rows → reason `limit.attachment_count`, the extra attachments are reported as not scanned, A6 S3). No parse row → engine failure `error`/`parse_row_missing` (not retryable; cannot happen for a `parsed.v1`). **Echo checks (review round 1):** every read selects its identifying columns and verifies them (message, organization and `received_at` of the parse row and of every attachment row, part indexes strictly ascending, every known-hash row among the requested hashes), and the number of attachment rows must equal `min(attachment_count, ATTACHMENT_MAX_PER_MESSAGE + 1)`; a mismatch (the §6 wrong-read defect) is the retryable attempt failure `error`/`inconsistent_read` (not the engine's fault, `scan_attachment_inconsistent_reads_total{read}`), never `skipped` or a verdict.
2. **Engine-level rules:** A0 (none), E1 (parse incomplete).
3. **Known-threat hash lookup (writer):** one `SELECT sha256, severity, family FROM malware_signatures WHERE sha256 IN (…) AND (expires_at IS NULL OR expires_at > now)` for every outer `sha256`; inner entry hashes are looked up after inspection (step 5e) in chunks of 500.
4. **Settings:** `ctx.settings` = the effective attachment settings (A8) resolved by the 4.1 `SettingsResolver` through `attachmentRegistration.settingsFor`.
5. **Per attachment** (at most `ATTACHMENT_PER_MESSAGE_PARALLELISM` at a time, default 2; every step honours `signal`):
   a. `object_key` NULL (`not_stored_size_limit`) or `size_bytes > effective maxAttachmentBytes` → no content scan; rule S3 `limit.attachment_size` (+ `attachment.not_scanned`).
   b. Part key check (`org/<org>/part/` prefix, equal to the row) → else engine failure `error`/`part_key_mismatch` (not retryable).
   c. **Cache lookup** (A10) with the current content-version key → hit: the cached **content result** (step d's output); count `cache{result="hit"}`.
   d. **Miss:** acquire `size_bytes` from the worker's byte budget (`ATTACHMENT_MEMORY_BUDGET_BYTES`, a weighted semaphore; validated ≥ `ATTACHMENT_MAX_BYTES`); read the S3 object fully into a `Buffer` (bounded by `size_bytes + 1`; more bytes or a different SHA-256 → engine failure `error`/`part_integrity`, not retryable; `NoSuchKey` → `error`/`part_unavailable`, not retryable; other S3 errors → thrown, transient); then **in parallel**: (i) clamd `INSTREAM` of the buffer (A7) and (ii) the inspector child (A4: true type, archive walk, YARA). Both must return a definite answer for a content result; a clamd failure fails the engine attempt (retryable, breaker), an inspector **wall-clock** timeout or crash fails the attempt (retryable, `inspector_timeout` / `inspector_crash`), an inspector **CPU or memory limit** kill is a definite content result with `limit.cpu_time` / `limit.memory` (A4, rule S3). Release the budget in `finally`.
   e. Inner entry hashes → known-hash lookup (always, also on a cache hit: the catalog is authoritative and not cached).
   f. Write the content result to the cache (A10) unless it contains an inspector-limit kill (those use the short TTL).
   g. **Map** (A6) content result + hash hits + tenant settings → attachment result (verdict, reason codes).
6. **Aggregate** the attachment results into the engine result (A6), build the per-attachment rows and the sandbox submissions (A11), return `{ kind: 'definite', result, attachments, sandbox }`.

An attempt failure on attachment _k_ discards the results of the attachments before it (nothing is persisted for a non-final attempt), but their content results are cached, so the retry is cheap. The engine call timeout `SCAN_ATTACHMENT_TIMEOUT_MS` covers the whole message.

### A4. The inspector: a pool of resource-limited child processes (YARA-X, type detection, archives)

**Runtime choice for YARA: YARA-X through `@litko/yara-x` (napi-rs binding, prebuilt for linux-x64/arm64-gnu and darwin), run inside an inspector child process.** Justification:

- YARA-X is VirusTotal's maintained Rust rewrite of YARA (the C YARA 4.x line is in maintenance mode); the binding has prebuilt binaries for the image (`node:22-bookworm-slim`, arm64 on the local VM and x64 in CI/production) and for the macOS host, so package and integration tests run without a system package, and there is no `postinstall` build step. It scans **buffers** (no temp files), supports a per-scan timeout (`setTimeout`), a max scan size (`setMaxScanSize`) and compiled-rule serialization.
- Risk: a single-maintainer community binding that releases often. Mitigations: exact version pin, chosen ≥ 14 days after its publication date (at design time `0.10.0`, published 2026-10-18; the implementer checks the advisories and the changelog and records the version); the binding runs **only in the child**, so a native crash or hang kills the child, never the worker; the rule bundle is compiled once per child start and its rule count and id are verified; fallback (recorded deviation, not implemented): the official YARA-X CLI (`yr scan`) in the same child-process sandbox.
- Rejected: the old `yara` npm binding (unmaintained, compiles libyara at install); the `yara` 4.x CLI per file (needs a temp file per scan, a system package on the host and the image, and a process spawn per file); in-process `worker_threads` (`resourceLimits` cap only the V8 heap, not native memory, and a native fault kills the whole worker).

**Process model (`scanning/engines/attachment/inspector/`):**

- `InspectorPool` in the worker: `ATTACHMENT_INSPECTOR_POOL_SIZE` children (default 2, max 16), one job at a time per child, a FIFO wait queue bounded by the engine concurrency. A child is recycled after `ATTACHMENT_INSPECTOR_MAX_JOBS` jobs (default 500) and after any kill.
- **Spawn:** `child_process.spawn` with `stdio: ['ignore', 'ignore', 'pipe', 'ipc']`, `serialization: 'advanced'` (Buffers over IPC), an **empty environment** except `NODE_ENV` and `PATH` (no credentials, no database/S3/Redis URLs), `execArgv` `--max-old-space-size=<ATTACHMENT_INSPECTOR_HEAP_MB>` (default 192), cwd = a private per-child directory (below).
  - On **Linux** the command is `prlimit --cpu=<soft:hard, see below> --core=0 -- node …` (util-linux `prlimit`, expected in `bookworm-slim`; WP2 verifies, else adds the package). `RLIMIT_NPROC` is not used (it counts every process of the uid); the child never spawns by construction (no `child_process` import in the child entry, enforced by a unit test that scans the child's module graph). Because `RLIMIT_CPU` is per process lifetime, the child enforces the per-file CPU limit itself (below) and the rlimit is the backstop: soft = `ATTACHMENT_INSPECT_CPU_SECONDS × ATTACHMENT_INSPECTOR_MAX_JOBS` (bounded), so a runaway native loop still dies. `RLIMIT_AS`/`RLIMIT_DATA` are **not** used (V8 reserves large virtual ranges; they break Node), memory is enforced by the RSS watchdog.
  - `ATTACHMENT_INSPECTOR_RLIMITS=required` (default; production, containers) refuses to start without `prlimit`; `best_effort` (local host on macOS only; refused when `NODE_ENV=production`) runs without it and logs a warning once. Recorded in readiness details.
- **Per-file limits** (security controls of the brief):
  - **CPU timeout:** the worker samples the child's CPU time every 100 ms (`/proc/<pid>/stat` utime+stime on Linux; `ps -o time= -p <pid>` elsewhere) and SIGKILLs the child when the job's CPU delta exceeds `ATTACHMENT_INSPECT_CPU_SECONDS` (default 10) → content result `limit.cpu_time` (definite, suspicious). CPU time is load-independent, so the result is a property of the file.
  - **Memory limit:** the same sampler reads RSS (`/proc/<pid>/status` VmRSS; `ps -o rss=`) and SIGKILLs above `ATTACHMENT_INSPECT_MAX_RSS_MB` (default 384) → `limit.memory` (definite, suspicious). The V8 heap cap and the inspector's own byte accounting (below) keep a well-behaved child far below it; an RSS kill means a limit bug or a hostile native-path input.
  - **Wall-clock timeout:** `ATTACHMENT_INSPECT_TIMEOUT_MS` (default 30 000) → SIGKILL, attempt failure `timeout`/`inspector_timeout` (retryable: wall time depends on host load).
  - A child exit for any other reason (crash, SIGSEGV, IPC error) → attempt failure `error`/`inspector_crash` (retryable); repeated crashes on the same file exhaust the attempt budget → final `error` (never clean).
  - YARA-X `setTimeout(ATTACHMENT_YARA_TIMEOUT_MS)` (default 10 000) per buffer and `setMaxScanSize(ATTACHMENT_MAX_ENTRY_BYTES)`; a YARA timeout is reported in the content result as `yara.timeout` → rule S3 (`limit.yara_timeout`, suspicious).
- **Safe temporary file handling:** no temporary files are written (buffers only). Each child still runs with cwd = `<ATTACHMENT_INSPECTOR_TMPDIR or os.tmpdir()>/eg-inspect-<pid>-<16 random hex>` created with mode `0700` (so any accidental relative write is private), removed in `finally` on child exit; at pool start, stale `eg-inspect-*` directories older than 10 minutes owned by the current uid are removed. The k8s manifest mounts the tmpdir as a size-limited `emptyDir` and the root filesystem read-only.
- **Protocol:** worker → child `{ id, op: 'inspect', bytes: Buffer, declared: { contentType: string | null, extension: string | null }, limits }`; child → worker `{ id, ok: true, result: ContentResult }` or `{ id, ok: false, code }`. Startup handshake `{ op: 'ready', yaraXVersion, bundleId, ruleCount }`; the pool refuses to start if `bundleId` differs from the worker's computed bundle id (A9).
- **No test hooks in production:** a `selftest` op (spin CPU, allocate memory) exists only when the child is spawned with `EG_INSPECTOR_SELFTEST=1`, which config refuses when `NODE_ENV=production`; integration tests use it to prove the CPU and memory kills.

**Inspection in the child (`ContentResult`, pure functions over a Buffer, unit-tested):**

1. **True type** (A5) from magic bytes and structure, compared with the declared content type and the filename extension.
2. **Archive walk** (depth-first, entries processed one at a time, all in memory):
   - Supported: **zip** (`yauzl` `fromBuffer`, ≥ 3.2.1 as in 3.1, `validateEntrySizes: true`, `strictFileNames: false`, never `getLastModDate()`; streaming inflate per entry with an output counter), **gzip** (single and multi-member, `zlib.createGunzip` with an output counter; the ISIZE trailer is a hint only), **tar** (`tar-stream` extract over the buffer; ustar/pax/gnu; entries of type file only, others counted), and their compositions (`.tgz` = gzip → tar counts as two levels).
   - **Unsupported** (recorded, not inspected): 7z, rar, cab, bzip2, xz, iso/udf, OLE containers other than the type check → reason `archive.unsupported_format` (rule U1). ClamAV still scans them (clamd unpacks 7z, rar, cab, bzip2, xz natively within its own limits, A7), so malware in them is still found.
   - **Limits** (platform, `ATTACHMENT_*`; validated): `ATTACHMENT_ARCHIVE_MAX_DEPTH` (default 3; the attachment is depth 0, its entries depth 1), `ATTACHMENT_ARCHIVE_MAX_ENTRIES` (default 1000, summed over all levels), `ATTACHMENT_MAX_ENTRY_BYTES` (default 26 214 400), `ATTACHMENT_MAX_DECOMPRESSED_BYTES` (default 104 857 600, summed over all levels), `ATTACHMENT_MAX_COMPRESSION_RATIO` (default 100; per entry `uncompressed / max(compressed, 1)` and overall `decompressed / attachment size`, checked **while** inflating so a bomb stops at the first breach). On a breach the walk stops for that branch (or entirely for the total limits) and records `limit.archive_depth`, `limit.archive_entries`, `limit.entry_size`, `limit.decompressed_size`, `limit.compression_ratio`. Content past a limit is not inspected (it is still in ClamAV's scope with clamd's limits).
   - **Encrypted** zip entries (general-purpose bit 0, or strong encryption bit 6, or AES extra field 0x9901) → `archive.encrypted`, entry not inflated. **Malformed** (bad central directory, truncated local header, CRC mismatch, truncated gzip, bad tar checksum) → `archive.malformed`. **Path traversal / absolute names / overlapping entries** → `archive.path_traversal`, `archive.overlapping_entries` (reason codes; the names themselves are discarded).
   - Per entry: SHA-256, size, true type (A5), YARA, nested walk if an archive. Entries are identified by an **index path** (`"2/0/5"`), never by name. At most `ATTACHMENT_MAX_ENTRY_FINDINGS` (default 20) entry findings with a non-clean signal are kept in the result, plus counts.
   - **Byte accounting:** the walk holds at most one entry buffer per depth level; the child refuses (limit) before allocating beyond `ATTACHMENT_MAX_ENTRY_BYTES × (depth + 1)`.
3. **YARA** on the attachment bytes and on every inspected entry. Each rule carries `meta: severity = "high" | "medium" | "low"` (required; bundle validation refuses a rule without it) and `meta: id` (stable). Matches are reported as `{ rule, severity, scope: 'attachment' | '<index path>' }` (rule names only, never matched strings or offsets).
4. **Office macro marker:** OOXML with `vbaProject.bin`, OLE with a `VBA` storage, ODF with `Basic/` → reason `office.macros` (informational; ClamAV's `Heuristics.OLE2.ContainsMacros` decides the verdict, A6).

`ContentResult` (bounded, JSON-serializable, cached): `{ inspectorVersion, type: { detected, family, executable }, clamav: { status: 'clean' | 'found', signature: string | null, engineVersion, dbVersion }, yara: { bundleId, matches[] (≤ 32) }, archive: { format, supported, depthReached, entries, decompressedBytes, maxRatio, encrypted, malformed, findings[] (≤ 20), entryHashes: [{ path, sha256, type }] (≤ ATTACHMENT_ARCHIVE_MAX_ENTRIES) } | null, limits: string[], codes: string[] }`. The ClamAV part is filled by the worker (A7), the rest by the child.

### A5. True file type and type rules

- **Vocabulary** `FILE_TYPES` in `@email-gateway/security-contracts` (data, so the api validates tenant settings): ids such as `pdf`, `zip`, `gzip`, `tar`, `7z`, `rar`, `cab`, `bzip2`, `xz`, `ooxml_word`, `ooxml_excel`, `ooxml_powerpoint`, `ooxml_macro` (docm/xlsm/pptm), `odf`, `ole_office`, `msi`, `rtf`, `pe_executable`, `elf`, `macho`, `lnk`, `jar`, `apk`, `iso`, `vhd`, `chm`, `script_js`, `script_vbs`, `script_ps1`, `script_batch`, `script_shell`, `hta`, `html`, `svg`, `xml`, `text`, `png`, `jpeg`, `gif`, `bmp`, `webp`, `tiff`, `ics`, `eml`, `unknown`; each with `family` (`document`, `archive`, `executable`, `script`, `disk_image`, `image`, `markup`, `text`, `other`), `executable: boolean`, the extensions that legitimately carry it, and its MIME types.
- **Detection (child):** magic bytes and structure, most specific first (extending the reviewed 3.1 table in our own code, ADR-0022 decision 5): PE requires `MZ` + a valid `e_lfanew` pointing at `PE\0\0`; zip sub-typing by central-directory names (`[Content_Types].xml` + `word/`/`xl/`/`ppt/`, `vbaProject.bin` → `ooxml_macro`, `META-INF/MANIFEST.MF` → `jar`, `AndroidManifest.xml` → `apk`, `mimetype` = `application/vnd.oasis…` → `odf`); OLE sub-typing (`msi` by its CLSID); ISO by `CD001` at 0x8001; text-like files by a bounded UTF-8/ASCII check, then by the extension for script types (scripts have no magic). `unknown` when nothing matches.
- **Mismatch (reason code `type.mismatch`):** the detected type is known (≠ `unknown`, `text`) and the extension maps to a different type family, or the declared content type is specific (not `application/octet-stream`, `application/x-download`, `binary/octet-stream`) and maps to a different family. **`type.executable_disguised`**: detected `executable` family (PE, ELF, Mach-O, MSI, LNK) with a non-executable extension (e.g. `invoice.pdf` that is a PE). The 3.1 flags (`filename_double_extension`, `filename_executable_extension`, `filename_bidi_control`) are carried as reason codes `filename.double_extension`, `filename.executable_extension`, `filename.bidi_control` (informational).
- **Deny/allow rules** use both the **detected** type and the **extension-implied** type (a `.exe` name with junk content is still deny-listed; a PE named `.pdf` is caught by detection). Platform default deny list `ATTACHMENT_DENIED_TYPES` (default `pe_executable,msi,elf,macho,lnk,script_js,script_vbs,script_ps1,script_batch,hta,jar,apk,iso,vhd,chm`); archives are not denied by default. Applies to archive entries as well (`type.denied_in_archive`).

**Engine level:**

- **A0** no attachments and parse complete → engine outcome `skipped`, `attachment.none` (A1).
- **E1** a parse row that is not final (`parsing`, `parse_failed`), has no `attachment_count`, or records **any limit except `body_size`** (review round 1: `message_size`, `nesting_depth`, `part_count`, `header_count`, `header_line_length`, `header_block_size`, `attachment_count`, `attachment_size`, `decoded_ratio`, `total_decoded_size`, `parse_timeout`, and any limit added later; the structural stops end the parse, so later parts get no row) → the attachment list may be incomplete: engine verdict at least `suspicious`, `attachment.parse_incomplete` (applies even with zero rows, so A0 never fires on an incomplete parse).
- Otherwise: engine outcome = most severe attachment verdict (a message with only `clean` attachments is `clean`); reason codes = union of the attachment codes (ordered by the verdict that raised them, then name, ≤ 32); `signals` = one per non-clean finding (`clamav:<signature>`, `yara:<rule>`, `hash:<first 12 hex>`), score 0, options `["part <index>"]` (≤ 200 signals); `score`/`requiredScore`/`action` null; `engineVersion` = `clamav/<engine>/<db>;yara-x/<ver>/<bundle12>` (≤ 64 chars; A9); `settingsVersion` = `attachment-map/1;p=<12 hex>;t=<row version | none>` (4.1 S8 format); `mappingVersion` `attachment-map/1`.
- **Failures** (attempt failures, 4.1 S5 path, never a verdict): `unavailable` / `timeout` / `protocol_error` / `circuit_open` (clamd), `inspector_timeout`, `inspector_crash`, `part_unavailable` (not retryable), `part_integrity` (not retryable), `part_key_mismatch` (not retryable), `parse_row_missing` (not retryable). Final failure → the round ends `scan_failed` (`scan_error` / `scan_timeout`), never `clean`. `failureReasonCode` / `failureMetricReason` gain the new codes (`engine.part_unavailable`, …).

### A7. ClamAV: `@email-gateway/clamav` (new package) and clamd configuration

- **Client `ClamdClient`** (TCP only, no local socket, no `clamdscan` binary): `ping()`, `version()` → `{ engine: '1.4.6', dbVersion: 28173, dbTime: Date }` parsed from `ClamAV 1.4.6/28173/Tue Nov  3 06:27:52 2026`; `scan(buffer | Readable, signal)` using the **null-terminated** protocol in one `IDSESSION`: `zIDSESSION\0`, `zVERSION\0`, `zINSTREAM\0` + chunks `[uint32 BE length][bytes]` (chunk size `CLAMAV_CHUNK_BYTES`, default 65 536, ≤ clamd `StreamMaxLength`) + `[0,0,0,0]`, `zEND\0`. Replies are id-prefixed (`1: ClamAV …`, `2: stream: OK` / `2: stream: <sig> FOUND` / `2: INSTREAM size limit exceeded. ERROR` / `… ERROR`), so the version recorded for a scan is the version of the clamd instance that scanned it (several clamd pods behind one Service may differ during a database update). If IDSESSION proves unreliable with INSTREAM on clamd 1.4.6, fall back to a `VERSION` call on its own connection right before each scan and record the deviation.
  - Result `{ status: 'clean' } | { status: 'found', signature } ` plus `{ engine, dbVersion }`; errors are typed: `ClamdUnavailableError` (connect refused/reset, DNS), `ClamdTimeoutError` (per-call `CLAMAV_TIMEOUT_MS`, default 60 000 — covers a non-concurrent database reload), `ClamdProtocolError` (unparseable reply), `ClamdSizeLimitError` (`INSTREAM size limit exceeded` → mapped to `limit.clamav`, definite suspicious — configuration keeps `StreamMaxLength` above `ATTACHMENT_MAX_BYTES`, so it signals a misconfiguration and is also logged at warn).
  - **Bounded concurrency:** at most `CLAMAV_MAX_CONNECTIONS` in-flight connections per worker (semaphore; default 4, validated ≤ 64), back-pressured writes (respect `socket.write` return / `drain`), socket timeout, `AbortSignal` destroys the socket. Signature names are validated (`^[\x21-\x7e]{1,128}$`) before use.
  - Unit tests against a fake clamd (`net.Server`); integration tests against the real container with an **EICAR string generated at test time** (never committed).
- **Breaker:** the 4.1 per-engine `CircuitBreaker` wraps the engine call; clamd failures are `engineFault: true`; inspector failures are `engineFault: true` too (they are the engine's own); part/parse failures are `engineFault: false`.
- **`infrastructure/clamav/clamd.conf`** (memory-conservative for the 8 GB VM, never two clamd instances): `MaxThreads 4`, `MaxQueue 32`, `StreamMaxLength 30M` (> `ATTACHMENT_MAX_BYTES` 25 MiB), `MaxScanSize 150M`, `MaxFileSize 30M`, `MaxRecursion 10`, `MaxFiles 2000`, `AlertExceedsMax yes`, `AlertOLE2Macros yes`, `AlertEncrypted no` (the inspector reports encryption; clamd would otherwise turn every encrypted zip into a heuristic hit), **`HeuristicScanPrecedence no`** (with `yes`, a heuristic hit such as macros stops the scan before a real signature can match, turning malware into "suspicious"), `ConcurrentDatabaseReload no` kept (comment updated: production sizes clamd pods for concurrent reload, `docs/deployment/attachment-scanning.md`). Compose `clamav`: `mem_limit: 1536m` (measured RSS ~780 MiB; the implementer measures the peak during a `RELOAD` and records it; the cgroup limit confines a runaway clamd instead of letting the VM's OOM killer pick mysqld). Changing the file needs a clamav **restart** (no rebuild).

### A8. Settings: platform defaults with bounded tenant overrides (as 4.1 S8)

- **Platform** (env, read by the api and the email-worker): `ATTACHMENT_MAX_BYTES` (26 214 400; ≤ `MIME_MAX_ATTACHMENT_BYTES`; ≤ 30 MiB clamd `StreamMaxLength` documented), the archive limits of A4, `ATTACHMENT_DENIED_TYPES` (A5), `ATTACHMENT_DENIED_TYPE_VERDICT` / `ATTACHMENT_TYPE_MISMATCH_VERDICT` / `ATTACHMENT_ENCRYPTED_VERDICT` (each `suspicious` | `malicious`, default `suspicious`).

Archive/CPU/memory limits are platform-only (they decide the cached content result, A10, which must not depend on the tenant). `resolveAttachmentSettings(platform, override)` (pure) returns effective settings or violations; `attachmentSettingsBounds(platform)` for the API; `settingsVersion()` reused.

### A9. Versions: engine, signatures, rules bundle

- **ClamAV:** engine version and database version from the same IDSESSION as the scan (A7); `scan_engine_info{engine="attachment",version}` keeps the 4.1 gauge; new `scan_attachment_signature_info{component="clamav_db",version}` and `scan_attachment_clamav_db_age_seconds` (now − db time from VERSION).
- **YARA bundle:** `apps/email-worker/yara/` holds `rules/*.yar` and `bundle.json` `{ "name": "eg-platform", "version": <int>, "rules": [file names] }`. **Bundle id** = `yara-<version>-<first 12 hex of SHA-256 over (yara-x version, each file name, NUL, its bytes, NUL) in sorted order>`, computed by the worker at start (and by `pnpm --filter @email-gateway/email-worker yara:bundle --check`, run by the package test, which validates every rule compiles, has `meta: id` and `meta: severity`, and that `bundle.json` lists exactly the files). Shipped rules: test rules (`EG_Test_Marker_High` on the marker `EG-YARA-TEST-HIGH-5f0c2e7a`, `EG_Test_Marker_Medium` on `EG-YARA-TEST-MEDIUM-8d41b9c3`, both `meta: test = true`) and a small set of maintained heuristics with low false-positive risk: HTML smuggling (`msSaveOrOpenBlob`/`createObjectURL` + large base64 blob, medium), PowerShell encoded command (`-enc`/`-EncodedCommand` + base64, medium), LNK with a command interpreter target (medium), OOXML external template injection (`attachedTemplate` with an http(s) target, medium). The production rule feed is configuration (`ATTACHMENT_YARA_RULES_DIR` points at another bundle directory with the same layout); tenant-authored rules (`yara_rules`) are out of scope (§10).
- **Content version** (cache key, A10) = SHA-256 (first 16 hex) over `inspectorVersion` (`att-inspect/1`), ClamAV engine + db version, YARA-X version, bundle id and the canonical platform archive/CPU/memory limits.

### A10. Content cache (Redis)

- **What is cached:** the tenant-independent `ContentResult` of A4 (type, ClamAV, YARA, archive, limits), keyed by **`eg:scan:att:v2:<sha256>:<contentVersion>`**. Never cached: the known-hash catalog lookup (always queried), tenant rules (always applied), anything with tenant or message identifiers. Value: `<mac>.<json>`, ≤ 128 KiB (larger → not cached, counted).
- **Authenticated values (review round 1):** `mac` is the base64url HMAC-SHA256 under **`ATTACHMENT_CACHE_HMAC_KEY`** (secret, ≥ 32 characters, held by the attachment-consuming email-worker only: Compose sets it on `email-worker` alone, Kubernetes mounts it from its own Secret `email-gateway-attachment-cache-key` in `email-worker-attachment` only) over the key and the JSON. A read verifies the MAC in constant time and then the JSON against the strict `contentResultSchema`; a missing or wrong MAC, a value moved to another key or a value of another shape is **`rejected`** (`scan_attachment_cache_total{result="rejected"}`, a warning with the content version only): the attachment is scanned and the entry overwritten. Reason: the Redis credentials are shared by every Node service (incl. the internet-facing api), so without a MAC any client of that Redis could plant a "clean" result for a chosen malware hash. `v2` replaced the unauthenticated `v1` format; `v1` keys are never read and expire by their TTL. Rotating the key only causes misses.
- **TTL by content verdict** (the verdict the content alone implies before tenant rules): `ATTACHMENT_CACHE_CLEAN_TTL_SECONDS` (default 21 600 = 6 h; validated ≤ 86 400: a clean verdict is never cached indefinitely), `ATTACHMENT_CACHE_MALICIOUS_TTL_SECONDS` (default 604 800 = 7 days; ≤ 2 592 000), `ATTACHMENT_CACHE_OTHER_TTL_SECONDS` (suspicious/unknown, default 3 600; ≤ 86 400); inspector-kill results use the other TTL. `SET … EX … NX`-free plain `SET EX` (last writer wins; identical inputs give identical results).
- **Invalidation:** a new ClamAV database or YARA bundle changes the content version, so old keys are unreachable at once and expire by TTL. The worker learns the current ClamAV version from the version poll (A13, TTL `SCAN_ENGINE_VERSION_TTL_MS`) for the **lookup**; when the scan reports a different version than the one used for the lookup, the result is stored under the key of the version that actually scanned.
- **Failure:** Redis errors or timeouts (`ATTACHMENT_CACHE_TIMEOUT_MS`, default 200) bypass the cache (full scan), count `scan_attachment_cache_total{result="error"}`, and never fail the attempt or produce `clean`. `ATTACHMENT_CACHE_ENABLED` (default `true`).
- Redis: the shared app Redis (`REDIS_URL`, DB 0, prefix `eg:scan:att:`), via `RedisService` of `@email-gateway/common` (new email-worker config key `REDIS_URL`, required when the attachment engine runs with the cache enabled). Cross-tenant sharing of content results is intentional (a file's ClamAV/YARA result does not depend on who received it); the cache holds no tenant data, and only the worker reads it and can write a value that is accepted. Its hit/miss outcome is **never shown to tenants** (A16).

### A11. Sandbox submissions (contract for step 4.6)

- **Who is submitted:** every attachment whose final attachment verdict is `suspicious` or `unknown` (not `malicious`: already decided; not `clean`) and that has a stored part object (an attachment that was not stored, `attachment.not_scanned`, cannot be submitted), at most `ATTACHMENT_SANDBOX_MAX_PER_MESSAGE` (default 5, most severe first), when `ATTACHMENT_SANDBOX_SUBMIT=true` (default `true`; the queue is a bounded dormant buffer until 4.6).
- **How:** in the engine's finalize transaction (A12): one `sandbox_submissions` row per attachment (`status = pending`, unique `(scan_id, attachment_id, received_at)`) and one `mail.attachment.sandbox_requested.v1` outbox row (A2). A redelivery hits the unique key and writes nothing.
- **Never blocks the round:** the engine's verdict is final for the round; the sandbox result arrives later.
- **How 4.6 consumes it** (documented contract, not implemented): `scan.sandbox` becomes a work queue (topology v5) consumed by the sandbox orchestrator (ledger consumer `sandbox-orchestrator.submissions`), which (1) deduplicates by `sha256` (+ its own engine version) across tenants, (2) reads the part through a read-only grant on `org/*/part/` keys named in the event (key prefix checked against `organizationId` of the envelope), (3) moves `sandbox_submissions.status` `pending → submitted → completed | failed | expired` (columns `external_ref`, `sandbox_verdict`, `completed_at` reserved in this step's table), and (4) on a definite sandbox verdict emits `mail.attachment.sandbox_completed.v1` (to be defined in 4.6) that policy/retro (5.x) consumes; a malicious sandbox verdict may also add the hash to `malware_signatures` (source `sandbox`). Pending rows older than `SANDBOX_SUBMISSION_TTL` become `expired` (4.6).

### A13. Signature updates: detector and rescans

- **Detector (`SignatureWatcher`, email-worker scan role, when the attachment engine is enabled):** leader via `AdvisoryLocks` (`scan:attachment-signatures`), every `ATTACHMENT_SIGNATURE_POLL_MS` (default 300 000): clamd `VERSION`, and the worker's own YARA bundle id. Upsert `scan_signature_versions (engine 'attachment', component 'clamav_db' | 'clamav_engine' | 'yara_bundle', version, first_seen_at, last_seen_at)`. A **new** version of a component that had a previous version is a **change**: log (versions only), `scan_attachment_signature_changes_total{component}`, and, depending on `ATTACHMENT_SIGNATURE_RESCAN` (`off` | `record` | `rescan`, default `record`): `record` writes an `attachment_rescan_jobs` row with `status = 'skipped'` (an audit trail of the change, no rescans); `rescan` writes it `pending` (dedupe key `sig:<component>:<version>`, unique, so the fleet creates one job per change). The new version row and its job are written in **one writer transaction** (review round 1, `SCAN_DB_TIMEOUT_MS`): a failed job insert rolls the version row back, so the next poll detects the change again and a change is never recorded without its job.
- **Admin API (api):** `POST /api/v1/platform/attachment-rescans` (new permission `platform:scan_rescan`, `@UserOnly`, `@RequireMfa`, rate limit 10/min per caller) body `{ windowHours: 1..168, states?: subset of ['scanned','scan_failed','quarantined','held_for_review'], organizationId?: public id, maxMessages?: 1..ATTACHMENT_RESCAN_MAX_MESSAGES, reason: 1..512, dryRun?: boolean }` → `202 { jobId, status, estimatedMessages }` (dry run: `200` with the count only, nothing written); `GET /api/v1/platform/attachment-rescans` (cursor pagination, newest first) and `GET …/{jobId}`; `POST …/{jobId}/cancel`. Audited (`attachment_rescan.requested` / `.cancelled`, actor, parameters, never content). The api only writes the job row; the worker executes.
- **Executor (`RescanJobRunner`, email-worker scan role):** leader lock `scan:attachment-rescans`; picks the oldest `pending` job, moves it to `running`; every `ATTACHMENT_RESCAN_INTERVAL_MS` (default 10 000) selects up to `ATTACHMENT_RESCAN_BATCH_SIZE` (default 50) candidates **on the writer**: messages with `received_at` in `[job.window_start, job.window_end]`, `status` in the job's states (default `scanned, scan_failed, quarantined, held_for_review`; never `scanning`, delivery or terminal states), optionally one organization, with at least one `email_attachments` row, whose **latest round's** attachment final outcome is not `malicious` (a `scan_failed` round always qualifies), ordered by `(received_at, id)` after the job's cursor. Per candidate, one writer transaction: `transitionMessage` **E19** (role **`scanner`**, reason **`signature_rescan`**, `transitionKey: 'sigrescan:<jobId>:<messageId>'`, `expectedFrom` the candidate's state, `newRound`) + the `mail.message.rescan_requested.v1` outbox row (built as the api's rescan does, in the email-worker, validated by `messageRescanRequestedV1` of `@email-gateway/event-contracts` in a contract test; the api code is not moved in this step) + the `email_events` row the lifecycle writes. Stale/invalid transitions are counted as skipped. The cursor, counts and `status` (`completed` when no candidate is left or `max_messages` is reached; `cancelled` by the API) are updated per batch. Rate: at most `ATTACHMENT_RESCAN_BATCH_SIZE` per interval (≤ 300/min by default) across the fleet; `ATTACHMENT_RESCAN_MAX_MESSAGES` (default 5 000, max 50 000) per job; `ATTACHMENT_RESCAN_WINDOW_HOURS` (default 24, max 168) for detector jobs.
- The rescan goes through the **existing rescan path**: new round, `rescan_requested.v1` on every engine queue (Rspamd scans again too; this is the documented cost of one consistent round model), cache misses on the new versions.
- Lifecycle (WP1): **E19** `roles: ['operator', 'scanner']`, `reasons: ['admin_rescan', 'signature_rescan']` (role/reason pairs validated: `scanner` only with `signature_rescan`), ADR-0025 amended by ADR-0028.

### A14. Resilience

- Timeouts: clamd per call (A7), inspector wall/CPU/RSS (A4), YARA per buffer (A4), S3 waits `SCAN_S3_TIMEOUT_MS`, Redis `ATTACHMENT_CACHE_TIMEOUT_MS`, engine call `SCAN_ATTACHMENT_TIMEOUT_MS`, writer transactions `SCAN_DB_TIMEOUT_MS`.
- Breaker per engine (4.1), bounded concurrency at four levels: messages (`SCAN_ATTACHMENT_CONCURRENCY` = prefetch), attachments per message (`ATTACHMENT_PER_MESSAGE_PARALLELISM`), bytes in memory (`ATTACHMENT_MEMORY_BUDGET_BYTES`, default 134 217 728), clamd connections (`CLAMAV_MAX_CONNECTIONS`) and inspector children (`ATTACHMENT_INSPECTOR_POOL_SIZE`).
- Hold-and-retry through the 3.2 `hold` retries (`SCAN_RETRY_BASE_MS`/`MAX_MS`), attempts as non-final rows until `SCAN_ATTACHMENT_MAX_ATTEMPTS` or the round deadline, then a final `timeout`/`error`; the deadline sweeper finalizes stuck rounds. With defaults a message survives a clamd outage of about two minutes; longer → `scan_failed` → operator rescan (runbook) or a rescan job.
- `processOnce` per (message, round, engine) and the child-row unique keys (§2.0-4).

### A15. Development pass-through and `malicious`

`DevPassThroughApprover` (delivery-worker, local/ci only): `outcome = scanned` with **`verdict = malicious` is not approved**: ledger row, `delivery_approvals_skipped_total{reason="malicious_verdict"}`, info log (ids, verdict). The message stays `scanned` until policy (5.2) or the `scanned` lifecycle deadline (`LIFECYCLE_DEADLINE_SCANNED_HOURS`, then `expired`); it is never delivered by the pass-through. Every other verdict (`clean`, `spam`, `suspicious`, `unknown`) is approved as in 4.1. Rationale: quarantine is a policy action (5.3, edge roles `policy`/`quarantine`); the pass-through must not invent one, but it must not deliver malware either. `DEV_PASSTHROUGH_WARNING` is updated ("mail is delivered after scanning without policy; malicious verdicts are held in `scanned`").

## 6. Carry-over defect: delivery-worker wrong reads after a writer pause

### 6.1 What is known

4.1 §13.5: after `docker compose pause mysql` (20 s), delivery-worker interactive transactions expired client-side while their statements were in flight; right after the unpause, **plain queries on the same pool read results that belonged to other queries** (an existing message "not found"; a `findMany` received the next query's rows; a wrong approval time). The only interactive transactions in the reinjection path that run with Prisma's defaults (5 s timeout, 2 s maxWait) are in `ReinjectionStore` (`claim` and the terminal commits) and the reinjector's own `$transaction` calls; the writer URL has no `socket_timeout`. Working hypothesis **H1**: when the query engine expires an interactive transaction (or a `pool_timeout`/cancellation drops a request) while a statement is awaiting the server's reply, the connection goes back to the pool with that reply still unread; the next request on that connection reads it (an off-by-one result stream). H2 (to exclude): our code shares a transaction client after its callback returned (an un-awaited `tx.*` call), which would also produce interleaving.

### 6.2 Required work (WP4)

1. **Deterministic reproduction first** (`apps/delivery-worker/integration/writer-stall.test.ts`, also usable as a regression test): a test-only TCP proxy (Node `net`, in the test support folder) between a `PrismaClient` (writer URL rewritten to the proxy, `connection_limit=1` and `=2`) and MySQL that can **freeze** both directions while keeping the sockets open (what `docker pause` does). Sequence: an interactive transaction with `timeout: 1000` runs a statement → freeze 3 s → the transaction expires → unfreeze → a sequence of distinct queries (`SELECT ? AS n` with distinct values, then `ReinjectionStore.context()` / `approvalTime()` on fixture rows) must each return their own result. Record whether H1 reproduces (expected: yes, on 6.16.x) and the exact Prisma/engine versions. Also grep for H2 patterns (un-awaited `tx.` calls, transactions passed to fire-and-forget work).
2. **Root-cause fix in production code**, in this order of preference, each verified with the reproduction:
   - **F1** upgrade `prisma` / `@prisma/client` to the newest 6.x patch/minor if its changelog or the reproduction shows the engine fixed (root `package.json`/`packages/database/package.json`, lockfile; `pnpm db:generate`, full gate).
   - **F2** (also if F1 fixes it, as defence in depth): never let the client abandon an in-flight statement on a reused connection: add `socket_timeout` to the writer and replica URLs of every service through the shared client construction (`PrismaService` / the URL helper in `@email-gateway/database`; new env `DATABASE_SOCKET_TIMEOUT_SECONDS`, default 30) so a stalled statement fails on its socket and that connection is **closed**, and make every data-plane interactive transaction use `withTransactionDefaults` with `timeout > socket_timeout` (delivery-worker `ReinjectionStore`, reinjector, planner, applier; grep the other services and list what changed). Verify with the proxy that the closed connection is not reused.
   - **F3** only if F1+F2 do not remove the wrong read under the reproduction: the `@prisma/adapter-mariadb` driver adapter for the writer client (a platform change; record measurements and the decision).
3. **Defensive changes in the delivery-worker** (they do not replace the fix): `ReinjectionStore.context()` and `approvalTime()` select the identifying columns and verify them (message id/org/received_at echo, every delivery's `reinjection_id` equals the row, every recipient id was requested, approval row's `approval_event_id` and `message_id` match); a mismatch throws `InconsistentReadError` (transient: the row is rescheduled with the attempt refunded, metric `delivery_inconsistent_reads_total`). "Message of the reinjection not found" becomes **retryable** (reschedule with backoff, error class `context_missing`) up to `DELIVERY_REINJECT_MAX_ATTEMPTS`; only the final attempt fails the row **and terminal-fails its active deliveries in the same transaction** (status `failed`, reason `message_missing`, through the shared recorder), so no delivery is left `pending` without a recovery path.
4. Tests: the reproduction above fails before the fix (record the failing output in §12) and passes after; unit tests for the echo checks and the retry rule; `tests/integration/messaging-db-outage.test.ts` passes **5 runs in a row** (WP5 records them).

## 7. Alternatives considered

- **Two engines (`clamav`, `yara`) on one queue / two queues:** rejected (A1): double S3 reads and archive walks, a second queue the brief does not have, one per-attachment verdict split in two.
- **A separate `attachment-scanner` deployable / broker user:** rejected for now (A1): same image and bounded context; `SCAN_CONSUMERS` gives independent scaling; a second user would carry the same grants.
- **YARA runtimes:** yara 4.x CLI per file (temp files, system package, spawn per file), the unmaintained `yara` npm binding, YARA-X in `worker_threads` (no native memory bound, a native fault kills the worker), a YARA sidecar container (one more service and network hop on an 8 GB VM). Chosen: YARA-X binding in a resource-limited child process (A4).
- **Extracting archives to a temp directory and scanning files with `clamdscan`/`MULTISCAN`:** rejected: disk writes of hostile content, path handling risks, needs a shared volume with clamd. Chosen: INSTREAM of the outer attachment (clamd unpacks internally) plus in-memory inspection with our limits.
- **Re-parsing the EML to find attachments:** rejected by the brief and ADR-0022 (the parse rows and part objects are authoritative).
- **Caching the final (tenant-specific) verdict:** rejected: tenant rules and the hash catalog must apply immediately; only the tenant-independent content result is cached.
- **A new known-hash table:** rejected in favour of evolving the unused `malware_signatures` (A17), recorded as a deviation from the directive.
- **Treating CPU/memory kills as `timeout`/`error`:** rejected: a file that deterministically exhausts CPU or memory would be retried six times and end `scan_failed`; a load-independent limit breach is a property of the file (S3). Wall-clock timeouts stay failures because they depend on load.
- **`unknown` vs `suspicious` for unsupported archives:** `unknown` (U1): we could not inspect, ClamAV did; policy decides, and the file goes to the sandbox.
- **Automatic rescans on every signature update by default:** rejected as the default (`record`); daily ClamAV updates would rescan every recent message repeatedly; operators switch to `rescan` or use the admin API with a bounded window.
- **Dev pass-through quarantining `malicious`:** rejected (A15): quarantine is a policy action; the pass-through holds instead.

## 8. Risks and mitigations

| Risk                                                                    | Mitigation                                                                                                                                            |
| ----------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| clamd OOM on the 8 GB VM (it happened before)                           | `MaxThreads 4`, `ConcurrentDatabaseReload no`, `mem_limit 1536m`, one clamd only, images built one at a time, never analytics/observability with apps |
| YARA-X binding defect or supply-chain risk                              | exact pin ≥ 14 days old, child-process isolation, bundle verification, documented CLI fallback                                                        |
| Memory blow-up from concurrent large attachments                        | byte budget semaphore, per-message parallelism, child RSS watchdog, V8 heap cap                                                                       |
| `RLIMIT_CPU` unavailable on the macOS host                              | CPU sampling by the worker is the primary control; `best_effort` refused in production; CPU-kill tests run where `prlimit`/`/proc` exist (container)  |
| IDSESSION/INSTREAM behaviour differs                                    | fallback to VERSION-then-INSTREAM, recorded                                                                                                           |
| Stale clean verdicts after new signatures                               | key includes the db version; clean TTL ≤ 24 h; rescan jobs                                                                                            |
| Rescan jobs overload (every engine rescans)                             | default `record`, batch/interval/max limits, bounded window, leader lock, cancel route                                                                |
| False positives from type rules (`application/octet-stream` everywhere) | generic declared types ignored for mismatch; tenant can only tighten; reason codes explain                                                            |
| Existing 4.1 suites assume `required_engines = ['rspamd']`              | WP3/WP5 update them; clamd is part of the default Compose profile                                                                                     |
| Prisma upgrade side effects (F1)                                        | full gate + every stack suite; F2 alone if the upgrade is not safe                                                                                    |
| Sandbox events pile up on a dormant queue                               | drop-head bounded buffer, `ATTACHMENT_SANDBOX_MAX_PER_MESSAGE`, info alert                                                                            |

**Root cause (H1, confirmed).** The Prisma 6.19.3 library engine (quaint/mysql_async) returns a pooled connection to the pool while a reply is still unread whenever the client abandons a statement in flight: when an interactive transaction expires (`timeout`) and when `socket_timeout` fires. The connection is neither closed nor drained; the next request on it reads the stale reply, so every later result on that connection is shifted by one (wrong rows, "Inconsistent column data", empty results for existing rows, panics). In the 4.1 runs, the 20 s `docker compose pause mysql` exceeded the reinjector's transaction budgets (claim: Prisma default 5 s; result commits 15 s), the transactions expired with statements in flight, and the reinjector's next reads on those connections returned other queries' results ("message of the reinjection not found", a wrong approval time, `emailDelivery.findMany` receiving `emailRecipient.findMany`'s rows). The same trigger exists without a pause: a row-lock wait longer than a transaction budget (`innodb_lock_wait_timeout` is 50 s, the old budgets 5–15 s).

**H2 (excluded).** Code review of `apps/delivery-worker/src`: no `tx.*` call without `await`/`return` (grep), no transaction client stored or passed to fire-and-forget work, no `Promise.all` over a transaction client (the only `Promise.all` waits on scheduler sessions), and `@typescript-eslint/no-floating-promises` is an error in `eslint.config.mjs` (type-aware, covers `src`). The proxy reproduces the wrong reads with plain Prisma calls and no application code, so H1 alone explains them.

**F1 (not applicable).** 6.19.3 is the newest 6.x (npm `prisma@6`: 6.19.1, 6.19.2, 6.19.3) and is what the lockfile already installs; the reproduction shows the defect on it. 7.x is a new major (Rust-free client, driver adapters by default), i.e. the F3 class of change. **No dependency change made.**

**F3 measured (not applied: a platform decision).** In a throwaway install outside the repository (`@prisma/adapter-mariadb@6.19.3` + `mariadb@3.4.5`, the generated 6.19.3 client of this repository, no schema change and no preview flag needed), scenario 3 through the same proxy: **every probe returned its own result** for `connectionLimit` 1 and 2; with the adapter's `socketTimeout: 1500` the stalled connection **was closed by the client and replaced** (proxy: opened 2 → 5, client-closed 1 → 3) and every probe was correct. So the driver adapter removes the wrong read and makes a socket timeout safe. Adopting it adds two runtime dependencies (`@prisma/adapter-mariadb`, `mariadb`) and changes how every service constructs its clients (`new PrismaClient({ adapter })`, pool options instead of URL parameters), which this package was not allowed to do. **Recommended to WP5/the platform owner as the definitive fix**; the reproduction's engine sections flip when it lands.

- **Deviation: `DATABASE_SOCKET_TIMEOUT_SECONDS` defaults to `0` (no socket timeout), not 30.** §6.2 assumed a socket timeout closes the stalled connection; attempts 4 and 5 show the 6.19.3 engine does not, so a 30 s socket timeout would add a wrong-read trigger for every statement waiting longer than 30 s (including lock waits up to 50 s). - **Every delivery-worker interactive transaction runs with one budget, `DELIVERY_DB_TX_TIMEOUT_MS` (new, default 120 000, 60 000–900 000)**, longer than `innodb_lock_wait_timeout` and the stalls the worker rides through, and validated to exceed `DATABASE_SOCKET_TIMEOUT_SECONDS` when that is set: `ReinjectionStore.claim` (was Prisma's 5 s default) gets explicit `{ timeout, maxWait }`, the reinjector's result commits and split, the recorder contexts, the planner, the dev pass-through, the reconciler and the status applier use the configured budget (was 15 s / 60 s), and `DeliveryModule` passes the writer through `withTransactionDefaults` to the store, reinjector, rate limiter and reconciler. `PLANNING_TX_TIMEOUT_MS` / `RECORDER_TX_TIMEOUT_MS` stay exported as the default (tests).
- **Which fix removed the wrong read:** this F2 variant. With a 120 s budget and no socket timeout the client never abandons a statement during a writer stall or lock wait shorter than the budget (attempt 6); the delivery-worker regression (attempt 8) is green after the change. It does **not** remove the engine defect: a stall longer than the budget still poisons a connection (the engine sections of the reproduction stay red, pinned with `it.fails`). The defensive checks below then keep wrong reads from becoming wrong decisions in the reinjector.

**Defensive changes (§6.2 item 3).** `ReinjectionStore.context()`, the new `activeDeliveries()` and `approvalTime()` select and verify the identifying columns (message id, organization and `received_at` echo; each delivery's `reinjection_id`, message, organization, `received_at` and an active status; each recipient requested, of the message, and every delivery's recipient returned; the approval row's `approval_event_id`, message, `received_at`, present — the claimed row itself always matches — and not newer than the row). A mismatch throws `InconsistentReadError(read, check)` (message without row content) → the reinjector reschedules the row with backoff and the attempt **refunded** (`error_class = inconsistent_read`, `delivery_inconsistent_reads_total{read}`). "Message of the reinjection not found" is **retryable**: rescheduled with backoff (`context_missing`, `delivery_reinjection_context_missing_total{result="retry"}`) until the new `DELIVERY_REINJECT_MAX_ATTEMPTS` (default 10); the final attempt fails the row **and** its active deliveries in one transaction (`failed`, reason `message_missing`, error class `other`, through the shared recorder; deliveries the recorder reports `unmatched` because their message row is gone are failed directly by `ReinjectionStore.failOrphanedDeliveries` in the same transaction), so no delivery is left `pending`. #### 13.2.3 Residual risks accepted in this round

- The attachment engine's round still has second-granular timestamps and the round's own `completedAt`; a tenant could in principle infer a cache hit from coarse timing when the attachment engine finishes last. Noisy (queueing, Rspamd runs in parallel) and far weaker than the removed fields.
- A wrong **empty** known-hash result cannot be detected by an echo check (nothing to echo); the catalog is only one input (ClamAV and YARA still run), and the parse/attachment reads of the same attempt are checked.
- `inconsistent_read` consumes an attempt of the budget (the delivery-worker refunds its attempt); repeated wrong reads end in `scan_failed`, never `clean`.
