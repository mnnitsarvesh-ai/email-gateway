### 1.2 Data volumes and the cost model

The target is 1M messages per day per large tenant (README). `email_messages`, `email_recipients`, `email_deliveries`, `email_headers` and `audit_logs` are partitioned monthly by `received_at` / `created_at` (ADR-0014); a 24 h window prunes to one or two partitions but a partition holds about 30M messages. The 6.1 scan budget examines 5 000 index entries per request: a filter that matches 1 % of mail fills a 50-row page per request, but an **identifier** search (a sender sending ten messages a day matches 0.001 %) needs about 200 requests per day of range, and a Message-ID lookup over 31 days about 6 200 requests. The explorer is unusable for the brief's searches without indexes; 7.2 adds them.

## 2. Decisions

### E1. Message search: driver indexes on generated search keys (ADR-0061, supersedes ADR-0051 decision 8)

- **Search keys** are MySQL **VIRTUAL generated columns** (INSTANT, no table rebuild on the partitioned tables) with secondary indexes (online `INPLACE, LOCK=NONE`), proven on a throwaway partitioned table on this machine's MySQL 8.4.13 (2026-11-14): REGEXP_REPLACE in a virtual column, indexed, equality served as a reverse covering range scan without a sort. Keys (exact SQL in §3.1):
  - `email_messages.subject_key` = the subject with leading reply/forward markers (`re`, `fw`, `fwd`, `aw`, `wg`, `sv`, `vs`, `antw`, `tr`, `rif`, `enc`, `odp`, optional `[n]`, then `:`; repeated) removed, whitespace runs collapsed to one space, trimmed, first 128 code points. Case and accents are ignored by the column collation `utf8mb4_unicode_ci`.
  - `email_messages.sender_domain` = the part of `envelope_from` after the last `@` (NULL for the null sender).
  - `email_messages.message_id_key` = `internet_message_id` trimmed, leading `<` and trailing `>` removed, first 255 characters.
  - `email_recipients.address_domain` = the part of `address` after the last `@`.
  - Plus plain indexes on `email_messages.envelope_from`, `email_messages.header_from`, `email_deliveries (organization_id, status, received_at, message_id)`, `quarantine_messages (organization_id, status, message_received_at, message_id)`.
- **The TypeScript normalizers** (`apps/api/src/modules/messages/domain/search-keys.ts`) mirror each SQL expression exactly (explicit Unicode `White_Space` class, not `\s`) and are applied to the input value; an integration test inserts a corpus (Re:/Fwd:/AW:/[3]:, tabs, non-ASCII, 200-character subjects, brackets) and asserts `normalizer(x) === subject_key` read back from MySQL.
- **Driver selection.** The plan is a pure function of which filters are present. The **driver** is the first present filter in this priority (most selective first): `internetMessageId` > `sender` > `headerFrom` > `recipient` > `subject` > `senderDomain` > `recipientDomain` > `subjectPrefix` > `quarantineStatus` > `deliveryStatus` > `verdict` (exactly one value) > none. Every other present filter is a **residual**.
  - **No residual:** the driver is read in its index order (keyset `received_at, id` DESC/ASC) with `LIMIT limit+1`: exact pages, no budget (the 6.1 index and verdict plans are the "none" and "verdict" drivers).
  - **Residuals present:** the 6.1 two-step budget (D6) runs **over the driver's index**: step 1 = the key of the `API_LIST_SCAN_BUDGET_ROWS`-th driver entry after the cursor (index-only); step 2 = the rows between the cursor and that boundary that pass every residual, `LIMIT limit+1`. A request never examines more than the budget, and a selective driver makes the budget cover far more time than the org-wide scan did. With no driver at all (only residual filters) the driver is `(organization_id, received_at, id)` (the 6.1 scan plan, unchanged).
  - **Foreign drivers** (`recipientDomain`, `deliveryStatus`, `quarantineStatus`) read `(received_at, message_id)` keys from their table, `GROUP BY received_at, message_id` (streams in index order: one row per message, so a message never appears on two pages), then the messages by primary key (`messagesByKeys`). With residuals, step 2 joins the grouped keys of the budget window to `email_messages` and applies the residuals (a sort over at most the budget). The `recipient` driver keeps its 6.1 keys `(received_at, recipient row id)` and its per-page collapse.
  - **Residual predicates** are fixed SQL fragments on `email_messages` columns (`direction`, `status`, `final_verdict`, `final_action`, `domain_id`, `envelope_from`, `header_from`, `message_id_key`, `subject_key =`, `subject_key LIKE`, `sender_domain`, `risk_score`, `attachment_count`) or `EXISTS` sub-queries on the foreign tables correlated by `(message_id, received_at)` (`email_recipients` unique key, `email_deliveries (message_id, received_at)`, `quarantine_messages (message_id, …)` unique key). Values are bound; identifiers are code constants (6.1 D4).
- **The capped subject-prefix driver.** A prefix is a range, not an equality, so its matches are not in time order. Step 1 is a probe `SELECT received_at, id … FORCE INDEX (subject key idx) WHERE organization_id = ? AND subject_key LIKE ? ESCAPE '!' AND received_at range AND after-cursor LIMIT cap+1` (no ORDER BY, index-only); more than `API_MESSAGES_SEARCH_MAX_MATCHES` (default 5 000) rows → `422 message_search_too_broad` ("more than N messages in this range start with that subject; type more of it, use the exact subject or narrow the range"); otherwise step 2 runs the same predicate plus residuals `ORDER BY received_at DESC, id DESC LIMIT limit+1` (a sort over at most the cap). Both statements carry `/*+ MAX_EXECUTION_TIME(API_MESSAGES_SEARCH_TIMEOUT_MS) */`; a timeout is `503 message_search_timeout` (index entries of the pruned partitions outside the window are filtered by index condition pushdown and are bounded by the partition, not by the cap: the timeout is the backstop). Minimum normalized prefix length 3, maximum 128. `%`, `_` and `!` in the input are escaped. **No LIKE ever runs without an index locating the rows**: as a driver it ranges over the subject-key index; as a residual it runs over at most the budget rows of another driver.
- **Cursor binding.** The cursor's filter hash now also covers the driver name, so a cursor is bound to its plan; a deploy that changes plan selection invalidates outstanding message cursors once (`400 cursor_invalid`, clients restart the list; `API_CURSOR_TTL_SECONDS` bounds the window). Key types per driver: `(received_at, id)` for every driver except `recipient` (`(received_at, recipient id)`, unchanged).
- **Audit of searches** (6.1 D11): `subject` and `subjectPrefix` join the identifying filters (`message.searched`, first page only, SHA-256 of the normalized value). Domain and status filters are not identifying and are not audited.
- **Every driver is EXPLAIN-checked** at volume (§9): chosen key, pruned partitions, no filesort for exact drivers without residuals, handler reads ≤ limit + 2 (exact) or ≤ budget + 2 per statement (budgeted), the prefix driver's refusal above the cap.

### E2. New and changed filters of `GET /messages`

- New: `subject` (string 1–998, normalized, matched on the 128-character key), `subjectPrefix` (string, normalized length 3–128), `senderDomain` and `recipientDomain` (new list-query filter type `domain`: trimmed, lower-cased, a leading `@` removed, `^[a-z0-9](?:[a-z0-9-]{0,61}[a-z0-9])?(?:\.[a-z0-9](?:[a-z0-9-]{0,61}[a-z0-9])?)+$`, ≤ 253; IDNs in A-label form), `deliveryStatus` (one value), `quarantineStatus` (one value).
- Changed: `internetMessageId` is matched on `message_id_key` (angle brackets optional, first 255 characters); `sender`, `headerFrom`, `recipient` unchanged in meaning, now index-driven.
- **Filter-level permissions** (checked in the service before any read, `403 message_filter_forbidden` naming the permission, documented in OpenAPI): `subject`/`subjectPrefix` need `message:reveal` (a subject search is a content oracle; ADR-0062), and so does the exact `recipient` (added by the closer, §13: it confirms a recipient address that every read masks; `recipientDomain` stays open), `deliveryStatus` needs `delivery:read`, `quarantineStatus` needs `quarantine:read`. A custom role with `message:read` alone cannot probe content or delivery/quarantine state through the list.

### E3. Audit history: a resource plan for `GET /audit/logs`

- When `resourceType` and `resourceId` are both present, the audit search (tenant and platform routes) reads the new index `audit_logs_org_resource_created_idx (organization_id, resource_type, resource_id, created_at, id)` in keyset order (`created_at, id`); other audit filters are residuals under the same budget rule as E1. The platform route's `scope=platform` (`organization_id IS NULL`) uses the same index. Range rules (`API_AUDIT_MAX_RANGE_DAYS` 90) are unchanged.
- The details page reads two resource types (`message` and `dlp_evidence`, whose rows carry the message public id since 4.5) and the quarantine entry histories (`quarantine_actions`); it never merges paginated streams (three groups, each with its own cursor).

### E4. Saved views: server-side, per user, tenant-scoped (ADR-0061)

- They **can** be stored server-side, so they are built (the directive's condition). Table `saved_views` (§3.1): `public_id`, `organization_id` (the scope), `user_id` (the caller), `kind` (`message_explorer` only), `name` (1–80, unique per organization, user and kind; case-insensitive by collation), `definition` (JSON, ≤ 8 KiB), `row_version`.
- Routes (`saved-views` tag, §3.3): list (v1 cursor, newest first), create, get, update (`PUT`, `expectedRowVersion`), delete. `@RequirePermissions('message:read')` (the only kind); **user principals that are members of the scope only** (API keys `403` through the existing `@CurrentUser()` rule; a platform override session `403 saved_views_member_only`, the notifications-preferences precedent); another user's or tenant's view is `404 saved_view_not_found`. At most `SAVED_VIEWS_MAX_PER_USER` (default 50) per user and kind (`409 saved_view_limit_reached`); duplicate name `409 saved_view_name_taken`; stale version `409 saved_view_conflict`. Audited `saved_view.created|updated|deleted` (view public id and kind only: names and filters may hold addresses).
- **Definition** (strict, §3.3): `{ version: 1, filters: { <GET /messages query parameter>: string }, sort, range: { kind: 'relative', preset } | { kind: 'absolute', from, to }, columns: string[] | null }`. The server validates `filters` + `sort` by parsing them with the real `MessageListQuerySchema` (unknown parameter or bad value → `400 validation_failed` with paths under `definition.filters`) and applies the filter-level permissions of E2 at save time. Saved values are the user's own data at rest (they may include an address or a subject searched by that user); they are never logged or audited in clear.
- Column sets: the DataTable's per-viewer column visibility (localStorage, 7.1 P2) plus `columns` of a saved view (applied when the view is applied).

### E5. Sensitive message metadata: masked by default, revealed only by an explicit, audited action (ADR-0062)

- **One new tenant permission `message:reveal`** — "Reveal masked message metadata (subjects, recipient addresses, To/Cc/Subject header values) through the audited reveal action (step 7.2)". Granted to `organization_admin` (through `TENANT_PERMISSIONS`), `security_analyst`, `compliance_auditor`; `super_admin` holds it through `ALL_PERMISSIONS`. **Not** granted to `platform_admin` ("no content access"), `domain_admin`, `quarantine_reviewer` ("no content access"), `read_only_user`, `mailbox_user`. Not in `TENANT_READ_PERMISSIONS`. Catalog 59 → **60**. API keys may hold it as a scope (no escalation: only a creator holding it can grant it).
- **On the message surface the API never returns these values in clear from a read**, whatever the caller's permissions: subject withheld (`subject: null`, `subjectMasked: true` when a subject exists); recipient addresses masked `f***@example.com` with `addressMasked: true` / `recipientMasked: true`; the matched user id withheld (`userId: null`); header values of `To`, `Cc`, `Subject` withheld (`value: null`, `masked: true`). Masks are applied in the service layer (pure functions of `domain/sensitive-masking.ts`), so they hold for API keys, the portal and every future client.
- **Clear values only through the reveal operations** (§2 E6), which require `message:reveal`, are explicit `POST` actions (CSRF in the portal, never prefetched or cached), are rate limited and write the audit row before the response is sent (an audit failure returns no value).
- Rationale for "masked for everyone, revealed per action" instead of "clear for privileged roles": the brief requires reveal **only** through an explicit, audited action; DLP (ADR-0038) already masks for evidence readers and opens values through one audited door; every clear view is attributable. The explorer keeps triage practical with a per-page subject reveal (E10).
- **DLP matches** are unchanged (ADR-0038): masked samples only with `dlp:read`, decrypted evidence only through `GET /messages/{id}/scans/{scanId}/dlp-evidence` (`dlp:evidence_read`, MFA user session, audited before decryption).

### E6. The reveal operations

- `POST /messages/reveal` (`MessageRevealController_revealMany_v1`): body `{ messageIds: uuid[1..100], unique }` → `{ revealedAt, data: [{ id, subject }] }` in request order for the ids found in the scope (missing and foreign ids are omitted; a foreign id looks exactly like a missing one). One audit row **per revealed message** (`message.revealed`, resource `message`/`<id>`, metadata `{ fields: ['subject'], bulk: true }`), written in one transaction before the response.
- `POST /messages/{messageId}/reveal` (`MessageRevealController_reveal_v1`): body `{ fields: ('subject'|'headers'|'recipients')[1..3], unique; recipientsCursor?: string (only with 'recipients'); recipientsLimit?: 1..100 (default 100) }` → `{ messageId, revealedAt, subject?, headers?: [{ seq, name, value }] (the stored rows of To, Cc, Subject), recipients?: { data: [{ rcptSeq, address, userId }], nextCursor } }`; `recipientsCursor` is a v1 cursor (resource `message_recipients_reveal`, bound to the message and organization). One audit row `message.revealed` (resource `message`/`<id>`, metadata `{ fields, headerCount, recipients: { count, firstRcptSeq, lastRcptSeq } | null }`, never values). `404 message_not_found` for missing and foreign ids.
- Both: `message:reveal`, user tokens and API keys, `Cache-Control: no-store`, per-principal limit `API_MESSAGES_REVEAL_PER_MINUTE` (default 30; config-driven guard like `QuarantineRateLimitGuard`, bucket `message-reveal`, `429` with `Retry-After`, `503` when the store is down), no Idempotency-Key (a read with an audit side effect, not a §3.5 sensitive mutation). Platform override sessions are audited with the override metadata as every other audit row.

### E7. Headers: `GET /messages/{messageId}/headers` and the safe subset

- `MessageHeadersController_headers_v1`, `message:read`, replica, echo-checked, by `(message_id, received_at)` on the `email_headers` unique key, at most 500 rows read (the stored limit is 200). Response (a bounded resource, not a list): `{ messageId, availability: 'available' | 'not_parsed' | 'none_stored' | 'retention_expired', storedHeaderNames, safeHeaderNames, headers: [{ seq, name, value: string | null, masked: boolean }] }`.
- **Safe subset (value in clear for `message:read`):** From, Sender, Reply-To, Return-Path, Date, Message-ID, In-Reply-To, References, Authentication-Results (sender side, identifiers and authentication facts). **Masked (value `null`):** To, Cc, Subject, and any name outside the 3.1 allow-list (fail closed). Values are attacker-controlled text, returned as stored (decoded), never parsed by the api.
- `availability`: `not_parsed` when the 3.1 parse row is missing or not `parsed`/`parsed_with_defects`; `retention_expired` when parsed, no rows, and the message is older than the `email_headers` retention of the partition registry (3 months); `none_stored` when parsed and no rows within retention. The **full header block** stays in the EML in S3 and is never fetched (stated in the UI and the API guide).

### E8. Quarantine operator routes: the recipient rule

- `GET /quarantine/entries` and `GET /quarantine/entries/{entryId}`: `recipient` is in clear only for callers holding a quarantine decision permission (`quarantine:release`, `quarantine:approve`, `quarantine:reject`, `quarantine:delete`, `quarantine:request_release`, `quarantine:manage`) or `message:reveal`; otherwise it is masked like E5 and the new field `recipientMasked` is `true`. ### E9. Addresses inside free text

### 3.4 Masking functions (WP2, `apps/api/src/modules/messages/domain/sensitive-masking.ts`)

- `maskAddress(value)`: `''` → `''`; without `@` → first code point + `***`; `local@domain` → first code point of `local` (none when empty) + `***@` + `domain` (as stored). Code points, never UTF-16 units. Example `finance.team@acme.example` → `f***@acme.example`.
- `maskAddressesInText(text)`: replaces the local part of every address-shaped substring (`[\p{L}\p{N}._%+\-!#$&'*/=?^`{|}~]+@[A-Za-z0-9-]+(\.[A-Za-z0-9-]+)+`, Unicode flag) with `maskAddress` of the match; inputs are already bounded (≤ 2 048).
- `MASKED_HEADER_NAMES = ['To', 'Cc', 'Subject']`, `SAFE_HEADER_NAMES` = §2 E7; comparison case-insensitive; unknown names masked.
- Unit tests: exhaustive table (null sender, IDN domains, quoted local parts, several addresses in one reply, addresses in angle brackets, no false positive on `user@localhost`-less text, code points).

## 4. Alternatives considered

| Alternative                                                                       | Why not                                                                                                                                                                                       |
| --------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| FULLTEXT index on `subject`                                                       | InnoDB does not support FULLTEXT on partitioned tables                                                                                                                                        |
| `LIKE '%term%'` within the scan budget                                            | An unindexed LIKE over a partitioned table (forbidden by the step directive) and unusable at 1M/day (thousands of short pages)                                                                |
| Prefix index `subject(N)` on the raw column                                       | No reply-marker normalization, encoded-word subjects before the parse; the generated key costs the same and normalizes                                                                        |
| A token search table written by the smtp-adapter / email-worker                   | New data-plane writer, backfill and privacy questions (hashed subject tokens) for a control-plane view; the analytics/search store of ADR-0009 (steps 9–10) is the place for content search   |
| Merging several `deliveryStatus` / `quarantineStatus` values (k-way keyset merge) | Correct but the budgeted-boundary merge is complex; one value per filter covers the UI (single select); recorded follow-up                                                                    |
| `subject`, `recipients` clear for privileged roles by default                     | The brief requires reveal only through an explicit, audited action; every clear view must be attributable; DLP precedent (ADR-0038)                                                           |
| Reusing `message:read_content` as the reveal permission                           | Its catalog meaning is "content (body and attachments) from object storage"; reveal is metadata and must be grantable separately (compliance auditors reveal metadata but do not read bodies) |
| A reveal token forwarded on later GETs (`X-EG-Reveal`)                            | New header through the BFF allow-list, token custody in the browser, cached GET responses with clear values; explicit POSTs with `no-store` are simpler                                       |
| One audit row per bulk reveal with a list of ids                                  | The details page's audit history queries by message id; one row per message keeps every reveal attributable to the message                                                                    |
| Masking quarantine recipients for everyone                                        | The quarantine workflow decides per recipient; deciders' reads are already audited (5.3)                                                                                                      |
| Saved views in `localStorage`                                                     | Not shared across devices, lost in private windows, not tenant-scoped; the directive allows saved views only server-side                                                                      |
| Explorer bulk rescan / release and export                                         | Not in the brief; bulk rescan needs a new API, bulk release exists on the Quarantine page, export is unbounded at scale and needs an async, audited, DLP-aware job (§10, §12)                 |
| A side panel instead of the details page                                          | The brief asks for the details page; the panel would duplicate it                                                                                                                             |

## 8. Security notes

- The tenant is always the principal's (or the audited override target's); no route takes an organization from the client. Foreign ids are `404` (messages, saved views, reveal), and bulk reveal omits them.
- Every clear subject, recipient address and masked header value leaves the api only through `message:reveal` operations, after the audit row commits, with `no-store`; the portal keeps them in component state only.
- Search filters that probe content (subject) or other modules' state (delivery, quarantine) require those modules' permissions.
- No body or attachment content is fetched by the explorer or the details sections; previews and downloads stay behind the 5.3 doors.
- Saved view definitions may contain identifying search values typed by their owner; they are tenant- and user-scoped, never logged, never in audit metadata.
- Secret-shaped strings: none are added; examples use obvious placeholders containing `EXAMPLE`; test literals that look like secrets are built at runtime.
