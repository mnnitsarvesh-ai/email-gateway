## 2. Decisions

### 2.0 Invariants (never traded away)

1. **Metadata only.** No webhook payload, stored webhook event, delivery attempt row, alert e-mail, audit row, log line or metric carries a message body, attachment content, subject, local part of an address, raw header (other than the documented `internetMessageId`), S3 key, URL found in mail, secret or token. A guard (§2 W4) refuses an envelope that violates it; a test asserts the absence on real stack payloads.
2. **Tenant from trusted context.** The api takes the organization from the principal (`scopeFromPrincipal`), never from a header or body; the worker takes it from the envelope `organizationId` the producer set, re-checks every row it reads against it (echo checks, D15 of 6.1) and **only ever matches subscriptions of that organization**. Another tenant's subscription, delivery, replay or domain id answers like a missing one (`404`).
3. **At least once, idempotent everywhere.** Projection is idempotent by deterministic public event ids and unique keys; deliveries are idempotent by `(subscription_id, event_id, event_occurred_at, delivery_seq)`; receivers dedupe by the event id (`Idempotency-Key` header).
4. **Outbound HTTP only through the SSRF guard**, dialing the validated address, without redirects, with bounded time and size.
5. **Secrets** are generated by a CSPRNG, shown once, stored only encrypted with a key held by the api (encrypt) and the webhook-worker (decrypt), never logged, audited, stored in idempotency rows or returned again.

### W1. Architecture: a projector, a delivery loop, one new app

New deployable **`apps/webhook-worker`** (`@email-gateway/webhook-worker`, HTTP port 3075: probes and `/metrics` only) with roles `WEBHOOK_WORKER_ROLES` (comma list of `fanout`, `delivery`; default `fanout,delivery`; Compose runs both in one container, Kubernetes two Deployments from the same image, like `policy-engine` / `quarantine-worker`):

- **`fanout`** consumes the new work queue `email.webhooks` (topology v11, §4.3; broker user `eg-webhook`, ledger consumer `webhook-worker.fanout`). For each internal event it (a) maps it to zero or more public events (W3), (b) matches them against the organization's active subscriptions (W5) and (c) decides whether a security alert is due (N2). When nothing matches, it acks **without a transaction and without a ledger row** (pure function of cached state; redelivery repeats the same no-op). Otherwise, in one writer transaction (`processOnce`, budget `WEBHOOK_FANOUT_TX_TIMEOUT_MS` ≥ 120 s, the 4.2 §6 rule): `webhook_events` rows (insert-ignore on the unique key), `webhook_deliveries` rows (`pending`, `next_attempt_at = now`, insert-ignore), alert windows and `notification.alert_requested.v1` outbox rows (N2).
- **`delivery`** is a database-driven loop (W8): claims due deliveries fairly per organization and subscription, signs and POSTs them through the guarded client (W9), records attempts, schedules retries (W10), dead-letters, auto-disables (W11), executes range replays (W12) and runs the maintenance purges (W13).

Why a projector and not new producer events: every fact except DNS record failures is already in an outbox event with at-least-once transport; projecting keeps the 2.x–5.x producers untouched (no risk to the mail path) and gives one owner of the public contract. Why a database-driven delivery loop and not RabbitMQ delay queues: per-endpoint `Retry-After`, per-tenant fairness, auto-disable, replay and the delivery history all need the row anyway; a broker hop per attempt would duplicate state.

The api owns registration, history, replay requests and settings (W6, W12, N3). The notification-worker owns e-mail (N1). **Apps never import each other**: shared logic lives in the new package `@email-gateway/webhooks` (W2).

### W3. Projection rules (fanout)

A missing row that must exist (message, scan, execution log) is retried (`InconsistentReadError`, at most the queue's retry policy, then dead letter); an optional row (release log, entries) missing means "no event".

### W4. Envelope and payload safety

```json
{
  "id": "0193a1b2-…-8…",
  "type": "email.quarantined",
  "version": 1,
  "occurredAt": "2026-11-13T09:14:03.120Z",
  "organizationId": "0192f0c4-7d1e-7b6a-9c55-6f3e2a1d4b10",
  "data": { "message": { … }, "quarantine": { … } }
}
```

- `id`: deterministic public event id (W2); also sent as `Idempotency-Key` and `EG-Event-Id`.
- `version`: the payload version of `type` (1 for every type in 6.2); a breaking change ships as version 2 (subscriptions keep receiving 1 until they opt in; not built in 6.2).
- `organizationId`: the organization **public** id.
- Serialized once at projection (`JSON.stringify` of the validated object), stored as text (`webhook_events.payload_json`) and sent byte-identically on every attempt and replay; `payload_sha256` stored.
- `assertWebhookPayloadSafe` runs in `buildEnvelope`; a violation is a programming error: the fanout dead-letters the source event (`NonRetryableError`, code `webhook_payload_unsafe`) and counts `webhook_fanout_events_total{result="unsafe"}`.

### W5. Subscriptions, event types and filters

- `eventTypes`: 1–10 unique values of `WEBHOOK_EVENT_TYPES`; no wildcard.
- `filters` (optional, strict, all fields optional): `directions` (1–3 of `inbound`, `outbound`, `internal`), `domainIds` (1–20 unique tenant domain public ids, resolved at write time inside the tenant scope; unknown/foreign id → `422 webhook_filter_invalid`), `minSeverity` (`info` < `low` < `medium` < `high`), `verdicts` (1–7 of the seven scan verdicts).
- Matching: type ∈ eventTypes **and** each present filter matches the event's attribute **when the event carries it** (domain events carry no direction or verdict and pass those filters; every event carries `severity`; message events carry `domainId` (may be null: a null domain never matches a `domainIds` filter)).
- The subscription index is cached per organization in the fanout process for `WEBHOOK_SUBSCRIPTION_CACHE_SECONDS` (default 5, 1–60): `active` subscriptions plus the `webhooks` feature flag. An event is delivered only to subscriptions whose `created_at ≤ event.occurredAt` (no back-fill). Changes take effect within the cache TTL (documented).
- Per organization at most `WEBHOOK_MAX_SUBSCRIPTIONS_PER_ORG` non-deleted subscriptions (`409 webhook_limit_reached`).
- The organization feature `webhooks` must be enabled to create, re-activate, test or replay (`403 webhooks_not_enabled`); the fanout skips organizations without it (no deliveries). The worker enforces the feature and the organization status at **every** stage (closing round, §13): the fanout projects nothing for an organization that is not `active` (suspended, `pending_deletion`, deleted); the claimer reads both in its claim transaction and `cancels` the due rows (`organization_inactive` / `webhooks_not_enabled`; replayable afterwards) instead of sending; the range replay processor ends `failed` with the same codes.
- Status: `active` (delivers), `paused` (no new deliveries are created; pending ones stay pending and are not sent until resumed: they are **parked**, `next_attempt_at = NULL`, by the api in the PATCH transaction and by the claimer for any due row it meets, and made due again on resume by the api, with the maintenance pass as a safety net; closing round, §13), `disabled` (set by the system after sustained failure, W11, or by `PATCH status=disabled`; pending deliveries become `cancelled`), `deleted` (soft delete; pending deliveries `cancelled`; purged by W13). `PATCH` may set `active`, `paused`, `disabled`; re-activation resets `consecutive_failures`, `failing_since`, `disabled_reason`.

### W6. Registration API (api module `webhooks`, OpenAPI tag `webhooks`)

All routes follow every 6.1 convention (ADR-0050–0053): strict zod schemas, coded errors with `requestId`, v1 signed cursors on lists, one permission requirement per route, global rate limits, `x-eg-*` extensions, explicit request/response examples, audit rows in the effect's transaction, echo-checked repositories (D15), writer for writes and read-after-write, replica for lists. Routes in §6.1.

- **URL rules** (`webhookUrlSchema` + `SsrfGuard.checkUrl` from `@email-gateway/url-security` with `allowedPorts = WEBHOOK_ALLOWED_PORTS`): absolute, ≤ 2048, no userinfo, no fragment, scheme `https` (plain `http` only when `WEBHOOK_ALLOW_HTTP=true`, refused by config outside APP_ENV `local`/`ci`), host passes the guard's name checks, an IP-literal host passes the address checks, the click-service host and the api's own public host are refused (`deny_list`). Failure → `422 webhook_url_not_allowed` with `reason` (a `BlockedReason`). DNS is **not** resolved at registration (it can change); the worker checks every resolved address at every attempt (authoritative). Stated in the API guide.
- **Create / rotate** return the secret once (`secret`); see W7 and ADR-0057 for Idempotency-Key with redacted replay.
- Audit metadata of URLs: `urlHost` and `urlSha256` only (a query string may carry a receiver token).

### W7. Secrets and rotation

- `generateWebhookSecret()` on create and rotate; encrypted with `WebhookSecretCipher` (AAD binds organization, subscription and secret version); stored in `secret_ciphertext`; `secret_version` starts at 1.
- **Rotate** `POST /webhooks/{id}/rotate-secret { overlapHours?: 0–168, default WEBHOOK_SECRET_OVERLAP_HOURS_DEFAULT (24) }`: the current ciphertext moves to `previous_secret_ciphertext` with `previous_secret_expires_at = now + overlapHours` (0 = no overlap: previous cleared), a new secret becomes current (`secret_version + 1`, `secret_rotated_at = now`). While the previous secret is unexpired, **every** attempt carries two `v1=` signatures (current first). A second rotation during an overlap replaces the previous secret with the one being retired (only one previous secret exists).
- Never returned again (`GET` shows `secretVersion`, `secretRotatedAt`, `previousSecretExpiresAt`), never logged (pino redaction paths `secret`, `*.secret`, `secretCiphertext`, `previousSecretCiphertext` in both apps), never in audit metadata, never stored by idempotency (ADR-0057: the stored response is the redacted representation with `secret: null`).
- The worker caches decrypted secrets in memory for ≤ 60 s keyed by `(subscription id, secret version)`; a decryption failure marks the attempt `secret_unavailable` (retryable, alert via `webhook_delivery_attempts_total{outcome="secret_unavailable"}`).

### W8. Delivery loop (worker `delivery` role)

Every `WEBHOOK_DELIVERY_POLL_INTERVAL_MS`:

1. **Organizations with due work** (one query, replica not used): `SELECT organization_id, MIN(next_attempt_at) FROM webhook_deliveries WHERE status = 'pending' [AND organization_id > cursor] GROUP BY organization_id HAVING MIN(next_attempt_at) <= ? ORDER BY organization_id LIMIT 200` over the new index `(status, organization_id, next_attempt_at)` (loose index scan; EXPLAIN-checked in an integration test). A per-process cursor rotates through `organization_id` (wrapping around), so with more than 200 due organizations every one is visited within ⌈n / 200⌉ ticks (closing round, §13). Shuffled each tick (fairness).
2. **Per organization**, while the process has free slots: free org slots = `WEBHOOK_MAX_INFLIGHT_PER_ORG` − Redis counter `wh:inflight:org:<orgId>`; claim up to that many rows in one short writer transaction: `SELECT … FROM webhook_deliveries d WHERE d.status='pending' AND d.organization_id=? AND d.next_attempt_at <= ? ORDER BY d.next_attempt_at LIMIT ? FOR UPDATE SKIP LOCKED`, join the subscription; skip rows whose subscription is at its in-flight cap (`wh:inflight:sub:<subId>`, cap = `max_concurrency` ?? `WEBHOOK_MAX_INFLIGHT_PER_SUBSCRIPTION`) or over its per-minute rate (`wh:rate:sub:<subId>:<minute>`, `WEBHOOK_RATE_PER_SUBSCRIPTION_PER_MINUTE`); subscription `paused` → **parked** (`next_attempt_at = NULL`, closing round); `disabled`/`deleted` → `cancelled`; organization not `active` or `webhooks` feature off → every due row read `cancelled` (closing round). A claimed row gets the **lease**: `attempt_count + 1`, `last_attempt_at = now`, `next_attempt_at = now + WEBHOOK_HTTP_TOTAL_TIMEOUT_MS + 60 s`. A crash leaves the lease to expire (the attempt counts; at least once).
3. **Send** outside any transaction (W9), bounded globally by `WEBHOOK_DELIVERY_CONCURRENCY` per process; Redis in-flight slots are one sorted-set member per reservation (`wh:slots:org:<id>`, `wh:slots:sub:<id>`, score = lease expiry; expired members dropped before every count), removed after the attempt: a killed process's slots expire one lease after the reservation however busy the keys stay (closing round; the first version used `INCR`/`DECR` counters whose TTL every new reservation refreshed). Redis unavailable → the tick sends nothing (fail closed, `webhook_rate_limit_store_errors_total`).
4. **Record** in one writer transaction with CAS (`WHERE id=? AND event_occurred_at=? AND status='pending' AND attempt_count=<claimed>`): insert the `webhook_delivery_attempts` row; on 2xx → `succeeded`, `completed_at`, subscription `consecutive_failures = 0`, `failing_since = NULL`, `last_success_at`; otherwise W10/W11. A lost CAS (row changed) is counted and ignored.

A slow endpoint can hold at most its subscription's cap and its organization's cap of slots; other organizations' rows are claimed in the same tick. Global process concurrency and per-replica slot accounting are documented; production sizing is not verified locally.

### W9. Guarded POST client (`@email-gateway/url-security`, `src/net/guarded-post.ts`)

`GuardedPoster` (exported from `net/index.ts`) built on the existing `SsrfGuard`, `RestrictedResolver`, `ConcurrencyLimiter`, `untraced`, dial-map and CA helpers:

- `post({ url, headers, body, signal })` → `PostResult { outcome, httpStatus, latencyMs, retryAfter: string \| null, snippetBytes: Buffer, blockedReason, errorCode }` with `outcome ∈ succeeded | http_error | redirect | timeout | dns_error | connection_error | tls_error | blocked | too_large`.
- Steps: `guard.checkUrl` (scheme, port, name) → resolve (A/AAAA, ≤ 16 answers) → **every** answer must pass `guard.checkAddress` (any blocked answer blocks the attempt: DNS rebinding safe) → dial the first allowed IP literal (`lookup` refused on the socket, as the fetcher) with TLS `servername` = host and certificate verification against the host name, TLS ≥ 1.2 → re-check the connected `remoteAddress` → one request `POST`, `Content-Type: application/json`, exact header set given by the caller plus `User-Agent: EmailGateway-Webhooks/1`, `Content-Length`; **no redirects** (3xx = outcome `redirect`, `Location` never followed or stored); timeouts `WEBHOOK_HTTP_CONNECT_TIMEOUT_MS` (connect + TLS) and `WEBHOOK_HTTP_TOTAL_TIMEOUT_MS` (whole exchange); response headers ≤ 16 KiB / 100; response body read up to `WEBHOOK_RESPONSE_MAX_BYTES` (default 4096; beyond → stop reading, outcome by status, not an error); no cookies, no proxy environment variables, no compression requested (`Accept-Encoding: identity`).
- Test seams (refused unless APP_ENV `local`/`ci`): `testAllowCidrs` (documentation ranges only, `validateTestAllowCidrs`), `dialMap`, extra CA, and `allowHttp`.
- Hooks for metrics (`onBlocked(reason)`).

### W10. Retries, backoff, Retry-After, dead letters

- Retryable outcomes: every non-2xx HTTP status, `redirect`, `timeout`, `dns_error`, `connection_error`, `tls_error`, `too_large`, `secret_unavailable`. **Not retryable**: `blocked` (SSRF guard) → `failed` immediately with `last_error = 'blocked:<reason>'` (counts toward auto-disable).
- Schedule: `delay(n) = min(WEBHOOK_RETRY_MAX_DELAY_SECONDS, WEBHOOK_RETRY_BASE_SECONDS × 2^(n−1))` for the retry after attempt `n`, with full jitter in `[0.8, 1.2] × delay`; defaults base 30 s, max 6 h, so the attempts run at ≈ 0, 30 s, 1.5 min, 3.5 min, 7.5 min, 15.5 min, 31.5 min, 63.5 min (8 attempts, `WEBHOOK_MAX_ATTEMPTS`).
- `Retry-After` (on any non-2xx) is honored: `delay = max(computed, retryAfter)`, capped at `WEBHOOK_RETRY_AFTER_MAX_SECONDS` (default 3600); a value above the cap is clamped, never ignored.
- **Dead letter**: when `attempt_count ≥ WEBHOOK_MAX_ATTEMPTS` or `now − first attempt > WEBHOOK_MAX_RETRY_AGE_HOURS` (default 24, ≤ 72), the delivery becomes `dead` (`completed_at`, `last_error`), metric `webhook_deliveries_dead_total`. Dead deliveries are the webhook dead-letter store: listed with `status=dead`, replayable (W12), purged with their partition. Poison **source events** of the fanout go to `email.dead-letter` through the queue policy (existing operator replay `POST /platform/dead-letters/replay`; the `ops` broker user gains the `email.webhooks` retry key, §4.3).
- **Backlog bound**: a subscription with more than `WEBHOOK_MAX_PENDING_PER_SUBSCRIPTION` (default 50 000) pending deliveries (count cached 30 s by the fanout) gets new deliveries inserted directly as `dead` with `last_error = 'backlog_exceeded'` (visible, replayable), so one dead endpoint cannot grow the table without bound.

### W11. Automatic disable after sustained failure

On each failed attempt: `consecutive_failures + 1`, `failing_since = COALESCE(failing_since, now)`, `last_failure_at = now`. When `consecutive_failures ≥ WEBHOOK_DISABLE_AFTER_FAILURES` (default 50, 5–10 000) **and** `now − failing_since ≥ WEBHOOK_DISABLE_AFTER_HOURS` (default 24, 1–168), in the same transaction: `status = disabled`, `disabled_reason = 'sustained_failure'`, `disabled_at = now`, `row_version + 1`, an `audit_logs` row (`actor_type = system`, action `webhook.auto_disabled`, metadata `{ subscriptionId, consecutiveFailures, failingSince }`) and one `notification.alert_requested.v1` outbox row (`kind = webhook_disabled`, refs `subscriptionId`). Pending deliveries of the subscription are `cancelled` by the claimer or the maintenance pass. Re-enabling is an explicit `PATCH status=active` (audited); dead/cancelled deliveries can then be replayed.

### W12. Replay

- **Single delivery** `POST /webhooks/{webhookId}/deliveries/{deliveryId}/replay` (Idempotency-Key, transactional, `sensitive`): in the api transaction, a new `webhook_deliveries` row for the same event (`delivery_seq = max(delivery_seq) + 1` for `(subscription_id, event_id, event_occurred_at)`, `trigger = replay`, `status = pending`, `next_attempt_at = now`); at most `WEBHOOK_REPLAY_MAX_PER_DELIVERY` (default 10) replays per event and subscription (`409 webhook_replay_limit`); the subscription must be `active` (`409 webhook_not_active`) and the event still stored (`410 webhook_event_expired` after retention). `202 { deliveryId }`. Audit `webhook.delivery_replayed`.
- **Time range** `POST /webhooks/{webhookId}/replays { from, to, statuses?, eventTypes? }` (Idempotency-Key, transactional, `sensitive`, route limit `WEBHOOK_REPLAY_REQUESTS_PER_HOUR` per organization): `to − from ≤ WEBHOOK_REPLAY_MAX_RANGE_HOURS` (default 72), `from` within delivery retention; `statuses` ⊆ {`succeeded`, `failed`, `dead`, `cancelled`} (default `failed`, `dead`); one `queued`/`running` replay per subscription (`409 webhook_replay_in_progress`). Inserts a `webhook_replays` row (`queued`) → `202 { replayId, status }`. The worker's `delivery` role processes queued replays in batches of 500 over the subscription's **original** deliveries (`delivery_seq = 0`) in the range with the keyset `(subscription_id, event_occurred_at, id)`, inserting replay deliveries as above, at most `WEBHOOK_REPLAY_MAX_EVENTS` (default 10 000; beyond → `completed` with `truncated = true`), recording progress (`cursor_*`, `matched_count`, `created_count`) so a crash resumes; idempotent (insert-ignore on the delivery unique key with the computed `delivery_seq` per event inside the batch transaction). Closing round: the batch locks the subscription row `FOR UPDATE` (the lock the api's single replay takes) and reads the sequences `FOR UPDATE`, so the two never compute the same `delivery_seq`; events that already have `WEBHOOK_REPLAY_MAX_PER_DELIVERY` replays are skipped (in `matched_count`, not `created_count`; `webhook_replay_events_skipped_total{reason}`); the organization must be `active` with the feature enabled. `GET /webhooks/{webhookId}/replays/{replayId}` shows progress. Audit `webhook.replay_requested`.
- Replays re-send the **stored** envelope (same `id`, same bytes, new `EG-Delivery-Id`, new timestamp and signature). Events that occurred while a subscription was paused or disabled were never recorded for it and **cannot** be replayed (stated).

### W13. Maintenance and retention (worker `delivery` role, leader-elected with `GET_LOCK('eg:webhook-maintenance')`, every `WEBHOOK_MAINTENANCE_INTERVAL_MS`)

- `webhook_deliveries`, `webhook_delivery_attempts`, `webhook_events`: monthly partitions, retention 2 months (partition registry, `operational`; `pnpm db:partitions apply`). No row-level purge.
- `webhook_subscriptions` with `status = deleted` and `deleted_at` older than `WEBHOOK_DELETED_RETENTION_DAYS` (default 62, ≥ 62 so every partition referencing them has dropped) are hard-deleted (batches of 100).
- `webhook_replays` in a terminal state older than 30 days, `notification_alert_windows` older than 7 days: deleted in batches of 1 000.
- Pending deliveries of `disabled`/`deleted` subscriptions → `cancelled` (batches of 1 000).
- Parked pending deliveries (`next_attempt_at IS NULL`) of `active` subscriptions → due now (batches of 1 000; closing round).
- Gauges `webhook_due_backlog` (pending with `next_attempt_at ≤ now`, capped count 100 000) and `webhook_oldest_due_age_seconds`, both excluding deliveries of paused subscriptions (closing round).

### 4.2 Public webhook contract (HTTP)

Request: `POST <subscription url>`, body = the stored envelope (UTF-8 JSON, ≤ 16 KiB). Headers (exact set):

| Header                | Value                                                                                                        |
| --------------------- | ------------------------------------------------------------------------------------------------------------ |
| `Content-Type`        | `application/json`                                                                                           |
| `User-Agent`          | `EmailGateway-Webhooks/1`                                                                                    |
| `EG-Signature`        | `t=<unix seconds>,v1=<hex HMAC-SHA256(secret, "<t>.<raw body>")>` (a second `v1=` during a rotation overlap) |

| `EG-Event-Type`       | envelope `type`                                                                                              |

## 7. Alternatives considered

| Alternative                                                                                                                  | Why not                                                                                                                                                           |
| ---------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| New producer events for every public type (smtp-adapter, email-worker, policy-engine, delivery-worker emit `webhook.*` rows) | Touches five services on the mail path for facts already in the outbox; two contracts for one fact                                                                |
| Webhook-worker tails `message_outbox` directly                                                                               | Scans ~10 M rows/day; bypasses the broker's retry/dead-letter; competes with the relay; RabbitMQ is the platform's transport (ADR-0024)                           |
| `email.webhooks` as `work-lossy` (drop-head) so it can never nack the relay                                                  | Silently loses webhooks during a worker outage; the 1 M bound plus an early backlog alert gives hours of headroom (risk §8)                                       |
| RabbitMQ delay queues per retry                                                                                              | Cannot honor per-endpoint `Retry-After` exactly, needs the delivery row anyway, no fairness per tenant                                                            |
| One delivery row per attempt (no attempts table)                                                                             | History of a delivery scattered; replay semantics unclear                                                                                                         |
| Standard Webhooks header format (`webhook-id`, `webhook-timestamp`, `webhook-signature: v1,<base64>`)                        | Viable; the brief asks for "timestamp plus raw body", and a Stripe-like `t=…,v1=…` keeps one header with rotation overlap; noted as a possible additive v2 header |
| Raw 32-byte key as HMAC key                                                                                                  | Receivers must base64url-decode correctly; using the whole `whsec_…` string as key is harder to get wrong                                                         |
| Secrets hashed (like API keys)                                                                                               | The worker must sign, so it needs the secret: encryption with a dedicated key, not `DATA_ENCRYPTION_KEY` (custody stays narrow)                                   |
| No Idempotency-Key on create/rotate (ADR-0052 decision 8 as is)                                                              | The brief requires it; redacted replay (ADR-0057) keeps the secret out of the store                                                                               |
| DNS resolution at registration                                                                                               | DNS changes; the authoritative check is at send time; a registration-time resolve would add a resolver to the api for advisory value only                         |
| Per-recipient `email.delivered`                                                                                              | Up to 1 000 events per message; message-level with counts covers the brief; per-recipient detail stays in `GET /messages/{id}/recipients`                         |
| Addresses in payloads (opt-in)                                                                                               | PII leaves the platform with every event; v1 carries domains only; an opt-in can be a later version                                                               |
| A second digest for webhooks/alerts                                                                                          | Reuses the 5.3 digest; alerts are throttled windows instead                                                                                                       |
| Throttling in the notification-worker                                                                                        | It would still receive every candidate event (ledger rows per event); throttling at the producer bounds the queue                                                 |

## 8. Risks and mitigations

| Risk                                                                                   | Mitigation                                                                                                                                                                                                                                    |
| -------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `email.webhooks` adds ~10 quorum-queue writes per message                              | Bindings limited to 8 event types; cheap no-op path without DB; measured in the stack (WP5 records queue rates); production capacity not claimed                                                                                              |
| Worker outage → 1 M backlog → reject-publish nacks the relay (all queues of a publish) | Alert `WebhookFanoutBacklog` (> 100 000 ready for 10 min, critical at > 500 000); runbook: scale fanout, or temporarily unbind with the documented `rabbitmqctl` procedure; at 1 M messages/day the bound is ~2.4 h of total platform traffic |
| No-op events leave no ledger → no reconciliation for webhooks                          | Excluded from `RECONCILE_QUEUES` (documented); at-least-once from the confirmed publish; broker data loss is the residual risk (quorum queues, 3 replicas in production)                                                                      |
| Cache TTL lets a new subscription miss events for ≤ 5 s                                | Documented; `created_at ≤ occurredAt` rule keeps it deterministic                                                                                                                                                                             |
| Slow or hostile endpoints hold worker slots                                            | Per-subscription and per-org caps, 10 s total timeout, 4 KiB read cap, no redirects, auto-disable                                                                                                                                             |
| SSRF via DNS rebinding or redirects                                                    | Every resolved answer checked, the socket dials the checked IP, remote address re-checked, no redirects, https in production, ports allow-listed                                                                                              |
| Secret leakage through logs/idempotency/audit                                          | Pino redaction paths, ADR-0057 redacted replay, audit metadata allow-list, tests grep logs and rows for `whsec_`                                                                                                                              |
| Payload drift adds content later                                                       | `assertWebhookPayloadSafe` at build time + stack test over every received payload (no `@`, no `://`, no subject string, no `org/<id>/` key)                                                                                                   |
| Partitioned `FOR UPDATE SKIP LOCKED` claim cost                                        | Index `(status, organization_id, next_attempt_at)`; EXPLAIN test; claim batches bounded                                                                                                                                                       |
| Prisma wrong-read defect (4.2 §6)                                                      | ≥ 120 s budgets, echo checks on every repository row (D15)                                                                                                                                                                                    |
| Alert floods during a spam campaign                                                    | One alert per organization/kind/scope/window; defaults high severity only                                                                                                                                                                     |
| A tenant re-enables a broken endpoint repeatedly                                       | Each disable is audited and alerted; the rate of alerts is bounded by the window                                                                                                                                                              |

### Closing round (review findings), 2026-11-13

Seven review findings (one high, six medium) were checked against the code; all seven were real and are fixed with unit and integration tests. One further defect was found while verifying the fixes.

1. **High: a paused subscription's backlog blocked the organization's other subscriptions.** The claim read the `min(2 × limit, 200)` earliest due rows of the organization and skipped paused ones without moving them, so ≥ 200 due rows of a paused subscription hid every active one forever (and kept the organization due). Fix: paused rows are **parked** (`next_attempt_at = NULL`, still `pending`): by the api in the PATCH transaction (`WebhookDeliveriesRepository.parkPending`, bounded like `cancelPending`; audit `parkedDeliveries`), by the claimer for any due row of a paused subscription it reads (rows in flight at pause time), and made due again on resume (`unparkPending`, audit `resumedDeliveries`) with a maintenance step `unpark` as the safety net for leftovers. Parked rows leave the `(status, organization_id, next_attempt_at)` range, so they are never read again. Tests: `claimer.test.ts` (450 paused rows ahead of an active row), `webhooks.e2e.test.ts` (pause/resume), api integration (`updates with CAS … pause parks, resume un-parks`), worker integration (450 real rows parked, active row delivered within ⌈451 / 32⌉ ticks, un-park on resume).
2. **Medium (security): no organization-status or feature check after the fanout.** The claimer and the range replay processor never read `organizations.status` or the `webhooks` feature; the fanout index ignored the status. Fix: the claimer reads both in its claim transaction and cancels the due rows (`organization_inactive` / `webhooks_not_enabled`, no reservation, nothing sent); the replay processor ends `failed` with the same codes; the fanout index carries `organizationActive` and matches nothing for a non-active organization. Tests: claimer (suspended, pending deletion, missing, feature revoked, feature absent), replay (suspended, deleted, feature off / absent), subscription index and fanout, worker integration (suspended organization and revoked feature: cancelled, receiver got nothing, replay failed, fanout projects nothing more).
3. **Medium: the due gauges counted paused work**, so `WebhookOldestDueAge` / `WebhookDeliveryStalled` fired for a legitimate pause. Fix: parked rows are outside `next_attempt_at ≤ now`, and both gauge queries exclude paused subscriptions (`NOT EXISTS`); the oldest-due query became `ORDER BY next_attempt_at LIMIT 1`. Tests: maintenance unit test, worker integration (unparked due rows of a paused subscription: backlog 0).
4. **Medium: `dueOrganizations()` always returned the same 200 lowest-id organizations** (`LIMIT` without order, shuffled afterwards). Fix: `ORDER BY organization_id` with a per-process cursor (`organization_id > cursor`, then wrap around up to the cursor); every due organization is visited within ⌈n / 200⌉ ticks. EXPLAIN still uses `webhook_deliveries_status_org_next_idx` (integration test). Test: 450 due organizations visited in 3 ticks.
5. **Medium: leaked in-flight slots never decayed on busy keys** (each reservation refreshed the TTL of the whole counter). Fix: `wh:slots:org:<id>` / `wh:slots:sub:<id>` are sorted sets with one member per reservation scored by its lease expiry; reserve and count drop expired members first; release removes the member. New key names (the old string keys would be `WRONGTYPE`; they expire on their own). Tests: unit (fake) and real Redis: a slot taken by a "killed" process stops counting one lease later while reserve/release traffic keeps the keys alive.
6. **Medium: range replays ignored `WEBHOOK_REPLAY_MAX_PER_DELIVERY` and raced the api's single replay.** Fix: the batch locks the subscription row `FOR UPDATE` (as `lockActive`) before reading `MAX(delivery_seq)` and `SUM(delivery_seq > 0)` `FOR UPDATE`; events at the bound are skipped (counted in `matched_count`, not `created_count`, metric `webhook_replay_events_skipped_total{reason}`). New worker key `WEBHOOK_REPLAY_MAX_PER_DELIVERY` (1–50, default 10; same name and value as the api's, already in `.env.example` and `.env`; added to Compose and the `webhook-delivery` manifest). Tests: replay unit tests (lock order, skip), worker integration (an event with 10 replays: matched 1, created 0; the batch waits while another transaction holds the subscription lock).
7. **Medium: W7 log redaction of the ciphertext columns was missing.** Fix: `secretCiphertext` and `previousSecretCiphertext` added to `SECRET_FIELDS` in `packages/logger` (top level and `*.`), with tests. Resolves the carried item WP2 13 / WP5 11.
8. **Found while verifying: multi-row key updates failed with MySQL error 1292.** `(id, event_occurred_at) IN ((?, ?), …)` with more than one tuple is rejected by MySQL through Prisma's binary protocol (the event-relay documents the same). The maintenance `cancel_pending` step therefore failed for any batch of two or more rows (the WP2 integration test used one row). Fix: `deliveryKeyMatch()` (`src/delivery/keys.ts`) builds `(id = ? AND event_occurred_at = ?) OR …`, used by the claimer (cancel, park) and the maintenance (cancel, un-park); the worker integration suite now cancels and un-parks 450+ rows.
