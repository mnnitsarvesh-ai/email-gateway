## 0. Scope in one paragraph

A user with `assistant:use` and `report:read` asks the chat to "generate a security report" (optionally for the last 24 hours, 7 days, 30 days or an explicit window of at most `REPORTS_MAX_RANGE_DAYS`, and optionally for some sections only). The model calls one new **native tool** `report_generate`. The api runs it as a fixed, server-defined composition: up to ten **loopback reads of existing operations** (the six `/reports/*` routes, `GET /quarantine/summary`, `GET /ato/overview`, `GET /ato/accounts?sort=-riskScore`) with the user's own bearer token, exactly as the portal's Reports and Dashboard pages read them (guards, RBAC, tenant scope, rate limits). A pure renderer in `@email-gateway/assistant` turns the validated responses into one **self-contained dashboard-style HTML document** (summary cards, six line/area charts, five donut charts, seven bar charts, tables, a data appendix) with **server-side static SVG**, no script, no link, no external resource and every data string escaped. The HTML is stored in **object storage** (mail bucket, `org/<org>/assistant/report/…`), its metadata in a new `ai_chat_reports` row; the chat shows it in a **sandboxed iframe** (`srcdoc`, `sandbox=""`) with "Open full size" and "Download HTML". "Send this report to my email / to <address>" makes the model call the native write tool `report_send_email`; it is a **proposal** confirmed in the AI-2 card (risk `medium`), with the **recipient rule enforced by the server** at proposal and again at confirm, per-user and per-tenant **daily limits** and a **size limit**. The confirmed send writes an `ai_chat_report_deliveries` row and an outbox event in one transaction; the **notification-worker** reads the stored HTML from object storage and sends it through the existing `NoticeMailer` and `postfix-notify` relay (HTML body + the same HTML attached + plain-text alternative). Generation and send are audited; the report object follows the conversation's content retention.

## 2. Decisions

### 2.0 Invariants added to I1–I14

- **I15 Reports are built from the API, by the server.** Every figure in a report is a value of an existing operation's response fetched in this request with the user's own credential; the composition (which reads, which charts) is fixed server code; the model only chooses the period and the sections. No figure is computed by or taken from the model.
- **I16 Report HTML is inert.** The stored HTML contains no script, no event handler attribute, no link or URL, no external resource and no data-derived markup: every data string is sanitized and HTML-escaped, every attribute value is a constant or a formatted finite number, colors come from a fixed palette by index. It is displayed only in a sandboxed iframe (`sandbox=""`, no `allow-scripts`, no `allow-same-origin`) and served by the api only inside JSON.
- **I17 Report mail goes only to the organization.** The recipient rule (own address, active users of the organization, addresses of the organization's verified domains) is evaluated by the server at proposal and again at confirm; the model cannot widen it, and a refused recipient never produces a confirmation.

### D1. Native tools (ADR-0095, amendment of ADR-0091)

- A **native tool** is a registry record that is not an OpenAPI operation: `packages/assistant/src/registry/native.ts` exports `NATIVE_TOOLS: OperationTool[]` with `native: true` (new optional field of `OperationTool`), `operationId` `AssistantNative_<camel>` (never an OpenAPI id; registry check), nominal `method: 'POST'`, `pathTemplate` `native:<name>` (not under `/api/v1`, so the loopback client refuses it), `module: 'reports'`, `phase: 'AI-R'`, a hand-written `inputSchema` (strict, `additionalProperties: false`), a `requirement` and a `testedBy`.
- Exactly two native tools in AI-R:

| Tool                | operationId                       | Access / risk / confirm               | Requirement                                     | Input                                                                                                                                                                                                                                                                                                                                                |
| ------------------- | --------------------------------- | ------------------------------------- | ----------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `report_generate`   | `AssistantNative_reportGenerate`  | `read` / `read_audited` / `none`      | `{ mode: 'all', permissions: ['report:read'] }` | `range?: '24h'\|'7d'\|'30d'` (default `7d`); `from?`, `to?` (ISO 8601 date-time, both or neither; when given they replace `range`; `to` ≤ now + 1 min, `from` < `to`, ≤ `REPORTS_MAX_RANGE_DAYS` days); `sections?`: unique non-empty array of `summary, traffic, threats, domains, delivery, processing, url_clicks, quarantine, ato` (default all) |
| `report_send_email` | `AssistantNative_reportSendEmail` | `write` / `medium` / `confirm+impact` | `{ mode: 'all', permissions: ['report:read'] }` | `reportId?`: UUID or a ref `@r<seq>.1` (default: the latest `available` report of this conversation); `to?`: one address (default: the user's own address), `format: email`, ≤ 254 chars, ASCII only, no display name                                                                                                                                |

- `PROGRAM_PHASES` becomes `['AI-1','AI-2','AI-3','AI-R','AI-4','AI-5','AI-6']`, `ASSISTANT_PROGRAM_PHASE = 'AI-R'` (no AI-4+ tool becomes enabled; the existing checks keep holding).
- `ALL_TOOLS = [...OPERATION_TOOLS, ...NATIVE_TOOLS]` is what `findTool`, `enabledTools`, the catalogue index, `describe_tool` and `GET /assistant/tools` use. The generator includes the native records in the capability matrix (section "Native assistant tools") and in the `REGISTRY_VERSION` hash input.
- Consistency rules (test-enforced): unique names across both sets; native operation ids match `^AssistantNative_[A-Za-z]+$` and are absent from OpenAPI; native path templates start with `native:`; every enabled native write has a confirmation spec with `native` set and an impact template; native tools name `testedBy`; no credential-pattern input key.
- The api additionally hides `report_generate` when `ASSISTANT_REPORTS_ENABLED=false` and `report_send_email` when `ASSISTANT_REPORT_EMAIL_ENABLED=false` (`denied_disabled`, absent from the catalogue and `GET /assistant/tools`).

### D2. `report_generate` execution (api `NativeToolsService` → `ReportGeneratorService`)

The executor's D5 steps 1–6 run unchanged (budget, lookup, availability/permission, refs, Ajv). Then, for a native read, instead of `run()`'s loopback:

1. **Organization:** a platform principal without an override is refused `denied_guard` (guard `report_needs_organization`, "Reports are built for one organization; start a platform override first").
2. **Daily generation limit:** `ai_chat_reports` rows of the user created since 00:00 UTC ≥ `ASSISTANT_REPORTS_PER_USER_PER_DAY` → `denied_budget`, code `assistant_report_generation_limit`.
3. **Window:** from `range` or `from`/`to` (validated again server-side); granularity `hour` when the window is ≤ 48 h, else `day`. ATO overview range: the arguments' `range`, or for an explicit window the smallest of `24h|7d|30d` that covers it (the report labels the ATO window separately).
4. **Source plan** (fixed table in the package, `REPORT_SOURCES`): per requested section, its source tools and arguments. A source whose tool the principal does not satisfy (`satisfiesRequirement`, the same predicate as the pre-filter) is **not called**; its sections are listed as omitted with reason `permission` (and the missing permission key).

| Section      | Source tool(s) and arguments                                                                                                                                    |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `summary`    | values from the sources below (no own read)                                                                                                                     |
| `traffic`    | `reports_traffic { from, to, granularity }`                                                                                                                     |
| `threats`    | `reports_threats { from, to }`                                                                                                                                  |
| `domains`    | `reports_top_domains { from, to, limit: 10 }`                                                                                                                   |
| `delivery`   | `reports_delivery { from, to, granularity }`                                                                                                                    |
| `processing` | `reports_processing { from, to, granularity }`                                                                                                                  |
| `url_clicks` | `reports_url_clicks { from, to, granularity }`                                                                                                                  |
| `quarantine` | `quarantine_tools_summary { from, to }`                                                                                                                         |
| `ato`        | `ato_overview_overview { range }`, then (only when `monitoring.featureEnabled` and the mode is not `off`) `ato_accounts_list { sort: '-riskScore', limit: 10 }` |

5. **Reads:** each source is an internal loopback GET (`LoopbackDispatcher`, the turn's `authorization`, `x-eg-client-ip`, correlation `<turn correlation>.<seq>.<n>`, `x-eg-assistant-execution` = the native execution's public id, the existing per-call timeout `ASSISTANT_TOOL_TIMEOUT_MS`, body cap 1 MiB), concurrency 4, aborted with the turn. They count against the user's API rate limits like portal reads (≤ 10 `expensive` calls per report against `API_RATE_EXPENSIVE_PER_MINUTE`=60). A `401` ends the turn as for any tool (`assistant_session_expired`). Any other non-2xx omits the source's sections with reason `unavailable` and the coded error (e.g. `report_timeout`).
6. **Parse:** each 2xx body is parsed by the package's zod parser of that source (only the fields the report uses; `passthrough` for the rest). A parse failure omits the sections with reason `unexpected_response` (logged with the tool name, never the body).
7. **No data:** when every requested non-summary section is omitted, the execution fails `503 assistant_report_sources_unavailable` (no object, no row beyond the execution and its audit).
8. **Compose and render** (package, pure, deterministic): `buildReportModel(sources, { window, generatedAt, organizationName, sections })` → `renderReportHtml(model)` (D4). Bytes > `ASSISTANT_REPORT_MAX_HTML_BYTES` → the renderer drops the data appendix rows beyond 50 per table and retries once, else the execution fails `413 assistant_report_too_large`.
9. **Store** (D6): insert the `ai_chat_reports` row `pending` (own short transaction), `PutObject` (content type `text/html; charset=utf-8`, `ChecksumSHA256`), then in the execution's persist transaction: the row → `available` with `execution_id`, the execution row (`decision allowed`, `status succeeded`, `http_status 201`, `operation_id AssistantNative_reportGenerate`, `http_method POST`), the card, audit `assistant.tool_executed` and `assistant.report_generated`. A failed PutObject fails the execution (`502 assistant_report_storage_failed`) and the row becomes `failed`; a crash between the steps leaves a `pending` row that the retention job cleans (D7).
10. **Card** (`assistant-card/1`, new kind `report`, ≤ 64 KiB, no HTML): `{ kind: 'report', title, status: 'ok', report: { reportId, title, period: { from, to, granularity, atoRange }, generatedAt, sizeBytes, sections: string[], omitted: { section, reason, code? }[], figures: { label, value }[] (≤ 8) }, portalLinks: [{ label: 'Open full size', href: '/assistant/reports/<reportId>' }], refs: ['r<seq>.1'] }`.
11. **Envelope** (`assistant-tool-result/1`, `status 'ok'`, `httpStatus 201`, `returned 1`): `data = { ref: 'r<seq>.1', reportId, title, period, sections, omitted, figures }` where `figures` are the same numbers as the card (totals, threats, quarantined, delivery success rate, p95 time to verdict, held, pending approvals, high-risk accounts), plus the fixed note "The user sees the report in the chat. Numbers come from the platform's report APIs; cite them only from here." Refs: `r<seq>.1 → { resourceType: 'assistant_report', publicId: reportId }`.

### D4. Renderer (`packages/assistant/src/reports/*`, pure)

- **Files:** `types.ts` (`ReportModel`, `ReportSection`, `ReportFigure`, chart specs), `sources.ts` (`REPORT_SOURCES`, zod parsers per source, the section ↔ permission map), `model.ts` (`buildReportModel`), `svg.ts` (chart primitives), `html.ts` (`renderReportHtml`), `escape.ts` (`escapeHtml`, `fmtNumber`, `fmtPercent`, `fmtDuration`, `fmtUtc`), `palette.ts`, `index.ts`. `REPORT_TEMPLATE_VERSION = 'assistant-report/1'`.
- **Document:** `<!doctype html><html lang="en"><head><meta charset="utf-8"><meta name="viewport" content="width=device-width, initial-scale=1"><meta http-equiv="Content-Security-Policy" content="default-src 'none'; style-src 'unsafe-inline'; img-src data:"><meta name="referrer" content="no-referrer"><title>…</title><style>(constant)</style></head><body>…</body></html>`. Light theme with an explicit white background (email and iframe identical), print styles, a responsive two-column grid of chart cards (single column below 720 px), summary cards as a wrapping row, system font stack. The `<style>` block is a constant string (no data), tested byte-equal.
- **Charts (static SVG):** line/area (multi-series, stacked option, time x-axis with UTC labels `MMM d` or `HH:mm`, "nice" y ticks, legend), donut (≤ 8 slices, the rest "other", centre total, legend with counts and percentages), horizontal bar (≤ 10 bars, value labels), vertical histogram (bucket bounds formatted as durations). `viewBox` fixed per kind, coordinates rounded to 2 decimals, `role="img"` + `aria-labelledby` (`<title>` and `<desc>` with a one-line textual summary). Colors: a fixed 8-color categorical palette validated for contrast on white plus semantic colors for verdicts (clean neutral, threats warm); chosen by series index, never from data. Implementers load the `dataviz` skill for palette and mark guidance.
- **Escaping:** every data string (domain names, account addresses and display names, country codes, error codes, organization name) passes `sanitizeText` (C0/C1, bidi overrides, zero-width removed; capped: 253 domain, 120 address, 80 display name, 120 organization) and then `escapeHtml` (`& < > " '`) for text nodes and double-quoted attributes. Attribute names, tag names and style values are never data. Numbers pass `Number.isFinite` (else 0) before formatting. Formatting is locale-fixed (`en-US`) and time-zone-fixed (UTC) so output is deterministic.
- **Allow-list (test-enforced with `parse5`):** elements `html head meta title style body header main section footer h1 h2 h3 p div span strong small ul li table caption thead tbody tr th td figure figcaption svg g path rect circle line polyline polygon text tspan desc`; attributes `class id lang charset name content http-equiv role aria-label aria-labelledby aria-hidden scope colspan viewBox width height x y x1 y1 x2 y2 cx cy r d points fill stroke stroke-width stroke-dasharray text-anchor dominant-baseline font-size font-weight transform opacity xmlns focusable`; no `on*`, `href`, `src`, `xlink:href`, `style` attribute containing `url(`, no `<script>`, `<a>`, `<img>`, `<iframe>`, `<object>`, `<link>`, `<form>`, `<base>`.
- **Deterministic:** same inputs → same bytes (snapshot of a fixture report); `generatedAt` is an input.

### D5. `report_send_email`: proposal, recipient rule, limits, confirm (ADR-0093 amendment AI-R)

**Proposal** (inside a turn; D5 steps 1–6 unchanged, then `NativeToolsService.prepareProposal` instead of the precondition read; the generic proposer then builds digest, token, summary and stores the confirmation exactly as AI-2 D1 steps 7–11):

1. **Report:** `reportId` resolved (ref or UUID; omitted → the latest `available` report of this conversation). It must belong to the owner (organization, user, override id) **and** this conversation, else proposal failure `404 assistant_report_not_found`; `purged` → `410 assistant_report_purged`; size > `ASSISTANT_REPORT_MAX_HTML_BYTES` → `413 assistant_report_too_large`.
2. **Recipient** (`classifyRecipient`, pure function in the package; lookups by the api's `RecipientDirectoryRepository`, writer, organization of the scope): normalize (trim, lower-case the domain, keep the local part as typed for display, compare case-insensitively); `to` omitted → the user's own address. Classes in this order:
   - `self`: the principal's own `users.email` (email verified, not deleted);
   - `member`: a user of the scope's organization with `status = active`, `email_verified_at IS NOT NULL`, `deleted_at IS NULL` (invited, disabled and locked users are refused);
   - `domain`: the address's domain equals (exactly; no subdomain match) the `name` of a domain of the organization with `status IN ('verified','active')` and `deleted_at IS NULL` (pending, failed, disabled and suspended are refused);
   - otherwise **refused**: `denied_guard`, guard `report_recipient_not_allowed`, message "Reports can be emailed only to your own address, to active users of your organization or to addresses in its verified domains." No confirmation is stored; audit `assistant.tool_denied` with `recipientDomain` and `recipientSha256` (never the full address of a refused recipient).
     Under a platform override the organization is the override's target; `self` is the operator's own address.
3. **Limits** (UTC day, counted on `ai_chat_report_deliveries`): user ≥ `ASSISTANT_REPORT_EMAILS_PER_USER_PER_DAY` or tenant ≥ `ASSISTANT_REPORT_EMAILS_PER_TENANT_PER_DAY` → `denied_budget`, code `assistant_report_email_limit` (`scope: user|tenant`). Pending confirmations do not reserve capacity (re-checked at confirm).
4. **Stored request** `{ method: 'POST', path: 'native:report_send_email', body: { reportId, to: <normalized address> } }`; **preconditions** `{ stateDigest, rowVersion: null }` with `stateDigest = sha256(canonicalJson({ reportId, sha256, status: 'available', recipientKind }))`; risk `medium`, `requiresReauth false`.
5. **Summary** (`assistant-confirmation/1`, template `report_send_email` in `impact.ts`): title "Email security report"; action "Sends the security report as an HTML email to <address>."; target: Report (title, period), Recipient (address, "your own address" / "user of your organization" / "address in verified domain <domain>"), Size; impact: "The email leaves the platform through the notification mailer; the recipient can forward it.", "The same HTML is attached as a file."; warnings: "Emails cannot be recalled after sending.", "<n> of <limit> report emails left today for you (<m> for your organization)."; `reversible false`; `portalRoute /assistant/reports/<id>`; request `POST native:report_send_email`.

**Confirm** (AI-2 D2 steps 1–11 unchanged: owner, session family, status, expiry, token, digest, tool still enabled and permitted, availability, conversation lock, atomic `pending → executing`):

- Step 12 (re-read) for a native spec: `NativeToolsService.readState` recomputes the report state and the recipient class with current data; a different `stateDigest` (report purged or replaced, recipient no longer allowed or of another class) → row `failed`, `409 assistant_confirmation_state_changed`; a recipient now refused → row `failed`, `403 assistant_action_not_allowed`.
- Step 13 (execute) for a native write: `ToolExecutorService.run` calls `NativeToolsService.execute` instead of the loopback; inside the execution's persist transaction (before `afterPersist`): `SELECT … FROM ai_chat_settings WHERE organization_id = ? FOR UPDATE` (serializes the tenant's sends), recount the user and tenant deliveries of the UTC day (limit reached → outcome `failed`, `httpStatus 429`, `assistant_report_email_limit`, nothing written), insert the `ai_chat_report_deliveries` row (`queued`, `confirmation_id` unique, the normalized address, its SHA-256, the class), insert the outbox row `assistant.report.email_requested.v1` (eventId = the delivery public id), audit `assistant.report_email_requested`; outcome `succeeded`, `httpStatus 202`, card kind `message` "Report email queued to <address>". Then AI-2 step 14 marks the confirmation `executed` (or `failed` for the 429) and audits it.
- The confirmation's idempotency comes from the state machine (one confirmation → at most one delivery: unique `confirmation_id`); no `Idempotency-Key` is used (no loopback).
- Action update to the model (next turn, `updates.ts`): "report_send_email (call r<n>): the user confirmed it; the report email was queued for <address> (HTTP 202)." / the existing cancelled, expired and failed lines.

### D6. Storage (ADR-0094 amendment AI-R)

- Object key `org/<organizationId>/assistant/report/<yyyy>/<mm>/<dd>/<reportPublicId>.html` in `S3_BUCKET_MAIL` (UTC date of generation; `organizationId` the internal id, as every mail-bucket key); checked with the `isKeyOf` pattern before every get/delete; never returned to a client, never logged.
- `ReportObjectStore` (assistant module): `put(key, bytes, sha256)`, `get(key, maxBytes)` (stream read bounded by `maxBytes + 1`, SHA-256 verified), `delete(key)` (the mail bucket is versioned: every version and delete marker of exactly the key is listed with `ListObjectVersions` and deleted by `VersionId`, so no noncurrent copy of the HTML remains; a missing object counts as deleted).
- The api serves stored HTML **only inside JSON** (`GET /assistant/reports/{reportId}` → `{ report, html }`), so navigating to the URL never renders HTML on the portal or api origin; `Cache-Control: no-store`.
- MySQL holds metadata only (I5): window, sections, omitted reasons, figures, size, SHA-256, key, statuses, delivery recipients.

### D7. Retention and purge

- **Content purge of a conversation** (retention job at `purge_after`, and immediately on `DELETE /assistant/conversations/{id}`), in the same transaction that purges the conversation content: its reports `available|pending|failed → purged` (`purged_at`), deliveries' `recipient_address = NULL`, and `queued` deliveries → `failed` (`assistant_report_purged`). After the commit the job deletes the objects of `purged` reports with `object_deleted_at IS NULL` in batches (`object_deleted_at = now`, `object_key = NULL`); the delete route attempts its conversation's objects inline (best effort; the job catches up).
- **Sweeps** in the same job: `pending` reports older than 1 hour → object deleted if present, row `failed` (`assistant_report_abandoned`); `queued` deliveries older than 25 hours (beyond the notification queue's 24 h retry age) → `failed` (`assistant_report_email_timeout`).
- **Hard delete** after `ASSISTANT_EXECUTION_RETENTION_DAYS`: report and delivery rows go with their conversation (the content purge, which always comes first, already deleted the objects; the hard-delete step skips a conversation that still has a report with `object_deleted_at IS NULL` and deletes those objects first).
- **Organization purge** (`AssistantTenantDataRepository`): new first steps `ai_chat_report_deliveries`, then `ai_chat_reports` (each batch: delete its objects, then its rows), then the existing order. The count object `reportObjects` is returned like DLP's `evidenceObjects`.
- The copy in a recipient's mailbox is outside the platform's control (stated in the confirmation warnings and in AI_SECURITY_STANDARDS.md).

### D8. Email delivery (notification-worker)

- **Event** `assistant.report.email_requested.v1` (§4.3), consumed from `email.notifications` (ledger `notification-worker.policy`, at least once), handler `AssistantReportEmailHandler` added to `dispatchNotification` and `NOTIFICATION_EVENT_TYPES`.
- **Handler**, inside the consumer's transaction, reads on the writer scoped to the envelope's organization: the delivery by public id (missing → `not_applicable`, nothing sent: the organization or conversation was purged), its report and the organization name. `status ≠ queued` → nothing (redelivery).
