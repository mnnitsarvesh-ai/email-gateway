## 0. Scope in one paragraph

A **late signal** — a sandbox risk revision of a message after `copy_scanned.v1`, a late URL dynamic-inspection verdict, a new threat-intelligence indicator or published malware hash, a campaign expansion, an analyst's report verdict or an admin decision — becomes a **clawback** (`api_clawbacks`): a per-organization search over the tenant's recorded API-mode copies by Internet Message-ID, attachment SHA-256, URL (identity hash) or sender + subject + time window, materialized into per-copy **targets** (`api_clawback_targets`) and executed **only through the API-2 remediation actions** (`api_remediation_actions` rows run by the `remediate` role: same budgets, `Retry-After` pause, back-off, audit, quarantine entries, restore). Automatic signals re-decide each copy through the tenant's **remediation policy** with the signal's facts (detect-only, pause and hard-delete rules unchanged); admins search, preview the hit list and **purge** (quarantine folder, Junk, soft delete; hard delete portal-only behind the platform setting) with a **second approver** above 50 distinct mailboxes (P2, configurable), with progress, per-mailbox results, audit and bulk restore. **Internal (east-west) mail** seen in the journal is recorded per recipient mailbox (direction `internal`) and remediated the same way; outbound-only journal copies are recognised and never recorded or delivered. A per-tenant **report mailbox** (P4: no add-in) turns user-forwarded mail into **reports** (`api_user_reports`): parsed (forward-as-attachment and inline forwards), the original identified and scanned, triaged in the portal, optionally clawed back across mailboxes, with **feedback e-mails** to the reporter through the notification-worker. The coverage page, metrics, alerts and the AI report gain clawback and report figures. The assistant gets read tools for coverage, remediation history, clawbacks and reports, and **confirmed write tools** for remediation, restore and purge (bulk purge high risk: password + TOTP; hard delete portal-only). §13 is the end-to-end program acceptance.

### 1.2 Gaps and conflicts found

1. **ADR-0101 (3): hard delete "is never manual or from the assistant"; R-I2.** The brief allows hard delete in a purge ("portal-only and behind the existing platform setting"). → ADR-0103 supersedes ADR-0101 (3) in part: an admin **purge** may use hard delete when `API_MODE_HARD_DELETE_ENABLED=true`, through a separate portal-only operation, always with a second approver; manual single-copy remediation and the assistant still never hard-delete; no default or preset contains it.
2. **ADR-0101 (4) / R-I3: inline-authority copies are never remediated automatically.** For a hybrid copy the inline decision is stale once a late signal arrives (that is the value of post-delivery protection). → ADR-0103: clawback decisions evaluate hybrid copies with verdict authority `copy` (the signal supersedes the inline decision); the first-time copy decision (R4) is unchanged.
3. **ADR-0100 / note 35 D7.4: API-1 records inbound recipients only.** → ADR-0104 supersedes in part: internal recipients are recorded (`direction = internal`) when the organization's internal-mail setting is on (default on).
4. **R4 / `DECIDED_STATES`: a copy already `pending`/`remediated`/`restored` is never re-decided** (API2-15). → Clawback targets use their own planning rule (C5.3: escalation only, restore-after-signal check); the copies-transaction decision stays as it is.
5. **No consumer of late verdicts and no event for them.** Risk revision 1 and URL dynamic verdicts change nothing outside their rows. → `mail.threat.late_signal.v1` from the email-worker, bound to `email.mailbox` (topology v18).
6. **`quarantine_approval_requests` requires a quarantine entry** (NOT NULL FK, every reader assumes it; 35 references in five services). → Purge approvals keep the Q14 rules but live on the clawback row (§6 records the rejected table extension).
7. **The notification event set has no end-user message other than quarantine notices.** → New event `mail.report.feedback_requested.v1` on the existing notification path (binding v18).
8. **`api_remediation_actions.trigger` has no value for system clawbacks or admin purges**, and an action row cannot point to its clawback. → Enum values `clawback`, `purge`; column `clawback_id`.
9. **Re-deciding a copy whose `action_key` row exists** (a `skipped`/`simulated`/`failed` policy row of the same action and generation) collides on the unique key. → The clawback re-arms that row exactly as the api does (note 36 §14.4 deviation 4): status `pending`, trigger and `clawback_id` updated, attempts cleared, decision replaced.
10. **`subject_key` normalization lives in the api only.** The mailbox-worker parses inline-forward subjects. → A parity copy in `@email-gateway/mailbox-api` with the api's test vectors (C4.4).
11. **API-1's protection-mode writes are bound to the wizard and MX checks (PO-D1).** → They stay portal-only with a new reason; every other API-mode write becomes a tool (C15).

## 2. Program position and invariants

Note 35 N1–N9 (N1 as amended by ADR-0102) and note 36 R-I1–R-I6 (R-I2 and R-I3 as amended by ADR-0103, §1.2 items 1–2) hold. API-3 adds:

- **C-I1 One action engine.** A clawback never calls a provider: it writes `api_remediation_actions` rows; the `remediate` role executes them with the per-connection budgets, the shared throttle gate and the `Retry-After` pause (N7, R5). The `clawback` and `reports` roles make no provider call.
- **C-I2 The hit list is frozen.** What an admin previews is what is purged: targets are materialized once (`api_clawback_targets`); a submit, approval or restore acts on those rows only, never on a re-run search.
- **C-I3 Never weaken by clawback.** A clawback only escalates (C5.3); it never replaces a stronger remediation, never restores, and never touches a copy the tenant restored after the signal.
- **C-I4 Two people above the threshold.** A purge whose eligible targets span more than the organization's threshold of distinct mailboxes (default 50), any hard-delete purge, and any automatic clawback above its cap need a second user holding `remediation:purge` who is not the requester; API keys and the assistant never approve on their own (an approval through chat is a high-risk confirmed write of the approver's own session).
- **C-I5 Reports never act by themselves.** A report creates no remediation; only an analyst's decision creates a clawback (which then follows C-I4). Report-mailbox copies are never remediated.
- **C-I6 Content-free state.** Clawback criteria store hashes, normalized keys (`subject_key` ≤ 128, `message_id` hash), sender addresses and time windows; reports store addresses, hashes, keys and codes; EML bytes stay in S3 (N4); analyst notes and reasons are operator text marked untrusted.
- **C-I7 Tenant from trusted context.** The api takes the organization from the principal (foreign ids `404`); signals carry the organization in the envelope and every worker read echo-checks it; a platform indicator is fanned out per API-active organization by the worker, never by a client value.

## 4. Decisions

### C1. Where things live (ADR-0103, ADR-0104)

- **email-worker** emits `mail.threat.late_signal.v1` (C2.1). **api** creates admin/campaign/report clawbacks, submits, approves, cancels, requests restores, triages reports, manages settings and report mailboxes. **mailbox-worker**: the `copies` role also consumes late signals (same queue `email.mailbox`, same ledger consumer `mailbox-worker.copies`, new event type) and records internal copies and report intake; the new **`clawback`** role materializes searches, plans and queues targets, reconciles progress, runs bulk restores, expires approvals and (leader) sweeps threat intelligence; the new **`reports`** role parses reports, identifies and ingests originals and queues acknowledgements; the existing **`remediate`** role executes every action. **notification-worker** renders reporter feedback and the two new alert kinds.
- `MAILBOX_WORKER_ROLES` default becomes `copies,feeds,inventory,health,remediate,clawback,reports`; `clawback` and `reports` are not provider-calling roles. Claim loops follow `remediation/claims.ts` (`FOR UPDATE SKIP LOCKED`, leases, CAS on `row_version`).

### C2. Signals

**C2.1 Late verdicts (email-worker, in the existing transactions; content-free outbox row, `aggregate_type = 'message'`).**

- _Sandbox revision_ (`sandbox-finalizer.ts` → `scoreRiskRevision`): when risk revision 1 of a round is written and its `level` is higher than revision 0's, or its risk verdict is a threat verdict (`malware`, `phishing`, `suspicious`, `bec`) different from revision 0's, write `mail.threat.late_signal.v1` `{ kind: 'sandbox_revision', messageId, receivedAt, scanId, revision: 1, verdict, level, hardBlocks (≤ 9 ids), attachmentSha256 (the hashes of the round's sandbox submissions whose verdict is `malicious`/`suspicious`, ≤ 20), urlSha256: [], signalAt }`. Emitted for every ingest source (gateway messages of hybrid tenants are clawed back through their journal copies' Message-ID).
- _URL dynamic verdict_ (`url-results.ts`): when an inspection is updated to verdict `malicious` or `suspicious` and the message's round is no longer `running`, write `{ kind: 'url_dynamic', messageId, receivedAt, scanId, revision: null, verdict: 'phishing' for `url.dynamic_phishing`/`malicious` else 'suspicious', level: 'critical' | 'high', hardBlocks: malicious ? ['hb.clawback.url'] : [], attachmentSha256: [], urlSha256: [inspection url sha256], signalAt }`.
- The mailbox-worker handler (copies role, `processOnce`): organization not API-active → ack (ledger only, metric `api_mode_late_signals_total{kind,result="not_active"}`); else `INSERT IGNORE` an `api_clawbacks` row (`trigger = late_verdict`, `signal_key` C2.5, `decision_mode = policy`, signal facts C3, criteria C4 from the message's Message-ID hash plus the payload hashes, window `[receivedAt − lookback, now]`, status `searching` or — when `auto_clawback = off` — not created, metric `skipped_off`).

**C2.2 Threat intelligence (mailbox-worker `clawback` role leader, every `API_MODE_CLAWBACK_TI_INTERVAL_SECONDS` 60).** Reads `threat_indicators` and `malware_signatures` created after the stored cursor (`api_mode_cursors`, `(created_at, id)` keyset, batch `API_MODE_CLAWBACK_TI_BATCH` 100, never older than the lookback on first run). Eligible indicators: not expired; types `url` (identity hash), `domain`, `file_sha256`, `email`; severity `high`/`critical`; `confidence ≥ ti_min_confidence` of the organization; `ip` never. Malware signatures are eligible as `file_sha256` with severity `high`. Platform rows (`organization_id` NULL) apply to every organization with API mode active; organization rows only to their organization. Per (indicator, organization) the worker runs the C4 search **inline** (index lookups only) and creates an `api_clawbacks` row (`trigger = threat_intel`, status `ready`/`review_required`/`queued` per C5.2) only when there is at least one target — no row for organizations without matches. The cursor advances after each batch commits.

**C2.3 Admin decision.** `POST /api-mode/clawbacks` (C14) with criteria or a seed detection: `trigger = admin`, status `searching`.

**C2.4 Campaign.** A clawback created from a seed (detection, report or an existing clawback's first target) with `expand: { attachments, urls, senderSubjectHours }` adds the seed message's attachment hashes (≤ 20), URL hashes (≤ 20) and its sender + `subject_key` within ±`senderSubjectHours` (1..168, default 72) to the criteria; `trigger = campaign`. `signal.refs.campaignRef` (string ≤ 64) is reserved for ATP-4 campaign entities and refused today (zod issue `unsupported_until_atp4`).

**C2.5 Signal keys** (hex SHA-256 of a NUL-separated tuple, version prefix `api-clawback-signal/1`): late verdict `(…, 'late', messageId, receivedAt, kind, revision ?? urlSha256)`; TI `(…, 'ti', 'threat_indicators'|'malware_signatures', rowId)`. One clawback per organization and signal (UNIQUE), so redelivery and sweep replays create nothing new.

### C3. Signal facts and re-decision through the remediation policy

**C3.1 Facts per signal** (API3-6; pure `signalFacts(signal)` in mailbox-api):

| Signal                              | verdict                                                                                                           | level                                                | hardBlocks                                                             |
| ----------------------------------- | ----------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------- | ---------------------------------------------------------------------- |
| Sandbox revision                    | revision's risk verdict                                                                                           | revision's level                                     | revision's hard blocks                                                 |
| URL dynamic                         | `phishing` (malicious) / `suspicious`                                                                             | `critical` / `high`                                  | `hb.clawback.url` / none                                               |
| TI `file_sha256`, malware signature | `malware`                                                                                                         | from severity (`critical`→`critical`, `high`→`high`) | `hb.clawback.threat_intel` when severity `critical` or confidence ≥ 90 |
| TI `url` / `domain`                 | category `malware`/`c2` → `malware`; `phishing`/`scam` → `phishing`; `spam` → `spam`; NULL/`other` → `suspicious` | from severity                                        | as above                                                               |
| TI `email` (sender)                 | as `url`                                                                                                          | from severity                                        | as above                                                               |
| Report analyst verdict `malicious`  | the original's scan verdict when it is `malware`/`phishing`/`bec`, else `phishing`                                | `critical`                                           | `hb.clawback.analyst`                                                  |
| Admin / campaign (policy mode)      | analyst-chosen verdict (`malware`/`phishing`/`bec`/`suspicious`/`spam`)                                           | chosen level (default `critical`)                    | `hb.clawback.analyst` when level `critical`                            |

**C3.2 Policy mode** (automatic signals, and admin/report/campaign clawbacks submitted with `mode: policy`): each target runs `decideRemediation` with `copy = { status: 'scanned', verdict: facts.verdict, riskScore: max(copy score, facts score), verdictAuthority: 'copy' }`, `risk = { level, hardBlocks }`, the copy's real context (grant, pause, domain effective mode, mailbox status, internal-mail setting) and the effective policy of the copy's mailbox (R2.6). The decision record (R2.4) gains `source: 'clawback'` and `clawbackId` in `notes`. `none` → target `skipped policy_none`; `skip` → `skipped <reason>`; simulated → `simulated`; `act` → planned action (then C5.3). This re-uses `RemediationDecider`'s context reads (WP3 extracts them into a function used by both).

**C3.3 Copy verdict update.** For a late verdict whose own message is the copy's registry message, the copy row's `verdict`/`risk_score` are raised to the revision's values when worse (`verdict_revision + 1`), so detections show the late verdict; other copies keep their own scan verdict (their targets reference the clawback).

**C3.4 Explicit mode** (admin purge): `planned_action = action`; still skipped for `no_mailbox_access`, `out_of_scope` (domain not `api`/`hybrid`), `mailbox_inactive` (`disabled`/`deleted`), `report_mailbox`, `hard_delete_disabled` (setting off at execution); a paused connection does **not** stop an admin purge (as admin rows in R5.1); automatic (`clawback` trigger) rows wait while paused.

### C4. Criteria and search (materialization)

**C4.1 Document `api-clawback-criteria/1`** (strict zod in mailbox-api): `{ v: 1, window: { from, to } (to − from ≤ API_MODE_CLAWBACK_MAX_WINDOW_DAYS 31; from ≥ now − 186 days, the copies retention), keys: { messageIdHashes?: hex64[1..10], attachmentSha256?: hex64[1..20], urlSha256?: hex64[1..20], urlDomains?: domain[1..5] (TI only), senders?: address[1..5] (TI only), senderDomains?: domain[1..5] (TI only), senderSubject?: { sender: address, subjectKey: string(1..128) } }, directions: ('inbound'|'internal')[1..2], includeReportMailboxes: false }` — at least one key; `senderSubject` needs a window ≤ 7 days unless it comes from a campaign seed; keys combine with OR (`match_keys` records which matched).

**C4.2 Lookups** (organization first in every index; every query also bounds `received_at` to the window for partition pruning): Message-ID → `api_message_copies (organization_id, message_id_hash)`; attachment → `email_attachments (organization_id, sha256, received_at)` → `(message_id, received_at)` → copies by UNIQUE `(message_id, received_at, mailbox_id)`; URL → `message_urls (organization_id, url_sha256)`; URL domain → `message_urls (organization_id, registrable_domain)`; sender → `email_messages (organization_id, header_from …)` and `(organization_id, envelope_from …)`; sender domain → `sender_domain`; sender + subject → `header_from` index filtered by `subject_key`. Only copies (never gateway-only messages) become targets; hybrid gateway messages are reached through their copies' Message-ID. Copies of report mailboxes are excluded (C9.3), as are copies whose mailbox is `deleted`.

**C4.3 Limits.** More than `API_MODE_CLAWBACK_MAX_TARGETS` (20 000) matches → status `too_broad` (no targets kept; the admin narrows the criteria). Zero → `no_match`. Materialization runs in pages of 1 000 inserts per transaction (`INSERT IGNORE` on the target unique key), so a lease loss repeats nothing; counts are written at the end.

**C4.4 Normalization.** The api normalizes admin input: Message-ID → `copyMessageIdHash(organizationId, id)`; subject → the explorer's `normalizeSubjectKey` (`apps/api/src/modules/messages/domain/search-keys.ts`); URL → `normalizeUrl(...).url.sha256`; addresses lower-cased. The mailbox-worker (inline-forward reports) uses a parity copy `subjectKeyOf`/`messageIdKeyOf` in `@email-gateway/mailbox-api` `clawback/search-keys.ts` with the same table vectors as the api's tests.

### C5. Clawback lifecycle, planning and execution

**C5.1 States.**

```text
searching → no_match | too_broad | failed
searching → ready                     (admin/campaign/report: preview; waits for submit)
searching → review_required           (automatic, eligible mailboxes > auto_max_mailboxes or auto_clawback = review)
searching → queued                    (automatic within the cap)
ready | review_required → pending_approval (submit; C6) | queued (submit below threshold)
pending_approval → queued (approved) | denied | expired | cancelled
queued → running → completed | completed_with_errors
ready | review_required | pending_approval | queued | running → cancelled (cancel)
```

**C5.2 Eligibility at materialization.** For each target the worker computes a preliminary status: `skipped` with `no_mailbox_access`, `out_of_scope`, `mailbox_inactive`, `report_mailbox`, `already_remediated` / `remediation_in_progress` (C5.3), else `matched`. `targets_eligible` / `mailboxes_eligible` count `matched` rows (distinct mailbox ids). Automatic clawbacks are then planned immediately (C3.2) and, within the cap, `queued`.

**C5.3 Target planning** (pure `planClawbackTarget` in mailbox-api; input: the copy's `remediation_state`, `remediation_action`, the last succeeded restore time, the clawback's `signal_at`, the decided or explicit action):

- strength order `tag < move_junk < move_quarantine < soft_delete < hard_delete`;
- copy `pending` (an action in flight) → `skipped remediation_in_progress`;
- copy `remediated` with an action of equal or higher strength → `skipped already_remediated`; lower (e.g. `tag`) → act (escalation; the earlier tag stays, C-I3);
- copy `restored` and its restore completed after `signal_at` → `skipped restored_after_signal` (a person reviewed it later); otherwise act;
- else act. Hard delete only in explicit mode.

**C5.4 Queueing** (`queued`/`running`): per tick up to `API_MODE_CLAWBACK_QUEUE_BATCH` (500) targets per clawback, never more than `API_MODE_CLAWBACK_MAX_PENDING_PER_CONNECTION` (1 000) pending clawback/purge actions per connection (so policy actions of the tenant keep flowing). Per target, in one transaction: lock the copy row (R5.2 lock order), re-plan (state may have changed), `INSERT IGNORE` the action (`action_key` R-I4 with the copy's current generation, `trigger = clawback` for automatic or `purge` for admin/report/campaign, `clawback_id`, decision record, `requested_by_*` of the submitter, `next_attempt_at = now`) or **re-arm** an existing `skipped`/`simulated`/`failed`/`cancelled` row of the same key (status `pending`, trigger, `clawback_id`, decision, attempts/locate attempts/lease/errors cleared, `row_version + 1`); an existing `pending`/`in_progress`/`succeeded` row → target `skipped remediation_in_progress`/`already_remediated` linked to it; copy `remediation_state = pending`, `remediation_action`, `last_action_id`; target `queued` with `action_id`. Status `running` after the first batch.

**C5.5 Reconcile** (every `API_MODE_CLAWBACK_TICK_MS` 5 000): targets `queued` whose action is terminal → `succeeded` (incl. `already_in_target`), `failed` (action `reason_code`), `cancelled`; counts recomputed by `GROUP BY status`; no `queued`/`matched` target left → `completed` (no failure) or `completed_with_errors`; one system audit row `api_mode.clawback_completed` `{ clawbackId, trigger, counts }`; counters `clawback_targets_*`. Mailbox quarantine entries come from the API-2 path unchanged (R9.1), with `reason` = the quarantine reason of the signal verdict (explicit purge of a copy without a threat verdict → `manual`) and the explanation template "Removed from the mailbox by clawback <public id> (<trigger>)".

**C5.6 Cancel.** The api sets `cancel_requested_at` (status `cancelled` immediately when nothing is queued yet); the worker then cancels every `pending` action with that `clawback_id` (`cancelled`, copy state recomputed by the R5.2 rule), marks unqueued targets `cancelled` and lets `in_progress` actions finish (their outcome is reconciled).

**C5.7 Execution.** The `remediate` role runs these rows like any other (R5); R5.1's paused-connection rule applies to `trigger = clawback` like `policy`; `purge` proceeds like `admin`. A `hard_delete` row is re-checked against `API_MODE_HARD_DELETE_ENABLED` at execution (note 36 §14.3 deviation 3).

### C6. Approval (P2; ADR-0103)

- **When:** at submit, `requires_approval` = `mailboxes_eligible > purge_approval_mailboxes` (`mailbox_threshold`), or `action = hard_delete` (`hard_delete`), or the clawback was `review_required` because of the auto cap (`auto_cap`). Otherwise `queued` directly.
- **Separation of duties on the threshold (review fix, §16.2):** the settings PUT records who raised `purge_approval_mailboxes` and the value before the raise (`purge_approval_raised_by` principal key, `purge_approval_before_raise`; migration 46); a submit by that principal is decided against `min(stored, before_raise)` (`effectivePurgeThreshold`), so a raise only takes effect for other people. A further raise by the same principal keeps their earliest value; a raise by someone else starts a new record; lowering to the recorded value or below clears it (`nextPurgeThresholdRaise`).
- **Rules** (5.3 Q14, pure `decidePurgeApproval` in mailbox-api mirroring `checkApprover`): approver is a user principal (API keys refused `api_mode_purge_approval_forbidden` reason `api_key`), holds `remediation:purge` (`missing_permission`), is not the requester or submitter (`requester`), the request is `pending` and not expired (`api_mode_purge_approval_not_pending`). Separation is by user id; a user who is a target mailbox owner may approve (no recipient rule: purges are tenant-wide operations).
- **Storage:** on the clawback row (`approval_*`, `approver_permissions_hash`), CAS on `row_version`; TTL `API_MODE_PURGE_APPROVAL_TTL_HOURS` (72). Expiry by the `clawback` role (`pending → expired`, status `expired`, audit).
- **Notification:** at submit the api writes `notification.alert_requested.v1` kind `api_mode_purge_approval` (refs `clawbackId`, severity `medium`, `high` for hard delete; recipients holding `remediation:purge`; throttled per clawback via `notification_alert_windows`); automatic clawbacks entering `review_required` write the same kind (`severity: 'medium'`).
- **Audit:** `api_mode.clawback_submitted`, `api_mode.clawback_approval_requested`, `api_mode.clawback_approved`, `api_mode.clawback_denied` (ids, counts, codes, the approver's permission hash).

### C7. Restore of a clawback (reversible where the provider allows it)

`POST /api-mode/clawbacks/{id}/restore` (`remediation:purge` + `quarantine:release`, reason) on `completed`/`completed_with_errors`/`cancelled` clawbacks sets `restore_status = requested`. The `clawback` role processes `succeeded` targets in batches (≤ 500 per tick): `tag` → queue `remove_tag`; entry-creating actions (quarantine folder, Junk, soft delete) → run `decideMailboxRestore` (operator mode) on the mailbox entry: `release` → the R10.2 write sequence (release log `pending` mode `operator`, entry `releasing`, `restore_inbox` action with `trigger = release`, `release_log_id`, `reverses_action_id`, requested by the restoring user), `approval_required` → target `restore_skipped approval_required` (released individually through the quarantine page and its approvals), refused → `restore_skipped refused`; `hard_delete` (Graph) → `restore_skipped not_reversible`; Google hard delete (Trash fallback, entry container `deleted_items`) is restored like a soft delete; entry no longer `held` → `restore_skipped entry_<state>`. Reconcile as C5.5 into `restores_*` and `restore_status` `completed`/`completed_with_errors`; audit `api_mode.clawback_restore_requested` / `_restore_completed`. A restore requested again from `completed_with_errors` retries the failures: when the worker moves `requested → running` it returns the clawback's `failed` targets to `none` (clearing `restore_action_id` and `restore_reason_code`) in the same transaction; the reversal keeps its action key and the failed action row is re-armed (review fix, §16.2).

### C8. Internal (east-west) mail (ADR-0104)

1. Copies handler, journal path: a recipient classified `internal` (sender and recipient org-side, D7.4) is **recorded** with `direction = internal` when `api_mode_org_settings.internal_mail_enabled` (default on); otherwise counted `skipped_internal` as before. Counter `internal_copies`; metric result `recorded_internal`.
2. Outbound-only journal messages (no recipient on an API-side organization domain, sender org-side) → result `outbound_only` (metric only; no copy, no mailbox discovery); mixed messages record their internal recipients only. The sender is never a target (journal recipients only; the locate step already ignores Sent Items, R5.3).
3. Dedupe unchanged: (mailbox, Message-ID hash) across journal and feed copies, so a second journal report of the same internal message (or the recipient's Inbox feed copy) is a duplicate (`seen_journal`/`seen_api`), never a second row.
4. Never delivered: journal copies stay `journaled` (N1); the stack suite asserts no delivery attempt and no `mail.delivery.*` event for internal copies.
5. Remediation: the same R4 decision. `decideRemediation` gains context `internalMailEnabled` and the copy's `direction`; step (4b) after `out_of_scope`: `direction = internal` and not enabled → `skip internal_mail_disabled` (covers feed copies, which API-1/API-2 already recorded and decided). Hybrid internal mail has no inline link (it never crossed the MX), so it is remediated with copy authority.
6. Detections list/filter gain `direction`; overview `internal` figures.

### C9. Report mailbox (P4)

1. **Designation:** `PUT /api-mode/mailboxes/{mailboxId}/report-mailbox` `{ enabled, reason }` (`remediation:write`): the mailbox must belong to the organization, have status `active`, `discovered` or `disabled` (shared mailboxes are often disabled accounts), and its domain must be effective `api`/`hybrid`; at most `API_MODE_REPORT_MAILBOXES_MAX` (5) per organization (`409 api_mode_report_mailbox_limit`). An alias reaches the mailbox through `api_mailbox_addresses`. A mailbox not yet known can be added by address through `POST /api-mode/report-mailboxes` `{ address, reason }` (resolved or discovered under the domain's API connection; `422 api_mode_report_address_out_of_scope` otherwise). Audit `api_mode.report_mailbox_updated`.
2. **Intake (copies handler, same ledger transaction):** a recorded copy (journal or feed) whose mailbox has `report_mailbox = 1` is recorded whatever its direction and the internal-mail setting, gets **no remediation decision** (C-I5), and `INSERT IGNORE`s an `api_user_reports` row (`status = received`, `reporter_address` from header From addr-spec else envelope, `reported_at`, `next_attempt_at = now`); counter `reports_received`. A duplicate copy creates nothing.
3. Report-mailbox copies stay in coverage (they are mailboxes) but are excluded from clawback targets (evidence is kept for triage).

### C10. Report parsing and identification (`reports` role)

1. **Claim** `received` rows (lease 120 s, batch 20). **Reporter checks:** reporter address not on an organization domain → `rejected external_reporter` (no feedback); a report mailbox address → `rejected loop`; header `Auto-Submitted` other than `no` or a `Precedence: bulk|auto_reply` header → `rejected auto_submitted`; more than `API_MODE_REPORTS_PER_REPORTER_PER_HOUR` (30) → `rejected rate_limited`. Reporter mailbox and user resolved by address (organization echo).
2. **Identification** (pure `extractReportedMessage(bytes, limits)` in mailbox-api `reports/`; reads the report copy's EML from S3, bounded `API_MODE_REPORT_MAX_BYTES` 25 MiB, depth ≤ 4, parts ≤ 200):
   - **attachment**: the first `message/rfc822` part (or `application/octet-stream`/`application/eml` whose filename ends `.eml`), transfer-decoded (7bit/8bit/binary/base64/quoted-printable) and ≤ `API_MODE_MAX_MESSAGE_BYTES`; its top-level headers give Message-ID, From, Date, Subject; count of further attached messages recorded (`extraOriginals`, only the first is used);
   - **inline**: the first `text/plain` part (or `text/html` stripped to text) contains a forward separator (`-----Original Message-----`, `---------- Forwarded message ---------`, `Begin forwarded message:`, `-------- Original Message --------`, localized variants listed in the code) followed within 20 lines by `From:` and `Subject:` (and optionally `Date:`/`Sent:` and `Message-ID:`); values parsed (From addr-spec, RFC 5322 or common `Sent:` date formats);
   - **unsupported**: an Outlook `.msg` (`application/vnd.ms-outlook`) attachment; **none** otherwise.
   - `original` document (`api-report-original/1`): `messageIdHash`, `sender`, `subjectKey` (C4.4), `date`, `attachmentSha256` (≤ 20, from the decoded original's attachments when attached; else from the report message's own `email_attachments` rows), `urlSha256` (≤ 50, from the report message's `message_urls`), `extraOriginals`. Never bodies.
3. **Original lookup** (organization only): by `messageIdHash` in the reporter's mailbox copies first, then tenant-wide (most recent); else (inline without Message-ID) by `senderSubject` within ±72 h of `date` in the reporter's mailbox copies. Found → `original_copy_*`, `original_message_*` = that copy's registry message, scan facts from its latest risk row → `pending_triage`.
4. **Ingest for scanning** (attachment present, original not found): the decoded original is written to S3 (`org/<org>/eml/...`, existing `EmlSink`) and committed as a registry message by a repository modelled on `MailboxCopyRepository.commit` **without a copy row and without a dedupe claim**: ingest key `v2:rpt:` + SHA-256 of `<reportPublicId>`, `ingest_source = mailbox_api`, recipient = the reporter's address (status `journaled`), direction by D7.4, `email_events` `received` with `details.userReport = { reportId }`, outbox `mail.message.received.v1` (`ingestSource: 'mailbox_api'`). Report → `scanning`, `original_ingested = 1`, `original_message_*` set. The email-worker scans it in detect mode (always for `mailbox_api`, N1), writes `copy_scanned.v1`; the copies handler finds no copy row and, instead of `no_copy`, looks up `api_user_reports` by `(original_message_id, original_received_at)` and stores the scan facts (`scan_verdict`, `scan_risk_score`, `scan_level`), report → `pending_triage` (same ledger transaction). The original is never archived (`mailbox_api`, D7.6) and never delivered. **Scan deadline (review fix, §16.2):** the move to `scanning` stores `next_attempt_at = now + API_MODE_REPORT_SCAN_TIMEOUT_MINUTES` (60); a `scanning` report past it (the scan event lost, dead-lettered or never emitted) is moved by the `reports` role to `pending_triage` with the original's latest risk row, else the report copy's own scan (C10.5), and `last_error_code = original_scan_timeout`; a scan arriving later still updates the scan facts of the open report and clears the code (no second alert).
5. **No original** (`none`/`unsupported`, or inline not found): scan facts from the report copy's own scan (it contains the forwarded content), report → `pending_triage`.
6. **Acknowledgement** (`report_ack_enabled`, not rejected): outbox `mail.report.feedback_requested.v1` `{ reportId, kind: 'received' }` in the transaction that leaves `received`; `ack_feedback = queued`.

### C11. Triage

1. **States:** `received → parsing → scanning → pending_triage → in_review → resolved`; `rejected` from `received`/`parsing` (automatic) or by an analyst (verdict-less dismissal, reason code `analyst_rejected`). `resolved` can be reopened to `in_review` once (`409 api_mode_report_not_reopenable` afterwards).
2. **Assessment** (automatic, at `pending_triage`, pure `assessReport`): scan verdict `malware`/`phishing` with level `critical` or a hard block → `malicious`; other threat verdicts → `suspicious`; `clean` → `clean`; no scan → `unknown`. Shown as a hint; never acts.
3. **Groups:** `group_key` = `original_message_id_hash`, else SHA-256 of the canonical `original` keys (sender + subject key + date hour), else NULL; the list shows the group size; a triage with `applyToGroup` (default true) resolves every open report of the group in one transaction.
4. **Triage** `POST /api-mode/reports/{id}/triage` `{ status: 'in_review'|'resolved'|'rejected', verdict? (required for resolved), note?, notifyReporter? (default = `report_feedback_enabled`), applyToGroup?, expectedRowVersion }` (`remediation:write`, Idempotency-Key, CAS); audit `api_mode.report_triaged`; `resolved` with `notifyReporter` writes `mail.report.feedback_requested.v1` `{ reportId, kind: 'resolved' }` per report (`result_feedback = queued`); counter `reports_resolved`.
5. **Clawback from a report** `POST /api-mode/reports/{id}/clawback` `{ expand?: { attachments, urls, senderSubjectHours }, reason }` (`remediation:purge`): needs an identified original (else `409 api_mode_report_original_unknown`); creates an `api_clawbacks` row (`trigger = report` or `campaign` when expanded, `report_id`, criteria from `original`, status `searching`) and links `clawback_id`; the admin then previews and submits it (`mode: policy` uses the C3.1 analyst facts, or an explicit action) under C6.

### C12. Reporter feedback (existing notification path)

`mail.report.feedback_requested.v1` (strict: `reportId` UUID, `kind` `received|resolved`, `requestedAt`; no address or text) → `email.notifications` (binding v18) → notification-worker handler `report-feedback.handler.ts` (ledger `notification-worker.report-feedback`): reads the report at send time; sends only when the report is not `rejected`, the reporter address is on an organization domain and still resolves to an organization mailbox or user, and (for `resolved`) the analyst verdict is set; fixed templates (plain text + HTML) per kind and verdict (`malicious`: "Thank you — this message was dangerous and has been removed"; `phishing_simulation`: "This was a phishing simulation — well spotted"; `spam`; `clean`: "This message is safe"; `inconclusive`) with the report date and public id; **no subject, sender or body of the reported message**; sender and relay are the existing notification mailer settings; local tests deliver to `notify-relay-sink` only. Metric `notifications_sent_total{kind="report_feedback_*"}`.

Rejected: the column is NOT NULL with an FK and lock order message → entries → requests, and 35 readers in api, policy-engine, notification-worker, tenant-data and mailbox-worker assume an entry; the policy-engine sweeper would have to skip the new kind. The Q14 rules (second user with the permission, not the requester, no API key, TTL, statuses, decider permission hash, notification) are kept, stored on the clawback row like the 8.4 ATO response actions.
- **Synchronous search in the api** (preview computed per request). Rejected: the preview could differ from what is purged (C-I2) and large tenants would hold api requests; materialized targets give a frozen, paged, auditable hit list.
- **Provider-wide live search** (locate by Message-ID in every mailbox, also those without a recorded copy). Not chosen: N6 (no backfill), one call per mailbox (50 000 per purge) against the tenant budget; journal intake covers every message since onboarding. Recorded as a later option (§8).
- **Automatic clawback from reports.** Rejected: users report many legitimate messages; C-I5.
- **Polling late verdicts from `message_risk_scores`** instead of an event. Rejected: partitioned scans by time with no suitable index; an event in the producing transaction is exact and idempotent.
- **TI fan-out by the api in the indicator transaction.** Rejected: platform indicators also arrive by import (breach import, feeds) outside the api; a cursor sweep catches every writer and decouples the api.
- **Reusing quarantine notification kinds for reporter feedback.** Rejected: quarantine notifications reference entries and digests; a dedicated, strict, content-free event keeps the quarantine contract unchanged (two bindings in v18).
- **A new `ingest_source` (`user_report`) for report originals.** Rejected: every "non-gateway" test, gate and archive rule would need it; `mailbox_api` already means "detect-scan only, never delivered, never archived".
- **An Outlook/Gmail report add-in.** Out by P4.
- **Separate permissions for reports (`reports:triage`).** Not chosen: the brief names the `remediation:*` family; analysts already hold `remediation:write`.

## 11. ADR texts (WP1 creates the files; WP7 updates status lines to "Accepted (date, evidence)" after verification)

### ADR-0103: API-mode retroactive clawback and search and purge

**Context.** Brief scope 6: later signals (threat intel, late sandbox/URL verdicts, campaigns, admin decisions) must find and remediate every copy across a tenant's mailboxes, matched by Message-ID, attachment hash, URL or sender + subject + window; admins search and purge manually; purges above N mailboxes (P2, 50) need a second approver. API-2 ([ADR-0101](0101-api-mode-remediation-policy-and-mailbox-actions.md)) provides the only mailbox action engine; ADR-0101 (3) forbids manual hard delete and (4) never remediates inline-authority copies automatically.

**Decision.** (1) Clawbacks (`api_clawbacks`) with frozen per-copy targets (`api_clawback_targets`) are created from `mail.threat.late_signal.v1` (email-worker: sandbox risk revisions and late URL dynamic verdicts; topology v18), a mailbox-worker sweep of new threat indicators and malware hashes (per API-active organization with matches), campaign expansions of a seed, report verdicts and admin searches; criteria `api-clawback-criteria/1` over indexed keys only; one clawback per organization and signal. (2) Targets execute only as `api_remediation_actions` rows (triggers `clawback`, `purge`) through the `remediate` role. Automatic signals re-decide copies through the remediation policy with the signal's facts (detect-only and pause respected); clawbacks only escalate and skip copies restored after the signal. (3) Admin purges preview the materialized hit list and act with quarantine folder, Junk or soft delete; a purge whose eligible targets span more than the organization threshold of distinct mailboxes (default 50), any hard-delete purge and any automatic clawback above its cap need a second user with the new permission `remediation:purge` (5.3 Q14 rules stored on the clawback row like 8.4 ATO responses). (4) **Supersedes ADR-0101 decision 3 in part:** hard delete may be used by an admin purge through a separate portal-only operation when `API_MODE_HARD_DELETE_ENABLED=true`, always with a second approver; still never in a default, preset, single-copy manual action or assistant tool. (5) **Supersedes ADR-0101 decision 4 in part:** clawback decisions treat hybrid copies with copy authority (the late signal supersedes the inline decision). (6) Every clawback is audited, shows progress and per-mailbox results, and can be restored in bulk where the provider allows it (mailbox entries through the stored-verdict restore check).

**Consequences.** One action engine; frozen, auditable purges; large automatic actions need a person; topology +1 binding for signals.

**Alternatives.** A separate purge engine; approvals in `quarantine_approval_requests`; synchronous api search; provider-wide live search; api-side TI fan-out (design §6).

### ADR-0104: Internal mail and user-reported phishing in API mode

**Context.** Brief scope 7 and 8: east-west mail must be scanned and remediated like inbound mail; users forward suspicious mail to a per-tenant report mailbox (P4: no add-in); reports are scanned, triaged, may trigger clawback and the reporter gets feedback. [ADR-0100](0100-api-mode-intake-mailbox-worker.md) (note 35 D7.4) records inbound journal recipients only.

**Decision.** (1) **Supersedes ADR-0100 in part (D7.4):** internal journal recipients are recorded as copies with `direction = internal` when the organization's internal-mail setting is on (default); outbound-only journal messages are recognised and never recorded; dedupe and N1 are unchanged; the remediation decision gains the skip `internal_mail_disabled`. (2) Report mailboxes are API-mode mailboxes flagged `report_mailbox` (≤ 5 per organization); their copies are never remediated and create `api_user_reports`. (3) The mailbox-worker `reports` role checks the reporter (organization-side, no loop, no auto-reply, rate limit), extracts the original (forward-as-attachment or inline forward headers) with a bounded pure extractor, links it to a recorded copy or ingests the attached original as a `mailbox_api` registry message without a copy row for a detect-mode scan. (4) Analysts triage reports in the portal (states, verdicts, groups); a report never remediates by itself; an analyst may create a clawback (ADR-0103 rules). (5) Reporter feedback (acknowledgement and result) goes through the notification-worker with the strict, content-free event `mail.report.feedback_requested.v1` (topology v18, one binding).

**Consequences.** East-west threats are visible and remediated; reports reuse copies, scanning and clawback; no add-in.

**Alternatives.** A new ingest source for report originals; quarantine notification kinds for feedback; automatic report-driven clawback (design §6).

**Deviations and interpretations (with evidence).**

1. C2.5 "…" in the tuple is read as the organization id: `api-clawback-signal/1\0<orgId>\0late\0<messageId>\0<receivedAt ISO ms>\0<kind>\0<revision ?? urlSha256>`, and `…\0ti\0<table>\0<rowId>` for threat intelligence. 2. C3.1 malware signatures have no confidence column (`malware_signatures`, schema.prisma), so `signalFacts` reads them as confidence 100. A confirmed hash therefore carries `hb.clawback.threat_intel`, and P1 quarantines it, as an inline hit on the same hash would (`hb.malware_attachment`). 4. C5.3: a copy that is `restored` with an unknown restore time, or `remediated` with an unknown action, is skipped (`restored_after_signal` / `already_remediated`). This is the conservative reading of C-I3.
5. C10.2: structure limits (parts > 200, depth > 4) and an original over `maxOriginalBytes` give `too_large` with `limit` (`bytes`, `original_bytes`, `parts`, `depth`). A multipart without a boundary parameter, with a boundary longer than 200 characters, or whose boundary never appears gives `parse_failed`, as does an unknown transfer encoding on the selected original. A missing close delimiter is tolerated. `message/global` is accepted like `message/rfc822`. The order of identification is attachment → inline → unsupported → none. Inline forward dates without a zone are read as UTC (the lookup window is ±72 h).
6. `REMEDIATION_TRIGGERS` keeps the API-2 list. The api builds its history filter (`maxValues: 5`) and OpenAPI snapshot from it, so changing it in wave 1 would break api tests. The full enum is `API_MODE_ACTION_TRIGGERS` (see the WP4 item).
7. `reportGroupKey` without a Message-ID needs sender, subject key **and** date (C11.3). Without a date it returns null rather than grouping by sender and subject alone, so unrelated reports cannot be resolved together.
