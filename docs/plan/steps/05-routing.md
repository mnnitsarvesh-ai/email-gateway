## 2. Decisions

### 2.0 Invariants (never traded away)

1. **Postfix owns delivery to remote servers**: MX resolution, the per-destination queue, exponential retry, `maximal_queue_lifetime` and DSN generation (ADR-0006). The delivery-worker never retries against a remote server; it retries only its own reinjection hop into postfix-outbound.
2. **`delivered` only after the remote server's `2xx`**, read from Postfix's own delivery record (§R8) and committed through the MySQL writer. A reinjection `250` means `queued`, never `delivered`. Missing signals end in `unknown`, never in a guessed outcome.
3. **Direction is never derived from headers**: it comes from the ingestion listener (authenticated connector or inbound MX) and the organizations' verified domains (§R1).
4. **Internal mail never goes to Internet MX; other tenants' recipients never shortcut across tenants** (§R1, §R4).
5. **Tenant from trusted context only**: the message row's organization (set by ingestion), never from headers or API input. Cross-tenant API access is `404`.
6. **Bodies never in MySQL or on the outbox**; the worker streams the EML from S3 and never holds a whole message in memory.
7. **Idempotent everywhere**: every approval, reinjection and status signal can be processed twice (and out of order) without a second effect (§R6, §R9).
8. **Fail closed**: Redis, DB or S3 trouble defers (worker retry, Postfix `4xx`), never drops and never sends without the checks.
9. **Organization-neutral traces**: added headers name only the gateway (`*.gateway.local`-style host names, `GATEWAY_TRACE_ID`), never a tenant.

### R1. Direction resolution (one routing module)

A new workspace package **`@email-gateway/mail-routing`** (`packages/mail-routing`, WP1) holds every routing rule. smtp-adapter (ingestion classification, socketmap maps, bounce matching) and delivery-worker (planning, reinjection, status) both use it; the api uses its destination-host and provider validation. Rules are pure functions over data loaded by a small repository in the same package.

**Classification per recipient** (`classifyRecipient`), with `L` = the ingestion listener direction (`inbound` for `:10050`, `outbound` for `:10051`), `O` = the message's organization (set by ingestion) and `R` = the recipient domain:

| `L`        | Condition                                                                                                                                 | Direction  | Delivery                                            |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------------- | ---------- | --------------------------------------------------- |
| `inbound`  | always (ingestion already proved `R` is a domain of `O`)                                                                                  | `inbound`  | `O`'s destination servers for `R`, listener `10026` |
| `outbound` | `resolveActiveDomain(R)` returns owner `O` (verified, `active` domain of an `active` organization; `inbound_enabled` is **not** required) | `internal` | `O`'s destination servers for `R`, listener `10026` |
| `outbound` | anything else, **including `R` owned by another organization `P` on this gateway**                                                        | `outbound` | Internet MX of `R`, listener `10027`                |

- **Inbound mail whose sender domain is `O`'s own is still `inbound`**: the inbound MX is unauthenticated, so a same-organization sender there is a spoofing candidate (SPF/DMARC/BEC are steps 4.x), never internal.
- **Other tenants are reached through their public MX** (normally this gateway's inbound MX). Justification: tenant `P` gets its full inbound path (recipient validation, rate limits, scanning, its own policies and audit), the two tenants' data never mix in one record, and `P`'s routing configuration is never readable from `O`'s delivery. The cost (one extra MX hop and a second scan) is accepted. Enforced twice: by the routing module (direction `outbound`), and by Postfix (§R4: 10027 mail bypasses `transport_maps`).
- **When**: classification runs **at ingestion** (WP4, smtp-adapter, outbound listener only) so the policy engine (5.x) sees each recipient's direction, and is **re-checked at planning** (WP3). Stored in the new column `email_recipients.direction`. `email_messages.direction` becomes `internal` when the listener is outbound and every recipient of that organization is internal; mixed messages stay `outbound` (the parent message stays **one** record; directions live on recipients and deliveries). The ingest key, the S3 object key and the loop check keep using the **listener** direction (unchanged contracts of 2.2 D7/D8/D14). The `mail.message.received.v1` payload's `direction` carries the message direction.
- **Re-check at planning**: if a recipient's current classification differs from the stored one (a domain was removed, moved or added between ingestion and delivery), that recipient is **not delivered**: `failed`, reason `direction_changed`, audited (mail approved under internal policy must never leave for the Internet, and vice versa). Rows without a stored direction (ingested before 2.3) are classified at planning.
- **Inbound recipient domain at planning**: `resolveDomainOwner(R)` must still be `O`; `suspended` domain or organization → the reinjection is held (worker retry, error class `gateway_hold`) until active again or `DELIVERY_REINJECT_MAX_AGE_SECONDS`; no owner or another owner → `failed`, reason `recipient_domain_inactive`.

New index `(host, port)` for the `tls_policy` map. One provider per domain (the api refuses mixing).

**Provider presets are configuration data**, not code: new platform table `mail_destination_presets` (seeded, keyed by `provider`), read by the api and the routing module. No tenant is ever special-cased in code.

The exact certificate names and Postfix `match=` semantics (leading dot = subdomains, wildcard certificate names) are verified by WP2 against sinks presenting test-CA certificates with the real providers' SAN sets; if Postfix matches differently, WP2 corrects the **seeded data** (WP1 file, coordinated through the WP2 report; WP5 may apply it) and documents it — the code paths stay unchanged.

**Customer-side setup** (documented by WP2 in `docs/domains/destination-servers.md`): Microsoft 365 — MX of the domain points to the gateway; an **inbound connector** "from partner organization" restricted to the gateway's egress IPs or its TLS certificate subject (`out.<gateway domain>`), "Reject email messages if they aren't sent over TLS", and Enhanced Filtering for Connectors (skip listing) so EOP sees the original client IP; optional outbound connector "to partner organization" routing all mail via the gateway's submission/relay connector for outbound and internal inspection (with an SMTP connector of step 2.2: SASL or client certificate, **never** source IP, 2.2 D10). Google Workspace — Gmail "Inbound gateway" setting with the gateway's egress IPs, "Reject all mail not from gateway IPs", "Require TLS for connections from the email gateways"; for outbound, the Gmail "Outbound gateway"/SMTP relay route to the gateway's submission listener with SMTP AUTH.

**Postfix answers** (smtp-adapter socketmap, WP4, using the routing module):

- `transport`: all enabled `inbound_destination` servers of the recipient's active tenant domain, ordered by `(priority, id)`, rendered as a Postfix 3.5+ next-hop list: `OK smtp:[h1]:25,[h2]:2525` (Postfix tries them in order: failover). Each host is re-validated with `validateDestinationHost` (§R3); invalid rows are skipped and logged; none left, or any host is a gateway host → `OK retry:4.4.1 Destination not configured` (unchanged). Maximum `ROUTING_MAX_DESTINATIONS_PER_DOMAIN` (10) next hops.
- `tls_policy`: `[host]:port` → the strictest mode of the enabled rows sharing it; `verify` renders `secure match=<tls_verify_names or nexthop> protocols=>=TLSv1.2`; `required` → `encrypt protocols=>=TLSv1.2`. WP2 verifies that Postfix looks up the policy per next hop of a list; if it only looks up the first, the api must require one TLS mode per domain (WP4 then enforces it) and this is documented. **Review fix (§12.7 F1):** rows of several organizations on one next hop must agree on the policy; the api refuses a conflicting custom `host:port` (`destination_tls_conflict`) and custom servers on preset hosts (`host_reserved_for_provider`).
- Cache: route and TLS answers stay in the 2.2 Redis caches (TTL `SMTP_DOMAIN_CACHE_TTL_SECONDS`), and the api writes a new outbox event `domain.routing.changed.v1` on every destination change, which the adapter's existing outbox-tail invalidator also handles (deletes the route key of that domain and the TLS keys of the old and new hosts).

### R3. Destination host safety

`validateDestinationHost(host, port, options)` (routing module; used by the api on write and by the adapter on every map answer):

1. Normalize: lower case, strip one trailing dot, IDNA to ASCII; LDH labels 1–63, total ≤ 253; port 1–65535 (presets: their port only).
2. **IP literals** (`1.2.3.4`, `[1.2.3.4]`, IPv6 with or without brackets): refused unless the address is globally reachable (IANA IPv4/IPv6 special-purpose registries: private, loopback, link-local, shared CGNAT, documentation, benchmarking, multicast, reserved, unique-local, NAT64 well-known with an embedded non-public address, IPv4-mapped), unless `ROUTING_ALLOW_NON_PUBLIC_DESTINATIONS=true` (dedicated deployments delivering to the customer's private network). **Metadata addresses** (`169.254.169.254`, `fd00:ec2::254`, `100.100.100.200`, `169.254.170.2`) are refused even with the flag.
3. **Names**: single-label names are refused (covers every Compose and Kubernetes short service name: `mysql`, `redis`, `smtp-adapter`, …); refused suffixes `.local`, `.localhost`, `.localdomain`, `.internal`, `.intranet`, `.lan`, `.home.arpa`, `.svc`, `.cluster.local`, `.consul`, plus `ROUTING_DENIED_DESTINATION_SUFFIXES` (comma list; production adds e.g. `.test,.example,.invalid`); refused names `localhost`, `metadata.google.internal`, `instance-data`, the bounce domain, and every gateway host (`GATEWAY_MX_HOSTS`, `POSTFIX_MYHOSTNAME`, `POSTFIX_OUTBOUND_MYHOSTNAME`).
4. **Resolved addresses are not checked** at write time (DNS can change, rebinding): production blocks postfix-outbound's egress to private ranges with security groups except the explicit internal next hops (documented in `docs/deployment/smtp-gateway.md`, WP2). A name that resolves to the gateway's own MX is caught by the trace loop check at ingestion (§R10).

The api answers `422` with a stable reason (`ip_not_public`, `metadata_address`, `single_label`, `internal_suffix`, `gateway_host`, `invalid_host`, `port_not_allowed`, `host_not_allowed_for_provider`). This closes the 2.2 low finding. **Review fix (§12.7 F2):** custom ports are limited to `ROUTING_ALLOWED_DESTINATION_PORTS` (default 25, 587, 2525) and the gateway's internal ports are always refused (`port_not_allowed`).

### R4. Delivery paths through postfix-outbound

| Direction  | Listener | Envelope sender      | `RCPT … NOTIFY=` | Trace prepended  | Next hop                                                                                                                                                                                                                   | DSN on failure                                       |
| ---------- | -------- | -------------------- | ---------------- | ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| `inbound`  | `10026`  | original (external)  | `NEVER`          | `d=in`, org `O`  | `transport` socketmap → `O`'s servers                                                                                                                                                                                      | **none** (ADR-0006: no backscatter); status recorded |
| `internal` | `10026`  | original (`O`'s own) | `FAILURE,DELAY`  | `d=in`, org `O`  | `transport` socketmap → `O`'s servers                                                                                                                                                                                      | Postfix DSN to the authenticated `O` sender          |
| `outbound` | `10027`  | original (`O`'s own) | `FAILURE,DELAY`  | `d=out`, org `O` | **`-o content_filter=smtp:`** (new, WP2): the empty next hop means "the recipient domain" (`default_filter_nexthop` empty), so Postfix does its own MX lookup and **never consults `transport_maps`** — no tenant shortcut | Postfix DSN to the authenticated `O` sender          |

- The 10027 content-filter change is what enforces §R1 "no cross-tenant shortcut" at the MTA. DSNs and postmaster copies are new messages without that filter, so they still route through `transport_maps` (sender's tenant destination; bounce domain → LMTP 10052) exactly as in 2.2. WP2 verifies the empty-next-hop semantics on Postfix 3.7; fallback if it does not hold: a dedicated `smtp-internet` transport in `master.cf` used as `content_filter=smtp-internet:` with the same semantics, or `-o transport_maps=` on a dedicated `cleanup`/`trivial-rewrite` pair for 10027 (documented).
- **Postfix retry, explicit** (both instances, from the environment, documented in `docs/deployment/smtp-gateway.md`): `minimal_backoff_time = 300s`, `maximal_backoff_time = 4000s`, `queue_run_delay = 300s` → a deferred message is retried after ≈ 5, 10, 20, 40, 66, 66… minutes (Postfix doubles the per-message backoff from the minimum up to the maximum), `maximal_queue_lifetime = bounce_queue_lifetime = 5d` → `expired` + DSN to the sender (none for inbound), `delay_warning_time = 4h` → delay DSN (not for inbound). New: `smtp_connect_timeout` from `POSTFIX_OUTBOUND_SMTP_CONNECT_TIMEOUT` (30s; local 5s), `smtp_helo_name = $myhostname`. **Test profile only** (local `.env` and CI): `POSTFIX_MINIMAL_BACKOFF_TIME=10s`, `POSTFIX_MAXIMAL_BACKOFF_TIME=60s`, `POSTFIX_QUEUE_RUN_DELAY=10s`, connect timeout 5s; nothing in code depends on these values.
- Per-destination concurrency and politeness stay Postfix's (`smtp_destination_concurrency_limit = 20`, `smtp_destination_rate_delay = 0` default, documented).

### R5. Approval contract (the trigger)

The scanning and policy pipeline does not exist yet. Delivery starts from an explicit **approval**, which the policy engine (5.x) and the quarantine release (5.3/6.1) will produce later:

- **Event `mail.delivery.approved.v1`** (`deliveryApprovedV1`, WP1, `packages/event-contracts`), written through `message_outbox` (`aggregate_type = 'message'`, `aggregate_id` = decimal message id), envelope `organizationId` = the message's organization:

  ```ts
  {
    messageId: decimalId,              // registry id
    receivedAt: iso datetime,          // partition key
    deliverySeq: int >= 0,             // 0 = initial delivery; releases use 1, 2, …
    source: 'policy' | 'quarantine_release' | 'dev_passthrough',
    emlS3Key: 'org/<id>/…',            // the object to deliver (policy may later produce a modified copy)
    recipients: [{ recipientId: decimalId, rcptSeq: int >= 0 }],  // 1..1000, the approved subset
    approvedAt: iso datetime,
  }
  ```

  The envelope `eventId` is the approval id. `deliverySeq` + `recipientId` is unique per delivery (`email_deliveries` unique key), so a duplicate approval never plans twice.

- **Transport behind an interface** (`ApprovalFeed` in the delivery-worker): the 2.3 implementation is an **outbox poller** (§R6); step 3.2 replaces it with a RabbitMQ consumer of the same event (queue binding added then) without touching planning. No RabbitMQ topology is added in 2.3. (The existing `QUEUES.delivery` assertion of the skeleton stays as it is.)
- **Development-only pass-through** (`DevPassThroughApprover`, WP3): when `DELIVERY_DEV_PASSTHROUGH_ENABLED=true`, the worker turns each `mail.message.received.v1` into a `mail.delivery.approved.v1` with `source = 'dev_passthrough'` for every recipient of the message whose `email_recipients.status = pending`, in one writer transaction with its `processOnce` ledger row and an `email_events` row `delivery.approved` (`details.source = 'dev_passthrough'`). Default **false**; config validation **refuses `true` unless `APP_ENV` is `local` or `ci`** (`staging`/`production` fail at startup). It logs a warning at startup and is counted (`delivery_approvals_total{source="dev_passthrough"}`). It starts from the outbox position at its first start (never replays old mail). **This is not production behaviour**: it delivers mail without scanning or policy; it exists so the stack can be tested end to end before steps 3.x/5.x.

### R6. Outbox poller (interim transport, replaced in 3.2)

`OutboxPoller` (WP3), one per consumer name, backed by the new table `stream_cursors`:

- Every `DELIVERY_OUTBOX_POLL_INTERVAL_MS`: `SELECT id, created_at, event_id, organization_id, event_type, payload FROM message_outbox WHERE id > :cursor AND event_type IN (:types) ORDER BY id LIMIT :DELIVERY_OUTBOX_BATCH_SIZE` (writer; PK range across daily partitions).
- Each row is parsed (`parseEvent` with the payload schema; an invalid row is logged, counted and skipped — it can never become valid) and handled with `processOnce(prisma, consumer, eventId, handler)`; a duplicate is skipped.
- **Out-of-order commits**: auto-increment ids are allocated at insert and committed later, so a smaller id can become visible after a larger one. The cursor therefore advances only to the largest processed id whose `created_at <= now - DELIVERY_OUTBOX_SAFETY_LAG_MS` (default 120 s, far above the writers' transaction timeouts of 15 s); newer rows are processed but re-read on the next poll (the ledger makes that free of effects; an in-memory set of recently processed event ids avoids the ledger round trip). A writer transaction open longer than the lag could be skipped; that bound is documented and monitored (`delivery_outbox_poll_lag_seconds`).
- Initial position: approvals consumer = the oldest retained outbox row (nothing approved is lost); dev pass-through consumer = `MAX(id)` at first start.
- Single active poller per consumer across replicas: MySQL `GET_LOCK('dw:outbox:<consumer>', 0)` on a dedicated connection; replicas without the lock idle. (2.2's invalidator tails from `MAX(id)` in memory because cache invalidation tolerates loss; delivery does not.)
- The outbox's `published_at` is **not touched** (it belongs to the 3.2 relay).

### R7. Planning and per-recipient split

`DeliveryPlanner` (WP3), consumer `delivery-worker.planner` of `mail.delivery.approved.v1`, one writer transaction per approval (inside `processOnce`):

1. Load the message (`email_messages` by `(id, received_at, organization_id)`) and the approved recipients (`email_recipients` by id + `received_at` + message + organization; unknown or foreign ids → logged and skipped; never trusted from the payload alone).
2. Per recipient, the routing module returns a **route**: direction (§R1), listener, `destinationKey` (`tenant:<domainId>` for inbound/internal, `mx:<recipientDomain>` for outbound), NOTIFY and trace direction (§R4), or a refusal: `suppressed` (outbound recipient with an active `delivery_suppressions` row of `O`), `failed` with reason `direction_changed` / `recipient_domain_inactive`.
3. **Split**: routes are grouped by `(listener, direction, destinationKey)` and chunked to `DELIVERY_BATCH_MAX_RECIPIENTS` (≤ 100 = postfix-outbound `smtpd_recipient_limit`). One group = one `delivery_reinjections` row = one SMTP transaction into postfix-outbound. Inbound/internal recipients of two domains → two groups; outbound recipients → one group per recipient domain (so per-domain rate limits and outages never hold other domains). Postfix splits further per next hop on its own.
4. Insert one `email_deliveries` row per recipient (`delivery_seq` from the approval; `status = pending`, or the refusal status), the `delivery_reinjections` rows (`status = pending`, `next_attempt_at = now`), and for each recipient a planner signal through the shared recorder (§R9: audit row, `email_events`, outbox `mail.delivery.status_changed.v1` for refusals). The message moves `received`/`policy_evaluated` → `delivery_queued` (optimistic `version` + `email_message_status_history`).
5. The parent message stays **one** record; each recipient has its own delivery state; the reinjection rows only group transport.

**Reinjection idempotency key** = hex SHA-256(`v1|{messageId}|{deliverySeq}|{listener}|{recipientSetSha256}`) with the recipient set = the group's lower-cased, de-duplicated, sorted, LF-joined addresses (same convention as the 2.2 ingest key). Unique `(message_id, idempotency_key, received_at)`. A re-planned approval (duplicate event after a crash between ledger and commit is impossible — same transaction — but a second approval with the same `deliverySeq`) hits the unique key and the delivery unique key: no second reinjection.

### R8. Reinjection (the delivery-worker's own hop)

`ReinjectionScheduler` (WP3): every `DELIVERY_POLL_INTERVAL_MS`, claims due rows with `SELECT … FROM delivery_reinjections WHERE status = 'pending' AND next_attempt_at <= now ORDER BY next_attempt_at LIMIT n FOR UPDATE SKIP LOCKED`, sets `status = in_progress`, `lease_expires_at = now + DELIVERY_REINJECT_LEASE_SECONDS`, `attempts + 1`, `started_at`; runs up to `DELIVERY_REINJECT_CONCURRENCY` sessions.

Per claimed row:

1. **Outbound rate limits** (10027 only; §R11). Over a limit or Redis error → release: `pending`, `next_attempt_at` = next window start + jitter (Redis error: retry backoff), recipients `deferred` with error class `gateway_rate_limited` / `gateway_rate_limit_unavailable` (one audit row per window, not per poll). Never dropped.
2. **Open the EML stream** from S3 (`GetObject` on the approval's `emlS3Key`, which must start with `org/{organizationId}/` of the row — checked). Read the header block (≤ `INGEST_HEADER_MAX_BYTES`, 64 KiB) from the stream before connecting; **hop check** (§R10). Missing object (`NoSuchKey`) → `failed`, reason `content_missing` (a reconciliation case for 3.2, error log); other S3 errors → retry.
3. **SMTP session** (a small purpose-built internal SMTP client in the worker — not nodemailer — because XFORWARD and per-recipient DSN parameters are required; plaintext on the internal network; strict multi-line reply parsing; timeouts per command `DELIVERY_REINJECT_COMMAND_TIMEOUT_MS`, after the final dot `DELIVERY_REINJECT_DATA_TIMEOUT_MS`):
   - `EHLO ${DELIVERY_REINJECT_HELO}` (default `delivery.gateway.local`, organization-neutral). XFORWARD must be advertised, else a configuration error (retry + error log).
   - `XFORWARD NAME=… ADDR=… HELO=… PROTO=ESMTP` with the **original client** of the message (`email_messages.client_ip`, `client_helo`; `[UNAVAILABLE]` when unknown) so Postfix's `Received:` for this hop shows the original client instead of the worker's internal address (the standard Postfix after-queue-filter pattern), then `XFORWARD IDENT=<token> SOURCE=REMOTE`. **`token` = `dw1-` + the reinjection's `public_id` without dashes** (36 characters). _Contract change (ADR-0021)_: 2.2 defined `IDENT` = original queue id for logging only; it is now the reinjection token, because Postfix logs it as `orig_queue_id=` on the `client=` line, which binds Postfix's queue id to the reinjection even if the worker crashes before reading the `250` (§R9). WP2 verifies (a) the log line, (b) that the forwarded `ADDR` does not change `permit_mynetworks` (if it does, the worker sends only `IDENT`/`SOURCE`, documented).
   - `MAIL FROM:<envelope_from> SIZE=<bytes incl. prepended header> RET=HDRS ENVID=<token>` (+ `SMTPUTF8` when an address is non-ASCII; `<>` stays `<>`). `ENVID` comes back as `Original-Envelope-Id` in DSNs: a second matching key for the bounce handler.
   - `RCPT TO:<addr> NOTIFY=<§R4> ORCPT=rfc822;<xtext addr>` per recipient. Per-recipient replies: `2xx` accepted; `4xx` → that recipient moves to a **new** reinjection (new recipient set, new key) scheduled with the worker backoff, delivery `deferred`, error class `reinjection_4xx`; `5xx` → `failed`, reason `reinjection_refused` (code, enhanced status and text recorded; no DSN — the worker cannot generate one and the refusal is a gateway policy outcome, e.g. a suspended sender domain).
   - No recipient accepted → finish (no DATA). Otherwise `DATA`: write `X-Gateway-Trace: <buildGatewayTrace(…)>` CRLF, then the EML **unchanged** (stream, LF → CRLF normalization, dot-stuffing, trailing CRLF guaranteed, `.`). No other header is added or removed by the worker; Postfix adds its `Received:` (`by out.gateway.local`).
   - Final reply `250 … queued as <QID>` → record `queued`: reinjection `status = queued`, `queue_id`, `queued_at`; accepted recipients' deliveries `queued` with `outbound_queue_id` (signal source `reinjection`). Unparseable `250` text → still `queued`, queue id left to the log binding. `4xx` → retry the whole group; `5xx` (e.g. hop count `554 5.4.0`, milter reject) → accepted recipients `failed`, reason `reinjection_refused`.
   - Connection errors, timeouts **before** the final dot → retry. Timeout **after** the final dot (ambiguous) → leave `in_progress` for the reconciler (§R12).
4. **Worker retry** (own hop only): `next_attempt_at = now + min(DELIVERY_REINJECT_RETRY_MAX_SECONDS, DELIVERY_REINJECT_RETRY_BASE_SECONDS × 2^(attempts-1)) ± 10 % jitter`; after `DELIVERY_REINJECT_MAX_AGE_SECONDS` since the approval → `failed` reinjection, deliveries `expired` (error class kept; reason `reinjection_expired`, no DSN, error log).

### R9. Delivery status: signals, sources and the state machine

**Decision: the primary success and failure signal is structured parsing of postfix-outbound's delivery log; postmaster DSN copies (LMTP 10052) are a corroborating second source for failures and delays; both are matched on the Postfix queue id recorded for the reinjection.**

Why not success DSNs (`NOTIFY=SUCCESS`): Postfix sends success DSNs to the **envelope sender**, not to a postmaster address (`notify_classes` has no success class), so every delivered message would mail a receipt to the tenant's user (or to an external sender for inbound mail). Catching them would require a gateway-owned envelope sender (VERP on a gateway domain), which changes the Return-Path of tenant mail, breaks SPF alignment of the tenant's domain and sends asynchronous remote bounces to the gateway instead of the tenant. Postfix's delivery log, by contrast, is written by the `smtp` client **after** the remote server's reply to the final dot (`status=sent (250 …)`), covers every recipient and outcome (`sent`, `deferred`, `bounced`, `expired`) with the queue id, relay, DSN code and the remote reply, and is the standard trustworthy record of a Postfix delivery.

**Log transport** (WP2 + WP3): postfix-outbound writes `maillog_file` to a dedicated directory (`/var/log/postfix-outbound/maillog`; Compose bind mount `${POSTFIX_OUTBOUND_LOG_DIR}`, default `./.local/postfix-outbound-log`, git-ignored), mirrored to stdout by the entrypoint for `docker logs`. Only Postfix writes it; readers mount it read-only. Rotation: `postfix logrotate` (Postfix 3.4+) renames the file; the tailer follows by file identity (device + inode) and drains the old file before switching. In production the **status reader** is the same delivery-worker image running on each postfix-outbound EC2 host as a sidecar with `DELIVERY_STATUS_LOG_ENABLED=true` and the other roles off (documented; Kubernetes reinjection replicas run with the log role off).

**`PostfixLogTailer`** (WP3): reads appended lines from `DELIVERY_STATUS_LOG_PATH`, parses them (`PostfixLogParser`), applies signals, and commits the cursor (`stream_cursors`: file identity, byte offset, last event time) **after** the signals of the batch are committed — at-least-once; the signals are idempotent. Single reader per source: `GET_LOCK('dw:postfix-log:<DELIVERY_STATUS_LOG_SOURCE_ID>')`. Lines of interest (Postfix 3.7 formats; the parser accepts the `maillog_file` timestamp with or without microseconds and infers the year from the current UTC date, handling the December/January boundary):

| Line (program)                                                                                                | Meaning → signal                                                                                                                                                 |
| ------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `postfix/reinject-(inbound\|outbound)/smtpd[pid]: QID: client=…, orig_queue_id=dw1-<hex>, orig_client=…`      | bind `QID` ↔ reinjection token (`bindReinjectionQueueId`); only from the reinjection listeners' `syslog_name`, which only `$reinject_networks` clients can reach |
| `postfix/qmgr[pid]: QID: from=<…>, size=N, nrcpt=M (queue active)`                                            | the bound queue file was accepted → every accepted recipient of that reinjection `queued` (covers a crash after `250`)                                           |
| `postfix/smtp[pid]: QID: to=<a>, [orig_to=<a>,] relay=h[ip]:p, delay=…, delays=…, dsn=2.x.x, status=sent (…)` | **`delivered`** (remote `2xx` after DATA) + `delivery_attempts` row (`success`), `remote_host`, `final_smtp_code`/`response`                                     |
| `… dsn=4.x.x, status=deferred (…)`                                                                            | `deferred`, `attempt_count + 1` when `relay` ≠ `none`, error class from the text (§R9.2), `delivery_attempts` row (`deferred`)                                   |
| `… dsn=5.x.x, status=bounced (…)`                                                                             | `bounced` + attempt row (`bounced`)                                                                                                                              |
| `postfix/(qmgr\|bounce)…: QID: to=<a>, relay=none, …, status=expired, returned to sender (…)`                 | `expired`                                                                                                                                                        |
| `postfix/(error\|retry)…: QID: to=<a>, relay=none, …, status=deferred (Destination not configured)`           | `deferred`, error class `no_destination` (no remote attempt)                                                                                                     |
| `postfix/bounce[pid]: QID: sender non-delivery notification: DSNQID` / `sender delay notification: DSNQID`    | record `dsn_queue_id` on the deliveries of `QID` that are `bounced`/`expired` (non-delivery) — the evidence that a DSN was generated to the original sender      |
| `postfix/qmgr[pid]: QID: removed`                                                                             | the queue file is gone: any delivery of `QID` still non-terminal → `unknown` (source `reconciler`, warn + metric; should never happen)                           |

Lines for queue ids that are not bound to a reinjection (submissions, ingestion LMTP hops, DSNs, bounce notices) are ignored. Address matching is case-insensitive on the whole address (Postfix does not rewrite on the reinjection listeners: `no_address_mappings`).

**Bounce notices** (WP4, smtp-adapter): the 2.2 handler first matches the notice to a reinjection by `X-Postfix-Queue-ID` (= `queue_id`) or `Original-Envelope-Id` (= token) and, if matched, emits per recipient a `bounce_notice` signal (`Action: failed` + `5.x.x` → `bounced`; `failed` + `4.x.x` → `expired`; `delayed` → `deferred`) with the organization **from the reinjection row** (any direction, including inbound 10026 deliveries, which closes the 2.2 limitation). The existing outbound behaviour (`bounce_events` + suppressions, gated on the valid outbound trace) is unchanged, and `bounce_events.message_id` / `message_received_at` are now filled when matched. Internal and inbound bounces create **no** suppressions and no reputation events.

#### R9.1 Recorder and transition rules

`recordDeliverySignal(prisma | tx, signal, ctx)` (WP1, `@email-gateway/mail-routing`), used by the worker and the adapter. One writer transaction per signal (or inside a caller's transaction for the planner):

1. Resolve the delivery: by `(deliveryId, receivedAt)`, or by `(queueId, address)` via `email_deliveries.outbound_queue_id`, or by `(token, address)` via `delivery_reinjections.public_id`. Not found → result `unmatched` (counted; the caller retries `unmatched` log lines for `DELIVERY_STATUS_UNMATCHED_RETRY_SECONDS` before dropping them, to cover a binding that commits later).
2. `SELECT … FOR UPDATE` the delivery row (serializes the tailer and the bounce handler).
3. Insert the audit row `delivery_status_events` if `(delivery_id, signal_key)` is new; a duplicate → result `duplicate`, nothing else happens.
4. Decide with the pure lattice `nextDeliveryState(current, signal)`:
   - `pending → queued | deferred | failed | suppressed | expired`; `pending → delivered/bounced` is allowed only for `postfix_log` / `bounce_notice` signals (the log can overtake the worker's own commit), implying `queued`.
   - `queued → deferred | delivered | bounced | expired | unknown`; `deferred → deferred (attempt + 1) | queued (worker re-queued a re-planned subset) | delivered | bounced | expired | unknown`.
   - **Terminal**: `delivered`, `bounced`, `expired`, `failed`, `suppressed`. Never left, except `unknown → <terminal>` when a late real signal arrives. A conflicting terminal signal (e.g. `bounced` after `delivered`) → result `conflict`, audit row kept with `applied = false`, warn + metric.
   - **Out of order**: a non-terminal signal older than `last_signal_at` → audit row `applied = false` (`stale`); a terminal signal always wins over non-terminal state. `delivered` is accepted **only** from `postfix_log` with `status=sent` and a `2.x.x` DSN.
5. If applied: update `email_deliveries` (`status`, `status_changed_at`, `last_signal_at`, `attempt_count`, `last_attempt_at`, `delivered_at`, `remote_host`, `final_smtp_code`, `final_smtp_response` ≤ 512, `enhanced_status`, `last_error_class`, `failure_reason`, `dsn_queue_id`, `outbound_queue_id`), insert `delivery_attempts` for remote attempts, update `email_recipients.status` (mapping: `queued`/`unknown` → `pending`, `deferred` → `deferred`, `delivered` → `delivered`, `bounced` → `bounced`, `expired`/`failed`/`suppressed` → `failed`), insert `email_events` (`event_type = 'delivery.<status>'`, `source_service`, details: `deliveryId`, `rcptSeq`, `queueId`, `smtpCode`, `enhancedStatus`, `errorClass`; never addresses) and the outbox row `mail.delivery.status_changed.v1` (validated).
6. **Message aggregate**: when every delivery of the message's `delivery_seq` is terminal → `email_messages.status` = `delivered` (all delivered), `partially_delivered` (some delivered), `failed` (none); with `version + 1` and an `email_message_status_history` row. `unknown` is not terminal for the aggregate.

**Signal keys** (`signal_key`, hex SHA-256): `log|{sourceId}|{queueId}|{address}|{status}|{logTimestamp}|{dsn}`; `dsn|{queueId}|{address}|{action}|{status}|{arrivalDate}` (same inputs as the 2.2 bounce dedupe key); `reinject|{reinjectionId}|{attempt}|{address}|{outcome}`; `plan|{approvalEventId}|{recipientId}`; `reconcile|{deliveryId}|{toStatus}|{reason}`; `ratelimit|{reinjectionId}|{windowStart}`. A duplicated log line, a re-read file, a redelivered bounce notice or a replayed approval therefore never produces a second transition or a second `email_events`/outbox row.

#### R9.2 Error classes

`classifyDeliveryError(text, dsn)` (WP1): `connect` (connection refused/timed out, no route), `dns` (host or domain name not found, name service error), `tls` (TLS is required but was not offered, certificate verification failed, cannot start TLS), `timeout` (conversation timed out, lost connection), `remote_4xx` (`host … said: 4xx`), `remote_5xx`, `no_destination` (Destination not configured), `loop` (mail for … loops back to myself), `gateway_rate_limited`, `gateway_rate_limit_unavailable`, `gateway_hold`, `reinjection_4xx`, `reinjection_error`, `other`. Stored in `email_deliveries.last_error_class` and every audit row.

### R10. Headers, hop count and loops

- **Preserved**: the worker never edits the EML; every original header (including earlier `Received:`, `Authentication-Results`, ARC, DKIM) reaches the destination as stored. **Added**: one `X-Gateway-Trace` (organization-neutral, HMAC, 2.2 D14) by the worker, and Postfix's own `Received: … by out.gateway.local (Postfix) with ESMTP id <QID>` whose `from` part shows the original client through XFORWARD; DKIM signature on 10027 (2.2).
- **Hop enforcement** (routing module `evaluateHops`, at reinjection before connecting): `Received:` count ≥ `ROUTING_MAX_RECEIVED_HEADERS` (25, below Postfix's `hopcount_limit = 30`) or valid traces of this gateway for organization `O` in **both** directions ≥ `ROUTING_MAX_GATEWAY_PASSES` (4) → recipients `failed`, reason `loop_detected`, error class `loop`, no DSN, error log. (The per-direction count at ingestion, 2.2 D14, stays the primary loop stop; this all-direction count stops loops that alternate directions, e.g. internal mail that the tenant's server sends back through submission.)
- **Loops proven by the stack tests** (§9): (a) **two tenants' routes**: `A`'s destination relays to the gateway MX for `B`'s domain and `B`'s destination relays back for `A`'s → the second arrival for `A` carries `A`'s `d=in` trace → `554 5.4.6` at ingestion; the message is delivered at most once per tenant and never endlessly. (b) **Self-referencing destination**: a destination equal to a gateway host is refused by the api (`422 gateway_host`) and, written directly to the DB, answered `retry:4.4.1` by the transport map → `deferred` (`no_destination`) until expiry, never delivered. A destination name that resolves to the gateway MX is case (a) with one tenant: delivered once to the MX, refused there as a loop.

### R11. Outbound rate limits (Redis, fail closed)

Applied by the worker before a 10027 reinjection, consistent with 2.2 D6 (fixed UTC-minute windows, Lua, Redis error = defer):

| Scope                                         | Key                                    | Limit                                                                                                               |
| --------------------------------------------- | -------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| tenant                                        | `dw:rl:out:{orgId}:{minute}`           | `organization_limits.outbound_recipients_per_minute` (2.2 key), else `DELIVERY_RATE_TENANT_RCPT_PER_MINUTE` (600)   |
| tenant × destination domain                   | `dw:rl:outd:{orgId}:{domain}:{minute}` | new limit key `outbound_recipients_per_domain_per_minute`, else `DELIVERY_RATE_TENANT_DOMAIN_RCPT_PER_MINUTE` (300) |
| destination domain (gateway-wide, reputation) | `dw:rl:dst:{domain}:{minute}`          | `DELIVERY_RATE_DESTINATION_DOMAIN_RCPT_PER_MINUTE` (6000)                                                           |

- One atomic Lua script checks all three keys and increments **only if** the group's recipient count fits under every limit (a deferred group does not consume quota); TTL = window + 10 s. A group larger than a limit is split by the scheduler into chunks that fit (new reinjection rows, same rules as §R8 4xx subsets). Limit `0` = no outbound delivery for that tenant: held until `DELIVERY_REINJECT_MAX_AGE_SECONDS`, then `expired`.
- Keys are separate from the adapter's `sa:rl:*` submission counters (a delivery after an outage must not consume today's submission quota twice); the limit values are the same organization limits.
- Limits are cached per organization in memory for 60 s. Inbound and internal deliveries are not rate limited by the worker (they go to the tenant's own servers; Postfix concurrency applies).

### R12. Reconciler

`DeliveryReconciler` (WP3), every `DELIVERY_RECONCILE_INTERVAL_MS`:

- **Expired lease** (`in_progress`, `lease_expires_at < now`): if the log binding recorded a `queue_id` for the token → `queued` (from the bound qmgr line); else if the tailer's `last_event_at` ≥ `started_at + DELIVERY_REINJECT_LEASE_SECONDS` (Postfix's log has passed the session without a `client=` line for the token) → back to `pending` (safe: Postfix never queued it); else wait. With the log role disabled everywhere (not recommended) → back to `pending` after the lease, accepting a possible duplicate delivery (documented). **Superseded by the review fix (§12.7 F3, F9):** the binding alone never queues; see §12.7.
- **Stale tracking**: `queued`/`deferred` deliveries whose `last_signal_at` is older than `DELIVERY_STATUS_STALE_AFTER_SECONDS` (default 6 days = queue lifetime + 1 day) → `unknown`, reason `status_signal_missing`, error log + metric. Never guessed as delivered or bounced.

## 7. Alternatives considered

| Topic                          | Chosen                                                                                 | Rejected and why                                                                                                                                                                                                                                                                                                                                |
| ------------------------------ | -------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Delivery success signal        | Postfix delivery log (queue-id matched), DSN postmaster copies as corroboration        | `NOTIFY=SUCCESS` DSNs: go to the envelope sender (users get receipts); intercepting needs VERP on a gateway domain (breaks SPF alignment, swallows async bounces). `postqueue -j` polling: shows only what is still queued, absence proves nothing. Postfix `smtp_delivery_status_filter`: rewrites texts, has no queue id or recipient context |
| Cross-tenant recipients        | Outbound through the public MX (10027 bypasses `transport_maps`)                       | Direct delivery to the other tenant's destination: skips its recipient validation, scanning, policies and audit; mixes two tenants' routing in one delivery                                                                                                                                                                                     |
| Where direction is decided     | At ingestion (stored per recipient), re-checked at planning                            | Only at delivery: the policy engine would not know the direction; only at ingestion: stale after domain changes                                                                                                                                                                                                                                 |
| Mixed recipients               | One parent message, per-recipient deliveries, reinjection groups per destination       | Split into one message per direction (diagram 8's earlier sketch): duplicates S3 objects and message rows, breaks the one-record audit                                                                                                                                                                                                          |
| Trigger transport              | Outbox poller with a safety lag, behind `ApprovalFeed`                                 | Build the RabbitMQ relay now (step 3.2's scope); a `delivery_approvals` work table (a second queue to migrate away from later)                                                                                                                                                                                                                  |
| Reinjection client             | Small internal SMTP client in the worker                                               | nodemailer: no XFORWARD, so no crash-safe queue-id binding and the worker's internal address in `Received:`                                                                                                                                                                                                                                     |
| Crash between `250` and commit | Token in XFORWARD `IDENT`, bound from Postfix's `orig_queue_id=` log line              | Accept duplicates (re-send after crash); a custom header with the token (visible to recipients, forgeable through submission)                                                                                                                                                                                                                   |
| Provider presets               | Seeded table + typed provider column                                                   | Code constants (would be code changes per provider change); per-tenant rows only (no shared, reviewable expectations)                                                                                                                                                                                                                           |
| Destination host safety        | Literal/name rules at write and at map time + egress security groups                   | DNS resolution checks at write time (rebinding, TOCTOU); allowing anything (SSRF-like delivery into internal services)                                                                                                                                                                                                                          |
| Rate limits                    | Worker-side, atomic check-and-increment, per tenant, tenant×domain, destination domain | Postfix `smtp_destination_rate_delay` only (global, not per tenant); reusing the adapter's submission counters (double counting after outages)                                                                                                                                                                                                  |

## 8. Risks and mitigations

| Risk                                                                          | Mitigation                                                                                                                                                                                                               |
| ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Postfix log format details differ (timestamps, `orig_queue_id`, syslog names) | WP2 captures real lines from Postfix 3.7 (fixtures committed under `apps/delivery-worker/src/status/__fixtures__` by WP3 from WP2's notes); the parser is table-tested on them; unknown lines are ignored, never guessed |
| Log loss (postlogd datagrams under extreme load, a missing volume)            | `unknown` after `DELIVERY_STATUS_STALE_AFTER_SECONDS` (never a guessed state), bounce notices as second source for failures, metrics on lag and unmatched lines, runbook                                                 |

| Postfix TLS policy per next hop of a list / `match=` semantics                | WP2 verifies with test-CA sinks; data-only corrections; api fallback of one TLS mode per domain                                                                                                                          |
| XFORWARD `ADDR` affecting `permit_mynetworks`                                 | WP2 verifies; fallback: only `IDENT`/`SOURCE`                                                                                                                                                                            |

## 9. Test plan

**Unit (vitest, each WP):** classification matrix (inbound always inbound incl. same-org sender; outbound same org → internal; other tenant → outbound; inactive → outbound); destination-host rules (every special-purpose range, metadata, single label, suffixes, gateway hosts, presets' patterns and ports); next-hop list and TLS policy rendering; route planning and grouping (two domains, chunking at 100, suppressed, direction changed); reinjection key determinism; hop evaluation; transition lattice (every allowed and refused transition, duplicates, stale, conflict, `unknown` recovery) and message aggregate; error classifier over real Postfix texts; event schemas; Postfix log parser over captured fixtures (sent, deferred variants, bounced, expired, retry/no destination, client/orig_queue_id, qmgr queue active and removed, DSN notification lines, year rollover, microseconds); SMTP client against a scripted fake server (multi-line replies, per-RCPT 4xx/5xx, DATA 4xx/5xx, timeouts before/after the dot, dot-stuffing, LF→CRLF, XFORWARD not advertised); rate limiter (fits/over/split/Redis error); outbox poller (safety lag, duplicate, invalid row, lock); dev pass-through config refusal outside local/ci; api DTO validation and service rules.

**Package/app integration (real MySQL, Redis, MinIO):** `packages/mail-routing/integration` recorder against MySQL (each transition, duplicate signals, concurrent signals for one delivery, aggregate + status history, outbox payload parses); `apps/delivery-worker/integration`: approval → planning rows; reinjection against an in-process fake SMTP listener (queued, partial RCPT, retry backoff, crash in the ambiguous window resolved by a bound log line, S3 object missing); tailer over a fixture log file with rotation; rate limits fail closed with Redis stopped (`docker compose stop redis` or a bad URL in-process); smtp-adapter integration: transport/tls_policy answers for lists and presets, classification at ingestion (`email_recipients.direction`, message `internal`), bounce notice matched by queue id and ENVID → delivery signal; api integration: destinations CRUD (presets, `422` reasons, `409`, audit, outbox event), delivery status endpoints, **cross-tenant `404`** for both, permission checks (`domain:read` cannot PUT; `delivery:read` required).

**Stack suites (`tests/integration/routing-*.test.ts`, WP5; real SMTP through both Postfix instances to the sinks, adapter and worker running, dev pass-through on, never the Internet):**

1. **Inbound** Internet → MX → tenant destination (`mx.sink.test`): delivered; one `delivered` audit row from `postfix_log`; sink copy has every original header byte-identical, one `X-Gateway-Trace`, a `Received: … by out.gateway.local`, no organization name or id in added headers.
2. **Mixed recipients** (one outbound submission of org `A` with SASL): internal to `A`'s second domain (M365 preset → `sink-m365` with verified TLS), internal to `A`'s third domain (Google preset → `sink-google`), external `x@ext.sink.test` (MX → `mail-sink`), and org `B`'s domain under `*.gwtenant.sink.test` (outbound via MX → gateway inbound → ingested for `B` → delivered to `B`'s destination). One parent message for `A` (`direction = outbound`), per-recipient directions `internal/internal/outbound/outbound`, three reinjection groups at least, all `delivered`; `B` gets its own message row; nothing of `B` reachable from `A`'s records. Plus an all-internal message → `email_messages.direction = internal`.
3. **Multiple domains** inbound to two domains of one org with different destinations → two groups, both delivered.
