## Original brief (verbatim, as given on 2026-11-09)

# TASK: Integrate Email Journaling + Security Scanning into the Existing Email Security Gateway

Act as a Principal Email Security Architect and Multi-Agent Engineering Lead.

We are already developing an enterprise Email Security Gateway targeting 1 million+ emails per day.

Your task is to extend the **currently developing Email Security Gateway** by adding Email Journaling, integrated security scanning, and compliance archiving capabilities.

IMPORTANT: This is an extension of the existing platform. Do not create a separate application, separate backend, separate database, separate authentication system, or duplicate email security engines.

## 1. First: Analyze the Existing Project

Before writing code:

1. Inspect the complete existing repository.
2. Understand the current architecture and development progress.
3. Identify existing SMTP gateway implementation.
4. Identify existing email ingestion and MIME parsing services.
5. Identify existing MySQL database schemas and migrations.
6. Identify existing RabbitMQ exchanges, queues and workers.
7. Identify existing security scanning engines.
8. Identify existing email lifecycle and delivery state management.
9. Identify existing tenant management, RBAC and API structures.
10. Identify existing frontend modules.

Create a gap analysis showing:

- Already implemented functionality.
- Partially implemented functionality.
- Missing functionality.
- Components that can be reused.
- Required database changes.
- Required API changes.
- Required integration changes.

Do not recreate functionality that already exists.

## 2. Extend the Existing Multi-Agent Development Team

Assign work to existing agents:

- **Agent 1 – Principal Architect:** Own architecture and integration.
- **Agent 2 – Backend Developer:** Extend existing APIs with journaling.
- **Agent 3 – Database Engineer:** Extend existing MySQL schema through migrations.
- **Agent 4 – SMTP Engineer:** Integrate journal capture into the existing Postfix pipeline.
- **Agent 5 – Processing Engineer:** Extend existing RabbitMQ workers and email lifecycle.
- **Agent 6 – Security Engineer:** Reuse existing security engines and attach scan results to journal records.
- **Agent 7 – Frontend Developer:** Add journaling and compliance features to the existing admin portal.
- **Agent 8 – DevOps Engineer:** Extend existing storage, monitoring and deployment infrastructure.
- **Agent 9 – QA Engineer:** Test the complete integrated email and journaling workflows.

Agents must use existing shared services and contracts. Do not create duplicate implementations.

## 3. Integrate Journaling into the Existing Email Lifecycle

Extend the existing email processing pipeline.

Target workflow:

Email Received
→ Existing SMTP Gateway
→ Durable Email Capture
→ Existing MIME Parser
→ Original EML Preservation
→ Existing Security Scanning Engines
→ Security Verdict
→ Existing Policy Engine
→ Delivery / Reject / Quarantine
→ Journal Record Processing
→ Encrypted Archive Storage
→ MySQL Journal Metadata
→ Journal Search and Compliance Portal

Important requirements:

- Capture inbound emails.
- Capture outbound emails.
- Capture internal emails.
- Capture rejected emails when configured by tenant policy.
- Capture quarantined emails when configured by tenant policy.
- Capture failed-delivery emails when configured by tenant policy.
- Keep journaling independent of the final delivery decision.
- Ensure the original email is preserved before any content modification.
- Do not lose journal records if the security engine or delivery worker fails.
- Prevent duplicate journal records during retries.
- Prevent SMTP reinjection loops.

Use the existing email security scanning pipeline. Do not create new Rspamd, ClamAV, YARA, URL scanning, phishing, BEC or DLP implementations if they already exist.

## 4. Integrate Security Scan Results with Journaling

For every eligible journaled email, associate the existing scanning results with the journal record.

Capture:

- Spam verdict and score.
- Malware verdict.
- ClamAV results.
- YARA findings.
- URL security results.
- Phishing verdict.
- BEC risk.
- DLP findings.
- SPF result.
- DKIM result.
- DMARC result.
- Overall risk score.
- Final security policy action.
- Scanner versions.
- Scan timestamps.
- Scan errors.

Do not execute unnecessary duplicate scans merely because an email is being journaled.

If an email is rescanned, store a separate scan execution record and preserve the previous result.

A scanner failure must be represented as SCAN_FAILED or an equivalent explicit state, never as CLEAN.

## 5. Extend Existing MySQL Database

Use MySQL 8.4 as the existing primary database.

First inspect the existing schema and reuse relevant tables.

Add only the missing tables or columns through version-controlled migrations.

Suggested entities, subject to existing schema:

- journal_configurations
- journal_policies
- journal_sources
- journal_messages
- journal_message_recipients
- journal_storage_objects
- journal_security_scan_results
- journal_security_scan_findings
- journal_retention_policies
- journal_legal_holds
- journal_export_jobs
- journal_audit_logs

Requirements:

- Maintain tenant isolation.
- Use existing organization and domain relationships.
- Use existing email/message identifiers wherever suitable.
- Avoid duplicate storage of email metadata.
- Preserve original EML in object storage, not MySQL BLOB columns.
- Store SHA-256 integrity checksums.
- Add appropriate indexes.
- Implement idempotency.
- Preserve referential integrity where practical.
- Consider data growth and retention before adding indexes or partitioning.

Do not introduce another ORM or database.

## 6. Extend Existing RabbitMQ Infrastructure

Reuse the existing exchanges, routing conventions and workers where possible.

Add journaling events only where necessary:

- journal.capture.requested
- journal.capture.completed
- journal.processing.failed
- journal.security.scan.linked
- journal.archive.persisted
- journal.export.requested
- journal.retention.expired

Use the existing transactional outbox and retry infrastructure if available.

Requirements:

- Durable processing.
- Publisher confirms.
- Manual acknowledgments.
- Retry and dead-letter handling.
- Idempotent consumers.
- Recovery after worker crashes.

Do not send raw EML or attachments through RabbitMQ.

## 7. Add Journaling Configuration to Existing Admin Portal

Extend the current admin portal. Do not build a separate frontend.

Add:

**Journaling Configuration**

- Enable/disable journaling.
- Inbound, outbound and internal journaling.
- Domain-wise configuration.
- User-wise configuration.
- Group-based configuration.
- Rejected and quarantined email capture.
- Failed-delivery capture.
- Journal retention settings.

**Journal Explorer**

- Search by sender.
- Search by recipient.
- Search by subject.
- Search by date.
- Search by message ID.
- Filter by security verdict.
- View original email.
- View scan results.
- View attachment scan results.
- Download original EML with authorization.

**Compliance Management**

- Retention policies.
- Legal holds.
- Export jobs.
- Journal audit logs.
- Journal processing failures.

Follow the existing frontend design system and permissions model.

## 8. Add Archive Storage to the Existing Platform

Reuse the current S3/object storage integration.

Requirements:

- Preserve original EML.
- Preserve attachments and MIME structure.
- Encrypt objects at rest.
- Use TLS for transport.
- Store object references and checksums in MySQL.
- Support tenant-specific retention policies.
- Prevent deletion of objects under legal hold.
- Support authorized retrieval and compliance export.
- Keep original archived content immutable at the application level.

Do not introduce a separate storage service if the current platform already provides one.

## 9. Preserve Existing Email Security and Delivery Behavior

The journaling implementation must not break existing:

- Inbound email processing.
- Outbound email processing.
- Internal email processing.
- SMTP routing.
- Security scanning.
- Quarantine.
- Delivery retries.
- Email tracking.
- Tenant policies.
- Existing APIs.
- Existing frontend functionality.

Do not delay SMTP acceptance indefinitely while waiting for asynchronous scanning or archive processing.

Only acknowledge SMTP acceptance after the existing durable acceptance requirements are satisfied, including the required durable capture and recoverable journaling intent when mandatory by policy.

If required durable persistence fails, return an appropriate temporary SMTP failure rather than falsely accepting the email.

## 10. Security and Access Control

Use existing authentication and RBAC.

Add appropriate permissions for:

- View journal records.
- Search journal records.
- Retrieve original emails.
- Download attachments.
- Export compliance records.
- Manage retention.
- Create legal holds.
- Remove legal holds.
- View audit history.

Every retrieval and export must be auditable.

Ensure one tenant cannot access another tenant's journal records.

Do not expose email content in application logs.

- First produce a repository gap analysis.
- Principal Architect approves the integration design.

- SMTP, backend and processing agents agree on contracts.
- Frontend development can proceed against approved API contracts.
- Agents must not modify the same files simultaneously.

## 13. Final Acceptance Criteria

The task is complete when:

- Email Journaling is integrated into the existing gateway.
- All three email directions are supported.
- Existing security scans are associated with journal records.
- Original emails are preserved.
- Journaling works independently of delivery outcomes according to policy.
- MySQL metadata and object storage are consistent and recoverable.
- Journal search and retrieval work in the existing admin portal.
- Retention and legal hold are operational.
- Existing email gateway features continue working.
- Automated tests and regression tests pass.
- Documentation is updated.

## Final Instruction

This is an extension of the existing Email Security Gateway, not a new application.

Inspect before implementing. Reuse before creating. Extend before replacing.

Do not overwrite existing working code, duplicate services, introduce unnecessary infrastructure or break existing functionality.

Implement the complete working feature through the existing multi-agent development workflow.
