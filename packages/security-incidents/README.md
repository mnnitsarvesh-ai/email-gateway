# @email-gateway/security-incidents

The security incident model shared by account takeover (step 8.4) and, later, advanced threat protection (ATP-4) ([design D12, D24](../../docs/plan/steps/24-account-takeover-core.md), [ADR-0075](../../docs/architecture/adr/0075-security-incident-model-shared-ato-atp.md)). One state machine, one timeline, one link table and one pair of incident events for every incident category; each category plugs in through a handler (subject types, read/manage permissions, detail, transition hook, feedback schema, report sections). ATO registers `account_takeover` (`atoIncidentHandler` of `@email-gateway/ato-detection`). Writer only (ADR-0014); the store is the **only** writer of `security_incidents`, `security_incident_events` and `security_incident_links`.

## Behaviour

- **One active incident per subject and category**: the unique key `(organization_id, category, subject_type, subject_ref_id, active_marker)` (generated `active_marker` = 1 for the four active states). `open` checks first and maps a racing duplicate (P2002) to `IncidentActiveConflictError` carrying the active incident's id.
- **State changes** run under `SELECT … FOR UPDATE` on the tenant's row plus a `row_version` compare-and-set (`expectedRowVersion` optional for callers that read earlier). `transition` validates the edge, the resolution code and the note (10–4 000 characters; free notes 1–4 000), validates `categoryFeedback` with the handler's strict schema, writes the timeline entry, runs the handler's `onTransition` hook in the same transaction, emits `security.incident.updated.v1` and writes the audit row.
- **Severity**: a `system` actor only raises (`setSeverity`, never automatic de-escalation); users may lower; `escalate` raises to at least `high` and records `escalated`.
- **Events**: `security.incident.created.v1` on open; `security.incident.updated.v1` on every status, severity, assignee or resolution change; an evidence-only update at most once per 15 minutes per incident (`last_update_event_at`). Payloads are parsed by the registry schema before insertion.
- **Audit**: resource type `security_incident`, resource id = public id, actions `security_incident.created`, `.status_changed`, `.assigned`, `.note_added`, `.severity_changed`, `.report_exported`; notes are audited by length only.
- **Category isolation**: `findByPublicId` and `list` take the categories the caller may read (`categoriesReadableBy(permissions)`); another category's incident looks missing (the api answers 404).

## Tests

- Unit (`pnpm --filter @email-gateway/security-incidents test`): every allowed and refused transition (6 × 6), resolution codes and note lengths, registry permissions and isolation, audit scrubbing and the audit row (override, request and correlation ids, clipping), report assembly and masking, equality of the event-contracts mirrors with the shared vocabulary, the runtime/test-kit boundary.
- Integration (`pnpm --filter @email-gateway/security-incidents test:integration`, real MySQL writer from `.env`, synthetic `it-ato-si-*` organizations removed afterwards): open with its timeline entry, event and audit row; one active incident per subject; a full transition walk with events and audit; CAS and tenant checks; feedback validation and the hook; assignment, severity, escalation and notes; link caps, duplicates and the 15-minute evidence throttle; the report; a second fake category proving category isolation.
