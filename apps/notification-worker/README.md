# notification-worker

Notification Service. **Step 5.2** ([design](../../docs/plan/steps/16-policy-engine.md) P15, P24, P25; runbook [policy-notifications](../../docs/runbooks/policy-notifications.md)) gives it its first job: the **policy notices** requested by the policy-engine — ALERT actions (to the organization's policy administrators) and sender non-delivery notices of rejected outbound/internal mail. **Step 5.3** ([design](../../docs/plan/steps/17-quarantine.md) Q16, Q20) adds the **quarantine notices** (`mail.quarantine.notification_requested.v1` on the same queue and ledger): per-user digests, approval requests and decisions, blocked releases, rate-bounded admin alerts and sender notices of rejected outbound/internal entries (`src/notifications/quarantine-notification.handler.ts`, `quarantine-reads.ts`, `quarantine-templates.ts`; metric `notification_quarantine_messages_total{kind,result}`; Message-ID `<quarantine-notice.<eventId>@<From domain>>`). Step API-2 (R10.5): a digest entry with `location = mailbox` adds a `Location:` line ("in your mailbox's quarantine folder" / "Junk folder" / "deleted items"); gateway entries render unchanged. **Step 6.2** ([design](../../docs/plan/steps/19-webhooks-notifications.md) N1–N4, ADR-0056) adds the **security alerts** (`notification.alert_requested.v1`, same queue and ledger) and applies the per-user **opt-outs** of the 6.2 preference center to the existing admin kinds (see below). **Step AI-R** ([design](../../docs/plan/steps/31-ai-chat-reports.md) D6–D8, ADR-0095) adds the **assistant report emails** (`assistant.report.email_requested.v1`, same queue and ledger; see below). DLP incident notifications remain out of scope.

## Run and test

```bash
pnpm --filter @email-gateway/notification-worker dev               # reads ../../.env, port 3050
pnpm --filter @email-gateway/notification-worker test              # unit (config, templates, mailer, handlers, preference filter, dispatch, wiring)
pnpm --filter @email-gateway/notification-worker test:integration  # real MySQL writer + RabbitMQ (throwaway vhost) + MinIO + in-process SMTP sink
```

## What it does

| Piece                                                                                                                                                                                                                                                                                    | File                                                                        |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| Consumer of `email.notifications` (`mail.policy.notification_requested.v1`), ledger `notification-worker.policy`, `processOnceHandler` with `NOTIFICATION_DB_TX_TIMEOUT_MS`, retry/dead-letter per topology v9 (hold, 8 attempts, 5 s–1 min, 24 h), consumer progress for the reconciler | `src/notifications/notifications.module.ts`                                 |
| Handler: writer reads (organization-checked, echo-checked), recipient resolution, template, send, metrics                                                                                                                                                                                | `src/notifications/policy-notification.handler.ts`, `notification-reads.ts` |
| Fixed plain-text templates, deterministic `Message-ID: <policy-notice.<eventId>@<From domain>>`                                                                                                                                                                                          | `src/notifications/templates.ts`                                            |
| nodemailer over the `NOTIFY_SMTP_*` relay (the api's transport options; plaintext only when APP_ENV is local or ci), Bcc only                                                                                                                                                            | `src/notifications/mailer.ts`                                               |
| `notification_policy_messages_total{kind, result}` (`sent`, `no_recipients`, `disabled`, `failed`), `notification_send_duration_seconds`                                                                                                                                                 | `src/notifications/notification-metrics.ts`                                 |

**Recipients (P25).** `policy_alert`: active, non-deleted, email-verified users of the event's organization holding `policy:publish` through a role (≤ `NOTIFICATION_MAX_RECIPIENTS`, sorted by user id); none → `no_recipients`. `sender_non_delivery`: the message's `envelope_from` from the writer row of the event's organization, only when its domain is an active domain of that organization (never an external address); else `no_recipients`. An event naming a message that is not the organization's is dead-lettered (`message_not_found`) without a send. `alerts.enabled` is evaluated by the policy-engine (a disabled ALERT is recorded there and never requested).

**Privacy.** A notice carries the organization name, the message public id, its received time, direction, the disposition, the decisive policy name and rule id and a portal link (`PORTAL_PUBLIC_URL/messages/<id>`); the sender notice adds the Internet-Message-ID and the recipient count. Never a subject, body, file name, URL of the message or any other address; database text is reduced to printable, bounded single-line text.

**Delivery semantics.** At least once: the SMTP submission runs inside the idempotency transaction before the ledger commits, so a crash between them can send a notice twice (same Message-ID). An SMTP failure is thrown and retried by the topology, then dead-lettered. Without `NOTIFY_SMTP_HOST` nothing is sent (`disabled`).

## Security alerts and preferences (step 6.2)

| Piece                                                                                                                                                                                                                                                   | File                                                                 |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| Dispatch by event type on `email.notifications` (`mail.policy.notification_requested.v1`, `mail.quarantine.notification_requested.v1`, `notification.alert_requested.v1`); one ledger `notification-worker.policy`; an unexpected type is dead-lettered | `src/notifications/notifications.module.ts` (`dispatchNotification`) |
| Alert handler: tenant settings, facts, recipients, one mail                                                                                                                                                                                             | `src/notifications/alert-notification.handler.ts`, `alert-reads.ts`  |
| Fixed plain-text alert templates, `Message-ID: <security-alert.<eventId>@<From domain>>`                                                                                                                                                                | `src/notifications/alert-templates.ts`                               |
| Opt-out filter shared by every admin kind                                                                                                                                                                                                               | `src/notifications/preference-filter.ts`                             |
| `notification_alert_messages_total{kind, result}` (`sent`, `no_recipients`, `disabled`, `failed`), `notification_alerts_suppressed_total{kind, reason}` (`opt_out`, `disabled`, `invalid_contact`)                                                      | `src/notifications/notification-metrics.ts`                          |

**Kinds.** `threat_detected` (an `email.threat.detected` public event at or above the tenant's `alerts.threatDetected.minSeverity`, default `high`), `domain_dns_failed` (a `domain.dns.failed` public event), `webhook_disabled` (a subscription auto-disabled by the webhook-worker). The "quarantine" and "policy triggered" alerts are the existing `admin_alert` (5.3) and `policy_alert` (5.2): no second mechanism.

**Throttling is done by the producer.** The webhook-worker writes the alert request only for the first event of a throttle window (`notification_alert_windows`, one per organization, kind, scope and window; `alerts.*.throttleMinutes`) and carries `counts.suppressedBefore` (events of the previous window that were not alerted). The worker never throttles; it renders `Events in this window so far` from the window row at send time.

**At send time** (writer, inside the ledger transaction, every read scoped to the envelope's organization and echo-checked):

1. Tenant settings (`notification_settings`, §6.3): a kind switched off since the request, or a threat below a raised `minSeverity`, → `disabled` (and `notification_alerts_suppressed_total{reason="disabled"}`); nothing else is read.
2. Facts: threat → the stored public event (`webhook_events` by `refs.webhookEventId` within ±24 h of the window; verdict, stage, severity) and the message identity (public id, received time; must match `refs`); DNS → the stored public event (failure kind, reason code, record purposes), the tenant's domain (`refs.domainId`) and its records still `invalid`/`missing`; webhook disabled → the subscription's name and failure counters (never its URL or secrets). A missing reference, another organization's row or a mismatch between the refs and the stored event is **dead-lettered** without a send (`organization_not_found`, `webhook_event_not_found`, `webhook_event_mismatch`, `message_not_found`, `message_mismatch`, `domain_not_found`, `subscription_not_found`).
3. Recipients (N3): active, non-deleted, e-mail-verified users of the organization holding `ALERT_RECIPIENT_PERMISSION[kind]` (`threat_detected` → `quarantine:approve`, `domain_dns_failed` → `domain:manage`, `webhook_disabled` → `webhook:manage`) through a role of the organization or a system role, minus users who opted out of the kind, sorted by user id, at most `NOTIFICATION_MAX_RECIPIENTS`; plus `organization_settings.notification_email` when `alerts.includeOrganizationContact` is true (default; de-duplicated; a value that is not an address is skipped and counted `invalid_contact`). None → `no_recipients`.
4. One plain-text mail through the relay, recipients as Bcc, deterministic Message-ID, before the ledger commits (at least once; a redelivery after the commit sends nothing; no relay → `disabled`, like the other kinds).

**API-mode alert (step API-1 D11.3).** `api_mode_unhealthy` (requested by the mailbox-worker's health role, ref `apiModeConnectionId`, severity `medium` degraded / `high` failing, one throttle window per API-mode connection) has no tenant setting (always on, like `journal_intake_silent`); recipients hold `remediation:read`; facts read at send time from `api_mode_connections` (provider, health now, the `api-mode-health/1` checks that warn or fail, by title) and its 8.2 connection's display name; link `/api-mode?connection=<id>`; never a mailbox address or check evidence. Preference kind `api_mode_unhealthy` (filters nobody until the shared `PREFERENCE_KINDS` vocabulary lists it, as for `journal_intake_silent`).

**API-mode clawback and report alerts (step API-3 C6, C13).** `api_mode_purge_approval` (requested by the api at submit and by the mailbox-worker `clawback` role for `review_required`; ref `clawbackId`; one throttle window per clawback) goes to holders of `remediation:purge`; facts read at send time from `api_clawbacks` (trigger, status, explicit action, eligible mailboxes and copies, approval reasons, approval state and expiry); link `/api-mode?tab=purge&clawback=<id>`. `api_mode_report_received` (mailbox-worker `reports` role; no refs; one window per organization) goes to holders of `remediation:write`; facts: bounded counts of reports waiting for triage, in review and received in the window, and the oldest waiting time; link `/api-mode?tab=reports`. Both are always on (no tenant setting), never carry an address, subject, sender or criteria value, and filter nobody by preference until `PREFERENCE_KINDS` lists them. The `api_mode_unhealthy` check titles include `clawback.stalled` and `reports.backlog`.

**Reporter feedback (step API-3 C12, ADR-0104).** `mail.report.feedback_requested.v1` (`{ reportId, kind: received|resolved }`, same queue; the handler also writes its own ledger row `notification-worker.report-feedback`) is handled by `src/notifications/report-feedback.handler.ts`: the `api_user_reports` row is read at send time scoped to the envelope's organization (missing → acked, counted `report_missing`); nothing is sent for a `rejected` report, a `resolved` request without an analyst verdict, a reporter address outside the organization's verified/active domains, or an address that no longer resolves to an organization mailbox (`api_mailbox_addresses`, mailbox not deleted) or active user. Otherwise one mail `To:` the reporter through the `NOTIFY_SMTP_*` relay, fixed text + HTML per kind and verdict (`malicious`, `phishing_simulation`, `spam`, `clean`, `inconclusive`) with the report reference and date only — never the reported message's subject, sender or body or the analyst note; `Message-ID: <report-feedback.<eventId>@<From domain>>`. Metric `notification_report_feedback_messages_total{kind="report_feedback_received|report_feedback_resolved",result}`.

**Preferences (N3, N4).** `notification_user_preferences.preferences.optOut` (written by the api's `PUT /notifications/preferences`) lists the kinds a user does not want: the three alert kinds, `policy_alert`, `quarantine_admin_alert` (5.3 `admin_alert`) and `quarantine_approval_requested` (5.3 `approval_requested`). `PreferenceFilter` removes opted-out users **before** the recipient cap (paging by user id, so an opted-out administrator never shortens the list while more holders exist) and counts them in `notification_alerts_suppressed_total{kind, reason="opt_out"}`. A stored document that does not validate opts out of nothing (logged without values). `approval_decided`, `release_blocked` and the sender notices are not optional; the quarantine digest opt-out stays `quarantine_user_preferences.digest_opt_out`, honored by the 5.3 scheduler and the digest handler (unchanged).

**Privacy.** An alert carries the organization name, the kind, severity, window, counts and per kind: verdict, detection stage, the message public id and received time of the first event and `PORTAL_PUBLIC_URL/messages/<id>`; the tenant's own domain name, failed and still-failing record purposes and `/domains/<id>`; the subscription name (printable, ≤ 80 characters, hidden when it looks like an address or URL) with its public id, status, disable reason, consecutive failures, failing-since time and `/webhooks/<id>`. **Never** a subject, body, file name, sender or recipient address, Internet-Message-ID, URL found in mail, endpoint URL or secret; recipients only see their own mailbox in the envelope (Bcc).

## Assistant report emails (step AI-R)

A user confirms `report_send_email` in the assistant chat; the api writes an `ai_chat_report_deliveries` row (`queued`) and the outbox event `assistant.report.email_requested.v1` (payload ids only: `deliveryId`, `reportId`, `requestedAt`; eventId = the delivery id) in the confirm transaction. The event is published to `email.policy` and bound to `email.notifications` (topology v15).

| Piece                                                                                                                                                                                                                                    | File                                              |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------- |
| Handler: decisions, bounded object read, one mail, conditional status update                                                                                                                                                             | `src/notifications/assistant-report.handler.ts`   |
| Writer reads and `queued → sent/failed` writes, all scoped to the envelope's organization and echo-checked; the mail-bucket reader (key under `org/<organizationId>/assistant/report/`, `Range` read ≤ bound + 1 byte, size and SHA-256) | `src/notifications/assistant-report-reads.ts`     |
| Fixed subject and plain-text part, attachment name, `Message-ID: <assistant-report.<deliveryId>@<From domain>>`                                                                                                                          | `src/notifications/assistant-report-templates.ts` |
| `NoticeMail.to` (one `To:` recipient, no Bcc), `html` (base64, byte-exact) and `attachments` (Buffer content only; file and URL access stay disabled)                                                                                    | `src/notifications/mailer.ts`                     |
| `notification_assistant_report_emails_total{result}` (`sent`, `failed`, `not_applicable`, `skipped`); send duration kind `assistant_report`                                                                                              | `src/notifications/notification-metrics.ts`       |

**Decisions** (writer, inside the ledger transaction, every statement filtered by the envelope's organization):

1. The delivery by public id with its report and the organization name. None → `not_applicable`, nothing sent (the organization or conversation was purged, or the delivery is another organization's: it is never read, sent or updated). A `reportId` that is not the delivery's report is dead-lettered (`assistant_report_delivery_mismatch`).
2. Delivery not `queued` → `skipped` (a redelivery or a second event after the row was settled).
3. Report not `available`, or the recipient address purged → delivery `failed` `assistant_report_purged`. A stored recipient that is not a single address → `failed` `assistant_report_recipient_invalid`.
4. No relay (`NOTIFY_SMTP_HOST` unset) → `failed` `relay_not_configured`.
5. The stored HTML from `S3_BUCKET_MAIL`: missing object (or no key) → `failed` `assistant_report_missing`; a key outside `org/<organizationId>/assistant/report/` (or with empty, `.`, `..` segments), a row `size_bytes` above `NOTIFICATION_REPORT_MAX_HTML_BYTES`, an object larger than `min(size_bytes, NOTIFICATION_REPORT_MAX_HTML_BYTES)` (the read stops at that bound + 1 byte), a different size or SHA-256, or bytes that are not UTF-8 → `failed` `assistant_report_integrity`. Nothing is sent in any of these cases. Other S3 errors are thrown and retried.
6. One mail `To:` the stored recipient (envelope recipient the same; no Bcc), `From:` `NOTIFY_SMTP_FROM`, subject `Security report: <organization> (<from> to <to> UTC)` (printable, single line, ≤ 200 characters), `multipart/mixed` of a `multipart/alternative` (fixed plain-text part: title, organization, period, the row's `figures`, the attachment hint and `PORTAL_PUBLIC_URL/assistant/reports/<reportId>` "(only the person who generated it can open it in the portal)"; the stored HTML as the HTML part, base64) and the same bytes attached as `security-report-<yyyy-mm-dd>.html` (`text/html; charset=utf-8`, UTC generation date); `Auto-Submitted: auto-generated`, `X-Auto-Response-Suppress: All`. Then `UPDATE … SET status='sent', sent_at, message_id WHERE id AND organization_id AND status='queued'`. A relay failure throws `NoticeSendError` (the queue's retry; the api fails a row still `queued` after 25 h, D7).

**Semantics and privacy.** At least once, like the notices: a crash between the SMTP submission and the commit can send the report twice (same Message-ID). Logs and metrics carry the event, delivery, report and organization ids and reason codes only: never the address, subject, title or HTML. The worker writes only the delivery row's status columns and no audit row (the api audits the request). The copy in the recipient's mailbox is outside the platform's control.

## Configuration

`DATABASE_URL`, `RABBITMQ_NOTIFICATION_URL` (`eg-notification`: read `email.notifications`, write retry and dead-letter copies), `NOTIFY_SMTP_HOST` / `_PORT` / `_SECURE` / `_USER` / `_PASSWORD` / `_CA_PATH` / `_FROM`, `NOTIFICATION_PREFETCH` (4, 1–32), `NOTIFICATION_DB_TX_TIMEOUT_MS` (120 000, 120 000–600 000), `NOTIFICATION_MAX_RECIPIENTS` (50, 1–500), `PORTAL_PUBLIC_URL` (https in staging/production), `S3_REGION` / `S3_ENDPOINT` / `S3_FORCE_PATH_STYLE` / `S3_BUCKET_MAIL` / `S3_BUCKET_ARCHIVE` / `S3_ACCESS_KEY_ID` / `S3_SECRET_ACCESS_KEY` (step AI-R; Compose passes them through `x-node-env`; on AWS the IRSA role needs only `s3:GetObject` on `org/*/assistant/report/*` of the mail bucket), `NOTIFICATION_REPORT_MAX_HTML_BYTES` (2 097 152, 65 536–4 194 304). Readiness: `mysql`, `rabbitmq` (not S3: an object storage outage fails or retries report emails only and does not stop the other notices). Locally the relay is `postfix-notify`, which discards mail unless `NOTIFY_RELAY_HOST` is set; Compose maps `NOTIFY_SMTP_HOST: ${NOTIFICATION_SMTP_HOST:-postfix-notify}` so a test can point the worker at a mail sink.
