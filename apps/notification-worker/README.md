# notification-worker

Notification Service. **Step 5.2** ([design](../../docs/plan/steps/16-policy-engine.md) P15, P24, P25; runbook [policy-notifications](../../docs/runbooks/policy-notifications.md)) gives it its first job: the **policy notices** requested by the policy-engine — ALERT actions (to the organization's policy administrators) and sender non-delivery notices of rejected outbound/internal mail. **Step 5.3** ([design](../../docs/plan/steps/17-quarantine.md) Q16, Q20) adds the **quarantine notices** (`mail.quarantine.notification_requested.v1` on the same queue and ledger): per-user digests, approval requests and decisions, blocked releases, rate-bounded admin alerts and sender notices of rejected outbound/internal entries (`src/notifications/quarantine-notification.handler.ts`, `quarantine-reads.ts`, `quarantine-templates.ts`; metric `notification_quarantine_messages_total{kind,result}`; Message-ID `<quarantine-notice.<eventId>@<From domain>>`). **Step 6.2** ([design](../../docs/plan/steps/19-webhooks-notifications.md) N1–N4, ADR-0056) adds the **security alerts** (`notification.alert_requested.v1`, same queue and ledger) and applies the per-user **opt-outs** of the 6.2 preference center to the existing admin kinds (see below). DLP incident notifications remain out of scope.

## Run and test

```bash
pnpm --filter @email-gateway/notification-worker dev               # reads ../../.env, port 3050
pnpm --filter @email-gateway/notification-worker test              # unit (config, templates, mailer, handlers, preference filter, dispatch, wiring)
pnpm --filter @email-gateway/notification-worker test:integration  # real MySQL writer + RabbitMQ (throwaway vhost) + in-process SMTP sink
```

## What it does

| Piece                                                                                                                                                                                                                                                                                    | File                                                                        |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| Consumer of `email.notifications` (`mail.policy.notification_requested.v1`), ledger `notification-worker.policy`, `processOnceHandler` with `NOTIFICATION_DB_TX_TIMEOUT_MS`, retry/dead-letter per topology v9 (hold, 8 attempts, 5 s–1 min, 24 h), consumer progress for the reconciler | `src/notifications/notifications.module.ts`                                 |
| Handler: writer reads (organization-checked, echo-checked), recipient resolution, template, send, metrics                                                                                                                                                                                | `src/notifications/policy-notification.handler.ts`, `notification-reads.ts` |
| Fixed plain-text templates, deterministic `Message-ID: <policy-notice.<eventId>@<From domain>>`                                                                                                                                                                                          | `src/notifications/templates.ts`                                            |
| nodemailer over the `NOTIFY_SMTP_*` relay (the api's transport options; plaintext only when APP_ENV is local or ci), Bcc only                                                                                                                                                            | `src/notifications/mailer.ts`                                               |
| `notification_policy_messages_total{kind, result}` (`sent`, `no_recipients`, `disabled`, `failed`), `notification_send_duration_seconds`                                                                                                                                                 | `src/notifications/notification-metrics.ts`                                 |

**Recipients (P25).** `policy_alert`: active, non-deleted, email-verified users of the event's organization holding `policy:publish` through a role (≤ `NOTIFICATION_MAX_RECIPIENTS`, sorted by user id); none → `no_recipients`. `sender_non_delivery`: the message's `envelope_from` from the writer row of the event's organization, only when its domain is an active domain of that organization (never an external address); else `no_recipients`. An event naming a message that is not the organization's is dead-lettered (`message_not_found`) without a send. `alerts.enabled` is evaluated by the policy-engine (a disabled ALERT is recorded there and never requested).

**Privacy.** A notice carries the organization name, the message public id, its received time, direction, the disposition, the decisive policy name and rule id and a portal link (`PORTAL_PUBLIC_URL/messages/<id>`); the sender notice adds the Internet-Message-ID and the recipient count. Never a subject, body, file name, URL of the message or any other address; database text is reduced to printable, bounded single-line text.

**Delivery semantics.** At least once: the SMTP submission runs inside the idempotency transaction before the ledger commits, so a crash between them can send a notice twice (same Message-ID). An SMTP failure is thrown and retried by the topology, then dead-lettered. Without `NOTIFY_SMTP_HOST` nothing is sent (`disabled`).

## Security alerts and preferences (step 6.2)

| Piece                                                                                                                                                                                                                                                   | File                                                                 |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| Dispatch by event type on `email.notifications` (`mail.policy.notification_requested.v1`, `mail.quarantine.notification_requested.v1`, `notification.alert_requested.v1`); one ledger `notification-worker.policy`; an unexpected type is dead-lettered | `src/notifications/notifications.module.ts` (`dispatchNotification`) |
| Alert handler: tenant settings, facts, recipients, one mail                                                                                                                                                                                             | `src/notifications/alert-notification.handler.ts`, `alert-reads.ts`  |
| Fixed plain-text alert templates, `Message-ID: <security-alert.<eventId>@<From domain>>`                                                                                                                                                                | `src/notifications/alert-templates.ts`                               |
| Opt-out filter shared by every admin kind                                                                                                                                                                                                               | `src/notifications/preference-filter.ts`                             |
| `notification_alert_messages_total{kind, result}` (`sent`, `no_recipients`, `disabled`, `failed`), `notification_alerts_suppressed_total{kind, reason}` (`opt_out`, `disabled`, `invalid_contact`)                                                      | `src/notifications/notification-metrics.ts`                          |

**Kinds.** `threat_detected` (an `email.threat.detected` public event at or above the tenant's `alerts.threatDetected.minSeverity`, default `high`), `domain_dns_failed` (a `domain.dns.failed` public event), `webhook_disabled` (a subscription auto-disabled by the webhook-worker). The "quarantine" and "policy triggered" alerts are the existing `admin_alert` (5.3) and `policy_alert` (5.2): no second mechanism.

**Throttling is done by the producer.** The webhook-worker writes the alert request only for the first event of a throttle window (`notification_alert_windows`, one per organization, kind, scope and window; `alerts.*.throttleMinutes`) and carries `counts.suppressedBefore` (events of the previous window that were not alerted). The worker never throttles; it renders `Events in this window so far` from the window row at send time.

**At send time** (writer, inside the ledger transaction, every read scoped to the envelope's organization and echo-checked):

1. Tenant settings (`notification_settings`, §6.3): a kind switched off since the request, or a threat below a raised `minSeverity`, → `disabled` (and `notification_alerts_suppressed_total{reason="disabled"}`); nothing else is read.
2. Facts: threat → the stored public event (`webhook_events` by `refs.webhookEventId` within ±24 h of the window; verdict, stage, severity) and the message identity (public id, received time; must match `refs`); DNS → the stored public event (failure kind, reason code, record purposes), the tenant's domain (`refs.domainId`) and its records still `invalid`/`missing`; webhook disabled → the subscription's name and failure counters (never its URL or secrets). A missing reference, another organization's row or a mismatch between the refs and the stored event is **dead-lettered** without a send (`organization_not_found`, `webhook_event_not_found`, `webhook_event_mismatch`, `message_not_found`, `message_mismatch`, `domain_not_found`, `subscription_not_found`).
3. Recipients (N3): active, non-deleted, e-mail-verified users of the organization holding `ALERT_RECIPIENT_PERMISSION[kind]` (`threat_detected` → `quarantine:approve`, `domain_dns_failed` → `domain:manage`, `webhook_disabled` → `webhook:manage`) through a role of the organization or a system role, minus users who opted out of the kind, sorted by user id, at most `NOTIFICATION_MAX_RECIPIENTS`; plus `organization_settings.notification_email` when `alerts.includeOrganizationContact` is true (default; de-duplicated; a value that is not an address is skipped and counted `invalid_contact`). None → `no_recipients`.
4. One plain-text mail through the relay, recipients as Bcc, deterministic Message-ID, before the ledger commits (at least once; a redelivery after the commit sends nothing; no relay → `disabled`, like the other kinds).

**Preferences (N3, N4).** `notification_user_preferences.preferences.optOut` (written by the api's `PUT /notifications/preferences`) lists the kinds a user does not want: the three alert kinds, `policy_alert`, `quarantine_admin_alert` (5.3 `admin_alert`) and `quarantine_approval_requested` (5.3 `approval_requested`). `PreferenceFilter` removes opted-out users **before** the recipient cap (paging by user id, so an opted-out administrator never shortens the list while more holders exist) and counts them in `notification_alerts_suppressed_total{kind, reason="opt_out"}`. A stored document that does not validate opts out of nothing (logged without values). `approval_decided`, `release_blocked` and the sender notices are not optional; the quarantine digest opt-out stays `quarantine_user_preferences.digest_opt_out`, honored by the 5.3 scheduler and the digest handler (unchanged).

**Privacy.** An alert carries the organization name, the kind, severity, window, counts and per kind: verdict, detection stage, the message public id and received time of the first event and `PORTAL_PUBLIC_URL/messages/<id>`; the tenant's own domain name, failed and still-failing record purposes and `/domains/<id>`; the subscription name (printable, ≤ 80 characters, hidden when it looks like an address or URL) with its public id, status, disable reason, consecutive failures, failing-since time and `/webhooks/<id>`. **Never** a subject, body, file name, sender or recipient address, Internet-Message-ID, URL found in mail, endpoint URL or secret; recipients only see their own mailbox in the envelope (Bcc).

## Configuration

`DATABASE_URL`, `RABBITMQ_NOTIFICATION_URL` (`eg-notification`: read `email.notifications`, write retry and dead-letter copies), `NOTIFY_SMTP_HOST` / `_PORT` / `_SECURE` / `_USER` / `_PASSWORD` / `_CA_PATH` / `_FROM`, `NOTIFICATION_PREFETCH` (4, 1–32), `NOTIFICATION_DB_TX_TIMEOUT_MS` (120 000, 120 000–600 000), `NOTIFICATION_MAX_RECIPIENTS` (50, 1–500), `PORTAL_PUBLIC_URL` (https in staging/production). Readiness: `mysql`, `rabbitmq`. Locally the relay is `postfix-notify`, which discards mail unless `NOTIFY_RELAY_HOST` is set; Compose maps `NOTIFY_SMTP_HOST: ${NOTIFICATION_SMTP_HOST:-postfix-notify}` so a test can point the worker at a mail sink.
