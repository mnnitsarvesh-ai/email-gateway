# delivery-worker

Per-recipient delivery of approved mail (step 2.3, [design](../../docs/plan/steps/05-routing.md), [ADR-0021](../../docs/architecture/adr/0021-mail-routing-and-delivery-status.md), operations: [mail-routing.md](../../docs/deployment/mail-routing.md)). The worker plans approved recipients into reinjection groups, hands each group to postfix-outbound (`10026` inbound/internal, `10027` outbound), and turns postfix-outbound's delivery log into per-recipient status. Postfix owns every remote retry (ADR-0006); the worker retries only its own hop. Data plane: the MySQL **writer** only (ADR-0014), Redis (rate limits), S3 (EML stream, never buffered whole), `GET /metrics`, `GET /health/{live,ready}` (mysql, rabbitmq, redis, s3) on port 3040.

**Transport (step 3.2, [design](../../docs/plan/steps/07-rabbitmq.md) Q13, [ADR-0024](../../docs/architecture/adr/0024-rabbitmq-topology-retry-dead-letter.md)):** approvals arrive over **RabbitMQ**, queue `email.delivery.pending`, with the worker's own least-privilege user (`RABBITMQ_DELIVERY_WORKER_URL`: read `email.delivery.pending`, write `email.delivery` and `email.events` for delay and dead-letter copies, limited by topic permissions to its own `retry.`/`delay.`/`dead-letter.email.delivery.pending` keys; no configure rights). Readiness `rabbitmq` = connected, not blocked, `email.delivery`, `email.events` and `email.delivery.pending` verified passively. Producers write approvals to `message_outbox`; the `event-relay` publishes them. The development pass-through therefore reaches the planner through **outbox → event-relay → `email.delivery.pending`**, and the step 2.3 end-to-end path runs through the broker. There is no outbox-poller fallback for the planner (design Q14): during a broker outage approvals stay unpublished in the outbox, and the relay's reconciler re-drives published approvals that were never planned (not those the planner dead-lettered or that are still retrying: the consumer records them in `message_consumer_progress`).

**Approval provenance (step 3.2 review round 1):** the broker is a trust boundary, so the planner plans an approval only when the gateway issued it: inside the `processOnce` transaction, once the message is found (an approval of a message that does not exist is rejected and acknowledged: nothing to plan), `assertApprovalIssued` requires a `message_outbox` row with the same `event_id`, `event_type` and `organization_id` (index `event_id`, partitions pruned by `created_at ≥ received_at − 5 min`) whose payload equals the delivered one. No row → fatal dead letter `approval_not_issued`; a different payload → `approval_mismatch`. Replays and re-drives keep event id and payload and pass; approvals older than the 7-day outbox retention can no longer be proven and are dead-lettered (fail closed).

## Configuration

`src/config.ts` validates every key it reads (design §5, `.env.example` section "Mail routing and delivery (step 2.3)"): `DELIVERY_*`, `ROUTING_MAX_RECEIVED_HEADERS`, `ROUTING_MAX_GATEWAY_PASSES`, `GATEWAY_TRACE_SECRET` (≥ 32), `GATEWAY_TRACE_ID`, `POSTFIX_OUTBOUND_MYHOSTNAME`, `INGEST_HEADER_MAX_BYTES`, `REDIS_URL`, `S3_*`, `DATABASE_URL`, `RABBITMQ_DELIVERY_WORKER_URL` (required, comma-separated node URLs, `_FILE` supported), `DELIVERY_APPROVAL_PREFETCH` (1–64, default 4), the base keys and `HTTP_PORT` (3040). `DELIVERY_OUTBOX_*` now configure only the dev pass-through's poller; `RABBITMQ_URL` and `RABBITMQ_PREFETCH` are no longer read. Startup refuses `DELIVERY_DEV_PASSTHROUGH_ENABLED=true` unless `APP_ENV` is `local` or `ci`.

**Writer client and transactions (step 4.2 §6, [§12 WP4](../../docs/plan/steps/10-attachment-scanning.md#12-deviations-log)).** With the Prisma 6.19 library engine, a connection whose statement the client abandons (an interactive transaction that expires, or a `socket_timeout`) goes back to the pool with the reply unread, and the next query on it reads that reply (the step 4.1 "wrong reads after a writer pause"; reproduced by `integration/writer-stall.test.ts`). So: `DELIVERY_DB_TX_TIMEOUT_MS` (default 120 000, 60 000–900 000) is the budget (timeout and maxWait) of **every** interactive transaction of the worker (planner, recorder, dev pass-through, claim, result commits, reconciler; the module also wraps the writer with `withTransactionDefaults`), longer than MySQL's `innodb_lock_wait_timeout` (50 s) and the stalls the worker rides through; `DATABASE_SOCKET_TIMEOUT_SECONDS` (default **0**, none) is applied through the shared `databaseClientUrl` and, when set, must be shorter than that budget (config refuses otherwise) — leave it 0 until the driver closes timed-out connections (F3). Defensive checks: `ReinjectionStore.context()`, `activeDeliveries()` and `approvalTime()` verify the identifying columns of their results (message id/organization/`received_at`, each delivery's `reinjection_id`, each recipient requested and present, the approval event); a mismatch is `InconsistentReadError` → the row is rescheduled with the attempt refunded (`delivery_inconsistent_reads_total{read}`). A reinjection whose message row is not found is rescheduled with backoff (error class `context_missing`, `delivery_reinjection_context_missing_total{result="retry"}`) until `DELIVERY_REINJECT_MAX_ATTEMPTS` (default 10); the final attempt fails the row and its active deliveries in one transaction (`failed`, reason `message_missing`, through the shared recorder; deliveries the recorder cannot resolve because the message is gone are failed directly).

## Running on the host

```sh
docker compose --profile smtp-test up -d --wait     # infra + reinject-forwarder (127.0.0.1:2626/2627)
pnpm --filter @email-gateway/smtp-adapter dev        # LMTP ingestion, socketmap and policy for Postfix
pnpm --filter @email-gateway/delivery-worker dev     # reads ../../.env; cwd apps/delivery-worker
```

The local `.env` points the worker at `127.0.0.1:2626/2627` and at `../../.local/postfix-outbound-log/maillog` (relative to `apps/delivery-worker`). Built output: `node --env-file=../../.env dist/main.js` from `apps/delivery-worker`.

## Tests

- `pnpm --filter @email-gateway/delivery-worker test`: unit tests (`src/**/*.test.ts`).
- `integration/writer-stall.test.ts` (part of the integration suite): a test-only TCP proxy (`integration/support/freeze-proxy.ts`) freezes the writer connection in both directions; it pins the engine defect (`it.fails`: an expired transaction and a socket timeout each shift later results on the connection) and proves the worker's claim survives a 7 s stall with every later read correct (connection_limit 1 and 2).
- `pnpm --filter @email-gateway/delivery-worker run test:integration`: against the real MySQL writer, Redis, MinIO and RabbitMQ from `.env`, with an in-process fake reinjection listener (`smtp-server`); fixtures in `it-*` organizations, cleaned up afterwards; fixture messages are inserted in a lifecycle state (default `approved`, the dev pass-through tests `scanned`/`scan_failed`) with matching history rows (step 3.3 L8.6). The lifecycle cases: the pass-through applies E27 for `scanned.v1` with `outcome = scanned` and writes the scan round as `lifecycleRound` (round 0 and a rescan round, both planned), never approves `scan_failed`, skips a message not `scanned` (one `lifecycle.ignored` row); the planner applies E20, plans a second chunk while `delivery_pending`, rejects approvals of an older round and of messages not `approved` (`persisted`, `quarantined`), and an all-refused plan ends `rejected/delivery_failed`. Claims and reconciler scans are scoped to the fixture organizations. The approvals and planning suites deliver approvals through a throwaway vhost `eg-it-<hex>` (full topology, deleted afterwards), published as the event-relay publishes them and consumed by `createApprovalFeed`: planning results, the dev pass-through end to end (its outbox approval relayed to the queue), a duplicate approval (one plan), a MySQL outage behind a TCP proxy (delay hops through `email.delivery.retry` and back, planned once, no dead letter) and a deterministic failure dead-lettered after `maxAttempts` with the failure headers.
