# @email-gateway/mailbox-worker

API-mode protection worker (step API-1, [design](../../docs/plan/steps/35-api-mode-protection.md) D4, D5, D7, D10, D11; [ADR-0100](../../docs/architecture/adr/0100-api-mode-intake-mailbox-worker.md)). Records one detection copy per mailbox for journal copies and mailbox change feeds, deduplicates them by Message-ID and mailbox, measures the lag from provider delivery to verdict, keeps the mailbox inventory, and evaluates coverage and connection health. API mode never delivers, forwards or bounces mail (N1). Step API-2 ([design](../../docs/plan/steps/36-api-mode-remediation.md) R1–R17; [ADR-0101](../../docs/architecture/adr/0101-api-mode-remediation-policy-and-mailbox-actions.md), [ADR-0102](../../docs/architecture/adr/0102-mailbox-located-quarantine-entries-release-as-restore.md)) adds post-delivery remediation: a decision per copy from the remediation policy, mailbox actions through Graph / Gmail, mailbox-located quarantine entries and their restore on release. Deployment: [docs/deployment/mailbox-worker.md](../../docs/deployment/mailbox-worker.md).

Data plane: the MySQL **writer** only (ADR-0014), Redis (budgets, throttle pauses, counters), RabbitMQ as `eg-mailbox` (copies role), the mail bucket (fetched copies; bounded header range reads), provider HTTPS through [`@email-gateway/mailbox-api`](../../packages/mailbox-api/README.md). HTTP `MAILBOX_WORKER_HTTP_PORT` (3087): `/health/live`, `/health/ready`, `/metrics` only.

Step API-3 ([design](../../docs/plan/steps/37-api-mode-clawback-reporting.md) C1–C13; [ADR-0103](../../docs/architecture/adr/0103-api-mode-clawback-search-and-purge.md), [ADR-0104](../../docs/architecture/adr/0104-api-mode-internal-mail-and-reported-phishing.md)) adds internal (east-west) copies, report-mailbox intake, late signals, retroactive clawback / search and purge (roles `clawback`) and user-reported phishing (role `reports`). The `clawback` and `reports` roles work from MySQL, Redis and the mail bucket only and never call a provider: every mailbox change is an `api_remediation_actions` row executed by `remediate` (C-I1).

## Idempotency (N8)

- Copies: `processOnce` ledger row and every effect in one writer transaction (also for skipped events: the queue is reconciled); copy rows are upserts; the dedupe key is unique per (mailbox, Message-ID hash).
- Feeds: the ingest key `v2:mbx:<sha256(connection|mailbox|provider message)>` makes a replayed page a no-op; the next link is stored after every page; the EML key is deterministic; a dedupe claim of a crashed attempt is taken over.
- Inventory: upserts by (connection, provider user id); address rows replaced with `INSERT IGNORE`.
- Remediation: one action per (copy, action, generation) (`action_key`, `INSERT IGNORE`); claims `FOR UPDATE SKIP LOCKED` with a lease; the provider state is read before acting (already in target → no call); outcomes CAS on the claimed `row_version`; mailbox entries are adopted on their unique key after a crash replay.
- Late signals: the copies ledger consumer plus `INSERT IGNORE` on UNIQUE (organization, signal key); threat-intelligence clawbacks use the same key, the sweep cursor advances after each batch (a replay creates nothing).
- Clawbacks: claims `FOR UPDATE SKIP LOCKED` with a lease (no `row_version` change); state transitions CAS on `row_version`; targets `INSERT IGNORE` on (clawback, copy) in pages of 1 000; queueing re-plans under the copy-row lock and inserts or re-arms the `action_key` row; reconcile is derived from the action rows.
- Reports: intake `INSERT IGNORE` on the report copy; claims with a lease and CAS; an ingested original uses the ingest key `v2:rpt:<sha256(report public id)>` and a deterministic mail-bucket key, committed with the report's move to `scanning` in one transaction (with a scan deadline: after `API_MODE_REPORT_SCAN_TIMEOUT_MINUTES` the report goes to triage with the report copy's scan, `last_error_code = original_scan_timeout`). A bulk restore requested again after `completed_with_errors` returns the failed targets to `none` first, so they are retried.
- Health: transitions with a CAS on the previous status; alerts throttled through `notification_alert_windows` and `health_alerted_at`.
- Counters: Redis `HINCRBY`, flushed by taking each hash atomically and adding it to `api_mode_counters` (failed writes are put back). Counters are best effort (a crash between a commit and the increment loses that increment, never a row).

## Logs

Classified codes, public ids (mailbox, connection), counts and recipient domains only: never tokens, delta links, history ids, client states, Google subjects, subjects, bodies or full addresses.

Integration suites (`integration/`): `copies` (fan-out, discovery, internal, dedupe takeover and seen-journal, hybrid link, lag and fallback, counters, redelivery, skipped events), `feeds-graph` (inventory, delta init/ingest/too large/cursor expiry, notifications and subscriptions, dedupe both orders with the simulator call log, `Retry-After` across two instances, budget isolation between two organizations, revocation), `feeds-gmail` (Directory as delegated admin, history init/continue/404, a backlog beyond the per-run page cap resumed after the processed pages, metadata-first dedupe, size pre-check), `health` (leader lock, coverage, every check, transitions with audit and throttled alerts, pruning, feed sweeps), `custody` (decrypting the grant with 8.2's grant store and token service against the TEST-ONLY fake provider), `broker` (the copies consumer over a throwaway RabbitMQ vhost), and step API-2: `remediation-graph` (decisions, hidden folder, locate, already in target, not found, tag/remove_tag, 429 / 503, revoked grant, lease expiry; the copy state after a failed `remove_tag`, a stale-generation admin action cancelled without a call, an outcome write that keeps throwing counted per re-claim and failed `internal_error`), `remediation-gmail` (labels, Junk, Trash, hard-delete fallback, tags, self restore) and `remediation-quarantine` (restore / failure / approved re-check / stale, entry delete, expiry, health checks, retention). Synthetic `it-apimode-*` and `it-apirem-*` organizations only; everything is removed afterwards; nothing reaches a real provider.

Step API-3 suites (`it-apiclaw-*`): `clawback-signals` (late signal → clawback → targets → P1 → executed → entries → `completed`, duplicate signal, not API-active, automatic off, detect-only, paused + `clawback.stalled`, hybrid copy authority, threat-intelligence sweep with cursor resume), `clawback-purge` (admin search → `ready` → submit, approval by a second user, expiry, cancel mid-run, `too_broad`/`no_match`, escalation/`already_remediated`/`restored_after_signal`/re-arm, per-connection pending cap), `clawback-restore` (release sequence, `remove_tag`, `approval_required`, `not_reversible`), `reports` (intake, original by Message-ID, ingest + scan, inline forward, no original, external reporter, rate limit, ack and alert rows, `reports.backlog`, retention), `internal-mail` (internal copies remediated, setting off, outbound-only, duplicates, counters).
