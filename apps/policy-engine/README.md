# policy-engine

Tenant policy evaluation and delivery gating (step 5.2, [design](../../docs/plan/steps/16-policy-engine.md) P13–P21, P24; [ADR-0043](../../docs/architecture/adr/0043-policy-dsl-and-deterministic-evaluator.md), [ADR-0044](../../docs/architecture/adr/0044-policy-evaluation-placement-and-delivery-gating.md), [ADR-0045](../../docs/architecture/adr/0045-policy-action-semantics.md); DSL reference: [policy-dsl.md](../../docs/architecture/policy-dsl.md); operations: [runbook](../../docs/runbooks/policy-engine.md), [deployment](../../docs/deployment/policy-engine.md)).

Since step 5.2 the policy-engine is the **only automatic producer of delivery approvals** (the delivery-worker's development pass-through was removed). Every scanned, scan-failed and parse-failed message gets exactly one evaluation per lifecycle round; ALLOW approves it for delivery, QUARANTINE / REQUIRE_APPROVAL / REJECT hold or reject it.

Data plane: the MySQL **writer** only (ADR-0014), the mail bucket (S3/MinIO), Redis (readiness only), `GET /metrics`, `GET /health/{live,ready}` (mysql, rabbitmq, redis, s3) on port 3030.

**Step 5.3** ([design](../../docs/plan/steps/17-quarantine.md), ADR-0046–0049; [quarantine runbook](../../docs/runbooks/quarantine.md), [deployment](../../docs/deployment/quarantine.md)): `POLICY_ENGINE_ROLES` (`evaluate`, `quarantine`, default both) selects the modules. The evaluation decides per recipient, writes the quarantine entries in its transaction and builds the delivered copy with WARN body banners and URL rewriting after the scan; the `quarantine` role runs the release executor and the sweeper. See [Step 5.3](#step-53-quarantine) below.

## Transport

`AmqpModule` with the role user `eg-policy-engine` (`RABBITMQ_POLICY_ENGINE_URL`: read `email.policy.evaluate`; write `email.policy` / `email.events` only for its own `retry.email.policy.evaluate.*` and `dead-letter.email.policy.evaluate*` keys; no configure). A `QueueConsumer` of `email.policy.evaluate` (topology v9, work queue) accepts `mail.message.scanned.v1` and `mail.message.parse_failed.v1`, prefetch `POLICY_EVALUATE_PREFETCH`, the topology's retry policy (`hold`, 10 attempts, 2 s – 1 min, 24 h), default failure classes (database/network outage transient; `NonRetryableError` fatal → `email.dead-letter`; anything else, e.g. an echo-check mismatch, retryable) and `PrismaConsumerProgress` (the relay's reconciler re-drives the queue when listed in `RECONCILE_QUEUES`).

### The policy copy (P21)

Key `org/<org>/policy/<yyyy>/<mm>/<dd>/<messageId>/r<round>-<32 hex of sha256(baseKey | canonical edits)>.eml` (deterministic: a retry overwrites the same key with the same bytes). Streamed from the base object: the header block (≤ `POLICY_COPY_MAX_HEADER_BYTES`) is edited — existing `X-EG-Policy-Tag` / `X-EG-Policy-Warning` fields removed, the new ones prepended, the subject prefix inserted after `Subject:` (not twice; folded at the inserted point beyond 998 octets; `Subject: <prefix>` added when missing), the original CRLF/LF kept, every other byte untouched — and the body is streamed byte-identical. `ContentType: message/rfc822`, `ContentDisposition: attachment`, `Tagging: eg-object=policy-copy` on the creating request (MinIO/S3 lifecycle rule `eg-policy-copy-expiry`). Objects over `POLICY_COPY_MAX_MESSAGE_BYTES` or with a larger header block get no copy: the base object is delivered and TAG/WARN are stored as `recorded` (`policy_copy_total{result}`). Other S3 failures are retried, never skipped. The upload runs inside the evaluation transaction with half of `POLICY_DB_TX_TIMEOUT_MS`.

## Configuration

`src/config.ts` (zod; `.env.example` section "Policy engine (step 5.2 …)"): `RABBITMQ_POLICY_ENGINE_URL` (required, `_FILE` supported), `POLICY_PLATFORM_DEFAULT` (`pol-default/1`), `POLICY_EVALUATE_PREFETCH` (1–64, 8), `POLICY_DB_TX_TIMEOUT_MS` (120 000–600 000, 120 000), `POLICY_SNAPSHOT_CACHE_MAX_ENTRIES` (10–100 000, 1000), `POLICY_COPY_MAX_MESSAGE_BYTES` (1–50 MiB, 25 MiB), `POLICY_COPY_MAX_HEADER_BYTES` (16 KiB–1 MiB, 256 KiB), plus `DATABASE_URL`, `REDIS_URL`, `S3_*` and the base keys. Step 5.3 adds `POLICY_ENGINE_ROLES`, the `QUARANTINE_*` bounds of the engine (hold/review days validated below the lifecycle deadlines, executor prefetch and budget, sweeper interval and batch, retention days, digest cap, staleness bounds), `POLICY_BANNER_MAX_PART_BYTES`, `POLICY_URL_REWRITE_ENABLED` and the sign-only URL keys (`URL_TOKEN_KEY_CURRENT` required while policy rewriting is on); see [deployment](../../docs/deployment/quarantine.md#configuration-5-policy-engine). Only the engine's own keys are read from the shared environment.

Alerts: `infrastructure/monitoring/rules/policy-engine.rules.yml`, `quarantine.rules.yml`.

## Tests

- `pnpm --filter @email-gateway/policy-engine test`: config bounds, the handler flow with fakes (every trigger, skips, write order, statuses, copies and refusals, every disposition, ARCHIVE/ALERT, sender notice, directory, input errors, inconsistent reads), the repositories' echo checks, the delivery object (ported from the pass-through), the policy copy byte by byte, metrics and the module wiring.
- `pnpm --filter @email-gateway/policy-engine test:integration`: the production handler in-process against the real MySQL writer and MinIO from `.env` and a throwaway RabbitMQ vhost (§9.2 cases); fixtures in `it-pe-*` organizations, every row and object removed afterwards. The live `event-relay` and `policy-engine` are paused for the run. `integration/quarantine.test.ts` (step 5.3): entries written atomically and idempotently, splits, supersede, policy URL rewrite, the executor from `quarantined` / `delivered` / `delivery_pending` and its blocked paths, expiry, purge with and without a legal hold, adoption, digests and admin alerts.
