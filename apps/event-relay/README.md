# event-relay

Publishes the transactional outbox to RabbitMQ and reconciles what was published against what the pipeline consumed (step 3.2, [design](../../docs/plan/steps/07-rabbitmq.md) Q11/Q12, [ADR-0023](../../docs/architecture/adr/0023-outbox-relay-and-reconciliation.md), topology: [messaging-topology.md](../../docs/architecture/messaging-topology.md), operations: [rabbitmq-messaging.md](../../docs/runbooks/rabbitmq-messaging.md)).

Every producer (smtp-adapter, email-worker, delivery-worker and the shared recorder, api) writes its events to `message_outbox` in the writer transaction of the state change. This service:

- **relay**: publishes every row at least once, with publisher confirms, persistent and mandatory, to the exchange of its event type, with the routing key `org.<organizationId>.<eventType>`, and sets `published_at` **only for rows the broker confirmed**;
- **reconciler**: reports outbox health (unpublished rows, their age, poison rows) and re-drives published events that the consumer of a tracked work queue never recorded in its ledger (`message_idempotency`), at most `RECONCILE_MAX_REDRIVES` times. Events the consumer dead-lettered, events still retrying and events behind a backlog on the broker are not re-driven (review round 1, see the rules below).

It owns no business table. It writes only `published_at`, `attempts`, `available_at`, `last_error` (relay) and `redrive_count`, `last_redriven_at`, `published_at`, `available_at` (reconciler) of `message_outbox`, and `stream_cursors.reconcile:unconsumed`; it reads `message_idempotency` and `message_consumer_progress` (written by the consumers). Data plane: the MySQL **writer** only (ADR-0014); RabbitMQ as the publish-only user `eg-relay` (`RABBITMQ_RELAY_URL`, write on the six exchanges with topic permission `^org\.[1-9][0-9]{0,19}\.` only, no configure, no read; the reconciler's passive queue declares need no permission). Port **3070**: `GET /health/live`, `GET /health/ready` (`mysql`, `rabbitmq` = connected, not blocked, the six exchanges verified passively), `GET /metrics`.

### Reconciliation rules (Q12)

For each row `id > cursor` with `created_at ≥ now − RECONCILE_LOOKBACK_HOURS`, in id order:

1. `created_at > now − RECONCILE_UNCONSUMED_AFTER_SECONDS` → stop (not due; the 300 s minimum is far above every writer transaction budget, so no uncommitted smaller id can be passed).
2. Untracked type (not bound to a queue of `RECONCILE_QUEUES`) or poison → settled for this check.
3. Unpublished, not poison → stop (the relay owns it; `OutboxUnpublishedOld` / lag alerts fire).
4. Published less than the threshold ago → stop.
5. Otherwise the ledger of each bound queue's consumer (`email-worker.mime-parser`, `delivery-worker.planner`) is checked: present → settled; absent → re-drive (`published_at = NULL, available_at = NOW(3), redrive_count + 1, last_redriven_at = NOW(3)`, guarded by `published_at IS NOT NULL AND redrive_count < RECONCILE_MAX_REDRIVES`) or, at the bound, **exhausted** (`reconcile_exhausted_total{queue}`, warn log with ids, `last_redriven_at = NULL`).
6. Not lost, only unhandled (review round 1): before a re-drive, the consumer's `message_consumer_progress` row decides. `dead_lettered` (written by `QueueConsumer` after the confirmed dead-letter copy) → settled, `reconcile_skipped_total{reason="dead_lettered"}`: replay is the recovery path, a re-drive would only produce another dead letter and a false exhausted alert. `retrying` with its last hop within the threshold plus the queue's longest hop gap (2 × `maxDelayMs`: 2 min for `email.received`, 30 min for `email.delivery.pending`) → deferred (`retrying`). Then the queue's ready count on the broker: above 0 → deferred (`queue_backlog`), not readable → deferred (`queue_unknown`). A deferred row is watched (`last_redriven_at = NOW(3)`, `redrive_count` unchanged) and judged again by the re-check. A ledger row always wins. A `dead_lettered` record whose reason a relay copy cannot produce (`contract_invalid`, `unknown_event_type`, `unsupported_schema_version`, `tenant_mismatch`, `approval_not_issued`, `approval_mismatch`: a forged or altered copy carrying a real event id) does **not** settle the row, so a forged copy cannot hide a lost event.

The cursor advances through the contiguous prefix handled. The re-check picks rows with `last_redriven_at` **and** `published_at` older than the threshold (implementation detail: the republished copy gets the full threshold before it is judged, so a slow relay does not cause a premature second re-drive), then settles (`last_redriven_at = NULL`, `redrive_count` kept as history), re-drives again or reports exhausted. `RECONCILE_MAX_REDRIVES=0` detects only. A re-driven row keeps its `event_id`: every queue bound to the event gets a copy and every consumer's ledger absorbs it.

Capacity: one sweep batch (`RECONCILE_BATCH_SIZE`) per `RECONCILE_INTERVAL_MS` (defaults 1 000 rows/min). The sweep only has to keep pace with rows older than the threshold; raise the batch or lower the interval for higher volumes.

## Scaling and operations

- **Shards ≤ replicas × `RELAY_MAX_HELD_SHARDS`.** A shard no replica can hold is not published; its lag grows on every replica's `outbox_relay_lag_seconds{shard}` and `OutboxRelayNoShardOwner` fires. Production runs two replicas (`infrastructure/kubernetes/base/event-relay.yaml`) with the defaults (4 shards, up to 4 per replica: one replica can carry everything when the other is gone).
- **Ordering** is per aggregate (one message, one domain) in the normal path: an aggregate hashes to one shard, one loop publishes it in id order, and a row in its backoff holds back the later rows of its aggregate. Within one batch the publishes are pipelined: if the broker nacks a row (e.g. `reject-publish`) but confirms a later row of the same aggregate, the later row is not withdrawn; consumers never relied on cross-event order of one message beyond what their writer-row checks enforce. A poison row does not hold back its aggregate (it is excluded and alerted).
- **First start drains the pre-3.2 backlog.** Every row written since step 2.1 is unpublished, so the first relay publishes all retained rows (locally ~3.5 k) in id order. Consumer names are unchanged, so ledger rows written by the step 2.3/3.1 pollers make them duplicates; dormant queues are bounded. Watch `outbox_unpublished_rows` fall to 0.
- **Changing `RELAY_SHARDS` safely.** Lock names contain the shard count (`er:relay#<i>/<n>`), so replicas with different counts would hold different locks for overlapping rows. Roll it as a stop-the-relay change: scale event-relay to 0 (rows accumulate in the outbox, nothing is lost), change `RELAY_SHARDS` (and `RELAY_MAX_HELD_SHARDS` so shards ≤ replicas × held), scale back up. If both counts ever run at once, rows may be published twice (duplicates are absorbed by the ledgers; marking is `WHERE published_at IS NULL`), never lost.
- **Lock connection loss** (MySQL restart, network) releases the locks server side; two replicas may briefly run the same shard → duplicates only.
- No poller fallback: if the broker is down, rows wait in the outbox (`OutboxUnpublishedOld`) and are published after recovery.

- Unit (`pnpm --filter @email-gateway/event-relay test`): batch walk (aggregate blocking, backoff skip, batch bound), poison classification and codes, outcome → row updates, broker/database backoff, shard predicate (CRC32 against MySQL values) and lock names, concurrent lock acquisition, unowned-shard lag; reconciler cursor rules (not due, unpublished stop, published recently, untracked/poison settled, re-drive bound, exhausted, re-check, lookback, first-start positions, batch size, scope); config bounds and cross-field rules; metric registration; lifecycle order; Nest wiring.
- Integration (`pnpm --filter @email-gateway/event-relay test:integration`, real MySQL writer and RabbitMQ from `.env`; a throwaway vhost `eg-it-<hex>` per suite; it-* fixture organizations; the live `event-relay`, `email-worker` and `delivery-worker` are paused during the suites by `integration/support/live-relay.ts`):
  - `relay.test.ts`: id order per aggregate with the Q2 properties/headers and org routing keys; poison rows (body-like payload, unknown type) never published; `reject-publish` nacks on a work queue with a lowered `max-length` → rows unpublished with backoff, `attempts` unchanged (never poison) across more nacking passes than `RELAY_MAX_ATTEMPTS`, drained after the queue is consumed; broker cut through a TCP proxy mid-stream → nothing marked while cut, everything published after the restore, every marked row delivered; MySQL behind a TCP proxy cut → no marks, recovery; two relays sharing four shards → every row delivered exactly once.
  - `reconciler.test.ts` (injected clock): re-driven once, republished by the relay, settled after a ledger row appears; exhausted after `RECONCILE_MAX_REDRIVES`; unpublished and poison rows in the gauges; lookback skip; `latest`/`oldest` first start; a dead-lettered approval (real delivery-worker consumer, `approval_not_issued`) is never re-driven and raises no exhausted alert; a retrying event is deferred and re-driven once its hops went quiet; a backlog on the real broker defers the re-drive.
