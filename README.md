# Email Security Gateway

A multi-tenant email security gateway: inbound, outbound and internal mail inspection, spam and phishing detection, malware and attachment scanning, URL protection, BEC detection, DLP, quarantine and optional archiving. It runs as shared SaaS or as a dedicated per-customer deployment. The design target is **1M emails/day**, scaling horizontally beyond that.

> **Status: Phase 4 in progress (step 4.4: phishing and BEC detection — the stage-2 `bec` engine with explainable deterministic rules, tenant profiles, trusted senders, feedback and opt-in history, and an optional bounded AI layer (local model in shadow; LLM off by default); implemented and verified locally (gate, images, the whole integration chain with the new `bec-smtp` suite); not complete: no real LLM call has been made, commit and CI pending, Kubernetes apply not verified; see [§13](docs/plan/steps/12-phishing-bec.md#13-verification-results)). Step 4.3 (URL protection — the URL engine with rewriting, the time-of-click click-service and the isolated browser worker; implemented, review round 1 fixed (click-time re-resolution of every URL, IP reputation of resolved addresses, tracing kept off untrusted egress and click tokens, atomically tagged rewritten copies) and verified locally (gate, images, the whole integration chain, the browser suite through the pipeline); not complete: commit and CI pending, real provider feeds, Kubernetes apply and gVisor not verified; see [§13](docs/plan/steps/11-url-protection.md#13-verification-results)). Step 4.2 (ClamAV and the attachment engine) is implemented and verified ([§13.2](docs/plan/steps/10-attachment-scanning.md#132-review-round-1-2026-11-06)); commit and CI pending; the Prisma 6.19 wrong-read defect is mitigated but not removed.** Phase 0 (monorepo, local stack, health, CI, architecture docs), step 1.1 (the MySQL schema with the read/write split), steps 1.2/1.3 (tenants, first-party authentication with MFA and API keys, eight default roles, tenant-scoped authorization with an audited platform override, the organizations API) and step 2.1 (domain onboarding: DNS verification, generated MX/SPF/DKIM/DMARC records, encrypted DKIM keys with rotation, the domain lifecycle) are in place. Step 2.2 adds the mail plane: an inbound MX (`postfix`, postscreen, relay domains and policy from smtp-adapter, Rspamd milter) and an outbound MTA (`postfix-outbound`: SASL submission, source-IP / client-certificate connector relay, internal reinjection listeners), durable LMTP ingestion into S3 + MySQL (`250` only after both), outbound connectors and recipient allow-lists in the api, DKIM signing in a dedicated Rspamd fed by the api through an isolated Redis, bounce processing into suppressions, loop prevention and Prometheus metrics. Step 2.3 adds routing and delivery: the delivery-worker plans approved recipients into reinjection groups and hands them to `postfix-outbound` (10026 for inbound and internal mail to the organization's destination servers — customer servers or the Microsoft 365 / Google Workspace presets, with failover and verified TLS — and 10027 for outbound mail via the recipient's MX, never shortcutting to another tenant), per-recipient directions (`inbound`, `outbound`, `internal`) with one parent message, outbound rate limits, loop prevention, and per-recipient delivery status read from Postfix's own delivery log (`delivered` only after the remote server's `2xx`), with an append-only delivery audit and the destination and delivery-status APIs. **Approval is still development-only:** until policies exist (step 5.2) local and CI stacks deliver through a pass-through that is refused outside `APP_ENV=local|ci`; since step 4.1 it approves only messages that the scan stage completed (`scanned`), never `scan_failed` ones. **Open item of step 2.3:** the gateway does not yet send its own DSN to the authenticated sender when it fails an outbound or internal recipient itself (refused at its internal hop, loop, hop expiry, domain inactive, content missing); those failures are recorded and visible through the API, and Postfix's own DSNs (remote `5xx`, expiry, delay) are sent ([§10](docs/plan/steps/05-routing.md#10-not-in-scope), planned with step 6.2). Step 3.1 adds post-queue MIME ingestion in the email-worker ([design](docs/plan/steps/06-mime-ingestion.md), [ADR-0022](docs/architecture/adr/0022-mime-parsing-and-post-queue-ingestion.md)): every received message is streamed from S3 through a bounded, non-rendering parser (`@email-gateway/mime-parser`); bodies and attachments go to S3 under deterministic `org/{organizationId}/part/…` keys, and one writer transaction records the parse status (`parsed`, `parsed_with_defects`, `parse_limit_exceeded`, `parse_failed`), allow-listed headers, attachment metadata (sanitized filenames, sniffed types, SHA-256, archive-bomb flags), the decoded subject, an `email_events` row and a `mail.message.parsed.v1` / `mail.message.parse_failed.v1` outbox event. The SMTP path is unchanged. Step 3.2 makes the pipeline event-driven over RabbitMQ ([design and verification record](docs/plan/steps/07-rabbitmq.md), [ADR-0023](docs/architecture/adr/0023-outbox-relay-and-reconciliation.md), [ADR-0024](docs/architecture/adr/0024-rabbitmq-topology-retry-dead-letter.md)): a ninth deployable, **`event-relay`**, publishes every `message_outbox` row with publisher confirms (marking it published only after the confirm) into topology v1 (vhost `email-gateway`, six topic exchanges, fourteen quorum queues, tenant-aware routing keys `org.<id>.<eventType>`, least-privilege role users) and reconciles published events against the consumers' ledgers; the email-worker consumes `email.received` and the delivery-worker `email.delivery.pending` through the shared client library (manual acks after the `processOnce` transaction, retries with exponential backoff that never consume an attempt during outages, a delay queue for delivery, one dead-letter queue, a content guard that keeps bodies off the bus); dead letters are replayed only through an audited, MFA-protected platform API. **The outbox poller is no longer a production transport and there is no fallback to it** (two transports per consumer would double the failure modes; a broker outage leaves rows unpublished in the outbox and the reconciler covers lost events); only the development-only dev pass-through and smtp-adapter's cache invalidation still tail the outbox. Step 3.3 adds the message lifecycle (fifteen states, one transition service, history, rescan and release APIs, expiry). Step 4.1 adds the security scan pipeline (below): every parsed message is scanned post-queue by Rspamd in the email-worker scan role and ends `scanned` or `scan_failed`, with standardized verdicts and SPF/DKIM/DMARC/ARC results recorded. Policies (5.x) come next. See [docs/architecture/overview.md](docs/architecture/overview.md#what-exists-now-and-what-comes-next) and [docs/plan/execution-plan.md](docs/plan/execution-plan.md).

## Quick start

**Prerequisites:** Node.js ≥ 22.12, pnpm 9 (`corepack enable`), and Docker with Compose v2 (≈ 6 GB RAM for the full stack).

```bash
pnpm install
pnpm env:init                       # creates .env with random local secrets (git-ignored)
docker compose up -d --wait         # MySQL primary + replica, RabbitMQ, Redis, MinIO, both Postfix MTAs, Rspamd, ClamAV, redis-dkim
pnpm db:migrate                     # history preflight + apply database migrations
pnpm test:integration               # verify every infrastructure service
```

Then either run the services on the host, with hot reload:

```bash
pnpm dev                            # all services (reads ../../.env)
pnpm --filter @email-gateway/api dev  # or just one
```

or run everything in containers:

```bash
docker compose --profile apps up -d --build --wait
pnpm test:integration               # now also checks every service's /health/ready
```

MySQL runs as a GTID primary plus a read replica. The one-shot `mysql-replica-setup` container creates the database accounts and seeds the replica with CLONE on first start (about 10 s). After that it is a no-op. Only the api reads from the replica (`DATABASE_READ_URL`); see [replication](docs/database/replication.md). If your `.env` predates the replica, append `MYSQL_REPLICA_HOST_PORT`, `MYSQL_READER_*`, `MYSQL_REPLICATION_*` (password at most 32 characters) and `DATABASE_READ_*` from `.env.example`, without regenerating the existing secrets.

Step 1.2/1.3 (tenants, authentication, RBAC) adds api keys: `AUTH_JWT_SECRET`, `AUTH_TOKEN_PEPPER`, `DATA_ENCRYPTION_KEY` (secrets), `PORTAL_PUBLIC_URL`, `HTTP_TRUST_PROXY` and the `AUTH_*`/`PLATFORM_*`/`ORG_*` tuning keys (see the "API authentication and tenancy" section of `.env.example`). If your `.env` predates them, append that section from `.env.example` and fill the `__GENERATE_64__` placeholders with `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`, without rotating existing secrets (never `env:init --force`). Transactional email (invitations, password resets) goes through `NOTIFY_SMTP_*`; when `NOTIFY_SMTP_HOST` is empty the api logs the email (with a dev link) instead of sending it.

Step 2.1 (domain onboarding) adds the section "Domain onboarding and DNS (step 2.1)" of `.env.example`: `DNS_*` (resolver mode, servers, DoH URL, timeouts, propagation upstreams, cache), `GATEWAY_*` (the MX hosts and SPF include customers publish, DMARC report addresses), `DOMAIN_*` (verification label and lifetime, reserved names, background-job tuning) and `DKIM_ROTATION_OVERLAP_DAYS`. None of them is a secret. `GATEWAY_MX_HOSTS` and `GATEWAY_SPF_INCLUDE` have no default: the api refuses to start without them. If your `.env` predates them, append the section without touching anything else:

```bash
grep -q '^GATEWAY_MX_HOSTS=' .env || sed -n '/^# --- Domain onboarding and DNS (step 2.1) ---/,/^DKIM_ROTATION_OVERLAP_DAYS=/p' .env.example >> .env
```

The local values point at `.test` names; in a real deployment set `GATEWAY_MX_HOSTS`/`GATEWAY_SPF_INCLUDE` to the gateway's public names and choose the DNS resolver ([runbook](docs/runbooks/domain-verification.md#dns-resolver-modes)). The API integration tests never use public DNS: they run their own in-process DNS server.

Step 2.2 (SMTP gateway) adds the section "SMTP gateway (step 2.2)" of `.env.example`: host ports of the outbound MTA and redis-dkim, `SMTP_ADAPTER_HOST` (where both Postfix containers reach smtp-adapter: `smtp-adapter` for the apps profile and CI, `host.docker.internal` when the adapter runs on the host with `pnpm --filter @email-gateway/smtp-adapter dev`), Postfix limits, TLS certificate paths (`POSTFIX_*TLS_*_PATH`) and queue timings, the redis-dkim passwords (`REDIS_DKIM_*_PASSWORD`, secrets) and URLs, `GATEWAY_TRACE_SECRET` (secret), and the adapter's cache, rate-limit, SASL and ingestion tuning. `POSTFIX_RELAY_DOMAINS` is deprecated: relay domains now come from the database through smtp-adapter. If your `.env` predates the section, append it and fill its placeholders yourself (never `env:init --force`):

```bash
grep -q '^GATEWAY_TRACE_SECRET=' .env || sed -n '/^# --- SMTP gateway (step 2.2) ---/,$p' .env.example >> .env
# then replace each __GENERATE__ / __GENERATE_64__ in the appended lines, e.g. with
node -e "console.log(require('crypto').randomBytes(24).toString('hex'))"
```

Step 2.3 (mail routing) adds the section "Mail routing and delivery (step 2.3)" of `.env.example` (no secrets): the delivery-worker's reinjection, polling, status-log and rate-limit keys, the destination-host rules (`ROUTING_*`, including the custom-destination port allow-list `ROUTING_ALLOWED_DESTINATION_PORTS`), the delivery-log directory (`POSTFIX_OUTBOUND_LOG_DIR`, git-ignored `.local/`), the outbound connect timeout and the test CA path. For a worker on the host the local `.env` uses the test-only `reinject-forwarder` (`DELIVERY_REINJECT_HOST=127.0.0.1`, ports `2626`/`2627`), `DELIVERY_STATUS_LOG_PATH=../../.local/postfix-outbound-log/maillog`, the test-profile backoff (`POSTFIX_MINIMAL_BACKOFF_TIME=10s`, `POSTFIX_MAXIMAL_BACKOFF_TIME=60s`, `POSTFIX_QUEUE_RUN_DELAY=10s`) and `DELIVERY_DEV_PASSTHROUGH_ENABLED=true` (**development only**: delivers without scanning or policy). Append the section with `grep -q '^DELIVERY_REINJECT_HOST=' .env || sed -n '/^# --- Mail routing and delivery (step 2.3) ---/,$p' .env.example >> .env`, set those local values, then recreate both Postfix containers. Run the worker with `pnpm --filter @email-gateway/delivery-worker dev` next to the adapter; details in [docs/deployment/mail-routing.md](docs/deployment/mail-routing.md).

Step 3.1 (MIME ingestion) adds the section "MIME ingestion (step 3.1)" of `.env.example` (no secrets): `MIME_INGESTION_ENABLED`, the feed's concurrency, polling, safety lag, shards and retry backoff, the S3 upload buffers and memory budget, and every parse limit (`MIME_MAX_*`, `MIME_PARSE_TIMEOUT_MS`, `MIME_ARCHIVE_*`). The email-worker refuses to start with inconsistent values (for example a per-part limit above `MIME_MAX_MESSAGE_BYTES`, parse buffers above `MIME_MEMORY_BUDGET_BYTES`, a `MIME_MAX_DEPTH` whose `part_path` could overflow its column, or `MIME_S3_TIMEOUT_MS` not below `MIME_PARSE_TIMEOUT_MS`). If your `.env` predates it, append the section unchanged. If it has `MIME_S3_TIMEOUT_MS=120000` (the first default), set it to `30000`, or the email-worker refuses to start:

```bash
grep -q '^MIME_INGESTION_ENABLED=' .env || sed -n '/^# --- MIME ingestion (step 3.1) ---/,$p' .env.example >> .env
```

Run the stage with `pnpm --filter @email-gateway/email-worker dev` (stop the `email-worker` container first, or set `HTTP_PORT`), or as the apps-profile container (`docker compose --profile apps build email-worker`, one image at a time on a small Docker VM). Since step 3.2 it consumes `email.received` (the `MIME_OUTBOX_*` keys are no longer read and can be removed from `.env`).

Step 3.2 (RabbitMQ) adds the sections "RabbitMQ" and "Event relay (step 3.2)" of `.env.example`: `RABBITMQ_VHOST`, `RABBITMQ_MGMT_URL`, `RABBITMQ_PROMETHEUS_HOST_PORT`, one user, password (`__GENERATE__`) and URL per role (`RABBITMQ_RELAY_*`, `RABBITMQ_EMAIL_WORKER_*`, `RABBITMQ_DELIVERY_WORKER_*`, `RABBITMQ_OPS_*`), the test-only cluster keys (`RABBITMQ_CLUSTER_*`), `EVENT_RELAY_HOST_PORT` and the relay/reconciler tuning (`RELAY_*`, `RECONCILE_*`), plus `DELIVERY_APPROVAL_PREFETCH` and `DEAD_LETTER_REPLAY_SCAN_MAX`. `RABBITMQ_URL` is now the administrator on `/` for tests and tools only (services no longer receive it) and `RABBITMQ_PREFETCH` is not read. If your `.env` predates the step, append the sections and generate the passwords (never `env:init --force`). The Compose one-shot `rabbitmq-init` provisions the vhost, topology and role users on every `docker compose up` and removes the empty pre-3.2 objects on vhost `/`; from the host, `pnpm rabbitmq:init` does the same without the cleanup. The first relay start publishes the whole pre-3.2 outbox backlog; the consumers record it as ledger duplicates. Operations: [RabbitMQ messaging runbook](docs/runbooks/rabbitmq-messaging.md); topology: [docs/architecture/messaging-topology.md](docs/architecture/messaging-topology.md); relay: [apps/event-relay/README.md](apps/event-relay/README.md). Details, metrics and cursors: [apps/email-worker/README.md](apps/email-worker/README.md); operations: [runbook](docs/runbooks/mime-ingestion.md).

The API serves business routes under `/api/v1` ([ADR-0015](docs/architecture/adr/0015-api-base-path.md)); health endpoints stay at `/health/*`, and outside production the OpenAPI UI is at `/docs` (snapshot: [docs/api/openapi.json](docs/api/openapi.json)). Endpoints and conventions: [docs/api/README.md](docs/api/README.md).

### First login (local)

The admin-portal pages for login, invitations and password reset arrive with steps 7.x, so the first platform administrator is created from the command line and activated through the API:

```bash
pnpm db:seed                                        # catalog: permissions, 8 roles, plans, the platform organization
pnpm --filter @email-gateway/api build              # the bootstrap CLI runs from dist/
pnpm --filter @email-gateway/api auth:bootstrap -- --email ops@example.com --display-name "Ops"
# prints an acceptance link …/auth/accept-invitation#token=egt_… to stdout (treat it like a password)

API=http://127.0.0.1:${API_HOST_PORT:-3000}/api/v1
curl -s -X POST $API/auth/invitations/accept -H 'content-type: application/json' \
  -d '{"token":"egt_…","password":"<12+ characters, not a common password>"}'   # → 204
curl -s -X POST $API/auth/login -H 'content-type: application/json' \
  -d '{"email":"ops@example.com","password":"…","organization":"platform"}'
```

The API must be running (`pnpm --filter @email-gateway/api dev`, or the `apps` Compose profile). The platform organization requires MFA, so the first login returns `mfaEnrollmentRequired: true`: enroll with `POST /auth/mfa/totp/setup` and `POST /auth/mfa/totp/enable { code }` (bearer token from the login; store the recovery codes), then refresh the session (`POST /auth/refresh`) to get an MFA access token; later logins finish with `POST /auth/mfa/verify`. Afterwards the administrator can create customer organizations (`POST /api/v1/organizations` with an `initialAdmin`), whose invitation emails go through `NOTIFY_SMTP_*` or, without a relay, are logged with a dev link. Details: [docs/security/authentication.md](docs/security/authentication.md).

On first start, ClamAV downloads about 300 MB of signatures. `--wait` blocks until it is healthy, which can take a few minutes.

Optional profiles: `--profile analytics` (OpenSearch, ClickHouse) and `--profile observability` (OpenTelemetry Collector, Prometheus, Grafana).

### SMTP stack tests

`pnpm test:integration` includes the stack SMTP suites `tests/integration/smtp-*.test.ts` (real SMTP through both Postfix instances, swaks/smtp-source from `smtp-tools`, S3 and MySQL assertions, MinIO/Redis/Postfix outages, a 40-session × 1 000-message zero-loss run). They need the `smtp-test` profile and a running smtp-adapter, and **fail** with an explanation when either is missing:

```bash
docker compose up -d --wait
docker compose --profile smtp-test up -d --wait mail-sink dns-sink smtp-tools
pnpm build                                          # the suites run the api's dkim:sync CLI from dist/
pnpm --filter @email-gateway/smtp-adapter dev       # with SMTP_ADAPTER_HOST=host.docker.internal in .env
pnpm test:integration
```

The step 2.3 routing suites (`routing-*.test.ts`) also need the delivery-worker with `DELIVERY_DEV_PASSTHROUGH_ENABLED=true`, and the step 3.1 suite `mime-ingestion.test.ts` needs an email-worker with the MIME stage on `EMAIL_WORKER_HOST_PORT` (`pnpm --filter @email-gateway/email-worker dev` or the rebuilt container; its gate checks `/health/ready` and the `mime_*` series on `/metrics`). With the email-worker running, every message of the other suites is parsed too; their fixtures clean up the parse rows and part objects. The step 3.2 stack suites `messaging-*.test.ts` (broker restart, MySQL writer pause, email-worker SIGKILL, duplicate events, a 500-message backlog, dead-letter replay through the api) need the whole apps profile **as containers** built from this tree (they restart, pause and kill them) and `DELIVERY_DEV_PASSTHROUGH_ENABLED=true`. The step 3.3 suites `lifecycle-*.test.ts` need the same (release and rescan through the live api, a SIGKILL of the delivery-worker); `lifecycle-event-relay.test.ts` stops the `event-relay` container for its duration, runs a test-only event-relay on the host (`LIFECYCLE_TEST_RELAY_PORT`, default 3071) with short sweep intervals, and starts the container again. The step 4.1 suites `scan-*.test.ts` send through the inbound MX's `mailtest` address (172.31.250.10, so the client is in the `scan.test` SPF records) and need the email-worker scan role and the scanned pass-through (the routing, MIME and messaging gates check both); `scan-resilience.test.ts` stops and starts the `rspamd` container. The step 4.2 suites `attachment-*.test.ts` need the email-worker container with the attachment consumer and a healthy `clamav`: `attachment-smtp` (EICAR, clean, archives, sandbox submissions through Postfix), `attachment-resilience` (stops and starts `clamav`; rescan job through the api) and `attachment-inspector-container` (the inspector's `prlimit` + `/proc` kill path inside the container). The step 4.3 suites `url-*.test.ts` need the email-worker container with the URL consumer, the `click-service` (apps profile) and `url-test` + `dns-sink` (smtp-test profile): `url-smtp` (links scanned, rewritten and delivered with protected links, 302 / block page after a platform feed add through the api, tampered and expired tokens, no URLs, S/MIME skipped), `url-ssrf` (redirects into loopback/metadata/private forms and DNS rebinding refused before connecting) and the focused `url-browser` (dynamic inspection through the pipeline; skipped unless the `url-browser` profile runs). Suites that send mail purge the dormant queues (`scan.auth`, `scan.dlp`, `scan.sandbox`, `email.policy.evaluate`, `email.quarantine`, `email.archive`, `email.analytics`) in `afterAll`; the URL suites also purge the lossy `scan.url.inspect`. The broker node-failure test runs only on the test-only `rabbitmq-cluster` profile: `pnpm --filter @email-gateway/integration-tests test:cluster` after the procedure in the [RabbitMQ runbook](docs/runbooks/rabbitmq-messaging.md#node-failure-test).


## Message lifecycle (step 3.3)

Every message has one lifecycle state in `email_messages.status` (fifteen states: `received`, `persisted`, `scanning`, `scanned`, `scan_failed`, `policy_evaluated`, `approved`, `quarantined`, `held_for_review`, `rejected`, `delivery_pending`, `delivery_retry`, `delivered`, `archived`, `expired`), plus `status_reason`, `version` (+1 per applied transition) and `lifecycle_round` (+1 on a rescan or release). Every write goes through `@email-gateway/message-lifecycle` ([packages/message-lifecycle](packages/message-lifecycle/README.md)): the transition table (edges E1–E27), a row lock plus a version compare-and-set, an idempotency key per transition, and in the same transaction one `email_message_status_history` row (actor role/service/type/id, reason, causing event, correlation id, occurrence time), one `email_events` row `lifecycle.<state>` and one `mail.message.state_changed.v1` outbox row. Late, duplicate or out-of-order requests never move a message backwards; they are recorded as `lifecycle.ignored`. Design: [step 3.3](docs/plan/steps/08-message-lifecycle.md), [ADR-0025](docs/architecture/adr/0025-message-lifecycle-state-machine.md), diagrams [11](docs/architecture/diagrams/11-message-state-machine.md) and [22](docs/architecture/diagrams/22-delivery-lifecycle.md), runbook [message lifecycle](docs/runbooks/message-lifecycle.md).

Who moves a message today: smtp-adapter (`received` → `persisted` in the SMTP commit), the email-worker scan role (`persisted → scanning → scanned | scan_failed`, step 4.1), the dev pass-through of the delivery-worker (`scanned → approved`, E27, local/CI only, until the 5.2 policy engine; E4 `persisted → approved` is retired), the delivery planner (`approved → delivery_pending`), the shared delivery recorder (`delivery_retry` / `delivered` / `rejected`, derived from the per-recipient states), the api (operator rescan and release) and event-relay (expiry, lost-derivation recovery). The policy states are valid in the machine but have no producer before Phase 5. A partial delivery is `delivered` with reason `delivery_partial`; every recipient failed is `rejected` with `delivery_failed`.

event-relay roles (each a flag, single owner through MySQL `GET_LOCK`): `RELAY_ENABLED` (outbox relay), `RECONCILE_ENABLED` (re-drive of unconsumed events), `LIFECYCLE_EXPIRY_ENABLED` (expires a message stuck past its state's deadline, `LIFECYCLE_DEADLINE_<STATE>_HOURS`), `LIFECYCLE_CHECK_ENABLED` (re-derives a lost delivery transition, gauges of stuck messages). Keys: `.env.example` section "Message lifecycle (step 3.3)".

Routes (OpenAPI at `/docs`, [docs/api/README.md](docs/api/README.md)):

| Route                                         | Permission           | Does                                                                                                                                                                                                                 |
| --------------------------------------------- | -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /api/v1/messages/{id}/lifecycle`         | `message:read`       | State, reason, version, round, parse outcome, recipient counts, allowed actions (replica)                                                                                                                            |
| `GET /api/v1/messages/{id}/lifecycle/history` | `message:read`       | Applied transitions oldest first, cursor pagination                                                                                                                                                                  |
| `POST /api/v1/messages/{id}/rescan`           | `message:rescan`     | `Idempotency-Key` required; E19 → `scanning` with a new round, `rescan_requested.v1`; since step 4.1 every registered engine scans the new round (old rounds are kept) and the round ends `scanned` or `scan_failed` |

ORDER BY version` (add `received_at` for partition pruning). ## Security scanning (step 4.1)

Every parsed message is scanned post-queue by the **email-worker scan role** ([design and verification record](docs/plan/steps/09-rspamd.md), [ADR-0026](docs/architecture/adr/0026-security-scan-pipeline.md), [runbook](docs/runbooks/scan-pipeline.md), [Rspamd deployment](docs/deployment/rspamd.md), diagrams [9](docs/architecture/diagrams/09-scanning-sequence.md) and [23](docs/architecture/diagrams/23-scan-pipeline.md)): `mail.message.parsed.v1` (or an operator's `rescan_requested.v1`) on `scan.spam` → the round opens (`persisted → scanning`, one `email_scans` row per lifecycle round) → the EML is streamed from S3 to Rspamd `/checkv2` with the trusted envelope (client IP, HELO and host name from Postfix XFORWARD, envelope sender, recipients) → the reply is mapped to one of seven verdicts (`clean`, `spam`, `suspicious`, `malicious`, `unknown`, `timeout`, `error`) with reason codes such as `spam.gtube`, `auth.spf_fail`, `auth.dmarc_reject`, `phishing.known_bad_url` → `scan_engine_results`, `email_auth_results` (SPF/DKIM/DMARC/ARC), `scanned` or `scan_failed` and `mail.message.scanned.v1` in one transaction. Engine timeouts, errors, an open circuit breaker or a missing EML are **never clean**: they are retried (non-final attempt rows) and end `scan_failed` when the attempt budget or the round deadline is spent. Rspamd also runs at SMTP time as the inbound milter ([ADR-0027](docs/architecture/adr/0027-rspamd-milter-policy.md)): it rejects only GTUBE and score ≥ 15 (`554 5.7.1`), strips forged `Authentication-Results`/`X-Spam*` headers, adds ours, and **accepts** when Rspamd is down (the post-queue scan still runs).

Running it locally: `docker compose up -d --wait` starts `rspamd`; `docker compose --profile smtp-test up -d --wait dns-sink` serves the `scan.test` zones Rspamd resolves (`RSPAMD_DNS_SERVERS=172.31.250.53`); the email-worker runs both roles (`MIME_INGESTION_ENABLED=true`, `SCAN_ENABLED=true`, broker user `eg-scanner` from `RABBITMQ_SCANNER_URL`; `pnpm rabbitmq:init` creates it). New keys: `.env.example` section "Security scanning (step 4.1)" — `RABBITMQ_SCANNER_*`, `SCAN_ENABLED`, `SCAN_ENGINES`, `SCAN_RSPAMD_URL`, `RSPAMD_CONTROLLER_URL`, `RSPAMD_CONTROLLER_PASSWORD`, `RSPAMD_CONTROLLER_ENABLE_PASSWORD`, the `SCAN_RSPAMD_*` thresholds, timeouts, attempts, breaker, deadline and sweeper keys, `SCAN_FUZZY_WEIGHT`, and the `RSPAMD_*` keys of the Rspamd container (DNS, Redis DB 1, Bayes `min_learns`, RBL profile, phishing feeds, milter reject score, authserv-id). Existing `.env` files: append the section and generate the three new secrets yourself (never `pnpm env:init --force`; see [docs/deployment/rspamd.md](docs/deployment/rspamd.md#environment-envexample-section-security-scanning-step-41)). `RECONCILE_QUEUES` now includes `scan.spam`.

## Attachment scanning (step 4.2)

Every round also requires the **`attachment` engine** ([design and verification record](docs/plan/steps/10-attachment-scanning.md), [ADR-0028](docs/architecture/adr/0028-attachment-scanning-engine.md), [runbook](docs/runbooks/attachment-scanning.md), [deployment](docs/deployment/attachment-scanning.md), [performance](docs/performance/attachment-scanning.md)) on `scan.attachment` (consumer `email-worker.scan.attachment`; production Deployment `email-worker-attachment`). Per round it reads the parse row and the attachment rows on the writer (no attachments on a complete parse → `skipped`; an incomplete parse, i.e. any parse limit but `body_size`, → at least `suspicious`), looks every SHA-256 up in the platform-wide known-threat catalog, and per attachment reads the stored part from S3 (size and SHA-256 verified) and runs, in parallel, clamd `INSTREAM` (`@email-gateway/clamav`) and an inspector child process (true file type, zip/gzip/tar walk under depth/entry/size/ratio limits, encryption markers, YARA-X with the bundle `apps/email-worker/yara`) under `prlimit` and a `/proc` CPU/RSS watchdog. Results map to `clean`, `suspicious`, `malicious` or `unknown` per attachment (`attachment-map/1`; `clean` only with a definite ClamAV `OK` and nothing else); the most severe one is the engine's result. Content results are cached in Redis under `eg:scan:att:v2:<sha256>:<contentVersion>` (the version changes with every ClamAV database and YARA bundle), authenticated with the worker-only `ATTACHMENT_CACHE_HMAC_KEY`. Suspicious and unknown stored attachments become `sandbox_submissions` rows with a `mail.attachment.sandbox_requested.v1` event (consumed in step 4.6). A signature watcher records new ClamAV/YARA versions and, with `ATTACHMENT_SIGNATURE_RESCAN=rescan`, a rescan job that the runner executes in batches. Locally the dev pass-through holds `malicious` messages (never delivered).

Running it locally: `docker compose up -d --wait` starts `clamav` (`clamav/clamav-debian:1.4`, about 1 GiB RSS once the database is loaded); the host email-worker reads `CLAMAV_HOST`/`CLAMAV_PORT` and needs `ATTACHMENT_INSPECTOR_RLIMITS=best_effort` on macOS (no `prlimit`; refused in production). New keys: `.env.example` section "Attachment scanning (step 4.2)" — `CLAMAV_*`, `SCAN_ATTACHMENT_*`, the `ATTACHMENT_*` limits, inspector, YARA, cache (incl. the secret `ATTACHMENT_CACHE_HMAC_KEY`), sandbox, signature-watcher and rescan keys. Existing `.env` files: append the section (`pnpm env:init` generates the secret for a new file).

| `GET /api/v1/messages/{id}/scans`                                                            | `message:read`                 | The `attachment` engine entry lists per-attachment results (type, hashes, verdict, ClamAV/YARA/archive findings, sandbox status; never the cache result) |
| `PUT` / `DELETE /api/v1/scan-settings/attachment`                                            | `scan:settings_manage`         | Tenant attachment settings within platform bounds (stricter only), audited                                                                               |
| `GET` / `POST /api/v1/platform/threat-hashes`, `DELETE …/{sha256}`                           | `platform:threat_intel_manage` | Platform admins only (MFA): the known-threat hash catalog, effective on the next scan; audited                                                           |
| `POST` / `GET /api/v1/platform/attachment-rescans`, `GET …/{jobId}`, `POST …/{jobId}/cancel` | `platform:scan_rescan`         | Platform admins only (MFA): bulk rescans by window, states and organization (dry run supported); audited                                                 |

## URL protection (step 4.3)

Every round also requires the **`url` engine** ([design and verification record](docs/plan/steps/11-url-protection.md), ADRs [0029](docs/architecture/adr/0029-url-security-engine.md) (engine), [0030](docs/architecture/adr/0030-url-rewriting-and-click-tokens.md) (rewriting and tokens), [0031](docs/architecture/adr/0031-time-of-click-service.md) (click-service), [0032](docs/architecture/adr/0032-url-browser-isolation.md) (browser isolation); [deployment](docs/deployment/url-protection.md); runbooks [url-scanning](docs/runbooks/url-scanning.md), [click-service](docs/runbooks/click-service.md), [url-browser-worker](docs/runbooks/url-browser-worker.md)) on `scan.url` (consumer `email-worker.scan.url`; production Deployment `email-worker-url`). From the stored bodies (and small text/html attachments) it extracts and normalizes every http(s) URL (`@email-gateway/url-security`), checks URL, host, registrable domain, literal IPs and the public addresses the hosts resolve to against the platform threat feed (`threat_indicators`, never cached), DNS blocklists and RDAP domain age through an HMAC-authenticated Redis cache, detects lookalike domains (Unicode confusables, edit distance, combosquatting, mixed scripts), resolves shorteners and suspicious links through **one SSRF-guarded fetcher** (every hop re-validated, IP-literal dialling, every non-public IANA range blocked) and maps them with `url-map/1` (`clean` only when every provider answered and every attempted fetch completed; outages → `unknown`). It then writes a **rewritten copy** of the EML (`org/<org>/rewrite/…`) whose links point at `URL_CLICK_BASE_URL/c/<signed token>`; approvals deliver that copy (signed/encrypted mail, DKIM policy `skip`, oversize mail and messages without URLs are delivered unchanged). Messages without URLs: `skipped` (`url.none`).

At click time the **`click-service`** (public port 3080, admin 3081, its own MySQL account `gateway_click`, no S3, no broker) verifies the token (HMAC, expiry), rechecks the URL within a 2.5 s budget (feed, cache, the redirect chain re-resolved for every clicked URL with lookalike and hop/address reputation of its destination, the dynamic result) and allows (302 to the URL stored server side — never an open redirect), warns (interstitial with an optional continue link) or blocks (403 with a reference id) under the tenant's click policy, logging one `url_click_events` row and `mail.url.clicked.v1`. Suspicious and unknown URLs can be inspected by the isolated **`url-browser-worker`** (real Chromium headless shell, profile `url-browser`, no database/S3/Redis/secrets, all traffic through the token-authenticated **`url-egress-proxy`** with the same SSRF guard); its result is used at click time.

Running it locally: the apps profile starts `click-service`; `docker compose --profile smtp-test up -d` starts `url-test` (TEST-ONLY corpus web server on 203.0.113.10, published 18080/18443) and the `dns-sink` corpus (published 1053); `docker compose --profile smtp-test --profile url-browser up -d url-egress-proxy url-browser-worker` starts the browser pair (about 1.3 GiB; never together with the analytics or observability profiles on an 8 GB VM). New keys: `.env.example` section "URL protection (step 4.3)" (≈ 113 keys, secrets `URL_CACHE_HMAC_KEY`, `URL_TOKEN_KEY_CURRENT`, `URL_EGRESS_PROXY_TOKEN`, `MYSQL_CLICK_PASSWORD`, `RABBITMQ_URL_BROWSER_PASSWORD`); `.env` values are host-run values, Compose fixes the container ones. Rewriting changes the body, so the tenant's mailbox platform must trust the gateway ([destination servers](docs/domains/destination-servers.md#link-protection-rewrites-messages-trust-the-gateway)).

| `GET /api/v1/messages/{id}/scans`                                  | `message:read`                 | The `url` engine entry lists per-URL results (verdict, reasons, reputation, lookalikes, redirect chain hosts, landing and dynamic signals, rewritten, clicks) and the round's rewrite; never cache flags or per-URL durations |
| `PUT` / `DELETE /api/v1/scan-settings/url`                         | `scan:settings_manage`         | Tenant URL settings within platform bounds (domain lists normalized, public suffixes refused; fetch mode, rewriting, click policy, dynamic inspection), audited                                                               |

## Phishing and BEC detection (step 4.4)

Every round also requires the **`bec` engine** ([design and verification record](docs/plan/steps/12-phishing-bec.md), ADRs [0033](docs/architecture/adr/0033-bec-engine-and-stage-dependencies.md) (engine and stage dependencies), [0034](docs/architecture/adr/0034-bec-ai-layer-invariant.md) (AI layer invariant), [0035](docs/architecture/adr/0035-bec-communication-context-privacy.md) (communication history); [deployment](docs/deployment/bec-detection.md); [runbook](docs/runbooks/bec-detection.md); [diagram 23](docs/architecture/diagrams/23-scan-pipeline.md)) on `scan.bec` (consumer `email-worker.scan.bec`; production Deployment `email-worker-bec`). It is the first **stage-2** engine: the transaction that inserts the last of a round's `rspamd`/`url` finals writes one `mail.message.scan_stage_ready.v1`, so the engine always sees that round's real SPF/DKIM/DMARC results and URL verdicts (a failed dependency is recorded as an unavailable input, never clean). Inbound mail only (`outbound`/`internal` → `skipped`).

- **Deterministic first** (`@email-gateway/bec`, verdict map `bec-map/1`, 50 rules with stable ids and reason codes): sender identity and alignment, display-name spoofing (UTS #39 confusables, embedded addresses, brand names), Reply-To and Return-Path mismatches, SPF/DKIM/DMARC failures and tenant-domain spoofing, lookalike domains of the tenant, its vendors and brands, executive and vendor impersonation against the tenant's profiles, payment/bank-change/gift-card/wire/payroll/urgency/secrecy/credential cues in English, Hindi and Hinglish (token-trie lexicons, linear pattern detectors for IBAN/SWIFT/IFSC/amounts), credential-harvesting links from the URL engine, and (opt-in) unusual communication patterns from keyed-hash history. `malicious` needs both identity and intent evidence. Every fired rule carries bounded evidence (codes, header names, parsed addresses/display names, profile ids, lexicon ids and offsets — never body text).
- **Optional AI layer, additive and bounded:** a packaged local model (`bec-lr/1`, shadow by default) and an LLM (Anthropic Claude via `@anthropic-ai/sdk`, **off by default**). The AI can never produce `clean`, never lowers a verdict, raises to at most `suspicious` alone and corroborates `malicious` only within a small band below the threshold; shadow mode never changes anything.
- **Tenant data:** executive and vendor profiles, trusted senders (trust only applies when the message authenticates as that sender), analyst feedback with bounded suppressions, a feature-only feedback export for retraining, opt-in history with purge. Four permissions: `bec:read`, `bec:manage`, `bec:feedback`, `bec:feedback_export`.
- **Dev pass-through:** a round whose `bec` result is `suspicious` or `malicious` is **not approved** locally (`delivery_approvals_skipped_total{reason="bec_verdict"}`; a bec `malicious` makes the round `malicious`, held as before). Policy (5.2) must treat the bec result explicitly.

Running it locally: nothing new to start — the email-worker runs the engine (`SCAN_ENGINES=rspamd,attachment,url,bec`, readiness check `bec-engine`), `pnpm rabbitmq:init` provisions topology v6 (17 queues). New keys: `.env.example` section "Phishing and BEC detection (step 4.4)" (secrets `BEC_CONTEXT_HMAC_KEY`, generated, and `BEC_LLM_API_KEY`, operator-supplied and empty by default); existing `.env` files: append the section and add `bec` to `SCAN_ENGINES` and `scan.bec` to `RECONCILE_QUEUES`. **Enabling the LLM** is an operator decision: set `BEC_LLM_API_KEY`, raise the platform cap `BEC_LLM_MODE` (`shadow` first), and let tenants opt in with `ai.llm` in `/scan-settings/bec`; read the data-handling and retention notes in [docs/deployment/bec-detection.md](docs/deployment/bec-detection.md) first. Tests never call a real LLM (`BEC_LLM_PROVIDER=fake` in integration runs, refused in production).

## Engineering rules (short version)

- Strict TypeScript, ESLint, Prettier. No `any`, no `console`.
- No business logic in controllers. No credentials in code or git.
- Apps never import each other. Shared code goes through `packages/*`.
- The tenant comes from authentication or the mail connector, never from headers. Deployment mode is configuration, never a code branch.
- Consumers are idempotent (`processOnce`). Events carry ids and S3 keys, never message bodies.
- Every schema change ships with a reviewed migration.
