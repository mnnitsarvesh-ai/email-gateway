# Email Security Gateway

A multi-tenant email security gateway: inbound, outbound and internal mail inspection, spam and phishing detection, malware and attachment scanning, URL protection, BEC detection, DLP, quarantine and optional archiving. It runs as shared SaaS or as a dedicated per-customer deployment. The design target is **1M emails/day**, scaling horizontally beyond that.

Step 3.2 makes the pipeline event-driven over RabbitMQ ([design and verification record](docs/plan/steps/07-rabbitmq.md), [ADR-0023](docs/architecture/adr/0023-outbox-relay-and-reconciliation.md), [ADR-0024](docs/architecture/adr/0024-rabbitmq-topology-retry-dead-letter.md)): a ninth deployable, **`event-relay`**, publishes every `message_outbox` row with publisher confirms (marking it published only after the confirm) into topology v1 (vhost `email-gateway`, six topic exchanges, fourteen quorum queues, tenant-aware routing keys `org.<id>.<eventType>`, least-privilege role users) and reconciles published events against the consumers' ledgers; the email-worker consumes `email.received` and the delivery-worker `email.delivery.pending` through the shared client library (manual acks after the `processOnce` transaction, retries with exponential backoff that never consume an attempt during outages, a delay queue for delivery, one dead-letter queue, a content guard that keeps bodies off the bus); dead letters are replayed only through an audited, MFA-protected platform API. **The outbox poller is no longer a production transport and there is no fallback to it** (two transports per consumer would double the failure modes; a broker outage leaves rows unpublished in the outbox and the reconciler covers lost events); only the development-only dev pass-through and smtp-adapter's cache invalidation still tail the outbox. Step 3.3 adds the message lifecycle (fifteen states, one transition service, history, rescan and release APIs, expiry). Step 4.1 adds the security scan pipeline (below): every parsed message is scanned post-queue by Rspamd in the email-worker scan role and ends `scanned` or `scan_failed`, with standardized verdicts and SPF/DKIM/DMARC/ARC results recorded. Policies (5.x) come next. See [docs/architecture/overview.md](docs/architecture/overview.md#what-exists-now-and-what-comes-next) and [docs/plan/execution-plan.md](docs/plan/execution-plan.md).

## Quick start

**Prerequisites:** Node.js ≥ 22.12, pnpm 9 (`corepack enable`), and Docker with Compose v2 (≈ 6 GB RAM for the full stack).

```bash
pnpm install
pnpm env:init                       # creates .env with random local secrets (git-ignored)
docker compose up -d --wait         # MySQL primary + replica, RabbitMQ, Redis, MinIO, both Postfix MTAs, Rspamd, ClamAV, redis-dkim
pnpm db:migrate                     # history preflight + apply database migrations
pnpm test:integration               # verify every infrastructure service
```

Then either run the services on the host, with hot reload:

```bash
pnpm dev                            # all services (reads ../../.env)
pnpm --filter @email-gateway/api dev  # or just one
```

or run everything in containers:

```bash
docker compose --profile apps up -d --build --wait
pnpm test:integration               # now also checks every service's /health/ready
```

MySQL runs as a GTID primary plus a read replica. The one-shot `mysql-replica-setup` container creates the database accounts and seeds the replica with CLONE on first start (about 10 s). After that it is a no-op. Only the api reads from the replica (`DATABASE_READ_URL`); see [replication](docs/database/replication.md). If your `.env` predates the replica, append `MYSQL_REPLICA_HOST_PORT`, `MYSQL_READER_*`, `MYSQL_REPLICATION_*` (password at most 32 characters) and `DATABASE_READ_*` from `.env.example`, without regenerating the existing secrets.

Step 1.2/1.3 (tenants, authentication, RBAC) adds api keys: `AUTH_JWT_SECRET`, `AUTH_TOKEN_PEPPER`, `DATA_ENCRYPTION_KEY` (secrets), `PORTAL_PUBLIC_URL`, `HTTP_TRUST_PROXY` and the `AUTH_*`/`PLATFORM_*`/`ORG_*` tuning keys (see the "API authentication and tenancy" section of `.env.example`). If your `.env` predates them, append that section from `.env.example` and fill the `__GENERATE_64__` placeholders with `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`, without rotating existing secrets (never `env:init --force`). Transactional email (invitations, password resets) goes through `NOTIFY_SMTP_*`; when `NOTIFY_SMTP_HOST` is empty the api logs the email (with a dev link) instead of sending it.

Step 2.1 (domain onboarding) adds the section "Domain onboarding and DNS (step 2.1)" of `.env.example`: `DNS_*` (resolver mode, servers, DoH URL, timeouts, propagation upstreams, cache), `GATEWAY_*` (the MX hosts and SPF include customers publish, DMARC report addresses), `DOMAIN_*` (verification label and lifetime, reserved names, background-job tuning) and `DKIM_ROTATION_OVERLAP_DAYS`. None of them is a secret. `GATEWAY_MX_HOSTS` and `GATEWAY_SPF_INCLUDE` have no default: the api refuses to start without them. If your `.env` predates them, append the section without touching anything else:

```bash
grep -q '^GATEWAY_MX_HOSTS=' .env || sed -n '/^# --- Domain onboarding and DNS (step 2.1) ---/,/^DKIM_ROTATION_OVERLAP_DAYS=/p' .env.example >> .env
```

The local values point at `.test` names; in a real deployment set `GATEWAY_MX_HOSTS`/`GATEWAY_SPF_INCLUDE` to the gateway's public names and choose the DNS resolver ([runbook](docs/runbooks/domain-verification.md#dns-resolver-modes)). The API integration tests never use public DNS: they run their own in-process DNS server.

Step 2.2 (SMTP gateway) adds the section "SMTP gateway (step 2.2)" of `.env.example`: host ports of the outbound MTA and redis-dkim, `SMTP_ADAPTER_HOST` (where both Postfix containers reach smtp-adapter: `smtp-adapter` for the apps profile and CI, `host.docker.internal` when the adapter runs on the host with `pnpm --filter @email-gateway/smtp-adapter dev`), Postfix limits, TLS certificate paths (`POSTFIX_*TLS_*_PATH`) and queue timings, the redis-dkim passwords (`REDIS_DKIM_*_PASSWORD`, secrets) and URLs, `GATEWAY_TRACE_SECRET` (secret), and the adapter's cache, rate-limit, SASL and ingestion tuning. `POSTFIX_RELAY_DOMAINS` is deprecated: relay domains now come from the database through smtp-adapter. If your `.env` predates the section, append it and fill its placeholders yourself (never `env:init --force`):

```bash

# then replace each __GENERATE__ / __GENERATE_64__ in the appended lines, e.g. with
node -e "console.log(require('crypto').randomBytes(24).toString('hex'))"
```

### First login (local)

The first platform administrator is created from the command line (there is no sign-up). Activate it in the admin portal by opening the printed link with the portal's origin (`http://localhost:3001/auth/accept-invitation#token=…`; the portal then enrolls MFA at the first login), or through the API:

```bash
pnpm db:seed                                        # catalog: permissions, 8 roles, plans, the platform organization
pnpm --filter @email-gateway/api build              # the bootstrap CLI runs from dist/
pnpm --filter @email-gateway/api auth:bootstrap -- --email ops@example.com --display-name "Ops"
# prints an acceptance link …/auth/accept-invitation#token=egt_… to stdout (treat it like a password)

API=http://127.0.0.1:${API_HOST_PORT:-3000}/api/v1
curl -s -X POST $API/auth/invitations/accept -H 'content-type: application/json' \
  -d '{"token":"egt_…","password":"<12+ characters, not a common password>"}'   # → 204
curl -s -X POST $API/auth/login -H 'content-type: application/json' \
  -d '{"email":"ops@example.com","password":"…","organization":"platform"}'
```

The API must be running (`pnpm --filter @email-gateway/api dev`, or the `apps` Compose profile). The platform organization requires MFA, so the first login returns `mfaEnrollmentRequired: true`: enroll with `POST /auth/mfa/totp/setup` and `POST /auth/mfa/totp/enable { code }` (bearer token from the login; store the recovery codes), then refresh the session (`POST /auth/refresh`) to get an MFA access token; later logins finish with `POST /auth/mfa/verify`. Afterwards the administrator can create customer organizations (`POST /api/v1/organizations` with an `initialAdmin`), whose invitation emails go through `NOTIFY_SMTP_*` or, without a relay, are logged with a dev link. Details: [docs/security/authentication.md](docs/security/authentication.md).

On first start, ClamAV downloads about 300 MB of signatures. `--wait` blocks until it is healthy, which can take a few minutes.

Optional profiles: `--profile analytics` (OpenSearch, ClickHouse) and `--profile observability` (OpenTelemetry Collector, Prometheus, Grafana).

## Message lifecycle (step 3.3)

Every message has one lifecycle state in `email_messages.status` (fifteen states: `received`, `persisted`, `scanning`, `scanned`, `scan_failed`, `policy_evaluated`, `approved`, `quarantined`, `held_for_review`, `rejected`, `delivery_pending`, `delivery_retry`, `delivered`, `archived`, `expired`), plus `status_reason`, `version` (+1 per applied transition) and `lifecycle_round` (+1 on a rescan or release). Every write goes through `@email-gateway/message-lifecycle` ([packages/message-lifecycle](packages/message-lifecycle/README.md)): the transition table (edges E1–E27), a row lock plus a version compare-and-set, an idempotency key per transition, and in the same transaction one `email_message_status_history` row (actor role/service/type/id, reason, causing event, correlation id, occurrence time), one `email_events` row `lifecycle.<state>` and one `mail.message.state_changed.v1` outbox row. Late, duplicate or out-of-order requests never move a message backwards; they are recorded as `lifecycle.ignored`. Design: [step 3.3](docs/plan/steps/08-message-lifecycle.md), [ADR-0025](docs/architecture/adr/0025-message-lifecycle-state-machine.md), diagrams [11](docs/architecture/diagrams/11-message-state-machine.md) and [22](docs/architecture/diagrams/22-delivery-lifecycle.md), runbook [message lifecycle](docs/runbooks/message-lifecycle.md).

Who moves a message today: smtp-adapter (`received` → `persisted` in the SMTP commit), the email-worker scan role (`persisted → scanning → scanned | scan_failed`, step 4.1), the policy-engine (step 5.2: `scanned | scan_failed | persisted → policy_evaluated → approved | quarantined | held_for_review | rejected`, E5/E8–E13; the dev pass-through's E27 and E4 are retired), the delivery planner (`approved → delivery_pending`), the shared delivery recorder (`delivery_retry` / `delivered` / `rejected`, derived from the per-recipient states), the api (operator rescan; since step 5.3 the quarantine module: manual quarantine E29/E16, reject and delete E17/E18), the policy-engine's quarantine role (step 5.3: releases E14/E15/E28, expiry E26 `quarantine_expired`) and event-relay (expiry, lost-derivation recovery). A partial delivery is `delivered` with reason `delivery_partial`; every recipient failed is `rejected` with `delivery_failed`.

event-relay roles (each a flag, single owner through MySQL `GET_LOCK`): `RELAY_ENABLED` (outbox relay), `RECONCILE_ENABLED` (re-drive of unconsumed events), `LIFECYCLE_EXPIRY_ENABLED` (expires a message stuck past its state's deadline, `LIFECYCLE_DEADLINE_<STATE>_HOURS`), `LIFECYCLE_CHECK_ENABLED` (re-derives a lost delivery transition, gauges of stuck messages). Keys: `.env.example` section "Message lifecycle (step 3.3)".

Routes (OpenAPI at `/docs`, [docs/api/README.md](docs/api/README.md)):

| --------------------------------------------- | -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /api/v1/messages/{id}/lifecycle`         | `message:read`       | State, reason, version, round, parse outcome, recipient counts, allowed actions (replica)                                                                                                                            |

## Security scanning (step 4.1)

Every parsed message is scanned post-queue by the **email-worker scan role** ([design and verification record](docs/plan/steps/09-rspamd.md), [ADR-0026](docs/architecture/adr/0026-security-scan-pipeline.md), [runbook](docs/runbooks/scan-pipeline.md), [Rspamd deployment](docs/deployment/rspamd.md), diagrams [9](docs/architecture/diagrams/09-scanning-sequence.md) and [23](docs/architecture/diagrams/23-scan-pipeline.md)): `mail.message.parsed.v1` (or an operator's `rescan_requested.v1`) on `scan.spam` → the round opens (`persisted → scanning`, one `email_scans` row per lifecycle round) → the EML is streamed from S3 to Rspamd `/checkv2` with the trusted envelope (client IP, HELO and host name from Postfix XFORWARD, envelope sender, recipients) → the reply is mapped to one of seven verdicts (`clean`, `spam`, `suspicious`, `malicious`, `unknown`, `timeout`, `error`) with reason codes such as `spam.gtube`, `auth.spf_fail`, `auth.dmarc_reject`, `phishing.known_bad_url` → `scan_engine_results`, `email_auth_results` (SPF/DKIM/DMARC/ARC), `scanned` or `scan_failed` and `mail.message.scanned.v1` in one transaction. Engine timeouts, errors, an open circuit breaker or a missing EML are **never clean**: they are retried (non-final attempt rows) and end `scan_failed` when the attempt budget or the round deadline is spent. Rspamd also runs at SMTP time as the inbound milter ([ADR-0027](docs/architecture/adr/0027-rspamd-milter-policy.md)): it rejects only GTUBE and score ≥ 15 (`554 5.7.1`), strips forged `Authentication-Results`/`X-Spam*` headers, adds ours, and **accepts** when Rspamd is down (the post-queue scan still runs).

Running it locally: `docker compose up -d --wait` starts `rspamd`; `docker compose --profile smtp-test up -d --wait dns-sink` serves the `scan.test` zones Rspamd resolves (`RSPAMD_DNS_SERVERS=172.31.250.53`); the email-worker runs both roles (`MIME_INGESTION_ENABLED=true`, `SCAN_ENABLED=true`, broker user `eg-scanner` from `RABBITMQ_SCANNER_URL`; `pnpm rabbitmq:init` creates it). New keys: `.env.example` section "Security scanning (step 4.1)" — `RABBITMQ_SCANNER_*`, `SCAN_ENABLED`, `SCAN_ENGINES`, `SCAN_RSPAMD_URL`, `RSPAMD_CONTROLLER_URL`, `RSPAMD_CONTROLLER_PASSWORD`, `RSPAMD_CONTROLLER_ENABLE_PASSWORD`, the `SCAN_RSPAMD_*` thresholds, timeouts, attempts, breaker, deadline and sweeper keys, `SCAN_FUZZY_WEIGHT`, and the `RSPAMD_*` keys of the Rspamd container (DNS, Redis DB 1, Bayes `min_learns`, RBL profile, phishing feeds, milter reject score, authserv-id). Existing `.env` files: append the section and generate the three new secrets yourself (never `pnpm env:init --force`; see [docs/deployment/rspamd.md](docs/deployment/rspamd.md#environment-envexample-section-security-scanning-step-41)). `RECONCILE_QUEUES` now includes `scan.spam`.

## Attachment scanning (step 4.2)

Every round also requires the **`attachment` engine** ([design and verification record](docs/plan/steps/10-attachment-scanning.md), [ADR-0028](docs/architecture/adr/0028-attachment-scanning-engine.md), [runbook](docs/runbooks/attachment-scanning.md), [deployment](docs/deployment/attachment-scanning.md), [performance](docs/performance/attachment-scanning.md)) on `scan.attachment` (consumer `email-worker.scan.attachment`; production Deployment `email-worker-attachment`). Per round it reads the parse row and the attachment rows on the writer (no attachments on a complete parse → `skipped`; an incomplete parse, i.e. any parse limit but `body_size`, → at least `suspicious`), looks every SHA-256 up in the platform-wide known-threat catalog, and per attachment reads the stored part from S3 (size and SHA-256 verified) and runs, in parallel, clamd `INSTREAM` (`@email-gateway/clamav`) and an inspector child process (true file type, zip/gzip/tar walk under depth/entry/size/ratio limits, encryption markers, YARA-X with the bundle `apps/email-worker/yara`) under `prlimit` and a `/proc` CPU/RSS watchdog. Results map to `clean`, `suspicious`, `malicious` or `unknown` per attachment (`attachment-map/1`; `clean` only with a definite ClamAV `OK` and nothing else); the most severe one is the engine's result. Content results are cached in Redis under `eg:scan:att:v2:<sha256>:<contentVersion>` (the version changes with every ClamAV database and YARA bundle), authenticated with the worker-only `ATTACHMENT_CACHE_HMAC_KEY`. Suspicious and unknown stored attachments become `sandbox_submissions` rows with a `mail.attachment.sandbox_requested.v1` event (consumed in step 4.6). A signature watcher records new ClamAV/YARA versions and, with `ATTACHMENT_SIGNATURE_RESCAN=rescan`, a rescan job that the runner executes in batches. Since step 5.2 the policy floor rejects `malicious` messages (never delivered).

Running it locally: `docker compose up -d --wait` starts `clamav` (`clamav/clamav-debian:1.4`, about 1 GiB RSS once the database is loaded); the host email-worker reads `CLAMAV_HOST`/`CLAMAV_PORT` and needs `ATTACHMENT_INSPECTOR_RLIMITS=best_effort` on macOS (no `prlimit`; refused in production). New keys: `.env.example` section "Attachment scanning (step 4.2)" — `CLAMAV_*`, `SCAN_ATTACHMENT_*`, the `ATTACHMENT_*` limits, inspector, YARA, cache (incl. the secret `ATTACHMENT_CACHE_HMAC_KEY`), sandbox, signature-watcher and rescan keys. Existing `.env` files: append the section (`pnpm env:init` generates the secret for a new file).

## URL protection (step 4.3)

Every round also requires the **`url` engine** ([design and verification record](docs/plan/steps/11-url-protection.md), ADRs [0029](docs/architecture/adr/0029-url-security-engine.md) (engine), [0030](docs/architecture/adr/0030-url-rewriting-and-click-tokens.md) (rewriting and tokens), [0031](docs/architecture/adr/0031-time-of-click-service.md) (click-service), [0032](docs/architecture/adr/0032-url-browser-isolation.md) (browser isolation); [deployment](docs/deployment/url-protection.md); runbooks [url-scanning](docs/runbooks/url-scanning.md), [click-service](docs/runbooks/click-service.md), [url-browser-worker](docs/runbooks/url-browser-worker.md)) on `scan.url` (consumer `email-worker.scan.url`; production Deployment `email-worker-url`). From the stored bodies (and small text/html attachments) it extracts and normalizes every http(s) URL (`@email-gateway/url-security`), checks URL, host, registrable domain, literal IPs and the public addresses the hosts resolve to against the platform threat feed (`threat_indicators`, never cached), DNS blocklists and RDAP domain age through an HMAC-authenticated Redis cache, detects lookalike domains (Unicode confusables, edit distance, combosquatting, mixed scripts), resolves shorteners and suspicious links through **one SSRF-guarded fetcher** (every hop re-validated, IP-literal dialling, every non-public IANA range blocked) and maps them with `url-map/1` (`clean` only when every provider answered and every attempted fetch completed; outages → `unknown`). It then writes a **rewritten copy** of the EML (`org/<org>/rewrite/…`) whose links point at `URL_CLICK_BASE_URL/c/<signed token>`; approvals deliver that copy (signed/encrypted mail, DKIM policy `skip`, oversize mail and messages without URLs are delivered unchanged). Messages without URLs: `skipped` (`url.none`).

At click time the **`click-service`** (public port 3080, admin 3081, its own MySQL account `gateway_click`, no S3, no broker) verifies the token (HMAC, expiry), rechecks the URL within a 2.5 s budget (feed, cache, the redirect chain re-resolved for every clicked URL with lookalike and hop/address reputation of its destination, the dynamic result) and allows (302 to the URL stored server side — never an open redirect), warns (interstitial with an optional continue link) or blocks (403 with a reference id) under the tenant's click policy, logging one `url_click_events` row and `mail.url.clicked.v1`. Suspicious and unknown URLs can be inspected by the isolated **`url-browser-worker`** (real Chromium headless shell, profile `url-browser`, no database/S3/Redis/secrets, all traffic through the token-authenticated **`url-egress-proxy`** with the same SSRF guard); its result is used at click time.

Running it locally: the apps profile starts `click-service`; `docker compose --profile smtp-test up -d` starts `url-test` (TEST-ONLY corpus web server on 203.0.113.10, published 18080/18443) and the `dns-sink` corpus (published 1053); `docker compose --profile smtp-test --profile url-browser up -d url-egress-proxy url-browser-worker` starts the browser pair (about 1.3 GiB; never together with the analytics or observability profiles on an 8 GB VM). New keys: `.env.example` section "URL protection (step 4.3)" (≈ 113 keys, secrets `URL_CACHE_HMAC_KEY`, `URL_TOKEN_KEY_CURRENT`, `URL_EGRESS_PROXY_TOKEN`, `MYSQL_CLICK_PASSWORD`, `RABBITMQ_URL_BROWSER_PASSWORD`); `.env` values are host-run values, Compose fixes the container ones. Rewriting changes the body, so the tenant's mailbox platform must trust the gateway ([destination servers](docs/domains/destination-servers.md#link-protection-rewrites-messages-trust-the-gateway)).

| `GET /api/v1/messages/{id}/scans`                                  | `message:read`                 | The `url` engine entry lists per-URL results (verdict, reasons, reputation, lookalikes, redirect chain hosts, landing and dynamic signals, rewritten, clicks) and the round's rewrite; never cache flags or per-URL durations |

## Phishing and BEC detection (step 4.4)

Every round also requires the **`bec` engine** ([design and verification record](docs/plan/steps/12-phishing-bec.md), ADRs [0033](docs/architecture/adr/0033-bec-engine-and-stage-dependencies.md) (engine and stage dependencies), [0034](docs/architecture/adr/0034-bec-ai-layer-invariant.md) (AI layer invariant), [0035](docs/architecture/adr/0035-bec-communication-context-privacy.md) (communication history); [deployment](docs/deployment/bec-detection.md); [runbook](docs/runbooks/bec-detection.md); [diagram 23](docs/architecture/diagrams/23-scan-pipeline.md)) on `scan.bec` (consumer `email-worker.scan.bec`; production Deployment `email-worker-bec`). It is the first **stage-2** engine: the transaction that inserts the last of a round's `rspamd`/`url` finals writes one `mail.message.scan_stage_ready.v1`, so the engine always sees that round's real SPF/DKIM/DMARC results and URL verdicts (a failed dependency is recorded as an unavailable input, never clean). Inbound mail only (`outbound`/`internal` → `skipped`).

- **Deterministic first** (`@email-gateway/bec`, verdict map `bec-map/1`, 50 rules with stable ids and reason codes): sender identity and alignment, display-name spoofing (UTS #39 confusables, embedded addresses, brand names), Reply-To and Return-Path mismatches, SPF/DKIM/DMARC failures and tenant-domain spoofing, lookalike domains of the tenant, its vendors and brands, executive and vendor impersonation against the tenant's profiles, payment/bank-change/gift-card/wire/payroll/urgency/secrecy/credential cues in English, Hindi and Hinglish (token-trie lexicons, linear pattern detectors for IBAN/SWIFT/IFSC/amounts), credential-harvesting links from the URL engine, and (opt-in) unusual communication patterns from keyed-hash history. `malicious` needs both identity and intent evidence. Every fired rule carries bounded evidence (codes, header names, parsed addresses/display names, profile ids, lexicon ids and offsets — never body text).
- **Optional AI layer, additive and bounded:** a packaged local model (`bec-lr/1`, shadow by default) and an LLM (Anthropic Claude via `@anthropic-ai/sdk`, **off by default**). The AI can never produce `clean`, never lowers a verdict, raises to at most `suspicious` alone and corroborates `malicious` only within a small band below the threshold; shadow mode never changes anything.
- **Tenant data:** executive and vendor profiles, trusted senders (trust only applies when the message authenticates as that sender), analyst feedback with bounded suppressions, a feature-only feedback export for retraining, opt-in history with purge. Four permissions: `bec:read`, `bec:manage`, `bec:feedback`, `bec:feedback_export`.
- **Delivery (since step 5.2):** a deterministic bec `suspicious`/`malicious` verdict is quarantined by the policy platform default (rule D2); a bec `malicious` round carries a risk hard block and is rejected. (Steps 4.4–5.1: the dev pass-through held it in `scanned`.)

Running it locally: nothing new to start — the email-worker runs the engine (`SCAN_ENGINES=rspamd,attachment,url,bec`, readiness check `bec-engine`), `pnpm rabbitmq:init` provisions topology v6 (17 queues). New keys: `.env.example` section "Phishing and BEC detection (step 4.4)" (secrets `BEC_CONTEXT_HMAC_KEY`, generated, and `BEC_LLM_API_KEY`, operator-supplied and empty by default); existing `.env` files: append the section and add `bec` to `SCAN_ENGINES` and `scan.bec` to `RECONCILE_QUEUES`. **Enabling the LLM** is an operator decision: set `BEC_LLM_API_KEY`, raise the platform cap `BEC_LLM_MODE` (`shadow` first), and let tenants opt in with `ai.llm` in `/scan-settings/bec`; read the data-handling and retention notes in [docs/deployment/bec-detection.md](docs/deployment/bec-detection.md) first. Tests never call a real LLM (`BEC_LLM_PROVIDER=fake` in integration runs, refused in production).

## Data loss prevention (step 4.5)

Every round also requires the **`dlp` engine** ([design and verification record](docs/plan/steps/13-dlp.md), ADRs [0036](docs/architecture/adr/0036-dlp-engine-and-extraction.md) (engine and extraction), [0037](docs/architecture/adr/0037-dlp-policy-actions-and-lifecycle-binding.md) (policy actions and lifecycle binding), [0038](docs/architecture/adr/0038-dlp-evidence-masking-and-aadhaar-gating.md) (evidence, masking, Aadhaar gating); [deployment](docs/deployment/dlp.md); [runbook](docs/runbooks/dlp.md); [performance](docs/performance/dlp.md); [diagram 23](docs/architecture/diagrams/23-scan-pipeline.md)) on `scan.dlp` (consumer `email-worker.scan.dlp`; production Deployment `email-worker-dlp`, the only email-worker holding `DLP_EVIDENCE_KEY`). It is a **stage-1** engine (in parallel with rspamd, attachment and url) and scans `outbound` and `internal` mail; `inbound` only when the tenant enables `inboundEnabled` (otherwise `skipped`, `dlp.not_inbound`).

- **Detection** (`@email-gateway/dlp`, verdict map `dlp-map/1`, 23 detectors): payment cards (Luhn, IIN table, test numbers excluded), IBAN/IFSC+account/SWIFT, PAN, Aadhaar (Verhoeff; **only with a recorded compliance basis**), passports and MRZ, e-mail/mobile/date of birth/GSTIN, confidential labels and business keywords, tenant keyword dictionaries, source code, private keys/AWS/JWT/API tokens, financial documents and tenant patterns (RE2 semantics through `re2js`, validated for breadth and cost). Hand-written linear scanners, context-aware confidence (positive/negative/disclaimer context, table columns, bulk, code penalty) and per-category thresholds.
- **Attachment text extraction** in a second resource-limited child pool (the 4.2 isolation: empty environment, Node permission model, heap/CPU/RSS caps, wall clock), reusing the 4.2 walker and limits: text/CSV/JSON/XML, HTML, PDF (`pdfjs-dist` 4.10.38, evaluation disabled), DOCX/XLSX/PPTX, ODF, zip/gzip/tar and nesting. What cannot be read (encrypted, images without OCR, PDFs without a text layer, legacy Office, oversize, not stored, limits) is a coverage code and the verdict is at least `unknown` — never `clean`.
- **Tenant policies** evaluated at scan time (deterministic, strongest action wins): `allow` < `alert` < `require_approval` < `quarantine` < `block`, with directions, sender/recipient scopes (`externalOnly`), counts, confidence and severity, coverage selectors, `monitor` mode and **exceptions** (sender/recipient address or domain, optional rule/policy target and detector filters, mandatory expiry). Without a tenant policy the platform default alerts on high-severity identifiers and credentials. Every action other than `allow` writes one `mail.message.dlp_incident.v1` (ids, codes and counts only; the notification hook of step 6.2).
- **Masked everywhere; evidence encrypted.** Results, the scans read API, incidents, logs, metrics and events carry masked values only. Matched values with their context are kept per round as an **envelope-encrypted evidence object** in S3 (`org/<org>/dlp-evidence/…`, data key wrapped with `DLP_EVIDENCE_KEY`, crypto-shredded at the tenant's retention ≤ 180 days by the evidence sweeper); card numbers stay first 6 + last 4 even there, Aadhaar numbers, private keys and secrets stay masked, CVV codes are never stored. The only door is `GET …/dlp-evidence` (`dlp:evidence_read`, MFA, users only, an audit row committed before decryption, `Cache-Control: no-store`).
- **Delivery (since step 5.2):** the DLP action is part of the policy floor: `allow` → no effect, `alert` → allowed with the mandatory TAG `dlp-alert` (header suppressed outbound by default), `require_approval` → `held_for_review`, `quarantine` → `quarantined`, `block` → `rejected` (outbound: a sender non-delivery notice is requested); a missing `dlp_scan_results` row → quarantined. (Steps 4.5–5.1: the dev pass-through held these in `scanned`.)

Running it locally: the email-worker runs the engine (`SCAN_ENGINES=rspamd,attachment,url,bec,dlp`, readiness checks `dlp-engine` and `dlp-extractor`), `pnpm rabbitmq:init` provisions topology v7 (`scan.dlp` becomes a work queue). New keys: `.env.example` section "Data loss prevention (step 4.5)" (secret `DLP_EVIDENCE_KEY`, generated, given only to the email-worker and the api; `DLP_EVIDENCE_KEY_PREVIOUS` for rotation); existing `.env` files: append the section and add `dlp` to `SCAN_ENGINES` and `scan.dlp` to `RECONCILE_QUEUES`. **Enabling Aadhaar detection** is a tenant compliance decision: an `organization_admin` with MFA records the basis, reference, attestation and review date with `PUT /api/v1/dlp/compliance/aadhaar` (`dlp:compliance_manage`); without it the detector does not run at all ([runbook](docs/runbooks/dlp.md)).

## Sandbox (step 4.6)

**Execution of unknown files is DISABLED.** The sandbox exists as an orchestration layer, an isolation contract and a threat model; it does not detonate anything in the default configuration, and it cannot in production in this release.

- **What runs:** the email-worker's asynchronous **`sandbox` engine** ([design and verification record](docs/plan/steps/14-sandbox.md), [ADR-0040](docs/architecture/adr/0040-sandbox-engine-dispatch-results-artifacts.md)) takes each `suspicious`/`unknown` attachment the attachment engine submits (`scan.sandbox.submissions`), checks the plan feature `attachment_sandbox` and the tenant opt-in, deduplicates by content hash, seals the sample into the restricted sandbox bucket and dispatches a task (`scan.sandbox`) to the isolated **`sandbox-controller`** ([ADR-0039](docs/architecture/adr/0039-sandbox-security-boundary-and-backends.md); no database, Redis, mail-bucket or token credentials — the configuration refuses them). The controller's MAC-protected result (`scan.sandbox.results`) is mapped by `sandbox-map/1` to the round's `sandbox` final. **Asynchronous:** the round never waits for the sandbox and its verdict never changes the round's verdict or the message lifecycle; delivery is unaffected by any sandbox outage. Artifacts are sealed with an X25519-wrapped key whose private half no service holds.
- **Backends (`SANDBOX_BACKEND` of the controller):** `disabled` (default everywhere: results are `not_executed` → `unknown`, never `clean`); `static` (static analysis in a resource-limited child process; **no execution**; production-eligible); `hardened-container` (a **local/CI test harness only**: one disposable hardened Docker container per task on an internal network whose only peer is a recording sinkhole — a shared-kernel container is **NOT a VM boundary**; refused outside `APP_ENV=local|ci`, inside Kubernetes and without `SANDBOX_ALLOW_NON_VM_EXECUTION=true`); `vm` (a preflight contract that **refuses to start**: no verified VM-class runner exists). **Production accepts `disabled` or `static` only.** No result is ever `clean` in this release (`clean` needs a complete VM-isolated run).
- **Opting a tenant in:** the organization needs the plan feature `attachment_sandbox`; then `PUT /api/v1/scan-settings/sandbox { "expectedVersion": 0, "settings": { "enabled": true } }` (`scan:settings_manage`; without the feature `409 feature_not_enabled`). Optional narrowing: `fileTypes`, `maxSampleBytes`, `browserAnalysis`. `GET /api/v1/scan-settings` shows the plan feature and the environment's `execution` mode (`disabled`, `static_only`, `local_test_runner`, from the api's informational `SANDBOX_EXPECTED_BACKEND`). Results: `GET /api/v1/messages/{id}/scans` (`message:read`) — the per-attachment sandbox outcome and the `sandbox` engine entry with findings, indicator hosts/IPs, process images, dropped-file hashes and artifact metadata; no artifact download ([API](docs/api/README.md)).
- **Running it locally:** the controller is part of the `apps` profile (`docker compose --profile apps up -d`, image from `node-service.Dockerfile` with `APP=sandbox-controller`, backend `disabled`; port 3092 inside the internal `sandbox-control` network only — read health and metrics with `docker compose exec sandbox-controller node -e "fetch('http://127.0.0.1:3092/health/ready').then(async r=>console.log(await r.text()))"`). Static analysis: `SANDBOX_BACKEND=static docker compose --profile apps up -d sandbox-controller`. The **execution override** (local/CI only, NOT a VM boundary; builds `email-gateway/sandbox-runner:local` and uses `email-gateway/url-browser-worker:local`; mounts the Docker socket into the controller): `docker compose -f docker-compose.yml -f infrastructure/sandbox/compose.exec.yml --profile apps --profile sandbox up -d --wait sandbox-controller`; undo with `docker compose --profile apps up -d --force-recreate sandbox-controller`. Never together with the analytics/observability profiles (browser runners take ~1 GiB). Stack suites: `tests/integration/sandbox-smtp.test.ts` (in `pnpm test:integration`; `SANDBOX_STACK_BACKEND=static` for the static variant) and the focused `sandbox-exec.test.ts` (`SANDBOX_EXEC_TESTS=1`, local only); the escape-resistance suite: `pnpm --filter @email-gateway/sandbox-controller test:integration:runner`.
- **Keys** (`.env.example` section "Sandbox (step 4.6 …)"): `SANDBOX_SAMPLE_KEY`, `SANDBOX_RESULT_KEY`, the X25519 artifact key pair (`SANDBOX_ARTIFACT_PUBLIC_KEY` for the controller; `SANDBOX_ARTIFACT_PRIVATE_KEY` for tests and the ops script only — the controller refuses it), `RABBITMQ_SANDBOX_PASSWORD`, `SANDBOX_S3_SECRET_ACCESS_KEY`, `SANDBOX_SINKHOLE_ADMIN_TOKEN`.

Read first: the [threat model](docs/security/sandbox-threat-model.md) (assets, attackers, boundaries, residual risks and the production preconditions for execution), ADRs [0039](docs/architecture/adr/0039-sandbox-security-boundary-and-backends.md) and [0040](docs/architecture/adr/0040-sandbox-engine-dispatch-results-artifacts.md), runbooks [sandbox-controller](docs/runbooks/sandbox-controller.md) and [sandbox-engine](docs/runbooks/sandbox-engine.md), [deployment](docs/deployment/sandbox.md) and [escape testing](docs/security/sandbox-escape-testing.md). **Not provided in this release:** execution of unknown files in production, a VM-class runner (gVisor/Kata/Firecracker; not verifiable on this workstation), applied Kubernetes manifests (rendered only), an artifact download API and the organization purge of sandbox rows.

## Risk scoring (step 5.1)

Every completed scan round gets **one risk score** ([design and verification record](docs/plan/steps/15-risk-scoring.md), ADRs [0041](docs/architecture/adr/0041-risk-scoring-model.md) (the model) and [0042](docs/architecture/adr/0042-risk-scoring-placement-and-policy-handoff.md) (placement and hand-off to policy); [deployment](docs/deployment/risk-scoring.md); [runbook](docs/runbooks/risk-scoring.md); [calibration report](docs/performance/risk-scoring-calibration.md)). The pure, deterministic library `@email-gateway/risk-scoring` (integer arithmetic, no I/O) maps every engine's reason codes and child rows (authentication, spam, IP/domain reputation, URL, attachment, phishing, BEC, DLP) through the versioned signal map `risk-signals/1` to signals in de-duplicating groups, and returns a score 0–1000, a level (`none`, `low`, `medium`, `high`, `critical`), a verdict, a recommended action (`deliver` < `tag` < `require_approval` < `quarantine` < `block`), the fired hard blocks (malware, DLP `block`, known phishing, tenant-domain spoofing, tenant-blocked URLs, deterministic BEC `malicious`), engine failures, trust decisions and a content-free explanation.

- **Where it runs and where the result is:** the email-worker scores in the round's completion transaction (also for rounds closed by the deadline sweeper) and writes `message_risk_scores` revision 0 plus `email_scans.verdict`, `risk_score`, `scoring_version`; a late sandbox final adds revision 1. The profile is snapshotted when the round opens (`email_scans.risk_profile_version_id`), so a profile change applies to the **next** round only. Unknown, timeout, error, a missing result or child row and a scoring error are never `clean`: failures force at least `medium` / `quarantine`, a scoring error writes a fail-safe row (`high`, `quarantine`).
- **What is enforced (since step 5.2):** the policy-engine's platform default `pol-default/1` follows the recommendation (`deliver`/`tag` → allow, `require_approval`, `quarantine`, `block` → reject) and its floor enforces hard blocks, failures, error rows and missing rows; tenant rules may be stricter, and weaker only for a level-only recommendation through an audited override ([Policy engine (step 5.2)](#policy-engine-step-52)). (In 5.1 the local/ci dev pass-through held these rounds.)
- **Profiles:** the platform default `rsk-default/1` (`RISK_PLATFORM_PROFILE`) plus per-tenant versions with bounded overrides (thresholds, level actions, group multipliers 0.5×–2×, hard-block toggles and actions within the allowed set, raise-only failure floors, trust factor, the AI tag switch). Drafts are editable; published versions are immutable; activation is a pointer (rollback = activate an earlier version, reset = platform default). Audited.
- **Dry-run:** `POST /api/v1/messages/{messageId}/scans/{scanId}/risk/dry-run` re-scores a stored round from the replica against `active` (the round's own snapshot: reproduces the stored `inputSha256` and result), `platform`, a version or inline overrides, and **writes nothing** (no row, no audit, no cache).
- **Not validated accuracy:** the default weights and thresholds are engineering defaults calibrated on a synthetic, self-constructed dataset (1 050 labelled fixtures). **No detection accuracy, precision or recall is claimed**; that needs a validated real-world dataset. No real IP or domain reputation feed is configured locally.

## Policy engine (step 5.2)

Every scanned, scan-failed and parse-failed round gets **one policy evaluation**, and only an `allow` is delivered ([design and verification record](docs/plan/steps/16-policy-engine.md), ADRs [0043](docs/architecture/adr/0043-policy-dsl-and-deterministic-evaluator.md) (DSL and evaluator), [0044](docs/architecture/adr/0044-policy-evaluation-placement-and-delivery-gating.md) (placement and delivery gating) and [0045](docs/architecture/adr/0045-policy-action-semantics.md) (actions), [DSL reference](docs/architecture/policy-dsl.md), [contracts §28](docs/architecture/contracts.md#28-policy-engine-step-52)).

- **Policies are data, not code:** versioned JSON documents (`policy-dsl/1`) over a closed catalog of sender, recipient, domain, IP, attachment, URL, risk, DLP, BEC, scan and time fields; AND/OR/NOT groups with three-valued logic; RE2 regexes only; rule and policy exceptions restricted to authenticated identity and the quantifier `all`; nine actions (`ALLOW`, `REQUIRE_APPROVAL`, `QUARANTINE`, `REJECT`, `TAG`, `WARN`, `URL_REWRITE`, `ARCHIVE`, `ALERT`). Drafts, immutable published versions, publish/activate/rollback, enable/disable; a change applies to the **next evaluation only**.
- **Decision:** the strictest matched tenant disposition, never weaker than the platform default `pol-default/1` (which follows the 5.1 risk recommendation) unless an `override` rule, the audited setting `allowRecommendationOverrides` and a level-only recommendation all agree; then the **strictness floor** (hard blocks, engine failures, missing risk/DLP rows, `scan_failed`, `parse_failed`, the DLP binding), which nothing weakens.
- **Enforced:** ALLOW → approved and delivered (the round's rewritten copy, or a **policy copy** with `X-EG-Policy-Tag` / `X-EG-Policy-Warning` headers and subject prefix for TAG/WARN); QUARANTINE → `quarantined`; REQUIRE_APPROVAL → `held_for_review`; REJECT → `rejected` (nothing delivered, no bounce inbound). Since step 5.3 held mail has per-recipient quarantine entries and is released only through the [quarantine API](#quarantine-step-53).
- **Requested** (performed by another stage): ARCHIVE (`mail.message.archive_requested.v1` into the dormant `email.archive`; the archive consumer is step 8.1), ALERT and the outbound REJECT sender non-delivery notice (notification-worker through `NOTIFY_SMTP_*`, at least once). **Recorded only:** TAG/WARN without a copy (headers suppressed, message too large), URL_REWRITE on a round that cannot be rewritten with `ifNotRewritten: deliver`; since 5.3 WARN body banners and URL rewriting after the scan are applied to the delivered copy (recorded `skipped_*` for signed, encrypted or too large messages).
- **Not in 5.2 (delivered by step 5.3 unless noted):** the quarantine store, end-user quarantine, digests and release re-validation; WARN body banners and URL rewriting after the scan; per-recipient dispositions. **Still open (so 5.2 is not complete):** the `email.archive` consumer, archiving and journaling (8.1); per-recipient dispositions; admin-portal screens.
- **No pass-through any more:** the delivery-worker's development pass-through and its keys (`DELIVERY_DEV_PASSTHROUGH_ENABLED`, `DELIVERY_DEV_PASSTHROUGH_RISK_HOLD`, `DELIVERY_OUTBOX_*`) are removed; `DELIVERY_DEV_PASSTHROUGH_ENABLED=true` is refused at startup. Local, CI and production stacks need the **policy-engine running**; without it mail stays `scanned` (held).

## Quarantine (step 5.3)

Held mail lives in a **per-recipient quarantine store** ([design and verification record](docs/plan/steps/17-quarantine.md), ADRs [0046](docs/architecture/adr/0046-quarantine-store-and-per-recipient-decisions.md) (store, per-recipient decisions), [0047](docs/architecture/adr/0047-quarantine-release-revalidation-and-approvals.md) (release re-validation and approvals), [0048](docs/architecture/adr/0048-quarantine-preview-and-download-controls.md) (preview and downloads), [0049](docs/architecture/adr/0049-policy-copy-body-edits-banners-and-url-rewrite.md) (banners and URL rewriting), [contracts §29](docs/architecture/contracts.md#29-quarantine-step-53), [runbook](docs/runbooks/quarantine.md), [deployment](docs/deployment/quarantine.md), [API reference](docs/api/README.md#quarantine-quarantine-tag-step-53)).

- **Entries:** the policy-engine writes one entry per held recipient (QUARANTINE → `held`, REQUIRE_APPROVAL → `pending_approval` with a review request) in the same transaction as the decision. When tenant rules are recipient-scoped, each recipient is decided alone (`recipientSplit`, default on): allowed recipients are delivered, the others held or rejected (`final_action = partial`). Messages held before 5.3 are adopted by the sweeper. No message content is stored in MySQL (the entry's subject column is never written).
- **Operators** (api, tag `quarantine`): bounded search, detail and history, a **sanitized preview** (JSON text from the decoded parts; no HTML, scripts, remote images or clickable links; DLP values masked; audited before reading), **downloads** only when the tenant enables them, through a single-use 60-second grant after password (+ TOTP) re-authentication and never of malicious content, **release** (pre-check, then the policy-engine's release executor re-validates against the latest scan round and the current policy; hard blocks, engine failures, DLP holds, policy rejections, reviews and stale verdicts need an **approval by a second, MFA-authenticated user** who is neither the requester nor the recipient), reject (sender notice outbound only), delete (refused under legal hold or retention; the sweeper purges the objects), manual quarantine (of a review or a policy rejection), **bulk** (≤ 100 items per request, ≤ 1 000 per organization and minute), settings.
- **End users** (`mailbox_user` role, `/quarantine/me/…`): their own entries only, preview (not for malware/phishing/hard blocks), self-release within tenant bounds (off by default), release requests, digest opt-out. Digests and approval/release notices are sent by the notification-worker (links require login; no one-click release).
- **Expiry never releases:** entries expire at the end of the hold period (tenant `quarantine_retention_days`, ≤ `QUARANTINE_MAX_HOLD_DAYS`) and the message becomes `expired`.
- **Delivered copies:** WARN rules add a body banner to the first text and HTML parts; URL_REWRITE rewrites links to the click service when the tenant's scan-time rewriting is off; a release delivers a copy with `X-EG-Quarantine-Release`. Signed or encrypted messages are left unchanged (`skipped_*` recorded).
- **Deployment:** the policy-engine image runs `POLICY_ENGINE_ROLES=evaluate,quarantine` in Compose; Kubernetes runs two Deployments (`policy-engine` with `evaluate`, `quarantine-worker` with `quarantine`). Topology v10 (`email.quarantine` is a work queue). The download token key `QUARANTINE_DOWNLOAD_TOKEN_KEY` is held by the api only; the policy-engine signs click tokens with the current URL token key only.
- **Not in 5.3:** admin-portal screens (7.x), webhooks and a preference center (6.2), legal-hold and retention management and archiving (8.1), post-delivery clawback (8.2), defanged-archive downloads.

New keys (`.env.example` section "Quarantine (step 5.3 …)", secret `QUARANTINE_DOWNLOAD_TOKEN_KEY=__GENERATE_64__`): `POLICY_ENGINE_ROLES`, `QUARANTINE_*` (hold/review bounds, transaction budgets, sweeper interval and batch, retention, digests, staleness, manual-quarantine window, search, preview, download, bulk), `POLICY_BANNER_MAX_PART_BYTES`, `POLICY_URL_REWRITE_ENABLED`; the URL token keys are now also passed to the policy-engine; `RECONCILE_QUEUES` += `email.quarantine`. The stack suite `tests/integration/quarantine-smtp.test.ts` covers the 14 cases of the design's §9.3 through Postfix and the live containers.

## Journal intake and the Journaling / Archive split (step 8.6)

Journaling and archiving without routing mail through the gateway, and a clear split between capturing mail and using the archive ([design and verification record](docs/plan/steps/27-journal-intake-and-archive-split.md), ADRs [0087](docs/architecture/adr/0087-journal-intake-path.md)–[0090](docs/architecture/adr/0090-archive-only-service-profile.md), [contracts §34](docs/architecture/contracts.md), [mail flow (management summary)](docs/architecture/mail-flow.md), [runbook](docs/runbooks/journal-intake.md), customer guides [Microsoft 365](docs/integrations/journal-intake-microsoft-365.md), [Google Workspace](docs/integrations/journal-intake-google-workspace.md) and [on-premises](docs/integrations/journal-intake-on-premises.md)). Implemented and verified on the local stack; **not complete**: commit, CI, a cluster apply and live Microsoft 365 / Google Workspace tenant tests are pending.

- **Two layers on top of the gateway.** **Journaling** decides what is captured — mail that flows through the gateway, and copies a customer's own mail system sends to a **journal intake address** (`journal-<token>@<JOURNAL_INTAKE_DOMAIN>`): Microsoft 365 journal reports, Google Workspace "Also deliver to" copies with a header token, on-premises Exchange journal reports and SMTP BCC copies. The **Archive** keeps and uses what was captured (retention, Object Lock, keys, access settings, search, legal holds, eDiscovery, access audit).
- **Journal intake** (`apps/smtp-adapter` LMTP listener 10053, ADR-0087): the inbound Postfix accepts mail for the intake domain only for existing sources, only from the source's proven sender (the bound step 8.2 connection's provider egress ranges, or the source's own networks, never a provider range), over TLS, one intake destination per transaction; the report is unwrapped (original EML + full journal envelope with Bcc), the content proof checked (Microsoft 365 tenant header, Google header token, stripped before storage); a failed proof is accepted and dropped (no backscatter). Intake copies are registry messages (`ingest_source = journal_intake`) that end in `journaled`: never delivered, forwarded, bounced, quarantined, evaluated by policies or sent to customer webhooks, and invisible in gateway views. Scanning them is optional per organization.
- **One record per message** (ADR-0088): gateway and intake copies of one message merge into one archive record (sources, merged parties, a differing body kept as a content variant under the record's key).
- **Health and alerts:** per-source counters, health (`healthy`, `silent`, `failing`, …) and the always-on `journal_intake_silent` e-mail alert.
- **Archive-only plan** (ADR-0090): plan `archive_only` (journal intake, journaling and archive without mail filtering); `GET /auth/me` returns `organization.serviceProfile`; the portal hides the gateway pages for it; archive-only domains need only the ownership record.
- **Api and portal:** the `journaling` tag (12 operations); Settings → Journaling (explainer, capture settings, intake sources with a wizard, setup guides with Markdown download, masked address with audited reveal and MFA rotation, health and 7-day counters, pause/resume/disable); the Archive menu (Search, Retention and lock with the moved Immutability and keys and Access settings tabs, Legal holds, eDiscovery, Access audit).
- **Local:** `JOURNAL_INTAKE_DOMAIN` (`journal.gateway.test`) and `JOURNAL_INTAKE_ADDRESS_SECRET` (api only) in `.env` (section "Journal intake and archive dedupe (step 8.6)" of `.env.example`); stack suite `tests/integration/journal-intake.test.ts`, Playwright `journaling.spec.ts`, `archive-split.spec.ts`, `archive-only.spec.ts`.

**Release note: archive access changed (ADR-0089).** Reading archived mail now needs an archive role, assigned explicitly and audited:

- **Existing organization administrators keep their archive access**: the migration `20261120053633_journal_intake` gave each of them the new **Compliance Officer** role (audited `rbac.archive_access_migrated`), so nothing changes for them.
- **New organization administrators** (created after this release) manage journaling but **cannot search or read archived mail** until someone with user management assigns them, or a colleague, the Compliance Officer role (or Compliance Auditor) — from a signed-in session with MFA, never with an API key, and never to themselves (another administrator must do it); the portal asks for a confirmation and the assignment is audited (`rbac.archive_access_granted`) and listed under Archive → Access audit.
- **Read-only users, platform administrators and custom roles that hold only `archive:read` lose archived-record detail** (`GET /archive/messages/{id}` and its journal and security views now need `archive:search`); they keep the archive configuration and status pages.
- New permissions `journal:read` and `journal:manage` (IT and mail administrators); organization admins and domain admins manage journaling.

## Account takeover detection (step 8.4)

Compromised-account detection over what the gateway observes itself ([design and verification record](docs/plan/steps/24-account-takeover-core.md), ADRs [0070](docs/architecture/adr/0070-ato-account-and-event-model.md)–[0075](docs/architecture/adr/0075-security-incident-model-shared-ato-atp.md), [contracts §32](docs/architecture/contracts.md#32-account-takeover-and-security-incidents-step-84), runbooks [account takeover](docs/runbooks/account-takeover.md) and [SMTP enforcement](docs/runbooks/smtp-ato-enforcement.md), [deployment](docs/deployment/account-takeover.md)).

- **Off by default.** The feature `ato_detection` is `false` in every plan; a platform operator enables it per organization with `PUT /api/v1/organizations/{id}/features/ato_detection` (audited). Tenants start in `monitor` mode with a 14-day learning period; high-impact automation stays off until a tenant enables it (`/ato/settings`).
- **Sources:** portal and API sign-ins (`login_audit_logs`, the trusted forwarder marks the portal channel), audited account changes, SMTP AUTH and submissions on `postfix-outbound` 587 (smtp-adapter telemetry after the reply, never on the reply path), and outbound/internal rounds (`mail.message.scanned.v1` on the lossy `ato.mail` queue plus a catch-up job). The `ato-worker` (`apps/ato-worker`, roles `detect`, `respond`, `maintenance`, `provider`; topology v13 queues `ato.events`, `ato.mail`, `ato.responses`) runs 53 explainable rules, baselines and correlation, scores accounts 0–100 with decay, opens incidents on the security incident model shared with ATP (`/incidents`), and executes or requests responses.
- **Responses:** alerts, SOC notifications and escalation run automatically (low impact); restricting SMTP sending and blocking SMTP authentication are enforced by the smtp-adapter (`550 5.7.1` at RCPT, `535` on AUTH) after the approval of a second analyst with MFA (four eyes: never the requester, nor the creator of a requesting API key), with roll-back; provider actions (revoke sessions, require MFA, suspend, remove forwarding, …) go to the connected identity provider (step 8.5, below) and count as done only when the provider confirms them. Tenant policies can hold or quarantine outbound mail of risky senders with the policy fields `ato.risk_score`, `ato.risk_level`, `ato.incident_severity`, `ato.incident_status` (stricter-only; the builder offers them in the "Account takeover" group).
- **Portal:** Account security (ATO dashboard, Accounts, Responses, ATO settings) and the generic Incidents list with the ATO panels, a print report and the shell's attention badge.
- **GeoIP is operator data.** Locations, new-country and impossible-travel rules need the MaxMind GeoLite2 City and ASN databases (Anonymous IP optional), provided by the operator through the `geoipupdate` sidecar component (`infrastructure/kubernetes/components/ato-geoip`); without them those rules are honestly `unavailable`. The local Compose `ato-worker` mounts the committed **synthetic** test databases (documentation ranges only, `ATO_GEOIP_ALLOW_DOCUMENTATION_RANGES`, refused outside `local`/`ci`).
- **Local `.env`:** `RECONCILE_QUEUES` must include `ato.responses` (the event-relay reconciles the provider response queue); `.env.example` and Compose carry it, but an existing local `.env` keeps its own value — add `ato.responses` by hand when upgrading. `NOTIFY_ATO_PLATFORM_SOC_EMAIL` (notification-worker) is the platform SOC mailbox of critical ATO incident alerts; empty = off. The other ATO keys are in the `.env.example` sections "Account takeover (ATO) detection" (worker, api) and "Account takeover telemetry and enforcement" (smtp-adapter).
- **Not in 8.4:** the Microsoft 365 / Google Workspace adapters and provider-confirmed actions (built in step 8.5), real GeoLite2 data (operator), Grafana dashboards (10.3), plan defaults for `ato_detection` (product owner, after calibration).

Protection **without an MX change** for Microsoft 365 and Google Workspace tenants ([design and verification record](docs/plan/steps/35-api-mode-protection.md), ADRs [0098](docs/architecture/adr/0098-protection-modes-and-detect-mode-copies.md), [0099](docs/architecture/adr/0099-mailbox-access-consent-and-custody.md), [0100](docs/architecture/adr/0100-api-mode-intake-mailbox-worker.md), contracts §36, [runbook](docs/runbooks/api-mode.md), [deployment](docs/deployment/mailbox-worker.md), [mail flow](docs/architecture/mail-flow.md#protection-modes-inline-api-hybrid)):

The add-domain wizard starts with a _Protection mode_ step; modes change on the domain and organization pages with a reason (audited). Every provider call is budgeted per tenant and honours `Retry-After`.

## API-mode remediation (step API-2)

Post-delivery remediation inside Microsoft 365 and Google Workspace mailboxes, with restore through the quarantine ([design and verification record](docs/plan/steps/36-api-mode-remediation.md), ADRs [0101](docs/architecture/adr/0101-api-mode-remediation-policy-and-mailbox-actions.md), [0102](docs/architecture/adr/0102-mailbox-located-quarantine-entries-release-as-restore.md), contracts §37, [runbook](docs/runbooks/api-mode.md#remediation-step-api-2), [quarantine runbook](docs/runbooks/quarantine.md#mailbox-located-entries-step-api-2), [deployment](docs/deployment/mailbox-worker.md#remediation-step-api-2)):

- **Remediation policy** per organization with per-domain overrides (_Mailbox protection → Remediation_): ordered rules over verdict, risk level, score and hard blocks → move to the gateway's **hidden quarantine folder** (Graph) / hidden label (Gmail), move to **Junk**, **tag** (category / label), **soft delete** (recoverable) or hard delete. Default **P1**: high-confidence malware and phishing (a hard block or level `critical`) go to the quarantine folder, other malware/phishing and suspicious/BEC mail is tagged, spam and DLP are left to the provider, nothing is hard-deleted. Presets **Detect-only start** (recommended for new tenants: decisions recorded as `simulated`, no mailbox change) and **Strict** (P1 + spam to Junk). Decisions use the scan verdict and risk of each copy; tenant policies (DLP, BEC, custom rules) are not evaluated on copies yet (product-owner decision).
- **Execution** by the mailbox-worker's new `remediate` role, after delivery (seconds to a minute after the verdict): idempotent (one action per copy, action and generation), budgeted per tenant together with the feeds, paused on `Retry-After`, retried with back-off, audited (`api_mode.remediation_executed`), per-connection **Pause remediation** switch. Hybrid copies the inline path already decided are never remediated automatically. Hard delete needs the platform setting `API_MODE_HARD_DELETE_ENABLED=true` (off) and an explicit tenant rule; Gmail falls back to Trash.
- **Restore through the quarantine.** Quarantine-folder, Junk and soft-delete moves appear in the existing **Quarantine** pages as **mailbox-located entries** (Location column and filter); _Restore to inbox_ uses the existing release flow, approvals (a hard block needs a second approver) and end-user self-service, and the worker moves the message back to the Inbox — no redelivery. Tags are removed from the detection (_Remove tag_). History tab with retry, detection actions (_Remediate…_, _Restore_), remediation tiles and health checks (`remediation.failures_1h`, `.backlog`, `.access`, `.paused`) on the Coverage tab.
- **Not in API-2:** clawback of late verdicts, manual search and purge, internal mail, the report mailbox and assistant write tools (API-3); restoring to the original folder (always the Inbox); changes to the add-domain wizard or domain page and tenant policy evaluation on copies (deferred by the product owner). **Live Microsoft 365 / Google Workspace tenant tests, CI and a Kubernetes apply are pending.**

## AI assistant (steps AI-1 to AI-6 and AI-R)

Chat-based management in the admin portal ([docs/assistant](docs/assistant/README.md); design and verification records [AI-1](docs/plan/steps/28-ai-chat-management.md), [AI-2](docs/plan/steps/29-ai-chat-confirmations-mail-writes.md), [AI-3](docs/plan/steps/30-ai-chat-identity-tenant-admin.md), [AI-4](docs/plan/steps/32-ai-chat-security-operations.md) and [AI-5](docs/plan/steps/33-ai-chat-compliance-integrations.md), ADRs [0091](docs/architecture/adr/0091-assistant-architecture-loopback-tools.md)–[0094](docs/architecture/adr/0094-assistant-conversation-storage-retention-audit.md), [contracts §35](docs/architecture/contracts.md)). AI-1, AI-2, AI-3, AI-R ([design and verification record](docs/plan/steps/31-ai-chat-reports.md), [ADR-0095](docs/architecture/adr/0095-assistant-reports-native-tools-static-html-email.md), contracts §35.3), AI-4, AI-5 (contracts §35.5) and AI-6 (contracts §35.6) are committed: the program is complete; CI, a cluster apply and a test against a real LLM provider are pending.

- **What it is.** An "Ask AI" panel in the portal header (`Ctrl/Cmd+J`) and the full-screen `/assistant` page. The api's `assistant` module sends the conversation and the user's permitted tool catalogue to the configured LLM provider; every tool is one existing `/api/v1` operation (generated from `docs/api/openapi.json`, [capability matrix](docs/assistant/UI_TO_CHAT_CAPABILITY_MATRIX.md)) executed by a loopback HTTP call into the api's own pipeline with the user's own bearer token, so permissions, tenant scope, MFA, rate limits, masking and audit are exactly the portal's. Results come back as tables, key-value and chart cards built from the real API response, with links to the portal pages.
- **Scope:** AI-1 enables 174 read tools (every eligible read operation). AI-2 adds **action confirmations** and 35 tools for mail operations (209 enabled in all): 31 writes on policies, quarantine, held messages, recipient suppressions and saved views, and 4 side-effect-free policy tools (validate, test, dry runs). The model can only _propose_ a write; the user sees a server-authored confirmation card (summary, risk, impact, warnings) and the write runs only when they confirm it there, bound to the exact stored request by a digest and a single-use token the model never sees; high-risk writes also ask for the password and authenticator code ([ADR-0093](docs/architecture/adr/0093-assistant-action-confirmation.md), [contracts §35.1](docs/architecture/contracts.md#351-confirmations-step-ai-2)). AI-3 adds 47 **identity and tenant administration** writes (users, roles, departments, API key revocation, domains, notifications, organization settings and the non-critical platform organization tools, scan settings, SMTP connectors and webhooks without their secrets) and the read `GET /api-keys/{id}` (257 enabled tools: 179 reads, 78 writes). Every role and permission change re-authenticates; changes that redirect mail, events or sign-in mail or weaken MFA escalate to high risk; nobody changes their own account, roles, MFA or sessions through chat, and the assistant cannot turn itself on or off or change who configures it (proposal guards, "Not allowed in chat"); the api's no-escalation rules stay the authority ([contracts §35.2](docs/architecture/contracts.md#352-identity-and-tenant-administration-tools-step-ai-3)). Writes of the security-operations and compliance modules came in AI-4 and AI-5. Credential ceremonies, creating, showing or rotating credentials, secret-returning operations, previews, downloads, reveal and critical actions stay portal only. No email body or attachment is ever sent to the model or stored.
- **Reports in chat (AI-R).** "Generate a security report" (last 24 hours, 7 days, 30 days or an explicit window; optionally some sections) makes the model call the **native tool** `report_generate` (`report:read`): the api reads the existing report, quarantine-summary and ATO operations through the loopback with the user's own token (sections the user cannot read are omitted, never requested), renders a self-contained dashboard-style HTML report with static SVG charts, no script and no link, stores it in the mail bucket (`org/<org>/assistant/report/…`, metadata in `ai_chat_reports`) and shows it in a sandboxed iframe with "Open full size" and "Download HTML". "Send this report to my email" calls `report_send_email`: a `medium` confirmation card; the server allows only the user's own address, active users of the organization and addresses of its verified domains (anything else refused, no card), with daily limits; the confirmed send writes `ai_chat_report_deliveries` and the event `assistant.report.email_requested.v1` (topology **v15**), and the notification-worker mails the stored HTML (body and attachment, plus a text part) through `postfix-notify`. 259 enabled chat tools (180 reads, 79 writes) of 423 operations plus the two native tools. New keys (`.env.example` section "AI assistant reports (step AI-R)", no secret): `ASSISTANT_REPORTS_ENABLED`, `ASSISTANT_REPORT_EMAIL_ENABLED`, `ASSISTANT_REPORTS_PER_USER_PER_DAY` (30), `ASSISTANT_REPORT_EMAILS_PER_USER_PER_DAY` (10), `ASSISTANT_REPORT_EMAILS_PER_TENANT_PER_DAY` (50), `ASSISTANT_REPORT_MAX_HTML_BYTES` (524288) for the api and `NOTIFICATION_REPORT_MAX_HTML_BYTES` (2097152) for the notification-worker (which now reads the mail bucket: `S3_*`).
- **Security operations in chat (AI-4, committed `3f19349`).** 64 more writes behind the confirmation card and 2 side-effect-free reads for DLP, BEC, risk-scoring profiles, incidents, ATO triage and responses, ATO settings and IdP integrations, plus platform-only threat intelligence, rescans, scan training and dead-letter replay (329 enabled tools: 186 reads, 143 writes). **Four eyes in chat:** the requester of an ATO response (or the creator of the requesting API key) can never approve or reject it; another responder with an MFA session can. Every change that weakens detection needs password + TOTP. The step also fixes the ato-worker's database handling (transient errors deferred by seconds; pool keys `ATO_DATABASE_CONNECTION_LIMIT` and `ATO_DATABASE_POOL_TIMEOUT_SECONDS`). Design and record: [note 32](docs/plan/steps/32-ai-chat-security-operations.md).
- **Compliance and integrations in chat (AI-5, committed).** 25 more writes behind the confirmation card for archive settings and retention policies, capture retry, journaling settings and intake sources (non-secret fields), eDiscovery cases, searches, review tags, exports (the file is downloaded only in the portal) and case holds, and provider connections guided by their wizard, plus the mail-flow preview and the new read `GET /archive/capture-issues/{messageId}`: every planned tool is enabled (356 enabled tools: 188 reads, 168 writes). Shortening retention, delete-on-expiry, changing which mail a policy matches, turning capture off or replacing its settings, and pausing or loosening an intake source need password + TOTP; legal-hold release, disposal and key rotation stay portal only; the mail-flow impact token is filled by the server, never by the model; a journal intake address is never revealed through chat. Design and record: [note 33](docs/plan/steps/33-ai-chat-compliance-integrations.md).
- **Hardening and operations (AI-6, committed; the last step of the program).** Design and record: [note 34](docs/plan/steps/34-ai-chat-hardening-operations.md), [ADR-0096](docs/architecture/adr/0096-assistant-async-report-jobs-session-job-token.md), [ADR-0097](docs/architecture/adr/0097-assistant-provider-routing-tenant-keys-pseudonymization.md), [contracts §35.6](docs/architecture/contracts.md#356-hardening-and-operations-step-ai-6), topology v16. An **AI administration** page (`/assistant/admin`): usage and estimated cost per user and day, the effective limits, an optional per-user daily token budget, the data-sharing level, the optional **tenant-supplied provider key** (off platform-wide by default; Anthropic or OpenAI; probed, encrypted with its own key, write-only) and the users' **feedback** (thumbs up/down with a reason and an optional comment under each answer). A **metadata-only conversation audit view** for `audit:read` (turns, tool calls, confirmations, reports, ratings; never message text: conversations stay private). **Search** in one's own conversations. The **`pseudonymized`** data-sharing level replaces e-mail addresses, IPs, domains and person names in known fields by stable placeholders before anything reaches the model and maps them back in the answer (names in free text are not detected). Reports longer than seven days are generated **in the background** (outbox → RabbitMQ `assistant.reports` → the `api-assistant` consumer, with a 5-minute GET-only token of the user's own session) and appear in the chat when ready. A **secondary provider** (`ASSISTANT_FALLBACK_PROVIDER`, off by default) takes over when the primary's breaker opens. ## Microsoft 365 and Google Workspace connectors (step 8.2)

Microsoft 365 (Exchange Online) and Google Workspace (Gmail) as mail platforms behind the gateway ([design and verification record](docs/plan/steps/25-m365-google-connectors.md), ADRs [0076](docs/architecture/adr/0076-provider-integration-framework.md)–[0081](docs/architecture/adr/0081-provider-mail-flow-loop-prevention-and-failover.md), [contracts §33](docs/architecture/contracts.md#33-provider-integrations-step-82), [deployment](docs/deployment/provider-integrations.md), [runbook](docs/runbooks/provider-integrations.md), customer guides [Microsoft 365](docs/integrations/microsoft-365.md) and [Google Workspace](docs/integrations/google-workspace.md)).

- **Read-only access, never a change in the customer's tenant.** A connection gets read-only access through Microsoft admin consent (OAuth2, signed single-use state) or Google domain-wide delegation, or a customer-owned app secret / service account key (encrypted with `PROVIDER_CREDENTIAL_ENCRYPTION_KEY`, decrypted only by the `integration-worker`, never shown again). Every customer-side change is a step of a **generated, customer-specific setup guide** (PowerShell, DNS values, Admin console steps) that the administrator applies and attests.
- **Explicit authorization for gateway-side changes.** Inbound destinations, the provider relay and activation change only through preview → impact token → apply with a typed confirmation, by a user holding `integration:manage` and `domain:routing_manage` / `connector:manage`; every change is audited.
- **Mail flow:** inbound uses the step 2.3 destination presets; outbound and internal mail arrive on the existing relay listener as a `provider_relay` connector and are accepted only from the provider's published ranges, for a linked sender domain, over TLS, with **tenant proof** at ingestion (Microsoft tenant header + aligned DKIM, Google fresh aligned non-replayed DKIM), else `550 5.7.26` (ADR-0078). Microsoft 365 internal routing uses a per-connection route token against loops (ADR-0081). Null-sender mail is refused on the relay.
- **Validation and health:** the `integration-worker` verifies grants, checks domains in the provider tenant, runs SMTP probes (never `DATA`) and probe-address validations, evaluates health periodically and emits `integration.health_changed` webhooks and `integration_unhealthy` alerts. The mail path never calls a provider API.
- **Portal:** Integrations → Microsoft 365 and Google Workspace (connections, the setup wizard with server-computed steps, health, validations, setup guide with Markdown download, settings and disconnect), the admin-consent callback page, and the read-only provider relay connectors on Mail servers → SMTP connectors.
- **Local:** the Compose `provider-fake` (profile `smtp-test`) stands in for Microsoft and Google; `PROVIDER_ALLOW_HTTP_ENDPOINTS=true` and `PROVIDER_EGRESS_EXTRA_RANGES` are refused outside `local`/`ci`. The seeded egress range snapshot is **not authoritative**: operators import current ranges with `node apps/integration-worker/dist/cli/egress-import.js` before enabling outbound relay.
- **Not in 8.2:** any write access to customer tenants (§15 Q5), Exchange configuration reads, null-sender relay, automatic egress-range fetching, customer certificate credentials, identity-provider telemetry and ATO actions (step 8.5). **Live verification against real Microsoft 365 and Google Workspace test tenants is pending** (verified against the local simulators only).

## Engineering rules (short version)

- Strict TypeScript, ESLint, Prettier. No `any`, no `console`.
- No business logic in controllers. No credentials in code or git.
- Apps never import each other. Shared code goes through `packages/*`.
- The tenant comes from authentication or the mail connector, never from headers. Deployment mode is configuration, never a code branch.
- Consumers are idempotent (`processOnce`). Events carry ids and S3 keys, never message bodies.
- Every schema change ships with a reviewed migration.
